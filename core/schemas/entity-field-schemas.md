## 1. Purpose & Relationships

This document enumerates, **per entity**, the exact field types, required-vs-optional status, cardinality, default value, cross-entity reference (`references:`), and the numbered **V-style validation rules** (with enforcement level) that govern a well-formed record. It is the G2 layer of the project-data-architecture initiative: G1 (`project-entity-model.md`) froze *what fields exist*; this doc specifies *how they validate*.

It is **DATA-centric** and derives mechanically from the FROZEN G1 surface:

| Layer | Doc | This doc's relationship |
|---|---|---|
| Conceptual (derivation source) | [`project-entity-model.md`](../disciplines/project-entity-model.md) | **transcribed** — field lists, Core schema, Axis-1 machines, owning-agent triplets are copied verbatim; this doc adds validation, never redefines a field |
| Persistence dialect | [`schemas/frontmatter-schema.md`](frontmatter-schema.md) | **referenced, never re-listed** — 7 MVP types, `RelEdge` schema, Domain A/B/C, Artifact Type Taxonomy are cited by pointer (duplicate-source-discipline) |
| Pattern template | [`schemas/project-schema.md`](project-schema.md) | structural skeleton — §3 mirrors its V1–V12 rule-table style; §6 mirrors its worked-example-with-trace; §7 mirrors its §5.2 failure-handling |
| First downstream consumer | RAID-Log machine-schema | consumes the **FREEZE-GATE RAID Item surface** ([§3.6](#36-raid-item-raid) Tables A–F) — every RAID field is fully typed/levelled here, so the consumer needs **zero** `[ASSUMPTION–CONFIRM]` interpretation |

**Boundary axiom (inherited from G1).** A logical entity is a *data record*; the file(s) that persist it are a separate concern. This doc specifies the validation *constraint + level + on-unresolved disposition*; it does **not** specify the physical resolver query (index lookup / `grep` / graph walk) — that is **G3/G4's physicalization**. The `references:` column declares the FK; the [§4](#4-cross-entity-consistency-rules-x-rule-table) X-rule table is the QA-enforceable checklist; the resolver is a **logical contract only**.

## 2. Enforcement-Level Taxonomy

`project-schema.md` §5 has exactly **one** enforcement level (`structural (auto)`) because `PROJECT.md` is a single self-contained file — no V-rule ever needs a second record. The 18-entity model is a **graph**: `RAID Item.owner_person_id` is meaningless without resolving a *Person* record. A binary taxonomy cannot express "deterministic but cross-record." The frozen 3-level taxonomy (D2, transcribed verbatim):

| Level | Name | Decidable from | Enforcement surface | `project-schema.md` analogue |
|---|---|---|---|---|
| **L1** | Structural / intra-record | the single record alone | schema-parse / linter (auto) | = their `structural (auto)` (V1–V12) — exact inheritance |
| **L2** | Referential / cross-record | the record **+ the entity graph** (resolve a typed reference to another entity) | entity-graph resolver (auto; **logical contract — physical resolver = G3/G4**) | *none* — net-new dimension the graph forces |
| **L3** | Judgment / manual | semantic assessment (not data-decidable) | agent-recommend → operator-confirm | implied by their §5.2 "judgment" mention; here made first-class |

**Discriminator rule (so Engineering/QA never guesses a level):** *If the rule can be checked with grep/regex on one record → **L1**. If it requires resolving `references:` to another entity → **L2**. If it requires reading meaning ("is this actually a Risk vs an Issue?") → **L3**.* Every V-rule below carries exactly one level tag + an `[AC-n]` traceability annotation (the `project-schema.md` `[AC-R2]` pattern).

**On-unresolved disposition (frozen enum — applies to every L2 rule).** Each L2 rule declares `on-unresolved ∈ {BLOCK-WRITE, WARN-HEALTH, DEFER-G8}`:

| Disposition | Meaning | Posture analogue |
|---|---|---|
| `BLOCK-WRITE` | the referencing record is malformed — refuse the write | `project-schema.md` §5.2 refuse-output posture |
| `WARN-HEALTH` | orphan surfaces in a health-check report, not a hard block | `frontmatter-schema.md` "relationship target resolves" checklist posture |
| `DEFER-G8` | referential lifecycle (e.g., cascade-on-delete) is a G8 automation concern — declared here, mechanism deferred | boundary-axiom WHAT/HOW split |

> **Dangling-reference-on-delete is `DEFER-G8`** ([§4](#4-cross-entity-consistency-rules-x-rule-table) X-08). Deleting a Person that RAID Items reference is **not** blocked by this layer — that is lifecycle automation (G8), not schema validation. This layer declares the constraint; it does not over-reach into G8 scope.

### 3.0 Core V-rule set (inherited by all 19)

Every entity carries the 7 Core fields (`project-entity-model.md` §3, Frozen Artifact 2). ### 3.0b D4 — per-entity V-rule generation rule

Engineering does **not** free-author 17×5 rules. The frozen surface mechanically generates the rule floor (D4, transcribed):

- **From Entity Core (Frozen Artifact 2):** the 7 V-CORE rules above (6 presence/type + `created_date` not-future + Axis-1 membership + `relationships[]` L2). **Core alone yields ≥7 rules → AC-2's ≥5 floor is satisfied by construction.**
- **From per-entity fields (Frozen Artifact 3):** each `✅` field → 1 L1 presence rule · each `enum` → 1 L1 membership rule · each `ref`/`typed-ref` → 1 L2 `references:` rule (with `on-unresolved`) · each `date` → 1 L1 ISO + ordering rule.
- **Negative tests (≥2/entity):** generated **1:1 from rules** — each L1 enum rule → 1 NT (out-of-enum value); each L2 ref rule → 1 NT (unresolvable id). The generation rule *is* the AC-3 spec; rules are **derived, not interpreted** (this structurally retires the prior Milestone Charter R1).

> **House style (from the FROZEN RAID exemplar).** Per-entity V-tables are *curated*: they enumerate the discriminating rules (Axis-1 membership, each entity-specific field, each FK, each date, conditional tightenings) + `created_date`. The 6 Core presence rules (V-CORE-01..02, 04, 05) are inherited (§3.0), not re-listed. RAID Item (§3.6) is transcribed **verbatim** from the frozen Tables A–F (Option-A-amended) — it sets the house style and keeps its own self-contained numbering.

### 3.0c External-identity field group (optional; adopted per-entity)

The **external-identity group** is carried by an entity record that **mirrors** an element authored in another system. Per [ADR-162](../ADRs/ADR-162-system-of-record-per-mirrored-element.md) a mirrored element's system of record is the system in which it is authored; these three fields record *which* system that is and *under what key*, so the rule is applicable per record. The group is **optional in whole** — absence means the record is not a mirror, which is the correct and common state. It is **defined here once and not re-listed per entity** (duplicate-source-discipline, per §3.0); each adopting entity's §3.N declares its adoption. **Adopting entities: Work Item (§3.18), RAID Item (§3.6).** The roster is unchanged at 19 and the Entity Core (§3.0) is untouched — this is a field-list amendment, not a Core-field or roster change.

| Field | Type | Req | Card | Default | references: | Notes |
|---|---|---|---|---|---|---|
| `source_system` | enum | ⚪ | 1 | — | — | the system that **authors** this element, i.e. its system of record under [ADR-162](../ADRs/ADR-162-system-of-record-per-mirrored-element.md). Value domain = the `source_system` enum in [`frontmatter-schema.md`](frontmatter-schema.md) § Category 3 — **referenced, not restated**. **Dialect projection:** `c3-external-sync-path-b.md` names this same value `source_adapter` in the poll snapshot; that is a *view of* `source_system`, **NOT a separate field** (the same relation as `RAID_ID`→`id`, §3.6) |
| `external_id` | string | ⚪ | 1 | — | — | the record's key **in `source_system`** (a Jira key, a GitHub issue number, a Smartsheet row id). Deliberately **`string`, not `typed-ref`**: the target is outside the entity graph, so it declares no FK and is outside §4's `ref`/`typed-ref` coverage population. **Opaque — never parsed**; a deep link is *rendered* from `(source_system, external_id)` plus the project's connector keys ([`project-schema.md`](project-schema.md)), never stored |
| `mirrored_date` | ISO `YYYY-MM-DD` | ⚪ | 1 | — | — | when the local copy was last refreshed from `source_system`. The local-side recency anchor ADR-051 Decision 2 and [ADR-162](../ADRs/ADR-162-system-of-record-per-mirrored-element.md) element **E2** compare against. Day-grain, matching the entity layer's `_date` convention and the platform's business-day staleness unit; **not** `_at` (that form is reserved for machine surfaces such as the c3 snapshot's `polled_at`) |

**V-rules — inherited by the adopting entities only** (derived by the §3.0b D4 generation rule: 1 enum ⇒ 1 L1 membership rule; 1 date ⇒ 1 L1 ISO + ordering rule; 1 conditional tightening):

| ID | Rule | Level | on-unresolved | Blocks | AC |
|---|---|---|---|---|---|
| **V-EXT-01** | `source_system`, if present, ∈ the [`frontmatter-schema.md`](frontmatter-schema.md) § Category 3 `source_system` enum | L1 | — | schema parse | AC-2 |
| **V-EXT-02** | `external_id` present ⟹ `source_system` present — an external key with no naming system is unresolvable and cannot render a link | L1 | — | schema parse | AC-2 |
| **V-EXT-03** | `mirrored_date`, if present, matches `^\d{4}-\d{2}-\d{2}$` ∧ ≤ today ∧ `external_id` present | L1 | — | schema parse | AC-2 |

**Negative tests (1:1 from rules):** **NT-EXT-1** `source_system: slack` → **V-EXT-01 FAIL** (out-of-enum). *Control:* `source_system: jira` → PASS. *Specificity:* all three fields absent → PASS (the group is optional in whole). · **NT-EXT-2** `external_id: PROJ-123` with `source_system` absent → **V-EXT-02 FAIL** (unqualified external key). *Control:* the same record with `source_system: jira` → PASS.

> **Inheritance is conditional, unlike §3.0.** V-CORE-01..07 are inherited by all 19; V-EXT-01..03 are inherited **only** by the entities in the adoption roster above. A non-adopting entity carrying these fields is malformed. Because these rules are *inherited*, they are **not** counted in any §3.N in-section rule total — the same treatment V-CORE-01..07 receive, which is why no in-section rule count moves with this amendment.

> **Asymmetry with the Project health group (§3.1), stated because both ship in one pass.** `health_derived_date` ⟺ `health_rag` is a **biconditional** (V-PRJ-11): an undated derived value cannot be told from a stale one, so both directions are malformed. `mirrored_date` ⟹ `external_id` is **one-way** (V-EXT-03): an as-yet-unrefreshed linkage is legitimate — recorded at intake, first poll not yet run — and forcing a date at linkage would force a fabricated one.

## 7. Validation-Failure Handling

Transcribes `project-schema.md` §5.2 to the entity layer. An entity record that fails **any** L1 or L2 (`BLOCK-WRITE`) assertion is **malformed**. A consumer skill (per the [§5](#5-consumer-matrix-field-granularity) matrix) encountering a malformed record MUST:

1. **Refuse** to produce entity-parameterized output from that record.
2. **Surface** the specific failing rule ID (`V-<CODE>-NN` or `X-NN`) + the field + expected-vs-actual to the operator.
3. **Route** the record for correction via its `owning_agent` (the maintainer in the §5 matrix; new records via the creator) or via `file-router` re-classification.

Skills MUST NOT silently work around a validation failure by defaulting a field, dropping a reference, or substituting an archetype. **Silent default / silent FK-drop is a named failure mode** — same posture as `project-schema.md` §5.2 (PROC-2 base-archetype blind fallback / PROC-3 block-skip) and `methodology-parameterization-v1.md § Failure Modes`.

**Disposition by level:**

| Failing rule level | on-unresolved | Handling |
|---|---|---|
| L1 | — | **BLOCK** — record malformed; refuse output, surface rule ID, route to repair (steps 1–3) |
| L2 | `BLOCK-WRITE` | **BLOCK** — same as L1; the referencing record is malformed (dangling FK) |
| L2 | `WARN-HEALTH` | **WARN** — record accepted; orphan logged to a health-check report (not a hard block) |
| L2 | `DEFER-G8` | **DECLARE-ONLY** — constraint recorded; enforcement is G8 lifecycle automation, not this layer |
| L3 | — | **AGENT-RECOMMEND → OPERATOR-CONFIRM** — surface the semantic concern; do not auto-block |

> **Boundary discipline.** This section specifies *what happens on failure* and *who repairs*. It does **not** specify the physical detector (linter binary, index query, CI hook) — that is G3/G4/G8 physicalization. The `on-unresolved` enum is the frozen logical contract the downstream resolver implements.
