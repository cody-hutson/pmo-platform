## 1. Purpose

`platform-config.toml` is the platform-BEHAVIOR configuration surface — the parameterized platform-behavior choices the pipeline tunes over time. It opened with four categories (bundling frame, release-size target, release-class default, relationship-mapping tuning) and has accreted further behavior categories since, each as its own dedicated section rather than by extending an existing one: calibration accrual, failure-mode detector thresholds, progressive-rollout log placement, spoke-runtime model posture, security-hook master activation, and git-native release-automation toggles. The § 3 field table below is the authoritative enumeration — this paragraph orients, it does not enumerate. This schema is the canonical specification of the surface's shape: what fields exist, their types, allowed values, defaults, calibration policy, consuming surfaces, and the cutover SHA recorded when a field's default changes.

It is DISTINCT from [`operator.toml`](../config/operator.toml.template), the operator-ENVIRONMENT / IDENTITY surface (identity, paths, `[adapters]` host-selectors, `[methodology].default_delivery_approach` — all named by ADR-017 §S2 as operator.toml concerns; `chmod 600`; depersonalization token vocabulary). The split rationale is recorded in [ADR-022](../ADRs/ADR-022-platform-config-vs-operator-toml-split.md). This schema relocates nothing from operator.toml — the categories below are NEW platform-behavior categories ADR-017 §S2 did not enumerate.

## 2. Layer model

| Layer | Carries | Storage | Git status |
|---|---|---|---|
| **Layer 1** | Field SCHEMA (this doc) + global DEFAULT values; read **in place from the clone** — the package installs no runtime copy of the template | [`core/config/platform-config.toml.template`](../config/platform-config.toml.template) | tracked (ships) |
| **Layer 2** | Per-tier override VALUES only | individual: `~/.config/pmo-platform/platform-config.toml` `[overrides]` · portfolio: `projects/_config/PORTFOLIO.md` frontmatter `platform_config:` · program: `projects/<Program>/_config/program-config.toml` · project: `projects/<Project>/PROJECT.md` frontmatter `platform_config:` | git-ignored (operator-instance) |

**Setting your own value: the individual rung is the XDG file, and there is no installed template to edit.** An operator's own value goes in `${PMO_PLATFORM_CONFIG_ROOT:-$HOME/.config/pmo-platform}/platform-config.toml` under `[overrides]` — the rung-5 individual surface, which per § 4 wins over every other rung. That file is Operator-instance: the package never creates it and never regenerates it, so an edit there is durable across updates. The Layer-1 template is read from the clone and is not installed anywhere, so there is no runtime copy of it to edit; editing the tracked template instead is a Track A governed change to the global default for every install, not a personal override.

No per-tier operator value ever lands in a tracked file. This mirrors the `delivery_approach` precedent exactly: the enum + validation is Layer 1 ([`project-schema.md`](project-schema.md)); the value (`delivery_approach: Kanban`) is Layer 2 (PROJECT.md frontmatter).

**`[git_release_automation]` resolves on 2 rungs, not 5 — a deliberate narrowing, recorded because the default reading of § 4 below is the full cascade.** The three toggles resolve from the global rung (the in-repo template) and the individual XDG rung (`~/.config/pmo-platform/platform-config.toml`) only; the portfolio, program and project rungs are semantically inapplicable, because the fact configured here is PLATFORM-scoped (one release pipeline per install) rather than per-portfolio or per-project. The narrowing follows the in-file precedent of `core/hooks/lib/master-enable.sh`, which narrows to the individual rung for the same reason and states so in-file. Re-implementing rungs 2–4 here would additionally shadow `resolve_platform_config`, the single 5-rung implementation in the repo.

**`[git_release_automation]` absent-key contract — the default is an in-code constant, not a template read.** An absent `platform-config.toml`, an absent `[git_release_automation]` section, an absent key, an empty value, and any non-boolean value ALL resolve to `off`, from a terminal in-code constant in `release/tools/lib/platform-toggle.sh`. Only the literal `true` (in any case) enables a toggle. This is load-bearing rather than belt-and-braces: the runtime `platform-config.toml` does **not** exist on a stock instance, so a template default alone never reaches a consumer, and an install that never receives the file must behave identically to a fresh install with every toggle off. The always-on facets of the same capability (feature-branch creation + naming, PR statusing) carry no key at all — their absence from the section is the non-toggleable declaration.

**`[spoke_runtime]` effort posture — a pointer, NOT a field (by design).** The section carries the two model scalars above and **no** effort field. Effort is MAX for all spoke work per the immutable, name-agnostic model-preference directive (SSOT: the operator-memory store — the "always highest-tier model + MAX effort" directive); a stored `effort` value here would be a **shadow-SSOT** of that directive and would drift (no-shadow-SSOT invariant). The concrete chip-runtime effort lives in `~/.claude/settings.json` (`effortLevel`) as the Anthropic chip contract; the SessionStart hook VERIFIES the resolved session effort against the directive. To change effort, change the directive (governed) — there is no schema row because there is no field. This satisfies the completion-condition "the canonical file … carries a comment block pointing to the immutable behavioral directive."

**`portfolio_framework` resolves on 2 rungs, not 5 — a deliberate narrowing, recorded because the default reading of § 4 below is the full cascade.** The field resolves from the global rung (the `operator.toml` template default) and the individual rung (the operator's own `operator.toml`) only; the portfolio, program and project rungs are semantically inapplicable, because a portfolio framework governs the deployment's portfolio rather than any single project beneath it, and a per-project override has no stated use case at v1. **This is why no [`project-schema.md`](project-schema.md) validation rule is owed for the field**: the project rung is not in its resolution set, so there is no project-level field to validate. Tightening later — admitting a portfolio or project rung — is additive. The narrowing follows the in-file precedent of `[git_release_automation]` (global + individual only) and of `core/hooks/lib/master-enable.sh` (individual only).

**`portfolio_framework` is delivered `opt-in`, and that is load-bearing.** Per the delivery convention in [`operator-toml-schema.json`](../config/operator-toml-schema.json), an `opt-in` key is documented by the template but never written by the generator and never touched by the reconciler. A deployment that does not select a portfolio framework therefore has no such key in its live `operator.toml` at all — which is what makes "resolves exactly as today" a property of the file rather than a behavior of a consumer, and keeps the key outside the live-instance coverage check's population so no operator sees a new warning. Declaring it `delivered` would emit `portfolio_framework = ""` into every operator's config on the next reconcile, and the no-observable-change property would then hold only by consumer discipline.

## 4. Resolution + fallback

The effective value of a field for a given scope is resolved by the 5-rung cascade in [`OPERATIONS.md § Platform-Config Resolution Protocol`](../governance/OPERATIONS.md): global default → portfolio → program → project → individual (most-specific wins; individual is highest precedence). The 3-level default-fallback:

1. Field set at ≥1 rung → resolve per precedence.
2. Field set ONLY at the global rung (this template) → use the default. **Common case.**
3. Field absent even from the global rung → the consumer uses its own documented hardcoded fallback and logs `[platform-config: field <F> unresolved; using consumer default <V>]`. Every consuming surface MUST declare its fallback so an absent/corrupt config never hard-fails a release.

**A section MAY narrow the rung set, and MUST say so at its rows.** The 5-rung cascade above is the default, not an invariant: a section whose configured fact is platform-scoped rather than tier-scoped resolves on the subset of rungs that carry meaning for it, and records the narrowing plus its reason alongside its § 3 rows. `[git_release_automation]` is the shipped instance (global + individual only); `core/hooks/lib/master-enable.sh` is the in-code precedent (individual only). A narrowing is never silent — an unrecorded narrowing is a defect, because the reader's correct default assumption is the full cascade.

## 5. Update governance (two-track)

Per [`OPERATIONS.md § Platform-Config Resolution Protocol`](../governance/OPERATIONS.md):

- **Track A — schema / default change (Layer 1):** editing a default in the template, adding/removing a field, changing an allowed-values set, or editing this schema = a **full governed PR** (GitHub Issue + plan + PR review per CLAUDE.md "No ungoverned changes"). This is a governance file. When a Track A change re-sets a default, record the merge SHA in the field's **Cutover SHA** column.
- **Track B — per-tier value set (Layer 2):** an operator setting a value for their own portfolio / program / project / individual scope = **no PR** (operator-instance write, like setting `delivery_approach: Kanban` in PROJECT.md). Audited by the operator's own instance history, never the platform repo.
