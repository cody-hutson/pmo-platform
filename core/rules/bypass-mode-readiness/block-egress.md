### What BLOCK-EGRESS-007 adjudicates

`-007` resolves command position at token level over quote-neutralized segments rather than matching a regex anchor. What that changes, stated as behaviour rather than mechanism:

| Property | Behaviour |
|---|---|
| **Spelling invariance** | Bare, single-quoted and double-quoted spellings of one path produce one verdict. The allowlist is matched against the resolved, unquoted path; a quoted pattern in the allowlist can never match. So do the spellings the shell itself resolves to one command word: a backslash-escaped word, an ANSI-C- or locale-quoted word, a brace group that expands to the words, a word split by a backslash-newline, a word whose letters are split by quote characters or written as adjacent ANSI-C strings, and a different letter case of `gh` or of a prefix word, which names the same program on a case-insensitive volume. The subcommand's letter case is significant (`gh` rejects `API`) and is not folded. These are read alike whether or not the scanner can tokenize the command. The rule's fast-path gate, which skips a command with no `gh` in any of those spellings, runs on every command and removes the quote characters and `$` in one linear pass, so a large command cannot hold the hook past its timeout there — past which a PreToolUse hook does not block. |
| **Allowlist scope** | The path is matched only against rows declared `gh-api-path` and rows with no scope directive — never against a row declared `host`, and never against a pattern whose first path segment carries a glob character — so a host wildcard such as `*.github.com` cannot grant a write to a path that merely ends in host-shaped text. BLOCK-EGRESS-004 is scoped the same way to `host` rows and rows with no directive. The grammar is stated in the egress allowlist's own header. |
| **Path location** | The path is found by walking flags, so `gh api -X POST <path>` and `gh api <path> -X POST` are equivalent, and the value of a value-taking flag the walk knows is never mistaken for the path, in each form `gh`'s flag parser accepts: separate (`-X POST`), attached (`-XPOST`, `-X=POST`), clustered after the boolean `-i` (`-iX POST`), and `--long=value`. A redirection among the operands is not an operand either, so `gh api -X POST >/dev/null <path>` writes to `<path>`. A value-taking flag the walk does not know, such as one a later `gh` release adds, can still take the path's place. |
| **Command position** | A write is adjudicated at every command position the rule's walk resolves — a loop body, an `if` branch, a subshell, a command substitution, a backtick, behind a `VAR=x` assignment prefix or its append form `VAR+=x`, which bash and zsh also read as an assignment word (an append whose value opens an array, a subscript and every other indirect form end the walk; a quoted assignment word is read as the assignment, because the scanner drops quote marks before a word is read, although the shell runs it as the command word, so a write behind it is recorded where nothing would run — an over-read in the strict direction), behind an I/O redirection (a redirection word and its operand are not argv words, wherever they stand, and a quoted `<` or `>` is content, never a redirection), and behind a prefix command such as `env`, `sudo`, `xargs`, `timeout`, `nice` or `stdbuf` (the hook holds the bounded list). A prefix word or the verb in a respelling the shell resolves — escaped, brace-expanded, ANSI-C- or locale-quoted, or in another letter case — is read as its plain spelling, and so is a command split across lines by a backslash-newline, except where the line after the backslash holds a `gh api` invocation of its own, which stays the command start it is. Behind a prefix command the rule does not model that command's own grammar: it looks for the first adjacent `gh` and `api` words later in the same segment, so an option that takes a separate argument (`env -u NAME`), a positional operand (`timeout 5`), an assignment only that command accepts (`env a-b=1`), an option the rule has never seen, in any spelling, and any other word between the prefix command and the verb are all passed over on the way to it. The verb is matched on its basename, so every absolute-path form is covered and an unlisted path prefix does not evade. |
| **Every invocation** | Each `gh api` in a command is adjudicated, with its own method determination. A second write cannot hide behind an allowlisted first one, and a read co-located with a write is not judged against the write allowlist. |
| **Write detection** | An explicit `-X` / `--method` write verb, **or** an implicit POST — `gh` defaults the method to POST when `-f` / `-F` / `--field` / `--raw-field` / `--input` is present, so a field flag alone is a write. Each flag is read in the separate, attached or clustered short form or the `--long=value` form `gh`'s parser accepts, and an ANSI-C-quoted method value as the shell decodes it. An explicit read method beside a field flag (`-XGET -f q=1`) is a read, as `gh` sends it. A method value that is itself escaped or brace-expanded is compared as written, so a write spelled that way is not detected. |
| **Comments** | A `#` that opens a word in unquoted text starts a comment, and the scanner treats the remainder of that LINE as quote-inert — an apostrophe in `# don't re-run` cannot desynchronize the scan, so an ordinary command carrying one is not this rule's business. Comment text is **not stripped**: a write reached through a separator inside a comment stays adjudicated exactly as the replaced matcher adjudicated it. |
| **Cannot-evaluate** | Four named causes, each with its own remediation: `not-allowlisted`, `unresolvable` (a placeholder or shell expansion in the path authority), `unparseable` (the scanner finds an unterminated quote in **command** text; a comment it recognizes cannot produce one, and a well-formed command it mis-models can — see below), `no-path`. None exits silently. |
| **Cost on a large command** | A PreToolUse hook that outlasts the runtime's command-hook timeout does not block, so what the rule costs on a large command is part of what it guarantees. Past the fast-path gate, every substitution the scanner makes — over a quoted span, a comment, a token, a physical line or the whole command — is one pass of `tr`, `sed` or `awk` in the C locale once the piece reaches a fixed bound, with output equal to the substitutions' byte for byte; on bash 3.2 a global pattern substitution costs more than linear time in the text it scans once that text carries a match for the pattern. A shorter piece keeps the substitutions, whose cost the bound keeps below the pass's own, and a pass that fails leaves the piece to them, so the text the scanner reads is the same on every path. A removal — a prefix or a suffix taken off a text — re-measures that text at every position it tries on bash 3.2, so one repeated once per step of a loop over a long text costs more than linear time too; the scanner's two loops of that kind now read a long text once. The quote walk takes the command as pieces that one `awk` pass splits at its quote characters and steps from piece to piece, never through the text left to scan; the continuation join reads a line at a time beside its mark-free twin and tests only the line it has just added, gathering the line it builds as parts joined once; and the comment and trailing-backslash tests read a long text once. The ANSI-C decode and the command-word normalization read a long body or word once as well: it is split once at its backslashes and decoded or unescaped a field at a time, where each loop stepped through the text left to read once per escape; and the basename the keep rule and the case step read from a long word is matched once, or taken from the word's last characters, rather than by a removal that retries its match at every position it could end. A shorter text keeps the code that read it before, and a walk whose pass fails reads the text that way, so what the scanner reads is the same on every path. Five more steps read their text once, with no fork: the normalization of a long brace group splits the word once at its braces and its commas and puts the group's words into the token list as slices of one expansion, where it took the words one at a time off the text left to split and read and copied them by index, which on bash 3.2 walks the array from its start; the redirection-word test steps over a long digit run or `{name}` descriptor by its length, where it removed it as a pattern; the restore of quoted operators takes the segment's tokens from one expansion of the list; the short-flag reader steps over a long run of the boolean `-i` by its length, where it took one off at a time; and the walk reads a long command word's basename from its last characters and tests it as the verb by one match, where two removals retried at every position, a cost the walk met on such a word in its upper-case or escaped spelling once the fast-path gate admitted those spellings. The look-ahead behind a prefix command tests each candidate's basename the same way, by one match, in its plain spelling and in a respelling, where a removal retried at every position; the widened fast-path gate hands it a long command word in those spellings too. So does the unparseable branch's second reader, on the first word of each piece of a command the scanner cannot tokenize. The suite holds the whole hook inside a fixed budget at 10, 20 and 40 KB, in UTF-8 and in C, on seven benign shapes — a dollar filler, a separator-dense command, one big quoted span after a long quoted comment, a redirection-dense command, a separator-dense command the scanner cannot tokenize, a continuation-dense command and a command of many short quoted spans — and at 10, 20, 40 and 80 KB on two more, a command holding one long ANSI-C span of many escapes and one whose continuation line is one long word dense with escapes, and on eleven beside a neutral twin of the same length whose long run the step does not read — a long brace group, a long digit run and a long `{name}` descriptor before a redirection, a long run of quoted operator tokens, a long short-flag cluster, a long upper-case and a long escaped command word, a long upper-case command word behind a prefix word and behind its option, and a long upper-case and a long escaped command word in a command the scanner cannot tokenize — holding each within a bound of its twin; it pins each pass byte for byte against its substitutions, pins the walk, the join, the two tests, the decode and the normalization against the code before them on a dense set of texts, and pins the five steps the same way, the walk's two basename reads, the look-ahead's two basename tests and the second reader's on the whole hook. **Not covered, and declared:** other work in the rule still grows faster than the text it reads, each part held for its own decision: expanding a brace group whose words share a long prefix or suffix, where the brace step reads the word once but the expansion it builds is the product of that text's length and the number of words; trimming a long run of blanks that opens a segment; and the unparseable branch's first reader, which steps from one verb to the next through the text left to scan on a command the scanner cannot tokenize. The timed shapes pin none of it. |

**What "behind a prefix command" covers, and what it does not.** The look-ahead is a domain test, not a parse of the prefix command's options: a table of which options take an argument fails open on the first one it omits, and the look-ahead interprets nothing it passes over. Its cost is over-evaluation: a `gh api` pair that is only text behind a prefix word is evaluated as a write — a printed command (`env X=1 echo gh api -X POST <path>`), and a heredoc body line that opens with a prefix word, several of which are also English words (`time`, `command`, `exec`, `env`, `nice`). What the rule reaches is literal adjacent `gh` and `api` words at a command position its walk resolves, with the method, fields and path it reads from the command's own text; anything else is undetermined, not covered. Known instances, not a closed list: a command carried as a string for another program to run (`bash -c '…'`, `env -S '…'`, `eval`), a command word that is a variable (`$GH api …`), a leading word outside the prefix set (`watch gh api …`), which the rule treats as the command, and spellings outside the ones the rule resolves: a command word produced by an expansion it does not perform (zsh's `=gh`, a pathname pattern, a nested, sequence, escape-bearing or all-empty brace group, an ANSI-C escape outside the decoded set), a redirection written against the word before it with no blank between them, a method value that is itself escaped or brace-expanded, a line continuation that leaves a prefix command's option argument or operand at the head of a line that also holds the verb, and arguments that arrive on standard input. Of those, the open card for this rule's unrecorded spellings owns arguments on standard input, the continuation that leaves an option argument or operand at the head of the verb's line, zsh's `=gh` and a pathname-pattern command word, and a respelled verb in an untokenizable command above the parse cap (each is admitted with no record today); every respelled write behind a prefix command, which is recorded at the shipped phase, is owned by this rule's graduation card, whose phase advance turns those records into refusals; and the remaining spellings in that list — the nested, sequence, escape-bearing or all-empty brace group, the ANSI-C escape outside the decoded set, the redirection written against the word before it and the escaped or brace-expanded method value — are owned by the open card for the unrecorded spellings as well. Every position behind a prefix command is a widening, so it follows the rollout phase described below. An invocation found only by the look-ahead, a read included, does not count as the command's first invocation, so it cannot move a later write at the head of a segment out of the day-one deny. Its `would-fire` row carries one more key, `pos` with the value `look-ahead`, which a row the head walk writes does not carry; the key says which locator found the verb, not whether the words are executed. A record written once the phase refuses — to the block log, or the warn-mode record under `.mode=warn` — is unchanged and carries no such key. The decision and its rejected alternatives are recorded in ADR-226.

**The `unresolvable` cause is not an allowlist problem, and its message says so.** `gh` resolves `{owner}` / `{repo}` at execution time from the environment, a default-repo setting, or the current remote — none of which a PreToolUse hook can see. No allowlist row can ever match such a path, so the remediation is to spell the owner and repository out in the command. Expanding them from the remote was rejected: the hook could resolve to a different repository than the command reaches, producing an allow for a repository it never adjudicated.

**Rollout is split by position, and is NOT the shared `.mode` dial.** A write is classified by the command position the shell resolves it to, not by how that position is spelled. A write at the head of a segment the replaced anchor admitted — the command's first counted invocation, with an explicit write method — is refused from day one in every spelling the rule resolves, whether or not the scanner can tokenize the command; every other position is a widening. The repairs — quote handling, the flag walk, `--`, and the respelling repairs — enforce from day one. Widenings — command position, every-invocation, implicit POST — ship in the `shadow` phase defined by the progressive-rollout convention (`core/standards/progressive-rollout-convention.md`): they evaluate, record a `would-fire` entry in `egress-warn-log.jsonl` carrying the cause class and path, and take no action. An invocation the rule resolves only through a respelling never advances the first-invocation counter, for the reason a look-ahead hit does not: it is refused on day one only when no counted invocation precedes it and it is the first such invocation, so a respelled read before a plain write leaves that write refused, stricter than its plain twin. An invocation the walk reaches only behind the append form of a prefix assignment advances neither counter, for the same reason: the shipped hook never reached it, so a read written that way before a write at the head of a segment leaves that write refused, stricter than its `VAR=x` twin, whose read is counted. **No rung can allow a case the shipped hook refuses.** The decision and its rejected alternatives are recorded in {{ADR:egress-respelling-takes-the-resolved-positions-rung}}.

Read that claim precisely, because it is narrower than it first appears. The *repairs* deliberately turn some old denials into passes — a quoted allowlisted path passing is the whole point of the change, and so are the declared precision classes the respelling repairs add: a redirection or a continuation among the operands, an ANSI-C- or locale-quoted path the shell resolves to an allowlisted one, a clustered short flag's separate value, which is no longer taken for the path, and an explicit read method beside a field flag, which is a read. So is the one the append form adds: an append-form assignment whose value ends in `gh`, ahead of the word `api`, which the shell runs as `api` with the assignment in its environment, is no longer refused as the `gh api` write the old reading took it for, and takes the verdict of its `VAR=x` spelling. What the **ladder** must never do is withhold a deny the old code already produced, and it is the ladder the sentence governs. `unparseable` sits on the enforcing side for exactly that reason: it denies at every rung, and it is raised only for a real `gh api` invocation at a command position the replaced matcher could have reached — read in every spelling the rule resolves there, and through no keyword, assignment or prefix word, so the respelled twin of a command this class refuses is refused too, a read included. Above the parse cap the feature set uses, only the plain spelling is located. So it softens no deny the old code produced. **It is not, however, free of new denies.** The deny costs nothing for a genuinely malformed command, which cannot run either. But the scanner reads some well-formed syntax as an unterminated quote — a heredoc body, an escaped, ANSI-C or nested quote, a comment it does not recognize — and there the class denies what the replaced matcher never did: a read (that matcher required an explicit write method), an implicit-POST write, or a write it had allowlisted. A wrapper, a `$( )` and a glued verb are outside that position set on purpose — the old matcher never adjudicated them, so allowing them loses no deny it produced. A genuinely malformed command there cannot execute anyway; a well-formed one the scanner mis-models executes unadjudicated and leaves no record. A line that is only text and has the shape of a quotation line — a bare `>`, one word, then a `gh api` call, as in a heredoc body — reads as a redirection before the verb, as the shell reads a command line, so a write there is refused from day one, and so is a read in a command the scanner cannot tokenize; the class is declared. So is one more over-read in the strict direction, with the root cause of the quoted assignment word in the Command position row: a backslash or a brace group inside a quoted command word, prefix word or subcommand, or an ANSI-C span that decodes to a backslash ahead of the verb, is read as its unquoted twin, because the escape and brace steps run on quote-erased text — refused at the head of a segment and recorded behind a prefix word, although the shell runs a command named with those literal characters, which does not exist, so no write is involved.

The phase is one constant in the hook; advancing or retreating it is a single edit. Flipping the shared `.mode` is **not** the instrument for this rule — that file is a cohort dial and would soften every mode-capable hook in the bundle at once.

**Reading the shadow log.** A rising `not-allowlisted` count means real writes are reaching unadjudicated paths and an allowlist row may be warranted. A rising `unresolvable` count means the opposite — agents are writing variable-bearing authority paths, and the fix is to spell them out. Conflating the two is the failure this rule was filed about. A row carrying `pos: "look-ahead"` was written for a write the look-ahead found behind a prefix command, and it may be a printed command rather than a write, so a rising count of those rows is not on its own a reason to add an allowlist row. A respelled write writes no new key: behind a prefix command it is a head-walk row or a look-ahead row like any other.

**Reading `unparseable` records.** Their `evidence` is the constant `path=unknown cause=unparseable`, so the warn-log and block-log records of this one class also carry a `features` object and a top-level `hook_build`, and they are classified by `features.shell_parse`, scoped by `features.oracle` — the parser that judged the syntax: `error` → rejected by the recorded oracle, `ok` → benign-shape (a false refusal of a well-formed command), `skipped` or `unavailable` → unclassified. An `error` record is a true positive only where the oracle's grammar is the executing shell's: the oracle is bash, the shell that runs a command may differ, and zsh accepts some commands bash rejects, so an `error` record can still be a false refusal — the residual the record names its oracle for. `features.heredoc` splits the false refusals by heredoc delimiter quoting, and reads `unavailable` when its scan could not run. Both computations are linear in the command's length and share one size cap, so neither can hold the deny past the hook's timeout. `hook_build` names the hook build that wrote the record: a record carrying `hook_build` whose features all read `unavailable` (the oracle `unknown`) is a current-build record whose features could not be computed, and one carrying `hook_build` without `features` is a current-build record whose features could not be written — neither is ever one from before the field set existed. No field carries the command's text, an offset or a length. The decision and its rejected alternatives are recorded in ADR-205.

### Allowlist row scope — who writes a row, and which rule reads it
<!-- design-artifact: flow-class=data-flow; name=egress-allowlist-row-scope; depicts=core/config/allowlists/egress-allowlist.txt,core/hooks/block-egress.sh,core/hooks/allowlist-add.sh -->

`egress-allowlist.txt` serves two match domains. A declared row is consulted only in the domain its scope directive names — `# egress-scope: host` or `# egress-scope: gh-api-path`, on the line directly above it — and a row with no directive is consulted in both, which is the behaviour every row had before directives existed.

| Producer | What it writes | Region of the deployed file | Scope the row carries |
|---|---|---|---|
| The package source, through the composition writer | every managed row, each under its own directive | MANAGED SECTION — regenerated on every update | declared |
| `allowlist-add.sh <file> '<entry>' --scope <domain>` | the directive and the entry, adjacent, before the END marker — or, when the entry is already there as a bare row, the directive directly above that row (upgrade in place) | OPERATOR ADDITIONS — preserved verbatim | declared |
| `allowlist-add.sh <file> '<entry>'` with no `--scope` | the entry alone, before the END marker, plus a notice saying how it will be matched | OPERATOR ADDITIONS | none — both domains |
| An operator editing inside the fence | rows, with or without a directive above each | OPERATOR ADDITIONS | as written |

| Consumer | Domain it asks for | Rows it consults |
|---|---|---|
| BLOCK-EGRESS-004 — the host of a curl upload | `host` | rows declared `host`, and rows with no directive |
| BLOCK-EGRESS-007 — the path of a `gh api` write | `gh-api-path` | rows declared `gh-api-path`, and rows with no directive — minus every pattern whose first path segment carries `*`, `?` or `[` |
| BLOCK-EGRESS-011 / -013 — their own single-domain files | none | every row; a directive line there is an ordinary comment |
| `allowlist-add.sh`'s duplicate check | — | the exact entry line; with `--scope`, the exact directive-plus-entry pair, and any bare copy of the entry inside the region, which it declares in place |

**Why the leading-glob exclusion holds whatever a row declares.** A host wildcard can match a path only by absorbing the whole front of it, and a query string lets any write end in host-shaped text, so a pattern that begins with a glob is exactly the shape that must never grant a `gh api` write. The exclusion keeps that true for rows with no directive, for mis-declared rows, and for an allowlist the update path has not yet regenerated. **It works in one direction only.** It keeps a glob off gh-api paths and does nothing at the host check, so a row with no directive and no `/` stays a curl host candidate — a glob such as `gist*` grants an upload to every host it matches, and a slashless literal matches its one exact string in both domains. A directive is what confines such a row. **Why a directive binds one row only.** A scope that ran on to later rows would silently re-scope a row added below it; binding the next line alone means a row's domain is always the line directly above it. **Revert safety.** A directive is a comment line, so the matcher that predates directives reads the same file exactly as it read the file before, and a revert restores the prior grant set without touching the preserved operator region. The decision and its rejected alternatives are recorded in ADR-206.
