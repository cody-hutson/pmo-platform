## `block-autonomy-ceiling.sh` (BLOCK-AUTONOMY-001..099)

| Field | Value |
|---|---|
| Hook | `.claude/hooks/block-autonomy-ceiling.sh` |
| Matcher | Bash, Write, Edit, `mcp__.*` |
| Scope | Autonomy-tier ceiling enforcement: an irreducible Tier-0 always-block floor (governance-file writes, plus cross-domain bridge writes **into** the tracked platform repository) · a mode-gated layer-discipline signal on the converse cross-domain direction · a ceiling check that blocks an action whose required Autonomy Tier exceeds the resolved `[automation].automation_level`. Composes with (does not duplicate) the destructive / fs-boundary / rm safety hooks — it adds the autonomy-tier dimension they do not gate. |
| Mode | Three postures, not two. The Tier-0 floor (`BLOCK-AUTONOMY-001`/`002`) is **always-block LIVE** — mode- AND level-independent (mirrors `block-destructive` / `block-rm-prefer-trash` permanence) for the payload-detectable classes only. `BLOCK-AUTONOMY-004` and the ceiling check (`BLOCK-AUTONOMY-003`) are gated by this hook's **OWN** mode file `.autonomy-mode` (warn / enforce / off), NOT the shared `.claude/hooks/.mode`, and both sit below the master-activation and workspace-scope gates; the hook ships **warn-mode-initial** because it gates every mutation (highest false-positive risk in the suite). Full precedence: `bypass → floor → master → scope → -004 → ceiling`. Permissive default: an unmapped action is treated at-or-below ceiling and ALLOWED. |

### Rule registry

| Rule ID | Description |
|---|---|
| BLOCK-AUTONOMY-001 | Governance-file modification (Write/Edit) — resolved path matching `CLAUDE.md`, `OPERATIONS.md`, `RELEASE_PROTOCOL.md`, `.claude/settings.json`, or any file under `.claude/hooks/` or `.claude/rules/`. **Two stages, and neither matches on basename alone.** *Stage 1 — by LOCATION:* the charter at the workspace root, the operations context anchor at `<workspace>/projects/CLAUDE.md` (installer-produced and agent-unwritable; named at its exact path, so a project's own `CLAUDE.md` one level deeper is NOT in the set), the platform checkout's own governance documents at any depth beneath `<workspace>/pmo-platform/`, and the `.claude/` security surface at the workspace root. *Stage 2 — by REPOSITORY MEMBERSHIP:* exactly the three basenames `CLAUDE.md` / `OPERATIONS.md` / `RELEASE_PROTOCOL.md` inside any working tree of **this** repository, wherever on disk that tree lives; the test is whether the tree's `.git` — a directory for a primary checkout, a one-line pointer (absolute **or** relative) for a linked worktree — resolves inside the platform checkout's git directory — `<workspace>/pmo-platform/.git`, itself resolved first (followed through a symlink or a pointer file, so a symlinked, `--separate-git-dir` or worktree-shaped checkout is recognized). The walk is the shared membership helper `lib/platform-membership.sh`, the same one the `-002`/`-004` classification and `block-draft-files.sh` use. **Read the two stages together, not composed.** Stage 1's anchors cover worktrees nested *under the checkout* and no others, so on their own they never delivered "all worktrees are covered"; a spawned session's worktree is routinely created outside the checkout, and stage 2 is what reaches it. The `.claude/` entries are **stage-1 only** — they name the *deployed* security surface and the repository tracks no `.claude/` files, so there is no worktree copy of them to reach. Outside both stages a file falls through to the normal mode- and level-dependent path: an unrelated repository's root doc, a worktree of a *different* repository, a foreign repo nested inside a platform worktree (nearest enclosing tree wins), and a loose copy in no repository at all. **`SKILL.md` is deliberately NOT in this set:** skills are owned by `block-skill-direct-edit.sh` (`BLOCK-SKILL-EDIT-002`), which can distinguish a sanctioned `pmo-skill-editor` session from a straight edit — a discrimination `always_block` structurally cannot make. Irreducible Tier-0 (operator-only per "No ungoverned changes"); always-blocks regardless of `automation_level` and without the worktree exemption `BLOCK-DESTRUCTIVE-019` carves out (governance edits are operator-irreducible regardless of cwd) |
| BLOCK-AUTONOMY-002 | Cross-domain bridge write **into the tracked platform repository** (Write/Edit) — a `projects/` cwd writing into `pmo-platform/`, detected by a pair: the target's domain and the working directory's side. The target is `pmo-platform` when it sits in any working tree of this repository, wherever on disk that tree lives — **repository membership**, through the shared helper `lib/platform-membership.sh`, the same test `-001`'s second stage applies — and `projects` only when it is under `<workspace>/projects/` and in no such tree; a target whose membership cannot be determined fails this rule closed unless it is under `<workspace>/projects/`. The working directory is on the `projects/` side when **either** reading places it under `<workspace>/projects/` — its payload spelling, or its resolved path compared against the operations root resolved the same way — even when it resolves into the platform; neither reading is ever used to allow. This is the direction that can place operations content into a **public git repository**, where it becomes committable and pushable. Irreducible Tier-0; always-blocks regardless of `automation_level` **and** regardless of `.autonomy-mode`, and it is evaluated ABOVE the master-activation gate, so master-OFF does not disable it. The converse direction is `BLOCK-AUTONOMY-004` and is NOT part of this rule. A working directory that cannot be resolved to an absolute path — the payload `cwd` and the hook process's `$PWD` both empty, or no absolute resolution — is treated as this rule's `projects/` side: the rule **fails closed** on it, and no other rule does |
| BLOCK-AUTONOMY-003 | Ceiling violation — the action's required Autonomy Tier (computed from a conservative declared-mapping table) EXCEEDS the resolved `[automation].automation_level` ceiling (effective = `min(ceiling, required)`). Mode-gated by `.autonomy-mode` (warn-initial); at/below the ceiling → allow. Structurally unreachable on a cross-domain `projects/` target, because `BLOCK-AUTONOMY-004` exits first in every mode |
| BLOCK-AUTONOMY-004 | Cross-domain bridge write **out of the platform checkout** (Write/Edit) — a cwd in a working tree of this repository, wherever it lives, writing into `projects/` (the Cowork-owned operations workspace) — that is, a target under `<workspace>/projects/` that is in no working tree of this repository. Membership is evaluated first, so for every working tree of this checkout's repository the premise below holds by construction: a platform worktree nested under `projects/` is classified `pmo-platform`, not `projects`. The two domains are **sibling directories, not nested**: `projects/` is not a git repository and is not in the platform repo's path space at all, so this direction cannot reach the tracked repo and carries no disclosure component. It is therefore a **layer-discipline signal, not a Tier-0 floor** — mode-gated by `.autonomy-mode` (`warn` → warn-log + allow · `enforce` → block · `off` → allow) and evaluated BELOW both the master-activation and workspace-scope gates. Override text names the relaunch remedy (launch operations work from the operations workspace) rather than leading with `CLAUDE_HOOK_BYPASS`, which would be a whole-session security-hook disable for a warn-class signal |

### Posture & cache — block-autonomy-ceiling.sh

**Ceiling resolution (section-aware, `=`-terminated).** The ceiling read parses the `[automation]` TOML section and matches `automation_level` with an `=` terminator, so a same-named key under any other section and any same-PREFIX key (e.g. `automation_level_ci_autoresolve`) are both unreachable. This supersedes the original section-blind `grep -E '^automation_level'` reader, whose safety rested on the key being unique repo-wide and was in fact file-ORDER dependent: a colliding key sorting *after* `[automation]` was harmlessly overridden, which is why the hazard evaded casual testing. The idiom is lifted verbatim from `lib/master-enable.sh` `_me_read_field`, and `resolve_level_direct()` is a byte-identical twin of the same function in `prime-autonomy-ceiling-cache.sh` — edit both or neither.

**Anchor/target resolution parity.** Every anchored comparison in this hook tests a realpath-resolved input — the write target, and the working directory — against a prefix built on `${PRIMARY_ROOT}`, which is resolved by the same function; the working directory's `projects/` comparison also resolves the prefix's `projects` segment when it is a symbolic link. Consumed raw, four benign shapes of `CLAUDE_WORKSPACE_ROOT` — a trailing slash, a trailing `/.`, a relative path, and a symlinked alias — each make every anchored pattern miss, and the failure is **total rather than partial**: the `-001` and `-002` floors, `-004`, and the ceiling's `projects/` mapping are all anchored on that one value. Location-anchoring the `-001` document entries took the anchored-entry count from 3 to 11 and widened the exposure accordingly. Path resolution itself carries a stated fallback: when `python3` is unusable — absent, or the Command Line Tools stub present but non-functional — resolution falls back to a shell resolver (`cd … && pwd -P` for the parent chain, `readlink` for a symlinked final component, bounded at 16 hops) rather than degrading to the raw path string, because a raw path is the *textual* reading of a target and every rule here is a path comparison. The working directory reaches that function as the payload `cwd`, or — when the payload omits it — as the hook process's own `$PWD`, the same second reading the workspace-scope gate falls back to; it is resolved only for a Write/Edit whose target lies in one of the two domains, the only writes whose verdict it can change. A working directory that still resolves to no absolute path is not trusted as text: `BLOCK-AUTONOMY-002` fails closed on it and nothing else does — `BLOCK-AUTONOMY-004` does not fire, and the workspace-scope gate keeps receiving the raw payload value and keeps its own stand-down direction. The block log keeps `cwd` as the payload value, as every hook writing that shared log does, and adds `cwd_resolved` — the value the verdict used, empty when the working directory was unresolvable — on `-002` and `-004` rows only. For `BLOCK-AUTONOMY-002` the working directory is also read as spelled, and that reading can only add a block, never remove one.

**Cache (FMF-1).** The session-stable dial is resolved ONCE at SessionStart by the sibling `prime-autonomy-ceiling-cache.sh` hook, which writes the numeric ceiling to `${HOME}/.cache/pmo-platform/autonomy-ceiling`. This PreToolUse hook reads that cache (a single file read) rather than re-resolving `operator.toml` on every tool call. If the cache is absent/unreadable, it falls back to a direct resolve so the ceiling is never silently dropped.

**Enforcement-surface caveat (do NOT read as "now hard-enforced" unqualified).** The Tier-0 floor is LIVE always for the payload-detectable classes ONLY: governance-file writes, plus cross-domain bridge writes **in the `projects` → `pmo-platform` direction only** (a write into `pmo-platform/` whose working directory cannot be resolved counts as that direction: the floor fails closed rather than standing down). Financial / account-creation / security-permission actions and the Stage 9 / Stage 12 gates are NOT mechanically detectable from a tool payload — they remain OPERATOR-IRREDUCIBLE by convention, not by this hook. `BLOCK-AUTONOMY-004` and the ceiling check are hard-enforced only after the operator flips `.autonomy-mode` from warn → enforce post-shakedown.

**Master-OFF reachability (the boundary of the `-004` audit trail).** `BLOCK-AUTONOMY-004` sits below the master-activation gate, and **master-OFF is the shipped default** — a fresh install with no XDG value reads `off`. On such an instance the hook exits at the gate and `-004` contributes nothing: no block, no warn, and **no row in `autonomy-warn-log.jsonl`**. The warn-log audit trail this rule offers therefore exists only where the operator has enabled the security-hook suite; it is not a property of the default install. `BLOCK-AUTONOMY-002` is unaffected — it is evaluated above the gate and blocks under master-OFF.

**Repository membership (the shared helper).** Whether a path belongs to this platform is answered by one sourced helper, `lib/platform-membership.sh`, shared with `block-draft-files.sh`. It performs a bounded upward walk (nearest tree wins) to the path's working tree and compares that tree's git directory with the platform checkout's. The checkout is `<workspace>/pmo-platform`. The workspace root is `CLAUDE_WORKSPACE_ROOT`, else the parent of the deployed `.claude` directory, else `$HOME/Claude`. That is the scope lib's order without its sandbox override, so a scope knob never steers the floor. The checkout's `.git` is resolved before comparison. The helper returns an answer and owns no failure branch; each rule maps the answer:

| Helper answer | `-001` stage 2 | target of `-002`/`-004` | cwd, for `-004` | `block-draft-files` identity gate |
|---|---|---|---|---|
| member | block | `pmo-platform` | `pmo-platform` | apply the rule |
| not a member | no block | `projects` under `<workspace>/projects/`, else none | `projects` under the operations root, else none | inert |
| undeterminable | no block | `projects` under `<workspace>/projects/`, else `pmo-platform` (fails `-002` closed) | `projects` under the operations root, else none | inert |
| no platform repository at the anchor | no block | as not a member | as not a member | abstain |
| helper unavailable | block (`LIB-MISSING`, fails closed) | as undeterminable | as undeterminable | abstain |

The cwd input is the resolved working directory described in the parity paragraph above. The cwd's `-002` side is not a helper answer: it is the two location readings in the `-002` row, so no answer in this table — a missing helper included — can block a platform-engineering session's ordinary writes, and an empty resolved working directory is the separate `unresolvable` state, on which only `-002` fails closed. While the helper is missing, a session rooted under `projects/` cannot write outside `projects/`: those targets read undeterminable, and `-002` refuses them with a `LIB-MISSING` reason and the reinstall remedy. The helper is loaded only on Write/Edit, independent of `.autonomy-mode`. A missing copy is **not** the mode-coupled `LIB-MISSING` posture of `lib/dep-resolve.sh`: it fails only the floor's membership questions closed, and `CLAUDE_HOOK_BYPASS` clears it because the bypass exits first. A platform worktree outside the governed workspace root is still reached by `-001` and `-002`, which sit above the scope gate. It is not reached by `-004`, or by `block-draft-files`, whose scope gates exit first. That is the documented verdict, not a recognition failure.
