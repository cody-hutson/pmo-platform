## `block-destructive.sh` (BLOCK-DESTRUCTIVE-001..023)

| Field | Value |
|---|---|
| Hook | `.claude/hooks/block-destructive.sh` |
| Matcher | Bash, Write, Edit |
| Scope | Destructive git ops, rm -rf catastrophic paths, primary-write guard, tamper resistance, script-exec ban |
| Mode | Always-enforce (high-confidence, narrow rules, low false-positive risk; not gated by `.claude/hooks/.mode`) |

> **Coverage boundary of BLOCK-DESTRUCTIVE-022 (and of every rule in this registry) — FOUR conditions.** "Always-enforce" above describes condition 4 only. A PreToolUse-enforced control is in force only when **all four** hold, and not when any one fails: (1) **loading** — the session resolved a settings surface declaring the hook wiring (any session, main or spawned, whose working directory is under the governed workspace root; a session resolving no such surface loads no hooks at all, and one outside the root is excluded by `core/hooks/lib/scope-guard.sh`); (2) **bypass** — `CLAUDE_HOOK_BYPASS` was not set in the launching environment (layer 1, which exits **both** hook classes, so the security/workflow asymmetry does **not** exist there; -023 denies *setting* it mid-session, which does not narrow the pre-launch case); (3) **master-activation class** — this hook is `security` class and therefore always enforces, going inert only on an explicit logged security-class opt-out; (4) **mode** — this hook is mode-independent. Naming fewer than four overstates the coverage. Canonical statement: [`core/standards/subagent-security-posture.md` § 3.1](../../standards/subagent-security-posture.md).
>
> **The specific over-claim this exists to stop:** describing `script-execution-allowlist.txt` as a *control* on a path where condition 1 does not hold. Where the wiring is not loaded, the allowlist is a convention — it governs review, not execution.

> **Currency — an orthogonal axis, and deliberately NOT a fifth condition.** The four conditions above decide whether the control **runs**. None of them decides **which version** of it runs, and a hook that is loaded, unbypassed, security-class and mode-independent can still be enforcing bytes that a merged fix superseded weeks ago. Every condition reads as satisfied throughout; the count above is correct as it stands and is not incremented by this paragraph.
>
> The mechanism is the publisher, not the hook. The deployed bundle under `.claude/hooks/` is advanced by the update path, while the recorded checksum baseline that path consults is written only by a full installer run — so on any maintained instance the two diverge, and a refresh that classifies from the baseline alone reads a stale *platform* copy as an *operator edit* and declines to touch it. Before the publisher gained a second oracle, that decline was an inline warning inside a run that exited 0: the merged fix never landed and nothing said so.
>
> **What a reader should take from this.** "Is the control in force?" is answered by the four conditions. "Is the control the rule I am reading?" is a separate question with a separate answer, and reading this registry entry is not evidence for it. The publisher now decides platform-copy versus operator-edit on a bounded git-history walk rather than on the baseline alone, preserves on every unclassifiable outcome, and exits non-zero naming any hook it declined — so a superseded copy is either updated or reported, never silently kept. Verify currency by refreshing the bundle and reading the result, not by re-reading the conditions: `docs/scripts/setup-workspace.sh --refresh-hooks`, with `--reconcile-hooks` as the force path for a copy the walk classifies as a genuine divergence.

> **What BLOCK-DESTRUCTIVE-022 resolves, and what it cannot.** Given all four conditions above, the rule adjudicates **the file that executes**, through **three arms of one matcher**: the first non-flag operand of each command whose command word names an admitted interpreter — `bash`, `sh`, `zsh`, `python`, `python3`, `perl`, `ruby`, `node` (the *interpreter* arm) — or `source` / `.` (the *source* arm), and the **command word itself** when it contains a slash (the *exec* arm). **The interpreter set is a CLOSED exact-literal enumeration, and the closedness is a safety property rather than a style choice:** the verb `case` is evaluated *before* the exec arm's slash discriminator and suppresses it on a match, so a trailing glob (`python3.[0-9]*`) would also claim a *script* named `python3.9-wrapper.sh`, remove that script from exec-arm adjudication, and turn a direct execution that is adjudicated today into an allow — a widening whose implementation narrows, and a silent one, since nothing asserts that an arbitrary `.sh` name is not a verb. **The non-shell interpreters are PHASE-GATED separately from the shell trio** — see the interpreter-arm rollout paragraph below — **and so is the shell trio's reach into an enclosure position**, on a third family of its own. **"Command word" and "non-flag" are both decided on the NORMALIZED token, not on raw argv** — a quoted verb is still that verb and a quoted flag is still a flag; the paragraph below on quoted flags and quoted verbs states what that changed and what constrains it. **The list of what this rule cannot resolve is explicitly not exhaustive** — it is enumerated below as the limits currently known and measured, after a closed enumeration of them was found to be smaller than the measured set. All three run through one matcher, one command-position walk, one token normalization and one adjudicator, so the guarantees below hold identically across them. Sourcing executes the file's contents in the current shell, and direct execution executes the file outright; both are the same execution capability an interpreter invocation is, not lesser ones.
>
> It resolves: a path in single or double quotes, and a path carrying a trailing run of shell syntax characters — the shape a command-substitution tail produces, where the operand arrives as `<path>.sh)` or `<path>.sh)"` or with a closing backtick attached; a path behind flags of any spelling — dash-form taking no argument (`bash -x <script>`, `. -x <file>`), **plus-form** (`bash +x <script>`), and options taking a **separate argument** (`bash -o errexit <script>`, `bash --rcfile <rc> <script>`) — because the operand walk terminates on the arm's **declared operand domain** rather than on the first non-flag token; before that correction only the first of those three spellings was resolved, and the flag-walk paragraph below records what the other two permitted; a script passed as an *argument* to another script (the argument is not what executes, so the executed script is what is checked); and a verb preceded by a **prefix run** — **variable assignments** (`VAR=v bash <script>`) and **transparent command wrappers** from a bounded set (`sudo`, `env`, `command`, `builtin`, `exec`, `nohup`, `time`, `xargs`, `nice`, `stdbuf`, `timeout`, and the compound-command keywords `then`, `do`, `else`, `elif`, `if`, `while`, `until`, `in`, `!`), each wrapper together with its own options and positional operands (`nice -n <adjustment>`, `sudo -u <user>`, `timeout <duration>`, `env NAME=value`), in any order and interleaved — because command position is resolved by walking that prefix run rather than by assuming the first token, and a wrapper's option grammar is read from a per-wrapper row beside the per-interpreter tables. The wrapper word is matched on the token's basename, so `/usr/bin/env bash <script>` resolves too. The set is one of four lists of this vocabulary, and they are not one set: the egress rule's prefix-command walk and the shared canonicalizer `core/hooks/lib/command-position.awk` each hold a list and walk it with their own grammar, and the SIGPIPE-idiom lint of the repository-integrity workflow holds a fourth for a different question. The canonicalizer matches the exact token, so an absolute-path wrapper is not a prefix there, and it alone steps over a leading redirection and an escaped verb; the egress walk alone steps over every dash-led token; the suite's parity arms (`WRAPVOCAB-PARITY-*`) enumerate every word-level difference with its reason, and fail on one they do not declare and on a declaration whose difference no longer exists. The set's gating direction is that a word **missing** from it leaves an invocation un-adjudicated (the status quo) and can never admit an evasion that would otherwise have been caught. An option a wrapper's row does not list is not the same case, and the difference is stated rather than argued away: the walk **steps over** such an option as a flag, a token stepped over leaves adjudication, and an option that itself carried an execution would leave with it — which is how the attached abbreviations of `env --split-string` (`env --split=<script>`) were lost until a long option was read the way its program's parser reads it. So each row reads a long option by its program's own option table, unique prefixes included, and reads every spelling of the one option known to carry a command line, `env`'s split string, for a command word of its own: the walk stops on a split value that carries one and goes on to the command that follows a value that carries none, as GNU env does — for a value written without shell quotes and carrying no slash, and for no other. A split value written with shell quotes and a split value carrying a slash are two open classes, declared with their owner in scope item 2; an option the tables do not list is the declared residual there too. The one row field that grants an allow — the options under which a wrapper executes nothing (`command -v`, `sudo -l`) — is two rows long, with a near miss pinned for each letter. It evaluates **every** command on a line, so an allowlisted first command does not shield a later one across `;`, `&&`, `||`, or `|`, and a verb behind an enclosure opener — inside `$( … )`, backticks, `<( … )`, `>( … )` or `( … )` — through the second view that item 3 of the residual list below describes.
>
> One consequence of `xargs` being in that set is worth stating on its own. `xargs <interpreter> <path> …` executes `<path>`, which is adjudicated normally — an allowlisted target still allows. When **no token** follows the interpreter, its operand list arrives on **stdin**, which a PreToolUse hook cannot see, so the executed target is unresolvable and the invocation **fails closed** (denied), on the same reasoning as the variable-bearing path below. That holds behind `xargs`'s own options as without them (`xargs -n 1 bash`), and for an interpreter of every family, with no rollout phase: a non-shell interpreter fed this way is refused, not recorded (`xargs -n 1 python3`, arm `WRAPOPT-xargs-stdin-py`), as it already was without an option. **The predicate is "no token after the interpreter", not "no operand on argv", so the deny is narrowed rather than closed:** an interpreter's own flag is a token, and `xargs -n 1 bash -x`, which runs the script named on standard input, is allowed (arm `WRAPDIV-xargs-interp-flag`).
>
> **The exec arm's discriminator is the shell's own, and this is why it is a slash and not a suffix or an exec bit.** POSIX Shell Command Language § 2.9.1.1: a command name containing at least one slash is used directly as a pathname; otherwise the shell performs a `PATH` search. So a slash-bearing command word *is* the shell's own execute-this-file test, and every `PATH`-resolved utility (`ls`, `git`, `grep`) is excluded by construction rather than by enumeration. **Four** root-owned system-bin prefixes are then excluded explicitly — `/bin`, `/usr/bin`, `/usr/local/bin`, `/opt/local/bin` — from a set the exec arm owns, **not** from `ANCHOR_PREFIX_BASH`.
>
> **Why that set is the exec arm's own, and why this paragraph used to say the opposite.** It previously said the prefixes were reused from `ANCHOR_PREFIX_BASH` "so the file keeps one definition of system bin", and that reuse was a defect rather than an economy: the two uses ask **inverted** security questions. Where the anchor originates, a prefix identifies the **interpreter binary** being invoked — a trusted-*source* question, where listing a directory only widens what counts as a command start. In the exec arm the same prefix exempts the **execution target** from adjudication — an untrusted-*target* question, where listing a directory *removes* coverage. One list cannot answer both. The measured consequence: `/opt/homebrew/bin` is mode 0775 owned by the operator's admin group on the reference host, so an agent can write into it without elevation — `/opt/homebrew/bin/x.sh` executed directly was never adjudicated while `bash /opt/homebrew/bin/x.sh` blocked, which is the script-laundering route the rule's own block message names. It is removed from the exec arm's set; `ANCHOR_PREFIX_BASH` is deliberately unchanged, because other rules depend on it in its original trusted-source role where dropping a prefix would narrow a matcher instead of an exemption. `/sbin` and `/usr/sbin` stay absent, unchanged — adding them would *widen* the exemption. Arms in `core/hooks/tests/block-destructive.test.sh` assert the removal and assert that the four remaining prefixes keep their exemption, so the change is pinned as a narrowing rather than a rewrite.
>
> **The exec arm is PHASE-GATED, and its phase is not the other two arms' posture.** "Always-enforce" in the table above describes the interpreter and source arms at every command position the first view reaches; at a position the enclosure view opens they follow a rollout phase of their own, stated in the paragraph on the third family below. The exec arm ships at rollout phase `warn` behind the per-rule constant `DESTRUCTIVE_022_EXEC_PHASE` = warn (`shadow` | `warn` | `enforce`) in `core/hooks/block-destructive.sh` — deliberately **not** the shared `.claude/hooks/.mode`, which is a cohort instrument and would soften seven unrelated hooks. At `warn` a would-fire is recorded and the call proceeds; the operand is adjudicated either way. Read a green run accordingly: at this phase the exec arm reports, it does not block.
>
> **Graduation criterion — the rollout is decided by a date, not by attention.** The arm writes every would-fire to `destructive-warn-log.jsonl` (this hook's first drain), and the criterion has two arms that are deliberately asymmetric. The **evidence** arm — `DESTRUCTIVE_022_EXEC_REVIEW_ROWS` = 25 — reads that drain, which is git-ignored and absent in a fresh checkout or CI, so nothing in the pipeline can read it and it can trigger nothing. The **deadline** arm — `DESTRUCTIVE_022_EXEC_ARMED` = 2026-10-16 plus `DESTRUCTIVE_022_EXEC_REVIEW_DAYS` = 60, escalating at `DESTRUCTIVE_022_EXEC_ESCALATE_DAYS` = 90 — reads a committed constant and today's date, so it is repo-derivable and it carries the teeth. `deploy.sh` Check 71 is the enforcement surface: silent inside the window, a warning at either threshold, and at 90 days with the phase constant anything other than `enforce` it increments `ISSUES` so `--check --strict` exits 1. Only two kinds of edit turn that green, and each is a recorded decision: advancing `DESTRUCTIVE_022_EXEC_PHASE` to `enforce`, which discharges the gate for good; or keeping the elapsed days below the escalation threshold — by re-dating `DESTRUCTIVE_022_EXEC_ARMED` forward (on its own, or together with a retreat to `shadow`), or by raising `DESTRUCTIVE_022_EXEC_ESCALATE_DAYS`. A retreat to `shadow` on its own does **not** turn it green: with the phase constant anything other than `enforce`, past the escalation day the check fails at `shadow` exactly as it does at `warn`. Rows landing in the drain do not turn it green either — the evidence arm only ever warns and never touches `ISSUES`. **Decision recorded 2026-10-16 (Fri), by the operator at the graduation gate:** the exec arm neither graduates nor retreats; it stays at `warn` and its arming date moves forward — the arm's second re-date, recorded as a decision, which reverses the earlier record that a second extension would have to be a graduation or a retreat. `DESTRUCTIVE_022_EXEC_PHASE` = warn, unchanged; next review 2026-12-15 (Tue), escalation 2027-01-14 (Thu). > **The NON-SHELL INTERPRETER arm is phase-gated too, and on its OWN constant family rather than the exec arm's.** Admitting `python`, `python3`, `perl`, `ruby` and `node` to the verb classifier is a second widening of the same rule, and it ships at rollout phase `warn` behind `DESTRUCTIVE_022_INTERP_PHASE` = warn (`shadow` | `warn` | `enforce`), armed at `DESTRUCTIVE_022_INTERP_ARMED` = 2026-10-16 with the same 60-day review and 90-day escalation thresholds the exec arm uses. **The families are separate so the two rollouts can retreat independently:** binding both to one constant would mean a noisy reading on either forces a retreat on both, which destroys the "retreat must be as cheap as advance" property the three-value enum exists to provide. **The shell trio never routes through the interpreter arm's router** — `bash`, `sh`, `zsh`, `source` and `.` route through a verdict router of their own, which at a first-view position is a pass-through to the adjudicator, so their always-enforce posture there is unchanged, and arms `T-NSI-04a`–`T-NSI-04d` and `AC-ENCL-P5` assert it by requiring a hard refusal *with a zero drain delta*. At an enclosure position that router applies the third family's phase, stated below. **Decision recorded 2026-10-16 (Fri), by the operator at the graduation gate:** the interpreter arm neither graduates nor retreats; it stays at `warn` and its arming date moves forward — the family's first re-date. `DESTRUCTIVE_022_INTERP_PHASE` = warn, unchanged; next review 2026-12-15 (Tue), escalation 2027-01-14 (Thu). > **Why `warn` and not `enforce`, measured rather than assumed.** At the introducing commit every one of the 289 non-comment entries in `script-execution-allowlist.txt` ends in `.sh`, so none of them can match a `.py` path, against 72 tracked `.py` files. Landing at `enforce` would refuse all of them on day one. The allowlist's non-shell section is therefore **deliberately empty at introduction** and is to be filled from drain evidence during the warn phase, not pre-populated from a corpus survey — a survey measures CI workflows and documentation, which do not load hooks, and would graduate the arm against a population nobody observed. **This creates a dated obligation on the operator:** a strict `deploy.sh --check` run turns red at the arming date plus 90 days unless the phase reads `enforce` or the arming date has been moved forward (equivalently, the escalation day-count raised). Rows landing in the allowlist do not move it, and a retreat to `shadow` does not either — rows are what make `enforce` survivable, not what satisfies the check, and `shadow` still fails past the escalation day. That is the mechanism working as designed, and it is a commitment rather than a side effect. **On 2026-10-16 the section took its first rows, read from the drain rather than from a survey:** one group in the four canonical forms for each of the 32 tracked tools the interpreter arm recorded from sessions outside spoke worktrees, every one a `.py` — among them every tool a pipeline specification prescribes, so each prescribed invocation is now admitted; one prescribed tool is admitted by a group that was not read from the drain, `release/tools/check-dark-branch.py`, rowed when this section first met a mainline that added that tool, as the allowlist header records. Not rowed, by the same rule: a tool seen only from spoke worktrees, any script outside the repository's tracked files, and any path whose value argv does not determine. The `.pl`, `.pm`, `.rb`, `.js`, `.mjs` and `.cjs` domains hold no row yet.

The two decisions the view carries with it follow the same phase there: the `xargs` standard-input deny, and the here-document receiver read from the innermost open enclosure. At `warn` such a finding is recorded with a would-fire row and a notice and the call proceeds; at `enforce` it is refused as a first-view finding is, and an unrecognised value falls through to `enforce`. **The router is a pass-through at a first-view position**, so the always-enforce verdict there is unchanged: arm `AC-ENCL-P5` asserts it with a first-view refusal and a zero drain delta, where an unedited call site used to carry it by construction. The family exists because the view adjudicates text a lexical matcher cannot tell from a command, and its cost on inline pull-request bodies was measured at several times what a commit-message corpus suggested; the warn phase measures how often the view would refuse, never how often it would be right. A later graduation decision is owed, and `deploy.sh` Check 71's deadline arm forces it: a warning from 2026-12-15 (Tue) and a finding from 2027-01-14 (Thu).

> **The three phased families write to one drain, and the `arm` field is what keeps the three graduations readable.** Every would-fire row carries `"arm"` — `exec`, `interp-nonshell` or `shell-enclosure`. Rows written before the field existed carry none, and a reader treats an absent field as `exec`, which is factual because the exec router was then the only writer. `deploy.sh` Check 71 is parameterized over the family list rather than copied per arm, and splits the drain on that field; the third family was added as one word in its family list, one line naming its `arm` value, and five constants in the hook. A row written from an enclosure position — a command position the second view opens after a `(` or a backtick — additionally carries `"pos": "enclosure"`, whichever arm wrote it, so a reader can separate what the enclosure view contributes to each arm's population. The field says where a row came from, not whether the text at that position is executed, which a lexical matcher cannot know. **A graduation decision on the `exec` or `interp-nonshell` family should read those two populations separately:** since the view landed, both drains also hold rows from enclosure positions, much of it prose — a path named in a code span, a program handed to `python3 -` that opens a script — which a graduation would start refusing.

> **A zero drain reads as INSTRUMENTATION-SUSPECT, never as "no evidence yet".** Run the must-flag control for the arm in question (`core/hooks/tests/block-destructive.test.sh`, T-EXEC-1 for `exec`, T-NSI-01a for `interp-nonshell`, AC-ENCL-P1 for `shell-enclosure`). If it writes a row the surface is genuinely quiet and the arm can graduate at near-zero risk; if it does not, the drain is broken and that is a defect, not a reason to extend the window. This distinction exists because the in-repo precedent lacks it: `BLOCK-EGRESS-007` phases its own widening through `EGRESS_007_WIDENING_PHASE`, and that drain holds two rows in total — a rollout that can never graduate on evidence, with nothing to surface the stall.
>
> **It also resolves a QUOTED FLAG and a QUOTED VERB, and until this was fixed it resolved neither.** Two readers upstream of every arm decided on the raw argv token. The **flag walk** tested `-*` against the raw token, so `'-x'` — which does not begin with `-` — stopped the walk and was handed to the operand adjudicator; `-x` is inside no arm's operand domain, so nothing was adjudicated and the real script, the next token, was never read. The **verb resolver** read the raw basename, so `"bash"` matched no verb, the interpreter arm was never entered, and the token fell through to the exec arm, which found a command word with no `.sh`/`.bash` suffix and correctly declined — both arms declining, one quote away from the unquoted spellings that block. `bash '-x' <script>`, `bash '-v' <script>`, `bash '--' <script>`, `"bash" <script>` and `'sh' <script>` all allowed while their unquoted twins blocked. Both readers now consult the normalized token, and the same measurement closes the adjacent spellings it exposed: the quoted absolute interpreter (`"/bin/bash" <script>`, which additionally reached the exec arm's system-bin *exemption*, so the interpreter binary itself carried its operand past both arms), the quoted `source`/`.`/`zsh` verbs, the quoted flag on the source arm, and the quoted `-c`.
>
> **The direction of both corrections is constrained, and the constraint is the thing to check any edit against.** A flag-walk skip and a verb-resolver fallthrough both *remove* a token from adjudication, so each is an exemption and each may only narrow. Two rules keep them narrowing. First, the raw view is asked **first and unchanged**, so every token that was skipped is still skipped and every token that resolved to an arm still resolves to it — the normalized view is consulted only where the raw view already declined, which makes the change additive by construction. Second, a normalized token is treated as a flag only when it is flag-shaped **and lands in no arm's declared operand domain**: a domain claim beats a flag shape, because the arm that claims a token is the arm that will adjudicate it. That reason holds for a claim the operand path reads — the normalizer's resolution, the probe, the raw token — and it did not hold for a claim made only by a quote-led word's own value, which the operand path never reads: that claim ended the walk on a token nothing then adjudicated. So an exact value that begins with `-` does not claim its whole word when the walk reads that word in flag position: unless one of those three claims it first, the word is read as its unquoted spelling and takes that spelling's place in the walk. A value that lands in the domain without beginning with `-` still claims its word; the paragraph on the walk's boundary below states both, and what each leaves open. Without that second rule the naive spelling of this fix — normalize, then test `-*` — flips a shipped BLOCK to an ALLOW, because `bash '-x.sh'` normalizes to a token that is *both* flag-shaped and already inside the interpreter arm's operand domain. That is the same manufactured-allow shape as the trailing-run strip this section records above, and `core/hooks/tests/block-destructive.test.sh` pins it as arm `F1-QFLAG-ctl-domain` — a control that was green before the fix, so a fix that swaps the subject instead of adding a view turns it red. A **fragment** — a token that leaves a quote open, one piece of a longer quoted word that whitespace splitting cut — is never skipped, and no unresolvable token is read for a verb, for the reason the exec arm's exemption already gives: a filename that cannot be determined from argv cannot be shown to be a flag, or to name an interpreter, either. A token that opens with a quote and closes every quote it opens is a different thing: a whole word, which the flag walk reads as its unquoted spelling wherever argv determines that spelling, as the paragraph on the walk's boundary below states.
>
> **The flag walk had a SECOND root cause, in its termination predicate rather than in its subject, and the two paragraphs above did not reach it.** Those corrections made the walk read the right *string*; this one makes it ask the right *question*. The walk answered "where is the operand?" with **"the first token that is not flag-shaped"**, which is wrong in two independent ways that land in the same place: a token that is not the operand became the adjudicated operand, fell outside the arm's declared operand domain, and the arm concluded the invocation was not its business — **reaching ALLOW without the allowlist ever being consulted.** (1) The skip arm was **dash-anchored**, so a **plus-form** option was not matched by `-*`, fell through, and the *option itself* became the operand: `bash +x <script>`. (2) The skip did not **consume a flag's argument**, so for an option taking a separate value the *value* became the operand: `bash -o errexit <script>`. The controls are what made this a defect rather than a declared boundary: an option taking no separate argument leaves the real operand in place, so `bash -x <script>` blocked while `bash -o errexit <script>` allowed — two spellings of one execution, one checked and one not. Both are closed by terminating the walk on the arm's **declared operand domain**: the walk now stops where the arm would actually adjudicate. Its shape is not new — it is the predicate every other adjudication point in this rule already uses, including the `-c` scanning loop directly beneath it.
>
> **Its consequence reached further than the walk, and this is the part worth stating separately: the defect DISARMED the variable-bearing fail-closed deny.** The paragraph below records that `bash "$DIR/x.sh"` fails closed because a PreToolUse hook cannot resolve unexpanded argv. That posture was bypassable by prefixing **any** value-taking flag — `bash -o errexit "$DIR/x.sh"` reached ALLOW while the bare spelling denied — because the deny is raised by the adjudicator and the adjudicator was never handed the operand. A documented fail-closed posture that a caller can switch off by adding a flag is not one, and it is recorded here as a coverage correction rather than a stylistic one.
>
> **Why the fix is a domain test and NOT a per-interpreter arity table, argued on failure direction rather than on effort.** A table of "which options take a separate argument" **fails OPEN on omission**: one unenumerated value-taking flag leaves its argument unconsumed, the argument becomes the operand, it lands outside the domain, nothing is adjudicated, ALLOW — the exact defect being fixed, re-entering through its own remedy. That is precisely the inverse construction this section already forbids of the suppression set below: *a denylist whose one missed entry is a silent fail-open is not an acceptable trade inside a fail-closed control.* The domain test has nothing to omit — `+x`, `errexit`, `extglob`, an rcfile path are all simply **not the operand**, and the walk keeps looking — so it needs no arity knowledge and no plus-form enumeration, and it adds **no new exemption**. A bare `+*` skip arm was also rejected and for the same class of reason: it would be a manufactured allow of the shape `F1-QFLAG-ctl-domain` exists to catch, since a file literally named `+x.sh` would then be skipped.
>
> **The direction is constrained here too, and the same two constraints carry over.** First, **a fragment is never advanced past** — a fragment being a token that leaves a quote open, one piece of a longer quoted word that whitespace splitting cut. *Advancing past* a token removes it from adjudication in exactly the sense *skipping* one does, so the new arm is an exemption and inherits the rule the paragraph above states — a filename that cannot be determined from argv cannot be shown *not* to be the operand either. That clause is not optional: without it the walk advances off `'/tmp/pmo` (whitespace splitting hands it the first fragment of a space-bearing quoted path, limit 3 below) onto a later fragment and adjudicates the wrong subject, and arm `F1-QTOK-RESIDUAL-space` turns red — which is how the clause was found, by measurement rather than by foresight. The clause is about fragments, not about every token the filename normalizer declines: a token that opens with a quote and closes every quote it opens is a whole word, and the walk reads it as the paragraph on the walk's boundary below states. Second, the change is **monotone ALLOW→BLOCK by construction**: if the old first-non-flag token *was* domain-claimed the new walk stops at the same token and behaviour is identical, and if it was *not* domain-claimed the old code adjudicated nothing so no block was possible. It can only turn an ALLOW into a BLOCK, never the reverse.
>
> **Two verdicts changed that no prior arm pinned, and both are declared rather than suppressed.** Both move ALLOW → **BLOCK**, and both are the same mechanism seen from two positions: the walk stops at the first token in the arm's operand domain, whichever token that is.
>
> *First — an extensionless executed target carrying a `.sh` argument*, `bash <wrapper> <script>`. The walk advances past the un-adjudicable wrapper (the shared extensionless residual, limit 5) and adjudicates the argument. Arm `F2-FWALK-CONSEQ-extless` pins it.
>
> *Second — a flag argument that is a **non**-allowlisted script while the real operand is allowlisted*, `bash +O <non-allowlisted>.sh <allowlisted>`. `interp`'s declared operand domain is `*.sh`, so the flag argument is domain-claimed, terminates the walk, and is adjudicated — the allowlisted operand is never reached, and the command blocks. This is the exact mirror of limit 8 below: same termination rule, opposite membership, opposite direction. **No arm pins it.**
>
> The direction of both is over-block, which this section's own reasoning calls recoverable, and `bash -- <wrapper> <script>` is **unchanged** — `--` remains a hard stop, so POSIX operand semantics are preserved exactly. Suppressing them was considered and rejected: widening the stop condition from "in the arm's domain" to "domain **or** path-shaped" would suppress the first, but would simultaneously reopen the value-taking-flag hole for any path-shaped flag value (`bash --rcfile /tmp/rc <script>`), trading a recoverable over-block for a reopened fail-open.
>
> **Forward note, now discharged.** Because the walk advances past a token the domain does not claim, two things that were previously *unreachable* rather than merely unlisted become reachable: an interpreter flag meaning "parse but execute nothing" presented as `-o <value>`, and a label for an interpreter whose script operand arrives through a flag argument. Both belonged to a separate in-flight change that declared itself blocked on this walk. **That change is the parse-only exemption and arity overlay recorded in the paragraphs immediately below, and the two are now merged**, so this note records a resolved dependency rather than an open one. What the overlay does *not* do is inherit the walk's own hazard: the arity table decides only how far the walk **steps**, never where it **stops**, so an omitted arity row costs an over-block rather than the fail-open that made an arity table wrong as the *termination* predicate.
>
> **The advance-past arm asks the arity question, and NOT the parse-only one; the asymmetry is the whole composition.** Advancing past a token asserts it is an option rather than the operand — the same assertion the `-*` skip arm makes — so the two arms must ask that token the same questions or the `+`-leading surface, which reaches only the advance-past arm, is judged by half the rule. **The hole this closes belongs to neither side alone and is created by the merge.** `origin/main` advances past `+-emulate` and then adjudicates the script, because main has no parse-only exemption to fool; this branch never advances past `+-emulate` at all, because `*) break` took it as the operand. Combine main's advance with this branch's exemption and `zsh +-emulate -n <unlisted>.sh` steps over `+-emulate`, hands the following `-n` to the parse-only table as a flag, and exempts a segment the real shell **executes** — a BLOCK → ALLOW that neither diff contains. Asking arity in the advance-past arm closes the class, not the spelling. The parse-only question is asked there in **one direction only, and an earlier form of this paragraph recorded just the half it refused.** A parse-only **grant** is still deliberately not taken from a `+` token, because that direction is wrong: arity can only remove a false inertness claim or add an adjudication (ALLOW → BLOCK), while a grant could manufacture an inertness claim from a `+` token (BLOCK → ALLOW) — and `+n` is zsh for turning `noexec` *off*, so the symmetric-looking widening would be wrong on its most obvious member. The **revoke** is the half that was owed, and its absence was a defect rather than a boundary: the same observation says a `+` token turns `noexec` off, so a walk that steps over one while still holding an earlier `-n` claim reports inert on an invocation the shell runs. It is now taken, in the ALLOW → BLOCK direction this arm already accepts for arity. Arms `FWALK-PLUS-*` pin the closure and `FWALK-DOM-py` pins the re-point below.
>
> **The walk's domain argument is re-pointed from the verb class to the interpreter domain, and the walk-termination fix asked for that by name.** Its own note states that a successor change splitting interpreter **domain** from verb **class** "must re-point this ONE argument to that domain variable, or a non-shell interpreter's real script is tested against the SHELL suffix set, found unclaimed, walked past, and silently under-adjudicated — a fail-open re-introduced by an otherwise clean merge." The per-interpreter operand-domain table below **is** that split, and it exists only on this side, so taking the termination arm verbatim would have been precisely the predicted fail-open: `python3 <path>.py` tested against `*.sh`, unclaimed, advanced past. The argument now reads `script_interp_domain`, the same variable every other adjudication point in this rule already asks.
>
> **A parse-only invocation is exempt, and the exemption is keyed on the INTERPRETER, never on the flag.** `bash -n <script>`, and the same form under `sh` and `zsh`, tells the interpreter to *parse and exit*: it executes nothing, whatever the operand is. The rule was refusing exactly that form while permitting several that do execute — a refusal inside no arm's declared scope, and the one it blocked was the syntax check that would have caught a real parse error. Inertness under `noexec` is a property of the interpreter's **mode**, fully determined by argv and independent of the target, so the exemption needs no path resolution and therefore also covers the non-allowlisted, variable-bearing and quote-unresolvable operands that otherwise hard-block. The RECOGNITION decision — which flag spelling means parse-only for which interpreter — lives in `script_interp_noexec_flag()`, a table keyed on the interpreter basename the verb resolver already decided on; every interpreter not named in it reaches an **explicit documented null** and its behaviour is unchanged. That table only ever *grants*, and only while the walk is still inside a run of option words it can read exactly — the paragraph after next: it never resolves the invocation, because the verdict is the last-one-wins state the next paragraph states, so a bare `-n` recognised here is exempt only until a later stepped-over token revokes it. Keying on the flag instead would be wrong on the merits and not merely stylistically: `-n` is a parse-only flag *for a POSIX shell*, while `perl -n` and `ruby -n` are implicit input loops that execute, `python3` has no `-n`, and for `source`/`.` — builtins that take no options — a `-n` is an operand. A flag-keyed exemption becomes a hole the moment the adjudicated interpreter set widens; widening this table means adding a `case` label to it, with a measured row for the new interpreter or the documented null, and changes nothing in the flag walk.
>
> **Parse-only is the interpreter's state as of the LAST option token seen, not a latch — and the fail-safe guarantee that follows from it is SCOPED, which an earlier statement of it was not.** Every shell in the table resolves mode options last-one-wins, so a flag set on first sight and never cleared reports inert on an invocation the interpreter executes: `bash -n +n <script>`, `bash -n +o noexec <script>` and `zsh -n +-noexec <script>` all run. Parse-only is therefore *granted* only by positive recognition in the parse-only table and *revoked* by every token the walk steps over, whatever it is spelled. There is deliberately **no clearing table**, because a clear-side enumeration symmetric to the set table fails **open** on omission — the identical failure direction that made an arity table wrong as the *termination* predicate. What that construction buys is stated exactly: for a token the walk **steps over**, an unrecognised spelling can cost an over-block and can never produce a parse-only verdict. It was previously written unqualified — "nothing to omit", "a spelling never seen cannot produce a parse-only verdict" — as a property of the whole predicate, and **in that form it is false.** The revoke sits *below* both of the walk's `break`s, deliberately: a token that **ends** the walk is not stepped over and must not revoke, or `bash -n <script>.sh` would revoke on the script itself and the exemption's entire value would be lost. For a token that ends the walk an earlier grant therefore **survives**, and what keeps that safe is **operand adjudication, not this predicate**. The two token classes are decidable per token, which is what makes the scoped claim checkable where the unqualified one was merely unfalsifiable.
>
> **The grant is also conditional on WHERE the `-n` stands, and until this was fixed it was not.** A bare `-n` is a parse-only flag only while the interpreter is still reading options, and only if the walk has read every token before it as the interpreter will. The walk keeps looking past any token the operand domain does not claim, so it granted on three kinds of `-n` the interpreter never reads as a flag. (1) One that follows **the first argument that is not an option**: `zsh -s -O extglob -n <path>` runs its stdin with `extglob` and `-n` as positional parameters, because zsh's `-O` takes no argument, and `bash <wrapper> -n <script>` runs the wrapper. A lone `-` ends option reading the same way. (2) One that follows **an option whose text is not its value**: `--rcfile""`, `--rc\file`, `\--rcfile`, `--rcfile$X` and `--{norc,rcfile}` are each `--rcfile` to bash, which takes the `-n` as the rcfile *name* and **executes** the script behind it; the arity table is asked about the text and has no row for it. (3) One that follows **an option argument that may be no word at all**: `bash --rcfile $X -n <script>` with `X` unset, or the same with a quoted list expansion of an empty list. All three were refused before the parse-only exemption existed, so each was a shipped BLOCK turned into an ALLOW — (2) and (3) on an invocation that runs the script. The walk now carries a second state beside the parse-only one, `script_optrun`. It stays set only while every token read in the segment is an **option word the walk can read exactly** — it begins with `-` or `+`, is longer than the sign, and carries only characters no shell rewrites inside a word — and every option argument the walk consumes is one word whose text the hook holds. The grant requires it. One of those characters is rewritten at the start of a word: zsh expands a word that begins with `=` to the path of the command it names, so the hook does not hold the text of a consumed argument spelled that way; the latch is unaffected, because an option word begins with a sign and such an argument is still one word, or nothing runs. **This state IS a latch, and the difference from the paragraph above is the point:** `noexec` is a mode, resolved last-one-wins, so its state is reassigned by every token the walk steps over; where option reading *ends* is not a mode, and nothing later on argv restores it. The test is a character allowlist with nothing to omit — no list of option names, of words that end option parsing, or of quoting and expansion constructs — so an unseen spelling costs an over-block and never an exemption. It moves no token: the walk still terminates on the arm's operand domain, so only the grant narrows and the change is monotone ALLOW→BLOCK by construction. **Three costs are declared rather than hidden.** `bash -eo pipefail -n <script>` only parses and is refused, because only a bare `-o` is in the arity table and the cluster's argument reads as a word (arm `NOEXEC-TERM-R1`) — the parse-only table already declines a cluster for the same reason. `bash -o "$VAR" -n <script>` is refused because the walk does not hold the argument's text (arm `NOEXEC-TERM-R2`). And zsh's `-b` and `+b`, which end option processing as `--` does, have the shape of an option word: `zsh -b -n <script>` and `zsh +b -n <script>` are still allowed, and what zsh then runs is a file named `-n` — the extensionless limit below, with the script-suffixed path as that file's argument (arm `NOEXEC-TERM-P1`; corpus rows `ZT11` and `ZG03`). Modelling either letter would be a list of end-of-options spellings whose omissions fail open.
>
> **An option the walk cannot read is not stepped over as if it took no argument.** A token whose reading carries a character outside the plain set — a quote, a backslash, an expansion, a glob, a brace, a redirection — has a value this hook does not hold, and so does a consumed option argument that may be no word at all. Stepping over such a token is a guess that it consumes nothing. When the guess is wrong, an allowlisted script in its argument slot is adjudicated as the operand while the script the shell runs is never read: `bash --rcfile"" <allowlisted>.sh <script>.sh`, `bash \--rcfile <allowlisted>.sh <script>.sh`, `bash $X--rcfile <allowlisted>.sh <script>.sh` and `bash --rcfile $X <allowlisted>.sh <script>.sh` each execute `<script>.sh`. Under an interpreter the walk takes the route `-c` takes instead: it ends, no parse-only exemption applies, and every remaining token that lands in the arm's operand domain is adjudicated. The route adjudicates and does not deny — `bash $X-x <allowlisted>.sh` is allowed (arm `FWALK-OPAQUE-ctl-allow`). A token a view places in the operand domain is the operand and is not routed, and a token whose quote the walk could not resolve still ends the walk where it always did. The route has one definition: a quote-led word of unknown value, which the next paragraph describes, reaches it by the same line, because the reading the walk holds for such a word is its raw spelling and that is never plain. **One cost is declared:** `bash $X-x <allowlisted>.sh <unlisted>.sh` is refused although only the allowlisted script runs, because the unread option might have taken it as its argument (arm `FWALK-OPAQUE-R1`). A here-string program is read as a program string for the same reason (`bash <<< '<program>'`, arm `FWALK-OPAQUE-06`). Under `source` there is no such route and no arity to get wrong, so the token is stepped over as before.
>
> **That boundary's one family is closed for a whole word the walk steps over unquoted; what remains is a fragment, and a word whose own value is the operand.** The family is a token whose leading quote closes early — `""+n`, `''+n`, `'+'n`, `"-"n`, and, with no `-n` anywhere, `""-x`. The filename normalizer declines such a token, rightly, because the value in hand when the quote closes is a prefix and a prefix is not a filename. The walk used to take that decline as its own answer, so the token ended the walk at the break *above* the revoke, became the operand, fell outside every domain, and nothing was adjudicated — `bash -n ""+n <unlisted>.sh` and `bash ""-x <unlisted>.sh` were **allowed** while their unquoted twins **blocked**, which placed the allow in the **unresolvable-operand path** rather than in the parse-only predicate. The walk now asks such a token its own question — is this the operand, or something in front of it? — through a second reader that reads one argv token the way the shell reads a word, under the same four quoting states this section's quote-state tracking uses. A token that opens with a quote and closes every quote it opens is a **whole word**, and where argv determines its value the walk reads it as its unquoted spelling and gives it that spelling's place in the walk: `""+n` revokes the grant, `""-x` is stepped over and the script behind it is adjudicated, `""-c` takes the `-c` route, and the parse-only grant and option arity apply exactly as they do unquoted. **In flag position, a word whose exact value begins with `-` is read as its unquoted spelling whatever its suffix, unless the normalizer, the probe or the raw token claims it first**, because that spelling is a `-`-led token and the walk decides every such token without asking the domain: `bash '-x.s'h <script>` — the word `-x.sh`, its quote closing inside the suffix — adjudicates the script as `bash -x.sh <script>` does, and revokes an earlier grant as that spelling does. Until this was fixed the word's own value claimed it, the walk ended on it, and the operand path, which reads the probe and the raw token and never the word, adjudicated nothing: fourteen measured spellings under `bash`, `zsh`, `source`, `python3`, `perl`, `ruby` and `node` were allowed where their unquoted twins were refused or warned on (arms `FWALK-QDASH-01` to `-14`). Where argv does **not** determine the value — a `$` or a backtick the shell expands, an unquoted `{`, `*`, `?`, `[` or `~` (brace, pathname and tilde expansion), a `$'...'` run, or a token longer than the reader's limit — the word is neither a flag this hook can read nor an operand it can name. Under an interpreter it takes the route `-c` already takes: the walk ends, no parse-only exemption applies, and every remaining token in the arm's operand domain is adjudicated. Under `source`, which has no such route and no parse-only grant, it is stepped over and the walk keeps looking. A command substitution with whitespace inside it is cut by the same splitting; when its first piece balances its quotes, that piece is read this way, as a word of unknown value. The normalizer is still asked first and unchanged, and a token that the normalizer, the probe or the raw token places in the arm's operand domain still ends the walk as the operand, so the change is **monotone ALLOW→BLOCK** by construction: every token whose reading changed was one none of those three claimed, that ended the walk, and that nothing adjudicated. Where such a token's unquoted spelling is one the walk steps over, the token is at least as strict as that spelling with two exceptions: behind a parse-only grant, and where the allowlist admits the token's own value. `'-x.sh'`, `"-"x.sh` and `''-x.sh` are refused with an allowlisted script behind them, where that spelling is allowed (arms `FWALK-QDASH-pin-resolved`, `-pin-raw` and `-pin-empty`). Behind a grant the token is looser: `bash -n '-x.sh' <script>` is allowed where `bash -n -x.sh <script>` is refused, because a token that ends the walk keeps an earlier grant, while the unquoted `-x.sh` is stepped over and revokes it. Where the allowlist admits the token's own value it is looser too: a claimed token is adjudicated on that value, so `bash '-x/<allowlisted path>' <script>` is allowed where `bash -x/<allowlisted path> <script>` is refused when an allowlist glob such as `*/<allowlisted path>` matches the `-`-led value, while the unquoted spelling is stepped over and the script behind it is adjudicated. In both cases the shell receives the same word from either spelling and rejects the option, so neither runs anything, as Stage 7 measured — the grant case under `bash`, `sh` and `zsh`, the allowlist case under `bash`, `sh`, `zsh` and bash's `source`; no arm pins either pair. What remains open is a **fragment** — a token that leaves a quote open, one piece of a longer quoted word that whitespace splitting cut. It still ends the walk above the revoke, an earlier grant still stands at it, and limit 3 below records it. **Open beside it is a word whose own value is the operand.** In flag position that is a whole word whose value lands in the arm's operand domain without beginning with `-`: it ends the walk as the operand, exactly where its unquoted spelling ends it. The reading never reaches two more such words, whatever their first character: the token behind an end-of-options `--`, where the walk stops, and an option's consumed argument. In all three the operand path decides, and it reads only the probe and the raw token, so where the quote closes inside the suffix and neither of those lands in the domain, nothing is adjudicated. Each of these is allowed where its unquoted spelling is refused: `bash '+x.s'h <script>`, which runs nothing, and `source '+x.s'h`, which runs the file the word names; `bash -- '-x.s'h <script>` and `source -- '-x.s'h`, which run that file too; and `bash --rcfile '-x.s'h <allowlisted>.sh`, which runs only the allowlisted script, and `bash --rcfile '-x.s'h -i`, which sources the file as its rcfile. Under a non-shell interpreter the same shape writes no would-fire record where its unquoted spelling writes one: `python3 -- '-x.p'y` runs the file. That is the split-suffix operand, which the operand fold this release did not take would close; its own card owns it. The corpus records the two shapes that run no unlisted script (group `dash-suffix-decl`, arm `FWALK-QDASH-pin-plus`); the executing ones are not rows. The symmetric clear on that break, measured inert against this family, stays unshipped: the family closed in the operand path, where its cause was. Arms `FWALK-QWORD-*` pin the closure, its must-stay-allowed controls and its mutants, `FWALK-QDASH-*` the word that spells a dash flag, `NOEXEC-QSPLIT-*` pin the family's spellings at their new verdicts, and `NOEXEC-ORD-*` pin the line order the scope depends on, so a hoist of the revoke above either break is caught structurally rather than only as a behavioural regression. **The reading reaches a token that opens with a quote, and no other**: a flag that begins with `-`, `+` or a backslash and carries a quote, a backslash, or a brace or glob character — `--rcfile""`, `+-emu""late`, `\-c`, `--{norc,rcfile}` — never reaches it. The walk closes that class instead, as the two paragraphs above on where the `-n` stands and on an option the walk cannot read state, and item 9 of the out-of-scope list below records the disposition.
>
> **`-c` is excluded, and the exclusion is enforced twice because the two orders fail differently.** `bash -c '<program>' -n <script>` genuinely executes, and the walk **breaks** at `-c`, so the trailing `-n` is never examined as a flag and the exemption can never be reached — structural, not asserted. The reverse order `bash -n -c '<program>'` *does* set the flag before `-c` is seen, so an explicit "no `-c` was seen" conjunct declines it as well. Whether an arbitrary program string is inert under `noexec` is a second-order argument this control deliberately does not carry.
>
> **A cluster that carries the command-string letter is `-c`, and until this was fixed the walk read only the exact token.** The shells read one-letter options as a cluster, so `bash -ec '<program>'`, `sh -xc`, `zsh -fc` and `bash +ec` each take the next argument as a program string and execute it, exactly as a bare `-c` does. The walk's label matched `-c` exactly: the cluster was stepped over as a flag, the first piece of the program string became the operand, and no word of the string was adjudicated — while the same program behind a bare `-c` was. The decision lives in `script_interp_cmode_flag()`, a fourth table keyed on the interpreter basename and placed beside the other three. It has nothing to omit: any single-sign cluster containing `c`, whatever the other letters and wherever the `c` sits; a long option is excluded by its second character, not by name. A token it claims takes the route `-c` takes, so a wrong claim can only add an adjudication, and a token a view already places in the operand domain is left to the arm that adjudicates it (`bash '+c.sh'` still blocks, arm `FWALK-CLUSTER-ctl-claimed`). The non-shell interpreters reach the explicit null, because their single-dash options are not all one-letter clusters. **Two costs are declared.** A script-suffixed word the program string only reads is refused, exactly as it is behind a bare `-c` (arm `FWALK-CLUSTER-R1`). And `bash -nc '<program>'`, which only parses, is refused: the cluster is read as command mode before the parse-only table is asked, the same order the paragraph above gives for `bash -n -c`.
>
> **Two spellings are declared residuals rather than omissions, and they keep blocking exactly as before.** A **cluster** (`bash -nx <script>`) is not admitted: admitting one requires proving that no letter in it takes an argument, and a letter that does would consume the following token and change which token is the operand. **`-o noexec`** is not admitted either, and it is *unreachable* rather than merely unlisted — `-o` takes a separate argument, so the arity table below consumes `noexec` **as that argument** and never offers it to the parse-only table as a flag; listing it would ship a dead branch on a security surface. Both fall through to today's adjudication, which is the narrowing-safe direction this section's constraint above requires. `-o noexec` stays **listed-but-unreachable**, and the flag-walk defect it used to point at has since been fixed — the row was inherited by that fix rather than rediscovered, which is what recording it here was for.
>
> **The flag walk knows OPTION ARITY, and until this was fixed it did not.** The walk stepped over `-*` one token at a time and called the first non-option the operand. An option that takes a **separate argument** therefore left that argument sitting in the operand slot, and the walk was wrong in two directions on the same invocation. It **adjudicated the argument instead of the script**: `bash --rcfile <allowlisted> <unlisted>` checked the rcfile, found it allowlisted, allowed the segment, and never read the script bash actually runs. And it **offered the argument to the parse-only table as though it were a flag**: in `bash --rcfile -n <unlisted>` bash has taken `-n` as the rcfile *filename*, so the invocation executes — but the walk read `-n`, set the inert-mode flag, and the parse-only exemption above allowed the whole segment. The second shape is the sharper one, because it converts a *shipped* BLOCK into an ALLOW rather than continuing an inherited gap. The decision lives in `script_interp_optarg_flag()`, a third table keyed on the interpreter basename and placed beside the others so widening the interpreter set means adding a label in one place rather than hunting four. Its set is **measured, not inferred**, and the probe is a **script-execution marker**, not an option-parse result: `<interp> <opt> <sentinel> marker.sh`, where the marker on stdout means `<opt>` consumed the sentinel and `marker.sh` became the script; the **sentinel** named in the error message means `<opt>` consumed it and then rejected it (arity 1 with a validated argument namespace); and `marker.sh` named in the error message means the sentinel was the *script* (arity 0). All three outcomes have to be read — an earlier form of this note stated the probe as "`<interp> <opt> -n -c 'echo X'` prints `X` exactly when `<opt>` consumed the `-n`", which is **not** a biconditional and would drop four correct rows: `bash -O +O -o +o` do consume the `-n` and then abort with `-n: invalid shell option name` (rc=2), printing nothing, as do `zsh -o +o` (rc=1). The measured set admits `--rcfile --init-file -O +O -o +o` for `bash`/`sh` and `-o +o --emulate` for `zsh` (zsh's `-O`/`+O` take no argument, and `zsh --rcfile`/`--init-file` do not exist — those two are listed for `zsh` anyway, so that the verdict never rests on another program's option parser rejecting the invocation). No long-option **abbreviation** is accepted by bash (`--rcf`, `--init-f`, `--initfile` all rc=2), so no unlisted spelling of those two exists.
>
> **`--emulate` is the row a letter-by-letter sweep misses, and zsh's own `--help` does not name it.** It exists regardless and it takes a separate argument: `zsh --emulate -n -s` **executes** its stdin while the control `zsh -n -s` prints nothing, because `-n` is eaten as the emulation-mode *name*. So `zsh --emulate -n <unlisted>` executes, and without this row the walk read that `-n` as a flag and the parse-only exemption allowed the segment — a shipped BLOCK (it blocks on `origin/main`) turned into an ALLOW, on the `interp` domain, not phase-gated. The sweep behind the row enumerated zsh's entire option surface — every `-X`/`+X` single letter, and `--<name>`, `--no<name>`, `--no-<name>`, `+-<name>`, `+-no-<name>` for all 197 setopt names plus the 12 documented aliases, 1135 spellings in all — and found exactly **two** arity-1 spellings that execute despite a following `-n`: `--emulate` and `+-emulate`.
>
> **`-c` is deliberately absent; `+-emulate` is PRESENT, and an earlier form of this paragraph said both absences were structural.** Half of that survived the merge and half did not, so it is corrected rather than annotated. `-c`'s absence stands: its own walk label breaks the walk first, so a `-c` row could never be reached. **`+-emulate`'s exclusion rested on `*) break`, and `*) break` no longer exists.** The argument was that a `+`-leading token matches neither the `-*` skip arm nor the `--`/`-c` labels, so it fell through to the operand branch and the table was never consulted for it — a dead branch. The walk now terminates on the arm's declared operand domain and **advances past** any token the domain does not claim, so every `+`-leading spelling reaches this table. The `+O`/`+o` rows kept above "for a later widening of the walk to `+`-leading tokens" are live for exactly that reason, as their own note anticipated.
>
> **The `+-emulate` consequence also stopped being inherited, and that is what makes the row mandatory rather than tidy.** `zsh +-emulate -n <path>` **BLOCKS on `origin/main`** — main advances past `+-emulate` and adjudicates the script — so without this row the merged hook would ALLOW it: a BLOCK → ALLOW on a shape the real shell **executes**, introduced by the merge rather than by either diff. Measured with controls firing both ways: `zsh +-emulate -n -c 'echo X'` prints `X`, `zsh -n -c 'echo X'` is silent, because `+-emulate` eats the `-n` as the emulation-mode *name*. The row was added only after the `+` surface was re-swept rather than inferred from the earlier sweep: 656 zsh `+` spellings (`+<letter>`, and `+-<name>`/`+-no<name>`/`+-no-<name>` over the live shell's own 197 `${(k)options}` plus the 12 documented aliases) and 89 bash/sh `+` spellings, classified by the three-outcome read this section already mandates, with controls firing on both readings (`--emulate`/`--rcfile` arity 1, `-x` arity 0). `+-emulate` is the **only** arity-1 `+` spelling zsh has beyond `+o`; bash and `sh` have none beyond the `+O`/`+o` already listed; and it is the only one that leaves the shell **live** after eating a `-n` (`+o`/`+O` abort, rc=2 / rc=1).
>
> **A consumed argument is STILL ADJUDICATED, and that is what keeps the arity fix narrowing.** Teaching the walk arity moves an argument out of the operand slot; merely stepping over it would move a token *out of adjudication*, which is the one direction this section's constraint above forbids — `bash --rcfile <unlisted> <allowlisted>` blocks today on the rcfile and must keep blocking, because an rcfile is a file the shell sources. So the argument is consumed for **operand selection** and adjudicated in place through the identical pair of calls the post-walk operand branch makes. No token is dropped *by the consumption step itself*, and the true operand — previously unreachable behind the argument — is adjudicated as well. `core/hooks/tests/block-destructive.test.sh` pins the whole model as arms `ARITY-01`…`ARITY-19e`; `ARITY-11` is the control for this paragraph specifically, and a consume-and-skip implementation passes every other arm in the block and turns that one red.
>
> **The change is NOT "purely additive", and an earlier form of this section said it was.** The claim — "direction: ALLOW may become BLOCK, never the reverse", offered as *the* property to check every edit against — is false as stated, and a maintainer was being asked to check edits against an invariant that does not hold. Changing which token is the operand necessarily changes post-walk **routing**: when an option's argument is `-c` or `--`, the walk's own labels no longer see it, so a segment that used to route through the cmode loop — which adjudicates every remaining token — now routes through the single-operand branch, and later tokens do leave adjudication. Measured against the pre-arity hook: **64 ALLOW → BLOCK and 15 BLOCK → ALLOW over 4775 payloads**, with an independent dev-testing differential measuring **154 and 23** over a different 4183-payload set. Two sets, same mechanism, no other.
>
> **The property that IS true, and the one to check every edit against, is narrower: every BLOCK → ALLOW must be a *precision improvement* the real interpreter agrees with, never an escape** — and it is checked against the interpreter, not argued from the code. Every measured instance holds: the shape either aborts in the real shell (`-c: invalid shell option name`, rc=1/2), or is genuinely inert (`bash --rcfile -c -n <script>` — rc=0, no output, because the rcfile is *named* `-c` and the `-n` is a real parse-only flag), or executes exactly the token the walk does adjudicate (`bash --rcfile -c <a> <b>` runs `<a>`).
>
> **Do not "fix" this by declining to consume `--` and `-c`.** It restores the literal additive claim and **opens a real hole**: `bash --rcfile -- -c <script>` **executes** `<script>` — measured against real bash with an executable marker, rc=0 and the marker prints — because `--` is the rcfile *filename* rather than an end-of-options marker and `-c` is a real command-mode flag. Under a decline the `--)` label breaks the walk and takes `-c` as the operand, a token no domain claims, and the segment is allowed; consuming keeps it blocked. Arm `ARITY-19a` is that hole and is the arm that goes red if the decline is ever implemented.
>
> **The candidate operand differs PER INTERPRETER, and none of the domains is "any path".** Each admitted interpreter carries its own suffix domain, because an interpreter's operand domain is what that interpreter can actually execute — a single shared suffix set would adjudicate `python3 x.rb`, a file no Python invocation can run, and would make the per-interpreter arms decorative:
>
> | Verb | Operand domain | Rollout posture |
> |---|---|---|
> | `bash` / `sh` / `zsh` | `*.sh` | always-enforce (unchanged) |
> | `python` / `python3` | `*.py` | phase-gated, `DESTRUCTIVE_022_INTERP_PHASE` |
> | `perl` | `*.pl`, `*.pm` | phase-gated, `DESTRUCTIVE_022_INTERP_PHASE` |
> | `ruby` | `*.rb` | phase-gated, `DESTRUCTIVE_022_INTERP_PHASE` |
> | `node` | `*.js`, `*.mjs`, `*.cjs` | phase-gated, `DESTRUCTIVE_022_INTERP_PHASE` |
> | `source` / `.` | `/*`, `./*`, `../*`, `~/*`, `*.sh`, `*.bash` | always-enforce (unchanged) |
> | direct execution (exec arm) | the union above, plus `*.bash` | phase-gated, `DESTRUCTIVE_022_EXEC_PHASE` |
>
> The exec arm's domain is the **union** deliberately: `python3 tools/x.py` and `./tools/x.py` are one execution by two spellings, and adjudicating the first while allowing the second would be exactly the arm-to-arm asymmetry this rule's earlier remediations exist to remove. The domains are written as separate `case` expressions rather than one shared one, so an edit to any of them cannot silently retarget another. The paragraph below states the shell-arm details this table summarises.
>
> **The shell arms' behaviour is unchanged at every position the first view reaches — by construction for their operand domains, and by assertion for their call path**, which now passes through a router that is a pass-through there (arm `AC-ENCL-P5`). The interpreter arm adjudicates an operand ending in `.sh`; an extensionless or differently-suffixed operand (`bash /tmp/evil`) is **not** adjudicated by it. The `source`/`.` arm adjudicates a path-shaped operand — one beginning `/`, `./`, `../`, or ending `.sh` or `.bash`. Two consequences worth stating rather than leaving to be discovered: a literal `~/…` operand reaches the filter only through the `.sh`/`.bash` branches, because the tilde branch is subject to tilde expansion when used as a shell pattern and so never matches a literal tilde token; and an operand that is neither path-shaped nor `.sh`-suffixed is outside both arms. The **exec** arm adjudicates a slash-bearing command word ending `.sh` or `.bash` — the interpreter arm's domain widened only by `.bash`, and deliberately **not** the source arm's wider `/*` domain. Adopting the wider filter was measured and rejected: on the documented-command corpus it finds the identical true-positive set while adding ten regex/awk-fragment false positives and one unresolvable hard-block, and it would leave the exec arm *wider* than the interpreter arm — a fresh asymmetry between arms of one rule, which is the mirror image of the defect the trailing-run normalization exists to remove. The three filters are written as three separate `case` expressions rather than one shared one, so an edit to any of them cannot silently retarget another.
>
> It **cannot** resolve a **variable-bearing path** — a PreToolUse hook sees unexpanded argv, so `bash "$DIR/x.sh"` has no resolvable target. That case **fails closed** (denied) on **both** verbs, consistent with the dependency gate's posture that a control which cannot evaluate its input must deny rather than guess. Invoke with a literal path, or register the resolved path.
>
> **Quoted-fragment suppression (why a described execution is not a blocked one).** The matcher is lexical: it splits raw argv on separators, so a separator and an interpreter appearing inside a **quoted argument** are shredded into fragments that look like commands. To stop the rule firing on text that *describes* an execution rather than performing one, such a fragment is skipped — but the test for "fragment" is **not** whether its own quotes balance. Quote parity cannot decide it: `bash <script>.sh --msg "it's here"` is a real execution whose segment carries one `'`, and `bash -c 'echo hi; bash <script>.sh'` puts a real command in an odd-parity fragment of a program string that genuinely executes. Odd parity is ordinary well-formed shell, not evidence that nothing ran.
>
> The discriminator has **two** conditions, and a segment is skipped only when **both** hold.
>
> The first is **who opened the quote**. Quote state is tracked across the whole command under shell quoting rules (inside `'…'` only the closing quote is special; inside `"…"` a backslash escapes the next character; inside `$'…'` a backslash escapes the next character too, so `\'` does *not* close it — a separate state, because reading it under the `'…'` rule ends one quote out of phase; outside quotes a backslash escapes the next character, so `\'` opens nothing). The command that opened the quote must be one of a small allowlisted set of verbs that cannot evaluate their arguments (`gh`, `printf`, `echo`, `jq`). `git` is deliberately **not** in the set: `git -c alias.x='!<cmd>' x` evaluates its own quoted argument, so it fails the set's membership criterion. A quote any other verb opens is therefore not suppressed, and prose in such an argument that follows a separator is read as commands: `git commit -m "note; if bash <script> then"` is refused — a declared over-block, already true after `then` and `do` and widened by the keywords `if`, `while` and `until` (arm `WRAPDIV-kw-prose`).
>
> The second is **whether the quoting construct itself expands anything**. `'…'` and `$'…'` perform no expansion, so they are inert unconditionally. `"…"` performs parameter expansion, command substitution and arithmetic expansion, so a double-quoted run is skippable only while **untainted** — no `$` and no backtick seen since it opened. An escaped `\$` or ``\` `` does not taint, because the backslash is matched first and consumes the character after it.
>
> **The invariant, and the thing to check any edit against:** *a suppression may fire only when the enclosing context provably cannot cause the shell to evaluate the segment.* A segment whose start state is *outside quotes* begins at **command position** and is **always** adjudicated. An earlier form of this sentence added that unquoted `$( … )`, backticks and `<( … )` were thereby covered; they are not — an enclosure is not a separator, so the verb inside it never starts a segment — and those positions are adjudicated by the second view described in item 3 of the residual list below. Condition 1 is what keeps `bash -c '…'` safe: the quote is opened by `bash`, so no prefix in front of it (`echo x; bash -c '…'`) can reattribute the program string to `echo`. Condition 2 is what keeps `echo "$( … )"` safe: **the shell** expands a command substitution before the enclosing verb ever runs, so a verb that genuinely cannot evaluate its argument does not have to — `$( )` does not *prefix* the inner command, it *encloses* it, and enclosure is not answered by asking about the carrier. Tainting on `$` and the backtick covers the class by construct rather than by shape, since every expansion inside `"…"` is introduced by one of those two characters.
>
> **What that coverage does and does not reach — the claim above is about SUPPRESSION only.** Taint guarantees the segment is never *skipped*; it does not by itself carry the segment's operand to the allowlist. Those are two different things, and reading the first as the second is what let a real bypass sit behind an accurate sentence. A segment lifted out of a command substitution carries the substitution's own closing punctuation onto its operand token, so `echo "$( … bash <script>.sh)"` presents the operand as `<script>.sh)"`. Reaching `check_script_target` therefore also depends on `normalize_script_token` stripping that residue. It previously stripped one quote character per end, which left `<script>.sh)` — a token the interpreter arm's suffix-anchored `*.sh` filter does not match. The segment was adjudicated and then silently dropped at the filter, and the allowlist was never consulted; the `source`/`.` arm survived the identical input only because its filter carries prefix alternatives that trailing punctuation does not disturb. Normalization strips the **trailing run** of shell syntax characters (`| & ; < > ( )` and the three quoting characters) ahead of both filters, so both arms receive a clean token. **The two arms keep their different operand domains** — that asymmetry is deliberate and is preserved; what is now symmetric is that a `.sh`-suffixed operand reaches the allowlist on either arm regardless of the punctuation the enclosing construct left on it. Regression arms in `core/hooks/tests/block-destructive.test.sh` assert the parity over the shared domain and, as the paired specificity control, assert the arms still differ outside it.
>
> **The trailing-run strip applies only to a token that did NOT open its own quote, and the earlier statement of it was false in the other direction.** A previous revision of this paragraph — and of the corresponding comment in the hook — asserted a *direction of error*: that stripping "only ever makes a token MORE likely to reach the allowlist, never more likely to bypass it", and that a path legitimately containing a stripped character "fails toward blocking". That was backwards for the **self-quoted** spelling. The strip ran straight through the token's own closing quote and kept consuming characters that were literal filename content, so `source './core/deploy/deploy.sh)'` — which runs a file named `deploy.sh)`, not allowlisted — normalized to `deploy.sh`, which is. **All ten** declared-stripped characters flipped BLOCK to ALLOW in that one spelling. The reasoning behind the claim was sound and was simply never carried to the stripped set: the carve-out set (`{ } [ ] , . -`, left unstripped precisely because removing them could rewrite one real path into another) had been audited for it, and the stripped set had not.
>
> **What replaces it: deny what cannot be fully resolved** — "denied by construction rather than best-effort-sanitized", the Injection resistance concept in [`core/standards/domain-best-practices/software.md`](../../standards/domain-best-practices/software.md), whose named exemplar is `block-fs-boundary.sh`'s strict branch. A token that **opens its own quote** is read as the shell reads it: everything from that quote to its **matching close** is literal filename, resolvable exactly when the close is the token's last character. `'…/deploy.sh)'` therefore resolves to `…/deploy.sh)` and fails the allowlist on its own merits instead of being sanitized into passing it. A token that opens a quote it never closes, or that closes and then continues, is **not** resolvable — it is denied, and the value carried alongside it is a *filter probe* used only to ask whether the arm's declared operand domain is implicated at all, never to permit. A token that did not open a quote keeps the trailing-run strip unchanged, which is what preserves the command-substitution-tail fix above. Both directions are pinned in `core/hooks/tests/block-destructive.test.sh`: one must-block arm per stripped character, the four carve-out characters as the control that the probe discriminates, and the command-substitution tail as a must-not-regress arm asserted at the same rank.
>
> **The probe is a PREFIX, and asking it a suffix question is how the deny got skipped.** The paragraph above is right that an unresolvable token is denied and that the value carried alongside is a filter probe — but it does not say what a probe *is*, and that omission was load-bearing. When a token closes its own quote and then continues — `bash '/tmp/'evil.sh`, ordinary shell concatenation that runs the real, non-allowlisted `/tmp/evil.sh` — the probe is the resolvable **prefix** `/tmp/`. The interpreter and exec arms' operand filters are **suffix**-anchored, so asking that prefix "do you end in `.sh`" answers *no*: the arm reads the token as outside its own declared domain and skips, and the deny the unresolvable verdict had **already reached** is never raised. `main` and the first remediation both denied this input; a later revision that corrected one layer and left the next deciding on the truncated value regressed it to a silent **allow** — and 1079 green assertions coexisted with that regression, because no arm in the suite covered the shape. The correction is that an unresolvable token's domain is now tested against **both** views the hook holds — the resolved prefix **and** the raw argv token — and the domain counts as implicated if **either** matches: a partial view of a token may add coverage, never veto it. The gate itself is kept rather than removed, because raising the deny above it would block every `bash -c '… ; …'` in the workspace (segment splitting hands that arm the fragment `'echo`). Both directions are pinned: five spellings of the concatenation family as must-block arms, a sixth inner-quoted spelling that resolves cleanly and blocked before the fix as the discrimination control, the `-c` fragment and a `.sh` named inside a suppressed quoted argument as false-positive controls, and — as the control against over-correcting — the pre-existing arm whose **probe** is the half that lands in the domain while its raw token does not, so a fix that *swapped* the raw token for the probe instead of adding it turns red.
>
> **Not claimed:** that every quote-bearing filename resolves. `"./x\".sh"` resolves to `./x\` and fails the allowlist — the safe direction, and a residual rather than a guarantee. It is stated because a comment on this same function has already asserted one impossible direction.
>
> **Here-documents ARE modelled, and this paragraph used to say they were not.** It previously read "Heredocs are outside the model, so suppression is switched off entirely for any command containing `<<`", and that was an accurate description of a blunt latch — `case "$COMMAND" in *'<<'*) script_qbail=1` — which disarmed the whole suppression for any command carrying the operator. It was over-broad in three separate ways: it matched a `<<` inside a **quoted argument**, where the characters are text and not an operator; it matched a here-**string** `<<<`, which is a single word the quote model already covers; and it disarmed the command for a here-document with nothing to do with the quoted argument in question. Measured on the shipped hook before the change: a script invocation quoted inside a `gh … --body` argument was **allowed**, and the identical bytes plus an unrelated trailing here-document were **blocked**. The machinery was already correct and was being switched off.
>
> **What replaces it: a pre-pass that excises only provably-inert bodies.** A here-document body is, by POSIX Shell Command Language 2.7.4, the *input data* a redirection supplies to a command — the shell never parses it as a command list. That is the same class of grammar authority this rule already relies on at 2.9.1 for the assignment-prefix walk and 2.9.1.1 for the exec discriminator, so the exemption extends an existing basis rather than introducing a new one. The pass runs **before** the separator substitution, because that substitution injects newlines indistinguishable from the true newlines a body is delimited by; detecting bodies after it fails **open** on an operator line that carries a post-operator command. A body is removed from the adjudicated text only when **both** of the rule's existing suppression conditions hold, extended by one term: **(1) carrier** — the command *receiving* the redirection is in the existing `gh|printf|echo|jq` set, resolved from the last quote-state-0 separator before the operator rather than from the head of the line, so a carrier ahead of a separator cannot lend its exemption to a real interpreter that receives the redirection after it; and **(2) construct-inert** — the delimiter is quoted (`'D'`, `"D"`, `\D`), or it is bare and the body contains neither `$` nor a backtick, which is the identical two-tier split already applied to `'…'` versus `"…"`. The decision is **all-or-nothing**: if any here-document in a command fails either condition, nothing is excised and the bail latches, so every shape the model declines keeps its pre-change verdict bit-for-bit rather than receiving a partially rewritten text whose verdict nobody measured. The same latch covers every shape the model cannot resolve — an unterminated body, a delimiter outside the accepted word charset, more than two here-documents queued on one line, more than eight in a command, or the work budget. No branch keys on a markdown fence, on "report"-like phrasing, on a CLI flag name, or on any other forgeable property of the body text.
>
> **What newly passes, exactly, and the four residuals it leaves.** The class admitted is: *the body of a here-document whose delimiter is quoted, or is bare with a body free of `$` and backtick, redirected into `gh`, `printf`, `echo` or `jq`.* Nothing else.
>
> 1. **Carrier impersonation.** A shell function or alias named `gh` makes the head token a carrier while the body executes; this rule cannot see prior-turn state. **This is not a new residual** — the quoted-argument suppression above already carries it, and ships allowed. The change grows that residual's *surface* from quoted arguments to here-document bodies; it does not change its *kind*, its precondition, or its fail direction. That is the honest cost of the change, and it is why the carrier set is reused at its current value rather than widened.
> 2. **A bare-delimiter expansion introduced by neither `$` nor a backtick.** None exists in POSIX. This is the same claim condition (2) already makes for `"…"`, so if a shell ever adds a third introducer both suppressions break together — the correct coupling, since it is one claim and not two.
> 3. **Enclosure positions are adjudicated by a second view, and this item states what that view reaches and what it does not.** A substitution is not a separator, so the inner command word of `echo "$(bash <x>.sh)"`, `` `bash <x>.sh` ``, `cat <( bash <x>.sh )` or `( bash <x>.sh )` never reached command position, and until the view existed each was allowed with nothing recorded. The second view gives every `(` and every backtick a command position of its own, appends the rest of the segment, cuts it at the position's own closer — scanned from a fresh quote state, and left whole when no closer is found within 200 steps — and runs the same walk there; an opener behind an odd run of backslashes opens nothing. It runs after the first view has finished, so it can add an adjudication and can never remove one. A shell or `source` finding at such a position follows the third phased family (the paragraph on it above): at the shipped `warn` phase it is **recorded, not refused**, until the graduation decision. A direct execution or a non-shell interpreter there is recorded at its own arm's phase. Two exemptions written for the head of the line are read at the enclosure as well: a segment the first view suppressed is re-opened when the command that owns its quote sits inside an enclosure, and a here-document body is excised only when the receiver read from the line head **and** the receiver read from the innermost open enclosure are both carriers. That here-document fix has two measured limits: it does not reach a receiver behind a line continuation, because the pre-pass reads physical lines, and it newly flags a carrier's unquoted substitution that reads a here-document through `cat`, where nothing runs. Two first-view corners move toward refusal: the pre-pass's scan now also stops at `(`, `)` and the backtick, so its shared work budget is spent sooner on a command dense with openers, and at `enforce` a body the second receiver reading declines is no longer excised. **What follows is the limits known and measured, and the list is non-exhaustive by declaration.** *Not reached:* every residual of the prefix walk that item 2 of the scope list below declares, inside an enclosure as outside it, because the view runs that same walk and inherits whatever it does not read; a `case` arm, at top level or inside an enclosure, whose command position follows a pattern's closing parenthesis; `coproc`; a command substitution opened by neither a parenthesis nor a backtick, at which the view opens no position, so a spelling of it is adjudicated only where the first view happens to split or walk into its verb; a backtick substitution nested through escaped backticks; quoting the cut does not model — ANSI-C quoting (`X=$'\')'`) or a `)` inside a parameter expansion (`${Y:-)}`) ends a position's text before the verb; an apostrophe in a nested double-quoted string, which turns the carried quote state over so that a carrier's exemption suppresses a real substitution; a carrier at the head of an unquoted substitution, whose exemption a later program string inherits; a here-document receiver behind a line continuation; and a command past either work budget — more than 512 enclosure openers, after which no further position is opened, or an operand lying beyond a nested opener once 262,144 bytes of remainder have been copied. The position ceiling counts every opener, quoted or escaped, so enough openers of inert text ahead of a substitution leave it unseen. *Adjudicated although nothing executes:* a quoted argument of a command outside the carrier set, a here-document body left in place, a comment, text after a closing backtick — where a sentence's full stop after a code span reads as the dot command, so its row can name a path such as `/` — a quoted argument that follows an unquoted enclosure in a carrier's argument list, an array literal, and an escaped dollar under a non-carrier. That is the posture this rule already takes for `;`, `&` and `|` in the same text; those shapes record now and are refused once the phase graduates. *Cost:* the budgets bound positions and copied bytes, not time. A long run of openers is slow — 500 parentheses took about 17 s on the reference host, where the hook before the view took under 2 s — and a command hook past the harness's timeout does not block; the first view has finished before the second starts, so a stall loses only the second view's own findings. *What pins these limits, exactly:* an `AC-ENCL-RESIDUAL-*` arm pins each limit this item names at today's verdict, paired with a copy of the hook on which it fails, with these exceptions. `coproc` and item 2's brace group are pinned only at top level, by rows of corpus group `open-encl` that record today's allow. Nothing pins the prefix-walk residuals inside an enclosure, the substitution opened by neither a parenthesis nor a backtick, the position ceiling's counting of inert openers, or the pre-pass budget spent sooner on a command dense with openers; and the cost is a measurement, not a pin. A green here-document arm is still not evidence about any of them.
> 4. **A non-carrier receiver keeps the false positive.** `cat <<'RPT'` still blocks. Deliberate, and in the direction this rule's gating already demands: a verb missing from the set costs a false positive and can never admit an evasion. `cat` and `tee` are plausible additions that would remove this residual; they are deliberately not added by a change whose job is to narrow.
>
> Membership in the carrier set is now a **conjunction**, because the one set gates two suppressions: a member must both be unable to evaluate its *argument* (what the quoted-fragment rule asks) **and** not execute its *stdin* (what the pre-pass asks). The four current members satisfy both. A verb that satisfies the first but not the second would be a fail-open on the pre-pass while remaining sound above, so both questions must be answered before a member is added.
>
> The gating direction is deliberate and is the second property to preserve if the set is ever edited: a verb **missing** from it means a false positive persists, and can never mean an evasion is admitted. The inverse construction — a denylist of *evaluating* verbs — would make one missed entry a silent fail-open, which is not an acceptable trade inside a fail-closed control.
>
> **Direct execution is IN scope, and this sentence used to say the opposite.** Until D-ScriptScope was rendered, this paragraph listed direct execution of an executable script (`./x.sh`, no interpreter token) among the forms out of the rule's scope "by construction, not by defect". That was a description of the matcher's shape presented as a decision, and it was never decided: the operator has since resolved that this allowlist governs **execution capability**, not interpreter invocations only. Direct execution is adjudicated by the `exec` arm above, currently at rollout phase `warn`. The prior wording is recorded here rather than deleted, because a reader who remembers it needs to know it was reversed on purpose.
>
> **The forms out of this rule's scope are the following, and this list is explicitly NOT exhaustive.** It previously opened "Two forms remain out of this rule's scope by construction, not by defect" and then named two — a closed enumeration, with no exhaustiveness disclaimer anywhere in this fragment, of a set that was already larger than two. That wording is the defect being corrected here, and it is worth naming as its own class: a closed enumeration of a control's limits is a *coverage claim*, and an unqualified one ages into a false one every time a new limit is measured. Read the list below as the limits currently **known and measured** — it is **non-exhaustive** by declaration, and is not the complete set; anything not named here is undetermined rather than covered.
>
> 1. **A script fetched or generated at runtime** is not visible as a path at PreToolUse time.
> 2. **Wrapper-prefix residuals.** Command position is now resolved by *walking* a prefix run — variable assignments, plus a bounded transparent-wrapper set (`sudo`, `env`, `command`, `builtin`, `exec`, `nohup`, `time`, `xargs`, `nice`, `stdbuf`, `timeout`, and the compound-command keywords `then`, `do`, `else`, `elif`, `if`, `while`, `until`, `in`, `!`) matched on basename, in any order and interleaved, each wrapper's own options and operands walked from its row — so the class this item once declared wholly open is closed for the listed words and the options their rows list. What remains open: **`eval`**, deliberately not in that set (it re-parses a program string this lexical matcher cannot resolve, the same nested-shell residual recorded for `bash -c '…'`); **launchers outside the set**, which resolve as the command word so the invocation behind them is not adjudicated — `doas`, `setsid`, `ionice` and `chrt` (the four the SIGPIPE-idiom lint's list names that this set does not), `caffeinate`, `watch`, `flock` and others (corpus group `wrap-declared`); **an option a wrapper's row does not list that takes a separate value**: the walk steps over an unlisted option as a flag and reads the value behind it as the command word (arm `WRAPDIV-unlisted-valued`) — and an abbreviation of a listed long option is not such an option, because a long option is read the way its program's parser reads it: every row with long options belongs to a getopt_long program (GNU coreutils' `env`, `nice`, `stdbuf`, `timeout` and `nohup`, GNU findutils' `xargs`, GNU `time`, and `sudo`), which takes an exact name, or any prefix naming exactly one of its long options, for that option, so each row carries its program's own option table and `nice --adj 10 bash <script>` and `env --split=<script>` are read as `--adjustment` and `--split-string` (arms `WRAPOPT-ab-*`, one per argument-taking long option at its shortest prefix), while a prefix of two or more options, or a name that is none, is kept as written and stepped over as a flag, and the program rejects it and runs nothing (arm `WRAPDIV-ab-ambiguous`); `exec`, `builtin` and `command` are shell builtins that read no long option; **a wrapper word or option written inside quotes** (`"sudo" bash <script>`): the walk reads the raw token (arm `WRAPDIV-quoted-word`); **a leading redirection** and **an escaped verb** (`>/dev/null bash <script>`, `\bash <script>`), which the canonicalizer steps over for the anchored rules and this walk does not (arms `WRAPDIV-redirect`, `WRAPDIV-escaped`); **a command line carried as one string** — `env -S "bash <script>"` (arm `WRAPDIV-env-S-quoted`), and the attached `env -S<command>`, by every spelling the parser takes for it — `env --split-string=<command>` and its prefixes, so `env --s=bash <script>` is allowed as `env -Sbash <script>` is — which the walk stops on and adjudicates as one token, exactly as it did before the rows existed (arms `WRAPDIV-env-S-attached-cmd`, `WRAPDIV-ab-split-cmd`) — an attached value written without shell quotes and carrying no slash that carries no command word of its own, empty or only options or an assignment, is not this residual: the walk goes on to the command that follows it, and an arg-taking option in the value consumes its separate argument (arms `WRAPOPT-sn-*`, corpus group `wrap-split-nocmd`); **two split-value classes stay open, on an always-enforce arm** — a split value written with shell quotes, and a split value carrying a slash (a value that holds a `/` is read as a command word, so an option carrying a path inside the value keeps the verdict it had before the rows) — and in both the program the guard models runs an unlisted script while the guard allows the line; neither is a regression, because the guard as it stood before this release behaves the same, and the open card that owns their fix is named under this section's References; **`xargs` with a replacement operand** (`xargs -I{} bash {}`), whose path arrives on standard input while the argv operand is a placeholder, and an interpreter flag after `xargs <interpreter>`, as the `xargs` paragraph above states; and **the brace group** (`{ bash <script>; }`), a *segmentation*-layer residual rather than a prefix one — the first view separates on `;`, `&`, `|` and newline only, and the second view opens a position after `(` and the backtick, not after `{`, so a verb behind `{` is at no position the walk reaches. The parenthesised group `( bash <script> )` is adjudicated by the second view (item 3 of the residual list above). Some spellings are read differently from what runs, each declared: a malformed `timeout <command>` with no duration is read one token late (arm `WRAPDIV-timeout-malformed`); `sudo -l`, `sudo -v`, `sudo -e` and `command -v` execute nothing and are not adjudicated; the long spellings of those `sudo` options (`--list`, `--edit`) are read as flags, so what follows them is adjudicated (arm `WRAPDIV-sudo-long`); and three shapes the walk used to read as a direct execution are now read as what the program does with them — an option argument shaped like a script path (`env --chdir=<path>.sh ls`, `sudo -D<path>.sh ls`, and the same through a prefix of a long option, `env --c <path>.sh ls`), an `env` operand whose name is not a shell name (`env a-b=<path>.sh ls`), and a dash-led token whose option name no row lists, unknown or a prefix of two or more options, carrying an attached script path (`env --zz=<path>.sh ls`, `sudo --c=<path>.sh ls`, `env -Z<path>.sh ls`, `exec --zz=<path>.sh ls`), which the walk steps over as a flag and the program rejects — none of which executes the path (arms `WRAPOPT-optpath`, `WRAPOPT-optpath-short`, `WRAPOPT-envop-name`; corpus group `wrap-prec-name` for the third). What was run, stated exactly: six of the eight corpus rows that record the first two classes (group `wrap-prec`) were run at the card's Stage 7 on the reference host's own programs, each in a sandbox holding only marker scripts, and none executed the path — `env --chdir=<path>` through the host's own `-C` spelling, because the host's `env` reads no long option; `sudo -D<path>` and `xargs -a<path>` were not run and rest on the published manuals, as do the rows that reach the class through a prefix (group `wrap-abbrev-prec`) and the rows of the third class (group `wrap-prec-name`), which were not run either; the third class rests on the parsers' documented rejection of an unknown or ambiguous option.
> 3. **A path bearing whitespace inside its quotes** — `bash '/tmp/a b.sh'`. This one is NOT the quoted-flag or quoted-verb class fixed above and is not closed by that fix; it is a **separate root cause**, and the distinction is load-bearing. Those two were matchers reading an un-normalized token, so normalizing the token reaches them. This one is upstream of normalization entirely: the matcher splits raw argv on whitespace *before* any token exists to normalize, so the operand token is `'/tmp/a` — the real filename's first fragment. Neither that token nor its probe ends `.sh`, so no arm's operand domain is implicated and nothing is adjudicated. Measured identical on `main`, on this branch's tip, and after this fix. Closing it requires **quote-aware tokenization** — not splitting a quoted span on its interior whitespace — which is a change to the primitive every arm traverses, and it was deliberately not attempted inside this fix: a half-correct tokenizer would be wrong for shapes nobody has enumerated, which is a worse outcome than a declared gap. Arm `F1-QTOK-RESIDUAL-space` pins the current verdict so that closing it later is a deliberate act rather than a drift. The same first fragment is also what remains open of the flag walk's quoted-token family, beside a word whose own value is the operand (item 9): it ends the walk, so an earlier parse-only grant stands at it, while the quote-led flag beside it is closed for a whole word the walk steps over unquoted; arm `FWALK-QWORD-ctl-fragment-noexec` pins the current verdict beside `F1-QTOK-RESIDUAL-space`. The same split reaches the verb through a quoted **assignment value**: `FOO='a b' bash <script>` is not adjudicated, because the value's second piece is read as the command word, and in the other direction `MSG='run bash now' echo <path>.sh` is refused, because a piece of the value is read as an interpreter invocation (arms `WRAPDIV-qval-sq`, `WRAPDIV-qval-fp`); a separator inside the quoted value splits the segment instead (`FOO='a;b' bash <script>`, arm `WRAPDIV-qval-sep`). Both directions are declared here and not closed: a step over the value's pieces must never cross a value that runs a command, and its fix is owned by its own card.
> 4. **A verb whose token cannot be fully resolved** — `'ba'sh <script>`, a token that closes its own quote and then continues. The verb resolver reads the normalized basename only when the token resolves to exactly one filename; when it does not, the value in hand is a strict prefix, and a prefix can name a verb the whole token does not (`'bash'x` probes to `bash`). Routing an arm on that evidence would be the same subject error the fix above closes, pointed the other way, so it is declined and recorded here instead.
> 5. **An extensionless target** — see the shared-residual paragraph below, which states it across all three arms.
> 6. **A path that is fully resolved and ends in a shell metacharacter** — see the suffix-anchoring paragraph below, which states which arms reach it and which do not.
> 7. **Portability of the exec arm's system-bin exemption set** — see the stated-limit paragraph at the end of this section.
> 8. **A value-taking flag whose ARGUMENT is itself an allowlisted script path** — `bash --rcfile <allowlisted>.sh <script>`. This was a fail-open while the walk had no notion of arity: the scan stopped on the allowlisted argument and never reached the script. **It is closed for the options the arity table names, read exactly:** the walk consumes the argument with its option, still adjudicates it, and goes on to the script (arm `F2-FWALK-RESIDUAL-flagarg`). An option the walk cannot read exactly — `--rcfile""`, `\--rcfile`, `$X--rcfile`, `--{norc,rcfile}`, or a listed option whose own argument may be no word — takes the conservative route instead (the paragraph on unreadable options above). **What remains open** is an option that takes an argument and is in no table: the non-shell interpreters' (the third residual below), and any the measured sweep behind the arity table missed. The other side of the old limit is unchanged and still declared: a non-allowlisted script in an option's argument slot is refused even when the real operand is allowlisted, which over-blocks and is recoverable.
> 9. **A flag-position token that opens with a quote and closes it early** — `bash ""-x <script>`, `bash -n ""+n <script>`, `bash '-x.s'h <script>`. It is closed for a whole word the walk steps over unquoted: the flag walk reads a token that opens with a quote and closes every quote it opens as its unquoted spelling — a word whose exact value begins with `-` is read so whatever its suffix, unless the normalizer, the probe or the raw token claims it first — or, where argv does not determine that spelling, adjudicates what follows it, as the paragraph on the walk's boundary above states. What remains open is the fragment case, which is limit 3 above, and a word whose own value is the operand: `bash '+x.s'h <script>` ends the walk where `bash +x.sh <script>` ends it, and the operand path, which reads the probe and the raw token only, adjudicates nothing — the split-suffix operand, which its own card owns. It includes two words the reading never reaches, whatever their first character — the token behind an end-of-options `--`, and an option's consumed argument — so `bash -- '-x.s'h <script>`, `source -- '-x.s'h` and `bash --rcfile '-x.s'h -i` are allowed where their unquoted spellings are refused, and each runs the file the word names. The neighbouring class the reading does not reach — a flag that begins with `-`, `+` or a backslash and carries a quote, a backslash, or a brace or glob character, such as `bash --rcfile"" <allowlisted>.sh <script>`, `zsh --emulate"" -n <script>`, `bash \-c '<program>'` and `bash --{norc,rcfile} <allowlisted>.sh <script>` — is closed by the walk rather than by this reading: the option-run latch keeps a `-n` behind such a flag from granting, and under an interpreter the flag takes the conservative route, as the paragraphs above on where the `-n` stands and on an option the walk cannot read state.
> 10. **A program that arrives on standard input** — `echo '<program>' | bash`, `cat <script> | bash -s`. A PreToolUse hook reads the command line, not the pipe, so the program is not visible and this rule does not adjudicate it (arm `STDIN-PIN-03`): the same reach limit as item 1, and the reason `xargs <interpreter>` with no operand is refused above. A shell is **not** refused for reading its program from stdin — that refuses `echo '<program>' | zsh -s`, the ordinary form, and arms `STDIN-M1*` pin that a deny does exactly that. **What the walk does with the command line of such an invocation is unchanged, and three consequences are declared.** A file named by a redirection (`bash -s < <script>`) is on the command line and is adjudicated (arm `STDIN-PIN-02`). A `-n` that follows the first non-option argument is not read as a flag, here as everywhere (the grant paragraph above). And a script-suffixed word behind `-s` is adjudicated as if it were the script: `bash -s <unlisted>.sh` blocks (arm `PARSE-12c`), although under `-s` that word is a positional parameter the shell does not execute by itself. That over-block is kept on purpose. The stdin program can execute its positional — `echo 'bash "$1"' | bash -s <unlisted>.sh` runs it (arm `STDIN-PIN-01`) — the hook cannot read the program to tell, and a walk that stopped adjudicating positionals allowed every measured spelling of that. It is not a boundary either: the same program behind an allowlisted positional is allowed. That is why this item is a limit and not a coverage claim, and the walk-payload corpus keeps its measured spellings in a group marked open.
>
> **Item 2 used to declare the whole wrapper class deliberately open, and that reasoning was refuted rather than merely superseded.** It argued that closing the class "requires a denylist of evaluating verbs" whose one missed entry would be a silent fail-open. That argument belongs to the **suppression** set above, where a missed entry does exactly that. It does not transfer here: the wrapper set gates *adjudication*, not suppression, so its failure directions are the mirror image — a missing word leaves the status quo, and a wrongly-included word over-blocks, which is recoverable. The class is closed for the enumerated words and the options their rows list; item 2 names what is left.
>
> A third limit is a **shared residual** rather than a scope boundary: an **extensionless** target escapes every arm. `./x` is not adjudicated by the exec arm and `bash /tmp/evil` is not adjudicated by the interpreter arm, for the same reason — both operand filters are suffix-anchored. It is one residual across three arms, not three, and `core/hooks/tests/block-destructive.test.sh` pins it so that widening any arm to cover it is a deliberate act rather than a drift.
>
> **Three further residuals belong to the admitted-interpreter set, and each is declared rather than half-closed.**
>
> 1. **Versioned interpreter spellings** — `python3.11 x.py`, `ruby3.1 x.rb`. Not covered. The interpreter set is a closed exact-literal enumeration, and the safe way to reach these is **not** a trailing glob (see the closedness argument in the "what this rule resolves" paragraph above — a glob would silently remove a script named like an interpreter from exec-arm adjudication) but an **order change**, running a slash-bearing token's exec test ahead of the verb `case`. That belongs to the operand-locating walk, not to this enumeration.
> 2. **Unadmitted interpreters** — `pwsh`, `awk`, `osascript`, `php`, `deno`, `bun`, `Rscript`, `tclsh`, `lua`. Closing any one is a `case` label in the classifier, one operand-domain row, one row in each of the parse-only, option-arity and command-string tables (or that table's documented null), and one measured test arm; the structure is built for it. **`awk` is a deliberate exception rather than an oversight:** its script operand arrives through `-f`, a flag *argument* the operand walk does not consume, so an `awk` label could never reach its operand — a dead branch on a security surface. `core/hooks/lib/positional-issueref.awk` states the same boundary from inside an unrelated library, and that in-source statement is a fourth uncoordinated copy of this set's edge: **an editor admitting `awk` must update it too, or it silently falsifies.**
> 3. **Option-taking flags of the admitted interpreters — the space-separated-argument case is adjudicated now; the arity residual remains declared.** The walk now advances past a flag whose argument the operand domain does not claim, so `python3 -X faulthandler <unlisted>.py` and `perl -I lib <unlisted>.pl` are adjudicated — arms `T-NSI-09a` and `T-NSI-09b` assert that verdict, with `T-NSI-09c` as the control that the same invocation *without* the flag is adjudicated in the same run. What remains is the non-shell interpreters' option arity, which rests on the explicit documented null the parse-only and arity paragraphs above record for them: a flag whose argument is *attached* to it, an inline program (`-c`, `-e`) and a module (`-m`) are not measured on this surface and are owed under a graduation of the interpreter arm rather than closed here. The fourth, the allowlisted-flag-argument limit, is measured now that the `.py` domain holds rows: with no arity table for these interpreters, an allowlisted `.py` in an option's value position is taken as the operand and admitted, and the script after it is never read — `python3 -X <allowlisted>.py <unlisted>.py` allows with no row, where before the first row it drew one. Arms `NSI-F2-RESID-python3` and `NSI-F2-RESID-python` pin that verdict, `NSI-ROW-01` shows the row live, and `NSI-F2-ctl-unrowed` shows the same line with an unlisted value still recorded. The perl, ruby and node domains hold no row, so the shape is not open for them yet; it is owed under a graduation with the other three. The direction is the same as this widening's — it strictly *increases* what these domains see and never decreases it.
>
> **`env`-mediated invocation is NOT a residual, and is stated because a reviewer will ask.** `env python3 x.py` resolves correctly today: `env` is already in the transparent-wrapper prefix set the command-position walk steps over, so the classifier sees `python3` at command position.
>
> **The same suffix-anchoring has a second reach worth naming here, because this paragraph used to record only the extensionless half of it.** A path that is fully resolved and *ends in a shell metacharacter* — `…/deploy.sh)`, the literal filename a self-quoted operand can name — is also not `.sh`-suffixed, so it too falls outside the interpreter and exec arms' filters. The **source** arm covers it, because that arm's filter carries prefix alternatives (`/*`, `./*`, `../*`). So the deny-what-cannot-be-resolved fix above closes the manufactured-allow on every arm, and the executed file is *blocked* on the source arm; on the interpreter arm it is *not adjudicated*, for the same suffix-anchoring reason `bash /tmp/evil` is not. That is a change of mechanism (from a bypass, to a declared domain boundary) without a change of verdict on that one arm, and it is pinned as such rather than described as closed.
>
> **The exec arm carried a fourth limit that this section did not record at all, and it was not a residual but a gap.** Its system-bin exemption was reused from `ANCHOR_PREFIX_BASH` and included `/opt/homebrew/bin`, a directory the agent can write to without elevation — so a script placed there and executed directly was exempt from adjudication entirely. That is now fixed at its root (the exec arm owns its own root-owned-prefix set); the correction is stated in full above under the exec arm's discriminator, and the point of recording it here is that a section listing this rule's limits omitted an exemption that removed coverage outright.
>
> **That exemption had a second defect of the same shape, which is why owning its own set was not yet enough.** Narrowing the prefix list fixed *which* directories are exempt; it left the exemption deciding on the wrong **subject**. The test was a glob against the raw token, and a token is not a location: `/usr/bin/../../tmp/evil.sh` matches `/usr/bin/*` and executes `/tmp/evil.sh`, so the exec arm exempted it and never adjudicated it — while `bash /usr/bin/../../tmp/evil.sh`, the same file through the interpreter arm of the same rule, blocked. Same file, same hook, opposite verdicts, on **all four** exempted prefixes. The exemption now resolves the path first — reusing the `os.path.realpath` primitive this hook already uses, with the opposite failure direction, because a check that cannot resolve must still check while an exemption that cannot resolve must not exempt — and exempts only when **both** the token and the resolved path fall under the set. That `AND` is deliberate: it can only narrow, where resolving first and testing only the result would newly exempt a relative `./usr/bin/x.sh` evaluated under `/`. An **unresolvable** token is never exempt, for the reason the rest of this arm already gives — a filename that cannot be determined from argv cannot be shown to live in a trusted directory. Pinned by one must-block arm per exempted prefix, an interpreter-arm control that states the asymmetry, an unresolvable-token arm, and a must-not-flag arm for a traversal that leaves and re-enters `/usr/bin` — which fails any implementation that merely rejects `..` instead of resolving it.
>
> **Stated limit — the exemption set is not portable, and nothing in this repo detects that.** The four retained prefixes were *measured* `root:wheel drwxr-xr-x` on the reference host: an Apple Silicon macOS machine, where Homebrew lives at `/opt/homebrew` and that directory measured `drwxrwxr-x` owned by the operator's admin group, which is precisely why it was removed. `/usr/local/bin` is root-owned **there for that reason**. On **Intel** macOS, Homebrew installs into `/usr/local`, where `/usr/local/bin` is group-writable by `admin` — the same agent-writable condition that disqualified `/opt/homebrew/bin`. So on an Intel host this set exempts a directory the agent can write into without elevation, and no check in this repo measures the mode of these directories at deploy or CI time. This is recorded as a known limit rather than solved: a runtime stat of each prefix is a separate change carrying its own failure modes (a stat that fails, a mounted volume, a container with no such directory), and naming the boundary honestly is worth more than a half-portable guess made inside an unrelated fix.

> **Second gate on governance-file writes (scope of the -019 worktree exemption).** The BLOCK-DESTRUCTIVE-019 worktree exemption (allowing a Write/Edit whose resolved target sits inside a repo-rooted worktree) does NOT clear governance-file writes on its own. `block-autonomy-ceiling.sh` BLOCK-AUTONOMY-001 independently blocks writes to its own governance set as an irreducible Tier-0 operator-only action, with NO worktree exemption. A rule's properties belong to the rule that owns them.*

> **Worktree exemption — keyed on the write target, two views.** `-019` reads one subject for its exemptions and its classification alike: the **write target**, never the session's working directory. A session launched in the primary checkout may Write/Edit into its own worktree, and a session inside a worktree may **not** Write/Edit a primary Layer-1 path — a deliberate tightening, since a worktree session has no business writing the primary checkout. An exemption is granted only when **two views agree**. The target **as written** is the entry gate: it must carry no `.` or `..` segment and must sit inside the exemption's home. Its **resolved location**, computed by the hook's fail-closed resolver, must sit in the **same** home. There is no raw-path fallback, so a target the hook cannot resolve — a symlink leaf that did not resolve, or any target when `python3` is unavailable — receives no exemption. The workspace root is resolved by that same resolver and fails closed the same way; a root resolved by a second canonicalizer would disagree with the target on a root that is absent and spelled through a symlink (a sandboxed `HOME` on macOS), turning every exemption into a block. The home is `pmo-platform/.claude/worktrees/<name>/…`, anchored at the repo root and requiring the `<name>/` segment. A `.git` leaf below that base is excluded, in both views and in any case spelling: in a linked worktree `.git` is a pointer file, which `-016`'s `.git/config|hooks|info` arms do not reach, and no Write/Edit workflow writes one. The block message names the refused target. **Coverage boundary:** the verdict is keyed on the target, but the rule's reach is not — the scope gate keys on the working directory, so under condition 1 above a session rooted outside the governed workspace root never reaches this rule. **Residual:** the Write/Edit-vs-Bash residual below is not closed by this re-key.

> **Analysis-workspace carve-out (scope, and why the predicate is static).** `-019` exempts the git-ignored analysis workspace — `pmo-platform/analysis/<subfolder>/…`, the home `core/standards/analysis-workspace-standard.md` §1 designates. The exemption requires a **subfolder segment** (so the one *tracked* file, `analysis/README.md`, stays blocked), refuses any path whose as-written spelling contains a `.` or `..` segment (the hook's normalizer falls back to the raw path when neither the target nor its parent exists, and a `case` glob matches across `/`), and grants only when the resolved location agrees (the two-view rule in the worktree paragraph above). It is anchored at the repo root, so a directory named `analysis` elsewhere in the tree is **not** exempt. **The predicate is a static pattern in the hook source on purpose:** the hook source sits inside `.claude/hooks/*`, which this very rule and `BLOCK-AUTONOMY-001` both protect. An exemption authored in an agent-writable surface — an allowlist file under `.claude/`, or git's own ignore resolution, which `git config --global core.excludesFile` re-points with no rule in the way — would make the self-modification guard's escape hatch writable by its own subject.

> **Roadmap-instance carve-out.** `-019` exempts the git-ignored roadmap instances — `pmo-platform/roadmaps/<name>`, the home the operator configuration's `operator_instance_roadmaps_path` defaults to — under the same two-view rule. The home is **flat** (one file per roadmap), so there is no subfolder segment to key on. The one *tracked* file, `roadmaps/README.md`, is excluded by name and **in any case spelling**: a case-insensitive volume resolves `readme.md` to it, and realpath keeps the spelled case. Any **dot-leading leaf** is excluded too: git reads an ignore file at the top of a flat home, and one could re-include the ignored instances, which the analysis home's subfolder segment rules out. The exclusions rest on a premise — `README.md` is the only tracked file under `roadmaps/` (`.gitignore`: `/roadmaps/*` + `!/roadmaps/README.md`) — so re-check them whenever `.gitignore` changes there. The predicate is static, like the analysis one, and anchored at the repo root, so it does **not** follow a repointed `operator_instance_roadmaps_path`: an instance home configured elsewhere is not exempt.

> **Tool-path coverage residual (Write/Edit vs Bash) — ACCEPTED.** `-019` is a **Write/Edit-matcher rule only**. The Bash branch of this hook carries **no** Layer-1 write guard: `BLOCK-DESTRUCTIVE-009` blocks `rm` on `pmo-platform/`, and nothing intercepts `cp` / `mv` / `tee` / `mkdir` / `sed -i` / `install` / a shell redirect / an interpreter's own file write. A Bash-mediated write to a tracked Layer-1 path therefore succeeds in a session where the same write via `Write` is denied. **Do not read `-019` as sealing the tree it names — it raises the cost of the Write/Edit path, it does not close the tracked-path surface.** Closing it would require a general Bash file-write detector over an open-ended command surface; this hook's own `-022` documentation already records that a closed enumeration of shell forms was measured smaller than the real set, which is the same failure mode one directory up. That is a new capability, not a defect fix, and it is out of scope for this corrective change. **Direction of travel:** for the analysis subtree and the roadmap instances the two tool paths now *agree* (both permitted), and so do they for a primary-rooted session writing into a worktree, so those changes reduce the asymmetric surface. For tracked Layer-1 paths the asymmetry is unchanged, except that target keying widens it for one session shape: a worktree-rooted session writing a primary Layer-1 path, which the Write/Edit path now refuses and the Bash path still permits.
