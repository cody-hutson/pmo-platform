## `block-rm-prefer-trash.sh` (BLOCK-TRASH-001..003)

| Field | Value |
|---|---|
| Hook | `.claude/hooks/block-rm-prefer-trash.sh` |
| Matcher | Bash |
| Scope | Workspace-scoped deletion containment; `rm`/`rmdir`/`unlink`/`trash`/`osascript` Trash-verb whose resolved path is outside `${HOME}/Claude/` or unresolvable under strict policy; `rm` inside workspace redirects to Trash via auto-detected command; one admitted class outside the workspace — a Trash-verb move of a single auto-memory entry (see Memory-store arm below) |
| Mode | Always-enforce (matches `block-destructive` / `block-credential-reads` posture; not gated by `.claude/hooks/.mode`) |

### Rule registry

| Rule ID | Description |
|---|---|
| BLOCK-TRASH-001 | `rm`/`rmdir`/`unlink` (at any command start; a `git` command exempts only its own segment) with resolved path outside `${HOME}/Claude/`, OR unresolvable under strict policy (variable / `$(...)` subshell / backtick tokens; a target word that is not literal, a home-relative word on a line that names `HOME`, another tilde prefix or a zsh equals-word; a target the hook cannot normalize into the workspace root's form — see Path Resolution), OR an `rm`/`rmdir`/`unlink` segment that does not name all its targets on its line (no target operand, or the line continues), judged after every other step. On an auto-memory entry the memory-store arm would admit, the refusal names the Trash move instead of telling the caller to cancel |
| BLOCK-TRASH-002 | `rm`/`rmdir`/`unlink` (at any command start; a `git` command exempts only its own segment) with resolved path inside `${HOME}/Claude/` — blocks permanent deletion; stderr suggests Trash-equivalent command (auto-detected via 3-tier: `trash` in PATH → `/opt/homebrew/opt/trash/bin/trash` → `osascript` Finder fallback) |
| BLOCK-TRASH-003 | `trash` invocation (bare, at a canonical bin prefix, or at the keg-only location `/opt/homebrew/opt/trash/bin/trash` that the tier-2 suggestion names) OR `osascript` Trash-verb (`delete POSIX file`, `move ... to trash`) with resolved path outside `${HOME}/Claude/`, OR unresolvable under strict policy, OR a Trash invocation whose segment does not name all its targets on its line (no target operand, or the line continues — strict policy: a Trash program can act on what the line does not name). `trash`/`osascript` Trash-verb targeting paths INSIDE the workspace are explicitly ALLOWED (the approved deletion mechanism). Outside the workspace, a Trash-verb move of a single auto-memory entry is likewise ALLOWED (see Memory-store arm below); every other outside target is refused |

### Path Resolution — block-rm-prefer-trash.sh

**Quoted here-document data (runs first).** The body of a here-document whose delimiter is quoted (`'D'`, `"D"` or `\D`) is data: the shell neither expands nor runs it. Before any other reader, the hook removes such a body, and its delimiter line, from the text every rule reads — but only when the operator sits at the top level of the command, the command receiving the body is on the data-receiver list, and nothing on the command can route the body to a program that runs it. The list is `cat`; `git commit` and `git tag`, after at most one `-C <dir>` pair (never `-c`), when no word after the subcommand — read to the end of the simple command, past the operator — is git's edit option in any spelling git accepts (short, long, a unique prefix of the long form, a bundled short cluster, quoted) or a word an expansion or a command substitution fills, because with that option git opens the message, which is the body, in an editor the line may have named; the built-in `gh issue`, `gh pr`, `gh release` and `gh api`; and `python3` whose program is `-` (standard input). Each is named bare or by a canonical bin path, with no wrapper, assignment or redirection in front. Everything else keeps today's verdict, because the command is then judged exactly as written: an unquoted delimiter (its body is expanded, so a substitution in it is judged); a here-document inside a command substitution, a backtick or a subshell, on every shell (bash 3.2 ends a body inside an unquoted substitution at an unbalanced `)` and runs the lines after it, so only a top-level body is read as data); a shell, `osascript`, `python3 -c`/`-m` or a script operand, or any other receiver reading the body; a pipe, process substitution, backtick or arithmetic anywhere on the command; a function definition, `alias`, `hash`, `enable`, `coproc` or `PATH` assignment on the command, or a subscript of or an assignment to a word ending in `aliases`, `functions` or `commands` — zsh's tables that define an alias, a function or a command path, with their global, suffix and disabled siblings; a path that merely carries such a word is not one (an enumeration: a redefinition it does not name, or one made outside the line, is not seen); a `<<` inside a parameter expansion; an unterminated body, a line continuation or an open quote at a pending body, more than 8 bodies or 500 lines, a scanned line over 4096 characters, or more than 20 000 scanned characters outside bodies. **The fail direction has two halves.** Every decline keeps today's verdict. Every admission rests on the hook ending a top-level body where the executing shell ends it: at the first line equal to the delimiter (after tab-stripping for `<<-`), the rule bash, zsh and dash share for a top-level here-document. **Declared residuals:** a body written to any file or named pipe is not judged, whatever reads it and whenever (the hook does not read a script file when it runs, as for one written by an earlier call); a `python3 -` program that itself hands text to a shell is not judged (a program for another interpreter, the `nested-shell` kind); a listed name redefined by state the line does not show (an earlier call, a repository-configured hook) is not seen. The two digests the hook logs are taken over the command as submitted.

**Command-position model.** Before any pattern is matched — and after the quoted here-document pre-pass above — the command is canonicalized by the shared primitive `core/hooks/lib/command-position.awk`, which all four regex-anchored hooks consume. The anchor recognises a command start only at start-of-line or after `;`/`&`/`|`; the canonicalizer inserts a `; ` in front of every *genuine* command start so those positions become ones the anchor already sees — grouping (`{ … }`, `( … )`, function bodies), compound-command keywords (`then`/`do`/`else`/`elif`/`in`/`!` and the condition keywords `if`/`while`/`until`), the bounded command-prefix word set (`sudo`, `time`, `env`, `nohup`, `command`, `builtin`, `exec`, `xargs`, `nice`, `stdbuf`, `timeout`) matched on its basename and stepped with each wrapper's own option grammar, `VAR=value` prefixes and their append form `VAR+=value`, leading redirects, the escaped verb (`\rm`), and an escaped or fully-quoted wrapper word (`\sudo`, `"sudo"`); a fully-quoted verb (`"rm"`) is not resolved and is routed to its own card. Detection is quote-neutralized, so a verb appearing inside a quoted span is content, not a command. Both the verb regex and `extract_target_tokens()` read the canonicalized form — they are atomically coupled, and canonicalizing only one of them either fires the gate and extracts nothing or leaves the regex gating first. **Every segment is judged.** The hook has no exit that allows on a match: a `git` command exempts only its own segment, and a deletion verb with no operand ends nothing — the line's other segments, every other `rm`-family verb, and the Trash and Finder steps are still judged. The hook therefore reads the canonicalized form alone, from one run of the canonicalizer, and its canary checks that form with two probes; the canonicalizer's frozen exit view, which served the two allow-on-match exits this hook once had, has no reader here. `xargs` has no argv target, so the canonicalizer emits a `$XARGS-STDIN` sentinel that routes to step 2's existing unresolvable branch rather than a new rule. See the § Command-Start Position Canonicalization and § Known Limitations sections of the parent readiness doc for the closed set and the nested-shell residual this deliberately does not close.

For each target token after the matched verb (flag tokens skipped; bare shell structure such as a subshell's closing `)` is skipped too, so a targetless `( rm -rf )` does not resolve `)` as a relative path — it is refused instead as naming no target operand, below):

1. Strip surrounding single/double quotes.
2. Detect unresolvable patterns: tokens containing `$`, backtick, or `$(` → **strict-policy BLOCK** (do not attempt to resolve dynamic values; emit BLOCK-TRASH-001 / BLOCK-TRASH-003 with "use explicit absolute paths" guidance). Then **the target-literal rule**: after step 1, a word that still carries a brace, a backslash or a quote, a wholly-quoted word whose body begins with `~`, and a path component that begins with `.` and carries a glob character (`*`, `?`, `[`) are not literal, and each is refused under the strict policy, the reason naming the class. Outside a whole-word quote the shell removes quotes, expands braces, unescapes, and before bash 5.2 can match `..` with such a component, so the path written is not the path acted on. Inside a whole-word quote the shell keeps a backslash, a quote of the other kind and a dot-leading glob component as written, and the word is refused all the same (a declared over-block); a quoted leading tilde is refused because the hook would otherwise expand a tilde the shell keeps. A brace inside a whole-word quote never reaches this rule: the shared canonicalizer removes it from the quoted span first, so the word is judged without it. An unquoted glob otherwise stays literal. A quoted path containing a space reaches this step as such words, because the extractor splits on whitespace first, so it is refused; for a Trash move, name it through the Finder delete, whose `POSIX file` string the hook reads whole. The Finder delete's own path goes through the same rule as written, so a brace or a backslash there is refused although AppleScript does not expand it (a declared over-block), and so is a quoted inside path with a space on the `trash` command.
3. Tilde expansion: `~` → `$HOME`; `~/<path>` → `$HOME/<path>` — except on a line that names `HOME` as a word, read on the command as judged and again with its quotes and backslashes removed (a declaration or name-operand builtin can spell the name with an embedded quote or a backslash, and the shell assigns by the processed word). There no home-relative word is expanded, because the command can change `HOME` before the verb runs, and the target is refused under the strict policy. The test over-approximates — a prefix assignment on the verb's own command, a later segment, a plain `$HOME` read and a path component named `HOME` all count — and a name that only contains `HOME` (`JAVA_HOME`, `HOMEBREW_*`) does not. Not seen: a `HOME` name the line composes through an expansion (the indirect-spelling class), and a change the line does not spell at all (a nested shell's program, a sourced file, a function or alias from the environment: the `nested-shell` residual). Any other tilde prefix (`~user`, `~+`, `~-`, a directory-stack index, a zsh named directory) and a zsh equals-word (`=cmd`) are refused as well: the shell expands them to a path the hook does not read.
4. Absolute (`/<path>`) → use as-is. Otherwise the operand is relative, and it is joined to every directory the command can be in when its verb runs — the payload `cwd`, plus each directory a change earlier on the line leads to (see **In-command working directory** below). Steps 5–6 run once per join, and the worst classification decides (unresolvable over outside over inside). A line with no directory change joins the payload `cwd` alone, exactly as before.
5. Normalize the target **and the workspace root together**, in one Python `os.path.realpath` call (system-default `/usr/bin/python3`) whose output must be exactly the two normalized paths and a sentinel line, one line each. Collapses `..`/`./`, does not require path existence, and follows symlinks, on both sides alike. If the call cannot run or does not finish, if a normalized path carries a line break (a link whose destination holds one), or if the configured root is not an absolute path (a relative root is never anchored to the hook process's own directory), the target is refused under the strict policy, the reason naming the normalizer — it is never compared unnormalized and never admitted as inside. Stage 5 spec referenced GNU `realpath -m`, but macOS ships BSD realpath without `-m` and `/usr/bin/realpath` is absent on this system; Python 3.9+ `os.path.realpath` is the portable equivalent.
6. Prefix-match the normalized target against the normalized root (`${HOME}/Claude/` unless `CLAUDE_WORKSPACE_ROOT` names another). A root spelled through a symlink, with a trailing slash or with a trailing dot segment is therefore compared in its targets' form; a root of `/` admits no target but `/` itself, as before.

**In-command working directory.** The payload `cwd` is where the call starts; a directory change earlier on the same command line moves where a relative operand lands. The directory changes (`cd`, `chdir`, `pushd`, `popd`) are read by the same segment walk that extracts the targets — over the canonicalized command, with one segment numbering for both, so the two readers cannot disagree on order. A relative target is judged from the payload `cwd` plus every directory a change in an *earlier* segment can lead to, and a change later on the line does not move it. The set only grows: a `cd` that fails before `;`, a subshell group and a pipeline stage each leave an earlier directory in effect, so none is ever dropped. Each destination is recorded in both readings — lexical, because `cd` is logical by default and `..` climbs the path as typed, and resolved, which is what `cd -P` and the operating system use — since either can be the true one. Where a loop (`for`, `while`, `until`, `select`, `repeat`, `foreach`) or a function definition lets a segment run again after a later one, every change on the line counts, whatever its position. A refusal of a relative operand judged from a changed-to directory names that directory after the path.

- **A change the hook cannot follow refuses the relative target.** Under the strict policy for targets it cannot resolve, with the same rule IDs (`BLOCK-TRASH-001` for `rm`/`rmdir`/`unlink`, `BLOCK-TRASH-003` for the Trash verbs) and a reason that names the working-directory basis, when an earlier change is: a non-literal operand (a variable, a substitution, a glob or brace word, an escape, a quote that does not wrap the whole word, `~user`, a zsh `=cmd` word); `cd -`; `popd`; a directory-stack form (`+N`, `-N`, bare `pushd`); an unknown option; more than one operand; a relative operand on a line that can re-run segments, or that names `CDPATH` (a bare name is then searched for along it); a destination that depends on `HOME` (a bare `cd`, a `~/` operand) on a line that names `HOME` (step 3); a set grown past 64 directories; or any change at all when the normalizer cannot run — no destination is ever joined unnormalized.
- **What is unchanged.** Absolute targets, and `~/` targets on a line that does not name `HOME`, are judged exactly as before, whatever the line's directory changes.
- **`--` and redirections.** A `--` ends option parsing for the target extractor too, so a dash-led operand after it is judged rather than skipped as a flag; a redirection (`>file`, `2>/dev/null`, a bare operator and the word after it) is not a target. A redirection that carries an ampersand does not end the reading of a command's words, although the walk cuts the line on it and the canonicalizer reads it as a separator: an operator left without its word (`2>&1`, `>&2`, `<&3`, `2>&-`, `>|file`) takes the next word as its word, and a both-streams redirection (`&>file`, `&>>file`, a separator in dash) is followed by the words the canonicalizer read as a new command, up to a separator the line itself carries before a compound keyword or a command-prefix word (`if … &>file; then` ends there). The target extractor and the directory reader read a verb's segment on through those words, so an operand or a directory after such a redirection is judged, and each cut-off piece is still judged as a segment of its own.

**Git subcommand exemption (per segment):** a segment whose command word is `git` (bare or by absolute path) is not judged as a deletion — version-controlled deletes have their own recoverability via git history, and `git rm`, `git clean`, `git worktree remove`, `git stash drop` and `git filter-branch` are handled by other hooks (`block-destructive.sh`) or by git itself. The exemption covers that segment only: a deletion, Trash or Finder verb in any other segment of the same line — after `;`, `&&`, `||`, `|` or a newline, or inside a group — is judged as if the `git` segment were absent, except that the Finder step reads every quoted Finder path on the line, the `git` segment's own text included. Text a `git` command carries as data is not a command start: a quoted message, and a quoted here-document's body read by a recognised data receiver (the quoted here-document paragraph above). A body line of an unquoted here-document, or of a quoted one the pre-pass declines, that begins with a deletion or Trash verb is judged as a command line, for `git` as for any other receiver.

**A verb that does not name all its targets on its line.** A Trash segment that names no target operand — flags, redirections or shell structure only — or whose line continues (the line's last word is a line-continuation backslash, which is not itself an operand, so the operands sit on a line the segment walk reads as another segment) is refused (BLOCK-TRASH-003): a Trash program can act on what the line does not name. The continuation is read once per line, not per segment, so a cut inside the verb's own words — such as the one a redirection's ampersand makes — cannot hide it, and every deletion or Trash segment of a continued line is reported. An `rm`, `rmdir` or `unlink` segment of the same kind is refused too (BLOCK-TRASH-001), judged after every other step so a refusal of a real target names that target. Neither ends the judgement of the line's other segments. Declared over-blocks: a help or version request of either verb family, a Trash call legitimately continued onto a second line of inside operands, and a Trash call on a line that continues past a later command. Declared residual: a Trash call that carries an option emptying the Trash together with at least one inside operand is judged by its operands alone and allowed; the option's reach beyond the line is not read.

**Symlink-following posture (intentional):** `os.path.realpath` follows symlinks. A symlink inside `${HOME}/Claude/` pointing to a target outside the workspace will resolve to the outside target and be blocked. The workspace root is resolved by the same call, so a root reached through a symlink is compared in its resolved form too. This matches the strict-policy requirement: "block any file deletion whose resolved path is outside `${HOME}/Claude/`."

**Trash-command auto-detection (3-tier):** when emitting BLOCK-TRASH-002's Trash-move suggestion (BLOCK-TRASH-001's refusal of a permanent-deletion verb on an auto-memory entry names instead the eviction command that `core/disciplines/knowledge-architecture.md` § Memory↔corpus boundary documents):

1. `command -v trash` under pinned PATH → emit `trash '<abs_path>'`. On systems with a user-installed `/usr/bin/trash` (root-owned binary, present on the canonical workspace), this tier resolves successfully.
2. `[ -x /opt/homebrew/opt/trash/bin/trash ]` → emit `/opt/homebrew/opt/trash/bin/trash '<abs_path>'`. Required when `trash` was installed keg-only via `brew install trash` (default Homebrew install is keg-only — `/opt/homebrew/bin/trash` is NOT created). The hook also recognises this location as a Trash invocation: the Step-3 verb test, the segment walk and this suggestion read one hook-local constant, so the hook never recommends a spelling it does not judge — a Trash move through it is allowed inside the workspace and refused outside it, and a call through it that names no target is refused like any other. The location is not a member of the shared absolute-path prefix set, which stays identical across the four anchor hooks.
3. Fallback → emit `osascript -e 'tell application "Finder" to delete POSIX file "<abs_path>"'`. Always-available on macOS 14+.

### Memory-store arm — block-rm-prefer-trash.sh

The one class this hook admits outside `${HOME}/Claude/`: a Trash-verb move (`trash`, or the Finder `osascript` delete) of a single auto-memory entry. It exists so the EVICT phase of the memory↔corpus lifecycle can be performed by the agent without a bypass. The procedure is stated once, in `core/disciplines/knowledge-architecture.md` § Memory↔corpus boundary, and why the act is not an irreducible human task is recorded in `core/specs/autonomy-tiers.md` § Irreducible Human Tasks item 8a. Neither is restated here; this subsection states the predicate.

- **Where the store is read.** From the `autoMemoryDirectory` key of the operator's user-scope settings (`~/.claude/settings.json`) only — the file the installer re-homes this hook's own PreToolUse wiring into. No environment override is honoured. Project and local settings are repository-supplied, and a repository must not be able to aim a deletion control, so they never admit.
- **What is admitted.** A target operand written only in characters the shell passes through unchanged — absolute, bare or wholly quoted, with no `..` component; a `~/`-led operand is not admitted and meets the outside-root refusal — whose leaf ends `.md` without a leading dot, is not the `MEMORY.md` index (compared case-insensitively), and is an existing regular file rather than a symbolic link, and whose resolved parent is the resolved store. The declared store must itself be absolute or `~/`-prefixed, resolve strictly beneath `$HOME`, and hold a `MEMORY.md`. The operand is judged before any settings file is opened.
- **What stays refused.** Every other target outside the workspace root (BLOCK-TRASH-003), and every permanent-deletion verb on an entry: `rm`, `rmdir` and `unlink` stay BLOCK-TRASH-001, with a message naming the Trash move.
- **A store declared outside user scope.** When an entry would be admitted but its store is declared only in project or local settings — looked for under the project root Claude Code passes its hooks, else under the tool call's working directory — the BLOCK-TRASH-003 refusal says so and names the two remedies, instead of the generic cancel text. Those settings word the refusal; they never admit.
- **Every admission leaves a row.** Once every operand of the command has been judged, each admission appends one compact line to the hook's `block-log.jsonl`: `action: "memory-evict-admit"`, the command's input digest and the working directory, never the command's text or the entry's path, and no rule key. A command refused as a whole leaves no row, and an admission whose row cannot be written is refused (BLOCK-TRASH-003), so the arm never admits silently. Read these rows with the block log.
- **Fail-closed.** The predicate is one `python3` program that admits only on an explicit success token. If `python3` is unusable, the settings file is absent or malformed, or anything raises, nothing is admitted and the existing refusal applies. The resolver above has no raw-path fallback: a target it cannot normalize is refused before this arm is consulted.
- **Not covered.** The runtime's default per-project store (used when `autoMemoryDirectory` is unset) is not admitted; an eviction there is operator-executed through the charter's Hook-Blocked → User-Side Handoff, as the encode-and-evict lifecycle in `core/disciplines/knowledge-architecture.md` states. The arm trusts the integrity of the user-scope settings file, the same file that wires this hook. Its verdict is reached once, when the hook judges the operand, and the command resolves the operand again when it runs, so the path judged is the path moved only while the operand's directories are unchanged between the two — the judgment-time class every path-resolving rule in this registry carries.

See [`§ Absolute-Path-Aware Verb Anchor`](../bypass-mode-readiness.md) — this hook's `extract_target_tokens()` awk script strips the canonical absolute-path prefix before the verb-equality check, atomically coupled with the anchor regex within the hook file; for the Trash verb it strips the keg-only location too, coupled the same way with the Trash-verb regex and the tier-2 suggestion through one constant. See [`§ Known Limitations`](../bypass-mode-readiness.md) for the nested-shell, quoted-path, other-deletion-mechanism, and pre-existing-`/usr/bin/trash` residuals.
