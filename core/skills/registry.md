# Skill Registry

## Purpose

This file is the **logical skill registry** — the single classification source the `pmo-skill-router` reads to route a role-shaped request to the correct role-Specialist. It is a central index, structured like `core/schemas/per-skill-output-contracts.md`: every role-Specialist is catalogued here in one table, keyed by its canonical skill `name`, **without editing any `SKILL.md`**.

**The registration contract.** Every role-Specialist is represented by exactly one row in this registry. A role-Specialist registers by having its row authored in the `## Registry` table here (centrally) — it does **not** add a registry/role field to its own `SKILL.md` frontmatter. A new role-Specialist is added to the suite's routing surface by **appending one row** to the table; an existing one is updated by editing its row. The router enumerates no skill list of its own — the table is the only source, so routing changes by editing this file, never the router. This is the parameterization the router consumes: a skill is added by appending an entry, not by editing classification logic.

Each registry row's `name` must equal the skill's `name:` frontmatter value and its directory name (the `deploy.sh` per-module array membership is the existence proof). The registry lives in `core/` — the shared kernel both the `operations/` and `release/` modules consume — and its links to `operations/`/`release/` `SKILL.md` files are accepted documentary cohesion (markdown doc-links, not code-imports), the same posture `per-skill-output-contracts.md` already relies on; hence the `<!-- reference-durability: allow-link -->` marker at the top of this file.

## Schema

One table row per role-Specialist. The four fields:

| Field | Type | Definition | Source of truth |
|---|---|---|---|
| `name` | string (kebab, unique key) | The skill's canonical `name:` frontmatter value (e.g. `pmo-portfolio-manager`). The primary key and the referent the router emits as the routing target. | `<module>/skills/<name>/SKILL.md` frontmatter `name:` |
| `module` | enum `operations` \| `release` \| `core` | Which module the skill physically lives under. Tells the reader where the `SKILL.md` is and drives the doc-link. | `deploy.sh` per-module array membership (`OPERATIONS_SKILLS` / `RELEASE_SKILLS` / `CORE_SKILLS`) |
| `trigger surface` | prose (1–3 sentences) | The description the router classifies on — the role's "Use when…" intent plus representative trigger phrases, condensed from the skill's `description:`. This is the field the router's classification matches an incoming query against. | `SKILL.md` `description:` (the `Use when` + `Triggers:` clauses) |
| `modes` | list (` · `-delimited) | The skill's mode set, lifted from the `Modes:` clause of its `description:`. Lets the router/operator see what the role can do once selected. | `SKILL.md` `description:` `Modes:` clause |

## What qualifies

A skill registers in this registry **iff it is a Role-Specialist** — a role-named skill (named by the role it emulates: Portfolio Manager, QA Lead, …) that composes shared function-skills per ADR-019. Function-skills — named by what they do (`comms-writer`, `tracker-manager`, `release-planner`, …), including the 3 core shared function-skills (`eval-writer`, `pmo-qa-auditor`, `prompt-builder`) and the Organizer/Orchestrator skills — do **not** register: the router routes role-shaped requests to roles; function-skills are the machinery roles compose, not routing targets. The router itself (`pmo-skill-router`) does not register — a router does not route to itself.

## Consumers

- **`pmo-skill-router`** (the capstone role-router) reads this registry as its sole classification source. On an incoming role-shaped query it (1) reads the `## Registry` table, (2) matches the query against each row's `trigger surface`, (3) emits the matched row's `name` as the routing target (optionally surfacing the row's `modes` so the operator sees what the selected role can do). No skill list is enumerated inside the router — adding or removing a role-Specialist changes routing by editing this file alone. This mirrors how `pmo-qa-auditor` consumes `core/schemas/per-skill-output-contracts.md` by path as its per-skill structural-review source.
