# Skill Registry — the single skill CMDB

## Purpose

This file is the platform's **single skill catalog (CMDB)** — the one Configuration-Management catalog of skills-as-Configuration-Items (CIs). Every deployed skill is one CI row, keyed by its canonical skill `name`, **without editing any `SKILL.md`**. It is a central index, structured like `core/schemas/per-skill-output-contracts.md`.

**The routing registry is a VIEW of this catalog, not a second artifact.** The `pmo-skill-router` reads the `kind == role-Specialist` projection of the `## Configuration Items` table (the `## Routing view` below) and classifies a role-shaped request against exactly the role-Specialist rows — the same surface it classified against before this catalog existed. There is exactly one skill catalog; routing is a typed view of it (per [ADR-038](../ADRs/ADR-038-registry-as-cmdb.md), which evolved this registry into the CMDB and supersedes [ADR-035](../ADRs/ADR-035-registry-as-classification-source.md) §Decision part 4 while preserving its central-index, four-field-schema, no-`SKILL.md`-frontmatter, and `core/`-placement decisions).

**The registration contract.** Every deployed skill is represented by exactly one CI row in the `## Configuration Items` table here (centrally) — it does **not** add a registry/role/CMDB field to its own `SKILL.md` frontmatter (ADR-035 part 3, preserved). A new skill is catalogued by **appending one row**; an existing one is updated by editing its row. The router enumerates no skill list of its own — the `kind == role-Specialist` view is the only routing source, so routing changes by editing this file, never the router. This is the parameterization the router consumes.

Each CI row's `name` must equal the skill's `name:` frontmatter value and its directory name; the `deploy.sh` per-module array membership is the **existence proof** (the catalog cites the roster, it does not re-originate it — see `## Sources of truth (do not duplicate)`). The catalog lives in `core/` — the shared kernel both the `operations/` and `release/` modules consume — and its links to `operations/`/`release/` `SKILL.md` files are accepted documentary cohesion (markdown doc-links, not code-imports), the same posture `per-skill-output-contracts.md` already relies on (ADR-007 v2 carry-forward); hence the `<!-- reference-durability: allow-link -->` marker at the top of this file.

## Schema

One table row per deployed Configuration Item. Fields split into **schema-required (stored here)** and **derived-by-citation (NOT stored — the row's source owns it)** to satisfy duplicate-source-discipline.

## Sources of truth (do not duplicate)

The CMDB stores only `kind` + the net-new axes (`lifecycle-state`, `dependencies`, `owner`) + the pre-existing condensed routing fields (`trigger surface`, `modes`, role-Specialists only). It **cites — never re-states — the axes that already have authoritative homes:**

| CMDB axis | Authoritative source (cited, not stored) | Why not re-stored |
|---|---|---|
| **roster existence + count** (which skills exist; how many) | `core/deploy/deploy.sh` `OPERATIONS_SKILLS` / `RELEASE_SKILLS` / `CORE_SKILLS` arrays (ADR-008, single roster source); `deploy.sh` Check 5 / Check 5(c) own the count | A hand-maintained roster table here would duplicate `deploy.sh` (a Check-5(c) failure) and **be** the second registry the single-catalog constraint forbids. The `## Configuration Items` table is **validated against** the arrays (every row's `name`+`module` matches an array member), it does not originate or re-count the roster. |
| **version** | each `<module>/skills/<name>/SKILL.md` frontmatter `version:` (present on 44 `SKILL.md`) | Per-skill frontmatter is the version source; a stored column drifts on every bump. |
| **I/O / processing / stage contract** | `core/schemas/per-skill-output-contracts.md` + `agent-processing-contracts.md` + `stage-io-contracts.md` (the 3 federated indexes) | These already are the central contract catalog; re-stating is duplicate-source. |

This section is the register-or-remove enforcement surface: the net-new axes are stored (nothing prior to remove); the cited axes are referenced (not re-registered). A future deploy check asserting "every CI row ↔ a `deploy.sh` member and vice versa, and every `name` resolves to a live `SKILL.md`" is **recommended** (ADR-038); at the current roster size manual review at backfill + each skill's definition-of-done covers drift.

## Routing view

The **routing view** is the projection the `pmo-skill-router` reads — **not** the whole catalog:

```
Routing view  ≝  Configuration Items  WHERE kind == role-Specialist
              =  the 19 role-Specialist rows (13 operations + 6 release)
              =  byte-for-byte the surface the router classifies on
```

The router reads the `## Configuration Items` table and **filters to `kind == role-Specialist`**, then matches the request against each view row's `trigger surface`. The 30 non-role CIs (`kind ∈ {function-skill, core, router}`) are **excluded from the view** by the filter, and carry `—` in `trigger surface`/`modes` regardless — so they add **zero** strings to the router's classification input. The router's classification logic, hints, tie-break ladder, and failure modes are unchanged by the catalog expansion; only the table it is a view of grew, the view did not. This is the de-blur mechanism that lets one catalog serve both configuration-management and routing without blurring what the router classifies against (ADR-038 §Decision part 4; the direct rebuttal to ADR-035's "blur what the router classifies against" concern).

**Every routing-registry row is a CI; not every CI is a routing target.** The router itself (`kind == router`) and the function-skills / core skills (`kind ∈ {function-skill, core}`) are CIs but are filtered out of their own routing view — preserving "a router does not route to itself" and the role-vs-function boundary.

## What qualifies

**What is a CI** (catalogued in `## Configuration Items`): every **deployed** skill — all 49 members of the `deploy.sh` per-module arrays. The source-only canary (`pmo-skill-refiner-selftest-canary`, ADR-04, no package) is **not** a CI.

**What is a routing target** (in the `## Routing view`): a CI **iff it is a Role-Specialist** (`kind == role-Specialist`) — a role-named skill (named by the role it emulates: Portfolio Manager, QA Lead, …) that composes shared function-skills per ADR-019. Function-skills (`kind == function-skill`, named by what they do — `comms-writer`, `tracker-manager`, `release-planner`, `pmo-process-designer`, `pmo-technical-analyst`, …), the 3 core shared function-skills (`kind == core` — `eval-writer`, `pmo-qa-auditor`, `prompt-builder`), and the router itself (`kind == router`) are CIs but are **not** routing targets: the router routes role-shaped requests to roles; the rest are the machinery roles compose, and a router does not route to itself.

## Consumers

- **`pmo-skill-router`** (the capstone role-router) reads the **`kind == role-Specialist` routing view** of this catalog as its sole classification source. On an incoming role-shaped query it (1) reads the `## Configuration Items` table and filters to the routing view (`kind == role-Specialist`, per `## Routing view`), (2) matches the query against each view row's `trigger surface`, (3) emits the matched row's `name` as the routing target (optionally surfacing the row's `modes` so the operator sees what the selected role can do). No skill list is enumerated inside the router — adding or removing a role-Specialist changes routing by editing this file alone. This mirrors how `pmo-qa-auditor` consumes `core/schemas/per-skill-output-contracts.md` by path as its per-skill structural-review source.
