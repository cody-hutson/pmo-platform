# Script Execution Allowlist — core/hooks/block-destructive.sh BLOCK-DESTRUCTIVE-022
#
# Scripts whose execution via `bash <path>`, `sh <path>`, `source <path>`, or `. <path>`
# is explicitly allowed. Other script invocations are blocked to prevent the
# script-laundering Red Team mitigation (write attacker.sh, then bash attacker.sh).
#
# COVERAGE BOUNDARY — FOUR CONDITIONS. READ THIS BEFORE CITING THIS FILE AS A CONTROL.
# ------------------------------------------------------------------------------------
# This file is read by a PreToolUse hook. A PreToolUse-enforced control is in force only
# when ALL FOUR of the following hold, and it is NOT in force when any one of them fails:
#
#   1. LOADING  - the session resolved a settings surface that declares the hook wiring.
#                 The wiring applies to any session, main or spawned, whose working
#                 directory is under the governed workspace root; a session that
#                 resolves no such surface loads NO HOOKS AT ALL, and a session outside
#                 that root is excluded by core/hooks/lib/scope-guard.sh.
#   2. BYPASS   - CLAUDE_HOOK_BYPASS was not set to 1 in the environment the session was
#                 launched with. This is the FIRST precedence layer and it exits BOTH
#                 hook classes. BLOCK-DESTRUCTIVE-023 denies SETTING it mid-session; it
#                 does not narrow the pre-launch case. At this layer the security/
#                 workflow class asymmetry does not exist.
#   3. CLASS    - the hook's master-activation class admits it. A security-class hook
#                 always enforces; a workflow-class hook is inert while master
#                 activation is off. block-destructive is security class.
#   4. MODE     - the hook's own mode admits blocking. Most block hooks warn-and-allow
#                 in warn mode; block-destructive is mode-independent.
#
# Where all four hold, this file is a CONTROL. Where any fails, it is a CONVENTION: it
# still records what the platform intends to permit, and it is still the right thing to
# maintain, but it is not an interlock and no threat model may treat it as one. Do not
# accept a risk on the basis that this allowlist "will catch" an unlisted invocation
# without first checking the four conditions on the path that invocation actually runs on.
#
# Canonical statement: core/standards/subagent-security-posture.md, section 3.1.
#
# Format:
#   - One bash GLOB PATTERN per line (shell `case` pattern syntax, NOT regex)
#   - Token-substituted at install time:
#       [PMO_PLATFORM_ROOT]      → the pmo-platform repo root (where the deploy +
#                                  release scripts live). Resolved at deploy time
#                                  by core/deploy/compose.py via self-location, so
#                                  it is correct for ANY clone directory name or
#                                  location (no hardcoded dir-name assumption).
#       [CLAUDE_WORKSPACE_ROOT]  → the Claude workspace root (default $HOME/Claude).
#   - Comments start with # (first non-whitespace char)
#   - Blank lines ignored
#   - Patterns match the literal path as it appears in the Bash command (not after ~ expansion)
#
# Per-tool form convention:
#   A registered tool is invokable from any cwd, so each tool is listed in FOUR
#   forms (grouped together, as the blast-radius.sh entry below illustrates):
#     1. Absolute install form:  [PMO_PLATFORM_ROOT]/<path>/<tool>
#     2. Worktree-glob form:     [PMO_PLATFORM_ROOT]/.claude/worktrees/*/<path>/<tool>
#     3. Relative dot form:      ./<path>/<tool>
#     4. Bare-relative form:     <path>/<tool>
#   Forms 1-2 match absolute/worktree-absolute invocations (a session running
#   from a different cwd); forms 3-4 match invocations from the repo root.
#
# Add custom entries to the OPERATOR ADDITIONS section at runtime, or run:
#   ./.claude/hooks/allowlist-add.sh .claude/script-execution-allowlist.txt '<pattern>'
