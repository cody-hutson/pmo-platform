# Gate-Efficacy Standard

## Purpose

An automated gate earns trust only when a green verdict *means* the invariant it claims holds. A gate that goes green without asserting its invariant is worse than no gate: it manufactures false confidence, and the failure it was built to catch ships behind a passing check. This standard is the normative contract for the platform's **automated-assertion gates** — the integrity checks in `core/deploy/deploy.sh --check` and the jobs in `.github/workflows/` — and for **prose-declared normative predicates**, the checks a corpus document declares in prose and nothing in the tree implements. It names three requirements every such gate MUST satisfy, plus a posture rule that decides whether a red verdict actually blocks.

The governing rule, stated unconditionally: every automated-assertion gate MUST verify the invariant it claims by inspecting the content that embodies that invariant — never a proxy signal that merely correlates with it — MUST self-declare whether it is required or advisory, and MUST be auditable both for false-confidence (a gate that passes when it should fail) and for coverage gaps (an invariant with no gate at all).

## Scope boundary — three gate classes, this standard governs two

The platform runs three distinct classes of gate. They share the word "gate" and little else; conflating them duplicates governance. This standard governs the second and third classes, and references — never redefines — the first.

| Gate class | What it gates | Surface | Owner document |
|---|---|---|---|
| **Pipeline stage-transition gates** | Movement between the 13 pipeline stages — Stage-N readiness, the named G1–G3 gates, GO/NO-GO decisions | Issue fields, anchors, artifacts; LLM-judged | `core/schemas/gate-criteria-spec.md` + `core/schemas/gate-evaluation-spec.md` |
| **Automated-assertion gates** | A code/corpus invariant on every change — package freshness, mirror sync, reference validity, depersonalization, link integrity | `deploy.sh --check` Check 1–N; `.github/workflows/*` jobs | **This standard** |
| **Prose-declared normative predicates** | A stated check whose assertion lives ONLY in corpus prose — a standard, schema, or reference doc that names a condition and states a FAIL verdict for its negation, with no `--check` gate, workflow job, or `--self-test` case implementing it | A passage in a durable-corpus `.md`; realized by a `**Runner:**` declaration in the passage + a row in the gate-coverage register | **This standard** |

A pipeline stage-transition gate asks a judgment question ("is this work ready to advance?") and is answered by an evaluator against criteria. An automated-assertion gate asks a mechanical question ("does this byte-level invariant hold?") and is answered by a script that either finds the violation or does not. This standard does not touch the stage-transition class; for that, read `core/schemas/gate-criteria-spec.md`.

A prose-declared normative predicate is admitted to this standard's scope by a conjunctive test over the three limbs below, and by no looser one. Admission always pairs **one** of the two alternative first limbs — a verdict limb or an obligation limb — with the same prose-only limb; the pair is what admits, and no passage is admitted by a first limb alone:

- **L1 — verdict limb.** The passage states a **negative verdict** for a named condition — it says what a violation *is* (`→ FAIL`, `is a FAIL`, `FAIL, not a pass`, `never a pass`), not merely that something MUST hold.
- **L1′ — obligation limb.** The passage declares a **procedure with a stated trigger**: a named condition (*"when X"*, *"before Y"*, *"at Z"*, *"whenever …"*) **and** an act the agent MUST perform when that condition holds — and it states no verdict for the negation. **The admission bar is the stated trigger, and nothing looser.** A rule with no named condition — *"be thorough"*, *"prefer durable structures"* — is **not** admissible, because there is no observable moment at which a runner could be said to have fired. This reuses the platform's own bar in intent (`core/rules/decision-time-adherence.md` § 6: a discipline that cannot state an observable trigger is not index-eligible), so no second admission philosophy enters the corpus.
- **L2 — prose-only limb.** No `deploy.sh --check` gate, `.github/workflows/*` job, or script `--self-test` case implements the assertion.

`L1 ∧ L2` is **class 3-V** (verdict-shaped) and `L1′ ∧ L2` is **class 3-O** (obligation-shaped); both are class 3, and in both the passage MUST name its runner. **Where a passage carries both a trigger and a verdict, L1 governs and L1′ adds nothing** — a passage is admitted once, by one form, and there is no double-admission. `L1 ∧ ¬L2` is class 2 — the implementing check carries the declaration and the prose merely cites it. All three limbs are decidable by the author at authoring time, which is where the obligation attaches: the author is the one who knows whether a verdict was written, whether a trigger was named, and whether code was written for either. A single marker is deliberately NOT the trigger — `fails closed` appears in the corpus in two senses, one describing an unrun predicate and one describing implemented behavior, so a marker-only test both over- and under-includes.

**This is a second admission FORM, not a fourth gate class, and the distinction is load-bearing.** The count in this section's heading stays at **three** by construction. A fourth class would cascade across that heading, the version-history rows below, and every consumer that repeats the count; an alternative first limb inside an existing class cascades nowhere, because 3-V and 3-O share one owner document, one register, one `runner-def:` form, and one computation. `deploy.sh --check` **Check 62 required no code change to admit 3-O** — it recomputes every `runner-def:` pointer in the register regardless of which limb admitted the row, and that fact is the falsifiable evidence that the existing structure fits rather than merely tolerates the extension.

**Why the obligation limb was missing, stated so it is not re-derived.** L1 alone excluded, in terms, every rule that constrains conduct without stating a verdict — which is most governed *procedures*. A procedure that declares a trigger and an act is exactly as unenforced as a verdict nobody runs, and is indistinguishable in the artifact from one that fires reliably. The observed failure class is a rule that exists, declares its moment, and has nothing that acts at that moment.

## Requirement (a) — Assert by content, not by proxy

Every automated-assertion gate MUST verify its claimed invariant by inspecting the **content** that embodies the invariant. A **proxy signal** — a value that correlates with the content but can diverge from it — is FORBIDDEN as the sole, verdict-bearing assertion.

The canonical failure this requirement closes: a package-freshness gate that compared file modification time (`mtime`) instead of file content. A modification time is a proxy for "rebuilt from current source" — it correlates, until someone runs `touch` (or a fresh `git checkout` resets every timestamp to checkout-time), at which point a stale package passes a green gate. The fix is to assert the content directly: hash what is *in* the artifact and compare against a known-good baseline.

### Proxy-vs-content decision table

| Claimed invariant | Proxy (FORBIDDEN as sole assertion) | Content assertion (REQUIRED) |
|---|---|---|
| "package is fresh / rebuilt from source" | file mtime (`stat -f '%m'` compare) | content-manifest hash vs committed baseline |
| "mirror matches source" | mtime, or mere file presence | `diff -q` byte-compare (already content — compliant) |
| "required field present and well-formed" | line-count, file-size | regex match on the field's value (already content — compliant) |
| "no forbidden token introduced" | filename or path heuristic | `grep` over the changed-file **content** of the base..head delta (already content — compliant) |
| "referenced file exists / anchor resolves" | link-text presence | resolve the target path and the heading slug (already content — compliant) |

Most existing gates already assert content (the right three columns of every row above are mostly already in place). The rule's bite is the first row: any freshness or rebuild claim asserted by timestamp is non-compliant and MUST be converted to a content hash.

### Pre-filter escape valve

A proxy MAY serve as a cheap pre-filter that *gates entry to* the content assertion, provided a content assertion remains the **verdict-bearing** step. Example: "if mtime is unchanged, skip the expensive hash and pass; if mtime is newer, run the hash and let the hash decide." This keeps the common case fast while making content the source of truth — a `touch` that bumps mtime forces the hash, and the hash (unchanged content) still passes correctly; a real source edit forces the hash, and the hash fails. The proxy narrows *when* the content check runs; it never *substitutes* for the content check's verdict.

## Requirement (b) — Required-vs-advisory declaration

Every automated-assertion gate MUST self-declare its enforcement posture in a machine-greppable form, so a reader (and an auditor's `grep`) can tell whether a red verdict blocks or merely signals — without reverse-engineering branch-protection settings or warn-mode files.

### Declaration schema

One declaration per gate, carrying these fields:

- **`posture: required | advisory`** — `required` means a red verdict blocks merge or ship (a branch-protection required check, or a `deploy.sh --check` block that is always-enforce). `advisory` means red is a signal that never blocks (a warn-mode `--check` during its shakedown window, or a workflow that no-ops on a path-skip).
- **`enforcement-surface:`** — where the posture is *realized*: the branch-protection rule name, or `always-enforce` in `--check`, or the `deploy-check.mode` warn-window.
- **`skip-semantics:`** (workflows only) — REQUIRED when a workflow carries a `paths:` or `on:` filter that can make GitHub report the check as skipped/absent for an unrelated PR. The declaration states whether absence is treated as a pass (`absent-is-pass`, the advisory posture) or whether the workflow runs filter-free to *always report a result* (the always-reports posture — the established `reference-durability.yml` pattern).

### Verdict-Input Closure — the criterion for whether a `paths:` filter is a legitimate cost control

A `paths:` roster is only ever an APPROXIMATION of a verdict's real input surface, and the moment it under-approximates, `skip-semantics=absent-is-pass` turns the miss into a false statement: the gate reports nothing on the very change that breaks its invariant, and absence reads as a pass. Declaring `absent-is-pass` is therefore not self-justifying — it is a claim about coverage, and this is the criterion that decides it.

**Verdict-Input Closure `VIC(W)`** is the set of repo paths `P` such that a PR changing only `P` could change `W`'s published verdict — green, red, or **absent**. Three member classes:

- **S — subject.** Files whose content the assertion is *about*.
- **E — engine.** Files that *implement* the assertion: checkers, engines, and self-test suites whose exit code gates the job.
- **C — control.** Files that are **not git-ignored** and that *switch* the assertion's behaviour: `.enforce` sentinels, arming declarations, manifests, scope globs. The scoping is `not git-ignored` and deliberately NOT `tracked`, because the two are different sets and the gap between them is exactly where a control lives: a git-ignored path cannot appear in a PR at all, but an **untracked-but-unignored** path can — creating it *is* the PR. A control file that does not exist yet is a VIC member, and rostering it is a reversal tripwire rather than a dead entry.

**The test.** `paths` roster ⊇ `VIC(W)` ⟹ trigger scope and verdict scope agree, and the filter is a legitimate cost control. Otherwise they disagree, and the workflow takes exactly one of three dispositions:

| The `VIC` gap is… | Disposition |
|---|---|
| **open-ended** — a target-resolution scope, a canonical living outside the subject tree, or a roster bound to another roster its own declaration says will grow | **CONVERT** — delete the filter, adopt `always-reports=yes`, drop `skip-semantics` |
| **finite, enumerable and stable** — a named set of engine or control files | **BIND** — widen the roster by exactly those paths and record the closure basis in the declaration |
| **empty** | **RECORD** — keep the filter, state the closure basis, correct any false declaration |

The disposition is **per workflow**. Two gates sharing a posture, a runner platform and a subject tree can land on opposite sides of this test, so a uniform ruling over a population of filtered workflows is wrong for at least one member; the test is applied to each, and the outcome is whatever it is.

**A `required` trajectory makes `always-reports` a PREREQUISITE, not a nicety.** A path-filtered context registered in branch protection leaves every non-matching PR permanently pending, so a workflow declaring `posture=required` — including `required(warn-mode-initial)`, whose graduation clause names that registration — cannot reach the enforcement it declares while a filter exists. Removing the filter is part of the flip, not a later optimization, and a graduation clause naming only the sentinel flip and the branch-protection registration is incomplete. This binds independently of coverage: it fires even where `VIC ⊆ roster` already holds.

### Realization per surface

**In `deploy.sh`:** the declaration is the existing inline Check-header comment, made uniform. Each `# Check N — <name> (<posture>; <enforcement-surface>)` header carries an explicit `required` or `advisory` token. The mapping from the historical free-text is fixed: a check that today says `always-enforce` is **required**; a check that today says `warn-mode initial` is **advisory** for the duration of its shakedown window (it becomes required at flip-to-enforce). This standard makes the token canonical and greppable; it does not change any check's behavior.

**In `.github/workflows/`:** the declaration is a standardized header comment block placed near the top of the file, formalizing the prose idiom that `reference-durability.yml` and `skill-count-imp-check.yml` already carry. The greppable form:

```yaml
# gate-efficacy: posture=required  enforcement=branch-protection:"<check name>"  always-reports=yes
#   invariant: <one line — what this gate asserts, by content>
#   falsification: <one-line repro that MUST turn this gate red>
```

or, for an advisory path-scoped workflow:

```yaml
# gate-efficacy: posture=advisory  enforcement=path-filtered  skip-semantics=absent-is-pass
#   invariant: <one line — what this gate asserts, by content>
#   falsification: <one-line repro that MUST turn this gate red on an in-scope change>
```

**In durable-corpus prose:** the declaration is a `**Runner:**` label inside the passage that states the predicate, naming the surface that executes it. The greppable form — already the established in-corpus convention, not a new one:

**Runner:** `<named runner>` — a `deploy.sh --check` gate id, a CI job name, a script `--self-test` case, or a **named human/agent review step** (a skill + mode, or a pipeline stage-gate). State explicitly whether a CI job executes it; when none does, say so rather than leaving it to be assumed.

`posture:` is **derived, never restated** on this surface: a predicate whose runner is a review step is not a blocking pre-merge status check, so Requirement (b′) makes it `advisory`. `advisory` here means *no pre-merge blocking status check* — it does not mean unimportant, and it says nothing about the authority of a pipeline stage-gate that runs it, which `core/schemas/gate-criteria-spec.md` owns. `posture:` and `falsification:` for a class-3 predicate live in that predicate's **gate-coverage register row**, so no value is stored twice.

A `posture=required` declaration records the *intended* posture and names its enforcement surface. It does NOT itself edit branch-protection — that is a repository-settings change made operator-side, outside the tree. Reconciling a declared `required` posture against the actual branch-protection configuration is a coverage-audit item under Requirement (c), not a file edit any single gate performs. The comment is the declaration of intent; the branch-protection rule is the enforcement; the two are kept honest by the audit.

### Written sink and terminable shakedown — the two axes of a warn-mode declaration

A warn-mode declaration makes two separable claims. Conflating them is how an advisory becomes permanent, so both MUST hold and both are stated per gate in its flip-decision register row.

**W1 — the sink is written.** A gate MAY declare a **drain-history** flip criterion only where some code path appends rows for that gate's id to a sink that exists. A declaration naming a sink nothing writes MUST instead carry the disclosure `**specified, not yet emitting**: no check emits this gate's FAIL row.` and MUST NOT declare a drain-history criterion. The platform's realized sink form is the single shared `$(pmo_instance_path)/deploy-check-warn-log.jsonl`, discriminated by the row's `check:` field; a per-gate sink file is not the convention and is not introduced. A zero drain is **INSTRUMENTATION-SUSPECT**, never "no evidence yet" — a zero whose instrument was never connected measures the wiring, not the behaviour.

**W2 — the shakedown is terminable.** A warn-mode shakedown MUST carry an exit criterion **evaluable from committed state**: a deadline arm, a committed phase constant, or another repo-derivable forcing function. Every `*-warn-log.jsonl` here is git-ignored, so a criterion whose only reader is a drain cannot be evaluated by a pull-request agent, in CI, or in a fresh clone — and a shakedown with no repo-derivable exit is an **undated deferral**, indistinguishable in the artifact from a gate that can never fire. The evidence arm MAY stay operator-local: it informs and triggers nothing.

**Written is not readable.** The axes are independent, and the cohort splits on them: a gate whose rows are written at scale can still fail W2, and satisfying W1 does nothing for its graduation. Checks 8 / 10 / 13b / 34–37 are the measured case — their sink is written continuously, and they have been held at an undated `shakedown continues` throughout.

**A deadline is a forcing function, not a blocker — and the distinction is what keeps W2 compatible with the disposition rule.** [`core/ADRs/ADR-163-split-predicate-gate-graduation.md`](../ADRs/ADR-163-split-predicate-gate-graduation.md) § *Second altitude* requires that **a disposition name its BLOCKER, not its schedule**, because a schedule is unfalsifiable — no observation ends it. W2 does not weaken that: the row still names the blocker, and the repo-derivable exit criterion is the mechanism that makes resolving that blocker non-optional rather than a substitute for naming it. A row carrying a date and no blocker fails ADR-163; a row naming a blocker with no repo-derivable exit fails W2; a conforming row does both. **W2 therefore does not apply to a disposition that declines the flip** — `RATIFIED ADVISORY` and the permanent-residual limb of a `SPLIT DISPOSITION` are not shakedowns, and arming a deadline against one would manufacture the inverse defect: a permanent advisory wearing the shape of a temporary one.

**Consumed by the flip-decision register.** A row held at warn names (i) a sink satisfying W1 *or* the W1 disclosure, and (ii) the repo-derivable ending condition satisfying W2. A held row naming a sink absent from the written-sink set does not meet this requirement.

**Relationship to class 3 — adjacent axes, not the same rule at two altitudes.** § *Runner resolution — class 3* asks whether anything **executes** a predicate (R1 carried ∧ R2 reached), and admits only passages for which **L2** holds — no `--check` gate, workflow job, or `--self-test` case implements the assertion. W1/W2 asks whether a **shakedown can end**, over a population defined by the warn-mode declaration rather than by L2. They are disjoint on their own motivating cases, and neither subsumes the other.

Set out side by side:

| | § Runner resolution — class 3 | W1 / W2 |
|---|---|---|
| Population | passages where **L2 holds** (nothing implements the predicate) | any gate declaring a warn-mode shakedown, implemented or not |
| Question | does anything execute this predicate? | can this shakedown terminate? |
| Disjointness witness | Checks 8 / 10 / 13b / 34–37 are implemented `--check` gates, so **L2 is false** and class 3 never reaches them — yet they are exactly the population W2 exists to catch | a class-3-O named-gap row declares no shakedown, so W1/W2 never fires on it |
| Strength on the overlap | the declared observable is **reviewer-verified, not machine-checked** (limit 7), and `runner-def:` cannot reach a surface outside the repo (limit 2) | **strictly stronger**: the ending condition must be *repo-derivable*, precisely because a reviewer-verified observable living in a git-ignored sink is the failure mode |

Where a gate is both — class 3 at authoring time **and** holding a warn-mode shakedown — the two compose in order and neither is optional: class 3's Disposition 1 (wire it) or Disposition 2 settles the **runner**; W1/W2 then settles the **sink and the exit** for whatever remains held at warn. G3-14 / G3-15 are the worked instance.

### Resolution — what makes a named enforcer resolvable

Every declaration in this standard names an enforcer: `enforcement-surface:` on the two automated-assertion classes, `**Runner:**` on the prose class. Naming one is not the same as having one. A named enforcer is **resolvable** only when BOTH conditions hold, and the conjunction is the whole point — either condition alone admits a runner that cannot fail:

- **R1 — carried.** The named enforcer's own definition contains the assertion. The predicate is in its check set, its code, or its encoded check bank — not merely in the passage that names it. An enforcer that exists but does not carry the predicate runs to completion and surfaces nothing.
- **R2 — reached.** Something executes the named enforcer: a call site that names it, a glob that provably matches it, a dispatcher arm, or a pipeline stage-gate that invokes it. An enforcer that carries the predicate but that nothing invokes cannot fire.

`R1 ∧ R2` is *resolvable*. Failing either invalidates the declaration, and the wire-or-downgrade rule below fires on it exactly as it fires on a wholly missing runner — **a runner that cannot fail and no runner at all are the same defect in the artifact**, which is the observation this standard's third class exists to act on.

**Resolution is computed, never asserted.** A declaration states its resolution target in a machine-checkable form — `runner-def: <path>::<anchor>` — so R1 is recomputed on every run instead of being vouched for by whoever wrote the row. `deploy.sh --check` Check 62 is that computation. This form is deliberate and its rationale is a recorded failure: the prior attempt at this obligation was a reviewer instruction reading *"verify the named runner actually carries the check"*, and it failed on its own first application — the release that shipped the instruction also shipped three rows naming a runner whose check set carried none of their predicates. An obligation only a reviewer can discharge is discharged only when a reviewer remembers to.

**An implemented-but-uninvoked check is an R2 failure, not a class-3 predicate.** Code that implements an assertion but that nothing invokes makes L2 false, so a passage citing it routes to class 2 — where its `enforcement-surface:` must satisfy R2 and cannot. The declaration fails *there*, and the author wires it or downgrades it. The obligation is not lost in the gap between the classes; it is placed on the class that owns the code.

**Why L2 stays keyed on *implements* rather than *executed by*.** Tightening the limb looks like the narrower fix and is not, on two measured grounds. First, **it does not reach**: the tightened limb re-classifies *passages*, and the committed uninvoked suites in this tree are cited by no passage at all — so the tightening would move zero passages and catch zero of the instances that motivated it. Second, **it is not decidable by the author**, which is the property both limbs are selected for. Reachability here is not a name lookup: invocation happens by name, by dispatcher array, and by glob, and a narrative mention in a release note reads exactly like a call site. A whole-tree by-name reachability scan over the committed test population misclassified **7 of 46 files (15%)** — one uninvoked suite read as invoked because a release note mentions it in prose, and six glob-invoked suites read as orphans because nothing names them. A limb an exhaustive mechanical scan gets 15% wrong is not a limb an author settles by inspection at authoring time.

### Runner resolution — class 3

A prose-declared normative predicate MUST resolve to a named runner, and that runner MUST be **resolvable** in the R1 ∧ R2 sense above. When no resolvable runner can be named, the author takes exactly one of two dispositions. **The first disposition is shared by both admission forms; the second differs, and the difference is not cosmetic:**

| | **class 3-V** (verdict-shaped, `L1 ∧ L2`) | **class 3-O** (obligation-shaped, `L1′ ∧ L2`) |
|---|---|---|
| **Disposition 1** | **Wire it** — implement the predicate as a `deploy.sh --check` gate, a CI job, or a script `--self-test` case. It becomes class 2 and is declared there. | **Wire it** — identical. |
| **Disposition 2** | **Downgrade it** — restate the passage as a **non-normative description** of what actually holds, dropping the verdict language, so the artifact stops claiming an enforcement nothing delivers. | **Register it as a named gap** — keep the obligation intact, record the register row with an empty enforcing-gate cell, and **declare the observable** that would close it. |

**Why disposition 2 diverges.** A verdict-shaped predicate that cannot be run is *lying*: it claims a FAIL that nothing can render, so deleting the claim is a correction. An obligation-shaped procedure that cannot be mechanically observed is **not lying** — it still correctly states what the agent must do; what it lacks is a detector. Downgrading it would delete a correct instruction, which is a regression, not a repair. Registering it as a named gap is the honest form, and the register's own coverage-gap method already sanctions that shape: *an invariant with an empty "enforcing gate" cell is a named gap, visible and trackable, not a silent omission.*

**The declared observable (class 3-O only).** A 3-O row whose runner is a named review step, or which is a named gap, MUST state **the observable the compliant path emits and the bypassing path does not**. Without it, "detectable record" is an aspiration rather than a property: a checkpoint that fired and emitted nothing is indistinguishable from a checkpoint that never fired, and the emitted token is what makes adherence reviewable. This reuses the existing emitted-observable pattern (`core/rules/decision-time-adherence.md` § 3) rather than introducing a second trailer family.

**A named-gap row carries no `runner-def:` pointer.** An empty enforcing-gate cell is honest; a pointer at a runner that does not carry the predicate is not. Deleting every pointer to silence the gate is itself flagged — Check 62 reports `NOSET` on a register declaring zero pointers, on every mode, so there is no silent-pass path out of this disposition.

Leaving the predicate normative and unrun is the defect this class exists to close: a fail-closed predicate with no runner cannot fire, so it cannot fail, and in the artifact it is indistinguishable from a clean check. **A predicate whose named runner is not resolvable is the same defect and takes the same two dispositions** — naming an enforcer does not discharge the obligation, resolving to one does. Requirement (b′) binds unchanged — the declaration never claims an enforcement the surface cannot deliver.

**The obligation attaches at authoring time, and is register-anchored.** A release that ADDS or MODIFIES a prose-declared normative predicate adds or updates that predicate's row in the gate-coverage register — the same incremental discipline the register already follows for classes 1 and 2. The check is on the change, not on the corpus: no scan and no allowlist — which is why admitting the obligation form adds **no** retroactive corpus sweep and no trigger-declaration field to any document. Each row that names a runner carries a `runner-def: <path>::<anchor>` pointer — a named-gap row names no runner and correctly carries none — and **`deploy.sh --check` Check 62 recomputes every one of them on every run** — so R1 is a standing computation over the register rather than a one-time authoring claim, and a row whose runner silently stops carrying its predicate goes red instead of going unnoticed. The authoring-time surface remains a named review step — **Stage 5 Collective Review / `design-review-checklist.md` Section 4 check 4.9** (primary), re-verified at **Stage 7 Dev Testing** (`pmo-qa-auditor` Mode G) on the PR (backstop) — declared `advisory` under (b′), reflexively conforming to the rule above rather than exempting itself from it. The review step decides *whether the named runner is the right one*; Check 62 decides *whether it still carries the predicate*, which is the half a reviewer demonstrably does not reliably discharge.

**What this class does NOT detect — stated, not implied.** A mechanism that leaves its own limits unstated reproduces the failure it exists to close, so the limits are enumerated here rather than inferred from what the register happens to contain.

1. **It does not detect a runtime skip.** For a row whose runner is a named review step, or which is a named gap, the detectable record is the **absent observable**, which a reviewer must notice. Check 62 asserts that the *named runner still carries the predicate*; it asserts nothing about whether the procedure *ran on any given occasion*. Reviewer-detected, not gate-detected.
2. **It does not reach any surface outside the repository.** `runner-def: <path>::<anchor>` resolves against repo paths, so a surface that lives outside the tree — the operator auto-memory store at `~/.claude/memory` being the concrete case — is unreachable by this mechanism. That is a statement about **this mechanism** and about nothing else: a `deploy.sh --check` gate can read such a surface at deploy time on an operator machine, and one does, so a register row may legitimately name a runner that reaches further than the register's own resolution can follow.
3. **No hook can distinguish compliance from bypass on a byte-identical tool call.** Where a governed procedure's sanctioned execution and its bypass issue the same tool call with the same payload, no tool-call-time surface can tell them apart — hooks read the payload and no session, subagent, skill, or mode field. This is a property of the payload, not of any hook's implementation, and no hook design changes it. It is why a tool-call-time enforcement surface was not the mechanism chosen here.
4. **R1 is anchor-presence, not predicate-completeness.** Check 62 asserts that the runner-definition file exists and still contains the declared anchor. A runner that carries **half** its predicate resolves `CLEAN`. Choosing the anchor is therefore a substantive authoring act: anchor on the part of the predicate whose loss would matter, not on the runner's name.
5. **The class is advisory and deploy-time-only.** Check 62 declares `advisory / deploy-time-only`, and Requirement (b′) bars `required` while no CI mirror exists. This class makes a declared obligation **detectable, not enforced**, and adds no pre-merge teeth.
6. **It does not detect an obligation that was never registered.** Check 62 recomputes the rows the register *contains*: it resolves the `runner-def:` pointers it finds in this file and asserts nothing about a predicate that declares no row. Nothing scans the corpus for a prose-declared normative predicate carrying no register row, so a never-registered obligation and a de-registered one are the same state to this mechanism — deleting a row returns a `CLEAN` verdict with a lower pointer count rather than a finding, because that count is reported and not compared against anything. The population this class resolves over is therefore *registered* governed procedures, not governed procedures. What puts a row in the population is the authoring-time review step named above — `design-review-checklist.md` 4.9 (primary), `pmo-qa-auditor` Mode G (backstop) — so registration is a review obligation, not a computed one.
7. **The declared observable is reviewer-verified, not machine-checked.** A 3-O row whose runner is a named review step, or which is a named gap, MUST state the observable the compliant path emits and the bypassing path does not — and no executable surface in this repository reads that statement. Check 62's parser consumes `runner-def:` pointers only, so a row that states no observable, and a row whose stated observable the compliant path never actually emits, both resolve exactly as a conforming row does. The observable is a required element of the register's form, checked where the rest of the row's judgment is checked: at review.

### Requirement (b′) — A required gate must be CI-enforced, not deploy-time-only

A gate declared `required` MUST run **pre-merge in CI** — its red verdict must be reachable as a blocking status check before a change lands on the main branch. A check that runs only at deploy time (after merge, on the operator's machine) cannot block a merge; declaring it `required` while it has no CI surface is a posture that the enforcement cannot honor. Such a check is **advisory** until a CI mirror exists.

This dimension classifies a real class of gap: a `deploy.sh --check` assertion that is genuinely load-bearing but exists only as a post-merge, deploy-time check has no pre-merge teeth. The required-vs-advisory declaration is the instrument that surfaces this honestly — a deploy-time-only check declares `advisory` (with `enforcement-surface: deploy-time-only`) until its CI mirror ships, at which point the declaration flips to `required`. The declaration never claims an enforcement the surface cannot deliver.

The pairing of a deploy-time check with a CI mirror is the structural pattern: the deploy-time check is the operator-machine safety net; the CI mirror is the pre-merge gate. A check that should block a merge needs both, and its posture declaration is `required` only once the CI mirror is in place.

## Requirement (c) — False-confidence and coverage auditability

The gate corpus MUST be auditable for two distinct failure modes. Each has a prescribed audit method.

### False-confidence — a gate that passes when it should fail

A false-confidence gate goes green without asserting its invariant (the mtime-package case under Requirement (a); the broad class of "the check is present but toothless"). 

**Audit method:** every gate carries a **falsification test** in its declaration — a one-line, concrete repro describing the tampered or stale input that MUST flip the gate red. The falsification test is not prose about the gate; it is an executable recipe ("`touch` the package and it must stay green; mutate one source byte without rebuilding and it must turn red"). A reviewer, or a Dev-Testing spoke, runs the falsification test and empirically confirms the gate fails when it should. A gate whose falsification test cannot be made to fail it is a false-confidence gate by definition, and the audit catches it.

### Coverage gap — an invariant with no gate

A coverage gap is a named platform invariant that no gate enforces (the governance-as-code class: rules the platform states but does not mechanically check).

**Audit method:** a **gate-coverage register** — a table mapping each declared platform invariant to its enforcing gate and that gate's posture. An invariant with an empty "enforcing gate" cell is a *named* gap, visible and trackable, not a silent omission. This mirrors the coverage-matrix discipline the platform already applies elsewhere ("an empty cell is a named gap, not a silent omission"). The register is authored incrementally: each release that touches a gate adds or updates that gate's row. The register is never required to be exhaustive in one pass — exhaustive population of every check and workflow is a standing coverage-completion effort, not a precondition for the register to be useful.

Advance remains an operator decision, never auto-promoted by row count (`progressive-rollout-convention.md` owns the ladder). **A zero drain is classified INSTRUMENTATION-SUSPECT, not "no evidence"** — the must-flag control (`block-destructive.test.sh` T-EXEC-1) distinguishes a quiet surface from a disconnected one. The counterexample this row exists to avoid repeating is in this same register's premise: `BLOCK-EGRESS-007` phases its widening through `EGRESS_007_WIDENING_PHASE` with no criterion, and its drain holds **2 rows in total** — unable to graduate on evidence, with nothing surfacing the stall. Recorded by the `hooks-block-their-declared-subject` release. |

**Pattern worth reusing, stated once here rather than re-derived per gate:** *make the forcing function repo-derivable and let the evidence stay operator-local.* The row above is its first instance. It is the general answer to this subsection's own stated blocker — a gate whose advance depends on a git-ignored drain can never be advanced by anything in the pipeline, but a gate whose *deadline* depends only on a committed constant can force the decision that reads the drain. Any future warn-mode gate blocked on the same signal problem should inherit this shape rather than accumulate another undated `shakedown continues`. **This is no longer only a recommendation:** § *Written sink and terminable shakedown* above codifies it as W2, which every warn-mode declaration MUST satisfy — the note records the pattern, the clause makes it binding, and neither restates the other.

Reconciled against `gate-criteria-spec.md`: **G-CL7 / G-CL8** retain their declared `auto (warn → enforce)` posture — they are correctly still in shakedown and already carry the `specified, not yet emitting` disclosure, so no *posture* edit is needed for them (a "still warn" edit would be redundant); under W1 they take limb 2, and under W2 they still owe a repo-derivable ending condition, which their own row is where it belongs. **G3-14 / G3-15 DID take a spec edit, so the earlier claim that none was needed no longer holds:** their declared per-gate drain sinks were never written, so all four declarations are re-pointed to the shared deploy-check warn log with that same disclosure per W1 above, and their register row is the SPLIT DISPOSITION recorded here rather than a shakedown. When a gate's local warn-log is drained to zero-false-positives, apply the one-token flip above, update its row here, add the CI job to branch-protection required checks where applicable, and validate it FAILS closed on its falsification input.

## Reversibility

MODERATE. The standard is a normative reference document; adopting it changes how gates are authored and audited going forward, and the Check 7 conversion changes a verdict mechanism. Reverting the standard is a documentation change (CHEAP in isolation); reverting the Check 7 content-hash back to mtime would re-open the false-confidence it closes (the reason the conversion is MODERATE, not CHEAP — the prior state is a known-defective state). Confidence: HIGH that the content-not-proxy requirement is correct; the design is grounded in an observed false-confidence failure and an empirically-confirmed rebuild-stable hash.

## Provenance

This standard graduated from a pattern review over three observations, all in the release-ops domain, converging on the mechanism "automated gates that do not verify what they claim":

### Source(s)
- #1080 — Check 7 package-freshness was mtime-based, so a stale `.skill` passed on a fresh checkout (the originating false-confidence instance).
- #312 — adversarial review of CI/git workflows that found gates going green without asserting the invariant, and named the missing required-vs-advisory declaration.
- #313 — the governance-as-code coverage-expansion roadmap (invariants with no gate; the natural umbrella for the bulk coverage-register population and the back-fill of the remaining check-header posture tokens).
