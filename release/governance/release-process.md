# Release Process — Git Workflow

## Lifecycle (Git-Native) — 13-Stage Pipeline

> For detailed stage specifications (10-point framework), see `release/references/pipeline/`.

### Pipeline Self-Governance

The pipeline is self-referential — it governs its own evolution. Work that changes the pipeline itself (governance docs, stage specs, rules, tooling) routes through the same stages as any other backlog item; it is not exempt from the process it defines. Do **not** jump straight to file creation and PRs for an item just because it is "infrastructure" or "pre-triage" work.

Any backlog item routes through at minimum: (1) **Planning** — a change spec; (2) **Solutioning** — design validation, activated when the Stage 5 criteria are met; (3) **Engineering** — write the files; (4) **Review** — the human gate before merge. Skipping Planning/Solutioning means design feedback surfaces *after* the code is written rather than before, when it is cheapest to act on. Small items (documentation-only or single-file) MAY compress Planning + Solutioning, but still get an explicit design review before the change is committed.

### Stage Compression (Git-Native)

The 13-stage reference model compresses to **~10 operational stages** for git-native releases. Three stages compress because git mechanisms provide their function automatically:

| Stage | Compression | Mechanism |
|---|---|---|
| Stage 10: Dry Run | **Compressed into Stage 9** | PR diff review IS the dry run. The operator reviews the diff during Plan Review — no separate dry-run step. |
| Stage 11: Snapshot | **Compressed (automatic)** | Git history IS the snapshot. `git revert` restores any prior state. No manual snapshot step needed. |

**Stage transition routing:**
- Standard flow: ... → Stage 8 (QA) → Stage 9 (Plan Review) → **Stage 12 (Execute)** → Stage 13 (Close)
- Stages 10 and 11 are not skipped — they are satisfied by git-native mechanisms during Stage 9 and the merge process respectively.

**When compression does NOT apply:**
- **Non-git deployment targets:** If a release includes changes that deploy outside git (e.g., GitHub Projects configuration, external system settings, manual infrastructure changes), those components require an explicit dry-run step separate from the PR diff.
- **Layer 2 file deployment:** Skill file deployment (S-2 copy mechanism) happens during Stage 12 Execute. The PR diff validates content, but the copy operation itself is the deployment — if the copy mechanism changes or targets change, an explicit dry run of the new mechanism may be warranted.
- **Destructive operations:** Any release that includes destructive operations (mass issue closures, label deletions, board restructuring) should include an explicit dry-run with rollback validation, even if the changes are also tracked in git.

When compression does not apply, Stage 10 activates as a distinct step between Stage 9 GO and Stage 12 Execute, with its own gate (dry-run passed, rollback validated).

### Stage-Gate Evaluation Protocol

At each stage boundary, the executing agent assesses gate readiness using the three-layer protocol defined in [gate-evaluation-spec.md](../../core/schemas/gate-evaluation-spec.md):

1. **Metrics:** Compute deterministic criteria from GitHub state. Report PASS/FAIL per metric.
2. **Judgment:** LLM-assess qualitative dimensions on a 1-5 scale. Report score and evidence per dimension.
3. **Calibration:** When ≥3 historical records exist for this boundary, include comparison and accuracy trend.
4. **Recommendation:** Apply decision matrix → PROCEED / PROCEED WITH CAVEATS / HOLD.
5. **Record:** Append assessment row to [calibration-data.md](<OPERATOR_INSTANCE_EVALS_RESULTS_PATH>/calibration-data.md).

Assessment output is posted in the stage review comment. The human operator renders the final transition decision. Outcome columns in calibration data are filled at Stage 13 close.

### Handoff Coordinator Protocol

At each stage boundary, the executing agent orchestrates the transition using the five-phase protocol defined in [handoff-coordinator-spec.md](../../core/schemas/handoff-coordinator-spec.md):

1. **Contract validation:** Verify required artifacts per [stage-io-contracts.md](../../core/schemas/stage-io-contracts.md). Missing artifacts = HOLD.
2. **Gate evaluation:** Invoke [gate-evaluation-spec.md](../../core/schemas/gate-evaluation-spec.md) three-layer assessment.
3. **Transition routing:** PROCEED → advance stage anchors. CAVEATS → advance + log. HOLD → escalate.
4. **Iteration tracking:** On downstream return per inter-stage feedback protocol — Tier 1: log. Tier 2: increment counter, apply `iteration: N` label. Tier 3: escalate + suspend. Default cap: 2 iterations (boundary-specific overrides in spec).
5. **Trend reporting:** At Stage 13 Close — compute chronic-caveat boundaries, cycle times, iteration frequency. Post Milestone rollup.

Iteration events recorded in [iteration-log.md](<OPERATOR_INSTANCE_EVALS_RESULTS_PATH>/iteration-log.md). Assessment records in [calibration-data.md](<OPERATOR_INSTANCE_EVALS_RESULTS_PATH>/calibration-data.md).

### Inter-Stage Feedback Protocol

Downstream stages may discover that upstream output is insufficient, incorrect, or unworkable. This protocol defines how feedback flows upstream within a single release, applicable to any inter-stage boundary.

**Tier 0 — Premise Rejection (Stage 4/5 Entry Re-Review):**
Stage 4 Phase A0 or Stage 5 Phase 0.5 re-review identifies a fundamental premise problem in a Triaged requirement (stale-assumption / subsumption / best-practices conflict / learnings contradiction). Tier 0 fires at stage **ENTRY** (before the stage produces output) — Tier 1/2/3 fire at stage **EXECUTION** (mid-process feedback). Numbering communicates "fires earlier than Tier 1" — Tier 0 is not a downgrade of severity; it is a different temporal anchor. Triggered by C3 classification per [triage-design-rereview.md](../references/standards/triage-design-rereview.md) § 3. Premise interrogation at stage-entry is a canonical discovery-class activity per [discovery-discipline.md](../../core/disciplines/discovery-discipline.md) § 3.1 + § 7.2 — the temporal-anchor distinction (pre-artifact discovery vs post-artifact review) operationalizes the same architectural pattern at the activity-class level.
- **Trigger:** Re-review artifact classifies any requirement as C3 (should be challenged).
- **Action:** Stage 4/5 spoke STOPS work on the affected issue, posts the Tier 0 escalation block (template per [triage-design-rereview.md](../references/standards/triage-design-rereview.md) § 9) on the parent issue (NOT the sub-task), and HOLDS the sub-task open until operator decision (Phase 1) or Tier 0 routing (Phase 2).
- **Operator decision options (Phase 1 — operator-approved on all PT):**
  - **(A) Return to Triage** — Issue Status → Triage; Stage 4/5 sub-task closed with `Returned to Triage per Tier 0 — Premise Rejection`; Triage re-runs with re-review evidence as input. Issue may re-bundle into the same Milestone or be excluded (operator decision at re-bundle time).
  - **(B) Override + proceed with deviation log** — operator records the override decision with rationale on the issue; Stage proceeds; deviation log entry appended to release plan's Deviation Log section. Sub-task continues.
  - **(C) Defer to next release** — Issue Status → Approved; issue removed from current Milestone via `gh issue edit --remove-milestone`; Stage 4/5 sub-task closed with `Deferred to next release per Tier 0 — Premise Rejection`.
- **Phase 1 default:** All Tier 0 escalations are operator-approved on all premise-problem types (PT-1 / PT-2 / PT-3 / PT-4). No autonomous returns.
- **Phase 2 protocol:** Tiered (Tier 0a autonomous-minor for PT-1 / PT-2 + Tier 0b operator-approved-major for PT-3 / PT-4). Phase 2 cutover gated on graduation thresholds per [triage-design-rereview.md](../references/standards/triage-design-rereview.md) § 10. Phase 1 → Phase 2 cutover is operator-approved; Phase 2 → Phase 1 reversion is auto-trigger.
- **Cutover discipline:** Applies to all releases going forward.
- **Gate impact:** Sub-task HOLDS pending operator (Phase 1) or autonomous Tier 0a routing (Phase 2). Other issues in the same release may continue.

**Tier 1 — Minor Adjustment:**
Downstream stage determines the plan requires a small correction that does not affect scope, sequence, or other issues. Examples: outdated file path in change spec, missing field in a template, clarifying ambiguous wording.
- **Action:** Downstream stage updates the release plan (or relevant upstream artifact) directly via git commit.
- **Signal:** Commit message includes `[ADJUST]` tag and references the affected issue(s). No operator notification required.
- **Gate impact:** None. No re-gate of the upstream stage.

**Tier 2 — Scope Change:**
Downstream stage determines the plan requires a change that affects scope, sequence, or other issues — but the plan is fundamentally sound. Examples: additional file needs modification, dependency ordering needs revision, acceptance criteria need refinement.
- **Action:** Downstream stage stops work on the affected issue(s) and flags the deviation to the operator.
- **Signal:** Comment on the relevant sub-task or Milestone with `[SCOPE CHANGE]` tag, specific description of what changed and why, and a recommendation (adjust plan vs. proceed with deviation documented).
- **Gate impact:** Operator decides: (a) adjust the release plan (operator or upstream stage re-runs relevant planning steps), or (b) proceed with the deviation documented in the release plan's deviation log.

**Tier 3 — Plan Rejection:**
Downstream stage determines the plan is fundamentally unworkable for one or more issues. Examples: critical file has been restructured since planning, design approach is infeasible, prerequisite not met, circular dependency discovered.
- **Action:** Downstream stage stops all work on the affected issue(s) and returns to the operator with specific blockers.
- **Signal:** Comment on the relevant sub-task with `[PLAN REJECTION]` tag, specific blockers with evidence, and which upstream stage should re-run.
- **Gate impact:** Operator re-runs the upstream stage (Planning or Solutioning) for the affected issue(s). Unaffected issues in the same release may continue.

#### AC-Drift Handling Protocol

Acceptance criteria are authored at Intake (Stage 1) and evaluated at QA Testing (Stage 8). Between those points, context may shift (version numbers, scope adjustments, dependency resolutions); AC text written at Intake may reference assumptions that no longer hold at QA time. This protocol defines (1) how Planning detects and refreshes drifted AC upstream and (2) how QA renders a verdict on residual drift downstream.

**Cutover discipline:** Applies to all releases entering Stage 4 strictly AFTER the v1.01-intake merge SHA recorded in [`<OPERATOR_INSTANCE_RELEASE_LOG_PATH>`](<OPERATOR_INSTANCE_RELEASE_LOG_PATH>). **The v1.01-intake release itself is exempt** — the protocol shipping in v1.01-intake cannot fire on its own bundling without creating a reflexive-pipeline loop. All releases that entered Stage 4 prior to v1.01-intake are also exempt.

##### Planning-side detection (upstream prevention)

Stage 4 Phase A0 (Triage→Design Re-Review per [`release/references/standards/triage-design-rereview.md`](../references/standards/triage-design-rereview.md)) per-issue table extends D2 (Platform-localized knowledge) finding to include an **AC-currency check**: for each AC line in the issue body, the spoke verifies the AC's stated context (version numbers, file paths, named upstream artifacts) against current platform state. Mechanism:

- AC text contains a version reference (`vX.Y` token) → verify the referenced version matches the active release version OR a still-relevant prior release. Mismatch (e.g., AC names a prior version while the active release is a later one) → CURRENCY-MISMATCH finding.
- AC text contains a file-path reference → `test -e <path>` against the release branch base. Missing path → CURRENCY-MISMATCH finding.
- AC text contains a named upstream artifact (issue #, sub-task #) → `gh issue view #N --json state` against current GitHub state. State change since Intake (e.g., the referenced issue closed-by-merge that subsumes this AC's premise) → CURRENCY-MISMATCH finding.

CURRENCY-MISMATCH findings route as Tier 1 [ADJUST] per § Inter-Stage Feedback Protocol when the AC can be locally refined to match current context (Planning spoke amends the AC text in the issue body via `gh issue edit --body`, commits a `[ADJUST]` deviation-log entry in the release plan). When the mismatch indicates the AC's premise itself is invalid (the rule the AC was asserting no longer maps to current platform shape), Planning escalates Tier 2 [SCOPE CHANGE] per § Inter-Stage Feedback Protocol for operator decision: refine, defer, or reject the AC. Composes with Bundle Mutability Protocol A7 sub-window B (Stage 4 Planning entry → Stage 5 per-issue Solutioning) — AC refinement is a permitted mutation in sub-window B with `[BUNDLE *]` comment + release plan deviation log entry.

##### QA-side interpretation (downstream verdict enum extension)

When the Planning-side detection misses drift (e.g., context shifts between Stage 5 Collective-Review scope-lock and Stage 8 QA, post-lock window), or when drift was detected but operator elected to proceed without amending the AC, the Stage 8 spoke renders a per-criterion verdict from the extended closed enum. The extended per-criterion verdict enum at [`release/references/pipeline/stage-08-qa-testing.md § 5 Phase B`](../references/pipeline/stage-08-qa-testing.md) is:

| Verdict | When the spoke emits this | Severity / Rationale field |
|---|---|---|
| `MET` | AC criterion satisfied by PR content | — |
| `NOT MET` | AC criterion unsatisfied | Severity: `Blocker` / `Warning` |
| `PARTIAL` | AC criterion partially satisfied | — |
| `N/A-WITH-RATIONALE` | AC references stale context; the criterion's premise no longer applies AND the underlying intent of the criterion has been met by a different mechanism (typical: version reference drift where the equivalent assertion holds for the new version) | REQUIRED `Drift-rationale:` field naming the stale-context premise + the equivalent-assertion evidence |
| `REINTERPRET-WITH-RATIONALE` | AC references stale context; the criterion's premise can be re-mapped to current context AND the re-mapped criterion is `MET` | REQUIRED `Drift-rationale:` field naming the stale-context premise + the re-mapping + the evidence the re-mapped criterion is met |
| `FLAG-UPSTREAM` | AC drift is structurally significant (criterion cannot be evaluated as written AND cannot be locally re-interpreted) | REQUIRED `Drift-rationale:` field + escalation to Tier 1 [ADJUST] (when fix-forward refinement of AC is possible) or Tier 2 [SCOPE CHANGE] (when scope of issue itself is affected) per § Inter-Stage Feedback Protocol |

The 3 drift verdicts are **not failure modes** — they record legitimate handling of upstream drift that escaped Planning-side detection. Drift verdicts compose with overall verdict at Phase E:
- All AC verdicts in `{MET, N/A-WITH-RATIONALE, REINTERPRET-WITH-RATIONALE}` → `ACCEPT` is permitted (Phase E Tier 3 operator decision).
- Any AC verdict = `FLAG-UPSTREAM` → operator decision required (typically `CONDITIONAL ACCEPT` with deviation-log entry OR `REJECT` if the flagged AC's premise breaks the release outcome).
- Drift verdicts do NOT trigger Lane 2 (QA→DT Return) per Phase C — they trigger Tier 1 [ADJUST] (Planning-side AC refinement on the issue body) OR Tier 2 [SCOPE CHANGE] (operator scope decision), not engineering rework.

##### Verdict-selection criteria (when each drift verdict applies)

- Use `N/A-WITH-RATIONALE` when: (a) the AC references a specific upstream artifact / version / configuration that is no longer the active context; (b) the spirit of the AC (what the operator was actually asserting) is satisfied by an equivalent observable signal in the current release; (c) verifying the equivalent signal does not require re-interpreting the AC text as a different criterion. Example: in one worked case, two issues' AC said "the prior release itself produces a deployment log entry"; QA verified that the current release produced a deployment log entry (equivalent assertion under the new version reference); N/A-WITH-RATIONALE = "the AC's prior-version reference is stale; the current release's deployment-log row at RELEASE_LOG.md confirms the equivalent assertion."

- Use `REINTERPRET-WITH-RATIONALE` when: (a) the AC text can be locally re-mapped to the new context by substituting the stale reference; (b) the re-mapped criterion is verifiable as `MET` against current state; (c) the substitution is a 1:1 mapping (no semantic shift). Example: AC says "the prior-version tag uses signed-annotated format"; the release is the next version; re-mapped criterion: "the current-version tag uses signed-annotated format"; verified MET → REINTERPRET-WITH-RATIONALE.

- Use `FLAG-UPSTREAM` when: (a) neither N/A nor REINTERPRET applies (no equivalent signal, no clean re-mapping); OR (b) the drift indicates the AC's premise is structurally invalid (the rule the AC was asserting cannot be evaluated in current context); OR (c) the spoke cannot resolve the drift without operator judgment. Tier 1 [ADJUST] is the default routing (Planning spoke amends the AC); Tier 2 [SCOPE CHANGE] if scope decision required.

##### Composition with adjacent protocols

- **Composes with Bundle Mutability A7** (same file lines 134-176): Planning-side AC-currency check IS a sub-application of trigger T4 (Stage 4 boundary currency check). The A7 protocol governs the broader scope-mutability surface; AC-Drift Handling is the AC-text-specific application within that surface.
- **Composes with Triage→Design Re-Review** ([`release/references/standards/triage-design-rereview.md`](../references/standards/triage-design-rereview.md)): the per-requirement table's D2 column is the place where the AC-currency check finding is recorded at Stage 4 Phase A0. C2 classifications (needs refinement) route Tier 1 [ADJUST] AC text refinement; C3 classifications (should be challenged) route Tier 0 Premise Rejection (AC's premise itself is rejected — out-of-scope for AC-Drift Handling, in-scope for Premise Rejection).
- **Composes with the planned Acceptance Assertion Framework** (relates-to, informational): when that framework ships, AC ingestion + grading rubric will provide a structured assertion type per AC. The 6-value verdict enum from this protocol is the verdict surface that the framework's grading rubric outputs into. No coupling is required until it ships.

##### Calibration

Stage 13 Close spoke logs per-release counts: (a) Planning-side CURRENCY-MISMATCH findings emitted at Phase A0; (b) per-criterion drift-verdict counts at Stage 8 Phase B (by-verdict-value tally); (c) FLAG-UPSTREAM escalations routed Tier 1 vs Tier 2. After the 3rd post-cutover release, calibration determines whether (i) Planning-side detection is over-firing (high CURRENCY-MISMATCH count + low downstream drift-verdict count) → tighten Planning-side detection criteria; (ii) Planning-side detection is under-firing (low CURRENCY-MISMATCH count + high downstream drift-verdict count) → widen Planning-side detection criteria; (iii) drift base rate is genuinely near zero → consider de-escalation to QA-only mode.

**Escalation rule:** When in doubt between Tier 1 and Tier 2, escalate to Tier 2. When in doubt between Tier 2 and Tier 3, escalate to Tier 3. Over-escalation is a process cost; under-escalation is a quality risk.

**Boundary generalization:** This protocol applies at every stage transition. While most feedback flows are downstream-to-upstream (e.g., Engineering → Planning, QA → Engineering), the same tiers and signals apply regardless of which stages are involved. Issue-specific boundary protocols (e.g., the DT↔Engineering boundary protocol) instantiate this general protocol with stage-specific criteria and examples.

### Stage 1: Intake
**Purpose:** Capture improvement proposals with enough structure for triage.
**Inputs:** Observation, user feedback, drift detection, gap discovery during any processing.
**Outputs:** GitHub Issue with structured fields (title, priority, category, description, evidence, proposed change, affected files, dependencies, documentation impact, acceptance criteria).
**Documentation-impact declaration.** Every Intake issue (`improvement.yml` + `bug.yml`) carries a required `Documentation Impact` field declaring the K1 codified docs the change touches. Two acceptable forms: (a) pointer list — one bullet per affected doc with `file path | action (link / create / update) | brief reason`; (b) explicit `None — no documentation impact (rationale: <one phrase>)`. The declaration is the trigger for downstream Beats 2/3 at Stage 6 and Stage 13. Scope boundary: K1 codified corpus only — `core/rules/`, `core/`, `core/governance/`, `release/skills/*/SKILL.md` + `references/`, `CLAUDE.md`. The *absence* of any answer is the gate-failing state (G-CL8); the explicit "None" answer resolves trivially. `observation.yml` is exempt — observations promote to `improvement.yml` at Stage 2 Triage, and the field fires at promotion. **Cutover discipline:** Applies to all releases going forward.
**Gate:** Triage Readiness — per `gate-criteria-spec.md`. All required fields populated, evidence labeled, format valid.
**Automation:** Tier 2 (Recommend) — agent drafts issue, human reviews.
**Self-repair:** Retry on `gh issue create` transients; Escalate to Observation tier when template fields cannot be populated. See [autonomous-execution-model.md](../../core/disciplines/autonomous-execution-model.md) § Per-Stage Application.
**Ref Model:** Part 6 Stage 1-2 — "Identify and capture demand."

### Stage 2: Triage
**Purpose:** Evaluate each issue for priority, feasibility, and fit — producing a binary decision (Approved/Deferred/Rejected).
**Inputs:** Intake issue with all structured fields populated.
**Outputs:** Triage decision, priority confirmation, category verification, board status update, native dependencies mirrored from body `FS+0d` subset per A3.5 (cutover applies after the release that introduced this mirror shipped; non-gate-blocking; per [`pipeline/stage-02-triage.md` § Native-Dep Mirror](../references/pipeline/stage-02-triage.md) and [`ticket-information-architecture.md § Native Dependencies`](../references/specs/ticket-information-architecture.md)); for SPLIT verdicts (5-test T1 atomicity failure per [`intake-style-guide.md`](../references/how-to/intake-style-guide.md)), see [`fission-convention.md`](../references/protocols/fission-convention.md). Applies to issues entering Triage after the release that introduced this rule shipped; the introducing release itself is exempt per reflexive-pipeline-loop discipline.
**Gate:** Workflow Readiness — per `gate-criteria-spec.md`. Priority validated, duplicates resolved, dependency state validation passed (G2-04), category verified, Decision Date set in GitHub Projects Date field (G2-06 — gate-blocking; see `pipeline/stage-02-triage.md` § Phase B B2a for forcing-function and failure-handling specification), similarity composite-signal candidate pairs routed (G2-09 — judgment-graded; 4-outcome routing; cutover applies post-introduction), size:XL decomposition routing recorded (G2-10 — `size:L` informational; cutover applies post-introduction), oversize-predicate decomposition routing recorded when ANY composite-OR predicate fires (G2-11 — COMPOSITE-OR: P1 `size:XL` OR P2 declared decomposition-hook OR P3 AC ≥ 7 OR file ≥ 5; 3-outcome enum: kept-as-one / split per [`fission-convention.md`](../references/protocols/fission-convention.md) / escalate per Tier 2 [SCOPE CHANGE]; cutover applies to issues entering Triage after the release that introduced this predicate shipped; **the introducing release itself is exempt** per the release-wide D-CutoverPosture reflexive-exempt-all ratification).
**Dependency validation:** Before Approved, all `#N` dependency refs validated against compatible states (Approved/Bundled/In Progress/Done). Rejected deps block; Deferred and Proposed deps warn. Per `gate-criteria-spec.md` G2-04 and `pipeline/stage-02-triage.md` A3.
**Native-dep mirror (A3.5):** After G2-04 passes, the spoke mirrors body `FS+0d` deps to native `blocked-by` per `pipeline/stage-02-triage.md` § Native-Dep Mirror. Non-FS-zero-lag types (`SS`, `FF`, `SF`, `FS±Nd`) stay body-only by design. Mirror is non-gate-blocking — failures surface in A6 summary but do not block Phase B verdict. **Cutover discipline:** Applies to all releases going forward.
**Triage cadence:** Triage runs on a hybrid cadence aligned with the per-archetype release rhythm declared in § Methodology Variation — Release Cadence. (1) **P1 SLA (on-arrival):** P1 (Critical) issues claim Triage AND render an Approve/Reject/Defer verdict **within 1 business day** [CALIBRATE-AFTER-3 — single-operator PMO posture; tune to N business days when team_size ≥ 2] of intake. (2) **P2-P4 batch cadence:** P2 (High) / P3 (Medium) / P4 (Low) issues batch-triage before each release-planning ceremony — the ceremony sequence is **Triage → Bundle → Plan**, executed once per `delivery_approach`-parameterized bundling rhythm (per-sprint for Scrum, per-bundling-session for Kanban, per-milestone for Waterfall). (3) **Weekly minimum (floor):** Independent of bundling cadence, the operator reviews all `status: proposed` issues at least once per calendar week to prevent backlog staleness — even when no bundling session is planned. The canonical cadence definition lives at [`pipeline/stage-02-triage.md` § 5 Process Phase B3](../references/pipeline/stage-02-triage.md); this paragraph is the release-process summary citing that shard (DRY single-source-of-truth). (4) **Deferred re-evaluation (floor):** Sibling to the `status: proposed` floor, the operator re-evaluates all open `status: deferred` issues on a recurring cadence — **at each release-planning ceremony, and at minimum monthly** — to prevent silent deferred-backlog accumulation. The sweep enumerates the deferred set (`gh issue list --label "status: deferred"`) and, for each issue, re-opens it to `status: proposed` when **any** re-open criterion holds: (a) the deferral's blocking dependency or precondition has cleared; (b) the deferred work re-enters scope for an upcoming release; (c) the item carries a staleness flag raised per [`deferred-item-tracking.md § 13.7`](../references/standards/deferred-item-tracking.md) (this cadence is the scheduled sweep that *reads* the §13.7 staleness signal — §13.7 *produces* the flag, the cadence consumes it, per the §13.9 composition seam); or (d) operator judgment that the original defer rationale no longer holds. This cadence **promotes to a defined recurring trigger** the enumerate-affordance described in [`deferred-item-tracking.md § 6`](../references/standards/deferred-item-tracking.md) ("the hub's next-release planning sweep *should* include a step to enumerate `status: deferred` issues … for re-triage consideration") — §6 is cited, not restated. A re-opened deferred issue follows the **standard Stage-2 re-triage path** back to `status: proposed` (full re-evaluation) or `status: approved` (priority/scope unchanged) per the Deferred → re-triage state transition at [`ticket-information-architecture.md` line 239](../references/specs/ticket-information-architecture.md) — no bespoke re-entry mechanics. **Downstream semantic dependency:** a sister management-task spec's Phase A6.5 Pattern (1a) "Stale issues" consumes the P1 SLA numeric as input. Revisions to the 1-business-day threshold after Collective Review trigger a re-review obligation on that sister spec. **Cutover:** Applies to releases entering Stage 2 strictly AFTER the v1.02-triage-and-related merge SHA recorded in [`<OPERATOR_INSTANCE_RELEASE_LOG_PATH>`](<OPERATOR_INSTANCE_RELEASE_LOG_PATH>). **The v1.02 release itself is exempt** per reflexive-pipeline-loop discipline (the cadence rule shipping in v1.02 cannot retroactively fire on v1.02's own Stage 2). All issues that entered Stage 2 prior to v1.02 are also exempt.
**Automation:** Tier 2 (Recommend) — agent analyzes and recommends, human renders decision.
**Self-repair:** Retry on `gh issue view` / `gh project item-edit` transients; Escalate on G2-04 dependency block (Rejected dep). See [autonomous-execution-model.md](../../core/disciplines/autonomous-execution-model.md) § Per-Stage Application.
**Pattern Review Cadence:** Observation-tier intake artifacts do NOT route through the Approve/Defer/Reject decision axis; they accumulate per `core/governance/OPERATIONS.md` § Pattern Review Cadence Protocol and graduate to Proposals via emergence-rule firing. Operator triages emergent patterns via `release-planner` Mode D — Pattern Review (DRAFT phase) + `release-executor` Mode G — Pattern Review Execute (EXECUTE phase on PROMOTE verdict).
**Ref Model:** Part 6 Stage 1-2 — "Assess and prioritize demand."

### Stage 3: Bundle
**Purpose:** Group approved issues into a versioned release with dependency ordering and capacity validation.
**Inputs:** Approved issues on the backlog, existing Milestones, dependency graph, file contention map, release history.
**Outputs:** Milestone with version number, assigned issues, dependency graph, capacity assessment, bundle rationale, Release Outcome Statement embedded in Milestone description (per [release-outcome-statement-template.md](../references/specs/release-outcome-statement-template.md); cutover applies to Milestones created after the release that introduced this requirement shipped; the introducing release itself is exempt per reflexive-pipeline-loop discipline).
**Process:** Agent analysis (A1-A8: Release Readiness gate check per `gate-criteria-spec.md` Gate 3, dependency graph construction including critical-path / longest-chain analysis, scope coverage, capacity heuristics, contention analysis, bundle recommendation, new-track placement rationale conditional) → Human decision (B1-B4: review gate results, adjust, create Milestone, assign version — note: version numbers are version keys, not chronological deploy order; see [RELEASE_LOG.md](<OPERATOR_INSTANCE_RELEASE_LOG_PATH>) § Deploy Order for the chronological timeline). Operator override with documented rationale for any gate failure.

**Churn-budget threshold (amend-vs-re-bundle classification):**

```
amend     := (composition_delta_pct ≤ 30%) AND (theme_preserved == TRUE)
re-bundle := (composition_delta_pct > 30%)  OR  (theme_preserved == FALSE)
```

where `composition_delta_pct = (issues_added + issues_removed) / |original_bundle|`. 30% threshold carries MEDIUM confidence — `[CALIBRATE-AFTER-3]`. Tie-break at exactly 30%: classify as `amend`.

**A8 — Critical-Path Analysis (CPM / longest-chain over typed-dep edges).** After A2's Kahn's BFS topological sort completes, Phase A runs a single forward-pass DP-DAG longest-path relaxation over the emitted topo-sorted sequence to compute the **schedule-determining chain** — the longest dependency-determined chain across the release graph. The chain emits at two surfaces: (1) **Stage 3 Bundle gate signal** — presented to operator at Phase B1 review for awareness of the schedule-determining chain before scope-commit; (2) **`release-planner` Mode B durable artifact** — persisted as `### Critical Path` H3 under the `## Dependency Graph` H2 in `release/releases/plans/vX.Y_RELEASE_PLAN.md` (per `release/skills/release-planner/SKILL.md` Mode B Output Format row 2). Same algorithm, two emit sites.

- **Algorithm:** DP-DAG (dynamic programming over Kahn's-emitted topo-sorted DAG) per `release/skills/release-planner/references/dependency-analysis.md § Step 5: Longest-Path Computation (CPM)`. Composes natively with the existing Kahn's BFS (ADR-1) — no parallel graph machinery; preserves the priority-desc → issue-asc tie-breaker. Complexity O(V+E).
- **Degraded-mode default (per D-DegradedMode RATIFY):** Degraded mode is the **DEFAULT** until the typed-dep substrate populates per-edge metadata for every in-bundle edge. Activation predicate is `any-untyped-edge` — if ANY edge lacks typed metadata, the whole computation runs in degraded mode and the output carries the `[DEGRADED-MODE: ...]` annotation header. Transition to typed mode fires automatically when every edge carries typed metadata; no operator-cutover ceremony, no `.mode` flag. `[CALIBRATE-AFTER-3]` MEDIUM-confidence on the activation predicate (rises to HIGH once the typed-dep mirror populates and three post-cutover releases exercise typed mode).
- **Canonicalization 1 (algorithm choice):** DP-DAG over Floyd-Warshall over longest-chain heuristic. Composability with existing Kahn's wins; Floyd-Warshall requires parallel adjacency-matrix machinery with no fidelity gain on sparse release DAGs. Full rationale at `dependency-analysis.md § Canonicalization 1`. Per R1 Evidence-Grounding artifact.
- **Canonicalization 2 (degraded-mode activation predicate):** any-untyped-edge activates degraded mode for the entire bundle (binary all-or-nothing) — prevents mixed-signal output where a chain length number's semantic interpretation varies edge-by-edge. Full rationale at `dependency-analysis.md § Canonicalization 2`. Per R1 Evidence-Grounding artifact.
- **Typed-dep read-surface coordination:** `read_dependencies(issue_number) → List[TypedEdge]` is the opaque interface owned by the typed-dep substrate; the CPM step consumes the resolved output via `is_typed_edge(edge)` field-presence check. Body Dependencies field is the canonical read-surface per `ticket-information-architecture.md § Conflict Resolution` and per Stage 6 Model A adoption (body→native one-way mirror).
- **Failure-mode discipline (per `release-planner/SKILL.md § Domain-Specific Failure Modes`):** "Critical-path output omits mode annotation — OUT" — Stage 7 DT asserts the `### Critical Path` H3 leads with one of the two canonical annotation forms (`[DEGRADED-MODE: ...]` or `[TYPED-MODE: ...]`) before chain or length emission.
- **AC-3 success-signal.** `release-process-fitness.md § 1 Success Signals` adds a Schedule-Management / CPM fitness signal, closing the audit dimensional blind spot identified by prior audit.

### Stage 4: Planning
**Purpose:** Transform a scoped Milestone into a dependency-ordered implementation plan with file-level change specifications.
**Inputs:** Milestone with assigned issues, dependency graph, current file state.
**Outputs:** Release plan file (`release/releases/plans/vX.Y_RELEASE_PLAN.md`) committed per the topology selected at the D-C Branch Topology decision gate — under single-branch topology, on the release branch at Engineering Commit 0; under Option-A topology, on main via a Stage 4 release-plan chore PR before per-issue scaffolding (per [`hub-spoke-bridge.md` Procedure 0 § Canonical location](../references/how-to/hub-spoke-bridge.md)). Content: implementation sequence, file change matrix, risk register, delivery strategy, verification plan, rollback strategy.

**Cross-PR Overlap Audit (A4 extension):** A4 file contention resolution covers two distinct operations. (1) **Within-release contention**: files claimed by multiple change-specs in the current release plan; resolved via sequencing or scope split. (2) **Cross-PR contention**: files in the current change-spec also being modified by recently-merged or open PRs outside this release; surfaced via baseline-pinned analysis (last-N merged PRs + open PRs at audit-start commit SHA per `<OPERATOR_INSTANCE_ANALYSIS_PATH>/file-overlap-audit-<date>/`). Cross-PR contention informs sequencing (defer until upstream merges) or risk-register entries. **Distinction discipline**: this audit is NOT byte-identity verification of release-plan files at Engineering Commit 0 — that check confirms internal consistency of the plan; this check identifies external collisions across PRs. Both check forms operate at A4 but answer different questions. **Append-pattern detection (per [ADR-005](../ADRs/ADR-005-append-pattern-aware-cross-pr-contention-scoring.md))**: post-cutover audits classify each contended file with an `overlap_class` enum (`append-pattern` / `line-range-overlap` / `single-pr`) computed from per-PR `line_ranges` (hunk-range JSON arrays); files with `overlap_class = append-pattern` are informational (structurally HIGH, operationally LOW — append-pattern PRs almost never conflict at merge time), while `line-range-overlap` retains the ADR-001 sequencing/scope-split mitigation guidance. Canonical implementation: `python3 release/tools/check-line-range-overlap.py` (optional for ≤3-PR audits; recommended for ≥3-PR cases for reproducibility). Cutover: applies to releases entering Stage 4 on or after the introducing release's merge SHA recorded in `<OPERATOR_INSTANCE_RELEASE_LOG_PATH>`; pre-cutover releases are exempt. Append-pattern detection (ADR-005) applies to releases entering Stage 4 after the release that introduced it shipped; **that introducing release itself is exempt** (reflexive-pipeline-loop discipline — the rule shipping in a release cannot fire on that release's own bundling).

**Baseline-pin temporal limitation:** The A4 audit is **baseline-pinned** — it surveys cross-PR contention against the audit-start commit SHA only. Concurrent releases merging to `main` AFTER the audit but BEFORE Stage 12 are NOT detected by A4. The mid-pipeline divergence checkpoint at [Stage 9 Phase A6.5](#stage-9-plan-review) (PRIMARY, HALT-eligible) plus informational checks at Stage 7/8 entry (SECONDARY, warn-only) complement the A4 baseline snapshot with stage-boundary re-checks; Stage 12 Phase A.5 remains the post-GO ultima-ratio detector per [`pipeline/stage-12-execute.md` § Phase A.5](../references/pipeline/stage-12-execute.md). **Cutover discipline:** Applies to releases entering Stage 4 strictly AFTER the v1.01-intake merge SHA recorded in [`<OPERATOR_INSTANCE_RELEASE_LOG_PATH>`](<OPERATOR_INSTANCE_RELEASE_LOG_PATH>); **v1.01-intake itself is exempt** (reflexive-pipeline-loop discipline — this limitation is the subject of the introducing change itself; v1.01-intake's own Stage 4 audit ran AS-IS per this discipline).

**Domain-Best-Practice Sourcing-or-Flag Step (Phase A1.5):** Between A1 milestone validation and A2 sequencing, the Planning spoke determines whether the release operates on a domain whose external best-practice the platform does not already encode. The ship-with-flag mechanism requires EITHER sourcing authoritative guidance (Mode A — a `domain_practice` label carrying a `source` citation, a `date`, and the `name` of the practice) OR emitting a machine-readable Unsourced-Domain flag (Mode B — a `domain_practice` label whose `source` is the literal token `UNSOURCED-DOMAIN`, with a `date` and a one-line `rationale`). #### Release-Plan Versioning Protocol

Governs the release plan **after** it has been authored and committed. The plan is a Stage 4 output artifact; this protocol defines how its revisions are tracked and when a plan change requires re-planning versus a minor adjustment. It introduces no new severity ladder — it **names which existing rung** a plan-file change lands on (Inter-Stage Feedback Tiers + Bundle Mutability A7 thresholds).

**Artifact of record.** The release plan lives as a single committed file at `release/releases/plans/vX.Y_RELEASE_PLAN.md` (one file per release; naming per [`release-corpus-schema.md`](../references/standards/release-corpus-schema.md) § `type: plan`). This file is the artifact of record for the release's plan. There is exactly one canonical plan file per release — no mirror copy exists (the legacy `.claude/rules` ↔ `engineering/rules` mirror-pair collapsed to this single governance file in the modular-monolith layout).

**Versioning invariant — git history IS the version trail.** Plan revisions are git commits to the plan file (on the release branch under D-C single-branch topology, or via the Stage 4 release-plan chore PR / subsequent commits under D-C Option-A topology, per [`hub-spoke-bridge.md`](../references/how-to/hub-spoke-bridge.md) Procedure 0). The plan file MUST NOT carry an in-file plan-version number, revision counter, or `vN`-of-the-plan marker. Auditability is provided by `git log --follow release/releases/plans/vX.Y_RELEASE_PLAN.md`. (A plan file MAY cite the release's own baseline SHA and dated operator-decision stamps — those identify the *release*, not a *plan revision number*, and are permitted.)

**Revision-commit discipline.** Each revision commit to the plan file MUST state, in its commit message, **what changed and why** (e.g., `plan(vX.Y): re-sequence #A before #B — dependency surfaced at Stage 5 [SCOPE CHANGE]`). When the plan is updated while the release PR is open, the update lands as a commit **in that same PR** (no out-of-band plan edits), so the plan diff is reviewable at Stage 9 Plan Review alongside the change it documents. This discipline also covers Change-Description refresh commits (the operator-facing `## Change Description` section embedded in the plan file) as a special case.

**Minor-vs-major classification.** A plan change is classified, then routed, per the table below. The classification reuses the existing Inter-Stage Feedback Tiers (§ Inter-Stage Feedback Protocol) and the Bundle Mutability A7 amend/re-bundle thresholds (§ Stage 3: Bundle, A7) — this protocol references those rungs and thresholds rather than restating them.

| Change class | Definition (when this row applies) | Routing | Re-gate? |
|---|---|---|---|
| **Minor adjustment** | Corrects the plan without changing **scope, the issue set, the issue sequence, or another issue** — e.g., outdated file path in a change spec, clarified wording, risk-register typo, a verification-step refinement. | Update the plan file directly via a git commit tagged `[ADJUST]` (Inter-Stage Feedback **Tier 1**). No operator notification, no re-gate. | **No.** |
| **Major scope change** | Adds or removes an **issue** from the release, OR changes the **issue set or the dependency sequence** such that the bundle's composition or ordering changes (this includes any dependency-driven re-sequence — see the disambiguation note below). Per A7: theme preserved AND ≤30% composition delta → **amend**; >30% OR theme broken → **re-bundle**. | Stop work on the affected issue(s); flag the operator with an Inter-Stage Feedback **Tier 2 [SCOPE CHANGE]** comment + a release-plan **deviation-log** entry. Operator decides amend vs. re-bundle. | **Yes — re-run the transition gate** (see below). |
| **Plan unworkable** | The plan is fundamentally infeasible for one or more issues (critical file restructured since planning, prerequisite unmet, circular dependency discovered). | Inter-Stage Feedback **Tier 3 [PLAN REJECTION]**; return to the operator with blockers; the operator re-runs the upstream stage (Planning or Solutioning). | **Yes** (upstream stage re-runs). |

**Re-sequence disambiguation (single unambiguous routing).** A change to the issue **sequence** — including a dependency-driven re-sequence (a dependency edge surfaces or changes such that issue ordering must move) — is a **Major scope change → Tier 2 [SCOPE CHANGE]**, not a Minor adjustment. The Inter-Stage Feedback Tiers settle this with no overlap: Tier 1 [ADJUST] applies **only** to corrections that "do not affect scope, sequence, or other issues," so any sequence change is excluded from Tier 1 by definition, while "dependency ordering needs revision" is the **named example** under Tier 2 [SCOPE CHANGE]. The A7 amend/re-bundle axis is orthogonal — it measures `composition_delta_pct = (issues_added + issues_removed) / |original_bundle|`, so a pure re-sequence (zero issues added or removed) computes 0% delta and classifies as **amend** (never re-bundle) **after** the Tier 2 escalation routes it to the operator. Severity routing (Tier 2) and composition mechanics (A7 amend) are therefore complementary, not a competing three-way split: a dependency-edge re-sequence is always Tier 2 [SCOPE CHANGE], handled as an A7 amend when no issue is added or removed.

**Re-run the transition gate — bound to existing gates.** For a **Major scope change**, "re-run the transition gate" resolves to the gate appropriate to where the release sits in the pipeline — these gates **already exist**; this protocol creates none:
- **Issue added/removed or bundle re-composed, pre-Engineering (Stage 3→5 soft-lock window):** re-execute the relevant **Stage 3 Bundle** steps for amend/re-bundle (Bundle Mutability A7 refresh-outcome paths (2)/(3): `[BUNDLE AMENDMENT]` / re-bundle ceremony + Milestone-description amendment + release-plan deviation-log entry), then **Stage 4 → 5 Collective Review** re-validates the changed scope before scope-lock.
- **After Collective Review scope-lock (Stage 6 through Stage 9, hard-locked):** the change is a scope-lock override governed by the **§ Collective Review Protocol Scope Lock Rules** (operator Decision Briefing with impact assessment + deviation-log entry) — NOT a silent plan edit.

In both cases the plan-file revision commit and the deviation-log entry are the durable trail; the re-gate is the existing ceremony, re-entered.

This protocol governs release plans going forward; it is not applied retroactively to plans completed before it was adopted.

### Collective Review Protocol (Post-Solutioning)
**Trigger:** Release has ≥2 issues with Solutioning activated (per Stage 4 applicability matrix) AND all applicable Solutioning sub-tasks are closed.
**Purpose:** Validate cross-issue design coherence before authorizing Engineering. Evaluates the set of Solutioning outputs as a coherent unit — conflicting designs, unresolved cross-dependencies, cumulative risk.
**Process:** Hub produces a consolidated Decision Briefing covering all Solutioning outputs:
1. Cross-issue dependency satisfaction (all directional dependencies resolved)
2. Design conflict detection (competing approaches to shared files or patterns)
3. Cumulative risk assessment (aggregate blast radius, compounding risks)
4. Scope confirmation (release scope still valid after Solutioning discoveries)
5. Cross-D upstream-compatibility scan — for each D-decision rendered at the Operator Decision Gate in this release, verify compatibility with Anthropic `anthropic-skills:skill-creator` convention. This check is a specific application of Mechanism 1 (Localization Check) per `decision-discipline.md` § 2.1 — upstream compatibility is one localization dimension. Hub aggregates per-D findings from the D-Gate template `Upstream compatibility` subsection (per `hub-spoke-bridge.md` Procedure 0 §D-Gate Template), deduplicates when multiple D-decisions share an upstream-compat concern, and surfaces aggregated flags. A missing or omission-without-rationale `Upstream compatibility` subsection on any D-decision is a structural defect surfaced by this scan. Any `**CONFLICT.**` signal surfaced in the scan blocks scope-lock approval pending operator resolution. Hub consults `upstream-reference-catalog.md` (R2; lives at `core/standards/`) to verify each D-decision's catalog citation matches the catalog entry's current state; catalog entries whose `last_verified_date` is older than 90 days are flagged for re-verification before the scan confidently marks aligned.
6. **N-way consistency table** — for each convention appearing in ≥2 artifacts in release scope, enumerate the artifacts and verify agreement. This catches multi-artifact convention drift that pair-wise consistency checks miss.

   | Convention | Artifact 1 | Artifact 2 | Artifact 3 | ... | Owner (reserved for future ownership map) | Agreement? |
   |---|---|---|---|---|---|---|
   | `<name>` | `<file:section>: <value observed>` | `<file:section>: <value observed>` | `<file:section>: <value observed>` | ... | `<concept owner per future ownership map, when applicable; empty until that map lands>` | aligned / disagreement / N/A |

   **Scope-lock rule:** ALL N-way consistency rows aligned → operator may approve scope-lock. ANY N-way consistency row marked `disagreement` → scope-lock BLOCKED until operator override with documented rationale. Override format: `"Override: convention <name> accepted as diverged because <reason>. Deviation logged for Stage 13 retrospective."` Override rationale is part of the Decision Briefing and propagates into the release plan's deviation log.

   **Convention scope:** R4 enumerates conventions that the release scope introduces, modifies, or relies on. Pre-existing conventions outside release scope are not enumerated (would explode the table).

   **Owner column composition with the ownership-map issue.** The `Owner` column is reserved for the canonical owner per the peer-spec ownership map. When that map lands (current state: OPEN; sequencing per Stage 4 D-C KEEP-SEPARATE), the column populates from the ownership map. Until then, the column remains empty — R4 scope-lock decision does NOT depend on Owner column population (forward-compatible per D-S4).

   **Out-of-scope drift discovery:** If R4 scan surfaces a disagreement on a convention NOT in release scope (e.g., legacy drift), route as Tier 2 [SCOPE CHANGE] per § Inter-Stage Feedback Protocol for operator decision: add to release / file as next-release issue / accept as residual.

   **Evidence-grounding scan (R1 ↔ R4 composition).** For each canonicalization in any Stage 5 Solutioning output in the release, the hub records whether the Evidence-Grounding artifact per `evidence-grounding-standard.md` is present. Verdict BLOCK on missing artifact triggers operator decision: return to Solutioning for re-grounding, or override with documented rationale. Default rule: BLOCK unless operator overrides.

   **Cutover discipline:** Applies to all releases going forward.
7. **Adversarial-design-review findings ingestion.** When Solutioning fires (Phase 0 Activation Gate ACTIVE) for the release, EVERY in-scope Stage 5 spoke output is paired with an independent adversarial-review output produced by the `pmo-adversarial` agent per Phase A6.5 of [`pipeline/stage-05-solutioning.md`](../references/pipeline/stage-05-solutioning.md) and registered as `RC-5-adversarial-design-review` in [`review-composition-framework.md` § 3](../../core/standards/review-composition-framework.md). The hub consumes the per-spoke adversarial outputs — each carrying 3 structured-list findings (Premise-Rejection / Failure-Mode / Counter-Design) — and folds them into the Decision Briefing as advisory input. Aggregate-severity routing per per-spoke adversarial-output summary verdict: **Blocker** findings SURFACE in briefing with explicit operator decision required at scope-lock (override-with-rationale OR return-to-Solutioning); **Major** findings SURFACE in briefing for operator awareness (no block); **Minor** findings APPEND to release plan deviation log without surfacing in briefing. Findings are ADVISORY to the scope-lock decision — they inform the Operator; the Operator decides scope-lock. Missing adversarial-review output for any in-scope Stage 5 spoke is a structural defect surfaced by this scan (treated identically to a missing R1 Evidence-Grounding artifact: BLOCK scope-lock unless operator overrides). **Cutover discipline:** Applies to all releases going forward.

Operator reviews the briefing and renders scope lock decision: approve (scope locks, Engineering authorized), adjust (modify scope, re-open affected Solutioning), or reject (return specific issues to Solutioning).
**Scope lock:** Post-review, scope is "hard locked" through Stage 9. Override requires Decision Briefing to operator with impact assessment — governed, not forbidden.
**Skip condition:** Does not fire when 0-1 issues have Solutioning activated or Solutioning was skipped for the entire release.
**Relationship to Stage 9:** Not redundant. Collective review validates design coherence (pre-engineering). Stage 9 validates implementation quality (post-engineering). Different timing, inputs, and decisions.

**Purpose:** Final review of the release plan, implementation, and test results before deployment authorization.
**Inputs:** Complete PR (code + tests + verification), release plan, risk register, test results, Release Outcome Statement (read from Milestone description).
**Outputs:** Go/No-Go decision (conditional on no post-GO main divergence per Phase A6.5 — see below; re-validation via Stage 12 Phase A.5 if divergence occurs between GO and merge), any last-minute adjustments, goal-conformance verdict (G-PR7 — ALIGNED / DIVERGED-WITH-RATIONALE / MISALIGNED), mid-pipeline divergence verdict (G-PR8 — CLEAN / DIVERGED-RELEASE-FILES-UNTOUCHED / DIVERGED-RELEASE-FILES-TOUCHED), GO baseline-currency verdict (G-PR9 — CURRENT / STALE-REVALIDATE / STALE-VOID).

**Routing:** Stage 9 GO → Stage 12 Execute (Stages 10-11 compressed; see Stage Compression above). If compression exceptions apply, Stage 9 GO → Stage 10 Dry Run → Stage 12 Execute.
**Goal-conformance check (G-PR7).** Phase A7 — hub reads the `### Release Outcome Statement` H3 block from the GitHub Milestone description (`gh api repos/{REPO}/milestones/<N> --jq .description`), reads the PR scope (`gh pr view <PR> --json files,additions,deletions`), reads the release plan §Implementation Sequence + File Change Matrix, AND reads each release-scoped issue AC. **Release Readiness Scan.** At Stage 9 Phase A6 of evidence assembly, the hub authors the 13-dimension Release Readiness Scan per [`release/references/specs/release-readiness-scan-spec.md`](../references/specs/release-readiness-scan-spec.md). The 13 dims aggregate Stage 4-8 outputs into a fixed-dimension table the operator reviews before rendering GO/NO-GO. Status enum: PASS / FAIL / PARTIAL / N/A. Aggregate verdict: All-PASS recommends GO, Any-FAIL recommends NO-GO, Any-PARTIAL recommends GO-WITH-CONDITIONS. Mechanism: 8 dims structural-auto (concrete evidence command); 5 dims judgment-recommend (LLM-graded on cited artifact). Invocation: HUB-NATIVE at Stage 9 Phase A6 — no new skill, no new pmo-qa-auditor Mode. Output: DUAL-SURFACE — markdown table comment on the Stage 9 Plan Review sub-task AND one `gate-outcome` row with subtype `plan-review-readiness-scan` appended to `<OPERATOR_INSTANCE_EVALS_RESULTS_PATH>/pipeline-event-log.md`. **Cutover discipline:** Applies to all releases going forward.
**Mid-Pipeline Divergence Re-Check (G-PR8 — Phase A6.5).** Per [`pipeline/stage-09-plan-review.md § Phase A6.5`](../references/pipeline/stage-09-plan-review.md), the hub runs `git fetch origin main && git log <release-branch-base>..origin/main --oneline -- <release-plan-File-Change-Matrix-files>` against the release branch's pinned base at Stage 9 Plan Review pre-GO. Three verdicts: (a) **CLEAN** — zero commits, GO is unconditional on main divergence; (b) **DIVERGED-RELEASE-FILES-UNTOUCHED** — commits exist on `main` post-baseline but none touch release-plan files, GO proceeds with informational note; (c) **DIVERGED-RELEASE-FILES-TOUCHED** — commits touch release-plan files → HALT pre-GO via Tier 2 [SCOPE CHANGE] per § Inter-Stage Feedback Protocol; operator decides resolution (rebase release branch on main + re-validate / Tier 3 [PLAN REJECTION] requiring re-baseline / accept-with-deviation-log). Composes with Stage 12 Phase A.5 (preserved as post-GO ultima-ratio detector for between-GO-and-merge windows). Informational mirrors at Stage 7 entry + Stage 8 entry per [`hub-spoke-bridge.md` Procedure 3 §Stage 7/8/9 Entry Divergence Re-Check Discipline](../references/how-to/hub-spoke-bridge.md): warn-only (Tier 1 [ADJUST]), comment-on-sub-task, no HALT. **Cutover discipline:** Applies to releases entering Stage 9 strictly AFTER the v1.01-intake merge SHA recorded in [`<OPERATOR_INSTANCE_RELEASE_LOG_PATH>`](<OPERATOR_INSTANCE_RELEASE_LOG_PATH>); **v1.01-intake itself is exempt** (reflexive-pipeline-loop discipline — the rule shipping in v1.01-intake cannot fire on v1.01-intake's own Stage 9).
**GO baseline-currency check (G-PR9 — Phase A7.5).** Per Gate 9 row G-PR9 in the gate-criteria spec, the Stage 9 GO records the **baseline SHA** it is rendered against (persisted in the release plan's `## Cross-PR Overlap Audit` → `### Baseline SHA` H3), and the hub evaluates the sibling-merge revalidation predicate `git log <recorded-baseline-SHA>..origin/main --name-status --find-renames`, intersecting the touched / renamed / deleted path-set against this release's structural-blast-radius surface `SURFACE(R)` (the F1 / F2 / F3 / F5 + in-tree-F6 union per the Stage 3 Bundle spec § A9.6.1 axis; F4 excluded as the release's own A3.2 rewrite obligation). Three verdicts: (a) **CURRENT** — no commit since the recorded baseline intersects `SURFACE(R)`, GO is current; (b) **STALE-REVALIDATE** — a sibling release merged since the baseline; the GO requires explicit revalidation (re-run the Stage 4 A4 structural sub-audit + the Phase A6.5 check against new `main`) before it is valid for Stage 12; (c) **STALE-VOID** — revalidation surfaces a `SURFACE(R)` intersection → NO-GO, re-baseline. G-PR9 makes the GO falsifiable (a GO is implicitly "this diff is correct against baseline SHA X" — recording X is what lets a sibling merge invalidate it) and composes with G-PR8 as a second axis/window: G-PR8 is syntactic (did a commit touch a File-Change-Matrix file in the Stage-4-pin→GO window?); G-PR9 records the GO's own baseline and catches a sibling whose mover-set invalidates a path this release's edit-set references but which is not itself in the File Change Matrix. The predicate is `--name-status --find-renames`, NOT `--merges`, so it is merge-style-agnostic (squash / fast-forward sibling landings are caught). **Cutover discipline:** Applies to releases entering Stage 9 strictly AFTER this criterion's introducing-release merge SHA recorded in the release log; the introducing release itself is exempt (reflexive-pipeline-loop discipline — it cannot fire its own new gate; its Stage 9 runs under the pre-existing G-PR1..G-PR8 checks).

**Semantic GO-invalidation check (Phase A.5, runs BEFORE the blind merge below).** The blind `git merge origin/main` described next only escalates on a *textual* merge conflict — it silently passes a clean merge that nonetheless voids the GO's correctness premise (a sibling that *renamed* a path this release merely *references* in prose produces no textual conflict, yet the reference is now dangling and the GO "this diff is correct against `main`" is void). Before the blind merge, the spoke reads the GO's recorded baseline SHA (the G-PR9 `### Baseline SHA` value) and runs the **same unified predicate as G-PR9** — `git log <recorded-baseline-SHA>..origin/main --name-status --find-renames` — collecting the touched / renamed / deleted path-set and classifying: (a) **GO-CURRENT** — zero commits since the recorded baseline → proceed to the blind merge; (b) **DIVERGED-SEMANTICALLY-CLEAN** — commits exist but none of their paths intersect this release's structural surface `SURFACE(R)` (the F1 / F2 / F3 / F5 + in-tree-F6 union per the Stage 3 Bundle spec § A9.6.1 axis; F4 excluded) and none rename / relocate / delete a path this release's edit-set references → proceed to the blind merge with an informational note (the GO premise survives); (c) **GO-VOID-SEMANTIC** — a commit since the GO baseline renamed / relocated / deleted a path in `SURFACE(R)` or referenced by this release's edit-set, **even if `git merge` would report no textual conflict** → HALT pre-merge via Tier 2 [SCOPE CHANGE] per § Inter-Stage Feedback Protocol; the GO is semantically void and a clean merge would silently ship against an invalidated premise. Operator decides: rebase + fresh Stage 9 GO / re-baseline / accept-with-deviation-log. This check is distinct from the blind merge (which catches textual conflict) and uses the same predicate as Stage 9 G-PR9 so the two defense-in-depth surfaces agree (merge-style-agnostic — squash / fast-forward sibling landings are caught, which a `--merges`-only filter would miss). **Cutover discipline:** Applies to releases entering Stage 12 strictly AFTER this check's introducing-release merge SHA recorded in the release log; the introducing release itself is exempt (reflexive-pipeline-loop discipline — its own Stage 12 runs under the pre-existing blind-merge pre-check).

Two stages, two windows, defense-in-depth. **Cutover discipline:** Applies to all releases going forward.

**Deferred item disposition.** Before Phase B chore PR creation, the Stage 13 spoke executes the enumerated Phase A2 procedure per [`release/references/standards/deferred-item-tracking.md`](../references/standards/deferred-item-tracking.md): (A2.1) enumerate bundled-but-not-closed issues via `gh issue list --milestone "v<X.Y>-<slug>" --state open`; (A2.2) for each issue `#N` — apply the `status: deferred` label (per [`core/specs/label-taxonomy.md`](../../core/specs/label-taxonomy.md) line 36 — ZERO new labels), remove the milestone assignment, post the canonical 3-line comment trail (template per [`release/references/standards/deferred-item-tracking.md`](../references/standards/deferred-item-tracking.md) § 4), verify the Projects Status field stays Proposed per the Stage 2 defer state-transition row at [`release/references/specs/ticket-information-architecture.md`](../references/specs/ticket-information-architecture.md) line 622; (A2.3) include the disposition summary in two surfaces — FULL enumeration in the Stage 13 sub-task comment, compact `Deferred items: <list>` OR `Deferred items: none (clean close)` in the Stage 13 chore PR body. Deferred issues stay OPEN per the Stage 2 defer protocol at [`release/references/specs/ticket-information-architecture.md`](../references/specs/ticket-information-architecture.md) line 232 — re-triage required before re-bundling. The `automated-closeout.sh` script composes with this protocol: Phase A2 manages deferred-item disposition (milestone removed), then the script's Phase 4 enumerates remaining open issues via `gh issue list --milestone <slug> --state open` as auto-close anomaly candidates. The `status: deferred` label is the state marker for downstream re-triage; the comment trail is for human-audit. **Cutover discipline:** Applies to all releases going forward.
**Automated close-out.** The Stage 13 spoke MAY invoke [`release/tools/automated-closeout.sh`](../tools/automated-closeout.sh) `--pr <N> --version v<X.Y> --milestone <N> --dry-run --markdown` to enumerate the close-out plan (RELEASE_LOG `DEPLOYED → VERIFIED` transition + INDEX/DIGEST append + RELEASE_NOTES scaffold + Stage 13 chore PR + Milestone close + auto-close-anomaly D-1 manual close + orphan-cleanup invocation); on operator approval at the dry-run review gate, re-invoke with `--apply` to execute Phases 5-16 per the script. The script is idempotent per phase — re-running after a partial failure is safe. release-executor Mode D wraps the script with input-collection + dry-run-review + AskUserQuestion approval gate + apply + report sequencing per [`release/skills/release-executor/SKILL.md`](../skills/release-executor/SKILL.md) Mode D. The chore PR body uses safe phrasing throughout (no `close|fix|resolve|#N` keywords per [`core/rules/git-workflow.md`](../../core/rules/git-workflow.md) parser-clean discipline) — the script's pre-submit grep self-check enforces this before `gh pr create`. **Cutover discipline:** Applies to all releases going forward.

## QA Checkpoint Framework

> QA is structural — no checkpoint is optional. Each checkpoint defines specific checks, pass/fail criteria, and self-repair behavior. Check types enable routing by the stage-gate evaluator (per gate-evaluation-spec.md).

### Checkpoint 1: Intake Quality Gate (Stage 1→2)

**Delegated to:** [gate-criteria-spec.md](../../core/schemas/gate-criteria-spec.md) Gate 1 (Triage Readiness, G1-01 through G1-08).

QA role: confirms gate criteria are applied structurally, not optionally. Core checks (schema completeness, evidence quality, AC verifiability) are defined and maintained in gate-criteria-spec.md — not duplicated here.

| Aspect | Definition |
|---|---|
| **Pass** | All Gate 1 criteria pass (structural: auto-check; judgment: agent assessment) |
| **Fail** | Issue returned to Proposed status with specific failing criteria identified |
| **Self-repair** | Agent drafts correction guidance citing specific failing criterion IDs (G1-01..G1-08). Issue re-enters Intake. |
| **Escalation** | Same issue fails Checkpoint 1 twice → flag to operator with failure history |

### Checkpoint 2: Dependency Validation (Stage 5)

**Pipeline position:** During Stage 5 (Solutioning), before engineering authorization.
**Purpose:** Re-validate dependencies after solutioning reveals new information — blast radius may expose dependencies invisible at Bundle time.
**Distinct from:** Gate 3 (fires at Stage 3→4, pre-planning); Collective Review (fires at Stage 5→6, checks design coherence not dependencies).

| ID | Check | Type | Automation |
|---|---|---|---|
| QC2-01 | All declared dependencies still in compatible states | structural | auto |
| QC2-02 | No circular dependency chains introduced by design decisions | structural | auto |
| QC2-03 | Cross-file impact: files in blast radius not claimed by conflicting design specs | judgment | recommend |
| QC2-04 | New implicit dependencies discovered during solutioning are registered | judgment | recommend |

| Aspect | Definition |
|---|---|
| **Pass** | All 4 checks pass. No unregistered conflicts. |
| **Fail** | Block engineering authorization. Return to hub for dependency resolution. |
| **Self-repair** | Agent identifies specific conflicting dependency or unregistered file claim, proposes resolution (resequence, defer, scope split). Hub presents to operator. |
| **Escalation** | Circular dependency or unresolvable file conflict → flag to operator as potential scope change |

**Sequencing:** Fires during individual solutioning spokes (before collective review at Stage 5→6).

### Checkpoint 3: Pre-Merge QA (Stage 8)

**Pipeline position:** Stage 8 (QA Testing), before Plan Review.
**Purpose:** Verify implementation quality with specific structural and content checks.

| ID | Check | Type | Automation |
|---|---|---|---|
| QC3-01 | Regression: existing cross-references in modified files still resolve | structural | auto |
| QC3-02 | Schema validation: modified files conform to defined schemas | structural | auto |
| QC3-03 | Cross-reference integrity: all inter-file references in PR scope resolve to valid targets | structural | auto |
| QC3-04 | Acceptance criteria: each issue's AC verified against implementation evidence | judgment | recommend |

| Aspect | Definition |
|---|---|
| **Pass** | QC3-01 through QC3-03 all pass. QC3-04 assessment posted. Zero critical/major defects. |
| **Fail** | Return to Engineering with specific defect list: failing check ID, file, line range, expected vs. actual. |
| **Self-repair** | Agent runs regression check, identifies failing assertions, proposes targeted fixes. Engineering re-implements and returns to QA. |
| **Escalation** | >3 QA→Engineering round-trips on same issue → flag to operator as potential design deficiency |

### Checkpoint 4: Post-Deploy Verification (Stage 13)

**Pipeline position:** Stage 13 (Close), after deployment execution.
**Purpose:** Confirm deployment produced a working, consistent platform state.

| ID | Check | Type | Automation |
|---|---|---|---|
| QC4-01 | Deploy integrity: deployed files match git source (diff-clean) | structural | auto |
| QC4-02 | Skill invocation: each deployed skill responds without error | structural | auto |
| QC4-03 | Tracker conformance: updated trackers match schema definitions | structural | auto |
| QC4-04 | Regression: existing platform behavior preserved | structural | auto |
| QC4-05 | Release-plan invariant re-verification: re-execute each AV-N assertion declared in the release plan against post-deploy main; per-AV verdict (PASS/FAIL) with affected files | structural (AV-1 grep mechanism) / extensible (future assertion types) | recommend |
| QC4-06 | Goal-attainment verification: Stage 13 spoke reads the Outcome Statement from the Milestone description AND reads post-deploy state evidence (Change Description + QC4-01..04 results + Success Indicator field when present). Produces a 1-paragraph attainment narrative answering "does post-deploy main exhibit the AFTER state?" Verdict: ATTAINED / PARTIALLY-ATTAINED / NOT-ATTAINED. | structural (Outcome-presence grep) + judgment (attainment narrative) | recommend |
| G-CL6-01 | Design artifacts refreshed when applicability fired during this release (cross-reference to [`gate-criteria-spec.md`](../../core/schemas/gate-criteria-spec.md) Gate 13 G-CL6) | structural | auto (warn → enforce) |
| G-CL7-01 | Goal-attainment verification recorded (QC4-06 verdict + 1-paragraph narrative present in release plan Verification Evidence section; cross-reference to [`gate-criteria-spec.md`](../../core/schemas/gate-criteria-spec.md) Gate 13 G-CL7) | structural | auto (warn → enforce) |

| Aspect | Definition |
|---|---|
| **Pass** | All 4 checks pass. Verification evidence written to release plan. |
| **Fail** | Trigger rollback assessment. Flag to operator with: failing check, affected file(s), severity. |
| **Self-repair** | Agent identifies failing component, proposes remediation: re-deploy (transient), hotfix (content error), rollback (systemic). Operator renders decision. |
| **Escalation** | Any QC4 failure → automatic operator notification (post-deploy = production-impacting) |

**QC4-05-specific criteria:**
- **Pass:** All declared AV-N assertions return zero substantive matches (or `pass` per their declared mechanism).
- **Fail:** ≥1 AV-N assertion returns non-empty / non-pass result. **Non-blocking for milestone close** — surface diagnostic for routing.
- **Routing options (operator choice per finding):**
  - (A) Immediate-hotfix Issue, P1/P2 label, bundled into next-immediate release (use when invariant violation is user-visible, security-relevant, or data-loss-adjacent)
  - (B) Carry-forward Issue, P3/P4 label, bundled into next-routine release (use for documentation drift, internal reference inconsistency, or governance-cosmetic violations)
  - (C) Accept-as-residual, document in RELEASE_LOG.md carry-forward register, no Issue (use only when violation is determined to be expected/accepted by operator)
- **Self-repair:** Agent compiles structured finding per FAIL (affected file, invariant violated, detected diff, originating release if detectable via `git log --follow`, severity assessment). Operator renders disposition (A/B/C).
- **Escalation:** ≥3 QC4-05 FAILs across the same domain (e.g., cascade-completion) across consecutive releases → flag systemic issue with the cascade pattern itself, not just per-release cleanup.

**Cutover discipline:** Applies to all releases going forward.

**QC4-06-specific criteria.**
- **Pass:** Verdict ATTAINED. Narrative cites Change Description + Success Indicator (when present) + ≥1 verifiable evidence anchor (`gh issue list`, `grep`, `gh pr view`, `core/deploy/deploy.sh --check`, etc.). Composes with the decision-outcome enum: ATTAINED → SUCCESS.
- **Fail (non-blocking for close):** Verdict PARTIALLY-ATTAINED or NOT-ATTAINED. Surface diagnostic for operator routing. PARTIALLY-ATTAINED composes with the decision-outcome enum → PARTIAL. NOT-ATTAINED composes with the decision-outcome enum → SUCCESS-document-divergence OR ROLLBACK per operator decision.
- **Composition:** QC4-06 runs AFTER QC4-05 (invariant re-verification) and AFTER decision-outcome capture. The Stage 13 chore PR's `**Outcome:**` field on the visible-H4 `#### Deployment Log v<X.Y>` block reads QC4-06 verdict as input — ATTAINED → SUCCESS / PARTIALLY-ATTAINED → PARTIAL / NOT-ATTAINED → SUCCESS-document-divergence OR ROLLBACK per operator.
- **Routing options (operator choice per finding):**
  - (A) Immediate-hotfix Issue, P1/P2 label, bundled into next-immediate release (use when goal-divergence is user-visible, security-relevant, or roadmap-blocking)
  - (B) Carry-forward Issue, P3/P4 label, bundled into next-routine release (use for partial-attainment with non-urgent gap)
  - (C) Accept-as-residual, document in RELEASE_LOG.md carry-forward register, no Issue (use only when divergence is determined to be expected/accepted by operator)
- **Self-repair:** Agent compiles structured finding per FAIL (Outcome AFTER excerpt, observed post-deploy state, gap analysis, severity assessment). Operator renders disposition (A/B/C).
- **Escalation:** ≥2 consecutive NOT-ATTAINED across the same theme → flag systemic goal-setting issue (Outcome Statements drafted too ambitiously OR scope-vs-Outcome mismatch at Stage 3).

**Cutover discipline:** Applies to all releases going forward.

## Methodology Variation — Release Cadence

The 13-stage pipeline Process is the platform's invariant release path — every release flows through Intake → … → Close regardless of methodology. What VARIES per archetype is the **release cadence** (how often releases cut), **go-live framing** (batch vs. continuous), and **rollback posture** (hot vs. gated). The table below is the authoritative per-archetype cadence reference, consumed by `release-planner` and `release-executor`.

| Archetype | Variation | Applies to | Notes |
|---|---|---|---|
| **Scrum** | Releases cut at **end-of-sprint** (typically every 2 weeks). Stage 12 Execute aligns with Sprint Review; Stage 13 Close aligns with Sprint Retrospective. Go-live framing: sprint-increment release. Rollback posture: hot (next sprint can contain fix-release). | §Stage 3 Bundle, §Stage 12 Execute, §Stage 13 Close | [SOURCE] Scrum Guide 2020 — potentially-shippable increment per sprint. |
| **Kanban** | Releases cut **continuously** (per completed work item or per cadence-based batch — typically weekly). Stage 12 Execute runs continuously as WIP-limited work completes; no Sprint-boundary batching. Go-live framing: pull-based release. Rollback posture: hot (continuous deploy supports hotfix). | §Stage 3, §Stage 12 | [SOURCE] Kanban Method — service delivery with pull-based release. |
| **XP** | Inherits Scrum cadence (end-of-iteration releases, typically 1-2 weeks) with **CI-driven hotfix** capability — failing CI prevents release; passing CI authorizes release. Rollback posture: hot + automated (CI re-run authorizes rollback). | §Stage 12, §Stage 13 | [SOURCE] XP continuous-integration governance. |
| **Waterfall** | Releases cut at **milestone / phase-gate**. Stage 9 Plan Review IS the phase-gate sign-off; Stage 12 Execute runs once per major milestone (may span weeks/months between releases). Go-live framing: big-bang deployment. Rollback posture: gated — rollback requires change-control-board authorization. | §Stage 9, §Stage 12, §Stage 13 | [SOURCE] PMBOK predictive-lifecycle + formal change control. |
| **PRINCE2** | Releases cut at **stage-boundary / end-stage-assessment**. Stage 9 Plan Review maps to end-stage review by Project Board; Project Board's continue/cease/re-plan decision authorizes next release. Go-live framing: stage-controlled. Rollback posture: gated — exception-plan review required. | §Stage 9, §Stage 12 | [SOURCE] PRINCE2 2017 management stage boundaries. |
| **SAFe** | Releases cut at **PI-boundary** (typically 8-12 weeks) for major releases; intra-PI micro-releases may run per-sprint per team. Stage 12 Execute aligns with System Demo + Inspect & Adapt workshop. Go-live framing: PI-increment release. Rollback posture: hot at sprint level, gated at PI level. | §Stage 3 Bundle, §Stage 9, §Stage 12 | [SOURCE] SAFe 6.0 — PI cadence + System Demo. |
| **Hybrid** | Release cadence partitions by phase: predictive-phase releases at milestone (Waterfall-style); iterative-phase releases at end-of-sprint or continuous (Scrum/Kanban-style). Stage 12 Execute cadence depends on current phase. Rollback posture: gated in predictive phase, hot in iterative phase. | §Stage 12 specifically | [INFERRED] Composition of Waterfall + Scrum/Kanban cadences. |
| **Custom** | See the `custom_methodology_definition` block in PROJECT.md; derive release cadence from declared `lifecycle`, `ceremonies`, `artifacts`, `cadence` fields. Cadence is free-form (e.g., "every Friday"); lifecycle drives release framing: continuous → pull-based release; phased → milestone-gated; timeboxed → iteration-bound. `release-planner` MUST consult the block before defaulting to any archetype cadence. | All stages | [SOURCE] [`methodology-parameterization-v1.md § Custom Extension Protocol`](../references/specs/methodology-parameterization-v1.md). |

**Consumer guidance.** `release-planner` reads `delivery_approach` at invocation and parameterizes its bundle-cadence + milestone-creation logic per the row above. `release-executor` reads `delivery_approach` at Stage 12 and parameterizes its deploy-sequence + rollback-authorization logic per the same row. When `delivery_approach: Hybrid`, both skills MUST identify the active phase before applying row semantics.

### Release-Class Variation

The methodology variation table above parameterizes by `delivery_approach` (Scrum / Kanban / Waterfall / SAFe / ...). A second variation axis parameterizes by Release Class — the per-release classification declared at Stage 3 Phase B3 per [`release/references/specs/release-class-taxonomy.md`](../references/specs/release-class-taxonomy.md). The two axes are orthogonal.

| Release Class | Engagement density | Stage 9 review depth | Stage 5 activation bias | Stage 13 outcome-window |
|---|---|---|---|---|
| `routine` | Light | Standard | SKIP-where-trivial | 30-day |
| `novel` | Standard | Deep | ALL | 30-day |
| `cross-cutting` | Tight | Deep | ALL | 30-day |
| `hotfix` | Light | Light | SKIP-where-trivial | 7-day OR immediate |

**Consumer guidance.** `release-planner` consults Release Class at Stage 3 Phase B3 to inform the per-class differentiation posture declared in the milestone description. The hub consults Release Class at every Procedure 0/1/5 touchpoint per [`release/references/how-to/hub-spoke-bridge.md`](../references/how-to/hub-spoke-bridge.md). Release Class is orthogonal to Autonomy Tier (per-action) — see [`core/specs/engagement-charter.md`](../../core/specs/engagement-charter.md) Section 1 Release-level dispatch axis sub-section.

**Cutover discipline:** Applies to all releases going forward.
