## Summary

Two non-trivial, functionally-testable enabler tasks that both extend the platform's automated quality-gate surface. The first adds a template↔schema **contract-fidelity** check (Check 34) to `deploy.sh --check`; the second adds an **L5 cascade-completeness** gate (G8) to `pmo-qa-auditor`. They share a *conceptual* surface (governance-as-code gating) but touch **disjoint files** with **disjoint mechanisms** (a `deploy.sh` shell check vs. a `pmo-qa-auditor` SKILL.md grep gate) and have **different edit constraints** (the cascade-gate edit must route through the `pmo-skill-editor` Gate 2 hook; the Check 34 edit does not). **Decision: keep separate**, sequence Check-34-work first, then the cascade-gate work. Both get Stages 5–13. Proposed Release Class: **`novel`**.

Release Class is `novel`: the Stage 4 plan rendered three D-class decisions (Release Class, Branch Topology, Version) and Stage 5 carried ADR-class design choices in both issues. The release is below `cross-cutting` (it touches zero `pipeline/stage-*.md` files and none of the named governance surfaces — it edits `deploy.sh`, a skill, and standards/specs/templates) and fails `routine` (D-class decisions present). Posture: Standard engagement, Deep Stage 9 review, Stage 5 activation bias ALL, 30-day outcome-window.

## Dependency Graph

There is **no hard dependency** in either direction — neither issue's acceptance criteria require the other's output to exist. The Check-34 work's body cited a sibling/sequencing coupling to a prior `deploy.sh --check` harness item; those references are pre-renumber rot (confirmed non-resolving) and are NOT load-bearing — the Description and ACs are self-contained. The cascade-gate work's body claimed a hard dependency on a prior cutover (L1–L4 cascade-completeness surfaces operational); that dependency is **already satisfied** in current `main` (the cascade-omission failure-mode entry + Stage 5 anchor exist in the current corpus).

The only real coupling is a **soft, coordination-level** edge: both extend the automated-gate surface, so they are reviewed together for consistency (naming, shakedown posture, warn→enforce graduation) — a Collective Review concern, not a build-order constraint.

## Implementation Sequence

**Sequence: Check-34 work first, then the cascade-gate work**, write-serialized under D-C SINGLE. Rationale (localized, not a generic smaller-first heuristic):

1. **Mechanism-risk ordering.** The Check-34 work is a pure shell check added to `deploy.sh` (no skill-edit hook in the path); the cascade-gate work requires routing a `pmo-qa-auditor/SKILL.md` edit through the **Gate 2 `block-skill-direct-edit` hook**. Doing the unconstrained-tooling change first de-risks the release: if the Gate-2 routing hits friction, the Check-34 work has already landed clean.
2. **Shared-shakedown precedent.** The Check-34 work establishes the new-check **warn-mode shakedown** pattern in this release; the cascade-gate work's deploy-time integration (if any) can mirror that posture, keeping the two new gates consistent.
3. **No reverse constraint exists** — nothing in the Check-34 ACs needs the cascade gate, so there is no pull to invert the order.

Under D-C SINGLE, Stage 6 Engineering is write-serialized regardless — the hub routes one Engineering chip at a time. At Stage 13, **mark the Check-34 issue as closed, then the cascade-gate issue as closed** (safe phrasing — this plan is transcribed into PR bodies where GitHub's auto-close parser fires on close-family verbs + a number).

## Change Description

> Authored at Engineering per the Change Description Protocol. Refreshed as items land on the branch.

**Outcome.** The platform's automated quality-gate surface gains two detection capabilities: (1) a template↔schema **contract-fidelity** check (Check 34) that asserts each schema-bearing canonical template carries every section its governing schema mandates — closing the gap where a canonical template could silently drift from the schema that governs its instances; and (2) an L5 **cascade-completeness** gate (G8) in `pmo-qa-auditor` that greps changed files for un-swept OLD-value cascade occurrences.

**Items resolved.** Two (see References). This first chip lands Check 34 + the Open Meetings template reconciliation; the cascade gate lands later in this PR via a subsequent Engineering chip.

**Key decisions.** Version identifier is v1.21 (provisional, reconciled at the Stage 12/13 chore PRs per the v1.18–v1.20 precedent). Release Class is `novel`. Check 34 is the canonical check number (the historical "Check 14" target collided with the live Doc-link-maintenance check; the Stage-4 "Check 24" recommendation was superseded by the hub's Check 34 assignment — 24 is retired-reserved). The schema-mapping mechanism is an explicit `TEMPLATE_SCHEMA_MAP` manifest in `deploy.sh` (mirrors the proven `TEMPLATE_SYNC_MAP` pattern; the in-template-frontmatter alternative is governance-barred by `template-storage.md` §3.4). The schema-bearing scope rule is opt-in by manifest presence (a template the manifest does not name is never inspected → structural skip, zero false positives — satisfying the no-false-positive acceptance criterion).

**Reversibility.** CHEAP — both new gates ship warn-mode-first; per-commit `git revert`.

**Downstream impact.** Check 34 reuses the existing `flag_warn_or_issue` / `DEPLOY_CHECK_MODE` / `deploy-check.mode` warn-mode machinery; no new helper, flag, or mode file. The reconciled Open Meetings template changes what newly-scaffolded projects start with (verified safe against `project-initiator` Step 4). No runtime data plumbing changes.
