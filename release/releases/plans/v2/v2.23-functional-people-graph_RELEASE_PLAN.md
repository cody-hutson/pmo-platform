# Release Plan — v2.23 functional-people-graph

> Single-branch release. Committed as Engineering Commit 0 on `release/v2.23-functional-people-graph`. This file is the durable engineering reference; per-issue stage detail and the accepted Stage 5 designs live as comments on the work items named in the Reference block at the end.

## Release identity

- **Version:** v2.23 — minor bump. Mainline anchor is v2.22 after a concurrent comms-and-facilitation release shipped mid-pipeline; the provisional v2.22 this release planned against was re-rendered to the next-free v2.23 at the Commit-0 freeness re-verify (version identity only — no scope or design change).
- **Release Class:** novel — Standard engagement density, Deep Stage 9 review, Stage 5 activation bias ALL, 30-day outcome window. A new roster schema and a new graph-layer spec are introduced; the plan renders five decision-class gates; one founding ADR is mandatory. Cross-cutting does not fire (no pipeline stage-spec files touched; one named governance surface, not three).
- **Branch topology:** single-branch. Every per-issue Engineering commit lands sequentially on this branch; the release merges to main once at Execute.
- **Capability outcome:** PMO agents resolve people from one maintained, never-committed functional people-graph — a closed-allow-list roster composed with the frozen Person and Resource entities, the four leadership-owner fields carried as typed Person references with an external fallback, and four skills reading names, owners, and coverage from the graph. The filled roster stays out-of-repo and commit-protected; only a de-identified template ships.

## Implementation sequence (dependency-ordered; serial under single-branch)

1. **Spike (research, no code).** Findings F1 entity-mechanism, F2 owner-reconciliation, F3 data-handling — accepted; they gate the design-bearing cards. Already complete; closes at release close.
2. **Data surface.** The operator-instance roster schema, the de-identified template, Person and Resource operationalized by reference, the PII-needle extractor, and the gitignore stray-copy backstop. The substrate every other card reads. First Engineering.
3. **Graph layer (leg C).** A read-time composed capability/coverage view over the data surface; ambient maintenance with a Tier-1 clarification queue. After the data surface.
4. **Owner reconciliation.** The four leadership-owner fields lifted from free text to typed Person references with an external fallback; the mandatory founding ADR. The release's only frozen-schema change — expensive once consumed. After the data surface (shares the entity-model file in a non-overlapping section).
5. **Consumption (leg D).** Four skills wired to read the graph; the deferred template-sync registrations. After the graph layer and the data surface.
6. **Governance and docs.** Register the graph, its maintenance, and its consumption in the operations governance file; confirm the template ships; run the self-containment audit. Last.

## Delivery strategy

Single-branch. Serial per-issue Engineering in the sequence above; one release pull request to main at Execute. Each per-issue commit carries its accepted design and binding amendments (recorded as comments on the cards in the Reference block). The owner-reconciliation card sequences after the data surface on the shared entity-model file.

## Verification plan

Per-card acceptance criteria map to verification methods: file-content / system-state grep assertions for the schema, template, governance-registration, and consumption-reference criteria; a seeded-name pre-commit-block test (with the hook installed in enforce mode) for the never-committed criterion; consumer read-path regression reads for the owner-reconciliation and consumption cards. The self-containment audit greps the corpus for any operator-local absolute path authored by this release (expected zero).

## Rollback strategy

Additive throughout — a git revert restores prior state pre-consumption. The owner-reconciliation typed reference is expensive once a reader binds it, so its invariants are locked before any reader is wired. The never-committed roster's accidental-commit branch is the irreversible one; the enforcement chain (out-of-tree placement, gitignore backstop, needle list) makes that branch unreachable rather than recoverable.

## Quota budget

PASS. The dependency chain forces near-serial execution; the worst parallel batch is two spokes (at Solutioning / Dev-Testing / QA), well under the per-account usage-window envelope. Checkpoint B re-validates at every parallel wave at runtime.

## Stage 5 outcomes (accepted)

All Solutioning is complete and accepted, with binding amendments recorded on each card:

- **Spike** — F1 operationalize Person by reference via a declarative config-layer (no frozen touch, no ADR for the entity mechanism); F2 typed Person reference plus external fallback, four new owner rules, expensive-once-consumed, founding ADR mandatory; F3 operator-instance never-committed roster plus a de-identified template. Independent adversarial review corrected the per-field consumer set (the strategic-initiative sponsor field is read by the comms skill). Four amendments folded.
- **Data surface** — accepted with six amendments: the roster is protected by out-of-tree placement (not gitignore, which is the stray-copy backstop); the depersonalization-token marker is inert for the roster placeholders and is dropped; the needle-staleness window is named; the no-inference criterion is honored-contract language, not enforcement; the template-sync registration is deferred to the consumption card; the pre-commit-hook enforce-mode is documented as a precondition, not expanded into this card's scope.
- **Graph layer** — accepted: a read-time composed view (no committed store), Tier-1 clarification queue, and an auto-invoke of the data-surface needle extractor that closes the staleness window.
- **Owner reconciliation** — accepted shape with three corrections: the founding ADR takes the next-free number (re-verified at authoring; the design's draft number collided with an existing ADR); the mutual-exclusion invariant and the field-conditional on-unresolved disposition are confirmed sound; the count cascade re-aims at the prose name-list; the migration handles the ambiguous multi-match case via the clarification queue.
- **Consumption** — accepted: four skills (the comms, tracker, portfolio, and delivery skills) cite one shared view contract read-only; three template-sync entries register the roster and clarification-queue templates against their actual readers; the non-reader skills are deliberately not registration targets.
