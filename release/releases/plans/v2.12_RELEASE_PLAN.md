## Summary (30 seconds)

Two `type:task` protocol cards, both inheriting design from the foundation-laying autonomy phase-out epic: **#164** (pipeline-wide shadow→warn→enforce rollout convention) and **#165** (operator-touchpoint inventory + phase-out plan schema). Their DoR records them as PARALLEL-COMPATIBLE companions bound by a shared consistency contract (#164's phase enum must equal #165's `current_phase` field; both touch an audit-trail/telemetry contract).

**Decision: ship together as ONE release, #164 leads at Engineering.** The phase enum is the shared dependency root — it must be authored once in #164, then #165's `current_phase` field references it. Splitting would force the enum to be invented twice or create a cross-release contract that can drift.

Verification flagged one structural fact that reshapes the plan: this release's deliverables split across two surfaces. #164's deliverables are entirely **tracked corpus** (PR-reviewable). #165's deliverables are **mostly operator-local** (git-ignored) — only the schema/framework + a minimal `deploy.sh --check` Check 11 stub are tracked; the populated inventory instance, the populated phase-out-plan instance, and the 3 pilot rows live operator-local and will NOT appear in the release PR. The Stage Applicability Matrix and Risk Register below classify every AC along that PR-reviewable / spoke-evidenced-only line.

Rationale for #164-leads: the single hard edge (E1) points #164 → #165. Within a single release branch the two are authored in close succession; the sequence is an authoring order, not a merge-gate sequence.
