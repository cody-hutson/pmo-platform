## Stage 4 Release Planning — delivery-capacity-and-lifecycle-gating

### Summary (30 seconds)

Four greenfield reference docs for the `delivery-engine` skill: gate-definitions.md (#275), lifecycle-stages.md (#274), estimation-standards.md (#273), capacity-model.md (#272). All `type:task` / `documentation` / `epic:knowledge-corpus`, all `status: bundled`. Single-source the focus-factor table in estimation-standards.md (#273); #272 and sprint-defaults.md reference it.

No merge/split of the four issues recommended — keep the 1-doc-per-issue granularity. Co-author #273 before #272 (shared table). All four carry functional impact (their ACs are agent-behavior gates), so Stages 7–8 apply to every issue.

### Recommendations

#### Merge / Split

**No merge or split of the four issues.** Keep the 1-doc-per-issue granularity. Evidence-based rationale:
- The two chains ({#275,#274} and {#273,#272}) are **independent** (no cross-chain directional edge) and target **distinct delivery-engine concerns** (gate/lifecycle gating vs. capacity/estimation planning). Merging across chains would couple unrelated content and create a single oversized doc-PR.
- Within each chain, the dependency is a **content-reference** edge (the leaf references a table/model the root defines), NOT a "these are really one document" signal. gate-definitions.md (gate sequence) and lifecycle-stages.md (stage sequence) are legitimately separate reference docs; estimation-standards.md (estimation rules) and capacity-model.md (capacity rules) likewise.
- **Co-authoring recommendation (NOT a merge):** author **#273 immediately before #272** in the same Engineering working session so the focus-factor single-sourcing (R-3b) is resolved in one design pass — #273 establishes the canonical table, #272 wires the reference. This is already the Implementation Sequence order; calling it out so the Stage 6 routing keeps them adjacent rather than interleaving the chain-2 docs with chain-1.
- Each issue's AC is independently verifiable, which is the marker that the granularity is correct (one testable behavior per issue).

**Gate input:** Spoke dependency analysis (two independent chains of doc-only new files) + contention map (no within-set new-file contention; shared-sibling edits on sprint-defaults.md / SKILL.md if wired).

**Localization Check (Mechanism 1, per decision-discipline.md § 2.1):**
- **Platform context that should localize this decision:** (1) The contention map shows the four new files are mutually disjoint, BUT up to two existing siblings (`sprint-defaults.md` R-3b, `SKILL.md` R-4) may be edited by MULTIPLE issues — SKILL.md by all four if wired. hub-spoke-bridge.md Procedure 3 (lines 488–491) states that under D-C SINGLE the blocker boundary is FILE-level (any file touched by an in-flight chip blocks the next), and that "shared section is NOT the relevant boundary" — git serializes at file content. (2) The two chains' independence is real but the SHARED-FILE edits (SKILL.md, focus-factor single-sourcing across #273/#272) couple the chains at the file level even though they are content-independent.
- **Generic heuristic I am defaulting to (if any):** the generic "independent workstreams → parallelize them on separate branches" heuristic (OPTION-A) — two independent dependency chains is the textbook case for parallel branches.
- **What would invalidate the heuristic for this release:** the chains are independent *in content* but NOT *in files* — if SKILL.md is wired (R-4), all four issues edit the same SKILL.md, and #273/#272 both bear on the focus-factor single-source. The doc-only nature also means there is no parallel-build time saving worth the merge overhead (no compile/test wall-clock to overlap; single operator).
- **Reconciliation:** the localized context **overrides** the generic parallelize heuristic. The chains' content-independence does NOT translate to file-independence once SKILL.md/sprint-defaults.md edits enter scope, and the doc-only single-operator context removes the parallelization payoff that justifies OPTION-A's merge overhead. **Recommend D-C SINGLE.** Serialized Engineering on one release branch in the Implementation Sequence order; the shared-file edits (SKILL.md, sprint-defaults.md) land as ordinary sequential commits with zero merge-conflict ceremony.
