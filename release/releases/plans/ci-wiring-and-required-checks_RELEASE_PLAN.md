## Change Description

*Authored at Stage 6 Phase C1 per `release/governance/RELEASE_PROTOCOL.md` § Change Description Protocol. Started by card 1 (#7036's Engineering spoke, sub-task #8239); each later card's Engineering spoke adds its row to § Issues resolved and extends the sub-sections its card changes, and the last Stage-6 run before the Stage-9 gate refreshes the whole section. Operator-facing.*

### Outcome

**Eight CI and pipeline controls are being taken from the instance first seen to the class they name** (§ Release Outcome Statement). **Landed — all eight cards and the release-wide late register commit.** **Card 1: the close-keyword parser-clean discipline covers every input GitHub's auto-close parser reads.** The rule is stated once, in `core/rules/git-workflow.md`, for the PR title, the PR body and every commit message, and it is projected into the hub-spoke bridge, the Stage-12 and Stage-13 specs, the Engineering persona, the operating model and the release hub's playbook. The commit-message input is enforced: a new fixture-backed tool, `core/deploy/tools/check-commit-close-keywords.py`, runs as a step of the already-required `Commit-message depersonalization gate` job on release heads, so a release-branch commit message that pairs a close-family verb with an issue reference turns that required check red before the merge instead of closing the issue at it. The same tool is the pre-push check every Engineering spoke runs.

**Card 2: the install-tests timeout guard is an invariant, not a list.** A committed suite, `core/deploy/tests/test_install_tests_step_timeouts.py`, called from the falsification probe, derives every step that runs a `core/deploy/tests` shell suite from the workflow itself — 37 at this head, where the old guard named five — and requires each to carry a `timeout-minutes` below its job's limit. It holds that population to a committed floor, so a refactor that moves invocations out of its sight fails instead of shrinking the denominator, and it reports covered over total. All 37 steps now carry measured budgets, and each of the four jobs carries a job-level limit as an outer bound for the steps that run no suite. A suite that hangs now fails its own step at a stated bound instead of running to the host's six-hour job limit.

**Card 3: a warn line names only the graduation form its own check sanctions.** The shared warn emitter used to append one instruction to every warn line — flip a runtime mode file — although the checks that record a graduation form record the committed default, which leaves a repository record where a mode file does not; seven of them printed both forms on one line. The emitter now states no graduation form of its own. A check declares its form with a closed one-member token, `committed-default`, and the emitter then renders the committed default naming that check; a check that passes no token, such as the doc-link check, prints none. The seven checks whose own dial governs a findings arm pass the token on their nine findings lines, and three of their header comments now say the same. The emitter-contract suite, already a required CI step, grades it: no per-caller fact in the shared body, every token a member of the set and true for its caller, every owed token present, and every dial read and tested in a shape the suite can follow — so a later check that owes the token cannot ship without it. Only remediation text changes: no check's verdict or exit status moves.

**Card 4: the check that compares declared and live required contexts has a definition of disagreement, fails on a measured one, and measures where it runs.** The reconciler used to report a difference between what workflow headers declare and what branch protection requires, exit 0 on every path, and — reading an endpoint the workflow token cannot read — measure nothing in CI. It now reads the public branch object, which returns the same list to any reader, and sorts the gap into three classes: a context that claims to be required but is not registered, a context held in warn-mode that is registered anyway, and a registered context no header declares. A warn-mode context that is not registered is listed as held and is not a disagreement. A measured disagreement turns its verdict check red; a read that did not return turns nothing red and nothing green — the verdict check is skipped and the measurement check warns. The check stays advisory and is never a required context. The gate-efficacy standard defines that disagreement and the registration track once, and its disposition table records every context on the track. The close-out smoke workflow, whose context branch protection already required, now reports on every pull request and declares it, and the conformance ratchet fails any required context declared on a path-filtered workflow. The pull-request-body close-keyword gate is corrected to the advisory posture it actually delivers and held until two defects are repaired. The operator registers four contexts — the two SAST jobs and the two eval-viewer test jobs — at Stage 12; until then this release's own verdict check is red, with exactly those four.

**Card 5: every tool in the two tool trees that names an interpreter on its first line is executable, and a check keeps it that way.** A file's tracked mode was whatever its authoring path left, so tools kept arriving non-executable — a tool run by its own path then fails with a permission error instead of giving a verdict — and were fixed one at a time. A new check, `core/deploy/tools/check-tool-exec-mode.py`, reads what git tracks rather than what is on disk: every file under `release/tools/` and `core/deploy/tools/` that begins with an interpreter line must be tracked executable, unless a short exemption list names it with a reason. Sixteen tools became executable, the four the card named among them, and five files that are sourced, imported or read as data are listed — one of them must stay non-executable, because the installer copies it beside the hooks and a required suite asserts that copy's mode. The check runs on every pull request as an advisory job that turns red on a finding, and inside `deploy.sh --check`, where it enforces from the day it ships: the operator ratified that as an exception to the rollout convention, because the whole firing population had been read and the remedy for a finding is one command. A tree it cannot read, or a reading it cannot vouch for, is reported as exactly that and never as clean.

**Card 6: a release's Stage 12 deploy records the release, whether or not another deploy got there first.** The deploy that runs after a merge — the post-merge hook, `./update.sh`, or an operator's own — keeps the installed copies current but carries no release identity, so the first deploy after a release merge wrote no `deployment-status` rows, and that read downstream exactly like a release that deployed nothing. The hook stays as it is: it runs on every checkout for every merge, and the rows are permanent. Stage 12's deploy step, which had no command, becomes Phase B4 — run for every release, from the executor's worktree at the tip of `main`: it asserts the release key non-empty and reads it back, derives the release's skills and packages from its own merge and keeps only those the deploy roster lists, and deploys them by name under the key, or declares that there are none. The deploy tool now refuses a stamped deploy that states no target set, an empty key and the two contradictory forms before it writes anything, so a forgotten target list can no longer pass for an empty one. Phase C2 reads the rows back by the recorded slug, so a Stage 12 that skipped the step is visible there. The hook-owner rule, the partial-deploy retry and the cycle-time standard say the same, and a decision record, {{ADR:release-identity-is-stamped-at-stage-12}}, keeps the rejected alternative — teaching the hook to stamp — from being proposed again.

**Card 7: a branch darkened by a sibling's merge is flagged at the merge, not at its next stage.** When one release merges into `main`, another open release pull request can become unmergeable; the host then runs none of that pull request's gates, and a read of the few checks left reports it green. Nothing on the darkened branch signals the change, because that branch did not move, so detection now sits on the events that cause it. A new read-only workflow, `.github/workflows/sibling-merge-dark-branch.yml`, runs on every push to `main` and on manual dispatch: it reads every open pull request on the base, fetches their heads as objects, and lets a new classifier, `release/tools/check-dark-branch.py`, decide which ones this push newly darkened. Its verdict check turns red on one, and is skipped — never passed — when the sweep could not measure, could not attribute a conflict, or could not cross-check the host's answer. The merging release does the same at its own Stage 12 merge, as Phase B1.1, and records the pull requests it darkened in its Stage 12 output without holding its own release. Every spoke that pushes to a release branch reads that pull request's mergeability for the commit it pushed and renders one line, so a head pushed while dark is never reported as passing checks that never ran. Stage 7 records the check roster it read on a settled, mergeable head, as information a later read can name missing rows against — it decides nothing — and Stage 8 renders that comparison beside its own entry read. Stage 7's branch-freshness remedy now merges the base into the release branch instead of rebasing it.

**Card 8: the declaration-obligation rule states the scope its matchers enforce.** The repository-integrity rule said the obligation to write a reason inside an override marker, naming which limb of the marker's criterion applies, held for every kind of override marker. The guide that owns the obligation scopes it to one marker, the issue-reference gate's, and the other gates read their markers differently — some require a reason, some stop matching when one is written inside the comment — so a reader following the old sentence could void an exemption without seeing it. The rule now says the obligation binds the issue-reference marker alone, and it carries the same `Runner: NONE` label as the close-keyword passage: nothing requires the reason, because that gate accepts the declared form and the bare one alike, and a gate-coverage register row, landed in the release-wide late commit, records the gap. For any other marker the rule makes no claim; it sends an author to that gate's failure output, or its matcher where the output prints none, and to a run of the gate. The decision-record index's restatement no longer carries the reason clause to the markers it lists. No gate's verdict changes.

**The late pass.** The release-wide late register commit appends nine gate-coverage register rows — cards 1, 2, 5, 7 and 8 — and lands card 4's four rewrites in place; card 6's row is held for the hub's ruling on its class (DEV-81). The branch is synced with `main` once (DEV-86).
