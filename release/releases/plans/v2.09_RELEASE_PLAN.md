### Rollback Strategy

Platform git-native model (`git revert` granularity).

- **Topology supports per-issue rollback.** Under D-C SINGLE, Engineering commits **one commit per issue** (11 commits on `release/v2.09-deploy-sh-script-health`). Post-merge, any single issue's change reverts via `git revert <that-issue's-commit-SHA>` without disturbing the other ten — the one-commit-per-issue discipline preserves granularity even though all eleven ship in one PR.
- **Whole-release rollback:** `git revert -m 1 <merge-SHA>` reverts the entire release if a systemic regression surfaces.
- **All changes are cleanly revertible.** Every change is additive or a surgical correction to existing logic:
  - #1104 (one-line path), #86 (residual sweep), #659 (allowlist lines), #984 (loop hardening), #1089 (matcher extension) — pure code, trivially revertible.
  - #661 (new sub-check, warn-mode-initial), #1036 (new registry section + check dispositions), #758/#760 (path-resolution) — additive; revert removes the addition with no data migration.
- **No issue is non-cleanly-revertible.** Specifically called out:
  - **#1104** ENABLES a previously-skipped Check 9 pair. Reverting re-introduces the silent SKIP (the pre-fix state) — safe, not a data-loss revert.
  - **#758 token codification** (depersonalization-spec §4 + template field) — reverting removes the token registration; the writer already falls back to the canonical default (per the issue: "hygiene, not a break"), so revert is safe.
