## Change Description

*Scaffolded at Engineering Commit 0; authored in full at Stage 6 Phase C1 per [`RELEASE_PROTOCOL.md`](/release/governance/RELEASE_PROTOCOL.md) § Change Description Protocol, before the draft PR transitions to ready-for-review at the Stage 9 gate. Operator-facing voice.*

### Outcome

A methodology pack can already declare kinds, fields and criteria — but nothing said which of those a methodology owns and which the platform fixes, so an author had no way to tell an over-reach from an under-delivery until a second methodology was written against the boundary. This release writes the boundary down, makes every authored criterion carry the named body of practice it came from, resolves all twelve empty criteria arrays in the shipped Scrum and Kanban packs — **eight** filled with content sourced from the Scrum Guide, INVEST, Cohn and the Kanban Method, and **four** transition gates stated as reasoned empty sets because neither methodology prescribes a per-item gate — and states what a pack resolves to when no kit is selected.

- **D-CriteriaVersion-BlockRule: a `criteria_version` bump tracks any change to the block, provenance included.** It is why every `[kinds.criteria.gate]` in this release moves `0.1.0 → 0.2.0` while its `checks` array stays empty — the block changed, the bar did not. The consequence worth naming: **no runner observes this.** A non-semver `criteria_version` passes the pack validator clean on the same manifest where a missing required field fails it, so conformance here rests on authoring discipline and on a Stage-8 probe that reads the **value**. A reviewer comparing the gate block for byte-identity would fail a conforming design.
- **D-PackDefault: the resolution-rule reading — a pack's default is the kind set it declares, and no pack-header field names a kit.** Ratified at the scope-lock and not re-opened. **One of its four grounds was falsified before the record shipped, and the record says so rather than shipping the original.** The ground claimed a `default_kit` field would *make* a plan-driven pack's default displaceable; it already is. The eligibility predicate's second limb tests the examined pack's own neutrality and role and never the requested archetype, so it fires under every archetype, and composition rank places a kit above a methodology pack. Executed on two conforming roots differing by exactly one directory: with no kit present a plan-driven resolution returns that pack's own work-package kind, and with one neutral kit added and **nothing selected** the identical invocation returns that same kind owned by the **kit**. The corrected ground is the difference between a reachable state and a blessed mechanism — the same conclusion, on a premise that holds. **The consequence worth naming:** this card's acceptance evidence excludes the only configuration in which the rule can fail, no fixture can currently do better because *"resolved to no kit"* is inexpressible in the tool's arity, and that boundary is declared in the record, in the corpus and in the Stage-8 grading note rather than left to be discovered.
- **D-AnnotationName: RETAIN `x-pmo-content-source` + ship a disambiguation table** *(deferred by the operator at Collective Review to Stage 6, rendered there against the real diff)*. Both candidates measured at zero corpus citations, so the call was genuinely open in either direction. **The design's stated ground for retaining did not survive measurement** — *"every sibling names the annotated thing"* is false across the annotation family — so the retention is re-grounded on three things that do hold: the containment criterion that rejected an earlier candidate does not fire on either of these, so it selects nothing; the entry object's practice-bearing member is already named `practice`, which the alternative stem would stutter against; and the corpus's own remedy for a **strictly worse** collision — an identical field name carrying two meanings — is a disambiguation note rather than a rename. **The deferral's timing premise is also corrected:** the window does not close when the two content cards commit, because neither cites the annotation name; it closes at the first materializer implementation, and none exists.
