### Decoupling Rationale (the defect edge)

The `§3 Hybrid` semantic anchor today asserts `"Hybrid" means the SPM-co-managed pattern — the same concept the legacy spm_comanaged: true binary represents`. That single sentence is **both** the SPM-coupling the decouple removes **and** the rigidity (one iterative + one phase-gated) the genericize removes. ### The new Hybrid definition (the literal S0 contract)

The `§3` anchor (the dual-lifecycle paragraph + the `Semantic anchor (resolves R8)` paragraph) is **fully rewritten** to:

> **Hybrid.** A project that runs a **user-configurable combination of two of the 8 archetypes** under a single project governance, declared `delivery_approach: [A, B]` (two distinct archetypes; e.g. `[Scrum, Kanban]`, `[Waterfall, XP]`). Each constituent track runs in its native methodology; the project reports status in **both** constituent framings simultaneously. Ceremonies and artifacts are the **union** of the two constituents. The per-track hierarchy mapping is defined in the work-organization-mapping-framework §2.5.
>
> **Decoupled from co-management.** Hybrid is a **methodology classification only**. The SPM-style dual-framing *output* — Agile + Waterfall framings rendered for a co-managing sponsor — is an **orthogonal operational capability** gated by the separate `dual_framing_enabled` flag (project-schema §7), NOT implied by `delivery_approach: Hybrid`. A Hybrid project may run with `dual_framing_enabled: false` (two native framings, no co-management bridge) or `true` (additionally emits the Dual-Framing Bridge). A non-Hybrid single-archetype project may set `dual_framing_enabled: true` independently.
>
> **Distinguishing constraint.** Two distinct archetypes named in one project; native-framing status output in TWO lifecycles, not one. (Single-track "mostly-Scrum-with-light-gate-review" is Scrum, not Hybrid. A *named variant that fuses* two archetypes into a third methodology is `Custom`, not Hybrid — see the Hybrid-Two-vs-Custom rule, project-schema §6.3.)

**Array syntax is convention-conformant, not invention.** The schema already expresses a fixed-size list of archetype enum values as an inline-flow YAML sequence — `derived_from: [Kanban, Scrum]` (project-schema §6.3) — so `delivery_approach: [Scrum, Kanban]` reuses the established list idiom with zero new notation. Array members are exactly 2 distinct values from `{Scrum, Kanban, XP, Waterfall, PRINCE2, SAFe}`; `Hybrid` and `Custom` are excluded (they are meta-archetypes, not composable constituents). The literal value `Hybrid` is **retained as a single-enum value** for backward-compatibility — existing single-value PROJECT.md still validate, and the array form is the forward-looking explicit declaration.
