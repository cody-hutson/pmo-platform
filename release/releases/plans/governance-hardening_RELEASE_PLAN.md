### Step 9 — the terminal reconciliation, restated to the decided population

The L4 provenance-header schema (`core/standards/template-protocol.md` §4.1) declares a `domain:` field with the enum `project | software | platform-internal` — this is **concept 5** in the registry (template-provenance). #3290's D3 retro-fits that header onto templates that lack it, so D3 changes the population #3825's registry maps.

**Restated at scope-lock (supersedes the Stage-4 and Stage-5 figures).** #3290's own Stage-5 decision **D-3290-5** chose option (r) — *"19 now + 7 recorded-blocked, routed."* D3 therefore adds **19** declarations, not 26: seven target files are hard-blocked by a silent PyYAML duplicate-key collision (PyYAML resolves a duplicate key last-wins with no error, so a naive insert would quietly delete an existing `domain: managed` line from templates that ship inside a skill package). Consequently:

- **Post-D3 population is 63 declarations across 58 files** — not the 70/58 recorded at Stage 5, and not the "~70 across ~65 files" estimated at Stage 4. `44 + 19 = 63`. The **58** file count is unchanged, because the 19 land on files already inside the 39.
- **The seven blocked files are mapped by concept pattern, not enumerated.** They keep exactly one declaration each (a body-level `domain: managed`, concept 2), which concept 2's `Declaration pattern` already matches. The registry records **no per-file list** for them; enumerating seven file paths in a registry designed to avoid frozen enumerations would reintroduce the drift target the design exists to remove.
- **Step 9 is a verification, not a re-authoring.** All 19 of D3's declarations are concept-5 instances already matched by concept 5's `Declaration pattern`. The only conditions that force a row edit are a **new concept** or a **new owning file**, and D3 introduces neither. Expect **zero row edits**; record the coverage verdict. If a row edit *is* required, surface it rather than silently amending — it means D3 introduced something the design did not anticipate.

- **Registry keying — concept × owning file, not per-declaration.** Forced rather than preferred: two of the six concepts have zero `domain:` declarations (one is a tag path segment, one is adjectival prose), so a declaration-keyed registry cannot represent them at all. - **`project-schema.md` receives a cross-link only.** The Stage-5 spec directed backfilling three concept rows there; that would have produced a second complete corpus-wide index maintained in parallel with the registry — the duplicate-source defect this card exists to close. Superseded by the re-repaired acceptance criterion and the adversarial review's coupled disposition.
- **The registry's completeness claim is scoped to declared-field senses.** Three further live prose senses of the bare word exist, including a PMBOK Performance-Domain axis sitting two lines from a paragraph this change edits. They are recorded as explicitly excluded adjacent senses rather than shipped under an unqualified "every concept the token names."
- **Drift check specified, not built.** A convention-linter coverage dimension is the right durable answer, but building it would add an executable surface to a doc card whose Stage-7 skip rests on having none. The registry carries its update trigger and reconciliation command inline as the interim.
- **The generated-artifact purge is declined on measured feasibility, never on "we never delete."** The doctrinal argument does not survive checking — the platform does purge, in one wired place. What eliminates the build is that its scope predicate cannot be evaluated (the archival-timestamp field is stamped on no live artifact), its retention constant cannot be grounded (the corpus carries no post-archive destruction clock), and the reclaim is under one percent of the workspace. The decision record states the correction rather than the over-claim, because an ADR cannot be edited later.
- **Every re-open trigger names an evaluator and a cadence.** A reversal condition nobody evaluates is not a reversal condition, and the record's MODERATE reversibility grade rests on the triggers being real. Two of the four fire on external events and two are checkable from the tracked corpus; the two that need a human to look name the owner, the cadence, and the observable that says the cadence lapsed. The grade is written as contingent on that evaluation rather than asserted unconditionally.
- **`core/governance/RECORDS_POLICY.md` gets zero edits from #3387, deliberately.** Its disposition rules already state destruction=none and already route file deletion outside their own scope, so a pointer sentence would restate a stance the file holds. The consequence is that risk **R-6** — the potential hard write-collision with #3715 on the same disposition table — **retires**, and #3715 is the sole in-release writer of that file.
- **An external target's facts get no storage home at all — the fix is the removal of a storable value.** The card asked *where* a target repository's conventions should live. On inspection the conventions tier does not exist: every example decomposes into an operator practice (holdable) and a target-side referent (observable), and the defect was one entry welding the two. Storing the conventions somewhere better — a new registry, or a field on the existing destination subtable — relocates the cache without fixing the drift, which is why the answer most readers reach for is the one that dies on the defect it fails to fix.
- **The read contract is stated at capability altitude, and the adapter operation it would prefer to name is recorded as owed.** The design's first draft cited the repo-host adapter standard as the read path. That standard is a *version-claim* interface: it requires exactly four operations, none of which returns a name, a state, or file content, and its own contract closes the set. Naming it would have shipped a binding the standard forbids. The rule now cites the §4.1 canonical host-binding rule instead and says plainly that no read operation exists yet — so a future implementer adds one rather than inferring a binding. **Passing the host-binding detector was treated as necessary, not sufficient:** that check tests only the rule's negative limb, so naming nothing scores identically to naming an operation.
- **The scope is narrowed to the population the evidence sampled.** The decomposition test ran against four examples, all from a target the operator controls. Two adjacent cases — a target the operator does not control, and a referent no practice can resolve uniquely — are named and routed to the operator rather than absorbed by a catch-all. Adding rows for them now would have shipped scope that never faced the adversarial pass the rest of this design did.
- **Reversibility is split by limb rather than graded on the diff.** The corpus rule is CHEAP; any operator-side retirement performed under it is IRREVERSIBLE by git, because it mutates a store the repository cannot reach. The same action class carries the same tier on #3556, so the release now states it consistently on both cards instead of CHEAP on one and IRREVERSIBLE on the other.
- **The gate on the release's only irreversible action was rebuilt at its shape, not its threshold.** As designed, the eviction's corpus-presence gate was an unanchored recursive search over two directories for a lowercase literal, qualified *in prose* as "an authored file, not a test fixture." Run verbatim it returned one hit — the fixture — so it greenlit an unrecoverable action before the codification existed. Three causes stacked: the authored heading is title-cased and the search was case-sensitive; the release plan lives inside the searched tree and quotes the search text, so the probe could match its own specification; and the stated exclusion named a path the plan is not under. Both limbs are now **anchored to the destination file**, which cannot be satisfied by a plan or a fixture and needs no exclusion clause at all. A file-anchored gate was already used elsewhere in the same spec — the loose form was the one guarding the irreversible step.
- **Both gate limbs were computed against the landed change set, not asserted.** The design stated one limb as an exact `1` in one place and `≥ 1` in another; the change set writes that string **twice**, so the strict form was false and, read literally, would have held *both* evictions — the opposite failure direction to the false-pass, in the same predicate. One stated form now, verified against what actually shipped.
- **The section's name and one guardrail's stated reason were re-grounded, because the survey behind them had only been run for the term that was rejected.** *Retention* is defined load-bearingly elsewhere in the corpus as a records **preservation floor** — a minimum period before a record is eligible for disposition — which is not a restraint on a removal recommendation. And *zombie* has **two** live in-corpus senses, one of them for backlog work items, in the very file the guardrails cite as their altitude counterparty. Re-surveying all four terms found every candidate name already occupied, so a rename relocates the collision rather than resolving it; the name is kept and the false groundings are replaced with an explicit two-neighbour disambiguation and a corrected reason. **The rules never depended on the wrong claims — but a false grounding in shipped text outlives the release.**
- **The Stage-13 absorption-reconciliation gate is bound to the right subject for this entry.** That gate diffs memories naming *the closing issue*; these two memories name the **originating** codification issue whose close-out stranded them. Evaluated on its default subject it computes an empty set and passes vacuously — unable to detect the exact condition this card remediates. The manifest names the alternate diff basis explicitly at the point of execution. Generalizing the gate is out of scope and is recorded as a routed observation.

### Reversibility

**CHEAP / Confidence HIGH** for the landed work — one added file plus additive prose clauses in eight existing files; `git revert` of the merge commit restores prior state with no runtime, package, or deploy consequence, and no field was renamed so there is no migration to unwind. **The release as a whole is MODERATE / Confidence HIGH**, and the reason is one carve-out: #3556's memory eviction mutates a store outside the repository, so reverting the merge does not restore it. Do not treat "revert the PR" as full rollback while #3556 is in scope.
