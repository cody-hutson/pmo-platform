## Stage 4 Release Planning — 05-ROLE-sustain-coverage-router

### Summary (30 seconds)

This release builds the **final 5 role-Specialists** (#1120 release-manager, #1121 tier-1-support, #1122 tier-2-support, #1123 ocm-lead, #1124 knowledge-manager) plus the **capstone router** (#181 pmo-skill-router) that closes out the 18-skill role-Specialist suite and declares it **GA**. **D-Registry — the chicken-and-egg resolution (recommend option (a)):**

> Every specialist AC says "register into the `core/` registry"; #181 consumes it; the 14 prior-wave specialists are also not yet registered. Three options were posed:
> - **(a) Establish registry as a foundation step first** (Step 1 above), specialists register as built, #181 consumes + builds router. **← RECOMMENDED.**
> - (b) #181 establishes + backfills all 19 (14 prior + 5 new) at the end.

### Architectural Decision Gates (D-blocks)

#### D-Registry: Where is the `core/` logical skill registry established in the sequence?
**Gate input:** Spoke analysis — the registry does not exist (verified `ls core/skills/`); every specialist AC says "register into it"; #181 consumes it; 14 prior-wave specialists are also unregistered.
**Gate decision:** Choose between —
- **(a) Foundation-first (RECOMMENDED):** establish the registry as Step 1 (its own work item — see Split rec); backfill all 14 prior-wave + 3 core skills; each new specialist registers as built; #181 consumes + verifies.
- **(b) Router-establishes:** #181 creates the registry and backfills all 19 at the end; the 5 new specialists ship with a deferred "register" AC.
- **(c) Other** (e.g., registry created empty in foundation, each wave backfills its own).
**Blocks:** Every specialist's "registered in the `core/` registry" AC; #181's "registry contains ≥17 entries" AC; the Implementation Sequence Step 1.
**Upstream compatibility:** **REQUIRED — touches skill-authoring surface** (defines what a NEW skill must contain: a registry entry). Anthropic `skill-creator` convention: frontmatter is `name:` + `description:` only; the scaffolder emits **no** registry-membership field — a `core/` logical registry is a **PMO-platform extension** with no upstream counterpart, so there is no conflict to resolve (it is additive PMO infrastructure, not a frontmatter change). Compatible-path evidence: `skill-creator` produces `SKILL.md` + `references/`; a separate `core/`-level index file does not alter the scaffolder's output contract — confirmed no conflict (schema reviewed this session; the registry is a sibling index, not a per-skill frontmatter field). **Sourcing posture (ADR-023):** the registry indexes **stakeholder-facing / judgment Role-Specialists** → **own-only**; no Anthropic runtime coupling is introduced by the registry. The registry itself is first-party PMO infrastructure.
**Reversibility / Confidence:** MODERATE / HIGH — once specialists register against the chosen home, relocating the registry is a multi-file cascade; pre-build it is CHEAP.

#### D-SupportPair: Keep #1121 (Tier-1) and #1122 (Tier-2) as two skills, or combine?
