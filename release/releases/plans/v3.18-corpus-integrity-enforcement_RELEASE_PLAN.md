# v3.18-corpus-integrity-enforcement Release Plan

**Release class:** cross-cutting. The File Change Matrix touches multiple governance surfaces (the git-workflow rulebook, the deploy-check harness, the Stage 4/5/6 pipeline shards) plus the agent-harness hook layer and CI — corpus-wide authoring discipline changes, not a localized addition.
**Branch topology:** single release branch with sequential Engineering commits and one release PR (shared-release-PR append model). This plan is committed as the first Engineering commit.
**Composition:** a two-issue capability slice on corpus-integrity enforcement — a reference-**durability** issue (D, establishes the standard plus a three-primitive enforcement spine) and a repository-**integrity** PR-gates issue (I, depersonalization + issue-reference validity + dead-file references).

## Scope — two corpus-integrity issues

1. **Reference-durability standard plus enforcement spine (D).** Ship a reference-durability standard that codifies an ordered durability ladder and a self-containment test, backed by three warn-mode-initial enforcement primitives: an agent-harness PreToolUse hook on Write/Edit to durable-corpus paths, a deploy-check check, and a CI backstop workflow scoped to durable-corpus diffs. The standard, the hook, the deploy-check check, and the CI workflow are the upstream artifacts the integrity issue's issue-reference-validity gate reuses.

2. **Repository-integrity PR gates (I).** Build a three-gate workflow — depersonalization, issue-reference validity, dead-file references — on the same CI surface plus the same override-marker scaffold, consuming the canonical depersonalization spec's token set plus allowlist (do not reinvent) and reusing the durability issue's workflow skeleton plus override grammar.

## Dependency graph

No hard prerequisite exists between the two issues. A real soft sequencing edge does, directional D before I: the integrity issue's issue-reference-validity CI gate is modeled on the durability issue's CI workflow plus the shared override-marker scaffold, so authoring D first means I reuses an established skeleton rather than co-inventing a divergent one. The two are semantically distinct (durability = survives renumber/migration; validity = resolves today) but mechanically coupled at the CI plus override-marker layer.

## Implementation sequence

Confirmed D before I (foundation before consumer).

1. **D — reference-durability standard plus three-primitive enforcement.** Establishes the standard (the authoring discipline), the harness hook, the deploy-check check, and the CI workflow that the integrity issue's gate reuses.
2. **I — repository-integrity PR gates.** Builds the three-gate workflow on the same CI surface plus the same override-marker scaffold, reusing D's skeleton plus the canonical depersonalization token set.

Intra-issue, D decomposes into five Engineering seams: (1) the standard foundation, (2) the harness hook, (3) the deploy-check check, (4) the CI workflow, (5) the pipeline-shard plus link-maintenance citations. Foundation leads; citations trail.

## Engineering serialization (the binding constraint)

Both issues edit the git-workflow rulebook (`core/rules/git-workflow.md`) — a hard, line-level overlap. Even though the edits target different sections, git serializes at file-content level. Under the single-branch topology, Stage 6 is write-serialized: one Engineering chip at a time per the implementation sequence (D before I), and the integrity issue's git-workflow edit must not start until the durability issue's git-workflow commit has landed on this release branch. Both issues also add new files under `.github/workflows/` — a directory overlap with distinct filenames (low merge-conflict risk) but still commit-serialized at push.

## Decisions of record

- **Release class:** cross-cutting (governance-surface breadth is the dominant trigger; the new reference-durability standard also fires the novel trigger, but cross-cutting dominates). Differentiation posture: Deep Stage 9 review depth; Stage 5 activated for both issues; thirty-day Stage 13 outcome window.
- **Branch topology:** single release branch with serialized Engineering, chosen over per-issue-branch parallelism because the git-workflow hard overlap makes parallel branches net-negative for a two-issue release (it would defer the same contention to PR-merge order with added branch-management cost).
- **Stage applicability:** no stage is skipped for either issue. Stage 5 Solutioning is activated for both (each carries a genuine, named mechanism deferral — the durability issue's detection scope; the integrity issue's allowlist scope plus collaborator-name-list storage location). Stages 7 and 8 apply to both (both have functional impact: CI gates, a harness hook, a deploy-check check).
- **Integrity-gate token source:** the integrity issue's depersonalization gate consumes the canonical depersonalization spec as its rule source (tokens plus allowlist), extending it with the collaborator-name list rather than forking a parallel vocabulary — this prevents a two-sources-of-truth defect and reduces the integrity issue's scope.

## Risk register (release-level)

- **Detection-regex false positives (D, major).** The detector could flag legitimate references, producing warn-mode noise that erodes signal and could block authoring on flip-to-enforce. Mitigation: flag only the operator-banned classes (links plus version-cutover apparatus) wholesale plus a positional issue-reference rule; path allowlist plus per-file override markers; warn-mode-initial absorbs tuning; a checked-in corpus fixture with a labeled expected-match set makes precision measurable. Owned at Stage 5.
- **Collaborator-name-list storage (I, major).** The depersonalization gate needs a collaborator-name list; inlining raw names in a visible workflow file re-introduces the exact data the gate prevents. Mitigation: store the list in an Actions secret or a gitignored local file, not inline in the workflow. Owned at Stage 5.
- **Git-workflow Engineering contention (major).** Concurrent Stage 6 work on the shared rulebook would cause non-fast-forward push or stale-base errors. Mitigation: single-branch topology plus implementation-sequence serialization (D before I); the hub surfaces one Engineering chip at a time. Fully mitigated by sequencing.
- **Reflexive-corpus risk (both, major).** This release authors new durable-corpus content that is itself subject to the durability standard it ships. If the release's own files embed fragile references, it violates its own standard at birth. Mitigation: author every release-introduced durable file self-contained — no load-bearing issue-reference/version-cutover/commit-hash/repository-URL references; describe by content and summarize inline. Stage 9 Deep review greps the release diff for link sequences plus reference patterns in introduced governed files.

## Rollback

Both issues are additive plus warn-mode-initial: a new standard, new primitives shipping in warn-mode via the shared harness mode file plus the deploy-check mode file, and new CI workflows that fail only on net-new added-line violations. A plain revert of the release PR restores prior state cleanly — no data migration, no schema change, no destructive edit. Even pre-revert the blast radius is observational, not blocking. Flip-to-enforce is a separate, later, reversible operator action per the shakedown-to-enforce ladder.

## Self-containment note

This plan is authored self-contained per the reference-durability standard it helps ship: it names the two issues and their sister by role and content rather than by number, states its rules unconditionally, and carries no version-cutover apparatus, commit hash, or repository URL as a load-bearing reference. The version label in the title is a narrative release identifier, not a governance rule reference.
