# Two releases can now finish at the same time without tripping over each other

2026-07-24 · v3.84

When two releases were being prepared at once, they would collide over the shared files that record release history — and the slower one had to redo work it had already finished. This release removes the most common collision and clarifies what the pipeline actually checks before a release is allowed to start.

## What changed for everyone using the platform

- **Shared release records now merge automatically instead of conflicting.** The index, digest, and changelog are append-only — each release adds its own line — so two releases adding lines at the same time is no longer a conflict anyone has to resolve by hand. *Why it matters:* a release that took a while to finish used to have to stop, untangle the overlap, and often give up its place in line. That stall is gone.

- **The release history log is deliberately left out of that automation.** It tracks each release's *state* as it moves from deployed to verified, and automatic merging would combine two versions of the same row into a record claiming both states at once. *Why it matters:* a visible conflict that someone resolves is much safer than a silently wrong history. This one still asks for a human.

- **A release can now be identified by name instead of a version number.** The readiness check that runs before a release begins used to assume every release has a version. It now confirms the release's identity is coherent — a version *or* a capability name — and leaves the version number itself to be assigned at the moment the release actually ships. *Why it matters:* small or continuous pieces of work no longer need a version number invented for them just to pass a checkpoint.

- **A record that was only collecting noise has been narrowed.** The re-version ledger recorded every instance of a release changing its number, but nearly all of those entries required no follow-up. It now records only the rare case that leaves something behind needing cleanup. *Why it matters:* what remains in that file is genuinely worth reading.

## Known limits

- The improvement to shared-record merging is proven by direct testing, but the specific real-world scenario that prompted it — two releases genuinely finishing at the same moment — can only be observed the next time it happens. That confirmation is deliberately left open and will be checked at the first concurrent close.
- Two related issues were found during this release and are tracked separately: the ADR-numbering check blocks two people from writing decision records at the same time (#3695), and one leftover tag from an old release is still unreaped (#3666).

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE** · confidence **HIGH**. The merge automation is a single new configuration file — deleting it restores the previous behavior with no data migration and no change to any existing record. The readiness criterion is additive, and no existing check was renumbered or removed. Whole-release rollback is `git revert -m 1` of the release merge; no historical record was rewritten by this release.

### Operator and engineering detail

Three issues, one branch, one merge — raw audit detail at the [`RELEASE_LOG` row](../RELEASE_LOG.md#version-identity-and-corpus-ledgers).

**#3016** created Gate-3 criterion **G3-19** (`field`/`judgment`/`recommend`) in `gate-criteria-spec.md`, schema 2.2 → 2.3. The criterion asserts release-identity-mode validity rather than claim-time version freeness — a distinction forced by two-phase allocation, where no concrete version exists at the Bundle → Planning boundary. A premise correction landed at Stage 5: the acceptance criterion had been written as "make the existing criterion conditional," but no such criterion existed in the gate spec — it lived only as prose in the Stage-3 shard, which had explicitly deferred the enforcement to a later card. The verb became *adds*.

**#3108** introduced a root `.gitattributes` binding `merge=union` to the three pure-additive ledgers. `RELEASE_LOG.md` and `RELEASE_REVERSIONS.md` are excluded as state-bearing. The exclusion was proven, not asserted: unioning `RELEASE_LOG` on the real schema with two branches transitioning different rows produced a clean merge landing four rows — each version recorded as both DEPLOYED and VERIFIED. The originally-specified mechanism (resolve by regeneration) was rejected because a regenerate path had been deliberately removed by an earlier fix as the cause of sibling-row reorder and notes-link drop.

**#3109** slimmed `RELEASE_REVERSIONS.md` to an orphan-tag recovery record. Evidence: 25 rows, reaper fired 0 times, one orphan tag ever. Retire was rejected as near-irreversible — it would require superseding an accepted ADR and span twelve files while the underlying churn is only half root-fixed. All historical rows and the twelve-column schema are byte-unchanged. This release is the mechanism's own first live test: with no re-version and no orphan tag, `append_reversions` correctly resolved to N/A and wrote nothing.

**[ADR-088](../../ADRs/ADR-088-release-state-binding-and-mechanical-merge-boundary.md)** records both boundaries under one rule — *bind state at the moment it becomes true, and resolve mechanically only what carries no state.*

**Unusual stage outcomes.** Stage 7 returned FAIL on #3109: the new gate had broken dry-run/apply parity on the dominant path, previewing a write that apply then skipped — the same defect class as a parity gap fixed in this script days earlier. The self-test had missed it because the design's required dry-run fixture was repurposed and coverage moved to the one path where parity coincidentally held. A Tier-1 fix pass routed both paths through a shared classifier; Stage 8 independently re-verified 7-of-8 parity cases broken before, 8-of-8 correct after, and found two additional broken cases Stage 7 had not reported. Mutation testing confirmed the restored fixtures fail when the bug is reintroduced. One narrower gap survives: no fixture asserts preview/apply parity on the already-present path.

Stage 8 was entered before the Stage-7 FAIL was formally retired — the fix pass reported to the Engineering sub-task rather than the DevTest one, and no re-review was recorded. Stage 8 substituted first-principles empirical re-verification, which is why the evidence is sound; the process deviation is recorded at the Stage-9 gate.

**Version lineage.** Scoped at provisional v3.80, lost to a concurrent release, re-versioned forward to v3.84 at the Stage-12 pre-merge relabel. The v3.80–v3.83 gap for this lineage is permanent and benign. This release encountered five in-flight identifier collisions in total — two version numbers, an ADR number, a schema version, and a second ADR number — every one an identifier bound from a snapshot that could not see concurrent claims. That is the class this release only partially addresses; the card naming it in full was returned to triage before the bundle was built.
