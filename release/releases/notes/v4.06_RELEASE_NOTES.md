# One release record, three generated views, and a file you can actually read

2026-08-03 · v4.06

The platform kept its release history in four places and wrote to all four by hand. When they disagreed — and they did — there was no way to say which was right. Now one file is the record and the other three are generated from it. That same file had grown to 783 KB, past the point where anything but a search could open it; it is now 148 KB, with nothing deleted.

> **Skip the rest** unless you read the platform's release history, or you author templates or governance documents in it.

## Who this affects

- Anyone who reads the release history — the log, the index, the digest, or the changelog.
- Anyone who authors or edits a template under `operations/templates/`.
- Anyone who has wondered what the word `domain` means in a given governance file.

## What you need to do

1. **Run the normal deploy step for your workspace.** Three packaged assistants — the process designer, the project agent, and the project initiator — were repackaged in this release, so an existing install keeps the previous copies until it is redeployed.

Nothing is migrated, no settings change, and nothing else is required.

## What changed for everyone using the platform

- **The release history now has one author instead of four.** `RELEASE_LOG.md` is the record; the index, the digest and the root changelog are generated from it by a single tool that cannot read a clock, cannot read your local configuration, and cannot rewrite what is already written. Every one of them has to be told the version, the merge point and the close point explicitly. *Why it matters:* four files updated by hand drift, and when they disagreed there was no rule for which one won — so the disagreement just sat there.
- **The release log is 81% smaller and nothing was deleted.** 147 older per-release write-ups moved into four archive files sitting in the same folder, so a recursive search finds them exactly where it always did. Every heading stays behind in the log with a line saying where its detail went, so every existing link still resolves. *Why it matters:* the file had passed the point where you could read it end to end; you could only search it, which meant you had to already know what you were looking for.
- **The question of whether the platform should ever delete a generated file now has a written answer, and the answer is no.** Archiving is the permanent end state. The reasoning is deliberately not "we never delete" — the platform does purge in three other places — but that the rule could not be written down: the field a deletion clock would read is set on zero files, and the whole population in question is about 1 MiB against a 1.45 GiB workspace. Four specific conditions are recorded alongside it, so re-opening the question later is a defined step rather than a fresh argument. *Why it matters:* this was asked once before and settled without a record, which is exactly why it came back.
- **The word `domain` turned out to mean six different things, and there is now one page that says which is which.** Two of the six were even called the same thing at their own definition files, with no overlapping values. Nothing is renamed and all 44 existing declarations are untouched — the fix is an index, not a migration, and each affected file now carries one line pointing at it. *Why it matters:* a word that silently means six things is a word you cannot check, and four earlier surveys of this same problem each missed at least one sense.
- **Twelve more templates now carry the provenance header every template is supposed to have.** They were waiting only for a family name to exist, which earlier work in this same release supplied. Each was read end to end and placed by hand rather than by a script, which mattered for one of them whose frontmatter has to sit above an opening marker comment to be read as frontmatter at all. *Why it matters:* provenance is what tells you where a generated document came from and whether it is current.

## Known limits

- **Seven templates still carry no provenance header, and that is now a decision rather than an oversight.** Those seven already have a `domain` line that belongs to the document they produce, not to the template itself. A markdown file has one frontmatter block, so adding the template's own header would put two `domain` lines in it — and the format resolves that by silently keeping the last and discarding the first, with no error. The decision is recorded: they are a named class, they are not exempt, and their header goes in a companion file beside the template. This release deliberately does not do the move, so the two dependent pieces of work now build against an answer instead of an assumption.
- **The release-plan verifier reports five errors against this release's own plan, and none of them is a criterion failing.** Three are the tool failing to extract a command that is present in the file; two are criteria that declare no method for it to extract. It is a gap in the tool, not a defect in the release.
- **One decision record still carries a stale section citation and was deliberately left alone.** Five other files carrying the same stale citation were repaired in this release. The sixth is an immutable decision record and is outside the change set, so it is recorded as known drift rather than quietly edited.
- **The check that reports whether packaged assistants are up to date is still advisory, not blocking.** It reports the true answer and exits distinctly, but it does not yet stop a change.
- Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:pipeline` label.

## Reversibility

MODERATE / HIGH confidence. Reverting the single integration commit restores every file's bytes — the archive files, the projector, the template headers and the governance text all go back together. What it does not restore is *provenance*: a reverted repository's next close-out would write the release history by the old four-author path again. Nothing was migrated and no stored data was transformed, and — importantly — no history was regenerated, so the surface a revert actually touches is one cell in the log plus the tooling. The three repackaged assistants need the deploy step run again after a revert rather than reverting on their own. Standard 7-day rollback window.

### Operator and engineering detail

**The card's literal ask was rejected on measured grounds and replaced.** `#4455` asked that the log become the single authoritative record and the other three be generated from it. The shipped design is **two file sources plus two run-scoped inputs, one projector, per-field provenance** — because the log carries neither a headline nor a summary, so forcing the narrative onto it would have imported roughly 160 headlines and 156 summaries into the exact file `#3715` exists to bound. The projector emits **entries to stdout, never files**, because about 63% of digest headlines and 60% of changelog blocks carry legitimate post-emission operator edits that a whole-file regenerate would destroy.

**The archival sweep's carve-out is the interesting part.** `#### Release Learnings` blocks are never swept, heading or body, while `#### Deployment Log` bodies are. The reason is that the learnings blocks have a consumer that reads the block **body** — and when the body is absent that consumer degrades to a legitimate-looking "no novel learning this release" sentinel, at exit zero, with its own guard silently satisfied because a stub body is non-empty. It would assert there were no learnings rather than that the learnings had moved. The carve-out costs about 2% of the swept volume. The general rule it encodes: the blast-radius question for a content move is *what reads inside a block*, never *what declares an anchor at it* — an anchor breaks visibly, a body parser degrades silently.

**One card withdrew its own design rather than cite an interface that would not satisfy it.** `#3413`'s Stage-5 specification routed a referent read through the repository-host adapter. Re-derived at Stage 6, that standard specifies exactly four operations, all scoped to version-claiming; they return versions and claim outcomes, never a referent. The probe was run with a control — zero hits for the referent vocabulary against 44 for the four operation names — and the delegation was withdrawn and recorded as a **named gap** owned by the adapter-interface work. The selector half of the design survives.

**The file-change matrix was reconciled in both directions, because a one-directional check is how it drifted.** Twenty-two shipped files were unnamed and three matrix entries resolved to nothing — including one naming a file that has never existed. A shipped-to-matrix check alone never surfaces a row naming a nonexistent file; a matrix-to-shipped check alone never surfaces an unnamed shipped file; and a group description credited by *name* rather than by *count* hides a stale figure indefinitely. One such figure read 26 where the truth was 7, because it was measuring three cards' work and attributing it to one.

**ADR-092's claim-time identity stamp fired for the first time in the `v4.x` sequence.** For three consecutive releases the mechanism was built, gated on an argument whose pre-flight requires a placeholder token, and skipped because no plan carried the token. This release's plan carried it. Forty-three placeholders bound at the claim and the plan took its versioned name. The stamp ran through the release's chore pull request rather than through the claim tool's own path, because that path pushes straight to the main branch, which the repository's own rules forbid.

**The version number was claimed as a minor bump against a planning note that said "patch".** The note was not executable as written — the claim tool halts on a patch bump without an explicit base version, and none was ever recorded — and supplying one would have declared an 86-file, 5,905-line release to be an in-place correction of its predecessor, which is the one thing the selection guide reserves that class for. The evidence is recorded in full in the log entry, including the ledger precedent across all four archive segments: 13 minor bumps, one patch, and that one carried an explicit base.
