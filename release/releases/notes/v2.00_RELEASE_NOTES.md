# Five skills get deeper: adoption tracking, tiered hypercare, gated releases, QA failure-mode detection, typed release plans, and artifact lifecycle states

2026-06-15 · v2.00

Five existing skills gain real capability without any new skill being added: change-management now tracks adoption and runs tiered hypercare with SLA compliance, the release executor checks a release against an ordered set of gates before it applies and can roll a gate out gradually, the QA auditor runs an eight-signal failure-mode battery, the release planner labels how a plan's artifacts relate, and the artifact generator stamps every artifact with a lifecycle state and flags the stale ones. Everything is additive except one contained field rename inside the artifact generator's own output.

## Who this affects

- **Anyone running a change-management go-live.** Adoption tracking and a tiered hypercare model with SLA compliance reporting are new outputs you can ask for; existing impact / training / readiness / hypercare modes are unchanged.
- **Anyone executing or planning a platform release.** The release executor now runs an ordered pre-apply gate ladder and the release planner now labels each edge in a release plan with how its artifacts relate. Both are additive over the prior behavior.
- **Anyone QA-auditing a skill output.** The QA auditor gained an eight-detector failure-mode battery and a RACI-accountability gate that run alongside the existing checks.
- **Anyone generating project artifacts.** Generated artifacts now carry a lifecycle state and the health check flags artifacts that have gone stale. One frontmatter field on generated artifacts is renamed (see "What changed", last bullet).

## What changed for everyone using the platform

- **Change-management now tracks adoption, not just plans it.** A new Adoption Tracking mode surfaces an ADKAR barrier assessment, a champion-ratio and sponsor-coverage read, a training-timing check, and a change-fatigue and outcome-measurement read, drawing on the existing change-methodology framework rather than restating it. *Why it matters:* you can see where adoption is actually stalling — which ADKAR barrier, whether enough champions are in place, whether training landed in time — instead of inferring it from a static plan.

- **Hypercare is now tiered, with SLA compliance you can prove.** The hypercare mode classifies each incident into one of three risk tiers, logs each one with its open and resolve times, and produces a compliance report showing met-versus-breached against each tier's committed response and resolution targets. An open SLA breach now blocks hypercare exit. *Why it matters:* you can answer "are we meeting our hypercare commitments?" with a per-tier report, and a go-live cannot quietly close hypercare while a service-level breach is still open.

- **A release is now checked against an ordered set of gates before it applies.** The release executor runs a three-step ladder — schema validation, then cross-reference integrity, then stakeholder approval — that fires in order and stops at the first hard failure, so a release with a broken schema halts before the later checks run. Each failure reports what failed, where, and what to fix. *Why it matters:* a release that would not pass its own checks is stopped before it changes anything, with an actionable reason rather than a downstream surprise.

- **A new gate can be rolled out gradually instead of switched straight on.** Each release gate carries a rollout setting — observe-only, notice-only, or blocking — so a new check can run silently and log what it would have caught, then warn, then block, with the move to blocking being an explicit operator decision after reviewing the hit rate. *Why it matters:* a new gate proves itself on real releases before it can ever block one, so it cannot break a deploy on its first day.

- **The QA auditor now runs an eight-signal failure-mode battery and a RACI check.** The auditor screens an output against eight named failure signals — over-reliance on automation, an impersonal PMO voice, an echo chamber, quality drift, single-point-of-failure concentration, breadth burnout, AI hallucination, and trust erosion — and adds a gate that flags a responsibility assignment with no single accountable owner. *Why it matters:* recurring ways an output goes wrong are caught by name with a stated threshold, instead of relying on a reviewer to notice each one unaided.

- **A release plan now labels how its artifacts relate.** The release planner tags each edge in a plan's dependency view with one of four relationship types — generates, depends-on, blocks, or supersedes — using the platform's existing relationship vocabulary. *Why it matters:* you read at a glance how a release's pieces relate rather than inferring the graph by hand, and the labels match the relationships the backlog already uses.

- **Generated artifacts now carry a lifecycle state and stale ones get flagged.** Every generated artifact is stamped with a state from the platform's canonical five-state lifecycle (draft → reviewed → approved → promoted → archived), and the artifact health check flags any artifact left unreferenced for more than 30 days while still in a live (non-archived) state, listing it in a documentation-debt register with a recommended action. *Why it matters:* you can tell at a glance where an artifact sits in its life and surface the ones that have quietly gone stale, instead of discovering them by accident. Note: the field that records this on generated artifacts is now named `artifact_state` (it was previously `status`); the change is contained to the artifact generator's own output and no other skill reads that value.

## Known limits

- The three hypercare risk-tier band edges ship as a recommended default pending operator ratification; adjust them to your environment if the default split does not fit.
- Two of the eight QA failure-mode detectors (a concurrency ceiling and a walk-back-rate floor) read their threshold from platform configuration rather than a fixed built-in value, so they are inert until that configuration is set.
- The release-plan relationship labels are a second, independent edge attribute; they sit alongside the existing schedule-precedence type and do not change any schedule or critical-path calculation.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

MODERATE / HIGH confidence. The release is skill-file and reference-doc edits on one branch — no schema migration, no data change, no external system. Whole-release rollback is `git revert` of the integration merge; per-skill rollback reverts that skill's commit. The one behavior change to undo is the artifact generator's `artifact_state` field default; because no other skill reads that value, reverting is clean. Standard 7-day rollback window.

### Operator and engineering detail

**Change-management adoption science (Mode G) and tiered hypercare (Mode D)** — A new Mode G (Adoption Tracking) surfaces ADKAR barrier assessment with training-timing validation, champion-ratio / sponsor-coverage / valley-of-despair preparation, and change-fatigue plus outcome measurement, all consuming the single-source change-methodology framework by reference (no duplicated scale or rule). Mode D (Hypercare) gains a risk-classification step with a stable three-tier set scored as Severity × Likelihood × Blast-Radius, where Severity and Likelihood are adopted by reference from the delivery-engine RAID scale and only Blast-Radius is net-new; a Mode-D tracking step then records each incident as an existing-prefix RAID entry with a met/breached verdict computed against the tier's committed SLA, emits a per-tier compliance report, and makes an open SLA breach a hard, non-waivable Mode-D exit gate. The new hypercare risk-classification and SLA-tracking sections reference, rather than replace, the existing 3-Tier Support model and S1–S4 severity→SLA matrix (an orthogonal management-posture axis).

**Release-executor quality-gate ladder, progressive rollout, and close-out build-out** — A canonical three-tier pre-apply gate ladder (T1 schema validation → T2 cross-reference integrity → T3 stakeholder approval) fires in order and short-circuits on the first hard failure, wired at both execution entry points (the git-native PR-merge pre-execution surface and the Cowork snapshot-apply path) from one source, and reusing existing instruments (the corpus schema lint and the doc-link checker; an unverifiable surface counts as a FAIL) rather than inventing new detectors. A three-cycle progressive-rollout model (shadow → warn → enforce) wraps the ladder via a per-gate `rollout-cycle` attribute that defaults to — and fail-safes to — enforce, with shadow/warn hits persisted to a per-rule append-only outcome log and advancement gated by an operator Advance Checklist; only an enforce gate short-circuits, so the ladder's ordering semantics hold while each gate becomes roll-out-able. Mode D (Close Release) is a documented build-out (not a rebuild) onto the existing close-out mechanism: an explicit issue-closure audit that treats a non-zero open-issue count as a blocking finding, carry-forward / deferred-item tracking named as a Step-6 close-out output reported every close, and a new close-out checklist reference doc.

**QA-auditor failure-mode detector battery (P1) and RACI gate** — A new failure-mode-detectors reference doc carries an eight-detector catalog (automation complacency, faceless PMO, echo chamber, quality drift, single-point-of-failure, breadth burnout, AI hallucination, trust erosion), each authored to the platform failure-mode five-field template with a category tag, observable signature, numeric threshold, and current-status read so structural conformance holds. Thresholds are lifted from existing corpus precedent rather than invented; the two operator-specific absolutes are config-referenced, not canonicalized inline. The auditor's own Domain-Specific Failure Modes section is untouched — the eight detectors are detection infrastructure, not the auditor's authoring surface — and the mode count stays five.

**Artifact-generator lifecycle states and zombie detection** — The generator adopts the platform-canonical Artifact Workflow vocabulary: the field `artifact_state` (replacing the prior `status` field) with the canonical five states DRAFT → REVIEWED → APPROVED → PROMOTED → ARCHIVED, stamped as DRAFT on emit. The original six-state intent maps onto the canonical five (Active → PROMOTED); the former `Superseded` value has no canonical state and is instead represented through the documentation-debt register. The health-check zombie step flags artifacts unreferenced beyond 30 days that are not yet ARCHIVED (flag, not auto-transition), and the lifecycle-states reference doc is re-specced as an application layer over the canonical state machine rather than restating it. The field rename is contained (verified: no skill outside the artifact generator reads the literal value).

**Release-planner typed artifact linking** — A generated release plan labels each in-release edge with one of four artifact-relationship types (GENERATES / DEPENDS_ON / BLOCKS / SUPERSEDES), adopted verbatim from the frozen canonical relationship vocabulary so planner output and backlog relations cannot diverge. The relationship type is a second, independent edge attribute added alongside the existing schedule-precedence type; the critical-path math never reads the relationship field, so the change is provably additive. Edges are typed deterministically with default-to-DEPENDS_ON as the weakest-correct-claim safety net.

For full implementation detail see the RELEASE_LOG.md entry for v2.00 and the v2.00 release plan.
