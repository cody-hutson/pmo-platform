# Finishing a release is now reliable and produces the same complete record every time

2026-06-28 · v2.38

The automated tool that finishes a release has been hardened so a close-out runs to completion, writes its full set of records, and reports "done" only when the release actually is. Several defects that could strand a close partway, mark it complete when it was not, or attach the wrong details to the published release page are fixed, and the tool can now skip the right work items and wait realistically for checks to finish. This is internal release-pipeline hardening — nothing changes for project work, status outputs, trackers, or artifacts. This release closes itself using its own fixed close-out tool.

## Who this affects

- The operator finishing a release, and anyone who reads a published release page on GitHub. No effect on project artifacts, trackers, status outputs, or any command.

## What changed for everyone using the platform

- **Finishing a release runs to completion instead of getting stuck partway.** A close that produced no changes on its records branch, or that hit a slow check, no longer strands the final steps; the tool now guards the empty-change case and waits a realistic amount of time for checks. *Why it matters:* a release gets fully finished in one run, instead of stopping halfway and leaving records and the milestone in a half-closed state someone has to clean up by hand.
- **A release is reported complete only when it actually is.** The tool now confirms a release's status from what truly landed in the merge, rather than trusting the prior recorded state, and it writes its full set of close-out records every time. *Why it matters:* "done" means done — a release can no longer read as finished while a record or the published page is missing.
- **The published release page is tied to the exact code that shipped.** The public release page is now bound to the specific merge it came from, with a check that confirms the match. *Why it matters:* the page people read points at the real shipped code, so there is no ambiguity about what a given release actually contains.
- **The close-out can skip the right items and add the right notes.** Finishing a release can now leave specific tracking items out of the auto-close step and attach a tailored note per item, instead of applying one fixed comment to everything. *Why it matters:* the items that should stay open stay open, and each closed item gets an accurate note, so the tracking record reflects what really happened.
- **A documentation-only change to a tool now reaches everywhere it is used.** A change that touches only a tool's reference material — not its main definition — is now recognized as still changing what gets delivered, so it is carried through to every copy rather than silently left behind. *Why it matters:* an updated reference actually shows up where you use the tool, instead of the published copy quietly going stale.

## Known limits

- These are release-pipeline fixes and guidance; they change how releases are finished and verified, not any project-facing behavior, artifact, or command.
- The fixes apply to releases finished after this one — they do not retroactively re-finish or re-verify past releases.
- The close-out still reads a release's recorded outcome; a close that never wrote its release-log entry at all remains outside what these checks can see (that stays a separate close-time check).

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:pipeline` label.

## Reversibility

MODERATE / HIGH confidence. The changes are tracked edits to the close-out tool, two pipeline references, a skill definition, and a deployment rule; reverting the integration PR restores the prior behavior in one step. The risk is MODERATE rather than CHEAP because the close-out tool is the mechanism that finishes releases, so a revert returns to the prior, less-reliable close behavior rather than to a no-op. No data migration, no stored-content move, no change to any existing project surface. Standard rollback window.

### Operator and engineering detail

**Close-out defect cluster — slug derivation, false-PASS transition, digest headline, merge-poll cap, phase seam (#667).** The automated close-out tool's slug mis-derivation (which produced a false zero-open count and wrong pull-request metadata), a false-PASS on the release-log state transition, a malformed digest headline, the unrealistic 30-second merge-poll cap, and a defect at the Phase 9→10 seam are all corrected. These were the defects that let a close report success while leaving work undone or stranding its terminal phases.

**Completeness check reconciled to the real release-log shape (#82).** The Stage-13 / Procedure-7 completeness check that asserts a release-log entry is present now matches the actual on-disk convention — the table row plus the visible-H4 `#### Deployment Log` block — rather than an older expected shape, so it stops mis-reading a correctly-written entry.

**Outcome field injected on the close (#37).** The close-out now injects the `**Outcome:**` field on the visible-H4 Deployment Log block (default SUCCESS, with an `--outcome` override and a required rationale for any non-SUCCESS value), so the deployment record carries the close-time outcome rather than omitting it.

**Per-item exclude and per-item close note (#38).** The auto-close step gains a repeatable `--exclude-issue` filter and a repeatable per-item close-comment override, replacing the prior single hardcoded comment applied to every item. This is what lets the orchestration sub-tasks be filtered out of the auto-close loop so they cannot self-close mid-run.

**Zero-commit guard and a CI-realistic merge budget (#1705).** The records-branch step now guards the no-change case so a zero-commit branch no longer strands the terminal phases, and the merge wait defaults to a realistic 300-second budget (configurable, replacing the 30-second cap) with a `--no-merge` escape that leaves the records PR for the operator when checks exceed the budget.

**Re-derive the verified state from deploy reality (#1681).** The release-log `DEPLOYED → VERIFIED` transition is now re-derived from the release pull-request merge rather than trusting the prior recorded row state, closing the false-PASS where a close could promote a row that had not actually shipped.

**Concurrency guard for the append-only ledgers (#1680).** The four append-only release-corpus ledgers gain a concurrency guard for the case where two closes run near each other, so a later close validates its records against current main and does not silently regress or drop a sibling release's record.

**Bind the published release to the merge identity (#1682).** The published GitHub Release is now bound to the merge it came from, with an identity check confirming the published release points at the correct merge, so the public page cannot drift onto the wrong code.

**References-only skill change now propagates (#84).** `core/rules/skill-deployment.md` codifies that a change touching only a skill's reference material still changes that skill's deployed surface — both the working-copy mirror and the packaged copy — and so must be carried through, defaulting to propagate with a record-deferred fallback that requires a tracked follow-up. The matching close-out and pipeline conformance landed in `stage-12-execute.md`, `hub-spoke-bridge.md`, and the `release-executor` skill.

**Reflexive-loop posture.** This release's own close-out improvements are exactly the tool that finished it: the merge landed the fixed close-out script, and it then closed v2.38 with its own zero-commit guard, re-derived verified-state, per-item exclude, outcome injection, and merge-identity binding. Development testing and quality review validated the fixed script self-test green before this close.
