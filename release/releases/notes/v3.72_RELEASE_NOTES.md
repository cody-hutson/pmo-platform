# The release orchestrator is safer and finishes cleaner

2026-07-12 · v3.72

This release hardens the platform's release orchestrator — the internal skill that drives a piece of approved work from "ready to build" through merge and deploy. Nothing changes in how you use the platform day to day; this is machinery the platform runs on itself, and these changes make its own release process safer, harder to leave half-finished, and clearer about what to do next.

> **Does this affect me?** Not directly. These are improvements to the release-engineering tooling. You benefit indirectly: releases are less likely to stall, get stuck "merged but not recorded," or quietly skip a safety step.

## What changed for everyone using the platform

- **The readiness check can no longer change things by accident.** The pre-flight that decides whether a batch of work is ready to release is now strictly advisory — it recommends fixes, it never executes them. Acting on any recommendation takes a deliberate, separately-authorized step. *Why it matters:* a check meant to *assess* readiness can no longer *alter* the very thing it is assessing.
- **The readiness check always tells you the next step.** Instead of stopping at a verdict, it now ends by naming the concrete next action — run the release, or clear this cleanup list first. *Why it matters:* no more guessing what to do after a "not ready" result.
- **A new architecture-conformance check.** Readiness now flags work that would hard-wire one way of working into the shared toolkit, or that proposes a risky folder rename, before it enters a release. *Why it matters:* it catches a class of design mistake that used to slip through the readiness gate.
- **The release driver always claims a version and logs the deploy.** Executing a release now always records the version, tags it, and writes a deployment record — never leaving a release "merged but not recorded." *Why it matters:* the release history stays complete and auditable.
- **A collision check before duplicate work.** Before building, the driver checks whether another release is already working the same item and surfaces it. *Why it matters:* it avoids two divergent builds of the same change.

## Known limits

- **Two related checks were deferred.** Two further readiness checks — *is this work already owned by another initiative?* and *is the problem real and at the right level?* — were pulled from this release because they require extending two neighboring skills to be done correctly. They are filed as a coordinated follow-up (#2574, #2575).

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH confidence.** These are additive edits to one skill with no data migration; rollback is a revert of the release PR plus a yanked tag and release — recoverable, though stakeholder-visible rather than a silent undo.
