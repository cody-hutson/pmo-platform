# Intake now adapts to your project's methodology

2026-07-10 · v3.67

Each project can declare how it runs — Scrum, Kanban, and others — but the front door for filing work ignored that choice: it offered the same generic templates and produced methodology-neutral items no matter what a project had configured. This release wires intake to the configured methodology. Filing a work item now renders the right vocabulary: you can create an Epic or a Story directly with the correct type applied for you, a determinate rule picks the correct template so you are not asked to guess, and a single space can run one methodology for its day-to-day operations and a different one for its releases. It builds directly on the methodology-pack foundation shipped earlier — this release populates the catalog at the point where you actually file work.

## What changed for everyone using the platform

- **You can file an Epic or a Story directly, and the right type is applied automatically.** Two new intake templates join the existing set; picking one stamps the correct work-item type and marks the item proposed, with no manual labelling. *Why it matters:* the work-item type that the platform's gates and reports rely on is now correct from the moment you file, instead of something a later step has to fix.
- **Intake speaks your methodology's language.** When a project has a methodology configured, intake reads it and offers the matching work breakdown and item kinds rather than a generic default. *Why it matters:* a Scrum project files Stories and Tasks; a Kanban project files Cards — you see the vocabulary your team actually uses, not a one-size-fits-all list.
- **A space can run different methodologies for operations and for releases.** You can now declare an operational methodology and a release methodology separately for a space. *Why it matters:* teams that run flow-based day-to-day work but stage-gate their releases (or any similar split) can finally represent both, instead of forcing one global choice.
- **You are no longer asked to guess which template to use.** A clear, deterministic rule now routes each idea to the right intake template — bug reports, improvements, under-specified observations, and decisions each have a defined home, applied up front. *Why it matters:* filing is faster and more consistent, and the platform stops surfacing a needless "which one?" question when the answer is already determinate.

## Known limits

- The two new templates take effect **after this release is on the main branch** — the live "file a test item from the template" check runs only once the templates are published there, so this release records that check as verified by the template definitions and confirmed post-merge.
- Templates exist for Epics and Stories specifically. Work-item kinds without their own dedicated form (for example a Kanban card or a plain task) are still filed through the general improvement template, with the type carried on the label.
- The new cross-cutting readiness-control capability for schemas ships as the shared mechanism plus its first design-and-architecture control set; that first control set lives in per-operator configuration rather than in the shared public corpus.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH.** Every change is additive and backward-compatible: the new per-space methodology fields are optional, and existing project files, single-methodology projects, and hybrid projects all continue to validate unchanged (verified by a full regression pass over the existing worked examples). Roll back by reverting the release pull request and removing the version tag — undoable in hours, with no data migration; the only manual follow-on is that any items already filed from the new Epic/Story templates keep their applied type.

### Operator and engineering detail

Five issues closed the methodology-pack-catalog milestone (RELEASE_LOG `87-methodology-pack-catalog`, **Outcome: SUCCESS**), delivered as one branch / one PR / one merge (release PR #3316, merge SHA `883baa6`, signed tag `v3.67`). Release Class **cross-cutting** — the work spans a skill, a protocol, two schemas, and the intake templates, atop the methodology-pack foundation shipped in v3.60. Provisional **v3.66** at plan time; a sibling release claimed that slot first, so the version was forward-computed to the next free number **v3.67** at first commit and confirmed free again at the tag — the expected behaviour when two releases run in parallel, not an error.

The five slices: **#1085** wires intake-desk to resolve the active methodology (a resolution step that reads the per-space `operational_methodology` before falling back to `delivery_approach`, via the platform's 5-rung config resolver) and to place-and-relate items by the methodology's own work breakdown, with the public skill body kept methodology-neutral (it reads configuration; it hardcodes no archetype). **#1067** codifies the determinate "which template" rule as a new section ahead of the existing intake test, plus a guardrail that a determinate classification is decided directly rather than raised as a question. **#1788** adds the optional per-space `operational_methodology` and `release_methodology` fields with two new validation rules (the meta-archetypes are deliberately excluded per space), and a precedence contract that the intake resolver reads. **#1803** specifies the previously-reserved cross-cutting control-field mechanism in the work-item type schema — a pack-level control concept that feeds the existing architecture/readiness gate rather than adding a second gate — recorded in founding **ADR-077**; the criterion grammar was not re-opened. **#1973** ships the Epic and Story templates as the chosen "one form per type" design (a single-dropdown alternative was evaluated and rejected because only a per-type form can structurally stamp the type at submission).

Two candidate members were returned to triage before the run rather than shipped: a documentation item made redundant by the v3.60 restructure, and a Kanban class-of-service item that the shipped v3.60 pack had already decided differently. Dev Testing passed all five slices, catching and fixing two real issues under verification — a stale "four templates" count in the getting-started doc (the change ships six), corrected count-free, and a branch-freshness gap closed by merging the disjoint sibling release forward. QA accepted all five at full score with zero overrides, including a check that the per-space grammar rejects all nine illegal shapes and that the new control cannot trigger its own gate. The one changed skill body (`intake-desk`) rebuilds its packaged form at close-out.
