# Checks now say when they could not measure, instead of reading green

2026-08-29 · v4.42

Nine automated checks and tools could report success while measuring nothing at all. Each now either measures the thing it names or states plainly that it could not — and the conditions that used to fool them are ordinary ones: a pull request with a conflict, a tracker that has not caught up, a busy interface, a different flavour of a common command.

## What you need to do

One step, for the workspace operator only, once. Automatic filing of recurring patterns needs a tracker label that does not exist yet, and this release deliberately does not create it — the platform's reconciliation reports a missing label, it never creates one. Run the label-parity tool with its fix-emitting option from the repository root, then run only the single create command it prints for `auto-promoted-pattern`. Until you do, the reconciliation check will keep reporting that label as missing; that report is the check working, not a fault.

## What changed for everyone using the platform

- **A pull request that cannot merge no longer reads as passing.** When a change has a merge conflict, its automated checks never start — and the pipeline was reading "no failures" from an empty set of results as though it were a clean sweep. Two stages now confirm a change can actually merge before reading any results, and compare what ran against the number of checks the repository genuinely requires. *Why it matters:* a release can no longer advance on a conflicted change that looked green because nothing had run.
- **A published release description can no longer be silently emptied.** The step that removes the metadata header from a release note behaved differently on Linux than on macOS and returned nothing at all, while the safeguard meant to catch a mismatch was comparing nothing against nothing and so always reported no problem. One shared routine now performs that step everywhere, and the publisher refuses to publish an empty description. *Why it matters:* the hosting service keeps no history of a release description, so publishing an empty one cannot be undone — that path is now closed.
- **Recurring problems now have a working path to becoming tracked work.** The tool that files an issue when the same lesson shows up across several releases could never finish: it invoked a command it was unable to locate, and applied a label that had never been created. *Why it matters:* a pattern the platform already noticed no longer gets noticed and then lost.
- **The check that confirms every release item is closed now waits for the tracker to catch up.** It re-read the list of open items two seconds after closing them and routinely saw stale data, so the last item closed still appeared open. It now waits up to thirty seconds, stops the instant the list empties, and reports a read it could not complete as exactly that rather than as a result. *Why it matters:* a release close no longer invents a leftover item, and a read that genuinely failed no longer passes quietly.
- **Parallel work now has a cap on how much starts at once.** The budget checkpoint that decides whether to go ahead produced only a yes or a no; it now also produces a maximum number of workers to start together. *Why it matters:* total consumption is unchanged, but if a run is interrupted partway, far less work is thrown away.
- **The budget checkpoint measures a second limit instead of assuming it.** It tracked one consumption window and simply took the hosting interface's own headroom for granted; it now reads that headroom once per turn and holds back when either limit is tight. Where both are healthy, behaviour is unchanged. *Why it matters:* a long run is less likely to stop in the middle because of a limit nothing was watching.
- **A usage report that failed can no longer finish quietly.** Two places in the usage extractor discarded an error and carried on, so a run could exit as though it had succeeded with a silently duplicated store behind it. *Why it matters:* a report you are about to rely on now tells you when it could not be produced.

## Known limits

- **The Linux-side proof for the release-note fix is argued, not executed.** The environment needed to run that falsification was unavailable, and a security control refused the attempt rather than being worked around. Two macOS-only pins therefore stay in place, with the reason recorded, until the proof can genuinely run. Tracked separately.
- **Nothing yet stops the retired copy of that same routine from coming back.** No committed check detects the old inline form, so a parallel change could reintroduce it without anything noticing. Tracked separately.
- **The new headroom reading cannot tell an unstarted window from a fresh one.** It renders "go ahead" in both cases, which is correct for a fresh window and unproven for an unstarted one. Tracked separately.
- **Nothing requires a release to keep an action-item ledger.** Because of that, "this release made no commitments" and "nobody kept a record" are indistinguishable to the check that grades them at close. This release hit that exact case. Tracked separately.
- **One readiness state still reports clean without consulting merge state,** which is the same family of gap this release closed elsewhere and was left deliberately unfixed here rather than widened into scope. Tracked separately.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. `git revert -m 1` on the release merge reverses all nine items together: every change is a script, a workflow, or tracked text, there is no data migration, no file move and no stored state. Two asymmetries are stated rather than hidden — the one operator step above creates a repository label that a revert does not remove (delete it separately, and only after reverting), and this release changed tooling that runs during its own close, so a revert cannot un-run a close that has already happened. Standard rollback window.

### Operator and engineering detail

**The release closed itself using the tooling it had just changed.** Of the fifty-six files in the merge, the close-out script accounts for the single largest change, and the note-publishing library, the drift checker and the learnings synthesizer were all rewritten in the same merge. The close that produced this note therefore ran on the new code paths on their first real execution rather than against fixtures — including the empty-body guard on the publish path, which is the release's only irreversible surface.

**One transform, two mirrors, one fixture.** ADR-159 records the governing rule: an invariant spanning several implementations must be executable rather than annotated. The frontmatter-strip transform was extracted into a shared shell library with two Python mirrors, and all three are bound to a committed conformance fixture covering the lead-in, unclosed-fence, trailing-whitespace-fence, horizontal-rule and empty-file cases. A divergent reimplementation now fails a test rather than publishing quietly. The prior idiom's failure was asymmetric by userland, which is why the drift gate that should have caught it reported clean for as long as it did.

**One defect, found three times by three stages across three releases.** The mode-branch placement rule — predict at dry-run, assert at apply — had lived only as three comments buried in three separate phase bodies, so each instance was rediscovered independently. ADR-158 states it once, in the close-out tool's own header, together with why a presence check for the branch passes on the defective code: the branch was always there, merely stranded below an abort. Two further members of the class were fixed here, one by relocating the mode test and one by a per-limb downgrade, because two of that phase's three limbs must keep running under a preview.

**Provenance is the eighth label group.** ADR-155 adds a group that records *how* a work item entered the tracker, distinct from what it is, where it sits, and what was decided about it. Its distinguishing property is persistence: it is applied at creation by the filing mechanism and never removed, because downstream counting rules read it on closed issues — which is precisely why it could not be modelled as a triage flag. The concrete row is contributed by the common methodology pack and looks like this:

```toml
[[labels]]
group = "provenance"
name = "auto-promoted-pattern"
color = "D4C5F9"
description = "Filed automatically by the release-learnings synthesizer's cross-release pattern detector; awaiting triage. Persists through close (the schema-maintenance trigger counts it)."
applied_at = "Auto-promotion (synthesizer pattern-detect --apply)"
```

**A declaration detects; it does not materialize.** That single sentence is why the label above is an operator step rather than something the merge performs, and it was recorded as a decision because the planning stage had read the declaration as satisfying the criterion. The reconciliation check will report the row as missing until the operator creates it, and it cannot turn the wider check run red while it does so.

**Checkpoint B gained an output, not just a second input.** ADR-156 establishes that the second axis is measured rather than declared; ADR-157 establishes that wave width is a second output of the checkpoint rather than a second verdict. The practical consequence is that every rule which previously bound a go-ahead to launching all N spokes now binds to the smaller of N and the computed cap, and healthy pools behave identically to before. ADR-160 records the companion rule for the self-test coverage engine: when one engine hosts more than one invariant, each population belongs to its own rule rather than to the engine — so the directory listing, never the manifest, is the population.

**The version this release carries is not the one it was planned under.** The slot chosen at planning was claimed by a sibling release while this branch was in flight; the pre-merge freeness check halted on it, the operator ratified a relabel, and the corrected label landed on the branch before the merge rather than after it. Six architecture records were allocated against a counter that two siblings were drawing from concurrently, and the allocation was re-anchored twice during engineering as sibling claims stopped being advisory. Numbering was re-verified after the merge rather than inferred from a clean merge.

**The action-item ledger for this release was reconstructed at the close, not kept during it.** No ledger was instantiated while the release ran, so none of the routing points ever scanned one and the close gate would have found nothing to grade. Rather than attest over that absence, the operator directed a single-pass reconstruction from the durable record — the pipeline event log, the stage sub-task comments, the plan-review decision record and the execution outputs. The resulting nineteen rows carry stage-boundary dates rather than emit instants, and the file states this in its own header. Every row had already resolved to a filed issue, a landed commit or a rendered decision before the file was written; nothing was marked done to satisfy the gate. The absence of any requirement to instantiate a ledger is itself carried forward as tracked work.
