# The platform can now read the new project folder layout

Projects used to be organised into eight numbered folders. They are now organised into five, plus a couple of transient ones — a change agreed some time ago and already used by newly-created projects.

The tooling that catalogues your files had never been taught about it. Every file in a project using the new layout came back **unrecognised**. Not misfiled, not warned about — simply invisible to the catalogue.

This release teaches it the new layout, and settles a question the old design never had to answer: **where does a project's own paperwork live?**

## What you need to do

The catalogue has not been rebuilt yet. Doing so needs six pieces of information the platform will not invent, so it stops and asks.

1. Provide the **portfolio name** and its **identifier**. These are not the same value — the platform deliberately does not assume one from the other, because they are unique in different scopes.
2. Decide how the **Portfolio record** and the **Person record** should be maintained — specifically, which agent owns each, and what content-lifecycle pattern each follows.
3. Name the **two files** those records should live in. The platform has deliberately deferred this choice rather than guessing a filename.
4. Once supplied, the catalogue rebuild runs under **#5815**, which takes a restorable snapshot first.

Nothing is waiting on you urgently — the platform behaves correctly in the meantime, simply with an out-of-date catalogue.

## What changed for everyone using the platform

- **Files in projects using the new five-folder layout are catalogued again.**
  *Why it matters:* before this release, such a project had **none** of its files recognised — they were invisible to the catalogue rather than flagged, so nothing indicated anything was wrong.

- **A project's own governance files now have a recorded home.**
  *Why it matters:* `PROJECT.md`, `README.md` and `CORRECTIONS.md` sit at the top of a project, in none of the five folders. They are now recorded as sitting outside the folder system rather than being forced into a bin they do not belong to — and no sixth folder was invented to accommodate them.

- **A project's status is no longer confused with its document maturity.**
  *Why it matters:* two different ideas had been sharing one field, which meant a project could never register a valid status at all. A project is `ACTIVE`, `CLOSING` or `CLOSED`; a document is a draft, or current, or stale. Those are now separate.

## Known limits

**The catalogue itself has not been updated yet, and that is deliberate.** This release delivers the tooling; it does not run it over your files. See *What you need to do* above. Tracked at **#5815**.

Until that runs, the catalogue still reflects the old picture. Nothing is broken by waiting, and nothing has been changed underneath you.

**One file remains unreachable.** A single file sitting at the very top of the corpus — above any project — cannot be attributed to a project, because there is no project to attribute it to. It is a known and accepted residual, not a bug awaiting a fix.

## Reversibility

**MODERATE.** Everything in this release is a code and schema change, and the whole release can be undone with a single revert that restores every file it touched. Each of the three pieces of work can also be undone on its own, in reverse order.

The part that would have been **expensive** to undo — writing to your actual project files — did not happen. That is the deferral described above, and it is gated so it cannot happen by accident.

### Operator and engineering detail

**The five-bin taxonomy needed a non-bin sentinel, and ADR-139 records why.** `_project-root` names a location *outside* the closed set rather than a member of it, so ADR-080's closed-set invariant is unchanged. It carries the `_` prefix the schema already uses for non-bin areas. Adding a sixth bin would have broken a frozen decision in order to solve a filing problem.

**ADR-138 separates the Project entity's Axis-1 carrier from document lifecycle.** `V-CORE-03` now resolves an entity's Axis-1 *carrier field* rather than naming `lifecycle_state` literally; 18 of 19 entities resolve exactly as before, and Project resolves to `status`. The two were structurally incompatible — `PROJECT.md` is Domain B, and Domain B and Project Axis-1 have an **empty intersection**, so `lifecycle_state` on a project root could never satisfy the rule regardless of its value.

**Three defects existed only in the merged state**, and no single-card review could have found any of them: a `TypeError` where one card returns `None` for what another dereferences; a snapshot write-set regression where one card pulls four files into another's write set and voids its restore path; and an ADR-number collision created by a sibling release merging mid-build. All three were caught before they shipped.

**Eight of thirty-seven acceptance criteria could not fail.** The sharpest case passed identically whether or not the change it graded had landed — implementing the pre-amendment rule produced the same 19/19 result. A separate criterion passed while 38.4% of relationship edges were being silently dropped. All were rewritten to be falsifiable before this release closed, with the corrected wording recorded per criterion.

**Two Stage-12 steps were skipped, and both were caught by controls rather than by review.** The merge used `--squash` against the documented `--merge` default, which structurally voided the per-issue rollback this release declares; it was repaired additively — net content change zero, two parents restored. The ADR-092 atomic claim was not performed, surfaced by the close-out smoke; `claim-version.sh` then refused to proceed because the Stage-4 plan described the claim in prose but carried no `{{RELEASE_VERSION}}` token — a Stage-4 authoring gap the tool declined to guess past.

**Broken probes were caught and disclosed throughout** — by every grader, and by the hub. Two would have been fabricated findings against correct code, including one reporting 2/19 against a true 18/19 and another reading as 55/55 package-integrity failures until its control arm exposed it. Every count in this release carries a sensitivity and a specificity arm for that reason.

**No control was ever bypassed.** Every hook firing was reworded to a literal-path equivalent running the identical query; `CLAUDE_HOOK_BYPASS` was not set at any point. Two Tier-0-blocked files were delivered operator-side. A leak scan across 14 top-level names, 266 path segments and 2,555 filenames confirmed **zero** project identifiers reached this public repository — every per-file reference uses an opaque `sha256(path)[:12]` key.
