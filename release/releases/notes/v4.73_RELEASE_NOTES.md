# Updates and safety guards now follow what they govern, not where they start

2026-10-04 · v4.73

Running the update from a working copy no longer writes that copy's location into your installed settings, an unattended install no longer waits for input, and the skill-edit exemption list now lives in one place. The safety guards now decide by the file being written rather than the folder a session started in, which also lets an agent move an old memory entry to the Trash.

> **Skip the rest** unless you run the update or the installer yourself, work in more than one working copy of the platform, keep your own entries in the skill-edit exemption list, or run the platform's test suites.

## Who this affects

- Operators who run the update or the installer, especially from a working copy other than the main checkout, or unattended
- Anyone whose sessions work across more than one working copy of the platform
- Operators who keep their own entries in the skill-edit exemption list, or whose memory location is set in their user settings
- Platform builders who run the hook and install test suites

## What you need to do

1. **Run the update from your main checkout** (`./update.sh`). It installs this release's guards, rebuilds your installed allowlist on the main checkout, moves the old copy of the exemption list aside when everything in it is already in the new list, and refreshes the version this workspace reports.
2. **Only if the update names an exemption entry with a command to re-add it:** run that command. The old copy stays in place until every entry it holds is in the new list, and each update names what is still missing.
3. **Only if the update stops with exit code 75, naming the exemption list as missing:** run the installer (`./docs/scripts/setup-workspace.sh`) to put the list in place, then run the update again.
4. **Only if a session started inside a working copy needs to change a file in your main checkout:** start that session in the main checkout instead. The guard now refuses that cross-copy write.

## What changed for everyone using the platform

- **The update binds your install to its main checkout, wherever you run it from.** Running the update or a settings refresh from a working copy used to write that copy's location into your installed allowlist, where it stayed after the copy was deleted. Your settings now come out the same whichever copy runs the refresh, and every run prints one line naming the checkout it used and where that answer came from. *Why it matters:* a refresh from a temporary working copy can no longer leave your safety allowlist pointing at a folder that no longer exists, and an install that already carries such a path is repaired by its first update after this release.

- **An unattended install no longer waits for an answer.** With the non-interactive flag, the installer never stops at a prompt, even when nothing closes its input. Where it would otherwise have to choose a recovery for you, it now changes nothing, says why, and exits with code 66. *Why it matters:* a scripted install either finishes or stops with a stated reason, instead of hanging until something kills it.

- **The skill-edit exemption list has one home.** The installer, the update, the command that adds entries and the skill-edit guard now read and write the same file, in your platform working-files folder. The update moves an old copy aside only when everything in it is already in the new list, and it stops before installing new guards if the list is missing. *Why it matters:* a skill you add to the exemption list is now actually exempt, where before the guard could read a different file and refuse the edit anyway.

- **The write guard judges the file being written.** The guard that protects your main checkout's platform files now decides by where the file is, not by which folder the session started in. A write into a working copy is allowed from any session, a write into the main checkout's protected files is refused from any session, and roadmap files can now be written from a session in the main checkout. *Why it matters:* a session started in a working copy can no longer change your main checkout by accident, and writes that were refused only because of where a session started now go through.

- **An agent can now move an old memory entry to the Trash.** When your memory location is set in your user settings, the deletion guard lets an agent move one memory entry at a time to the Trash, and records each such move in its log. Deleting a memory entry outright is still refused, and the refusal names the Trash command to use instead. *Why it matters:* retiring a memory whose content now lives in the platform no longer needs you to run the command yourself, and the move can be undone from the Trash.

- **The install test suite tells the truth when it runs in a sandbox.** The standing install regression now passes under a temporary home folder as well as under your real one, stamps each verdict with the environment it ran in, and reports a safety check with nothing to check as skipped rather than passed. *Why it matters:* a passing result now means the checks ran against something real.

- **The hook test layout builds where its documented commands expect it.** The helper that prepares the hook test suite now builds inside the checkout by default, so its two documented commands run without being refused, and it flags a layout that is stale or that a test run changed. *Why it matters:* running the hook tests the documented way no longer trips the platform's own script guard.

## Known limits

- The single exemption-list location holds on the default workspace folder, or on one passed to sessions through the workspace-root setting. On an install that moves its workspace without passing that setting, or that sets the working-files location for the install's shell but not for sessions, the checks and the guard can still read different copies. Both cases refuse an exemption rather than grant one, and they are tracked in [#7654](https://github.com/cody-hutson/pmo-platform/issues/7654).
- The install record's new entry, which names where its checkout came from, is written the next time the installer runs. Until then, an older record is used only when it agrees with the checkout's own repository; otherwise the update warns, names both locations, and uses the checkout's repository.
- An update now refuses to run, with exit code 65, when it cannot tell which checkout the install belongs to, for example from a copy that is not a git checkout and has no install record. The message names the reason and the fix.
- The memory Trash move applies only when your memory location is set in your user settings. A location set only in a project's settings, or the default per-project location, still goes through the manual handoff, as does an entry whose name or folder path carries a character the shell would change.
- A workspace picks up this release when the update next refreshes its guards and its allowlist. This workspace was refreshed at release time, and each changed guard file was checked against the merged source.
- The version this workspace reports changes to v4.73 on the first update after this release closes. Until then, the start-of-session notice may offer v4.73 as available.

Report issues at https://github.com/cody-hutson/pmo-platform/issues, and report a suspected vulnerability privately as the [Security Policy](https://github.com/cody-hutson/pmo-platform/blob/main/SECURITY.md) describes.

## Reversibility

MODERATE / HIGH. The release is a single merge, so reverting it restores the previous behavior; a workspace then needs its guards refreshed from the reverted source and its settings rebuilt from the main checkout. Reverting the write-guard change reopens writes from a working copy into the main checkout, an exemption-list copy that was moved aside can be restored from its backup, and memory entries already moved stay recoverable from the Trash. The version tag stays in place as the record that the version was claimed.

### Operator and engineering detail

**Root resolution.** `[PMO_PLATFORM_ROOT]` now resolves through five tiers, first valid tier wins: `cli`, `env`, `install-record`, `declared-source` and `main-worktree`; when none resolves, the composing write fails. A linked worktree maps to its repository's main working tree, and every tier refuses a linked worktree, a `.claude/worktrees` path segment, a glob metacharacter, a control character and, on POSIX, a backslash. `update.sh` resolves once, in pre-flight, prints `INFO: Resolved [PMO_PLATFORM_ROOT] = <root> (source: <tier>); templates are read from <checkout>`, and exits 65 when no tier yields a root. The allowlist template changed in this release, so every install regenerates its allowlist on the first update after it, with a pre-write backup. The decision is recorded in ADR-214.

The installer now records the tier alongside the root in the workspace's install record. Two of the record's keys after an install under this release (values illustrative):

```json
{
  "source_repo_path": "<absolute path of the main checkout>",
  "source_repo_path_source": "declared-source"
}
```

A record without `source_repo_path_source`, written before this release, is advisory: it is used only when the `main-worktree` tier cannot resolve or agrees with it.

**One exemption-list path.** A resolver pair in `core/deploy/lib-instance-path.sh` gives the skill-editor exemption list one instance-tier path for the installer, `update.sh`, `allowlist-add.sh`, the Gate 2 skill-edit hook and `deploy.sh` Checks 6 and 10. The update's completeness gate now stops with exit 75 on an absent member of the declared hook-read set, before the hook refresh. A new Phase 5c1, after the hook refresh, moves a lossless legacy hook-tier copy to the pre-update backup and keeps a copy with extra entries, naming each with the writer command; `--surfaces-only` runs no reconcile. The decision is recorded in ADR-215.

**Target-keyed write guard.** `BLOCK-DESTRUCTIVE-019` now keys on the write target, read both as written and as resolved, never on the session's working directory. Its three exemptions — a target inside a repo-rooted worktree (a `.git` leaf excluded), the analysis workspace, and the roadmap instances — apply only when both views agree, and a `.` or `..` segment excludes all three. Three shipped test arms invert, as approved at the scope-lock, and the block message names the refused target.

**Memory-store arm.** `block-rm-prefer-trash.sh` admits a Trash-verb move of one direct `*.md` entry of the store declared in the user-scope `autoMemoryDirectory` setting: an absolute operand, bare or wholly quoted, with no `..`, naming a regular file that is neither the `MEMORY.md` index nor a symbolic link. Each admission appends one `memory-evict-admit` row to the hook's block log, carrying the command's digest and never its text, and an admission whose row cannot be written is refused. `rm`, `rmdir` and `unlink` on an entry stay refused as `BLOCK-TRASH-001`, with a message naming the Trash move. Tier-0 item 8 is re-scoped, with the eviction as item 8a at Tier 1. The decision is recorded in ADR-216.

**Unattended install.** The installer's three human-answer prompts are guarded by `--non-interactive`, and a census arm in the durability suite checks that every human-answer read stays guarded. Guided recovery under the flag exits 66 with nothing modified, naming the schema-mismatch trigger.

**Test suites.** The install regression's verdict line now carries `[env: <home-account|home-override|home-unresolved>; skipped: <N>]`, and the durability member's live-install proof takes its subject from the account home and skips an empty subject. CI gained a HOME-override step and an open-stdin observer. The hook-suite layout helper builds at the checkout root, with an ownership marker, a recorded footprint, a freshness digest and a purge.

**Decision records.** ADR-214, ADR-215 and ADR-216 were ratified as Accepted at this release's close.
