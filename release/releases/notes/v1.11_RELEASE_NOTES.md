# Workspace cleanup is now self-protecting and finishes in one pass

2026-06-12 · v1.11

The workspace cleanup sweep — the tool that removes merged release branches and leftover worktrees at every release close — can no longer delete the worktree it is running from or one a live session is using, and a single apply pass now finishes the whole job. Protection comes first: every removal is re-checked against live process state seconds before it happens.

> **Skip the rest** unless you run the workspace cleanup sweep (directly or via a release close).

## Who this affects

- Anyone who runs the orphan-state cleanup sweep — directly, via the release-close step, or via an agent session that invokes it
- Release operators and Stage 13 close sessions (the sweep runs at every release close)

## What changed for everyone using the platform

- **The sweep can no longer delete the worktree it is running from.** Its own runtime worktree is classified as protected and survives every apply, including a forced one. *Why it matters:* a cleanup launched from inside a worktree can't destroy its own session mid-run — previously the running session's directory could qualify for removal.
- **Worktrees held by any live process are off-limits.** The sweep maps which directories live processes are actually working in (an all-process scan, not a lock-file guess) and skips them; when that scan is unavailable, the affected removals are blocked rather than guessed. *Why it matters:* a concurrent session's workspace can't be deleted out from under it, and the safety degrades toward refusal, never toward deletion.
- **Every removal is re-checked seconds before it happens.** Liveness is verified again at apply time, not just when the report was generated. *Why it matters:* a session that starts between the report and the apply is still protected.
- **One apply pass now finishes the job.** Branches freed by the same run's worktree removals are removed in that run, through one bounded re-evaluation. *Why it matters:* no more running the sweep twice to reach a clean workspace.
- **The self-test now covers the destructive path end-to-end.** Three new fixtures exercise the self-protection, the live-holder skip, and the single-pass completion against real git state, on top of the preserved apply-path guards. *Why it matters:* regressions in removal behavior get caught by a ten-second self-test instead of by a lost worktree.

## Known limits

- The liveness check keys on process working directories: a process holding a worktree only through an open file (with its working directory elsewhere) is not detected. This boundary is a documented, accepted residual with a 30-day re-triage criterion — any protection miss of that shape escalates the check to a wider predicate (decision record ADR-021).
- The check's self-canary proves the scan ran, not that it saw every process — paired with the block-when-unavailable behavior above, a degraded scan refuses removals instead of risking them.
- Follow-ups filed rather than fixed here: duplicate branch rows under the widest sweep scope, a truncated help text, two unregistered invocation forms in the script-execution allowlist, per-branch lookup performance, protect-list seeding on fresh installs, and harness-branch sweep coverage (issue numbers in the References below).

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. A single `git revert -m 1` of the release pull request restores prior behavior — one code file plus one new decision record and three doc edits, no data migration, and all new protections are classification-side. The release's own close ran the new sweep first under a halt-revert-rerun guard, and the standard 30-day outcome window applies.
