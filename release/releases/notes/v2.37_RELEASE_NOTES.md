# Published release notes can no longer silently drift from the note we wrote

2026-06-28 · v2.37

The release-notes close-out is now hardened so the public release page matches the note in the repo and the close-out checks run no matter how a release is finished. Two un-checked gaps that let a release page ship with a bad title or a broken link are now caught, and a separate safeguard makes sure a shortened work-item checklist can no longer quietly skip a close-out step. Nothing changes for project work, status outputs, or artifacts — this is internal release-pipeline hardening.

## Who this affects

- Anyone who reads a published release note on GitHub, and the operator finishing a release. No effect on project artifacts, trackers, status outputs, or any command.

## What changed for everyone using the platform

- **The published release page now stays faithful to the note we wrote.** When a release is published, its public page is now rebuilt directly from the source note every time, and a check confirms the two match afterward. *Why it matters:* a wording fix or correction to a release note actually reaches the page people read, instead of the page going stale while the repo copy is correct.
- **Release notes are checked the same way no matter how a release is finished.** The release-note quality check now runs on every way of closing a release, not only the scripted one. *Why it matters:* a release closed by hand can no longer ship a note that skips the checks, so what you read is held to the same standard regardless of how it shipped.
- **More note defects are caught before they reach you.** The note check now also catches a release page whose title is missing its version and links that work in the repo but break on the published page. *Why it matters:* you get a correctly-titled page with links that actually resolve, instead of finding the breakage after the release is out.
- **A shortened work-item checklist can no longer quietly skip a close-out step.** A new safeguard confirms a finished release produced its full set of close-out records, independent of how the work was tracked. *Why it matters:* releases can be reported "done" only when they actually are complete, so a missing release page or record gets caught at close instead of weeks later.

## Known limits

- These are release-pipeline checks and guidance; they change how releases are finished and verified, not any project-facing behavior, artifact, or command.
- The completeness safeguard is logged but not blocking at first, and applies only to releases finished after this one — it does not retroactively flag past releases.
- The completeness safeguard reads a release's recorded outcome; a close that never wrote its release-log entry at all is outside what it can see (that remains a separate close-time check).

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:pipeline` label.

## Reversibility

CHEAP / HIGH confidence. Every change is a tracked governance, standard, lint, or check edit plus one founding decision record; reverting the integration PR restores the prior text and removes the new check in one step. The completeness check ships logged-but-not-blocking, so reverting it unwinds no live enforcement. No data migration, no stored-content move, no change to any existing project surface. Standard rollback window.

### Operator and engineering detail

**Lint coverage for the posting defects the structural check missed (#2120).** `release/references/standards/release-notes-standard.md` reconciles the three un-versioned title-format descriptions (§5.2 / §5.3 / §5.5 State-0) and the un-versioned `--title` cell in `stage-12-execute.md` to the single canonical `vX.Y — <headline>` form (matching the already-correct bash exemplar), and the §3.1 template's repo-relative plan link is fixed to the absolute `https://github.com/{REPO}/blob/main/...` form so newly-authored notes pass the link check. A new whole-body link-purity lint (check 13) in `core/deploy/tools/lint_release_corpus.py` flags any repo-relative markdown target anywhere in the frontmatter-stripped body — the bytes that publish to the GitHub Release surface — while still permitting `https://`, intra-page `#anchor`, and `mailto:` targets (it discriminates, not a blanket ban). The Stage 13 close runbook (`hub-spoke-bridge.md` Procedure 7 + `stage-13-close.md` Phase B5.6) gains two `gh release view`-based assertions on the LIVE Release — that the posted title is versioned and the posted body carries no repo-relative link — which the in-repo structural lint cannot see. The eval rubric is synced from 12 to 13 checks to agree with the lint and the standard.

**The §3.2 note-content lint is now bound to the close EVENT, not a single skill path (#2082).** The note-content conformance check previously ran only on the `release-executor` self-lint path; an abbreviated hub-direct close could ship a non-conformant note and still close the milestone. The lint is now wired into the `automated-closeout.sh` close phase (`phase_lint_release_notes`, between note-scaffold and the chore commit) AND named at the hub-direct / Phase-B chore-PR fallback's Step 4 verification (the path that runs no script). On every path, a finding naming the closing version blocks milestone close, while a pre-existing finding for an unrelated version does not (audit-baseline discipline). This is the RCA fix for the v2.26 governance failure — the rule existed but was unenforced on the hub-direct path.

**Deterministic Release-body re-emit + standing drift gate (#2085).** The published Release body is now an enforced deterministic transform of the in-repo source note (frontmatter-stripped via `sed`), never a hand-assembled string, applied identically on the script path and the spoke path; the §5.5 State-machine emit and the §5.6 post-VERIFIED correction procedure are reconciled to that stripped-body form. A standing detective gate (`release/tools/check-release-body-drift.sh`, surfaced by `deploy.sh` Check 47 and the post-emit verification phase) asserts `published body == strip_frontmatter(note)` after the fact — it flags drift, it never re-emits (auto-remediation would raise an autonomy-tier decision). This closes the gap the v2.26 close exposed, where a hand-assembled body diverged from the note and stayed stale through a correction PR.

**Rigor is an invariant of scaffolding; a scaffold-independent completeness gate (#1290, ADR-048).** A work-item scaffold selects which tasks exist for a release; it must never attenuate the rigor of any task's codified checklist. Absorbed into this release: a named Rigor-Invariance Principle and a canonical-checklist attestation at the Procedure 1 scaffolding seam (with a hub-direct ≡ spoke equivalence clause — collapsing stages waives no codified step), plus `deploy.sh --check` **Check 48** and a verdict-driven `--check-close-completeness` CI probe sharing one body. Check 48 is an umbrella invariant that asserts the complete canonical Stage-13 output set on main for every `VERIFIED` `RELEASE_LOG` row at/after its cutover, delegating each sub-assertion to the engine that already owns it (note-content to the corpus lint, body-drift to the drift tool, companion-presence to the existing path resolution) — composing, never duplicating. It reads main's state, not the path that produced it, which is scaffold-independence by construction. It ships warn-mode-initial and dormant-by-default behind a cutover sentinel, so it does not retroactively flag historical rows and has zero blocking impact until an operator opts in. Founding decision recorded in [ADR-048](https://github.com/cody-hutson/pmo-platform/blob/main/core/ADRs/ADR-048-rigor-invariant-of-scaffolding-close-completeness-gate.md).

**Reflexive-loop posture.** v2.37's own new close-out gates — the close-event lint binding (#2082), the drift gate (#2085), and Check 48 (#1290) — are cutover-anchored strictly AFTER this release's merge, so they do not gate v2.37's own close (the reflexive-pipeline-loop discipline). The `.version` stamp (v2.36 → v2.37), the CHANGELOG append, and the `chore/v2.37-stage-13-closeout` branch are the manual completions the automated close-out tool drops for theme-named (non-version-named) milestones, completed in this Stage 13 close-out.
