# Release records are now complete, and the check that proves it actually runs

2026-08-01 · v4.03

One shipped release was missing from every record the platform keeps of what it has released, and the automatic check meant to catch exactly that had never once evaluated — it was reporting a pass that only meant "did not run". The missing release is now recorded, the check now runs against real entries, and the wrap-up step that writes those records is harder to leave half-finished.

## Who this affects

- Anyone who looks up what a past release changed, or relies on the release history being complete.
- Anyone who runs a release and depends on the close-out step to write the records correctly.

## What you need to do

- **Run the platform deploy step before your next release close-out.** This release added a new close-out tool and registered it as permitted to run, but that permission list only takes effect in your installed copy after a deploy. Until then a close-out that reaches for the new tool will be refused. Running the normal deploy for your workspace clears it; nothing else is required, and no data is affected.

## What changed for everyone using the platform

- **A shipped release that was missing from the history is now in it.** One past release had shipped without being written into any of the four records the platform keeps — the log, the index, the summary digest, or the changelog — and had no written notes of its own. All five are now present, and the index and log now agree on 150 entries each where the index had been one short. *Why it matters:* asking what that release changed now returns an answer instead of silence, and the two records that are supposed to match each other now do.
- **The completeness check now actually runs.** The check that asks "does every finished release have its full set of records?" depended on a setting that nothing in the project ever supplied, so it had been quietly skipping every release since it was built and returning a pass that meant only that it had skipped. It now ships with that setting built in, and reports how many releases it examined so a pass with nothing examined can no longer look like a pass. *Why it matters:* the safeguard against incomplete release records is now doing the job it was added for, rather than being a green light nobody could tell was switched off.
- **The wrap-up step refuses to continue on an unwritten release note.** It used to accept a release note that was still a blank template, so a release could be published with placeholder text where its summary should be. It now stops and names the exact placeholder and line it found, and it accepts a note you wrote in advance instead of overwriting your text. *Why it matters:* a published release stops being able to carry an unwritten summary, and writing the note first is now a supported way to work rather than something the tool undoes.
- **A record-count check no longer passes when it cannot count.** The comparison that confirms two release records hold the same number of entries used a counting method that returned a broken value when one record was present but empty — and a broken value was being read as agreement. A genuinely empty record against a full one now reports the mismatch. *Why it matters:* the worst case, where a record exists but has lost its contents, was the one case this check was silently passing.
- **The close-out learnings write-up is now produced for you.** The per-release reflection document had to be assembled by hand from a template each time. A tool now creates it, pre-filled with the release's own three recorded observations and its reference table, and deliberately leaves the lessons and follow-up-action rows blank for a person to write. *Why it matters:* the document gets created every release instead of only when someone remembers, and the parts that are supposed to represent human reflection still say so honestly rather than being machine-filled.
- **The close-out no longer fails when the release records live outside the project folder.** Installations that keep their release records in a separate location were getting a hard failure from a path check that treated "not here" as "broken". It now records those as not applicable and carries on, while still failing on a genuinely broken path. *Why it matters:* a supported way of arranging your files stops being reported as an error, without weakening the check that catches real ones.

## Known limits

- **The completeness check reports but does not stop anything yet.** It is switched on and logging, but a finding does not block a release. Turning it into a blocker is a separate decision, and needs both a review of its log and a change to the repository's required-checks settings.
- **Two parts of that check remain switched off.** Its checks on the published release page and on whether that page still matches the written note are governed by a second setting that has not been turned on. They are not evaluating.
- **The check confirms the records exist, not that they are complete in every field.** Two entries the close-out is supposed to write — the delivery-throughput line and the three recorded observations — are neither written by the close-out tool nor checked for. A release can pass the completeness check while missing both; this release wrote both by hand.
- **Two known record-history repairs were deliberately left for later.** Correcting a past release's mis-tagged author identity, and clearing four stale references in the release-anchor set, were both kept out of this release and are tracked separately. The check that would flag them ships with those four entries listed as known exceptions.
- **The tolerance test suite does not model every supported layout.** It now catches resolvers that quietly do nothing, but it grades one genuinely supported file layout as a failure because its test fixture never creates that layout. That is a gap in the test, not in the behaviour it tests.
- Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:pipeline` label.

## Reversibility

CHEAP / HIGH confidence. Reverting the single integration commit reverses everything in this release at once: the two scripts and the checker return to their previous behaviour, the completeness check returns to skipping, and the restored history entries return to being absent. Nothing was migrated and no stored data was transformed, so nothing needs rebuilding in either direction. One surface is worth naming: the changes sit in the close-out path that every release runs, so re-run its self-test after any revert. Standard 7-day rollback window.

### Operator and engineering detail

**The gate was dormant because its cutover literal had no carrier.** `CLOSE_COMPLETENESS_CHECK_CUTOFF` was read from the environment by `deploy.sh` Check 48 and set by nothing in the repository — no workflow, no sentinel, no default. Check 48 had therefore returned exit 0 with zero rows in scope on every run since it shipped, which is byte-indistinguishable from a clean verdict. Per **D-E** the carrier is now a committed default in `core/deploy/deploy.sh`, and the check reports its *resolved* row count and *resolved* arm row at runtime, so a mis-set cutoff surfaces as a wrong number rather than as silence. The arm row is `v3.89`, chosen on **calibration integrity** rather than on blocking: the sentinel reads `warn` and the probe exits 0 at `v3.69`, `v3.88` and `v3.89` alike, so an earlier arm would not have reddened this release's PR — it would have pre-poisoned the warn log with known legacy debt and destroyed its value as evidence for the later flip to enforce. The Stage-4 rationale asserting the opposite was disproven and corrected on the record (Deviation 6). One derived hard bound survives: because Check 48 iterates `RELEASE_LOG` rows, it is structurally blind to a release that never wrote one — which is why the backfill had to land first and the check be armed against the final ledger, reversing the originally-planned sequence.

**The backfill shipped five artifacts where the criteria named four.** Per **D-J**, `release/releases/notes/v3.69.1_RELEASE_NOTES.md` was authored despite the release-notes standard's File Location clause stating that a hotfix emits no separate notes file. Both prior patch releases carry one and every `RELEASE_INDEX` row carries a resolving notes link, so the clause is inconsistent with its own corpus; reconciling it was routed to intake rather than done here (Deviation 9). Index-to-log row parity moved 149/149 to 150/150, and that parity is now itself a regression guard.

**`grep -c` was the shared root cause of a fail-open.** A zero-match `grep -c` prints `0` *and* exits 1, so the common `... || echo 0` fallback emits a second `0` and captures the two-line string `0\n0`; the subsequent `[[ "$x" -ne "$y" ]]` then raises a syntax error, and a failed arithmetic test evaluates false, taking the PASS branch. A *missing* ledger failed correctly; a *present-but-empty* one — the worse case — passed clean. All three defective sites now route through a single `grep_count()` helper whose contract is one integer or a preserved missing-file failure, and the self-test drives it against a present-but-empty ledger so the idiom cannot be reintroduced.

**The register producer seeds; the operator authors.** Per **D-G** the producer is a standalone tool rather than a phase inside the close-out script — a recorded override of the reuse-first default. It preserves every canonical section marker verbatim, fills the triple-linkage table, inserts the release's `Surprise` / `Would-change` / `Watch-for` fields as labelled seed bullets, and never writes into an `L<n>` or `A<n>` row. That last constraint is a correctness property, not a style choice: the close-class telemetry read-model counts a populated lessons row as evidence of human reflection, so machine-filling those cells would make it report a fully-authored retrospective on a release nobody reflected on. An existing register is preserved rather than overwritten, so a resumed close cannot clobber operator prose.

What the producer writes, taken from this release's own register — a filled header, seeded prompts, and lesson rows deliberately left empty:

```
**Release version:** v4.03
**Milestone:** #304
**Close date:** 2026-08-01
**Release class:** novel
**Triple source-row anchors:** pipeline-event-log.md row(s) at ts 2026-08-01T11:22:14Z

**What did we learn?** (seed from the triple's `Surprise` field, then expand)
- [seed: triple `Surprise`] F3's hook-block never fired ...

| L1 | <…> | <…> | <…> |        <- lesson rows are never machine-written
```

**The release's own verification instrument was the last thing fixed.** Stage-8 QA falsified the corpus-home tolerance suite's arming rule: it armed on a purely behavioural proxy — *fixture A exits 0* — so five distinct non-conforming resolvers passed while resolving nothing, including one that crashed on absence and one degenerate universal acceptor, and one of those greens actively instructed the operator to harden the thing that was broken. The rule was replaced with a structural-or-behavioural disjunction plus two new assertions requiring a per-path resolution record rather than an exit code alone. All five falsifications now exit 1 naming the violated constraint; the fix was mutation-tested at 20 mutants over 22 rows with zero survivors. The governing standard's own text was reconciled in the same change rather than annotated, because it had documented the old rule verbatim — shipping a standard that misdescribes its own enforcement, inside a milestone about exactly that failure class, was not an option.

**One post-release defect was found and fixed before close.** For a release with no version number, the close-out script wrote its release-note scaffold to a flat path while three consumers read a different one, so the residue check silently saw nothing and the resume step rejected the script's own output permanently — and, unrecorded by either report, authoring the note did not clear it, because the blocking condition was the untracked flat path no tolerance names. The one-line behavioural delta needed three load-bearing co-changes to avoid shipping two new defects, and the path is now single-sourced so the six hand-kept copies of one rule cannot diverge again. Shipped as [#4430](https://github.com/cody-hutson/pmo-platform/pull/4430) at `620751d0`.

**Two declared artifacts did not land, and are recorded rather than absorbed.** The File Change Matrix declared one release-scoped ADR recording the self-arming conditional gate posture — a gate that ships armed by a committed default rather than deferring its arming to a step that can be forgotten. No ADR shipped in the release diff and the Deviation Log carries no entry removing it. Separately, `core/config/allowlists/script-execution-allowlist.txt` gained the new tool in the repository but the deployed copy is refreshed only by the platform deploy step, which is the operator action named above.
