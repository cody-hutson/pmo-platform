# Closing a release now reports what it actually shipped

2026-08-21 · v4.34

When a release finished, the record it left behind could disagree with what the release
delivered — and in the worst cases it disagreed silently. This release makes the closing
record match reality, and makes a close that cannot produce a complete record stop and say
so rather than finish quietly.

## What changed for everyone using the platform

- **A release's "delivered" figure no longer reads zero on a release that shipped everything.**
  *Why it matters:* seven past records show zero delivered against work that was fully
  delivered. That figure feeds how future releases are sized, so a wrong one quietly skews
  planning for every release after it.

- **A close that is missing part of its own record now stops and names what is missing.**
  *Why it matters:* a release could previously be marked complete while pieces of its record
  were absent — and the absence produced no message, no warning, and no failure. Nothing in
  the system would ever have surfaced it.

- **A close started before its lessons were captured now stops at the door, before anything is written.**
  *Why it matters:* it used to fail partway through with four files already changed, leaving
  you to undo them by hand. It now stops with nothing written and prints the single command
  that fixes it.

- **The closing record can no longer pick up a second result line that contradicts the first.**
  *Why it matters:* a repeat run could add a conflicting outcome beneath the original, leaving
  two different answers in the same record and no way to tell which one was current.

- **The close summary no longer prints two run references joined into a single number.**
  *Why it matters:* the joined value looked like a real reference and pointed at nothing, so
  anyone following it to check the work landed nowhere.

## Known limits

- **The planned-versus-delivered figure counts everything still attached to a release**,
  including an item finished in an earlier release and deliberately kept attached. For this
  release that adds 2 points to both sides of the figure, which is why it reads 16 rather than
  the 14 the five items delivered here account for. A durable record of what a release
  contained when it *started* does not exist yet, and that is the missing piece — noted here so
  a later reader does not mistake it for the defect this release fixed.
- **Recovering items removed from a release during closing is best-effort in both directions.**
  It matches on the release's name, and any removal naming that name counts no matter when it
  happened. Measured at a release's own close this cannot bite, because the removal and the
  close are the same step; it can bite when an old record is recalculated later.
- **One review finding was filed rather than fixed:** #5764 — a release check whose method
  cannot be satisfied as written, so it cannot be graded either way.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE**, confidence **HIGH**.

Reverting the release commit restores every changed file, and the tool changes carry no stored
state to unwind. The one part that does not revert cleanly is the corrected history: seven past
records had their delivered figures recalculated and annotated in place. Those corrections are
recoverable only because each states what it changed and why, rather than silently overwriting
the old number.

### Operator and engineering detail

Raw audit detail sits in the `v4.34` Deployment Log row; this is the narrative around it.

**The originating diagnosis was directionally right and mechanically wrong, and the correction
changed the fix.** The reported cause was ordering — the velocity measurement runs twenty
dispatch positions before the phases that close the members it counts. The real variable is
whether the release PR's close keywords resolved at Stage 12: when they did, members already
read CLOSED and the number was right; when they did not, the field booked zero. Any predicate
reading issue state inherits that split, so "run it later" was never the fix.

**The design's first answer was falsified by its own cited evidence.** Stage 5 proposed deriving
delivered from labels rather than state, and drafted the governing principle as *evidence
invariant across the close*. The independent adversarial review found that milestone membership
is not invariant: the close's own deferred-item step applies a terminal label **and then removes
the milestone**, and the design had quoted that step with an ellipsis over the removal. Its sole
counter-example was falsified three ways — both issues read `milestone=NONE` today, and the
timeline shows the removal preceding the label by one second, so the state the claim described
never existed at any instant. Measured across all seven affected rows plus this release's own
slice, the proposal would have pinned the ratio to exactly 1.00 everywhere: a loud, filed defect
converted into a silent, permanent one.

**What shipped instead recovers rather than assumes.** Delivered is now the current membership —
which *is* the shipped set, by construction of the deferred-item step — and planned is recovered
by reading removal events over the bounded terminal-status population. Those events are
immutable, which is what makes the figure identical across a dry run and a real run.
**ADR-137** records the restated principle: a measurement written during the close must
reconstruct what the close removes, not assume its evidence survives. Invariance is explicitly
rejected as the test — it is unachievable for a population the close is chartered to mutate, and
demanding it forbids every available design.

**Two skills were version-stamped in the closing commit rather than during the build.** Their
edits are material, but the correct value — the release tag — does not exist until the tag is
claimed at Stage 12. An earlier build wrote it ahead of the claim and it was reverted for exactly
that reason; the stamp is applied here, after the claim, as the sequencing the standard requires.

**Seventeen broken probes were caught and disclosed across this release** — by spokes, by
reviewers, and by the hub itself. The recurring shape is a zero whose control arm also returns
zero, which is not a finding but a broken instrument. That is this release's transferable
lesson, and it is recorded as the close's captured learning.

**Cycle-time reads N/A** — the Stage-9 GO was emitted under a decision subtype rather than the
gate outcome the measurement queries, so the anchor it needs was never written in the shape it
looks for. Unchanged from the prior release and tracked separately.
