# Releases now claim their version at the finish line, so two releases can't collide on a number

2026-06-21 · v2.16

A release no longer reserves its version number early and then hopes to still have it at the end. The number is now claimed atomically at the moment the release merges, against the live list of what's already published — so when two releases are in flight at once, the slower one can no longer silently lose its number to the faster one. This is foundation: it changes how the platform's own release machinery picks and locks a version, and it changes nothing about how project work, status outputs, or skills behave.

> **Skip the rest** unless you cut releases of the platform itself.

## Who this affects

- The workspace operator and anyone running the release pipeline. There is no change to how project work, status updates, or skills behave for everyday users.

## What changed for everyone using the platform

- **No change to everyday platform behavior.** This release reworks the release pipeline's version-claiming machinery, governance docs, and tooling; it does not change any skill output, status report, or decision a human makes day to day. <!-- impact:foundational -->
- **Releases stop colliding on version numbers.** When two releases are open at the same time, each now claims its number atomically when it merges rather than reserving it up front, so neither silently overwrites the other's slot. *Why it matters:* a release you're shipping can no longer quietly lose its version to a faster one that merged first — the number it ends up with is the number that actually got locked.

## Known limits

- The mechanism is defined to be host-agnostic (a config-selected release-host adapter), but GitHub/git ships as the only reference adapter in this release; other hosts are gated on their own adapter tickets.
- If two releases still race for the same number, the loser is told to recompute and claim the next free one — the new CI freeness check and the machine-readable re-version ledger make that case detectable and auditable, but a contended slot is reconciled by re-claiming, not by reserving ahead of time.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. Every change is additive — corpus standards, two founding ADRs, new release-claim scripts, and one CI freeness workflow; no skills or packages changed. Reverting the release merge restores the prior state exactly; no data migration and no skill rebuild are required.

### Operator and engineering detail

**Version-claim contract + host adapter (#1697, #1675, #1673)** — the founding ADR (ADR-036) records the determinism contract: slug-primary identity, intent-to-bump in-pipeline, defer-to-claim, atomic compare-and-swap at the merge tag, defense-in-depth. The capability is defined as host-agnostic via a `repo_host` adapter exposing four operations — `anchor()` / `claimed_set()` / `atomic_claim()` / `lineage()` (`core/standards/repo-host-adapter-versioning.md`), selected through `operator.toml [adapters].repo_host`. GitHub/git is the v1 reference adapter (`anchor()` = `releases/latest`; `atomic_claim()` = signed-tag ref-CAS push), and the new `release/tools/claim-version.sh` implements the atomic ref-CAS claim-with-retry. The authoritative allocation rule reconciles the semantic-bump doctrine with `git describe` practice. This very release dogfooded the path: v2.16 was claimed Tag-SHA-Direct on the merge SHA after a final ref-CAS next-free re-verification (v2.13/v2.14/v2.12 were already held by sibling releases; v2.16 was the free slot above the v2.15 ceiling).

**Grammar, semantics, and the contended-axis model (#1676, #65, #66, #1674)** — a canonical version grammar (X.Y / X.Y.Z / suffix) is applied to the freeness checks (`release/references/standards/version-grammar.md` + `release/tools/version-grammar.sh`), milestone-numbering semantics gain a chronological caveat (`core/standards/version-field-semantics.md`), parallel-release semantics are specified (the v-number is a slot identifier; ship-order = merge-order), and the version number is modeled as a contended axis in the cross-release impact model (extending ADR-024, recorded in ADR-037).

**Pre-merge + CI defense-in-depth (#769, #1008, #1677)** — the Stage-12 pre-merge check now re-verifies the version is still unclaimed against fetched/authoritative refs (not just file/gate divergence), the hub D-Version check verifies next-free against authoritative refs and re-verifies at Commit 0, and a new CI workflow (`.github/workflows/version-freeness.yml`, with `release/tools/test_version_freeness.sh`) gives proactive pre-merge collision observability.

**Recovery, ledger, and close-out doctrine (#1678, #1679, #1092)** — a post-tag re-version recovery doctrine covers orphaned-tag/ledger reaping (`release/references/how-to/re-version-recovery.md`), a machine-readable re-version ledger (`release/releases/RELEASE_REVERSIONS.md`) makes collisions auditable, and the concurrent-release Stage-13 corpus conflict-resolution doctrine is documented in `stage-13-close.md`. The close-out tooling (`automated-closeout.sh`, `cleanup-orphan-state.sh`) was reworked for the slug-primary identity. Source observation **#950** (version assigned at Stage 4 but claimed at Stage 12) closes as the fixes land.

**Pipeline-context note** — this release carried provisional-display v2.16 throughout and claimed v2.16 at the merge tag; the claim was confirmed free one final time against authoritative refs immediately before the signed tag was created. For full implementation detail see the [RELEASE_LOG.md entry](../RELEASE_LOG.md#deployment-log-v216) and [the release plan](../plans/release-version-claim-determinism_RELEASE_PLAN.md).
