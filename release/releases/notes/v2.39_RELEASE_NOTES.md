# The platform now audits itself on a schedule and remembers where its advice differed from your call

2026-06-29 · v2.39

The platform's self-checks no longer depend on someone remembering to run them: there is now a written schedule that says when to re-run each kind of health audit, triggered by specific events with a regular fallback if no event fires. The platform also starts keeping a record of the moments where the agent's recommendation and your actual decision differed, so that pattern can be reviewed later instead of being lost. This is internal release-pipeline and platform-maintenance work — nothing changes for project work, status outputs, trackers, or artifacts, and the new record only observes; it never changes anything on its own.

## Who this affects

- The workspace operator and anyone auditing platform health or reviewing release retrospectives. No effect on project artifacts, trackers, status outputs, or any command.

## What changed for everyone using the platform

- **The platform's self-audits now run on a defined schedule instead of when someone happens to think of it.** Two kinds of health check — one for whether the release process still matches established delivery practices, one for whether the documentation structure is still sound — now each have a written rule for when to re-run them: specific events that trigger a check, plus a 90-day fallback if no event has fired. *Why it matters:* the platform's health gets re-checked on a dependable rhythm, so drift is caught on a cadence rather than only after it has become a visible problem.
- **All three of the platform's audit types are now discoverable from any one of them.** The two new schedules and the existing one (which checks platform features against the toolkit they build on) now cross-reference each other as one connected set. *Why it matters:* finding one audit's schedule leads you to all of them, so no axis of health checking is overlooked because it was tracked off on its own.
- **The platform now keeps a record of where its advice and your decision differed.** At decision points where the agent makes a recommendation, the platform can now log the agent's recommendation alongside the choice you actually made and a short note on why they differed — and a look-back view can summarize those differences across recent releases. *Why it matters:* a fresh session can see, unprompted, where the platform's judgment has been diverging from yours, so recurring blind spots surface instead of being lost between sessions.

## Known limits

- These are release-pipeline and platform-maintenance changes; they govern how the platform audits itself and captures learning, not any project-facing behavior, artifact, or command.
- The recorded recommendation-vs-choice differences are a read-only signal: a recurring pattern is surfaced for review and, if it repeats, raised as a proposed improvement through the normal governance path — it never changes the platform on its own.
- The audit schedules and the learning roll-up apply to releases and audits going forward; this release that introduces them does not retroactively run them on itself.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:pipeline` label.

## Reversibility

CHEAP / HIGH confidence. The changes are two new reference documents, one new optional record type with a read-only look-back, and a small edit to one pipeline reference; reverting the integration PR removes them in one step with nothing to migrate. The new record only observes — it never changes anything automatically — so removing it unwinds no live behavior. No change to any existing project surface. Standard rollback window.

### Operator and engineering detail

**Release process-fitness audit cadence (#167).** A new protocol, `release/references/protocols/process-fitness-cadence.md`, defines the *when-to-re-run* policy for the release process-fitness audit — the recurrence layer that sits on top of the how-to-run methodology in `core/standards/AUDIT_FRAMEWORK.md` (it adds triggers and a fallback; it does not restate the dimensions or scoring). The audit tests whether the release pipeline still conforms to its external delivery-process reference frames (PMBOK 7, DORA, Stage-Gate, ITIL 4, Lean, CD). Three event triggers fire a re-audit: a major change to the pipeline definition, a retrospective surfacing a Tier-2+ process-fitness concern, or a new methodology archetype being added. A 90-day time-based fallback covers the no-event case.

**Structural audit cadence (#168).** A second new protocol, `release/references/protocols/structural-audit-cadence.md`, applies the same cadence-not-methodology split to the structural audit (the Session 1 "Structural & Behavioral Audit"). It governs Diátaxis information-typing, NARA / ISO 15489 naming, orphan-file detection, and cross-reference integrity. Three triggers: a milestone close that touched the tree, a release start, or a major taxonomy change. A continuous-vs-periodic note records that the link-check CI gate already covers cross-references continuously, so this 90-day cadence is the periodic deep pass across all structural dimensions.

**3-axis audit-cadence cross-reference (shared).** `release/references/protocols/platform-health-audit-framework.md` gains a sibling-axis paragraph establishing that its §2 cadence is the Anthropic Base-vs-Build axis — one of three sibling audit-cadence axes alongside the new process-fitness and structural axes. Each carries a distinct benchmark roster and triggers, and the three mutually cross-reference so the full audit-cadence surface is discoverable from any one of them.

**Recommendation↔choice delta capture surface (#46).** A new `recommendation-choice-delta` `event_subtype` is added under `event_type=decision` in `release/references/standards/pipeline-event-log-schema.md` § 3. It reuses the schema's existing ten columns — no new fields — with the delta-tuple carried in the `payload`, keyed `rec:` (the agent's prior recommendation), `chose:` (the rendered operator choice), `delta:` (one of `aligned` / `diverged` / `partial` / `operator-deferred` — `aligned` records the zero-delta state explicitly), `why:` (divergence rationale), and `via:` (provenance). The subtype composes with the decision-confidence pause-to-learn surface and the learnings-triple synthesizer rather than duplicating them. A sample pair of rows:

```markdown
| 2026-06-29T14:00:00Z | v2.39 | 4 | decision | recommendation-choice-delta | hub | milestone:#N | CHEAP | resolved | rec:bundle-A+B; chose:bundle-A-only; delta:diverged; why:B-blocked-on-dep; via:stage4-bundle |
| 2026-06-29T14:00:01Z | v2.39 | 5 | decision | recommendation-choice-delta | spoke:#N | #N | CHEAP | resolved | rec:new-subtype; chose:new-subtype; delta:aligned; via:stage5-design |
```

**Look-back read + Stage-13 roll-up (#46).** `release/tools/query-pipeline-event.sh` gains a `--window N` flag that restricts matched rows to the trailing N distinct version tags (positive-integer validated). `release/tools/append-pipeline-event.sh`'s subtype-validation enum is extended to accept the new subtype. A new Stage-13 **Phase A7.1** in `release/references/pipeline/stage-13-close.md` rolls the release's `recommendation-choice-delta` rows (`diverged` first) into the F7 retro / lessons-learned register produced at close. The surface is signal-only: three or more same-pattern `diverged` rows across the trailing window promote to an `improvement.yml` candidate through the governance gate (issue → plan → PR), never an automatic change.

**Scope and reflexive-loop posture.** The bundle shipped #167, #168, and #46; #1097 was trimmed from the milestone, and the cross-chain architecture index (#912) was deferred as a different capability; the per-session-retrospective idea was filed as #2423 for a later release. The audit cadences' own triggers and #46's Phase A7.1 look-back are anchored to fire on releases and audits *after* this one, so v2.39 does not run them against its own close (reflexive-pipeline-loop discipline). Stage 12 for this release was completed as a remediation (the initial hub-driven merge landed without the tag-claim + DEPLOYED-row steps; root cause and the durable Mode-O fix are tracked in #2428).
