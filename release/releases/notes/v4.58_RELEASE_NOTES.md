# Release checks now match what the platform actually does

2026-09-06 · v4.58

Ten rules and checks in the platform's own release machinery described behaviour that the shipped code did not have, and several of them were reporting problems that were never there. This release reconciles each one against what the code actually does; the most visible effect is that a handful of checks stop raising false alarms.

> **Skip the rest** unless you run releases on this platform or read the checks it produces.

## Who this affects

- Anyone running a release through the platform's pipeline
- Anyone acting on the pipeline's planning, dependency or close-out reports

## What changed for everyone using the platform

- **Release planning no longer reports blockers that do not exist.** The check that asks whether a release is waiting on other work was matching keywords anywhere in an item's free text, so ordinary English like "depends on whether" counted as a dependency. Measured against this release's own ten items, the old form returned five blockers and the corrected form — which reads the item's declared dependency section — returns none. *Why it matters:* work is no longer held back waiting for a blocker nobody can find, and a genuine blocker is no longer buried among false ones.

- **A reference to a file that has moved is now caught before it ships.** The scan that finds references to files that no longer exist only looked at outright deletions, so a file that had been relocated still read as present and its stale references passed through. *Why it matters:* a path or link that would break after a reorganization is caught while it can still be fixed, instead of shipping broken.

- **Closing a release is no longer blocked by unrelated older debt.** One close-out rule swept the entire history and stopped the release being closed whenever anything anywhere was unresolved. It now looks only at the release actually being closed. *Why it matters:* a finished release ships on its own merits rather than waiting on someone else's backlog.

- **A test run no longer fails for a reason that is not real.** A required sandbox setting was making at least one class of test suite report a failure that had nothing to do with the code under test. *Why it matters:* a red result now means something is genuinely wrong, so it is worth stopping for.

- **A rule can no longer become blocking just because it fires often.** Promoting one of the platform's guard rules from advisory to blocking now requires evidence that it stops the right things, not only that it stops a lot of them — three rules accounted for 73% of 1,556 blocks with nothing recording whether those blocks were correct. *Why it matters:* a rule that interrupts you constantly without being right can no longer be made harder to work around on that record alone.

- **A local folder path no longer leaks onto a public page.** One command form used to publish text quietly posted the *path* to a file rather than the file's contents, which put a local directory path onto a public artifact. *Why it matters:* nothing about the layout of your machine ends up somewhere anyone can read.

## Known limits

- The new evidence requirement for making a rule blocking is recorded in the standard going forward. It does not by itself re-grade the rules already in place.
- One corrected check still overstates its own reason: the cycle-time tool reports that a deploy "did not succeed" when the deploy did succeed and simply had nothing of the kind it measures to deploy. The wording is recorded, not yet fixed.
- Several defects found while running this release — including one still-live instance of the same faulty range comparison — are recorded as follow-up candidates rather than fixed here.
- Six of the release plan's own verification rows were found to test for a word rather than for the property they claimed to check. They were re-graded against the design and the plan's tables are marked superseded; the rows themselves are left as written.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH confidence.** Reverting the release merge restores the previous corpus in a single operation. Nine rule files are also copied outside the repository by the deploy step, so a complete rollback needs a re-deploy as well as the revert. No data is migrated and no stored state changes shape, which bounds the exposure.

### Operator and engineering detail

**The unifying defect is a description that outran its mechanism.** Every one of the ten items is a governance or reference surface asserting behaviour the shipped code does not have — not a code defect with a documentation consequence. The dependency reconfirm query is the clearest case: it was published as the milestone-level procedure for answering "does this carry an unresolved dependency edge?", but it ran a keyword alternation over the whole issue body, so it was false-positive by construction on ordinary prose and false-negative by construction on the phrase members actually use to declare independence. Re-measured on this release's own ten members it returned five hits against zero real edges. The replacement reads the structured dependency section, where the answer is actually stated.

**The specificity criterion is the release's one genuinely new rule.** The gate-efficacy standard previously let a warn-mode rule graduate to enforcement on catch-rate evidence alone. Three syntactic hook rules accounted for 73% of 1,556 recorded blocks with no measure of whether those blocks were correct, which is precisely the shape a catch-rate-only criterion cannot distinguish from a well-targeted rule. Graduation now requires a specificity owner and a warn-mode drain, so volume alone is no longer a qualifying record.

**Two close-out surfaces were unscoped rather than wrong.** Procedure 4a step 6's BLOCK rule swept the whole population, so any release close inherited every other release's unresolved debt; and four corpus surfaces still asserted a signed tag and a published GitHub Release for a release identity that carries no version at all, which cannot produce either artifact. Both are now scoped to the release under close and to the identity mode that can satisfy them.

**Six verification-method rows in the release plan were falsified at acceptance.** Across three issues, the plan's stated verification method was a term-presence proxy for a semantic property — checking that a word appears rather than that the property holds. All six were authored at planning time, before the designs they were meant to verify existed. Acceptance graded against the Stage-5 design tables instead, by standing operator instruction, and the plan's verification tables carry a superseded marker; the rows are preserved as written rather than rewritten after the fact. This is the release's own learnings triple: bind a verification method to its design table at design time, never author it ahead of the design.

**Carried forward, not closed here.** A separate pull request writing the same gate-efficacy standard remains open and now owns the obligation to regenerate the hook registry as the second merger. Follow-on candidates recorded during the run include a root-intersection trap in the release-link checker, a stale-baseline misclassification that silently withholds security-hook updates, unsound fence handling in the documentation-link checker, an override message naming a command form the hook refuses, and one unresolvable anchor with a known exact repair.
