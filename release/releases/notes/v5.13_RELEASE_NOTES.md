# A newer push cancels the older push's CI runs, and a gate keeps it that way

2026-11-18 · v5.13

When you push a newer commit to a pull request, CI now ends the runs it had started for the commit you replaced, so the hosted macOS runners work only on commits that can still merge. A new pull-request check fails any workflow that runs on pull requests without that cancellation, written the one safe way.

> **Skip the rest** unless you open pull requests on the platform repository or change its CI workflows.

## Who this affects

- Anyone who opens a pull request on the platform repository, or pushes new commits to one.
- Anyone who adds or edits a CI workflow that runs on pull requests.

## What you need to do

1. After pulling this release, run `./update.sh --surfaces-only` from the platform repository root, or a full `./update.sh`. It refreshes your install with this release's entries for the new workflow checker.
2. When you add or edit a workflow that runs on pull requests, put the cancellation block shown under Operator and engineering detail directly above its top-level `jobs:` line, exactly as written.

## What changed for everyone using the platform

- **Superseded pull-request runs are cancelled.** When a newer commit reaches a pull request, each of the 27 workflows that run on pull requests cancels the runs it still had in progress or waiting for the commit it replaced. *Why it matters:* the macOS runners stop spending hours on commits nobody will merge, so the checks on the current commit start sooner.
- **Runs on the main branch are never cancelled.** A run started by a push to the main branch, a tag, a schedule or a manual dispatch is grouped on its own, so a later push can neither cancel it nor make it wait. *Why it matters:* every merge to the main branch keeps its full set of results.
- **A pull-request check keeps the setting in place.** The new workflow concurrency check runs on every pull request and fails when a workflow that runs on pull requests lacks the cancellation block, writes it any other way, or adds a trigger whose runs would wrongly share the pull request's group. *Why it matters:* a new or edited workflow cannot quietly bring the queue back, and the check names the file and line to fix.
- **A cancelled close-out smoke run gives its runner back at once.** Five trailing steps of the release close-out smoke job now skip when the run is cancelled, and still run after an earlier step fails. *Why it matters:* a cancelled run releases its macOS runner straight away instead of after about five more minutes.

## Known limits

- The check does not read the concurrency setting of a job inside a reusable workflow that other workflows call. No workflow of that kind exists in the repository today, and the release records the gap as a follow-up.
- The check does not read which pull-request activity types start a workflow. A trigger type that can fire more than once on the same commit, such as `labeled`, lets each new event cancel the run before it.
- A workflow that runs only on a push to the main branch, a tag, a schedule or a manual dispatch may carry any concurrency setting; the check does not grade it.
- Marking a pull request ready for review, or editing its description, re-runs some workflows on the same commit. The newer run replaces the older one, and the pull request shows the newer run's result.
- The check is not a required check, so a red result does not stop a merge by itself. It does hold the close-out tool's merge of a chore pull request, which merges only when every check is green.

## Reversibility

CHEAP / HIGH. Reverting the release merge restores the previous workflows; to revert in parts, revert the check's commits before the cancellation commits, because the check fails while any workflow that runs on pull requests lacks the block. Every workflow runs with read-only permissions, so a cancelled run leaves nothing half-written, and the version tag is kept as the record that the version was claimed.

### Operator and engineering detail

**The cancellation block.** Every workflow with a `pull_request` or `pull_request_target` trigger carries one block at workflow level, immediately above its top-level `jobs:` line, with no job-level `concurrency` key. On a pull request the group is per workflow and per pull request, so a newer run cancels the older one; on any other event the key falls back to the run's own id, so the run never shares a group. The 28 workflow names are distinct after case-folding, so no two workflows share a group. The block, with its comment:

```yaml
# Superseded-run cancellation: on a pull request, a newer run of this
# workflow for the same pull request (a new push, or a re-run on the same
# head) cancels this one. Any other event (a push to main, a tag, a
# schedule, a dispatch) keys on its own run id, so it is never cancelled
# and never waits behind another run.
concurrency:
  group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.run_id }}
  cancel-in-progress: true
```

**The gate.** The `Workflow concurrency gate` job in `repo-integrity.yml` runs `core/deploy/tools/check-workflow-concurrency.py` over the whole of `.github/workflows/` on every pull request, with no paths filter. Equality is textual on the three canonical lines, located by a structural parse, so the gate and a fixed-string search for the group line cannot disagree. Its findings name a missing block (`MISSING-GROUP`), a key built any other way, `github.ref` included (`NONCANONICAL-GROUP`), a job-level key, a pull-request trigger beside `workflow_call` (`CALLED-WITH-PR-TRIGGER`), a review event beside a pull-request trigger (`REVIEW-WITH-PR-TRIGGER`), and a workflow-level key in a called workflow (`CALLED-CARRIES-GROUP`). Its `--self-test` grades every fixture case against its declared verdict and requires a failing scan to exit 1 with a finding; the job also fails a clean exit that prints a finding. It is advisory and enforcing: a finding turns the check red, and its context is not registered in branch protection. The gate-coverage register in `core/standards/gate-efficacy-standard.md` carries its row, `core/rules/git-workflow.md` names it among the non-blocking integrity jobs, and a short decision record, ADR-241, points at both.

**What a cancelled job proves.** The runtime-suite selection map now says that a job cancelled because a newer commit reached the pull request has no result for its commit, that a job which had already finished keeps its conclusion, and that a commit superseded within minutes is evidenced by a job that concluded before the next push or by the `test-run` event of its suite run locally.

**At Stage 12.** A sibling release merged first and added `process-catalog-check.yml` without the block, so the planned sibling-workflow branch fired: the release branch merged `main` in, gave that workflow the block, and its counts moved from 26 to 27 workflows. The version moved twice as siblings claimed first, and the atomic claim bound v5.13 with no collision. The four new allowlist entries for the checker sit in a composition surface the deployment manifest did not list; they were propagated after Stage 12 by the surfaces refresh on the operator's decision.
