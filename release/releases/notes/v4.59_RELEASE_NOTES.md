# Release tools now actually run, and a green check means it measured

2026-09-06 · v4.59

Tools that the release process requires an agent to run were blocked from running at all, and one of the platform's own checks could report "clean" when it had in fact examined nothing. Both are fixed, and every gate the platform declares now either genuinely stops a merge or carries an explicit, verified record of the action still needed to make it stop one.

> **Skip the rest** unless you run releases on this platform or rely on the checks it reports.

## Who this affects

- Anyone running a release through the platform's pipeline
- Anyone acting on a pass or fail result the platform's checks report

## What you need to do

1. Run the platform's deploy step so the new permission entries reach your live workspace. Until it runs, the new entries exist in the repository but not in any running session, and the tools stay blocked exactly as before.
2. If you maintain the repository's settings, see Known limits below for the one gate whose enforcement still needs an administrator to register it.

## What changed for everyone using the platform

- **Release tools an agent is told to run can now actually run.** The release process names a set of tools an agent must invoke, but the permission list that decides what an agent may execute carried no entry for several of them, so the agent was refused at the moment of use. *Why it matters:* a step the process mandates no longer fails on permission grounds partway through a release.

- **A check can no longer report "clean" when it measured nothing.** One check returned the same success result whether it had examined the record and found it complete, examined it and found something missing, or been unable to examine anything at all. Each outcome now has its own distinct result, and success is reserved for the case that was genuinely measured. *Why it matters:* a green result is now evidence the check actually ran, rather than only evidence that it did not crash.

- **Every declared gate now either stops a merge or says what is missing.** Where the platform declares that a check should stop a bad change, that claim is now reconciled against whether the check is really wired to stop one — and where it is not, the gate is recorded as advisory with the specific action still required named alongside it. *Why it matters:* you can tell from the declaration whether a gate would really catch something, instead of assuming it would.

- **A coverage report no longer counts folders that do not exist.** One check declared ten locations to scan; three of them had never existed and were skipped in silence, overstating its reach by about a third. *Why it matters:* the number of places a check says it looked is now the number it actually looked at.

- **A known-red advisory check no longer hides the checks behind it.** One check is deliberately left failing as a standing reminder of work with a deadline attached. Because it ran early in its sequence, everything after it was skipped and never reported at all — including the two probes whose whole purpose is to prove the check has teeth. It now runs last. *Why it matters:* an accepted, expected red no longer silently suppresses results you needed to see.

## Known limits

- The duplicate-and-gap check on architecture decision records remains advisory. Making it stop a merge is a repository-settings action that no code change can perform, so it stays advisory until an administrator registers it. The release records that requirement explicitly rather than implying the gate is already enforced.
- The same "one result for three different outcomes" flaw still exists in another check — and that one does stop merges. It was found while running this release and is recorded for a follow-up rather than folded in here.
- One advisory check stays red by design, reporting five tools that still need permission entries before a December 2026 deadline. It blocks nothing, and the entry that would silence it is deliberately not added, because the pattern it would need matches any path at all.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH confidence.** Reverting the release merge restores the previous corpus in a single operation. Two elements sit outside that: the permission list is also copied outside the repository by the deploy step, so a complete rollback needs a re-deploy as well as the revert; and a claimed version tag is permanent by policy, so it is recorded rather than removed. No data is migrated and no stored state changes shape.

### Operator and engineering detail

**One verdict collapsed onto one exit code, and that was the release's whole thesis.** The decision-emission check mapped `CLEAN`, `INCOMPLETE` and `NOSET` all onto exit 0 under the shipped warn sentinel, and its consuming workflow printed an unconditional completeness claim on that branch. A green therefore asserted something the engine had never established — and, decisively, the same green appeared on a bare checkout where the asserted-set file was missing entirely, which the engine's own contract calls a repository defect. The fix gives every degraded verdict its own code, so the clean state no longer shares an exit with an unmeasured one:

```
CLEAN        -> 0    every in-scope release emitted every asserted class
INCOMPLETE   -> 2    measured; an in-scope release is missing an asserted class
SKIP         -> 3    not evaluated; the verdict was withheld, not granted
NOSET        -> 4    the asserted-set file is absent or declares zero classes
(unexpected) -> 1    fail-closed
```

**Declaration and enforcement were reconciled in one direction, deliberately.** The gate-efficacy standard contradicted itself: one passage defined a `required` posture extensionally as "blocks merge or ship", another as merely recording the intended posture, and a third stated that posture is derived rather than restated. Two of the three agree, and the derivation rule is decisive — so a gate declares itself advisory while it is unregistered and flips to required when registration actually lands. Twenty-eight declarations were examined against that reading and one was wrong.

**The checker was running inside the defect it would have caught.** The static test that grades every workflow's gate-efficacy header runs inside the very job whose own header declared six contexts as required-and-branch-protected while none of them were live. It reported green because posture-to-enforcement agreement was the one property it did not grade. That missing predicate is now asserted, with five anti-vacuity arms, and the offending declaration corrected.

**Aggregation was traced upward but never sideways.** A permanently-red advisory step sat fourth in a six-step job with no per-step failure tolerance, so the two precision probes behind it — the arms whose stated purpose is that without them the gate is a claim about itself — had never executed once. The design had traced the exit code from step to job to required context, and stopped there. Moving the red step last restored both probes. This is the release's own learnings triple: trace a gate's exit code sideways to its sibling steps, not only upward.

**Carried forward, not closed here.** The branch-protection registration for the decision-record gate is an operator repository-settings action and remains outstanding, which is why its issue stays open rather than closing with the release. Also recorded during the run: the merge-blocking check carrying the same collapsed-verdict flaw, two register rows in the gate-efficacy standard that went stale from the operator's own registration event, and a documented-versus-actual divergence in the version-claim tool's help text.
