# Once planning starts, a release stops changing underneath it

2026-08-04 · v4.07

Work approved after a release has entered planning now waits for the next bundle instead of being added to the one already running — an addition used to silently invalidate the dependency graph, file map, contention list and schedule that planning had just finished computing. Four checks that decide what belongs in a bundle also stopped trusting stale inputs, including one that had been reading a label the platform's own rules forbid anything from creating, so it had never once run.

> **Skip the rest** unless you plan releases, bundle work into milestones, or read the release history.

## Who this affects

- Anyone who bundles approved work into a milestone or plans a release.
- Anyone who relies on a release's planned scope staying fixed once work starts.
- Anyone who runs the release close-out and expects its record to have somewhere to land.

## What you need to do

1. **Run the normal deploy step for your workspace.** Two packaged assistants — the release hub and the release planner — were repackaged in this release, so an existing install keeps the previous copies until it is redeployed.

Nothing is migrated, no settings change, and nothing else is required.

## What changed for everyone using the platform

- **A release's contents close to new work the moment planning starts.** Newly-approved work that matches the theme now routes to a *next* bundle rather than into the running one, and the boundary is written into the milestone as a visible marker instead of being guessed at. *Why it matters:* adding one issue after planning finished invalidated every artifact planning had just produced — the dependency graph, the file map, the contention list, the capacity budget — and until now nothing stopped it happening.
- **Removals still work; only additions are closed.** Dropping or deferring an issue, or re-ordering the ones already in the bundle, keeps working exactly as before at the same ceremony. *Why it matters:* a freeze in both directions would have left a genuinely cancelled issue with no legal way out of a running release.
- **The planner's priority tie-breaker actually executes.** Its ordering rule had been reading a priority label that platform rules forbid anything from creating, so it silently never fired; it now reads the Priority field in the issue body. *Why it matters:* every ordering decision that claimed to be breaking ties by priority had in fact been falling through to issue number.
- **Bundling re-checks its own claim at bundle time.** The bundler re-validates that the milestone it is about to write into is still the right one, and re-runs the duplicate check, instead of trusting a verdict recorded when the issue was first filed. *Why it matters:* a filing-time verdict can be weeks old, and both the milestone and the duplicate landscape move in between.
- **Sequencing strategy is measured rather than assumed.** Planning now computes how dense the dependency graph actually is and picks the ordering approach from that measurement. *Why it matters:* a flat graph and a tangled one want opposite orderings, so assuming one wastes the planning pass and produces a sequence nobody can build to.
- **Release scaffolding now creates the gate-stage tasks the close-out writes to.** Scaffolding used to create the middle stages only and skip the three gate stages, so the close-out's own proof had nowhere to be posted. *Why it matters:* those tasks were being created by hand every release, and when they were not, the close-out record quietly landed somewhere else or nowhere.
- **Planning reads the readiness briefing it already produced.** The readiness check's output is handed to planning as a cached input with a freshness test, rather than planning re-deriving the same answer from scratch. *Why it matters:* the same analysis was running twice per release, and the two runs could disagree with no rule for which one won.

## Known limits

- **The new bundle-entry check does not apply to this release itself.** It applies to bundling decisions made after this release shipped; the release that introduces a gate cannot fire it against its own run.
- **Eight malformed table rows in the gate-criteria file are left as they are.** One was repaired here under a narrow approval because this release was editing that exact table. A survey found nine in total — three more than an earlier count, which had only looked for one of the two shapes. The remaining eight are a single mechanical repair routed to a follow-up.
- **One file still states two contradictory ordering rules.** The dependency-analysis reference rejects leverage-based ordering unconditionally in one section while another section now conditions it on the measured density. The third site sits inside a different issue's territory, so it was deliberately deferred rather than edited across a scope boundary. Tracked as [#4718](https://github.com/cody-hutson/pmo-platform/issues/4718).
- **A membership check silently drops about two-thirds of what it reads.** It asks for stage-titled issues under a limit of 1000 against a population near 2990 and never checks whether it hit the ceiling — in a file whose own documentation forbids exactly that. It cannot change any check's pass/fail result and the close-out does not call it, so the effect is bounded to an advisory count. Tracked as [#4720](https://github.com/cody-hutson/pmo-platform/issues/4720).
- **A quality-testing reference contradicts itself** about whether a partial result that does not block acceptance still needs an override record — three reviewers hit it in this one release. Tracked as [#4719](https://github.com/cody-hutson/pmo-platform/issues/4719).
- Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:pipeline` label.

## Reversibility

MODERATE / HIGH confidence. Reverting the single integration commit restores every file's bytes — the lock rule, the gate criterion, the parser fix and the scaffolding change all go back together, and the merge is a true two-parent commit so the revert form stated in the plan applies. What does not revert is *protocol semantics*: milestones already carrying the lock marker keep it in their descriptions, since the marker lives in milestone data rather than in the repository. The two repackaged assistants need the deploy step run again after a revert rather than reverting on their own. Standard 7-day rollback window.

### Operator and engineering detail

**The lock binds the act, not the disposition bucket — and that distinction was found adversarially, not designed in.** The Stage-5 A6.5 adversarial review found a cross-table consistency gap that no pre-existing acceptance criterion could catch: a correct sub-window table plus a correct gate can *together* strand removals and zero-delta re-sequences with no legal outcome path at all. Two criteria were added mid-flight as a result — the lock conjunct is addition-typed rather than path-typed, and the lock state resolves three-valued. `amend` therefore stays fully available for removals (triggers T3 and T6 are themselves removal events) and for pure re-sequences, which compute a 0% delta. `re-bundle` is not an exception to the lock but its lift condition: it re-executes Stage 3 Phase A1–A5 and returns the bundle to sub-window A, so any addition it carries happens *after* the lock lifts. There is deliberately no hotfix carve-out — the `hotfix` Release Class is already the faster emergency route, and injecting corrective scope into a `cross-cutting` bundle would inherit that bundle's Deep Stage-9 posture and its ship date.

**`UNMARKED` is a state, not a pass — the release's most load-bearing design decision.** `lock_state` resolves in order: the verbatim marker in the milestone description (positive), then a two-limb union of attachment-or-exact-title evidence that Stage 4 was entered (positive, used *monotonically* — it may only ever establish a lock, never certify openness), then `UNMARKED`. A zero probe result is an **absence**, and no consumer may coerce it to "pre-Stage-4"; on the `UNMARKED` arm the gate passes only with an explicit eligibility basis recorded in the amendment comment. Soundness rests on the state machine's default rather than on probe coverage — which is why the failure direction is toward refusing a legal amend, a state the operator clears with one recorded line. The rationale is carried inline in the schema so a later release does not "simplify" the resolution back to a two-valued probe.

This is the marker the boundary-crossing act appends to the milestone description, and the shape the order-1 resolution matches verbatim:

```
### Composition Lock
**Locked at:** Stage 4 Planning entry · YYYY-MM-DD · planning sub-task #{PLANNING_SUB_TASK_NUMBER}
```

**One rule is stated once and cited three times.** The act-typed rule lives in the release-process protocol; the outcome-path table, the Stage-3 bundling shard and the new gate criterion each *cite* it and restate none of it, so a future outcome path inherits the guard without an edit. The gate criterion itself is conditional — it fires only when the selected path is `amend` **and** the addition count is above zero — so removal-amends, zero-delta re-sequences and the other three outcome paths pass trivially rather than being exempted by hand. The gate-criteria schema took a non-breaking additive bump for the one new criterion; no existing criterion ID was renumbered.

**Fixing the priority tie-breaker meant retiring symbols, not adding one.** The parser had been reading a forbidden priority label, which preserved the label taxonomy's rule 5 only by accident — the signal is now sourced from the issue body's Priority field. The slice collapsed three undefined prose symbols for the same concept into one defined key and recorded that no fourth would be added; a downstream slice landing afterwards consequently cited the defined symbol rather than re-introducing a parenthetical form of the key that had just been retired.

**One card's design was reversed at the adversarial review, and the reversal shrank it.** The cache-read work originally made the readiness mode itself the writer — which required narrowing that mode's read-only guardrail, adding a fourth hub-state surface and its two registration points, and an architecture decision record. The operator took the reviewer's counter-design instead: the hub relays the briefing into a sub-task comment thread it already creates and already posts to. Net effect four modified files, no new files, no new surfaces, no contract change, and no decision record — and the read-only guardrail was verified untouched by restricting the diff to its two regions and confirming the result was empty. The trust boundary the bridge document already mandates supplies a provenance control the operator-local file could not have.

**Architecture-decision numbering churned five times in one release.** A sibling release merged mid-flight and landed five decision records, colliding all three of this release's allocations at once. Two numbers were re-derived, and the third obligation was discharged by elimination rather than derivation — the clause that had justified an ADR at all was deleted by the design reversal above, so there was no number left to claim. The general reading: allocating a number at authorship against a namespace another branch can claim concurrently is structurally unsound, and the stable rule is allocate at authorship but *claim at merge*. The same failure shape one directory over — criterion IDs in the gate-criteria file — has no collision guard at all, and is recorded as out of scope.
