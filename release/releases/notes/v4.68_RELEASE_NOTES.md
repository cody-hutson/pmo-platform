# Write protection for the platform repository now follows its working copies

2026-09-25 · v4.68

Work started in the operations workspace can no longer write into a working copy of the public platform repository just because that copy sits outside the usual folder or is reached through a shortcut. The safety guards now ask which repository a file belongs to instead of trusting its folder path, and they read your session's own folder as carefully as the file being written.

> **Skip the rest** unless you start sessions from the operations workspace, do platform work in a working copy outside the usual folder, or review the safety guards' block records.

## Who this affects

- Anyone who starts sessions from the operations workspace
- Anyone whose platform work happens in a working copy outside the usual folder, including the working copies that helper sessions create for themselves
- Operators who review the safety guards' block records

## What changed for everyone using the platform

- **Working copies of the platform are recognized wherever they are stored.** The guard now decides whether a file belongs to the platform by asking which repository the file sits in, not whether its path starts with the usual folder, so a working copy created somewhere else — even one placed inside the operations workspace — is treated exactly like the main checkout. *Why it matters:* a write from the operations workspace into any working copy of the public repository is now refused, where before this guard did not recognize a copy stored outside the usual folder and let the write through.

- **Your session's folder is read the same way as the file being written.** The guard used to take the session's folder as literal text while carefully resolving the target file; it now also resolves shortcuts, `..` steps, relative spellings and trailing slashes in the session's folder. *Why it matters:* a session gets the same answer however its folder happens to be spelled, so reaching a folder through a shortcut no longer changes whether a write is allowed.

- **A write the guard cannot place is refused rather than allowed.** If a session's folder cannot be determined at all, a write into the platform repository is now refused by the check that keeps operations content out of it. When a request simply does not name a folder, the guard uses the session's own, so ordinary sessions are unaffected. *Why it matters:* an unreadable situation now fails safe at the one check whose failure would put operations content into a public repository.

- **A folder that only looks like the platform is no longer guarded as if it were.** A folder in the platform's usual location that is not actually a repository no longer triggers this refusal, because nothing written there can be committed to the public repository. *Why it matters:* the guard stops blocking writes that could never reach the repository it protects.

- **Both platform guards now agree on what counts as the platform.** The guard that keeps stray draft files out of the platform now uses the same shared check as the write guard instead of its own. *Why it matters:* the two guards can no longer give opposite answers about the same folder.

## Known limits

- A separate clone of the platform repository — downloaded again rather than created from your checkout — counts as a different repository, so this check does not recognize it. Working copies created from your checkout are recognized.
- The draft-file guard acts only inside the workspace folder, so it does not recognize a platform working copy stored outside that folder. This is by design.
- On an install that uses a custom workspace location without passing it to sessions, the location-based checks read the default location and may not apply. This predates this release and is tracked as [#7654](https://github.com/cody-hutson/pmo-platform/issues/7654).
- If the new shared helper file is missing from a workspace's guard bundle, the guard refuses the writes that depend on it and names the reinstall step, rather than guessing. A normal update installs the helper.
- A workspace picks up this release when the update next refreshes its guard bundle. This workspace was refreshed at release time, and its three changed guard files were checked against the merged source.

Report issues at https://github.com/cody-hutson/pmo-platform/issues, and report a suspected vulnerability privately as the [Security Policy](https://github.com/cody-hutson/pmo-platform/blob/main/SECURITY.md) describes.

## Reversibility

MODERATE / HIGH. The release is a single merge, so reverting it restores the previous guard behaviour in one step; a workspace then needs its guard bundle refreshed from the reverted source and the no-longer-used helper file removed. The version tag stays in place as the record that the version was claimed.

### Operator and engineering detail

**Working-directory canonicalization.** `block-autonomy-ceiling` resolved the write target through `realpath` but compared the payload `cwd` as raw text. It now resolves the working directory through the target's own resolver, lazily — only inside the Write/Edit branch, and only when the target lies in a domain — with the hook process's `$PWD` as the fallback when the payload omits `cwd`. A working directory that still resolves to no absolute path is a named third state, `unresolvable`: `BLOCK-AUTONOMY-002` alone fails closed on it, `BLOCK-AUTONOMY-004` does not fire, and the workspace-scope gate keeps its raw input. For `-002` the working directory's operations side is read twice, as spelled and as resolved, and either reading can only add a block.

**One repository-membership helper.** The new shared library `core/hooks/lib/platform-membership.sh` answers member, not a member, or undeterminable, and owns no failure branch — each caller maps the answer to its own direction. It is now the only membership implementation: the governance-file rule's repository stage, the domain classification behind `-002` and `-004`, and `block-draft-files`' identity gate all call it, and membership replaces the `pmo-platform` path prefix. Its anchor locates itself and resolves the checkout's `.git` physically, so symlinked, `--separate-git-dir` and worktree-shaped checkouts are recognized. The helper is registered in the installer's co-deploy block, in `hook_publish_set()` and in the CI sandbox layout. [ADR-204](https://github.com/cody-hutson/pmo-platform/blob/main/core/ADRs/ADR-204-cross-domain-classification-is-repository-membership.md) records the decision, supersedes ADR-149 in part, and was ratified to Accepted at this close.

**A new block-log field.** The shared block log keeps `cwd` as the payload value, and this hook's `-002` and `-004` rows now also carry `cwd_resolved` — the value the verdict used, or empty when the working directory was unresolvable and `-002` failed closed. Readers that ignore unknown keys are unaffected. One `-002` row, with illustrative paths:

```json
{"ts":"2026-09-25T01:00:00Z","hook":"block-autonomy-ceiling","rule":"BLOCK-AUTONOMY-002","tool":"Write","input_digest":"3f9a0c1e5b7d2a46","cwd":"/home/you/Claude/projects/acme","cwd_resolved":"/home/you/Claude/projects/acme"}
```

**How it shipped.** Both cards were built assertion-first on one branch and landed as one two-parent merge. The Stage-9-approved head moved by one codified stamp commit, which resolved a deferred citation of the new decision record to its number, and every check re-ran green on the moved head before the merge. The hook bundle was refreshed from the primary checkout by the update path, and the three changed runtime files match the merged source by hash. A CI-faithful run of the full hook harness on the merged tree at close read 1637 PASS and 0 FAIL across 24 suites.
