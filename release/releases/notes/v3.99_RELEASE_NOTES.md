# Release runs now say how reversible each decision is — and where they stand

2026-07-29 · v3.99

Every decision a release run puts in front of you now arrives labelled with how reversible it is and how sure the run is, and every turn opens with one line telling you which stage and gate you are at. Before this release just over half of those decisions carried a label at all, and the shortest turns — outage notes, retries, terse acknowledgements — dropped the position line entirely.

> **Skip the rest** unless you run a release through the release orchestrator, or you are the person answering its decision prompts.

## Who this affects

- Anyone who runs a release through the release orchestrator and answers its gate prompts.
- Anyone auditing a past release run who needs to see how reversible each decision was judged to be at the time it was made.

## What changed for everyone using the platform

- **Every decision now says how reversible it is.** A decision the run asks you to make carries a plain label — CHEAP, MODERATE, EXPENSIVE or IRREVERSIBLE — alongside how confident the run is in it: HIGH, MEDIUM or LOW. *Why it matters:* you can tell at a glance whether an answer is easy to take back or one to think hard about, instead of reading through the reasoning to work it out.
- **The labelling rule now covers the whole orchestrator, not half of it.** The obligation was written to bind only the readiness-check side of a release run, so the side that actually drives a release carried no labelling duty at all — measured against real runs, 41 of 75 decision turns carried the label (54.7%). It now binds both sides. *Why it matters:* the label is there whichever part of a run you are talking to, so you no longer have to notice which mode you are in to know whether to expect one.
- **A decision is never put to you inside a prompt you were not briefed on.** Before opening a decision prompt, the run now checks itself that the full four-part briefing is already on screen. *Why it matters:* you are not asked to choose between options whose consequences were never spelled out.
- **Putting the briefing off is now a named move — and saying nothing is not.** When a run folds several decisions into one briefing later on, it now has to say so explicitly in a named form; anything else counts as a skipped briefing. *Why it matters:* a genuinely consolidated briefing stays legitimate, while a briefing that was quietly dropped becomes visible instead of blending in with the legitimate case.
- **Every turn opens with where the run stands.** Each turn begins with a single line naming the stage, the gate and the progress — and that line is explicitly not waivable on the short mid-stream turns where it used to disappear. *Why it matters:* you keep your place in a long release run, including at the moments when something has just gone wrong and knowing the position matters most.

## Known limits

- The two headline numbers this release targets — how often the label appears, and how often the briefing renders — are measured by re-reading real release runs after the fact, not by anything that runs during a release. Confirmation that the fix worked comes from the next scheduled re-audit, not from this release.
- Nothing stops a turn that omits the label. The rules live in the orchestrator's own instructions and are checked by that later re-reading; no tool blocks a turn at the moment it is written.
- The new rules apply to release runs that start after this release. The run that shipped them is deliberately not measured against them.
- The measuring instrument has a known ceiling, so a future re-audit will not read 100% even if every turn conforms. The numbers, and what a shortfall does and does not mean, are in the operator detail below.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

MODERATE / HIGH confidence. Reverting the release restores the previous instructions in a single step, followed by a rebuild of the packaged skill. It is MODERATE rather than CHEAP because a second release has since attached its own rule to the same numbered list, so a revert must be read against that neighbour rather than applied blind. Standard rollback window.

### Operator and engineering detail

**Scope widening and the emission-time predicate.** The root cause was a scope clause, not a missing rule: the Output Contract opened with *"Six requirements hold on every **Mode R** emission"*, so every requirement under it — including the reversibility obligation — was structurally unenforceable on Mode O, which is where release orchestration actually happens. The fix widens the opener to bind both modes and marks the genuinely Mode-R-scoped requirements inside the list, so widening does not wrongly bind a Mode O turn to the readiness-check schema. Requirement 5 is retargeted from "the milestone verdict" to every decision-class emission in either mode, and a new emission-time predicate paragraph answers the question the emitter actually faces while composing a turn: does this turn ask the operator to decide, approve, authorize, or act? It carries a closed enumeration of the hub's decision-class artifacts, an explicit operational residual making that list a floor rather than a ceiling, a ceremony bound naming what carries no label, and the disqualifier that reasoning about reversibility in prose does not satisfy the requirement.

**Gate 3, declared deferral, and a falsified premise.** The originating ticket claimed the briefing gate was being skipped ahead of prompts. The audit falsified that: every turn that fired a decision prompt did render its briefing (31 of 31), and all 28 briefing defects fired no prompt at all. The real defect is the *ungoverned deferral* — a run consolidating decisions into a later briefing, with nothing distinguishing that from a silent skip. Rather than amend the ticket, the design was adjusted at the gate: deferral becomes a first-class declared form with a falsifiable deferral-versus-skip discriminator, and gate 3 gains an emission-time self-gate that cites the briefing's item-1 content by reference rather than enumerating its fields, so it cannot drift against the new reversibility field added in the same release. The briefing contract's own declared Mode-O-only scope was reconciled at its title and intro, since it had been carrying both-mode obligations under a single-mode heading.

This release adds two required emission shapes. One turn, showing both — the position anchor and the decision label:

```text
Stage 12 · gate: Execute · progress: 11 of 13 stages complete

Recommendation: merge the release PR now rather than waiting on the sibling release.
[MODERATE · confidence: HIGH]
```

**The concurrent-release renumber — the notable event of this release.** A sibling release merging days earlier independently added its *own* requirement 7 to the same numbered list and made the same count bump. Two different requirement 7s, one slot. The resolution was forced by evidence rather than chosen: the sibling's requirement self-references its own number inside its body text and its reference file cites "requirement 7" twice, so renumbering it would have edited already-shipped prose and broken a live reference cascade — while this release's anchor requirement was net-new with zero inbound citations by number, and renumbered at zero cost. The anchor therefore ships as **requirement 8** and the count word reconciles to **Eight**, a value neither release specified alone. A correction commit landed before the merge restating the frozen release plan's requirement-7 references — including an acceptance criterion that, post-merge, literally described the *sibling's* requirement — against requirement 8; the mechanical criteria checks passed either way, so nothing else would have caught it.

**Two acceptance criteria are recorded as deferred, and the instrument has a ceiling.** The two rate criteria (labelling at 95% or better, briefing render at 90% or better) measure a population that does not exist until a later release runs on the merged instructions, so they are recorded as declared-verification-deferred into a 30-day outcome window, to be graded by a second run of the same governance audit. Read that result with this discriminator in hand: against the frozen instrument a perfectly-conforming agent ceilings at **70/75 = 93.3%** on the labelling criterion and **100/117 = 85.5%** on the briefing criterion, because the instrument counts turn shapes the rules exempt. A shortfall whose non-conformers are dominated by those rule-exempt shapes is instrument over-inclusion and is **not** grounds to reopen either issue; a materially lower result — or non-conformers that are genuinely decision-shaped turns missing a label, or turns sitting in the silence cell — is a real fix failure. The instrument's own miscalibration (a non-canonical confidence value and no deferral-aware clause) is tracked separately and must land before the re-run, or the grade under-reports.
