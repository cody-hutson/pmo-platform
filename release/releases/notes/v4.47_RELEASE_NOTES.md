# Decision records can now say what replaced them — and how much

2026-09-02 · v4.47

The platform records its architectural decisions as numbered decision records, and each one carries a status saying whether it still holds. That status machinery had gaps: a decision could only be marked wholly replaced, never partly, so thirteen real "this was partly replaced by that" relationships lived in prose where nothing could find them. This release gives those relationships a real representation and puts them where search can reach them.

> **Skip the rest** unless you read the platform's decision records, or you maintain them.

## Who this affects

- Anyone who reads decision records to find out whether a decision still holds
- Anyone authoring or reviewing a new decision record
- Anyone who has relied on a decision record's status field as current

## What changed for everyone using the platform

- **A decision can now be recorded as only partly replaced.** Records carry a matching pair of "replaces" and "replaced by" fields, and each one says whether the replacement is whole or partial. *Why it matters:* before this, a decision that was superseded in one respect and still binding in every other had no honest way to say so — the choice was to overstate the replacement or leave it unrecorded.

- **Thirteen replacement relationships are now recorded where they can be found.** They previously existed only as prose inside the records themselves. *Why it matters:* a reader checking whether a decision still holds now sees the answer in the record's own fields instead of having to read every other record that might have replaced it.

- **The two halves of a record can no longer disagree silently.** Each replacement relationship is now checked from both ends, so a record claiming to replace another is reconciled against what that other record says. *Why it matters:* a one-sided claim used to be invisible; now it surfaces.

- **One stage now owns marking a decision approved.** The record template promised an approval step, and no stage actually performed it. That step now has a named owner. *Why it matters:* records could sit indefinitely in a proposed state while being treated as settled, which made the status field unreliable as a signal.

- **Recurring decision patterns are indexed.** Eleven clusters of related decisions are now listed in one place. *Why it matters:* a question already answered by an earlier decision is easier to find before it gets decided again differently.

- **A gate now checks the move that was made, not the shape of it.** One acceptance check matched a renumbering by its appearance rather than by what actually happened. *Why it matters:* it can no longer pass on something that merely looks like the required change.

## Known limits

- **One contradiction was flagged, not fixed.** ADR-032 remains in an approved state while the corpus surfaces it assigns to a separate operator home are still tracked in the repository. That disagreement is real and is carried forward, not closed by this release; it is owned by #6627, which decides the corpus location and the home selector. This release applied the new partial-replacement grammar to ADR-032 to record what is already known about it — that is a description of the situation, not a resolution of it.
- **The pattern-cluster population could not be reproduced as originally specified.** The index ships with clusters re-derived at build time; the original count could not be reconstructed from its stated method, and that gap is recorded rather than papered over.
- **One record was deliberately excluded.** ADR-029 is frozen and was not edited, including for otherwise routine hygiene.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE**, confidence **HIGH**. The change is additive to the record schema plus field edits across the record corpus and three supporting tools; no interface or stored-state format changes shape. Rollback is a single revert of the release merge, which retains both parents for that purpose. The one caveat is that records edited by hand after this release would need their replacement fields reconciled by hand as well.

### Operator and engineering detail

Raw audit detail is in the RELEASE_LOG Deployment Log for this version. Three things are worth reading rather than inferring.

**The version claim failed the first time, and the failure is recorded rather than elided.** The initial Stage-12 claim pushed a malformed but correctly signed tag and exited zero. The cause was a caller that read the version anchor inside a command substitution and discarded its return code: a transient failed read produced an empty string, parsing produced nothing, and arithmetic on an empty operand produced a version number that looked plausible. The anchor function itself was never at fault — it returned non-zero and printed its diagnostic exactly as specified, and nothing acted on it. The fix adds the missing return-code check and a canonicality assertion, and ships a test arm proven to discriminate by reverting the production fix and confirming the arm fails while reproducing the exact malformed value. It shipped as its own change with all checks green before the release was re-claimed.

**Install propagation was owed here and was performed.** Unlike the preceding release, this one declares a skill copy in its delivery strategy, and the measurement agreed: the change touches a skill reference file and its rebuilt package. Both install roots were confirmed drifted before the copy, the copy was scoped to the affected skill rather than run across the whole roster, and it was verified by comparing content hashes rather than by trusting an exit code — which is what rules out the known failure mode where the deploy silently does nothing and still reports success.

**The malformed tag was removed under an operator-performed exception.** Deleting it required relaxing the tag-protection ruleset, which is an operator action; it was performed with the ruleset captured beforehand and restored from that capture, and the restoration was verified to carry the same rules and conditions rather than assumed from the absence of an error.
