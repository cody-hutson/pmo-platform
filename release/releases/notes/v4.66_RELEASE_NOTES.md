# Your methodology now shapes what intake asks and what gates check

2026-09-18 · v4.66

Until this release, choosing a methodology changed almost nothing you could see: intake asked the same generic questions whatever kind of work you were filing, and readiness and done gates checked a fixed list instead of the criteria your methodology declares. Both now read your resolved methodology and act on it — and where they cannot, they say so instead of passing quietly.

> **Skip the rest** unless you file work items, run a readiness or done gate, or maintain a methodology pack.

## Who this affects

- Anyone filing a work item through intake
- Anyone running a readiness or done gate on a work item
- Anyone authoring or maintaining a methodology pack

## What changed for everyone using the platform

- **There is now a stated bar for what a good work item looks like, per kind.** A new authoring standard states the expected structure, the required content and the appropriate depth for each kind of work item, and it is altitude-aware — what over-definition means for a container is not what it means for a task. *Why it matters:* until now the only written guidance applied across all kinds, so nothing told you how a good story differs from a good epic, and "well-formed" was a matter of taste.

- **Intake asks for what your resolved kind actually needs, not a generic field set.** When a methodology kit resolves, intake composes its questions from that kind's own declarations and uses the authoring standard's depth guidance to decide how deep to go. *Why it matters:* you stop answering questions that do not apply to the thing you are filing, and stop being let through without the ones that do.

- **When no methodology resolves, intake says so out loud.** Instead of quietly falling back to a default, intake now states in its run output that the methodology was unresolved and that it is using the neutral registry and its altitude floor instead. *Why it matters:* a silent fallback is indistinguishable from a working one, so you could not tell whether the questions you were asked were the right ones for your methodology.

- **Readiness and done gates now evaluate the criteria your methodology kit declares.** A gate resolves the kit for the work item's kind and evaluates that kind's declared checks alongside its own exit criteria, instead of reducing over a fixed checklist that never consulted the kit. *Why it matters:* passing a gate now means your methodology's bar was met, rather than that a list unrelated to it was satisfied.

- **A gate over a kind with no declared criteria now reports that, instead of passing silently.** Where a kind declares no bar, or the kit or kind cannot be read, the gate states what it could not evaluate — naming the kind, the key, and how many of the criteria it read — and renders no verdict for it. *Why it matters:* a gate that passes because it found nothing to check reads exactly like one that passed on the merits, and that is worse than having no gate at all.

## Known limits

- The consumer contract that lets one program read another project's resolved methodology is **stated but not machine-enforced**. Its middle tier is a rule programs are expected to follow, not one a check executes today, and the release records that plainly rather than implying coverage it does not have.
- A methodology pack may declare a kind without giving it a matching label, which would leave work items of that kind untypeable on the label surface. Every pack in the platform today projects all of its kinds, so no such pack exists — but nothing yet stops one being written.
- Whether a judgment-level check can be evaluated is settled **per check, by measurement**, not by its level. A check's declared level does not tell you whether it will be admitted to a gate's verdict.
- The depth guidance shapes what intake asks; it does not change when intake stops. The existing clarity gate still decides that.

Report issues at the platform's GitHub issue tracker.

## Reversibility

CHEAP / HIGH. The whole release reverts as a single merge revert, which restores the previous intake questions and the previous gate behaviour together. A gate that now blocks an item it would previously have passed is returning work, not destroying it — the item is unchanged.

### Operator and engineering detail

**The pack consumer contract is tiered, and its middle tier is read defensively.** The spike on whether any project can be consumed by any consumer returned a tiered verdict rather than a yes or no. Tier M1 — the resolved kind set, keyed on `kind_id` — is archetype-blind and reaches a consumer already resolved, so it may be read unconditionally. Tier M2 — the join surface each kind declares, the criteria sub-objects and the check shape — reaches a consumer unconsulted, so it is read defensively: on any violation the consumer emits `NOT-EVALUATED` naming the kind, the key and the denominator, and renders no verdict. Tier M3 has exactly one member, the kind-to-label projection, and is not read at all. The partition is by specification-presence, never by observed enforcement, so a check shipping or flipping re-derives the enforcement column and moves no property between tiers. The denominator is contractual rather than advisory: without it, a consumer emitting the caveat for every kind it meets is indistinguishable from one working correctly, which is the same vacuous-verdict defect in the opposite sign.

**Criterion evaluability is a per-check measured property, and it gates admission.** The judgment-level spike measured the two shipped packs' 26 criteria checks — 19 at level L3, 4 at L1, 3 at L2 — and established that the level set and the machine-evaluable set are not the same set: they diverge on two checks carrying L2 together with `automatable = false`, so any arithmetic subtracting the L3 count from the total to obtain the evaluable count is wrong by two. Evaluability is therefore recorded per check and never inferred from the level, and it decides whether a check is admitted to a gate's aggregate rather than how that aggregate is scored.

**The read scope is fixed by the transition, never chosen.** A gate reads exactly one criteria key per evaluation — readiness, done, or gate-class — bound to the transition being evaluated; the keys are never unioned. Resolving a kit is a two-part selection, and naming only the first is how a gate reads the wrong criterion set and still renders a confident verdict: the pack comes from the operator's declared delivery approach, the kind from the work item's own type label. A delivery approach resolves a pack, never a kind. The gate reads the resolved manifest directly and is explicitly prohibited from delegating that read to the shipped pack reader's default path, which returns fragments on an inline-table array while reporting a clean parse — a mechanical implementation would evaluate shredded input and appear to have worked.

**The type-pack schema gained a way to distinguish a reasoned empty bar from an unauthored one.** An empty `checks[]` is valid — a Kanban card's readiness bar is legitimately shorter than a Scrum story's — but emptiness alone could not tell a consumer whether that was a decision or an omission. An empty array now carries its provenance on the enclosing block, mirroring the rule an empty field array already followed, and that block-level `source` is the key a consumer reads to tell the two apart:

```toml
[kinds.criteria.readiness]
criteria_version = "1.0.0"
source = "Kanban: pull-based readiness, no per-item entry bar by design"
checks = []
```

**The authoring standard is a reading, not a carrier.** It states what good looks like inside the space the schema deliberately leaves unbounded — no minimum check count, no required topic, no prescribed level ratio. It names no kind, states no minimum, and adds nothing the schema's conformance table would have to enforce, so it guides authoring without becoming a second place where the bar is defined. Each of its rules is either tied to a criterion the gates evaluate or explicitly marked as guidance, per the evaluability verdict above.
