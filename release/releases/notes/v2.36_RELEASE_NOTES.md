# Triage and bundling now follow written signals instead of being re-figured each release

2026-06-28 · v2.36

Several judgment calls the release pipeline made fresh on every run — how an approved ticket's structure is treated downstream, how priority is read, when related issues get grouped, and how sub-tasks are tracked — are now written down as standing rules, and one repeatedly hand-derived step becomes a tracked tool. Nothing changes for project work or existing artifacts; this is internal pipeline guidance.

## Who this affects

- Anyone running work through the release pipeline (triage, bundling, engineering). No effect on project artifacts, trackers, or status outputs.

## What changed for everyone using the platform

- **An approved ticket now counts as direction, not a fixed blueprint.** The pipeline states plainly that approving a ticket signs off on the problem and the outcome — not on the ticket's proposed structure, which a later design step is free to confirm or rework. *Why it matters:* you can approve a good idea without being locked into the first guess at how to build it, and downstream stages stop treating an early structural sketch as settled.
- **Priority is read as two separate things, not one blurred score.** Triage now separates how urgent something is from how valuable it is, with how many other items depend on it as a third signal — without hardwiring any one scoring method. *Why it matters:* a low-value-but-urgent item and a high-value-but-can-wait item are no longer flattened into the same "priority," so sequencing decisions are clearer.
- **Related issues get grouped on a written threshold.** There is now a stated rule for when a set of related issues is large or connected enough to be tracked as a group, and which grouping mechanism to use. *Why it matters:* clusters of related work get a tracking home consistently, instead of depending on whoever happens to notice the pattern.
- **Sub-task breakdown follows a stated threshold.** The choice between formal sub-issues and a lighter in-PR checklist for breaking a work item down now has a defined trigger. *Why it matters:* small items stop being over-tracked with full sub-issues, and genuinely large ones stop being under-tracked with just a checklist.

## Known limits

- These are pipeline guidance and one tool; they change how release work is planned and tracked, not any project-facing behavior, artifact, or command.
- The directional-ticket principle is stated here; the gate that enforces it ships separately ([#501](https://github.com/cody-hutson/pmo-platform/issues/501), a different milestone).
- The priority decomposition deliberately stays method-neutral — it does not pick a scoring formula for you.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:pipeline` label.

## Reversibility

CHEAP / HIGH confidence. Every change is a tracked spec, governance, or schema edit plus one new tool; reverting the integration PR restores the prior pipeline text and removes the tool in one step. No data migration, no stored-content move, no behavior change to existing surfaces. Standard rollback window.

### Operator and engineering detail

**Directional-not-authoritative handoff (#500).** `release/references/pipeline/stage-02-triage.md` §4 Inputs gains the statement that an approved ticket authorizes the problem/outcome, not its structural premise — downstream stages treat the ticket structure as a proposal to confirm or overturn at Solutioning. `stage-01-intake.md` §6 Outputs carries the forward-pointer and `core/schemas/stage-io-contracts.md` records the Stage 1 → Stage 2 boundary. Principle statement only; the enforcing gate is #501 on milestone `68-stage-gate-criteria-completeness` — composed-with, not duplicated.

**Priority-model decomposition (#283).** `stage-02-triage.md` splits priority's former triple duty (urgency / importance / scope) into urgency vs value with a dependency-count triage signal; `.github/ISSUE_TEMPLATE/improvement.yml` is reconciled to match. The public corpus stays methodology-neutral — no hardwired WSJF or other formula is bound.

**Native-dep mirror promoted to a tracked tool (#662).** The Stage 2 A3.5 native-dependency mirror, previously re-derived each run, is promoted to a tracked tool (AS2) at `release/tools/native-dep-mirror.py` with a fixture test (`release/tools/tests/`). The parser is line-directional, ignores relates-to / sibling edges, and is comma-safe against real-format input.

**Related-issue-cluster threshold + tracking selection (#280).** `stage-03-bundle.md` documents a Stage-3 cluster-detection threshold and a tracking-mechanism selection rule over the existing epic / cluster / sub-issue primitives — a rule over what already exists, not a new primitive.

**Stage 3 A6 fires per-milestone behind gate G3-17 (#292).** `release/governance/release-process.md` makes the Stage-3 A6 New-Track Placement Rationale fire per milestone rather than once per MAJOR track, and `core/schemas/gate-criteria-spec.md` adds the enforcing gate **G3-17** (G3-13 retired per ADR-012; G3-14/G3-15 shipped via closed #293/#294; G3-16 reserved for the cross-milestone gate). This edit is what changed release-planner's source and triggered its package rebuild at release-cut.

**Sub-task container threshold (#225).** `stage-06-engineering.md` defines a threshold for the Stage-6 sub-task container choice (formal GitHub sub-issues vs a lighter PR checklist). It sits on a forward edge to #213 (milestone `74-controlled-deployment-environment-and-modes`) and ships regardless of #213's state.
