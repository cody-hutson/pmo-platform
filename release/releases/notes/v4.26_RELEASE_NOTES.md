# Checks stop failing correct work, and say when they are switched off

2026-08-15 · v4.26

A check that fails work which is actually correct trains you to ignore it, and a check that can be switched off without a trace is one you cannot trust when it passes. This release fixes both shapes across five platform checks, and closes two gaps where a problem could only surface late — an unsigned commit, and a tool that quietly left packages out of date.

## What changed for everyone using the platform

- **A correct setup no longer gets failed.** The corpus-home tolerance suite used to report a properly-built resolver as a violation; it now passes one, and a companion test proves it still fails a resolver that does not actually demonstrate the rule. *Why it matters:* you can act on this suite's red again — a failure now means something is genuinely wrong, rather than something merely being done correctly in a way the suite did not anticipate.

- **Switching a check off is now a visible change.** That suite's on-or-off state lives in a committed file, so turning it off shows up as a change someone reviews. *Why it matters:* a check cannot go quiet without anyone noticing, so a green result means the check actually ran.

- **Two result labels that could never be recorded now record.** The audit trail rejected two of its own outcome labels, so those results had nowhere to go and were simply lost. *Why it matters:* release verification results now land in the audit trail instead of vanishing, so the record of what was checked is complete.

- **Acceptance criteria are checked when work is bundled into a release.** Bundling now looks for a work item's acceptance criteria and reports when they are missing. *Why it matters:* missing criteria surface while the release is being assembled rather than at the quality gate, when there is far less room to fix them. This is logged but not blocking today — nothing is stopped, so you will see the report without any change to how releases run.

- **An unsigned commit is named before the merge, not after.** A pull request now reports any commit that is not signature-verified, with its identifier. *Why it matters:* previously this showed up only as an unexplained "blocked" state at the merge itself, with no indication of the cause — the fix is now obvious at the point you can still act on it.

- **Renumbering tells you what it made out of date.** When the tool renumbers architecture decision records, it now names each packaged skill the renumber left stale and prints the exact command to rebuild them. *Why it matters:* you are told what to do next instead of finding out later from a failing freshness check.

## Known limits

- **The acceptance-criteria check reports but does not stop anything.** It ships in a logged-but-not-blocking posture by operator decision, so a work item bundled without acceptance criteria is surfaced, not rejected. Tightening that is a separate decision.
- **Three safeguards ship without a proof that they can fail.** Each of the five checks above was itself tested by deliberately breaking something and confirming the check caught it. The smaller safeguards that guard three of those checks could not be tested the same way, because the test tooling is not permitted to run under the current script-execution rules. That block is tracked at #5501. No evidence suggests these safeguards are broken; the release simply cannot prove they are not.
- **The signature report does not block a merge.** It is advisory by design and is deliberately not a required check, so an unsigned commit is named but not stopped.

Report issues on the platform's GitHub issue tracker.

## Reversibility

CHEAP / HIGH. Reverting the release merge restores every file; the two added files are a plain-text posture marker and an advisory workflow, and neither holds state anything else depends on. No operator data is touched and no migration runs.

### Operator and engineering detail

**The false red was coupled to conformance, which is why it looked like an arming problem.** The tolerance suite's R5 rule failed a resolver *because* that resolver was conformant on CH-1 — the more correctly it tolerated an absent root, the more certainly R5 mis-verdicted it. The Stage-4 rationale attributed the failure to the `ARMED` disjunct of `a != 0 && (ARMED || b == 0)` and sequenced the arming card behind the discriminator card on that basis. The Stage-5 spoke falsified the stated cause by deleting the disjunct: R5 still failed, because `b == 0` satisfies it alone. The sequence was retained on two surviving grounds — shared-file serialization, and the principle that a posture assertion should not be pinned against a mis-verdicting suite — and the record says the original cause was wrong rather than quietly keeping the conclusion.

**The event-log label registry gained the two subtypes it already documented.** Label validation in the append tool was scoped by `event_type` alone, so `qc4-05-result` and `qc4-06-result` were structurally un-emittable despite being named in the schema's own emit table — the Stage-13 invariant and goal-attainment results had a documented home and no way to reach it. Validation is now scoped by the `(event_type, event_subtype)` pair. A row carrying one of the newly-emittable subtypes looks like this — ten pipe-delimited columns, subtype in the fifth:

```
| ts_iso | version | stage | event_type | event_subtype | actor | subject | reversibility | outcome | payload |
| 2026-08-15T03:40:00Z | corpus-tolerance-and-hygiene | 13 | release-synthesis | qc4-05-result | spoke:#5126 | milestone:#324 | CHEAP | resolved | invariant:AV-1; verdict:PASS; files:release/tools/append-pipeline-event.sh |
```

**Cross-issue acceptance criterion 4 shipped PARTIAL under an Operator Override Record, and is not recorded as satisfied.** The criterion requires every check the release ships or repairs to be mutation-proven. Every shipped *gate* is; the anti-vacuity *controls* guarding three of them are not, on the tolerance-discriminator card, the arming-sentinel card, and the renumber-disclosure card. All three trace to one cause — the package builder and the affected suites hold no script-execution-allowlist entry — so no spoke session could falsify them, which is a structural block rather than a diligence gap. Six spokes hit that control across Stages 5 through 8 and not one routed around it, including after a documented matcher gap (#5285) was available; each surfaced the block and left the check explicitly unverified. The operator declined to edit a security control's allowlist mid-flight in a scope-locked release, and recorded the override instead. The residual is stated rather than minimised: three controls ship without a demonstrated failure mode, and if one were itself vacuous the release would not detect it. Tracked at #5501; a future release that closes it should re-run the three arms and settle the criterion properly rather than inheriting this disposition.

**One defect class recurred five times in a single release, and it is the most transferable finding here.** Each instance was durable text asserting more than had been verified: a comment block, a specification line, a runtime headline, a function contract, and a plan summary line. All five were corrected in-release, each by narrowing the assertion to what actually holds rather than by deleting the claim or widening the capability. The recurrence across five different surface types — code comment, spec prose, user-visible output, API contract, planning document — is what makes it a class rather than five unrelated slips, and worth watching for in the next release.

**The version slot moved four times before it settled.** This release was determined as `v4.22`, then `v4.23`, `v4.24`, and `v4.25` as sibling releases merged ahead of it — the last of those during this release's own first Stage-12 attempt, which halted on a stale-branch guard rather than merging. The claim finally bound `v4.26` at the atomic compare-and-swap, first attempt, no collision. There was no provisional label to correct: the release carries no version literal in its branch name, plan filename, or pull-request title, so the comparison was vacuous by construction rather than skipped.

For the full merge, tag and claim record — including the halted first Stage-12 attempt and the branch-freshness guard that stopped it — see the `#### Deployment Log v4.26` block in the release log, and the release plan for design decisions, probe records and verification evidence.
