# Stage 12 no longer pushes to main; rebuilt packages land only by pull request

2026-10-28 · v4.80.1

The release procedure's deploy stage no longer contains a step that commits in your primary checkout and pushes straight to `main`. Everything a release lands now goes through a pull request and its required checks, and a rebuilt skill package reaches `main` only in the pull request of the change that edited the skill.

> **Skip the rest** unless you run releases through the release pipeline, write or follow release briefs, or edit a skill.

## Who this affects

- Operators and sessions that run a release's deploy stage (Stage 12), and anyone who writes or reads the briefs those sessions follow
- Anyone who edits a skill and lands its rebuilt package

## What changed for everyone using the platform

- **Stage 12 no longer commits in your primary checkout or pushes to `main`.** The step that staged rebuilt packages in the primary checkout, committed them there and pushed them straight to `main` is removed, together with the table row that described that push as intended. *Why it matters:* nothing a release lands can skip a pull request and its required checks, and running a release never writes to the checkout you browse.
- **A rebuilt skill package reaches `main` only through a pull request.** When a change edits a skill, the package is rebuilt in that change's own pull request, before the merge, and Stage 12 rebuilds no package of its own. *Why it matters:* a rebuilt package is checked like any other change, and the merged tree already carries the current package when a release deploys it.
- **Briefs that still name the removed step get an answer.** A one-line note stands where the step was, saying it is removed and where package rebuilds land instead. *Why it matters:* an older brief or checklist that names the step leads to a plain "removed", not to a missing section or an old command.

## Known limits

- The removed step never ran in a release. Its trigger could not occur, and its commands aimed at a folder that is not a repository, so this release closes a latent path rather than reversing a habit.
- The release rollback procedure still pushes its revert straight to `main`. That is a separate defect, owned by [#8427](https://github.com/cody-hutson/pmo-platform/issues/8427).
- Saved release briefs from earlier releases, kept outside the repository, can still quote the removed step's commands. This release does not edit them; each new brief is written from the current procedure.
- The last part of this release's success test is not observed yet: the next release that rebuilds a skill package is the first to show that package landing through a pull request.

Report issues at https://github.com/cody-hutson/pmo-platform/issues, and report a suspected vulnerability privately as the [Security Policy](https://github.com/cody-hutson/pmo-platform/blob/main/SECURITY.md) describes.

## Reversibility

CHEAP / HIGH. Reverting the single release merge restores the seven documents and the plan, and the next deploy re-lays the one deployed rules file from source; the version tag is kept as the record that the version was claimed. A revert puts the removed step and its push back into the procedure.

### Operator and engineering detail

**The removed phase.** Phase J.5 of the Stage 12 shard (steps J.5.1 to J.5.5) staged rebuilt packages with `git -C` aimed at the primary checkout, committed them there and ran `git push origin main`, and the merge-verification applicability table stated that direct push as intended. It contradicted three standing rules: every change goes through a pull request, the primary checkout is read-only for sessions, and a spawned spoke has no primary access. Admins are not held to branch protection on `main`, so had it run, a push made with the operator's credentials would have landed unreviewed. The phase is deleted rather than rewritten, because its trigger cannot occur: the Phase B4 deploy runs from the session worktree and copies packages without rebuilding them, and the post-merge hook deploys without rebuilding. A one-line, command-free marker stands where the phase stood, and its applicability-table row is gone.

**One invariant, stated where the rules live.** The release-process governance file's Stage 12 section gains a paragraph headed "Package rebuilds land by pull request; Stage 12 rebuilds none." It names the places a rebuild happens (the Stage 6 package-rebuild beat in the release PR, the Phase B3 claim-version stamp commit for a `--stamp-file` artifact, Stage 13 Phase B5.9 in the Stage 13 chore PR, and a partial-deployment fix-forward's own chore PR) as examples, not a closed list, and keeps the freshness gate's posture text and its warning that a gate does not discharge the rebuild obligation. The same rule is carried by the references-only disposition in the Stage 12 shard and by the skill-deployment rules file, whose Deployment Step 3 is now owed before the merge, in the pull request of the change that edited the skill.

**The reference cascade.** The same commit carried the change to the Stage 13 shard, the hub-spoke bridge, the partial-deployment recovery standard (its fix-forward now rebuilds a stale package with the canonical builder and lands it by chore PR, and a Check-1 probe line that read the primary checkout is dropped) and the decision-outcome tracking standard. A sweep for the phase's name outside the release corpus read 20 lines in 7 files before the change and 3 after, each kept with a reason: the removal marker, one retrospective evidence line and one history list. One edited line also carried a spent introducing-release cutover clause, replaced with the unconditional form in the same edit so the fragile-reference check stays green without a file-wide exemption.

**How it shipped.** One card on one branch: Commit 0 (the plan), the change set, and the evidence update, then a Stage 6 fix cycle that landed three Stage 7 findings. Stage 7 passed with no blocker, and Stage 9 returned GO WITH CONDITIONS. The release merged at `b35a87db` and claimed `v4.80.1`, a patch on `v4.80`, with a signed annotated tag on the first attempt. Phase B4 ran with no targets and re-laid the rules mirror, including the one changed rules file; no package was rebuilt and no schema changed. No release note existed at Stage 12, so the GitHub Release is created at this close.

For full implementation detail see the Deployment Log v4.80.1 entry in the release log, and [the release plan](https://github.com/cody-hutson/pmo-platform/blob/main/release/releases/plans/v4/v4.80.1_RELEASE_PLAN.md).
