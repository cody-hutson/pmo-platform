# Bundle protocols — domain best-practice sourcing, standing Parallelization Map, cascading-rebundle

2026-06-02 · v1.03

This release codifies three bundle-and-planning protocol improvements within the Pipeline Discipline track. Releases on an unfamiliar domain now either source authoritative external guidance or explicitly flag the gap before planning proceeds; every milestone now carries a standing, dated Parallelization Map that operators stop re-deriving by hand; and a re-milestone event that strips a milestone's namesake deliverable now triggers automatic re-evaluation of that milestone rather than leaving a stale namesake-without-deliverable on the books.

## Who this affects

- Anyone running a Stage 4 Planning pass (planning now includes a domain best-practice sourcing-or-flag step before sequencing; pipeline-internal releases are exempt and record an explicit exemption marker)
- Anyone bundling or planning a milestone (each milestone now carries a standing Parallelization Map in its description, reconfirmed at Bundle and at Planning entry)
- Anyone moving an issue between milestones (re-milestoning the work that defined a milestone's identity now triggers re-evaluation of the milestone it left behind)

## What changed for everyone using the platform

- **Planning now sources or flags domain best-practice.** Before a Planning pass sequences the work, it determines whether the release operates on a domain whose external best-practice the platform does not already encode. If so, it either cites authoritative guidance or attaches a machine-readable provenance marker that records the gap, a date, and a one-line reason. *Why it matters:* a release that touches an unfamiliar domain can no longer proceed silently on assumed knowledge — the gap is either filled or visibly recorded for the operator to weigh.

- **Sourcing carries through Solutioning and gets checked at Dev Testing.** When design work is activated, it inherits the provenance marker and tries to upgrade an unsourced gap to a cited source where design exposes a concept worth grounding. Dev Testing then verifies the marker is present and dated. *Why it matters:* the sourcing decision travels with the release as a visible, checkable record instead of being a one-time prompt that gets lost.

- **Every milestone carries a standing Parallelization Map.** Each milestone's description now holds a dated record of which other in-flight milestones it can run alongside, which ones hard-block it, and which ones it is only loosely coupled to. The map is reconfirmed at Bundle and again at Planning entry, and goes stale-flagged when its date falls behind. *Why it matters:* operators stop re-deriving the "can these run in parallel?" answer from scratch on every ask — one durable, queryable artifact answers it and is kept current at the boundaries where it can drift.

- **Re-milestoning a namesake deliverable triggers re-evaluation.** When an issue that defined a milestone's identity is moved to a different milestone, the milestone it left enters re-evaluation — amend, re-bundle, or defer — instead of silently retaining a name with no remaining work behind it. *Why it matters:* milestones no longer accumulate stale namesakes after their defining work is reassigned; the bundle stays honest about what it actually contains.

## Known limits

- The three protocols apply going forward. The Parallelization Map convention and the cascading-rebundle protocol do not retroactively bind milestones that predate their adoption — those carry no map by construction and trigger no re-evaluation for historical re-milestone events. The sourcing step's cutover follows the same forward-only discipline, and this release itself is exempt from satisfying the conventions it ships.
- Automatic detection of an unfamiliar domain is not yet built in. The sourcing-or-flag step relies on a planning-time judgment (with an explicit unsourced-flag path) rather than auto-detection; an automated detector is deferred to a follow-up.
- The Parallelization Map can be drafted as a natural extension of the existing cross-milestone dependency mapping, but auto-population is a recommended convention, not an enforced gate.

Report issues through the standard intake process.

## Reversibility

CHEAP / HIGH. All three protocol changes land together as one release; reverting the release reverts the slice atomically. The changes are documentation and protocol-definition edits only — no schema migrations with data impact, no breaking interfaces, no new source files. Standard rollback window.

### Operator and engineering detail

**Authoring-standard change (in-release).** This release adopted a stricter authoring standard for durable release-corpus content, enforced through three correction cycles during integration review: governance and release-corpus entries authored from this release forward are link-free and version-reference-free — content is summarized inline and described by capability rather than by issue or PR citation, so each entry stands on its own when read in isolation. These release notes, the changelog entry, and the digest entry for this release follow that standard. The pre-existing index and digest rows from earlier releases were left as-authored (the catalog-wide convention question is routed to the operator separately rather than restyled here).

**Domain-best-practice sourcing-or-flag step.** A Stage 4 Planning sub-step (between milestone validation and sequencing) requires either sourcing authoritative external guidance for the release's domain or emitting a machine-readable provenance marker recording an unsourced domain with a date and a one-line reason. Software, governance, and pipeline-internal releases are exempt and record an explicit pipeline-internal exemption marker with a date, preserving the no-extra-ceremony posture for internal releases. The marker schema is inlined in the Stage 4 Planning spec rather than split into a separate standard. Stage 5 Solutioning inherits the marker and may upgrade an unsourced gap to a cited source during design refinement; carry-forward without upgrade is acceptable when the design genuinely does not depend on external practice or the source is inaccessible at design time. Stage 7 Dev Testing adds a provenance-verification check (one of seven structural checks; conditional, warning-class) asserting the marker is present and dated. The sourcing marker and the existing evidence-grounding discipline are independent and may both apply to one spec — one grounds claims about external domain practice, the other grounds canonicalizations of internal conventions.

**Standing Parallelization Map convention.** Every milestone reaching Stage 3 Bundle carries a dated map section in its milestone description recording parallel-safe, hard-blocked, and soft-coupled relationships to other in-flight milestones. It shares the milestone-description persistence surface and read path with the existing rationale-in-description convention. A hard-versus-soft edge classifier — a reproducible grep over issue bodies that sorts each cross-milestone reference into hard (blocks / depends on / requires / after), soft (composes with / coordinates with / adjacent to), or file-contention (same file as) — is the canonical edge-class semantics applied during reconfirm, and lives in the release-planner dependency-analysis reference. Reconfirm fires at two boundaries: the Stage 3 bundle-mutability refresh checkpoint (a new staleness trigger for an absent or stale-dated map) and the Stage 4 Planning entry currency check (a stale-dated map routes a minor adjustment to re-run the scan and update the date, or escalates to a scope change when re-running surfaces new hard edges that materially change sequencing). The map is positioned as a standing-reference-and-reconfirm layer, explicitly distinct from the gate-emission surface.

**Cascading-rebundle protocol.** When a re-milestone operation moves a milestone's namesake-defining work to another milestone, the donor milestone enters re-evaluation under the existing bundle-mutability classification (amend versus re-bundle versus defer per the churn-budget threshold). A new mutability trigger captures this surface so future re-milestone events automatically prompt donor-milestone re-evaluation. The trigger fires independently of the queue-depth, priority-shift, dependency-state, boundary-currency, and map-staleness triggers, and composes naturally — a single re-milestone event may also surface a priority shift among remaining issues or move hard-deps cross-milestone. Disposition is recorded in two surfaces: a bundle comment on the donor milestone naming the trigger, the moved issue, and the chosen disposition; plus a release-plan deviation-log entry when the donor milestone is mid-pipeline. The protocol governs future re-milestone events only and does not retroactively re-evaluate historical ones.
