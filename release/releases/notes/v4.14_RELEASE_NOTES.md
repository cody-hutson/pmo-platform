# The gates now measure what they claim, and reach only the right work

2026-08-07 · v4.14

The platform's deploy-time checks were reporting on the wrong things — reading a field from a place the platform does not use, judging the whole backlog instead of the release in front of them, and failing work that was correctly filled in. Every one of those instruments now measures the thing it claims to measure, and the number of cards the main gate blocks on fell from 258 to 1.

## What changed for everyone using the platform

- **The deploy-time readiness check now judges the release being deployed, not the entire backlog.** It used to evaluate every open card in the backlog on every deploy, so an unrelated stale ticket could stop work it had nothing to do with. The set of cards it enforces against went from 258 to 150 to 1 — and that one survivor was a real problem inside this release's own work. *Why it matters:* when a deploy is stopped now, the reason is something you are actually shipping.

- **Correctly-filled-in tickets stopped being failed by a label check.** The check did not know about the two newest ticket forms, so it graded them against a rubric written for a different shape. Measured over the live backlog, 112 of 304 findings — 37% — were this false alarm on cards that were labelled correctly. That count is now zero. *Why it matters:* every finding the check reports is now worth opening, because none of them are noise.

- **The priority check stopped looking in the wrong place.** It read a ticket's priority from a carrier the platform does not actually use, so it failed most of the tickets it looked at for a reason that had nothing to do with their readiness. *Why it matters:* this was the measuring instrument the release's bigger scope decision depended on, so it was corrected first and every later count was taken on repaired data.

- **A failing required check now counts against a release at its go/no-go review.** Two review stages never read the one signal that actually blocks a merge, so a release could be recommended for approval while a required check was red. *Why it matters:* the review that decides whether to ship now sees the same evidence the merge button does.

- **The pipeline's own records stopped tripping the pipeline's own gates.** Its stage tickets were being created without the label its checks key on, so the platform's own paperwork failed its own rules. Backfilling 74 of them lifted a coverage figure from 308 to 366 and cleared four releases that had been falsely reporting they had no stage records at all. *Why it matters:* four releases that looked unmonitored were simply mislabelled, and the difference is now visible instead of assumed.

- **The gate caught a problem aimed at itself, before it could cause one.** The check that identifies which release is in flight was reading only the first page of results. This release's own milestone sits at position 188 of 217 — past that first page — so as originally written the check would have failed to recognise the very release shipping it. *Why it matters:* the fix was proven against the exact case that would have broken it, rather than against a hypothetical one.

- **New advisory review asks whether a ticket's promised outcome can come from the files it says it touches.** When a ticket claims more than its own stated scope could produce, triage now says so in its summary. It only comments — it never blocks a ticket from being accepted. *Why it matters:* the most expensive failure in the pipeline is discovering at build time that the plan was bigger than the files it named.

## Known limits

- **One check's not-applicable message still describes a component that was not built.** When no release is in flight, the readiness check reports that a backlog-wide detector is unaffected — but that detector was never built in this release. The message is wrong; the behaviour around it is correct. It was left in place deliberately because the line sits in a file three other in-flight changes were editing at the same time, and it is recorded in the release record rather than quietly fixed.
- **Half of one acceptance criterion could not be demonstrated and was accepted by explicit operator override.** The documentation-impact gate could not be shown to behave identically before and after, because that gate has no test coverage anywhere in the repository — not a missing case, no coverage at all. The override is recorded with its rationale rather than the criterion being marked passed.
- **The amount of enforcement did not change in this release.** Findings that used to stop a deploy and no longer do are still reported, at a lower severity, with that severity named. A drop in the failure count is a measurement fix, not a loosening of standards.
- **The new advisory review does not apply to tickets filed before this release.** It runs only on tickets entering triage after this release shipped, and it does not run against this release's own tickets.
- **One check that guards merges is failing for a reason unrelated to merge safety.** Its search pattern matches a close-style word followed by a bare number, which collides with ordinary text. It is not one of the required checks and did not block this release. Tracked in [#4976](https://github.com/cody-hutson/pmo-platform/issues/4976).

Report issues at [github.com/cody-hutson/pmo-platform/issues](https://github.com/cody-hutson/pmo-platform/issues).

## Reversibility

MODERATE / HIGH confidence. Nine of the ten recorded risks revert cleanly at whole-release and per-ticket granularity, because each ticket is exactly one commit. Two do not: applying a label to 74 tickets is a change to tracker state outside the repository and must be undone there, and a deploy that ran between the merge and any revert ran under the changed enforcement scope and cannot be un-run. Two skill packages were rebuilt inside the release, so reverting either content change must rebuild them in the same change.

### Operator and engineering detail

**One undifferentiated authority became a detector plus a release-scoped gate, and the split is recorded.** [ADR-120](https://github.com/cody-hutson/pmo-platform/blob/main/core/ADRs/ADR-120-g1-enforcement-authority-is-class-scoped-and-release-scoped.md) carries the durability contract. The decomposition behind the scope decision was measured by driving the shipped evaluation region over the live population rather than a replica — population 256, pre-filter 258, post-class-filter 150, demoted 108 (94 / 7 / 7 by criterion), post-milestone-filter 1 — and the design-time figures were deliberately not carried forward, because the population had moved from 169 at design time to 256 at build time. Every count in the record carries its own anchor and read date.

**Three of the seven commits ship hermetic regression nets that drive the shipped code rather than replicas of it.** Each extracts the real implementation between its own sentinels and grades it against a deliberately regressed copy that must go red. The release-identity net drives the shipped resolver against a stub honouring the live API's pagination semantics over a 201-row fixture; the form-family net reads its vocabulary from the source of truth so no ticket form is named in the test itself.

**A sibling check can now distinguish "named in another milestone" from "named in no milestone".** Previously both collapsed to one finding, so the operator could not act on either. The two now emit as separate sub-classes. Its call site remains a known weak point — it invokes the shared reporting helper without a guard, so a future severity change would silently make the advisory leg gating. That is tracked in [#4890](https://github.com/cody-hutson/pmo-platform/issues/4890) rather than fixed here, since it is outside this release's scope lock.

**The new triage determination is stage-local by construction.** It is deliberately not a registry criterion, which places it outside the judgment aggregate, outside the workflow-readiness pass set, and outside the deploy-time check's population — so there is no path from a firing determination to a blocked intake. Its entire output is one bullet inside the per-issue summary's existing feasibility-flags field; no field was added. The five emit values it can produce:

```
CONTAINED             evaluated; no limb fired
FLAG(<limb>, <shape>) evaluated; a limb fired
n/a(N#)               evaluated; a named guard applies
UNKNOWN(<reason>)     could not evaluate — never reported as CONTAINED
HELD(untrusted-body)  body flagged untrusted; surfaced as unverified
```

`UNKNOWN` is kept structurally distinct from `CONTAINED` on purpose: a degraded read and a clean read must never collapse into the same value, which is the same failure class this release exists to eliminate.

**One member ticket closed itself at the merge, and the guard that exists to prevent it could not have seen it.** A commit message carried a close keyword in its references block, and the tracker's parser reads commit messages on merge to the default branch — so that ticket closed two seconds after the merge rather than at close-out. The leak-detection check scans pull-request bodies only and never reads commit messages, so this release's one genuine auto-close path was outside its scope entirely, while the check simultaneously failed on a harmless text collision in the body. Impact is low — the work shipped in this release and the close reason is correct — but the scope gap is real and is handed forward as an intake candidate rather than fixed here, because changing a check is itself a governed change.

**Tool documentation coverage is a systemic gap, not a local one.** The tools reference documents 11 of 31 tools and carries no row for the sibling check at all. Tracked in [#4891](https://github.com/cody-hutson/pmo-platform/issues/4891).
