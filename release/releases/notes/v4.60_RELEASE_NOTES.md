# Checks that pass without looking now have to prove they looked

2026-09-06 · v4.60

Eight fixes to the platform's own deploy checks, unified by one finding: **a control that cannot reach the failure it names is not a control.** Several checks were reporting clean over populations they could not see, and one log family had been quietly unreadable for months — this release closes those gaps and adds the assertions that would have caught them.

## What changed for everyone using the platform

- **A deploy that changes nothing can no longer report success as though it did.** Deploying now compares against actual installed state instead of a stale marker.
  *Why it matters:* the previous behaviour could leave your installed copy days out of date while every message said it was current.

- **662 log records that could not be read at all have been recovered.** A stray tab character inside one field had been making whole records invalid, so anything reading that log silently skipped them.
  *Why it matters:* those records are the audit trail for deploy warnings. Skipped records do not look like errors — they look like a quieter log, which is why this went unnoticed.

- **The security hooks installed on your machine are now checked against their source.** They had drifted, and nothing compared them.
  *Why it matters:* a security control that has silently diverged from what was reviewed is the one you would most want to know about.

- **Deploy warnings now say which release they belong to.** A deploy run without a release identity says so out loud instead of recording nothing.
  *Why it matters:* previously, "deployed nothing" and "deployed without saying what" were indistinguishable afterwards.

- **Two checks that were reading a drifted second copy of their own rules now read one source.** A third named the wrong decision record, which resolved to a real document and so looked correct.
  *Why it matters:* a check quoting an outdated copy of its own criteria gives an answer that is confidently wrong rather than obviously broken.

## Known limits

The follow-up work this release surfaced but deliberately did not absorb is tracked and open:

- **#7208** — one parity check still passes vacuously on two independent vectors and has no test coverage; three sibling controls certify nothing.
- **#7209** — three restated facts in the deploy script have drifted from their source, including a leg-set that contradicts a CI workflow.
- **#7210** — two static analyses anchor on indentation, so each is blind to a legitimate call site or definition.
- **#7211** — release-plan fields cache a pre-correction read; one verification row instructed a step that could not produce its evidence.
- **#7212** — a second log sink still writes unescaped, the same defect class fixed here.
- **#7213** — three silent-staleness vectors in the deployed-skill surface.
- **#7214** — a warning naming a file this release introduced, needing a disposition.
- **#7204** and **#7206** — the hook-publisher baseline self-latch, and a false positive in the pipeline-idiom gate.

One decision was deliberately left open rather than settled: which carrier should regenerate the deployed hook tier. It sits downstream of the self-latch defect in #7204, so deciding it now would settle the question on the wrong axis.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE**, confidence **HIGH** for the repository changes and **MODERATE** for the recovered log family. Reverting the merge restores the previous state of every tracked file exactly, and the version tag is retained as the record that this version was claimed. The log recovery ran outside version control against roughly 110 MB of live data; it was applied only after a dry run reported zero unrepairable records, and the row count was verified unchanged at 447,801 before and after, so no record was lost.

### Operator and engineering detail

Raw audit detail is on the `v4.60` row of the release log, anchor `#deploy-checks-hardening-batch`.

**The release found its own thesis nine times, then produced a tenth.** Each card began as a separate defect, but every one resolved to the same question — not *is the code right?* but *can the thing that would catch a failure actually reach the failure?* The instances included a test with no executor, a gate blind to one call shape, two control arms printing PASS while certifying nothing, a harness writing evidence no arm read, a change manifest nothing reconciled, and a completeness marker asserted by nothing. The tenth appeared during verification: the acceptance test for "deploy reports success while doing nothing" asserted a failure it could never reach, because the deploy makes its target writable as the first step of its own repair and so undid the test's staging. It was reporting a **correct** green deploy as the defect it was written to catch.

**Five new test suites could not execute before merge, by construction.** Their allowlist entries exist only on the release branch while the deployed allowlist publishes from the main branch. Four acceptance criteria were therefore graded PARTIAL rather than accepting "the test exists" as satisfying "a control confirms it", and were dispositioned to be settled by the pull request's own required checks. All four resolved to MET on that evidence, with no override records. Three defects surfaced only at that point, two of them regressions this branch introduced — a required check went red and was repaired before merge.

**Stage-13 close-out refused to proceed on a missing input**, declining to append a release-learnings block because the learnings had never been captured, and explicitly rejecting hand-assembly as producing by hand exactly the unevidenced record the phase exists to refuse. The learnings were captured as events first.

**Seventeen residual findings were routed to tracked homes rather than closed at the milestone boundary**, and the action-item ledger closed at zero unresolved of 124 recorded.
