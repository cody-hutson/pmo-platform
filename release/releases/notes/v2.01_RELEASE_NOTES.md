# Seven skills get stricter: enforced estimation, lifecycle and gate checks, RAID dedup, watermelon scanning, formula-driven status, and quality scoring

2026-06-16 · v2.01

Seven existing skills gain real enforcement without any new skill being added: the delivery engine now enforces estimation discipline, a 15-stage lifecycle and a 10-gate ladder, and classifies tech debt; the PPM agent scores and governs intake; the tracker manager de-duplicates RAID entries; the weekly roll-up scans for projects that look green but aren't; daily status drives its colour from a formula; and the process designer and technical analyst score requirement and design quality. Every change is additive — nothing is removed or renamed.

## What changed for everyone using the platform

- **The delivery engine now enforces estimation discipline.** Estimates are checked against a buffer-and-variance standard the skill already carried, instead of being accepted as-is. *Why it matters:* an estimate that is missing its buffer or sits outside the expected variance is flagged when you run the check, not discovered later in the sprint.

- **Work is now tracked through a 15-stage lifecycle with a 10-gate ladder.** The delivery engine places each item on a defined 15-stage lifecycle and runs a ten-gate check that returns pass, conditional, or fail at each gate between the stages. *Why it matters:* you can see exactly which stage an item is at and which gate is holding it, rather than inferring progress from status text.

- **Tech debt is now classified and ranked, with a capacity floor.** The delivery engine applies a Fowler-quadrant classification and a Cost-of-Delay ranking, and checks tech-debt work against a reserved-capacity floor with an aging read. When the input needed for the rework-rate is not present, the skill says it cannot compute the rate rather than inventing a number. *Why it matters:* you get a defensible order for paying down debt and an explicit "not computable" instead of a fabricated figure.

- **The PPM agent now governs and scores intake.** Incoming work runs through an intake-governance check and a WSJF priority score, and the agent detects the delivery org model and escalates RAID items that have gone stale. *Why it matters:* intake is prioritised on a consistent basis and an aging risk or issue is surfaced instead of sitting quietly past its review date.

- **The tracker manager now catches duplicate and cascading RAID entries.** RAID updates are checked for near-duplicates above a similarity threshold and for cascade relationships between entries. *Why it matters:* the same risk logged twice in slightly different words is caught before it clutters the register, and linked entries are surfaced together.

- **The weekly roll-up now scans for "green outside, red inside" projects.** The roll-up runs the platform's eight-signal watermelon scan — reusing the single owned copy of those signals rather than its own fork — alongside a metric-governance check. *Why it matters:* a project reporting green while its underlying signals are red is flagged in the roll-up, so a watermelon status does not reach the steering audience unchallenged.

- **Daily status now drives its colour from a formula.** The red/amber/green rating in daily status is computed from defined inputs, and buffer consumption is tracked alongside it. *Why it matters:* the status colour is reproducible from the numbers instead of being a judgement call that varies day to day.

- **The process designer and technical analyst now score quality.** The process designer scores requirements against INVEST, checks acceptance criteria are in Given-When-Then form, and classifies non-functional requirements against the ISO/IEC 25010 standard; the technical analyst treats accepted design decisions as immutable, scores design-document quality, and reads Accelerate/DORA delivery metrics. *Why it matters:* a weak requirement or an under-specified design is caught with a stated rubric, not left to a reviewer to notice unaided.

## Known limits

- The watermelon scan reads its thresholds from the project metric registry; a project that has not set an `investment_class` is reported as an "Unclassified" coverage gap rather than scanned against a class baseline.
- The tech-debt rework-rate depends on a rework-input source; where that source is absent the skill reports "not computable" instead of a rate.
- These are enforcement checks layered onto existing skill behaviour — the prior estimation, lifecycle, RAID, roll-up, status, and review outputs are unchanged except for the new checks running alongside them.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. The release is skill-file and reference-doc edits on one branch — additive only, no schema migration, no data change, no field rename. Whole-release rollback is `git revert -m 1` of the integration merge; per-skill rollback reverts that skill's commit. The three new reference docs and the supporting ADR are new files with no external reader to unwind. Standard 7-day rollback window.

### Operator and engineering detail

**delivery-engine estimation / lifecycle / gate / tech-debt chain (5 cards, serialized on one SKILL.md)** — The whole cohort is enforcement-wiring of pre-existing substrate. #264 establishes estimation buffer/variance vocabulary against `references/estimation-standards.md` (with `references/capacity-model.md` as a read-only reference). #265 adds 15-stage lifecycle tracking in `references/lifecycle-stages.md`. #266 adds a 10-gate PASS/CONDITIONAL/FAIL enforcement ladder in `references/gate-definitions.md`, the gates sitting between #265's stages (it edits `gate-definitions.md`, not `lifecycle-stages.md`). #366 creates `references/tech-debt-capacity.md` (capacity floor + aging + rework-rate) with a "not computable" fallback when the rework-input source is absent. #180 creates `references/tech-debt-classification.md` (Fowler quadrant + Cost of Delay) ranking against #366's floor with a lexicographic sort, and registers a row in `core/specs/framework-catalog.md`. The five cards were serialized on the shared SKILL.md in strict order with rebase-before-edit.

**ppm-agent intake-governance + org-model (2 cards)** — #253 creates `references/ppm-intake-governance.md` (intake governance + WSJF), renamed from the intake-desk basename to avoid a Check 13b shared-reference collision; WSJF is consumed by reference to `intake-desk/references/intake-governance.md §2`, not restated. #254 adds org-model detection derived from `delivery_approach` and stale-RAID escalation that wires the existing `references/escalation-thresholds.md`.

**Independent pool (5 cards)** — #251 (tracker-manager) adds RAID deduplication at a ≥0.70 similarity threshold plus cascade detection (`references/tracker-schemas.md`). #256 (weekly-status-rollup) consumes the canonical W1–W8 watermelon signal set via-public-api from `pmo-qa-auditor/references/watermelon-detection.md` and adds metric governance; `investment_class` becomes an optional project-template field (absent → "Unclassified"). #260 (daily-status) is a SKILL-only edit wiring formula-driven RAG + buffer tracking to existing registries with no new `references/` dir. #263 (pmo-process-designer) adds INVEST + Given-When-Then + ISO/IEC 25010 NFR enforcement (`references/process-checklist.md`). #259 (pmo-technical-analyst) adds ADR-immutability + FDD quality scoring (4.0/3.0) + Accelerate/DORA metrics (`references/technical-review-checklist.md`).

**Supporting decision — ADR-024 (Accepted)** — Records that an operations skill needing a core safety-control reference consumes it via-public-api by role-name rather than forking a module-local copy. It codifies the #256 watermelon reuse and reverses the Stage-4 plan's local-copy recommendation in favour of the Stage-5 design, on the reasoning that the operations→core direction is pre-authorized accepted cohesion (no code-import cycle) and a forked green-masking control silently diverges the moment the owner refines a signal. Sibling axis to ADR-023 (the skill ↔ Anthropic sourcing posture); both express one-owner-of-truth on different axes.
