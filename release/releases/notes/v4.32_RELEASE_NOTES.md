# A release's plan is now named by the release, not by hand

2026-08-16 · v4.32

Finding the plan behind a shipped release used to mean guessing at a filename nobody had updated. The plan file now takes its name and its home from the release itself, in the same step that fixes the version, and a release can no longer finish while the two disagree.

## What changed for everyone using the platform

- **A release's plan is named at the moment its version is decided.** The plan file is renamed to the version and filed under it in the same step that stamps the release, instead of being renamed afterwards by whoever remembered. *Why it matters:* the name on a plan is the version the release actually shipped as, so you can find a release's plan from its number without guessing.

- **Fourteen plans that had drifted are back in their proper homes.** Plans left loose by a rename that never fired were folded into their version folders, with every link pointing at them repaired in the same move. *Why it matters:* those links resolve instead of dead-ending — eleven were found when this work was planned, and three more arrived while it was being done.

- **A release now stops if its plan is named for the wrong version.** A new check joins each plan's filename to the release record and refuses to let the release finish when they disagree. *Why it matters:* a mismatch surfaces at the release that caused it rather than being discovered three releases later.

- **Two releases in flight at once no longer make the naming step skip in silence.** The step that renames the plan is now told which release it is working on instead of inferring it from whatever it can see. *Why it matters:* a release that overlaps another still gets its plan named, rather than finishing with the name missing and nothing saying so.

- **A failed version claim now tells you what to run.** When the naming step fails after the version has already been fixed, the message names the version, the step that failed, the state the repository was left in, and a command that repairs it. *Why it matters:* recovering a half-finished release no longer means reconstructing what happened from the tooling itself.

- **A release that would package nothing stops before the version is spent.** The step that rebuilds changed skills now announces how many it expects to rebuild — including zero — and refuses ahead of the point where the version becomes permanent. *Why it matters:* an empty rebuild is caught while it can still be fixed, instead of after a version number has been used up.

- **The fault happened once more while this fix was under review, and the fix caught it.** A release that shipped during this one's review gate bound its version and left its plan un-renamed — precisely the fault being repaired. This release's own new check found it, and that plan was folded in here. *Why it matters:* the check is known to fire on a real occurrence, not only on a test built to prove it can.

## Known limits

- Links pointing at a plan's old loose filename no longer resolve. Every such link inside the platform was repaired in the same change; a link saved somewhere else was not, and there is no way to find those from here.
- Three loose plans were deliberately left where they are. One predates the version series this move covered, and two belong to releases that never took a version number at all, so there is no version to name them for. Moving them would have invented an identity rather than recorded one.
- The new filename check runs when a release closes, not before it merges. A wrong name is therefore caught at the end of a release rather than at its start.
- Plans older than this convention still carry names and homes from the previous scheme. They are recorded as known debt and tracked separately rather than repaired here.
- Ownership of the tool that carries the new check is still an open question, deliberately left open by this release rather than settled inside it.

Report issues at the repository issue tracker.

## Reversibility

MODERATE / HIGH. Reverting the single merge commit restores every message, gate and emitter at once. The exception is the fourteen file moves: reversing those is a second rename rather than an automatic undo, and a version number, once claimed, is never reversible by construction — which is the whole reason the naming step was moved to the instant the claim happens.

### Operator and engineering detail

**Six mechanisms, each hiding the next.** ADR-092 decided that a release plan binds its identity at the Stage-12 atomic claim rather than at authoring time. Six mechanisms carry that decision and every one was broken silently: the `{{RELEASE_VERSION}}` token was absent from the authoring contract that produces the plan, the `--stamp-slug` flag that consumes it was passed by nobody, the rename it triggers had not fired for three shipped releases, the close-out tool emitted a flat plan pointer at three sites while the claim files nested, no gate compared a plan filename against the ledger, and the post-claim failure message named a bound identifier without supplying a remediation. Each defect masked the one behind it, which is why the population of un-renamed plans grew unobserved. All six are closed; the release also adds a commit-time assertion that a plan carries its token before Engineering commits it, and a network-free verification verb that classifies a refusal into three mutually-exclusive verdicts rather than a single opaque non-zero.

**The relocation and its cascade.** Stage 4 measured the v4 relocation set at 11 plan files, 12 inbound referring files, 28 occurrences — correcting a milestone-description figure of 14 files and 37 referrers that did not reproduce under any tested interpretation. The delivered total is nonetheless 14, and the arithmetic is a coincidence rather than a vindication: the mainline shipped three further releases while this one was in flight, each leaving its plan flat, so 11 planned plus 3 late arrivals equals 14 by a different route. The move and its reference repairs land as one commit so the operation reverts atomically, and the relocation is committed separately from the mechanism fix so the expensive half reverts independently of the cheap one.

**The defect recurred at the review gate.** While this release sat at Stage 9, v4.31 shipped: tag bound, plan left flat. That is the exact failure this release exists to stop, occurring one more time, and it was surfaced by this release's own contention check rather than by inspection. The plan was folded into its versioned home at commit `36ee67a9` inside this release. The move left one dangling pointer behind it — v4.31's release note still named the plan's flat path in its `links.plan` field — and that pointer is repaired in this same close-out rather than deferred, since this release's own move is what broke it. Its published body is unaffected: the field lives in frontmatter, which is stripped before publication.

**Shape contracts this release changed.** The authoring template's Header gained a required token row, and the plan corpus gained a canonical nested destination that the close-out tool now cites from one place instead of three. The before-and-after of a single plan's identity:

```
# authoring template — the required Header row
| **Version** | {{RELEASE_VERSION}} |

# what the atomic claim writes, in the same step that pushes the tag
| **Version** | v4.32 |
release/releases/plans/plan-file-identity-adr-092_RELEASE_PLAN.md
  -> release/releases/plans/v4/v4.32_RELEASE_PLAN.md
```

**Enforcement stated honestly, and the residuals named rather than counted.** Mainline carries nine required status checks and none is a release-corpus or release-tooling check; the workflow running this release's new fixtures self-declares an advisory posture. No CI gate is proposed by this release and no merge-blocking effect is claimed — the new filename check is a close-time gate, which is a real block at a real moment but not a pre-merge one. Two documentation surfaces declared in the change matrix did not land on this branch and are named individually: the release-protocol reconciliation, which is Tier-0 operator-only and which the autonomy ceiling correctly refused to an agent — the finished replacement text is carried on the owning card's Stage-7 sub-task, surfaced rather than bypassed — and the release-log inbound-reference repair. Both files are byte-identical to mainline on this branch. Two review-gate residuals ship accepted at the operator's GO, with their substance verified from git rather than from the gate's own instrument: an absent file-change-matrix coverage record, and cross-issue criteria that carry no explicit method clause. Ownership of the corpus lint remains a held escalation and is unresolved here by design.
