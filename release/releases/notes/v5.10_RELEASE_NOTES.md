# The engineering harness has catalog pages, and CI fails when they go stale

2026-11-17 · v5.10

The process catalog now holds one page for each process in the engineering harness: install and update, the hooks, the deploy checks, the CI gates and the release tools. Planning and review steps for a harness change can now start from a current-state page instead of re-reading the scripts. A pull request that moves a line a page cites, or changes generated output without regenerating it, turns a catalog check red.

## Who this affects

- Anyone who changes a hook, a deploy check, a CI workflow, the installer or a release tool.
- Planning, design and close-out work on the harness, which now reads these pages.

## What you need to do

1. After pulling this release, run `./update.sh --surfaces-only` from the platform repository root, or a full `./update.sh`. It refreshes the script guard's allowlist with entries for the five catalog tools. Until it runs, the guard refuses those tools when an agent runs them.

## What changed for everyone using the platform

- **One page per harness process.** The catalog's first universe holds 48 pages. Each describes one process: what triggers it, its inputs and outputs, its steps, who acts, and the files it is built from, cited by line. *Why it matters:* a harness change can be planned from a written description of how the harness works today, and a page that disagrees with the code is corrected rather than trusted.
- **A generated index, graph and views.** An index, a machine-readable graph and 13 views are built from the pages. The views cover structure, jobs, state, data flow, interfaces and the controls each process relies on. *Why it matters:* you can find every process that touches a given script or control without opening every page.
- **A catalog check on every pull request.** CI runs three catalog checks on each pull request and on the main branch. The first confirms the generated output matches a fresh build, the second that every cited line still says what its page cites, and the third that every page passes the catalog's rules. *Why it matters:* a page cannot quietly fall out of step with the code it describes, and each failure names the one command that repairs it.
- **Pages name their measures, never one machine's numbers.** A page says what is measured and which script measures it. The figures themselves are generated on each install into a folder that is never committed. *Why it matters:* the published pages read true on every install and never carry one machine's numbers.
- **The tools that build and check the catalog ship with the platform.** The builder, the checker, the element inventory and the pre-publication scan each come with a self-test. *Why it matters:* the next two universes reuse the same tools, definitions and registers instead of starting over.

## Known limits

- Only the engineering-harness universe is published. The other two universes and the browse view come in later milestones.
- The three catalog checks are not required checks. A red run does not stop a release pull request from merging. It does hold the close-out tool's merge of a chore pull request, and the release's execute and close steps read the run on the main branch.
- A fresh clone shows each measure and the script that produces it, not a value. The value appears only after that install generates its own figures.
- Two comparison rows on one page and one measure were held out of this release, and one page states a self-test property more widely than its sources support. The release's follow-up sweep, [#9046](https://github.com/cody-hutson/pmo-platform/issues/9046), carries each of them.

Report issues at https://github.com/cody-hutson/pmo-platform/issues, and report a suspected vulnerability privately as the [Security Policy](https://github.com/cody-hutson/pmo-platform/blob/main/SECURITY.md) describes.

## Reversibility

MODERATE / MEDIUM. Reverting the single release merge restores the previous tree, because every change is a file addition or a bounded edit. Page text that reached the public repository stays in its history, and the version tag is kept as the record that the version was claimed.

### Operator and engineering detail

**Where the catalog tools live.** The builder, the checker, the element inventory, the pre-publication scan and their shared library sit beside the deploy tools. They take this repository's paths as argument defaults. The placement is recorded on its card rather than in a new decision record.

**The definitions pack.** The catalog's vocabulary, its four page templates, the controls and identifier registers, and the tables the tools read are tracked together, with one machine-readable pack file the tools load. The published controls register carries only rows sourced to a tracked file. The sample below is the frontmatter of one published page, trimmed to its identity and link fields.

```yaml
id: bootstrap-workspace
level: L3
universe: engineering-harness
parent: install-platform
precedes: [validate-install]
triggered_by: [external:fresh-clone]
owner: operator
last_verified_commit: 7fae37579a54714fa6c56f469ab067b389219ad6
pack_version: 2
```

**Publication was signed and held.** Every push that changed page text, a generated file or the catalog README carried the operator's signature. The pre-publication scan is the step run before a push of catalog text. The execute stage checked the catalog and wrote nothing under it on its own. After the main branch moved, it carried two catalog repairs, each signed, that re-cited moved lines and re-verified the affected pages.

**CI posture.** The catalog checks fail from their first run and are deliberately not required contexts. The gate-efficacy standard records that posture, and the catalog README names the repair command for each check.

**Exit checks on the merge commit.** The milestone's own checks ran on the merge commit, each with a control that shows it can fail. The page validator read 0 errors over the 48 pages, while a planted invalid page read its planted error. The generator's self-test passed. Two regenerations matched each other and the committed output, and every link on the pages resolved. The depersonalization job and a project-name scan were clean, and the three catalog checks were green on the push to the main branch. The milestone's measured cost is recorded as the measure and the script that produces it; the figures stay with the install.
