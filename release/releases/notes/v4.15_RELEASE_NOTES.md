# Install and update stop losing the settings you already chose

2026-08-08 · v4.15

Installing or updating the platform used to quietly discard operator configuration: one setting was written empty on every single first install, hook registrations you had added were dropped on every update, and two files the update process promised to refresh were never actually refreshed. All three are closed, and a fresh install can now run start to finish with nobody at the keyboard.

## What changed for everyone using the platform

- **A fresh install can run unattended.** Passing the new non-interactive flag makes the installer take each setting's declared default instead of stopping to ask; when a required setting has no default, the install stops, names the missing setting, and writes no configuration file at all rather than writing a broken one. *Why it matters:* you can script or repeat an install without sitting through the prompts, and a run that cannot succeed tells you which value it needs instead of finishing with a hole in it.

- **The Cowork install location is no longer blanked on every first install.** The installer was storing that value under one name and the file writer was reading it under another, so the field was written empty every time and you were asked for it again on the next run — forever. Both halves now agree. *Why it matters:* the location you enter is actually saved, and the installer stops re-asking for something you already answered.

- **Your customizations to the managed settings file survive an update.** Previously the file was overwritten whole, with nothing checking whether you had added anything to it. Keys you added are now migrated rather than dropped, and the platform's own hook registrations are refreshed at the same time — a live install was missing four of them plus one whole block. *Why it matters:* an update no longer silently removes the hooks and settings you put there yourself.

- **Updating now refreshes CLAUDE.md, which it had long claimed to do but never did.** The refresh rewrites only the region between the managed markers; anything you wrote outside that region is left byte-for-byte alone, and the first time this runs on your machine it takes a backup whether or not it detects a change. *Why it matters:* you get improvements to the platform's core instruction file without hand-copying them, and your own additions to that file are not the price.

- **There is a new configuration section for git-native release automation, and every switch in it is off.** An absent file, an absent section, an absent key, an empty value, or any value other than the literal `true` all resolve the same way: off. *Why it matters:* nothing about your setup changes until you deliberately turn something on, and an install that never receives the new file behaves exactly like one where you turned everything off.

- **A setting that limits how much an agent may do without asking you can no longer be lowered by an unrelated key.** The two places that read that limit were matching on the key name alone without checking which section it belonged to, so any similarly-named key elsewhere in the file could silently drop the limit to its fallback value. Both now check the section. *Why it matters:* this failure ran in the permissive direction — it would have quietly widened what agents could do on their own, without telling you.

## Known limits

- **The unattended install needs its input stream closed.** With the terminal still connected, a fresh run reaches the hook-activation question and waits. Three of the four questions the installer can ask do not check the non-interactive flag; only the one covering settings does. This was found during testing, is outside what this release committed to, and is tracked in [#4994](https://github.com/cody-hutson/pmo-platform/issues/4994).
- **The preservation guarantee does not cover multi-line arrays.** A setting written across several lines is collapsed into invalid configuration by the file writer's single-line parser — the opening line survives and the continuation lines are dropped. Single-line values of every type are covered and tested.
- **New configuration keys still do not reach an existing install.** The update process warns about a changed configuration shape but performs no migration, so the new release-automation section arrives only on a fresh install. This is why every switch in it defaults to off when the key is simply absent, rather than requiring the file to be present and say `false`.
- **A fresh install still never receives several configuration sections at all**, so the features that read them run on their built-in fallback values. This was confirmed during the release and deliberately not bundled into it.
- **The check that would have caught the blanked-setting problem still cannot see it.** It scans one naming prefix, one file extension, and three of the four directories where these values are written — reaching 252 of 504 places they appear. Tracked in [#4992](https://github.com/cody-hutson/pmo-platform/issues/4992).
- **The standing install regression suite reports a failing verdict on an unmodified tree** when run the way its own specification says to run it. The failures are not real breaks, but the verdict is the signal a reviewer is told to trust. Tracked in [#4993](https://github.com/cody-hutson/pmo-platform/issues/4993).

Report issues at [github.com/cody-hutson/pmo-platform/issues](https://github.com/cody-hutson/pmo-platform/issues).

## Reversibility

MODERATE / HIGH confidence. Three of the four changes are additive and content-only and come out cleanly by reverting the release commit. The CLAUDE.md refresh does not: once managed markers have been written into your live file, reverting the platform does not un-write them. That is mitigated rather than undone — the regeneration routes through the existing tamper-backup path, so a bad refresh is recoverable from the backup taken on the first run.

### Operator and engineering detail

**The release found a live config-loss defect inside the subject its own gate was built to protect.** `[paths].cowork_install_path` was blanked on every first install because `resolve_token` stored the value under `[COWORK_INSTALL_PATH]` while `write_operator_toml` read the registered `[COWORK_INSTALL_PATH_BASE]`. It was fixed in scope under operator decision D-1531-D Option 1, as two one-token edits that had to land together — `core/CLAUDE.md.template` drives `ACTIVE_TOKENS` through `compute_active_tokens`, so correcting the resolver without the template would have removed the token from the active set instead of repairing it.

**The preservation gate probes with the consumers' own shape, and that was the sharpest call in the release.** Five production consumers read `operator.toml` with a line-anchored, section-blind `grep -E '^key'`. A section-aware assertion would have passed on an indented re-emit that every one of those consumers would have missed — silently dropping the autonomy ceiling to its fallback. Suite P therefore asserts with the consumers' shape, including `grep -c '^automation_level' == 1`. Arm P-8 is the negative control: it drives the comparator against a deliberately mutated copy (one table deleted, one key indented) and requires it to report a difference, so a green suite is provably able to fail.

**Both autonomy-ceiling readers were hardened from section-blind to section-aware while keeping the column-0 anchor.** This closes a fail-open on a security control at the reader rather than only at the writer, and the strict-parity variant was chosen on evidence: the permissive reader *raised* the ceiling from `recommend` to `bounded_auto` on 2 of 14 fixtures for an operator who had changed nothing — a security-posture widening delivered by an update.

**The new config surface landed on `platform-config.toml`, not `operator.toml`.** The Stage-4 matrix had assigned it to `operator.toml`; the ADR-022 identity/behavior split puts platform behavior on the other file. That relocation is what discharges the collision constraint by construction — the two surfaces are different files with no shared key name or key prefix. The shipped section, with its three switches and their in-code absent-key defaults:

```toml
[git_release_automation]
# Valid: true | false.  Default: false.
review_process_integration = false
# Valid: true | false.  Default: false.
ci_auto_resolve = false
# Valid: true | false.  Default: false.
comment_auto_resolution = false
```

The always-on facets — feature-branch creation timing and naming, and PR statusing — expose no dial, and their **absence** from the section is the declaration: no key matches `branch` or `status`, which is mechanically assertable. Resolution is deliberately narrowed to 2 rungs (global template and individual) rather than the usual 5, because the fact is platform-scoped.

**[ADR-122](https://github.com/cody-hutson/pmo-platform/blob/main/core/ADRs/ADR-122-claude-md-composition-surface-recategorization.md) was ratified CLAUDE.md-only, extending `COMPOSITION_SURFACE_FILES` rather than minting a parallel array.** That overturned #3831's own AC-2 — Stage 5 working as designed — and it decoupled #1355 from #3831, which let #1355 expand under [ADR-121](https://github.com/cody-hutson/pmo-platform/blob/main/core/ADRs/ADR-121-settings-json-baseline-anchored-refresh.md) to own the settings refresh rather than the release narrowing its Outcome Statement. The mechanism needed a marker dialect, because a comment fence has different syntax in each host file; the manifest entry format gained an optional fourth field for it:

```
# manifest entry: "<src-relpath>|<tier>|<tokens-flag>[|<dialect>]"
plain     → # === BEGIN MANAGED SECTION (regenerated by update.sh; do not edit) ===
markdown  → <!-- === BEGIN MANAGED SECTION (regenerated by update.sh; do not edit) === -->
```

The fourth field is optional and back-compatible; an entry that omits it resolves to `plain`.

**The release lost an identifier three times to concurrent releases, and the two kinds of loss cost very different amounts.** Two version slots went (`v4.13` at Commit 0, then `v4.14`) and cost nothing, because the version is carried as a token and bound at the merge claim. Two ADR numbers also went (119, then 120) and cost two citation sweeps — the first touching 34 references in the plan, the second touching 98 occurrences across 14 files, plus a residual the renumber tool's line-wise historical exemption could not handle and that was reverted by hand. The asymmetry between the two identifiers is filed as [#4995](https://github.com/cody-hutson/pmo-platform/issues/4995).

**Verification.** The full install regression suite reports `818 passed, 0 failed` at the release head under the real `$HOME`, with the hook floor at `571 passed, 0 failed`; the member added by this release contributes 114 of those. Both testers who ran it recorded that they had deviated from the mandated environment to obtain a usable verdict rather than hiding the deviation, which is what surfaced [#4993](https://github.com/cody-hutson/pmo-platform/issues/4993).
