# Triage backlog-hygiene checks that silently returned nothing are fixed

2026-06-14 · v1.24

The triage assistant's automated backlog-hygiene checks — finding issues with an orphaned (rejected or missing) dependency, and finding P1 work blocked by lower-priority work — were quietly returning nothing because of a shell-parsing bug, so those problems went unsurfaced even when they were present. The bug is fixed and the checks now return correct results. A stale cross-reference in the release-process documentation was also corrected.

## What changed for everyone using the platform

- **Triage now catches issues with an orphaned dependency.** The check that scans open issues for a dependency that was rejected or no longer resolves was silently returning nothing; it now reads each issue's dependency list correctly and flags the orphaned ones. *Why it matters:* an issue waiting on a dead dependency is surfaced during triage instead of slipping through to planning. ([#309](https://github.com/cody-hutson/pmo-platform/issues/309))
- **Triage now catches a P1 blocked by lower-priority work.** The escalation check that finds a Critical (P1) issue blocked by a lower-priority issue was hitting the same parsing bug and returning nothing; it now extracts each issue's priority correctly and flags the mis-ordered blockers. *Why it matters:* a top-priority item stuck behind lower-priority work is caught and raised for re-sequencing instead of stalling unnoticed. ([#309](https://github.com/cody-hutson/pmo-platform/issues/309))
- **A stale cross-reference in the release-process documentation is corrected.** A pointer in the release-process guide named the wrong section of the triage spec for where the "stale issues" check lives; it now points to the correct section. *Why it matters:* anyone following that reference lands on the right place instead of an unrelated one. ([#309](https://github.com/cody-hutson/pmo-platform/issues/309))

## Known limits

- These backlog-hygiene signals are advisory — they surface candidates for the operator during triage; they do not block a triage verdict on their own.
- This release corrects three carried-forward findings from an earlier triage release; it changes no skill behavior and ships no skill or package update (two pipeline reference documents are the whole changed set, plus a supporting CI-gate allowlist entry).
- The third carried-forward finding (a YAML-parsing dependency in the roadmap-cascade gate's detection bash) was not addressed here because that gate was already retired — see the operator detail below.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `cluster: process-protocol` label.

### Operator and engineering detail

**CF-2 — the silent-zero awk-range fix (#309)** — the Stage-2 Triage A6.5 management-task detection table extracted issue-body sections with the range form `awk '/^### Dependencies/,/^### /'` (and the parallel `/^### Priority/,/^### /`). That range is non-functional: the start regex `^### Dependencies` is itself matched by the end regex `^### `, so the range opens and closes on the heading line — the body content is dropped and the downstream `grep` returns nothing. Three instances in `release/references/pipeline/stage-02-triage.md` were affected — the Pattern (1b) orphaned-dependency extraction, the Pattern (2a) P1-blocked-by-lower dependency extraction, and the Pattern (2a) blocker-priority extraction — and all three were replaced with the robust `awk 'BEGIN{flag=0} /^### <heading>/{flag=1;next} /^### /{flag=0} flag'` form, which uses `next` to skip the heading line and a separate flag toggle to emit the body. Pattern (4a) (a `grep -cE` predicate with no awk) was correctly untouched, and the markdown table-cell pipe-escaping before each downstream `grep` was preserved (the BEGIN/flag awk contains no pipe, so no new escaping was needed).

**CF-3 — the stale cross-spec citation fix (#309)** — the Stage 2 Triage-cadence paragraph in `release/governance/release-process.md` cited the sister management-task spec's "Stale issues" detection as living at `Phase A4 (ii) detection-pattern (1a)`. That anchor was stale — the stale-issues pattern lives at `Phase A6.5 Pattern (1a)` in `stage-02-triage.md` (Phase A4 there is the unrelated feasibility quick-check). The underlying bilateral contract (the P1 SLA numeric feeding the sister spec's stale-issues input) is real and intact; only the citation anchor was wrong, and it was corrected to `Phase A6.5 Pattern (1a)`.

**CF-1 (yq toolchain) de-scoped — already resolved by ADR-012** — the third carried-forward finding targeted a `yq` YAML-parsing dependency inside the **G3-13 Roadmap-Cascade Validation** detection bash in `core/schemas/gate-criteria-spec.md`. That finding no longer has a live home: ADR-012 (roadmap-instance-descope, Accepted 2026-06-02) retired the roadmap-cascade enforcement surface — including the G3-13 gate criterion and its detection bash — because roadmap instances are operator-local, not reusable platform structure. With G3-13 retired there is no in-repo detection bash carrying the `yq` dependency to fix, so CF-1 was de-scoped at verification rather than engineered.

**CI-gate remediations + re-version** — three CI-gate remediations rode along on the touched lines: the operator-handle reference on the re-touched A6.5 lines was tokenized, an `allow-link` marker was added so the per-file reference-durability gate passes, and a `release/references/pipeline/stage-02-triage.md` entry was added to `core/hooks/reference-durability-allowlist.txt` so the issue-ref detector does not false-positive on two pre-existing `#`-shaped patterns the awk-fix and tokenization re-surfaced in the added-lines delta (the `#5-process` anchor fragment of a `[Phase B B3](#5-process)` link, and the `#[0-9]+` grep regex inside the detection bash — an anchor fragment and a regex, not net-new fragile refs; mirrors the sibling stage-03 / stage-04 / stage-12 allowlist entries). `routine` class, CHEAP reversibility, 30-day Stage 13 outcome window. **Re-versioned from the planned v1.21 to v1.24** per the #769 version-collision class: `v1.21`, `v1.22`, and `v1.23` were all claimed by concurrent releases (governance-as-code-quality-gates, deploy-toolchain-defect-cleanup, pmo-skill-reference-substrate) between this release's planning and its execute, so it landed at next-free **v1.24**. The branch name (`release/v1.21-pipeline-detection-bash-debt`) and the build-commit messages retain the as-authored `v1.21` label (a cosmetic build-record artifact); every durable artifact ships v1.24.
