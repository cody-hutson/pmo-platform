# Release records stop naming a version before it exists

2026-08-05 · v4.08

Nothing in the platform now writes down a release version before the moment it is actually claimed — branch names, plan filenames, telemetry keys and planning records either wait for that moment or say plainly that they are still provisional. The visible consequence is that the release cycle-time measurement produces a number for the first time, having reported "not available" for its entire life.

> **Skip the rest** unless you run releases, read release history, or rely on the platform's delivery metrics.

## Who this affects

- Anyone who runs a release through the pipeline, or plans one while another is in flight.
- Anyone who reads release history or follows a plan link out of an older release note.
- Anyone who relies on delivery measurements such as cycle time.
- Anyone who edits a packaged assistant and expects its package to stay current.

## What you need to do

1. **Run the normal deploy step for your workspace.** One packaged assistant — the session retro — was repackaged in this release, so an existing install keeps the previous copy until it is redeployed.

Nothing is migrated, no settings change, and nothing else is required.

## What changed for everyone using the platform

- **Delivery measurements record the release, not a version it might lose.** Every telemetry row is keyed to the release's own name, and the component that writes those rows now refuses a version-shaped key outright rather than accepting it. *Why it matters:* a release whose version changed part-way through used to scatter its own history across two different keys, so any measurement built on that history was reading a fraction of the run.
- **The release cycle-time measurement works for the first time.** Pointing it at the release key made it find rows at all, which then exposed a second, older fault that had it reading the wrong column. *Why it matters:* the tool reported "not available" when it matched nothing and failed outright when it matched, so in practice it had never once produced a value.
- **Claiming a version rebuilds the assistant packages that claim stales, in the same step.** *Why it matters:* the claim used to leave a stale package behind with no step that owned rebuilding it, so the staleness surfaced days later as a failing check on the main branch.
- **An assistant's version field is now actually checked against the format the rules already state.** A malformed value fails the structure check and the failure names the value it saw. *Why it matters:* the format rule was written down but enforced nowhere, so a wrong value could ship and only be caught by a person reading the file.
- **Release planning reports the other releases running alongside yours.** Planning records which in-flight releases are editing the same files and which are competing for the same version slot, as a measurement with a timestamp rather than a verdict. *Why it matters:* concurrent releases used to discover they had collided only at merge, which is the most expensive moment to find out.
- **The release runbook's copy-paste commands work as written.** Plan paths and branch names in the runbook now use the release's name instead of a version that is not yet decided — including one command that could not have worked at all. *Why it matters:* following the documented steps literally used to fail on a name the platform had stopped using.
- **Two mis-filed release plans are back where their history says they belong.** Two historical plans had been filed under a version that was never shipped or under no version at all, and both release notes that pointed at them now resolve. *Why it matters:* following a plan link out of an older release note landed on a file that was not there.

## Known limits

- **The version-collision check stays advisory, and that is now a recorded decision rather than an unfinished one.** A check that runs before the version is claimed cannot be authoritative over an identifier that does not yet exist, so making it able to stop a release would assert an authority it cannot hold.
- **The belief that this check was incapable of failing turned out to be wrong, and the real fault is a different one.** Three separate reviews read the code and agreed it could only ever pass; an executed test disagreed and produced a genuine failure. The two sides of its comparison are drawn from populations that filter differently. Tracked as [#4716](https://github.com/cody-hutson/pmo-platform/issues/4716) and [#4705](https://github.com/cody-hutson/pmo-platform/issues/4705); deliberately not fixed here.
- **The close-out's own package rebuild still covers two of the three places a shared file can live.** A package staled through the third location would not be rebuilt and the run would still report success. This release fixed the equivalent gap in the sibling tool and routed this one rather than widening its own edits. Tracked as [#4722](https://github.com/cody-hutson/pmo-platform/issues/4722).
- **Close-out writes plan links in a flat shape while the claim files plans in a versioned folder.** Five of the fifty-two notes carrying a plan link currently point at a file that is not there. Tracked as [#4706](https://github.com/cody-hutson/pmo-platform/issues/4706).
- **The rename that files a plan under its version does not fire every time.** Three shipped releases still carry flat, slug-suffixed plan filenames. Tracked as [#4707](https://github.com/cody-hutson/pmo-platform/issues/4707).
- **The new concurrent-release report cannot classify part of what it looks at.** Its overlap classifier accepts only work that has an open pull request, so the branches without one are counted but not classified. Tracked as [#4724](https://github.com/cody-hutson/pmo-platform/issues/4724) and [#4725](https://github.com/cody-hutson/pmo-platform/issues/4725).
- Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:pipeline` label.

## Reversibility

MODERATE / MEDIUM confidence. Reverting the single integration commit restores every file's bytes — it is a true two-parent merge, so the revert form the plan states applies, and five of the six changes are prose, comments and scripts that go back cleanly. What does not go back is the event log: it is append-only, so rows already written under the new key stay written, and reverting the component that writes them does not un-write them. Treat any data operation on that log as separately reversible from the key change itself. The repackaged session-retro assistant needs the deploy step run again after a revert rather than reverting on its own. Standard 7-day rollback window.

### Operator and engineering detail

**The one ground that could be falsified was falsified, by the only method that could falsify it.** The collision-detection decision rested on three grounds, the first being that the pre-merge gate was tautological by construction — it derives its candidate by running the allocator and then compares that candidate against the same claimed set the allocator produced. Stage 5, an adversarial design review, and the release hub each read the call graph and independently agreed. Dev Testing built a differential harness from the workflow's exact configuration and got `NOT_FREE`, rc=1. The two populations are not the same population: the allocator's claimed set is orphan-filtered and the gate's is not, so when the derived candidate is itself orphan-classified the gate returns a failure — and in that state the failure is correct. The orphan class is live in this repository. The advisory posture is retained, but on the binding-moment argument alone, which never depended on detectability; the set divergence is filed as its own defect rather than remediated inside a release that would then be shipping an unreviewed enforcement change.

**The telemetry key moved at the writer, not by convention.** The release join key changes from the version string to the milestone slug, and the change is enforced where rows are written rather than documented where they are read. The guard sources the version grammar from its library rather than mirroring a copy of the regex — the library's own consumer contract forbids the copy, and a copied pattern is a second source that drifts — and it fails closed when the library is absent, because a guard that silently skips is the exact failure class it exists to remove. This is the shape a row now takes, and what the writer accepts and rejects:

```
# one emitted row — the second column is the release join key
| 2026-08-04T23:28:30Z | version-binding-lifecycle | 12 | decision | d-class | hub | milestone:#306 |

# accepted at the writer
--version version-binding-lifecycle     # a milestone slug
--version "(none)"                      # the reserved no-release-context sentinel

# rejected at the writer
--version v4.08                         # version-shaped
--version "{{RELEASE_VERSION}}"         # unresolved token
```

**The card named six consumers; the true set was seventeen.** Five were named correctly, one was a phantom that is not a consumer at all, and twelve were missing. Two of the twelve were *writers* rather than readers — the category that breaks loudly instead of silently — and one of those two was found only by an independent sweep at implementation time, absent from the design-stage enumeration entirely. It emitted the contents of the version file with a version-shaped fallback, and it swallows emission failure into a skip message, so the new rejection would have stopped its emissions permanently and silently. The sweep is the load-bearing probe: denominator 1521 tracked files, 33 invoke the writer, 6 pass a release key; the sensitivity arm returned both already-known writers and the specificity arm returned zero against a non-existent tool name.

**A consumer re-point that leaves the metric uncomputable does not deliver the card.** Re-pointing the cycle-time tool made it find rows for the first time — and it then died parsing them, because it read the second field as a timestamp when the row's leading separator leaves the timestamp in the first. Verified pre-existing against the untouched tool at the branch head, which fails identically. The tool had therefore never produced a number in its life: "not available" when its filter matched nothing, an error when it matched. Fixed in scope at both extraction sites, with a genuinely-absent release still returning "not available" as the control.

**The release is a live worked instance of the defect it exists to detect.** Both halves of the new concurrent-release predicate fired on its own execution: it co-edits two governance files with an in-flight sibling, and it computed the same next-free version slot as that sibling. The sibling claimed the slot roughly twenty minutes before this merge. Under the model this release ratifies, that cost one arithmetic recompute at the claim; under the prior model the same event would have forced renames across the branch, the plan file and every version-keyed reference. The in-flight population also inverted inside a single day — one open pull request at planning, four at the first engineering commit — which is why every baseline in the plan is marked perishable and re-measured rather than carried.

**The release ships without an architecture decision record, on two independent grounds.** Every decision here applies a principle already recorded in an existing decision record, so a new one would restate a settled principle in different words; and the adversarial review measured a live number collision in the in-flight population, which makes allocating a number inside this release unsafe. The decisions are written into the registers that already own them.

**This release produced almost no telemetry about its own run, and that is recorded rather than smoothed over.** Two rows carry its release key, both written at execution; a same-shape sibling release carries ninety, spanning every stage from planning to close. It emitted no gate-outcome rows at all, which is precisely why the cycle-time figure above is "not available" for this release specifically — the start anchor is genuinely absent rather than mis-read. The release therefore contributes no delivery-lead-time datapoint and no stage-grained audit trail, and given that the run also produced thirteen defect tickets and a documented recurring failure pattern, that missing record is the single largest gap of the exercise.
