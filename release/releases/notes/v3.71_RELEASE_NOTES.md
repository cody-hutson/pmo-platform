# New projects use one simpler folder set and a single inbox

2026-07-12 · v3.71

This release reshapes how projects are organized. Every new project is created with one uniform, simpler folder set and a single inbox for incoming files, and the platform now records where each generated document came from. It is the foundation of the platform's Project Data Architecture. Projects you already have keep working unchanged.

> **Does this affect me?** Yes, in a good way, if you create or organize projects: new projects look simpler and more consistent. Existing projects are untouched — the old folder names stay valid during a compatibility window.

## What changed for everyone using the platform

- **A simpler, uniform project folder set.** New projects are created with one standard set of five top-level folders instead of the previous eight, grouped the way work actually flows — governance, delivery, tracking, evidence, and generated output. *Why it matters:* every project looks the same, so you always know where a document lives without relearning a different layout for each one.
- **One inbox that files things for you.** Each new project has a single inbox where you drop any incoming file; the platform classifies it, records where it came from, and files it in the right folder. *Why it matters:* you no longer decide the destination yourself, and nothing is lost between "received" and "filed."
- **Generated documents remember their origin.** Files the platform generates now carry a record of the raw input they were built from, and that record is preserved when a draft is promoted to its final home. *Why it matters:* you can trace any finished document back to the source it came from, even after it moves.

## Known limits

- **Existing projects are not reshaped.** The old eight-folder names stay valid during a compatibility window, so projects created before this release keep working; only newly created projects use the five-folder set.
- **This is the foundation, not the full feature set.** Three follow-ups were filed for the layers that build on this data architecture — wiring status and rollup skills to read the new tracking layer (#3386), refreshing the generated-artifact lint (#3385), and evaluating a retention-purge step for archived generated files (#3387). None are in this release.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH confidence.** While the compatibility window is open and no existing project has been reshaped, rollback is a revert of the release PR plus a yanked tag and release — recoverable, though stakeholder-visible rather than a silent undo. Reversal becomes more costly only after the old folder vocabulary is eventually retired.
