# A held rule now fires at the moment it is needed

2026-08-05 · v4.09

Four agent behaviors that had previously been corrected one conversation at a time are now written down as rules the agent is expected to follow and a reviewer can check. More consequentially, the release ships the thing that was actually missing: a short index of observable situations that says *when* a rule has to fire, so a rule the agent already holds stops being skipped at the moment it matters.

> **Skip the rest** unless you work with the agent on analysis, audits, renames, or anything where you expect it to hold a position under disagreement.

## What you need to do

1. **Copy the new operating rules into your workspace's rules folder.** Three new rule files ship in this release. The deploy step does not copy rule files into a running workspace — that is a manual step today, and a workspace that skips it will pass every automated check while the agent never reads the new rules. This is the one action that decides whether this release does anything for you.
2. **Run your normal deploy step.** One packaged assistant — the quality auditor — was repackaged, so an existing install keeps the previous copy until it is redeployed.

Nothing is migrated and no settings change.

## What changed for everyone using the platform

- **The agent is expected to re-check before it agrees with you.** When you push back on something it said, and your objection asserts a fact it can go and verify, it re-reads the source and then either holds its position with the evidence or changes it and says specifically what changed. *Why it matters:* the previous behavior was to fold on the objection alone, which quietly turns a correct answer into a wrong one and removes the value of having an independent check at all.
- **Disagreement about a fact no longer blocks your call.** Where your instruction carries a factual premise the agent believes is wrong, it corrects the premise once, in one sentence, and then does what you asked. *Why it matters:* re-raising the same correction against a decision you have already made is more annoying than the folding it replaces, so the rule bounds it — one correction, then compliance, and never a re-litigation.
- **Asking for analysis gets you analysis.** When the request is to map, assess, check, review or diagnose something, the agent finishes that and holds the action its findings imply, naming what it is not doing and what would authorize it. *Why it matters:* an assessment that stops half-way to go fix what it found leaves you with a report on a situation the assessment itself changed, and without the rest of the answer you asked for.
- **Renaming something now includes finding everything that pointed at it.** A rename, move or delete is treated as a change to a whole web of references rather than a single edit, and it is not reported as done until a re-run of the same search over the same set of files comes back empty. *Why it matters:* the old pattern left links that no longer navigate and prose citing files that no longer exist, discovered later by whoever followed one.
- **The agent stops saving things to memory that you did not ask it to save.** Before writing anything durable about you, it checks whether the platform already has a governed home for that information, and saves only when there is none and it can say why the fact is worth keeping. *Why it matters:* unrequested notes accumulate, and a note that duplicates a written rule can quietly start overriding it.
- **Quality scoring reads a conversation as a conversation.** The scoring instrument that grades agent responses now picks which of two kinds of output it is looking at before it scores, and applies markers written for that kind. *Why it matters:* a decision briefing was previously graded against markers that assume a finished document, so a turn that did its job well scored badly for not producing an artifact nobody wanted.

## Known limits

- **A rule in the repository is not yet a rule the agent reads.** The rules folder has a governed contract and a check that detects drift, but nothing in the deploy step actually copies the files into a running workspace, and when the destination is missing the check reports a clean skip that reads as success. Roughly half of sessions — the ones doing operator, communications and project work — do not load that folder at all. This is the largest open gap from this release and is tracked as [#4740](https://github.com/cody-hutson/pmo-platform/issues/4740).
- **Links inside the new rule files do not resolve from the copied location.** Fifty cross-file links in the rule files are written to work from where they are stored, not from where they are read after copying. The written instruction for how to avoid this mandates a link form that a later decision retired, and no rule file follows it. Tracked as [#4739](https://github.com/cody-hutson/pmo-platform/issues/4739).
- **The claim that these rules reduce the failures they target is not yet measured.** It is declared with a 30-day observation window as its verification method, but no baseline count and no repeatable counting method ship with it, so the window currently closes by the calendar rather than by a measurement. Tracked as [#4741](https://github.com/cody-hutson/pmo-platform/issues/4741).
- **The reworked scoring instrument has no regression coverage.** Two of its five dimensions were rewritten and a new step decides which marker set applies, with no test fixtures behind any of it. Tracked as [#4742](https://github.com/cody-hutson/pmo-platform/issues/4742).
- **Two files must be kept in step by hand.** The list of files the mirror check enforces and the list the impact-analysis tool believes in are separate and must match; nothing asserts that they do. Tracked as [#4738](https://github.com/cody-hutson/pmo-platform/issues/4738).
- Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:pipeline` label.

## Reversibility

MODERATE / HIGH confidence. Reverting the single integration commit restores every file — the changes are additive text plus one rebuilt package, and the merge is a true two-parent commit, so the revert form the plan states applies. Two things do not come back with it. Three staging notes in the operator's personal memory store are due for removal now that their content is written into the repository; those live outside version control, so a revert after their removal would leave the disciplines recorded nowhere and they would have to be restored by hand. And a workspace that has already copied the new rules into its rules folder will be ahead of the reverted source, which the drift check will correctly report — re-running the check after a revert is part of the rollback. Standard 7-day window.

### Operator and engineering detail

**The release's central determination was to add nothing to the charter list.** The recurring failure this release addresses is not a missing rule; it is a held rule that does not fire. Three of the four disciplines were already bullets in the charter's Universal Preferences list when the failures were recorded, which makes a twenty-ninth bullet the intervention already falsified for this class. All five governance cards reached that conclusion independently. What was added instead is a trigger layer: an index of observable signatures, each naming the situation that fires it, the read that discharges it, the token it emits, and the point in a session where it recurs. Admission to the index is gated by a declaration contract rather than by author discretion — a discipline that cannot state a falsifiable trigger stays a rule and does not become a checkpoint, which is what bounds the index against the same unbounded growth the charter list was showing.

This is the shape of one index row and the token it emits, which together are the contract a new checkpoint has to satisfy:

```
| ID      | Trigger signature (observable)          | Governing rule       | Required ground-truth read              | Locus      |
|---------|-----------------------------------------|----------------------|-----------------------------------------|------------|
| DTA-6   | About to create a new entry in the      | memory-architecture  | Search the corpus for an existing       | close-out  |
|         | operator memory store, unasked          | § 5 write rule 4     | governed home; state what it returned   |            |

[DTA-6: searched core/ and release/ for a governed home for <claim> → 1 found (memory-architecture.md § 5); not saving]
```

Nine checkpoints ship in the index. Two of them deliberately emit no token of their own — where the governing rule already defines a trailer, that trailer discharges the checkpoint, because two observables for one obligation is how a convention starts being ignored.

**The pushback clause is symmetric, and that is the part likely to be misread.** The failure is not capitulation; it is the position moving, or failing to move, for a reason other than a read. Holding a prior conclusion without re-verifying is the same violation as reversing without re-verifying — reversal simply dominates in practice because it is the low-friction branch, since ending a disagreement requires producing nothing while holding forces the evidence into the open. The scope test is nameability: the clause fires only when a read exists that would settle the question without asking the operator, and every ambiguity resolves toward operator prerogative. It fires once per proposition; a second pushback on the same point is prerogative by construction, including in the case where the re-verification was itself wrong. The rule fails safe toward the operator, never toward the agent's own conviction.

**The analysis-only rule moved its trigger to where the crossing actually happens.** An earlier fix for this failure was scoped to one read-only mode; the generalization moves the trigger off the moment the request arrives and onto the finding-to-action transition. The reasoning is that a rule firing at request time is silent at the moment of failure and noisy at a moment when nothing is wrong — the failure is not misreading the request, it is receiving it correctly and crossing later, when a surfaced gap pulls toward closing it. The rule's third satisfier is what makes it general: a declared read-only contract binds the surface whether or not that surface carries its own guardrail, and the count of surfaces that declare one is far larger than the count that guard one.

**A cross-issue acceptance criterion was amended after plan approval, and the amendment is the more defensible position.** The original predicate asserted the four disciplines would land in exactly one file — a pre-design assumption encoded as a gradable check before the designs existed. Design work produced four independently well-reasoned homes, and enforcing the literal form would have forced one discipline to hold a parallel copy of a rule outside its own single source of truth, which is the shadow-source failure the platform explicitly guards against. The constraint's real intent was one surfacing index, not one file, and the amended predicate grades that.

**A probe-validity warning had to be written into that criterion, because a sweep scoped to markdown by file extension returns a false zero.** The charter template is not a markdown-extension file and is invisible to such a sweep; a direct read returned a hit where the extension-scoped sweep returned zero, with the sensitivity arm confirming the sweep was finding real files. This is filed as its own observation because the exposure is not specific to this release — it applies to any audit scoped that way, and the sweep gives no signal that anything was skipped.

**The three memory-eviction verifications were re-derived, because the originally-prescribed probes were defective and defective in three different ways.** One card's corpus-wide anchor false-passes, because the discipline's own clause home cites the checkpoint identifier in its prose — so the anchor stays non-zero even with the index row deleted, and both originally-prescribed control arms return non-zero in that state too. A second card's path anchor false-passes, because the file it points at was created by a different card in the same release: the file's existence proves that other card landed, never that this one's section did. A third card's content anchors false-pass, because both phrases already existed on the mainline before the release. The corrected probes are per-card rather than uniform — a row-shape match pinned to the rules file, a path anchor with a pre-release counterfactual, and five content anchors scoped to the specific file version — and each carries a sensitivity arm returning a non-zero result. This is the pattern worth carrying forward: a live instrument pointed at the wrong property is more dangerous than a dead one, because it reports confidently.

**The release survived a two-slot version collision and produced almost no telemetry about its own run.** It determined one version at planning, and while it was held at the review gate two sibling releases claimed that slot and the next one, so it was re-rendered forward before the claim rather than recovered afterward. Separately, and repeating the immediately-preceding release's finding: a whole-population probe of the event log returns two rows keyed to this release, both written at execution, against ninety-seven for a same-shape sibling. The probe demonstrably fires, so the zero is real. This release therefore contributes no delivery-lead-time datapoint and no stage-grained audit trail, and it is now a recurring pattern across consecutive releases rather than a one-off.
