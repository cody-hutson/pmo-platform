# Transcript and meeting processing now follow one named pipeline with clear automation boundaries

2026-06-29 · v2.40

How the platform handles transcripts and meetings is made explicit. The transcript flow that already ran across the daily cycle is now named as one pipeline, and its outputs are sorted into three clear tiers: routine tracker updates flow without interrupting you, anything stakeholder-facing or risk-bearing stops for your approval, and action items are surfaced for you to decide on rather than logged on your behalf. Alongside that, meetings gain a governed lifecycle state on the Open Meetings Tracker, and meeting materials — pre-reads, agendas, invites, and context blocks — are redesigned so you can take in what a meeting needs from you in about five seconds. This formalizes flow that mostly already existed; it adds one tracker field and a content redesign, and changes nothing about how your existing artifacts are stored.

## Who this affects

- Any operator whose project work involves processing meeting transcripts or running meetings — the automation boundaries and the meeting-material redesign change what you are asked to approve and what you receive. No effect on the underlying folder layout, existing trackers' storage, or any command.

## What changed for everyone using the platform

- **The transcript flow is now one named pipeline.** The implicit transcript-handling steps are named as a single pipeline — Entry → Routing → Core-Tracker → PPM → Stakeholder-Review → Action-Triage — with each stage tied to where it already runs in the daily cycle and to a shared lifecycle state. *Why it matters:* there is now a clear, shared vocabulary for where a transcript is in processing, instead of an unnamed flow you had to infer.
- **Transcript outputs are sorted into three automation tiers.** Routine operational-tracker updates flow without a per-item prompt; changes to stakeholder-facing artifacts or the RAID log stop for your approval; and action items are surfaced for you to dispose of and are never auto-logged. *Why it matters:* routine updates stop interrupting you, while anything visible to stakeholders or carrying risk still stops for review — and nothing is committed on your behalf.
- **The same boundaries apply uniformly to every project.** Stakeholder-Review and Action-Triage are first-class named stages that apply the same way across all projects, with no per-project variations. *Why it matters:* the rules for what flows and what stops are consistent everywhere, so you do not have to relearn them per project.
- **Meetings carry a governed lifecycle state.** The Open Meetings Tracker gains a lifecycle state (`scheduled` → `held` or `cancelled`) with defined transitions, while keeping its familiar status labels for display. *Why it matters:* meetings move through their stages with a traceable, consistent state instead of an ad-hoc status, and the meeting processing keys off that state.
- **Meeting materials are built for a 5-second scan.** Pre-reads, agendas, invites, and context blocks are redesigned so the essentials land at a glance — no pre-read points you at a raw transcript without an inline summary, and every invite passes a scan test. *Why it matters:* you can absorb what a meeting needs from you immediately, instead of opening source files to reconstruct the context.

## Known limits

- These changes formalize and bound transcript and meeting handling; they do not migrate or re-process any existing transcripts, meetings, or trackers — they apply to processing going forward.
- The meeting lifecycle state is the frozen three-value set `scheduled` / `held` / `cancelled`. Richer steps you see in a tracker's status label (such as "needs scheduling") remain display detail; the governed state stays the three values.
- The skill behavior changes here (transcript output tiering, meeting extraction, meeting-material formatting) take effect once the updated skills are deployed to your environment.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:project-data-architecture` label.

## Reversibility

CHEAP / HIGH confidence. The changes are tracked edits to governance, a schema, two formatting standards, and two skill definitions; reverting the integration PR restores the prior behavior in one step. No data migration, no stored-content move, and no change to how existing artifacts are stored. Standard rollback window.

### Operator and engineering detail

**Three-tier automation boundaries for transcript output (#237).** `core/governance/OPERATIONS.md` § Transcript Processing Protocol § Three-Tier Output Model sorts transcript-derived outputs into three automation tiers that map onto the existing Document Tiers: **auto-write** (Document Tier 2 operational trackers — Daily Status Log, Communications Tracker, Open Meetings Tracker, carry-forward — which flow without a per-output prompt and are confirmed in-response), **approval** (Document Tier 1 stakeholder-facing artifacts and RAID-log changes, which stop for operator approval — the Stakeholder-Review stage), and **user-triage** (action items surfaced for the operator to dispose of, never auto-logged). `operations/skills/ppm-agent/SKILL.md` tags each output block with its tier so the downstream write path knows whether the block flows, stops for approval, or is surfaced. The model composes with the existing global Document-Tier rules rather than duplicating them.

**Named transcript pipeline stages (#1157).** The same OPERATIONS.md section names the implicit flow as one pipeline — Entry → Routing → Core-Tracker → PPM → Stakeholder-Review → Action-Triage, with a terminal resolution gate — and cross-references each stage to its Daily-Processing-Cycle step number(s) and to its Context-Lifecycle state, using the five object-typed state names verbatim from `core/disciplines/context-lifecycle-model.md §2` (`Context-Captured` / `Context-Structured` / `Context-Reviewed` / `Context-Decided` / `Context-Closed`, no aliases). Stakeholder-Review and Action-Triage are promoted from prose buried in the cycle's approval and next-step steps to first-class named stages, and the pipeline is stated to apply uniformly across all projects (the shared 01-08 layout means there are no per-project variants).

**Meeting lifecycle state on the Open Meetings Tracker (#243).** `core/schemas/tracker-schemas.md` adds a `lifecycle_state` field to the Open Meetings Tracker — the frozen three-state Axis-1 machine `scheduled → held | cancelled` (the V-MTG-05 enum from `core/schemas/entity-field-schemas.md §3.7`). The human-readable `Status` display field retains richer sub-steps (such as `NEEDS SCHEDULING`) via an explicit display-to-governed map. The stage-transition rules and evidence bar are defined (`held` and `cancelled` are terminal, there is no re-open, and the transitions carry the same evidence bar as a tracker CLOSE), and `ppm-agent` meeting extraction sets the entry state (Cascade B). A reconcile note pins the canonical three-state machine against a legacy six-stage proposal so a body-only reader cannot build a competing six-state machine.

**Human-behavior-aware meeting content (#1158).** `core/standards/meeting-agenda-format.md`, `core/standards/meeting-recap-format.md`, and `operations/skills/comms-writer/SKILL.md` (with `references/audience-profiles.md`) redesign pre-reads, agendas, invites, and context blocks for a 5-second scan — no pre-read references a raw transcript without an inline summary, and every invite passes a scan test — so an operator or attendee absorbs what a meeting needs from them at a glance instead of opening source files.
