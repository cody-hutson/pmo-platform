# Knowledge and decision confidence — lenses, learning altitude, and a living roadmap

2026-06-28 · v2.34

New work now gets classified the same way every time, captured learnings record the scope they came from, and the roadmap has a skill to keep it current. Additive throughout — new and edited reference docs, a new skill, and one build-check extension, with no behavior or data change to anything already in place.

## What changed for everyone using the platform

- **A written set of design-time lenses for sizing and routing new work.** A new reference doc names the cross-cutting questions to ask when scoping work — the right skill, the right method, the right altitude, and whether the work is universal or install-specific — and wires them in as a design check. *Why it matters:* new work gets classified the same way every time instead of relying on recall, so it lands in the right place.
- **Captured learnings now record the scope they came from.** The knowledge model gains a scope ladder, from a single unit of work up to the whole organization, that sits alongside the existing how-universal tiers, plus a defined way for lower-scope learnings to roll up to the next scope. *Why it matters:* a learning now carries the scope of work it was generated at, so related learnings can be aggregated rather than read one at a time.
- **Two more facilitation-technique domains are available.** The technique library adds the retrospective and planning domains on top of the existing estimation set, surfaced through the same delivery-engine prompt you already see. *Why it matters:* technique suggestions now cover more of the delivery lifecycle, not just estimation.
- **A skill that keeps the living roadmap current as issues arrive.** A new roadmap-curator skill sorts new and changed issues against the established initiative set, updates the roadmap, and flags drift, with a separate operator-triggered mode for a full re-baseline. *Why it matters:* the roadmap stays sequenced and current as work arrives instead of drifting back into an unsequenced pile.
- **Retiring a folded-in note no longer leaves dead links or stranded notes.** When a note that has been absorbed into the reference corpus is retired, the platform now re-points or drops links to it and reconciles notes against their tracking issue, and the build validation reports either gap. *Why it matters:* cleaning up a note no longer leaves links that go nowhere or notes that can never be retired.

## Known limits

- The two new facilitation domains (retrospective, planning) are the first of a larger planned set; the remaining lifecycle domains are sequenced as separate follow-on work, not shipped here.
- The two new knowledge-eviction reports are logged for review, not yet blocking, consistent with the existing eviction-check posture.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:knowledge-corpus` label.

### Operator and engineering detail

**Architecture evaluative-lens layer (#1102).** A new cross-cutting evaluative-lens doc under `core/disciplines/` enumerates the design-time lenses — the triple-Venn (right skill ∩ right methodology ∩ right altitude) and the plug-and-play K1-universal vs K2–K5-install-specific classifier — cross-linked from `knowledge-architecture.md` and `work-organization-mapping-framework.md` and referenced as a Stage 2 Triage / Stage 4 Planning design check. Graduated from observations #577/#69 via Pattern Review (N=2).

**Organizational-altitude axis (#564).** `knowledge-architecture.md` gains a learnings-altitude/aggregation axis (Unit → Task → Workstream → Project → Program → Portfolio → Organization) explicitly declared orthogonal to the K1–K5 universality tiers and reconciled against the existing work-organization vocabulary; `km-protocols.md §3` records altitude as a capture-time attribute and defines an adjacent-altitude rollup relation. The existing K1–K5 classifier and the K5→K1 pipeline are unchanged — the axis is purely additive.

**ADR-029 encode-and-evict dangling-ref closure (#2214).** The encode-and-evict lifecycle in `knowledge-architecture.md §6` now handles both mirror-image reference gaps — downstream links to an evicted note are re-pointed or dropped at eviction, and a close-time reconciliation diffs a closing codification issue's absorbed-note list against every note naming it so partially-absorbed notes are re-homed before close. `deploy.sh` Check 36 gains two finding classes (dangling-link-to-evicted-note and ledger-pointer-to-closed-issue), logged but not blocking, consistent with Check 36's existing posture; ADR-029's Decision reflects the extended lifecycle.

**Facilitation-technique domains (#1945).** `core/standards/facilitation-techniques/` adds the retrospective and planning domains on top of the v2.22 estimation foundation, each conforming to the established 9-field schema and surfaced through the existing delivery-engine Mode D/E trigger; the remaining lifecycle domains remain sequenced as separate per-domain follow-on cards.

**Roadmap-curator skill (#453).** A new roadmap-curator skill encodes the consolidation pipeline as an incremental, repeatable capability with two modes — default incremental maintenance (classify new/changed issues against the stable ratified initiative set; never silently re-draw initiatives) and an operator-triggered point-in-time re-baseline — applying the same evidence labels, gap diagnostic, and sequence-not-time horizon disciplines as the original consolidation.
