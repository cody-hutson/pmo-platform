# Project health and RAID escalation are now consistent and predictable

2026-06-14 · v1.20

Health colors and RAID escalations used to depend on which skill produced them and how each one decided where the lines were. This release writes those lines down once — the thresholds that turn a metric green, yellow, or red, and the ages at which an open risk or issue is warned and then escalated — and has every skill read from the same place. The same project situation now produces the same color and the same escalation no matter which part of the platform reports it.

## What changed for everyone using the platform

- **One agreed set of health thresholds.** There is now a single index of which measure drives a health color at which level (portfolio, program, project, team), where its green / yellow / red lines fall, and what each color tells you to do. *Why it matters:* a project that is, say, eight percent behind schedule comes back the same color every time, instead of green from one skill and yellow from another.
- **"Green on the outside, red on the inside" status is now caught.** The quality auditor has a defined set of checks for a status reported green while the underlying evidence is amber or red — the most common way a status report misleads. *Why it matters:* a health roll-up that looks fine but is hiding a slipping schedule or overdue risks gets flagged for you instead of passing review.
- **Stale risks and issues escalate on their own.** An open RAID item now has agreed ages at which it is first flagged and then escalated — an issue at 14 and 30 days, a risk at 30 and 60 — with the flag naming the owner and the threshold it crossed. *Why it matters:* a risk that has been sitting open for two months surfaces a recommended escalation on its own, instead of quietly aging until someone happens to notice.
- **Escalation routing reads from the same agreed thresholds.** The way a scored risk or issue is routed to an escalation tier, and the ages that trigger escalation, are defined in one place that the others cite. *Why it matters:* how severe an item has to be to escalate, and how long it can sit before it does, are the same everywhere rather than re-decided skill by skill.

## Known limits

- The age-based escalation covers risks and issues; assumptions and dependencies age under their own closure rules and are not auto-escalated by this protocol.
- Escalation is a recommendation — the platform flags a stale or severe item and names the owner and tier; it never closes, reassigns, or edits the RAID log on its own.
- This release makes health and escalation read from one agreed set of thresholds; it does not change which metrics are tracked or how a project's data is collected.

### Operator and engineering detail

**One canonical metric registry, referenced rather than restated (#271, #270)** — `operations/skills/weekly-status-rollup/references/metric-registry.md` is authored as a cross-level index of metric → RAG-threshold → decision-rule mappings at the portfolio / program / project / team levels. It is deliberately an INDEX: where a band is already owned by a sibling document it references that owner (project schedule/budget/risk/scope bands at `comms-writer/references/channel-formats.md`; team capacity-utilization at `delivery-engine/references/capacity-model.md`; portfolio health / dependency-ratio cut-points at `delivery-engine/references/backlog-health.md`; RAID-age timing at `escalation-thresholds.md`) and OWNS only the metrics that exist nowhere else — Overdue RAID Count and the cross-level roll-ups. It fixes a lower-inclusive / upper-exclusive boundary convention so boundary values classify deterministically (the determinism the registry exists to create) and maps its 🟡 YELLOW band to the "Amber" vocabulary used by the referenced sources. The watermelon-detection reference at `core/skills/pmo-qa-auditor/references/watermelon-detection.md` consumes those thresholds by registry role-name (it does not restate the values): it defines eight named signals (W1–W8) for green-masking-risk — a status reported GREEN while a contradicting band reading (overdue RAID, an SPI/CPI breach, a milestone slip) is present — each with detection logic, data sources, false-positive filters, and an escalation action, plus the rule that composes fired signals into a watermelon verdict. The auditor consults it in Mode A (Single Output Review) and Mode C (Push-to-Resolve Audit) whenever an output asserts or rolls up a health status.

**Escalation thresholds as doc-of-record, and a stale-RAID protocol that cites them (#269, #261)** — `operations/skills/ppm-agent/references/escalation-thresholds.md` is the doc-of-record for two things the PPM Agent owns: the score → escalation-tier routing (the score-band → tier partition) and the age-based auto-escalation thresholds (when a stale item is warned versus escalated). It references the 5×5 probability × impact scoring scale owned by `delivery-engine/references/raid-templates.md` § 5 rather than re-deriving it, and reproduces the product grid only as a routing aid — the routing layer (band → tier, plus the age axis) is the PPM Agent's contribution. The Stale-RAID Auto-Escalation Protocol is appended as a new `### Stale-RAID Auto-Escalation Protocol` H3 under the existing `## Cross-Skill Protocols` H2 in the `OPERATIONS.md` canonical+mirror pair (`core/governance/OPERATIONS.md` + `operations/OPERATIONS.md`, edited in the same commit). The protocol states the operational trigger — age = `today − open-date` validated against the RAID Log, two warning/escalate bands by RAID type (Issue: > 14 / > 30 days; Risk: > 30 / > 60 days), and the per-band action ladder (Nominal → carry forward; Warning → `[RECOMMENDED]` owner nudge; Escalate → flag with an escalation action naming owner, breached threshold, and routed tier) — and defers the threshold values and routing to `escalation-thresholds.md` as its doc-of-record. PPM Agent owns the weekly RAID review and `[RISK]` / `[DECISION]` routing; Delivery Engine emits the escalation in its RAID Update output and hands the tag back to PPM Agent (no self-routing). Each escalation is a CHEAP recommend-tier flag the operator reviews; the protocol never auto-closes, auto-reassigns, or mutates the RAID Log without the normal Document Tier 1 approval gate.
