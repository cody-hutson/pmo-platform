# Shared reference content is single-sourced, and stray issue/PR links get flagged

2026-06-13 · v1.12

Reference content that several skills used to carry as their own private copies now lives in one canonical place and is injected into every skill that needs it, so the copies can no longer quietly drift apart. Separately, raw GitHub issue, pull-request, and milestone URLs are now flagged anywhere outside the small set of release-tracking files where they belong. Both checks are logged but not blocking for now — they go live as warnings first.

> **Skip the rest** unless you author or maintain platform skills, governance docs, or other tracked reference files.

## Who this affects

- Anyone editing a platform skill that shares reference content with other skills (the document-output and operational-artifacts references)
- Anyone authoring governance docs, standards, ADRs, release plans, or other tracked files who might paste a GitHub URL into them

## What changed for everyone using the platform

- **Shared reference content now has one canonical source.** The two reference files that several skills used to each carry their own identical copy of now live once under the shared standards area and are injected into every skill that uses them when the platform deploys. *Why it matters:* the copies can no longer silently fall out of sync — every skill gets the same up-to-date content, so a fix made once reaches everyone.
- **A reintroduced duplicate copy is now caught at deploy time.** The deploy self-check fails if the same shared reference is found copied back into a skill — whether the copy is identical or has been edited to differ. *Why it matters:* the single-source guarantee is enforced mechanically instead of relying on memory, so the drift problem cannot quietly creep back.
- **Raw GitHub issue, pull-request, and milestone URLs are flagged outside the release ledger.** A new check flags a raw `github.com/.../issues`, `/pull`, or `/milestone` URL pasted into any tracked file except the small set of release-tracking files (the release log, changelog, index, digest, and release notes) where such references are the whole point. *Why it matters:* those URLs break when issues are renumbered or the repository moves, so keeping them out of durable docs keeps those docs readable years later. For now this is logged as a warning, not a hard stop.

## Known limits

- Both new checks run in "logged but not blocking" mode to start. They report findings but do not stop a commit or a deploy yet; the operator turns them into hard blocks after a short shakedown period (this release defers that switch — see the operator detail below).
- The single-source change covers the two reference files that were actually duplicated today (document-output formats and operational-artifacts). It does not change how skills declare their dependencies in their own metadata — that was evaluated and deliberately left out this release because it conflicted with the skill-packaging schema.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

MODERATE / HIGH confidence. A single `git revert -m 1` of the release pull request restores the prior state: the single-source change restores the eight deleted per-skill copies, and the URL check ships as a warning so there is no enforced behavior to unwind. After a revert, re-running the platform deploy re-syncs the skill copies. Standard 30-day outcome window.
