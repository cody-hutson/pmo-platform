# Runtime code tests now gate releases, and there is a standing install regression suite

2026-06-13 · v1.13

The platform's runtime code tests — the suites that exercise the deploy and hook layers — now run in CI and stop a release if they break, their results are recorded in a machine-readable form the pipeline can read, and a new standing regression suite checks a fresh install, onboarding, and a simulated version upgrade on every release. Before this release those tests sat outside CI and could rot unnoticed, and there was no standing regression corpus to catch install or onboarding breakage.

> **Skip the rest** unless you contribute code to the platform's deploy/hook layers, run a release, or install or upgrade the platform.

## Who this affects

- Anyone changing the platform's runtime code (the deploy tooling, the hooks, or the composition layer) — their tests now gate the pull request
- Release operators — runtime test results now appear in the pipeline's event log, and a standing install/onboarding regression suite runs at release time
- Anyone installing, onboarding to, or upgrading the platform — a regression suite now guards that path

## What changed for everyone using the platform

- **The platform's runtime code tests now run in CI and gate pull requests.** The committed deploy-layer and hook-layer test suites — which previously ran in no automated workflow — now run on every pull request and fail it if a test breaks, and they pass regardless of where the repository is checked out. *Why it matters:* a change that breaks the deploy or hook behavior is caught on the pull request instead of slipping through to a release.
- **A changed code path now maps to the test suite that gates it.** Dev Testing now has a documented rule connecting a changed runtime code area to the suite that must run for it, plus a step that runs that suite. *Why it matters:* there is no longer a guessing game about which tests cover a given code change — the gating suite is named and run.
- **Runtime test results are now machine-readable in the pipeline.** Test outcomes are recorded as a structured `test-run` entry in the pipeline's event log and carried in the Dev-Testing-to-QA handoff, instead of living only inside raw CI logs. *Why it matters:* downstream reviewers and agents can see whether a release's code tests passed without digging through Actions output.
- **A standing install, onboarding, and update regression suite now runs at release time.** A new sandboxed suite performs a fresh install, checks that no configuration placeholders are left unresolved, verifies file links and references in the deployed tree, confirms a two-phase deploy succeeds, and checks that user configuration survives a simulated version upgrade. *Why it matters:* install and onboarding breakage — the kind that only shows up on a clean machine — is now caught by a repeatable suite before a release ships, the platform's first standing regression corpus.

## Known limits

- The standing regression suite covers the install / onboarding / update surface only. The broader behavior-scenario engine — declarative scenarios scored by a judge against a pass-rate gate — is deliberately out of scope this release and is sequenced to a later slice of the QA & Eval Infrastructure work.
- Follow-ups filed rather than fixed here: a path-resolution defect in the release-analytics helper tools (so cycle-time and learnings synthesis can run against the live layout), and a link-checker that assumes a repository-root layout and so cannot yet validate a sandboxed or deployed tree (issue numbers in the References below).

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

**#319 — runtime test-suite rot fixed and brought under CI.** The eight committed hook tests (`core/hooks/tests/*.test.sh` and their `test-runner.sh` harness) ran in no CI workflow and failed when checked out in the source tree because they depended on the deployed runtime layout (co-located, token-resolved allowlists plus a `.mode` file). The release makes the hook suite portable and wires it into CI via a `setup-ci-layout.sh` shim and four refreshed hook tests (`block-destructive` / `block-egress` / `block-shell-injection` / `block-skill-direct-edit`), so a pull request that breaks a wired hook test fails CI regardless of checkout location, and it makes the composition manifest-count assertion in `test_lib_composition.sh` derive its expected value from the manifest rather than asserting a hardcoded literal that re-rots when the manifest grows. The AC-currency reconciliation at Stage 5 had already confirmed two of the issue's three original defects fixed on main and a third a phantom, so the build targeted the still-live core (per reconcile-don't-annotate).

**#430 — runtime code-test gating + machine-readable result tracking.** Runtime code-test suites become a first-class gated surface at Stages 6–7: a new `runtime-suite-selection-map.md` documents the changed-code-path → gating-suite mapping, `stage-06-engineering.md` and `stage-07-dev-testing.md` gain the steps that select and run the mapped suite, and `pipeline-event-log-schema.md` adds a `test-run` event type with the Dev-Testing-to-QA handoff carrying the test-results block. The event-log writer/reader pair (`release/tools/append-pipeline-event.sh` + `release/tools/query-pipeline-event.sh`) was repaired so `test-run` events actually emit and read back (the dedup survivor #590 — the extinct `pmo-platform/engineering/` path that made Surface B emission impossible — was resolved by this repair and closed). `stage-09-plan-review.md` was updated for the new gated surface.

**#706 — the first standing install/onboarding/update regression suite.** A new sandboxed, CI-gated regression suite (`core/deploy/tests/run-install-regression.sh` + `test_upgrade_config_durability.sh`, wired into `install-tests.yml`) productizes the pre-public-flip QA sweep (Suites A–H under a `HOME`→`/tmp` sandbox): a fresh sandboxed install, post-install token-substitution and file-link/reference integrity, two-phase deploy success, and user-config durability across a simulated version upgrade. Scoring is deterministic (no judge layer) — the suite reuses the existing CI test harness as the regression floor and is the most build-ready slice of the #325 regression-suite decomposition (the seed corpus already existed). The behavioral / judge-graded scenario engine (#325 tickets C2–C5) and bring-your-own scenarios (C7) stay out of scope and sequenced to a later #325 slice.

**Deploy is a no-op.** PR #747's 17 changed paths are confined to `core/hooks/tests/`, `core/deploy/tests/`, `.github/workflows/`, `release/references/**`, and `release/tools/**` (plus the Engineering-Commit-0 plan) — zero `{core,operations,release}/skills/`, `packages/`, or harness paths — so `./deploy.sh --deploy` has nothing to deploy.
