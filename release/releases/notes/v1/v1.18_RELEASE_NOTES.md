# The release pipeline now catches releases that would collide with each other

2026-06-14 · v1.18

The pipeline used to plan and approve each release as if it were the only one moving. It now holds a model of every release in flight or planned and checks each new one against that set, so two releases that would step on each other are caught and run one-at-a-time instead of colliding mid-way through. This is a foundation change inside the release pipeline; there is nothing to do and nothing changes in how you use the platform day to day.

## What changed for everyone using the platform

- **Releases that would clash are now caught before they break each other.** When one release moves or renames files that another release depends on, the pipeline now detects the clash up front and runs the two in order rather than in parallel. *Why it matters:* a release no longer fails partway through because a sibling release quietly moved the ground under it — the conflict surfaces at planning time, not as a broken merge late in the process.
- **An approval to ship is re-checked if the ground shifts before it ships.** A go-ahead to release is now recorded against the exact state it was approved against, and it is re-checked if another release lands first. *Why it matters:* a release is only shipped against the state it was actually reviewed on, so an approval that has gone stale is caught instead of being acted on as if it were still valid.

## Known limits

- This is a pipeline-internal change with no change to how you use the platform; you will not see new behavior in skill output, project files, or commands.
- The new checks cover content-file moves; moves inside source-code trees are handled by a separate, already-existing path.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `cluster: cross-cutting` label.

## Reversibility

CHEAP / HIGH confidence. `git revert <sha>` reverses the integration PR; every change is additive specification and gate criteria with no data migration. Standard 7-day rollback window.

### Operator and engineering detail

**Cross-release impact model (#87)** — The pipeline now maintains a durable, architecture-native, repo-agnostic model of the concurrent and planned release set and its mutual impact, consulted at five stages (3 / 4 / 5 / 9 / 12) rather than re-derived from operator memory. The substantive addition is a third contention axis: alongside the existing ticket-dependency-edge and same-path-overlap classifiers, releases are now scored on a **structural-blast-radius** axis. Stage 3 Bundle (`§ A9.6.1`) defines a four-token git mover-classifier (`RENAME` / `RELOCATE` / `DELETE-RECREATE` / `DIR-RESTRUCTURE`), each tied to a reproducible `git diff --name-status --find-renames` signal; computes the mover's break surface `SURFACE(R)` via the F1–F6 reference-form sweep (F4, the mover's own outbound-link rewrite obligation, deliberately excluded so high-traffic governance files do not over-serialize); and tests `EDITSET(sibling) ∩ SURFACE(R) ≠ ∅` to mark a serialization point — surfaced as a new `Tier-S` verdict and `structural-blast-radius` edge on the existing standing Parallelization Map.

**Where the model is consulted** — Stage 4 Planning carries the authoritative structural sub-audit (the first pipeline point a branch exists) plus a sibling-merge stale-pin self-invalidation trigger, so a pinned cross-PR audit re-runs when a sibling parallel release merges after the pin; Stage 4 Phase A0 re-derives the Tier-S verdict on entry. Stage 5 Solutioning adds a cross-*release* coherence row to the Collective Review. Stage 9 records a new gate criterion (`G-PR9`) in `gate-criteria-spec.md`: a GO records the **baseline SHA** it was rendered against and a sibling-merge revalidation predicate (verdicts CURRENT / STALE-REVALIDATE / STALE-VOID), composing with the existing Phase-A6.5 divergence check as a second axis rather than duplicating it. Stage 12 Phase A.5 adds a semantic GO-invalidation check that catches a renamed-since-baseline referenced path even when a plain merge reports no textual conflict. All three surfaces (Stage 4 trigger / G-PR9 / Phase A.5) share one merge-style-agnostic predicate. The architecture decision is recorded in `ADR-024-cross-release-impact-model.md`; each new criterion carries the introducing-release-exempt cutover clause (reflexive-pipeline-loop discipline). The model's persistence reuses systems already in place — the live Parallelization Map in the milestone description plus the release plan's recorded baseline SHA — with no new datastore and no repo-specific hardcoded paths, milestone names, or counts.
