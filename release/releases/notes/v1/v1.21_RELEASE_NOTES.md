# Two new quality gates catch drift and rename leftovers before release

2026-06-14 · v1.21

The platform's automated quality checks gain two new gates. One confirms that a starter template still carries every section the rules say it should, so a template cannot quietly fall out of step with its own format. The other scans a change for leftover old values after a rename or restructure, catching the case where some occurrences got updated and some were missed. Both gates start in a logged-but-not-blocking mode while they settle in.

## What changed for everyone using the platform

- **Starter templates are checked against their own format rules.** A new gate confirms that each template governed by a schema carries every section that schema requires, and flags one that has drifted. *Why it matters:* a project scaffolded from a template gets the structure the format actually calls for, instead of a stale template that quietly lost a section. ([#318](https://github.com/cody-hutson/pmo-platform/issues/318))
- **The Open Meetings tracker template was brought back in line.** The first template the new gate caught — the Open Meetings tracker — was reconciled to the section structure its schema defines. *Why it matters:* a newly-scaffolded project starts with an Open Meetings tracker that matches its specification, not an older divergent stub. ([#318](https://github.com/cody-hutson/pmo-platform/issues/318))
- **Leftover old values after a rename or restructure are now caught.** The quality auditor gained a check that scans the changed files in a piece of work for occurrences of an old value that a rename or restructure was supposed to sweep, and flags any it missed. *Why it matters:* a rename that updated most references but missed a few is caught and surfaced, rather than leaving a half-renamed change to be discovered later. ([#79](https://github.com/cody-hutson/pmo-platform/issues/79))

## Known limits

- Both gates start in a logged-but-not-blocking mode during their shakedown window — they report a finding for review rather than stopping a release, until they have been observed clean and switched to blocking.
- The template gate only inspects templates that are explicitly registered as having a governing schema; a template with no registered schema is skipped, not flagged, so it never produces a false alarm.
- The leftover-value scan checks the files changed in a piece of work; it is a back-stop that complements the earlier authoring-time and review-time checks for the same problem, not a replacement for them.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `cluster: ci-enforcement` label.

## Reversibility

CHEAP / HIGH confidence. `git revert -m 1 <merge-sha>` reverses the release PR. Both gates are additive detection surfaces that ship in a logged-but-not-blocking mode, so a false finding is logged rather than breaking a deploy, and a revert removes each gate cleanly with no data migration and no prior consumers to unwind. Standard 7-day rollback window.

### Operator and engineering detail

**Check 34 — template↔schema conformance, the third fidelity axis (#318)** — `core/deploy/deploy.sh` gains a `TEMPLATE_SCHEMA_MAP` manifest plus a Check 34 block that asserts each schema-bearing canonical template carries every section its governing schema mandates. This is contract-fidelity, the third axis over the existing Check 13 (canonical↔mirror copy-fidelity): Check 13 verifies a runtime mirror matches its canonical byte-for-byte, but nothing previously verified that a canonical template conforms to the schema that governs its instances. The manifest mechanism mirrors the proven `TEMPLATE_SYNC_MAP` pattern (the in-template-frontmatter alternative is governance-barred by `template-storage.md` §3.4), and the scope rule is opt-in by manifest presence — a template the manifest does not name is never inspected, so a schema-less template is a structural skip rather than a false failure. `operations/templates/open-meetings-tracker-template.md` was the first divergence the check caught (it shipped `ACTIVE` / `COMPLETED` sections against the `tracker-schemas.md` Tracker 3 `Upcoming Meetings` / `Recently Completed` / `Recurring Cadences` structure) and was reconciled in the same release; the third fidelity axis is documented in `core/standards/template-storage.md` §3.5b. Check 34 reuses the existing `flag_warn_or_issue` / `DEPLOY_CHECK_MODE` / `deploy-check.mode` warn-mode machinery — no new helper, flag, or mode file — and ships warn-mode-first per the established shakedown precedent.

**G8 — L5 cascade-completeness detection in pmo-qa-auditor (#79)** — `core/skills/pmo-qa-auditor/SKILL.md` gains a G8 cascade-completeness check: when the output under audit is a Stage 5 spec carrying a `### Cascade-Sweep` block, G8 re-runs each declared sweep against the changed-file set on the release branch and verifies the swept-declaration table enumerates every old-value occurrence found. This is the L5 automated-detection complement to the cascade-omission failure mode's existing L1–L4 prevention surfaces (the Stage 5 spec anchor, the rule-tier mirror, the design-review forcing-function checklist, and the failure-mode catalog entry) — L1–L4 prevent at authoring/review time within the change matrix; L5 detects at audit time across the whole changed-file set, the back-stop the Stage 5 spec already ceded to "pmo-qa-auditor automation." The supporting detail lives in the net-new `core/skills/pmo-qa-auditor/references/cascade-completeness-detection.md`, and the cascade-omission anti-pattern in `core/specs/failure-mode-standard.md` now cross-references L5 as the automated-detection surface. The SKILL.md edit routed through `pmo-skill-editor` Mode A (Gate 2 hook discipline preserved); the `pmo-qa-auditor.skill` package was rebuilt at Stage 13 to carry the new check and reference (Check 7 package-freshness).

**Version, release class, and package rebuild** — this release ships as **v1.21** (provisional at planning, confirmed at the Stage 12/13 close — the version was free, so no re-version was needed, unlike the v1.18→v1.20 concurrent-collision chain). `novel` class (two D-class plan decisions plus ADR-class Stage 5 design choices on the gates' deploy-time-vs-audit-time placement and the schema-scoping mechanism), CHEAP reversibility, 30-day Stage 13 outcome window. Both issues #318 and #79 auto-closed at the release-PR merge. The only deployable artifact is the rebuilt `pmo-qa-auditor.skill` package, which lands in the Stage 13 corpus chore PR; the runtime skill-mirror sync (`./core/deploy/deploy.sh --deploy pmo-qa-auditor`) is an operator action from the primary post-merge.
