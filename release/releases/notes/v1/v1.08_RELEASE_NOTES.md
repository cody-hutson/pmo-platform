# The skill-suite architecture spine — a decomposition rule, a skill-to-pipeline alignment, and a factory guard

2026-06-08 · v1.08

The platform gains the architectural spine its skill suite was missing. A binding rule now governs how role-named skills are built — they **compose** the shared skills they need rather than re-implementing them; the way skills line up against the delivery pipeline is written down as a standard; and the skill factory that wraps an external scaffolder now fails loudly if that scaffolder ever changes shape, instead of quietly producing broken skills. These are foundations for the role-skill suite that later work builds on.

> **Skip the rest** unless you care about how the platform's skills are structured, how they map to the delivery pipeline, or how new skills are generated. Day-to-day status, comms, and project artifacts are unaffected by this release.

## Who this affects

- Anyone who will design or configure the platform's role-named skills, or reason about how skills relate to one another and to the delivery pipeline (this release lays the foundation that later milestones build on)
- Anyone who creates or refines a platform skill through the skill factory (the factory now refuses to produce a skill silently when the underlying scaffolder has drifted)
- General platform use — status outputs, comms, project artifacts — is unaffected; nothing changes operationally yet

## What changed for everyone using the platform

- **The skill factory now fails loudly when its scaffolder drifts.** When a new or refined skill is generated, the factory first checks that the underlying generator produced the expected shape, and stops with a clear error if it did not. *Why it matters:* before this, a change in the external generator could have silently produced a malformed skill that looked fine until it misbehaved in use — now the failure surfaces at creation time, not in production. <!-- impact:foundational -->

## Known limits

- This release lands the **spine only** — the decomposition rule, the alignment standard, and the factory guard. It does not build the role-named skills themselves; that role-skill suite is downstream work that consumes this rule.
- The decomposition rule is recorded as a *Proposed* decision record; it governs how the role skills will be built but does not retroactively restructure existing skills.
- Two follow-ups were opened and are tracked separately: a correction to a skill census count, and a remediation that exercises the guard end-to-end (proof of mechanism).

Report issues via the standard intake at the GitHub Issues page.

## Reversibility

MODERATE / HIGH confidence at the release level. The three changes land via a single release PR (#570); `git revert <merge-sha>` reverses the slice, and the corpus chore PRs revert the same way. The changes are additive governance + tooling — the decision record is *Proposed* (not yet a consumed contract), the alignment standard is a new document, and the factory guard composes an existing drift-check rather than replacing a subsystem — so undoing the spine before the downstream role-skill suite adopts it is low-cost; the rating is MODERATE rather than CHEAP because the guard sits in the live skill-generation path. Governance, standard, and tooling changes only; no data migration ships in this release.

### Operator and engineering detail

**Release shape.** `novel` class (operator-rendered at the Stage 4 Decision Gate; basis: two new tracked files — the establishing ADR-019 + a new `core/standards/` alignment standard — plus ≥4 D-class decisions and a clean Tier-0 premise rejection). Deep Stage 9 review (Collective Review N-way consistency + cross-D upstream-compatibility scan + blast-radius). Branch topology `D-C SINGLE` — one release branch, sequential Engineering commits, one release PR (#570), the plan committed as Engineering Commit 0. The milestone held four work items; three shipped and one (#8) was premise-rejected, so the surviving release is a 3-issue spine.

**#406 — the decomposition rule (the governance act).** The new establishing `core/ADRs/ADR-019-specialists-compose-not-absorb.md` records the operator-adopted (2026-06-06) decision that role-named **Specialists compose shared function-skills rather than absorb them**, and that a single role MAY span several Specialists, split per the skill-boundary test (distinct trigger surface AND distinct write-scope AND distinct primary role). The ADR cites the existing cascade rule **C1 (depth bound: max 2)** at `agent-handoff-framework.md` and the Skill Chaining Protocol (C1–C7 + the 4-skill allowlist) as the composition substrate the design already relies on — a role that composes shared skills keeps routing depth ≤2 by construction, so the ADR coins no new bound. It carries a forward-reference to #2 as the reconciliation venue for specific overlapping role/function pairs, not a hard ordering dependency. The record ships at `status: Proposed`.

**#2 — the skill-to-pipeline alignment standard (the audit codification).** The new `core/standards/skill-pipeline-alignment.md` codifies how skill modes line up against the 13-stage delivery pipeline, carrying decision-tests DT-1/DT-2/DT-3, and is cross-linked into `core/disciplines/execution-framework.md` and the `core/governance/OPERATIONS.md` + `operations/OPERATIONS.md` mirror pair. The alignment audit's analysis and recommendations registers are operator-local read-once artifacts and are deliberately out of the tracked release; the tracked deliverable is the standard itself.

**#193 — the fail-loud factory guard (the smallest-robust-guard re-scope).** A structure-assertion pre-injection check was added to the `pmo-skill-refiner` factory by extending `release/skills/pmo-skill-refiner/scripts/quick_validate.py`, with a new `release/skills/pmo-skill-refiner/scripts/test_scaffolder_drift_guard.py` covering it; the guard captures the expected output skeleton of the wrapped Anthropic `skill-creator` scaffolder (required frontmatter, the `references/` directory convention, body anatomy per `upstream-reference-catalog.md`) and fails loudly on mismatch. It composes the existing `upstream-reference-catalog.md` drift-check (re-verified this release) rather than inventing a parallel subsystem; #193's two other proposed mechanisms — a compatibility-shim layer and a version-pinning strategy — were flagged out as over-engineering for current state (a shim presupposes a drift that has not occurred; pinning depends on plugin-version machinery the issue itself marks uncertain).

**#8 — premise rejection (no tracked deliverable).** The fourth milestone work item was a clean Tier-0 Premise Rejection: ADR-012 had already de-scoped *tracked* roadmap instances (instances are operator-local; the initiative-roadmap *framework* already ships in-repo) and removed `core/governance/roadmaps/`. The premise that a tracked roadmap family needed building no longer held, so #8 carries no tracked deliverable. Relatedly, #193's native `Blocked by #160` was confirmed a roadmap-consolidation mislink (#160 is the unrelated Project-Data-Architecture initiative) and was not a genuine blocker.
