# A shared fix-now / defer / accept framework for Dev Testing and QA findings

2026-06-06 · v1.06

Dev Testing and QA reviews now share one explicit framework for deciding whether a finding is fixed now, deferred to a later release, or accepted as-is — replacing case-by-case judgment. QA carries a stricter version of the rule: a not-met acceptance criterion can no longer be quietly deferred or accepted, and a Stage-5 design-template guard now calls out the safety-allowlist entries any new in-tree script needs.

> **Skip the rest** unless you drive releases through the platform's review pipeline (Stage 7 Dev Testing / Stage 8 QA) or author Stage-5 design specs.

## Who this affects

- Anyone running Stage 7 Dev Testing or Stage 8 QA on a release (there is now a single disposition framework backing the fix-now / defer / accept call)
- Anyone authoring a Stage-5 design spec that introduces a new in-tree script (the design template now prompts for its security-allowlist entries)
- General platform use — status outputs, skills, project artifacts — is unaffected

## What changed for everyone using the platform

- **Dev Testing and QA decide finding disposition the same way.** When a review surfaces a finding, one shared framework (five weighted factors + a two-step decision) now says whether it is fixed now, deferred, or accepted — instead of ad-hoc judgment per finding. *Why it matters:* review outcomes are consistent and predictable across releases, and a trivial, best-practice fix on an open PR no longer gets quietly waved through as "accept as-is."
- **QA can't silently defer an unmet acceptance criterion.** At QA, a not-met acceptance criterion now requires an explicit, recorded operator override before it can be deferred or accepted. *Why it matters:* something you committed to deliver can't slip away unnoticed — choosing not to deliver it is now a conscious, logged decision.
- **New in-tree scripts get a safety-allowlist callout at design time.** The Stage-5 design template now prompts the author to list the security-allowlist entries a new script needs, in all four invocation forms. *Why it matters:* a new tool is far less likely to be blocked at build time by a permission it should have declared up front.

## Known limits

- The disposition framework is advisory — a human still confirms each call; the scoring-function form is documented as a future automation trajectory, not an active automated decision.
- The dedicated adversarial design-review agent is not shipped yet (it arrives with a later agent-layer carryover); v1.06's design review was performed inline at Collective Review.
- The Stage-5 template guard is preventive — the specific allowlist gap that motivated it was already fixed; this hardens the template against recurrence rather than fixing a live break.

Report issues via the standard intake at the GitHub Issues page.
