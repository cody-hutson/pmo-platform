# Hybrid is now a two-archetype combination, separated from co-management

2026-06-21 · v2.18

You can now declare a project that runs two methodologies in one line — `delivery_approach: [Scrum, Kanban]` — and the "Hybrid" label no longer means the specific co-management arrangement it used to be tied to. The dual Agile/Waterfall status framing still works exactly as before; only its name and how you turn it on have changed.

> **Skip the rest** unless you set up or configure projects (especially Hybrid projects or co-managed projects with dual Agile/Waterfall status framing).

## Who this affects

- Anyone onboarding or configuring a project — particularly a project that runs two methodologies (a Hybrid), or a co-managed project that reports status in both Agile and Waterfall framings. There is no change for everyday status, RAID, or skill output on existing projects: a project file using the old setting keeps working.

## What changed for everyone using the platform

- **"Hybrid" now means a two-archetype combination you choose.** Declare it as a two-element list — `delivery_approach: [Scrum, Kanban]`, `[Waterfall, XP]`, any two distinct archetypes — and the project runs both methodologies side by side, reporting status in both native framings. *Why it matters:* a two-methodology project no longer has to drop into the heavyweight `Custom` block to describe what is really a two-archetype selection — one line does it.
- **"Hybrid" is no longer tied to a specific co-management arrangement.** The methodology label and the co-management capability were conflated; they are now separate. A Hybrid project can run with or without co-management, and a single-methodology project can turn co-management on by itself. *Why it matters:* picking the Hybrid methodology no longer silently implies an unrelated co-management setup, so the two choices can be made independently.
- **The co-management setting is renamed `dual_framing_enabled` — your existing project files keep working.** The setting that turns on dual Agile/Waterfall status framing now has a clearer, operator-agnostic name. A project file still using the previous co-management setting is read automatically (with a one-time reminder to update it). *Why it matters:* nothing breaks on existing projects, and the setting name now says what it does instead of referencing an internal arrangement.
- **The dual-framing status artifact is renamed the "Dual-Framing Bridge".** The artifact that presents a project's status in both an Agile and a Waterfall view is renamed, with plain audience labels ("PMO view" / "Sponsor view"). *Why it matters:* the artifact's content and behavior are unchanged — only the name is clearer.

## Known limits

- **Splitting methodology by space is not in this release.** Declaring a different methodology for different parts of one project (for example, a continuous-flow operations space alongside a stage-gated release space) is a separate, planned capability and is not yet available — this release delivers the two-archetype combination and the decoupling only.
- The previous co-management setting is accepted through a compatibility shim that logs a reminder rather than blocking. It is intended as a migration aid and will be removed in a future release once existing project files have moved to the new setting name; updating the setting now silences the reminder.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. Every change is additive — a methodology-spec rewrite, a renamed setting and artifact, and the new two-archetype declaration form — with a compatibility shim that keeps the old setting working. Reverting the release merge restores the prior state; the only thing to migrate back is a project file that adopted the new setting name, and even that is read by the shim. No data migration and no manual rebuild are required.

### Operator and engineering detail

**One conceptual correction with two consequences (#1778 + #32).** The `§3 Hybrid` semantic anchor in `release/references/specs/methodology-parameterization-v1.md` previously asserted that "Hybrid" *means* the co-managed pattern — a single sentence that was both the co-management coupling and the rigidity (one iterative + one phase-gated track). Neither could be fixed without rewriting the other, so the decouple (#1778) and the genericize to a user-configurable two-archetype combination (#32) were unified into one release on milestone `86-hybrid-comanagement-decouple` (#224). The anchor is fully rewritten: Hybrid is a methodology classification only — a user-configurable combination of two of the named archetypes declared `delivery_approach: [A, B]` — and the co-management dual-framing *output* is an orthogonal capability gated by the separate `dual_framing_enabled` flag. The literal `Hybrid` value is retained as a single-enum value for backward-compatibility.

**The rename surface (decouple + genericize + parameterize, never removal).** The legacy co-management trigger field is renamed `dual_framing_enabled` across `core/schemas/project-schema.md` (declaration, presence rule, semantics, Migration §7) — the `delivery_approach` validation rule is amended in place to admit the two-element array (length 2, distinct members, drawn from the 6-archetype set) rather than claiming a new validation-rule number, so the downstream PDA-schema keystone keeps its reserved slot. The dual-framing status artifact is renamed the "Dual-Framing Bridge": its template under `operations/templates/` is renamed to `dual-framing-bridge-template.md` (retitled, audience labels "PMO view" / "Sponsor view"), and the `core/CLAUDE.md.template` clause, both `OPERATIONS.md` clauses, and the five registries (`template-taxonomy`, `template-storage`, the two READMEs, `docs/module-apis.md`) follow. The dual-framing capability is preserved — the renamed XC-06 regression check (byte-paired with its `pmo-skill-editor` mirror in one commit) still asserts that a project with the flag set emits both Agile and Waterfall framings, and the pmo-qa-auditor + pmo-skill-editor D5 audits pass.

**Consumer propagation and back-compat.** The 26 migrated `SKILL.md` files (and 11 references) were updated through `pmo-skill-editor` Mode A — the active branchers (`ppm-agent`, `delivery-engine`, `daily-status`, `weekly-status-rollup`, `comms-writer`, `tracker-manager`, `file-router`, `project-initiator`) gained the renamed references plus tolerance for the array form, and the role-specialist set had its boilerplate clause renamed. `project-initiator` hosts the deprecation shim: a live or imported `PROJECT.md` carrying the legacy co-management key (or its legacy input label) is accepted, emits a one-line deprecation warning, and is treated as `dual_framing_enabled` — so the rename ships non-breaking. The partner-team identity and the related operator-config fields relocate to operator-local (K4) configuration outside the public tree; the operator-specific token survives only there.

**The new capability and what is deferred.** The Hybrid-Two array-validation logic is finalized in `project-schema.md` §5, with a §5 CASE 1-ARRAY consumption pattern in `methodology-parameterization-v1.md` (dual-framed output, union of ceremonies per the work-organization-mapping-framework §2.5, with the phased constituent governing gate surfaces and the timeboxed/continuous constituent governing iteration surfaces, rendering both on contention and never silently picking), a §6.5 `[Scrum, Kanban]` worked example, and a grep-discoverable Hybrid-Two-vs-Custom partition rule (the array form is two canonical archetypes as-is; `Custom` remains the home for a named modification or fusion such as Scrumban). The per-space methodology split — separate `operational_methodology` / `release_methodology` fields — is deferred to #1788, coordinated with the PDA-schema keystone (#351) and #262.

**ADR posture.** No new ADR — the durable decision kernel (Hybrid = a user-configurable two-archetype combination, decoupled from co-management which is `dual_framing_enabled`; the array-vs-Custom partition) folds into the project-schema §7 prose and the expanded §3 anchor, which are the architecture record (per the ADR-durability discipline).

**Pipeline-context note.** Cross-cutting release; Stage 6 Engineering ran on a single release branch with the seven slices write-serialized (S0 the standalone-mergeable decouple firebreak, then the field rename, the artifact rename and consumer propagation, the gate updates, the K4 parameterization, and the Hybrid-Two surface last); Stage 9 PR review was the independence/review gate. For full implementation detail see the [RELEASE_LOG.md entry](../RELEASE_LOG.md#deployment-log-v218) and [the release plan](../plans/v2.18_RELEASE_PLAN.md).
