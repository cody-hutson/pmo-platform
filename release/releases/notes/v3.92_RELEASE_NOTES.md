# A standing audit of delivered work against the platform's architecture

2026-07-25 · v3.92

This release adds a standing architecture-conformance audit: you can now check what the platform has actually shipped against the platform's own architecture, catching drift and cross-release fragmentation that a forward, per-change check cannot see. It also lands two foundational references — a cross-chain index that maps every management chain to its governing model, flow, and gate, and a consolidated actor-model baseline the audit reads from.

## Who this affects

- **Anyone doing platform QA or review** — you have a new audit that grades delivered work against the architecture and reports what has drifted.
- **Anyone who runs a project health-check** — its full sweep now surfaces a platform-level conformance flag alongside the usual project findings.
- **Contributors navigating the architecture docs** — a new cross-chain index and a consolidated actor-model baseline give you a single map instead of a hand-traced one.

Everyday project work is otherwise unchanged and needs no action.

## What changed for everyone using the platform

- **New architecture-conformance audit.** `pmo-qa-auditor` gains an as-built architecture-conformance audit you invoke by name; it reads the release record and grades delivered work against the platform's own architecture, then reports — it changes nothing and files no issues. *Why it matters:* conformance drift and cross-release fragmentation (related work shipped under diverging architectures) now have a place to surface, instead of staying invisible until they compound.
- **Health-check now flags platform-conformance context.** A project health-check's full sweep now reads a committed conformance summary and surfaces a platform-level flag, clearly labeled as platform context, not project drift. *Why it matters:* you get a heads-up that a platform-wide architecture check is stale or flagging while you are looking at a single project, without running the platform audit yourself.
- **A cross-chain architecture index.** A new index maps every management chain to its governing data model, process flow, and holding gate — in one place, pointing at the existing docs rather than restating them. *Why it matters:* when you need to know how a chain fits together or what governs it, there is now one map to follow instead of tracing it by hand.
- **A consolidated actor-model + governance-as-contract baseline.** The platform's actor model — who orchestrates, which work is a bounded specialist skill, and which stays human or free-agent judgment — is now stated in one place as a forward-looking baseline. *Why it matters:* there is a single reference for how the pieces are meant to fit, and it is the same baseline the new audit checks against. <!-- impact:foundational -->

## Known limits

- **The audit reports; it does not fix or file anything.** Every finding is an observation for you to triage — the mode creates zero issues and edits no backlog.
- **Cross-release fragmentation detection is a candidate-grade heuristic, not a guarantee.** The release record does not capture which architecture each past delivery followed, so fragmentation is inferred only where a decision record makes it citable; treat those findings as leads, not verdicts.
- **No audit has run yet on a fresh install.** The committed conformance summary ships in an "awaiting first run" state until someone runs the audit, so health-check reports the platform-conformance context as unavailable until then.
- **This is the retrospective half only.** The forward, per-change architecture-fit gate this audit complements is still parked (it depends on a separate acceptance-gate item); today the audit is the after-the-fact complement.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE** · confidence **HIGH**. The release is a single pull request (#3923); a `git revert` of the merge commit cleanly restores the prior behavior. Most of it is additive documentation (cheap to undo); the one higher-risk element is the new executable audit mode, which is purely additive — no existing mode was renamed or removed — so removing it leaves the rest of `pmo-qa-auditor` untouched. No data migration.

Serial build-order plus append-only edits resolved the three-way contention without a merge conflict.

**#877 — actor-model + governance-as-contract baseline.** A new discipline doc frames the actor model (orchestrator / specialist-skill / free-agent classes) and governance-as-contract as *target-state*, forward-looking prose — it carries a status that does not assert the model is ratified, and no ADR was minted (the adversarial design review challenged an ADR as altitude-inflation over an open decision, so it was dropped). The claim that judgment stays with free agents is dual-grounded on both the script-promotion mixed-determinism rule and ADR-019 "specialists compose, not absorb." Shared-file edits are append-only to protect 31/37 inbound references; `orchestrator` is disambiguated inline rather than minting a new glossary sense, so the term count is unchanged.

**#912 — cross-chain architecture index.** A sibling doc indexes every management chain against its governing data model, process flow, and holding gate, citing #877's baseline as one entry without restating it. Its gate-wiring acceptance criterion is deferred: it depends on the architectural-fit acceptance gate (#779, open), so wiring the index into a gate that does not yet exist is correctly out of scope.

**#1097 — as-built architecture-conformance audit (pmo-qa-auditor Mode I).** The operator-facing headline. Mode I is the retrospective, cross-release complement to the forward per-ticket architecture-fit gate: it reconstructs the delivered-item set from the release record, maps each to its governing architecture baseline (the ADR corpus is the primary, discriminating baseline; the #912 cross-chain index is a secondary routing aid), and classifies each item as conformant / conformance-drift / cross-release-fragmentation-candidate / no-governing-baseline. Severity and baseline-confidence are kept on orthogonal axes, so a high-severity divergence under a low-confidence baseline is surfaced honestly rather than diluted. It is OBSERVE-only: it writes a git-ignored dated audit folder, overwrites one committed hand-off surface, and echoes a summary in chat — it never creates an issue or touches the backlog. `health-check` `full` composes the platform-conformance flag by reading that committed surface; it never re-runs the audit (compose-not-absorb, ADR-019). Two skill packages (`pmo-qa-auditor.skill`, `health-check.skill`) were rebuilt in-PR with refreshed baselines.

**Mode I shape (new output contract).** Mode I is invoked by name and produces three surfaces; the committed hand-off surface that health-check reads has the shape below, shown in its shipped "awaiting first run" state:
