# Release decisions are now auditable, and the hub writes down what it commits to

2026-09-19 · v4.67

You can now run a repeatable health check on how the release hub and its helpers made decisions across a range of releases, and compare its coverage score from one run to the next. The hub also records each commitment at the moment it makes it, so the close-out check on those commitments has a real record to read.

> **Skip the rest** unless you run releases through the release hub or review how its decisions were made.

## Who this affects

- Operators who run releases through the release hub
- Anyone reviewing how a release's decisions were made, or running the QA auditor's audits

## What changed for everyone using the platform

- **A decision health-check you can run on command.** The QA auditor has a new decision-health audit: point it at a window of releases and it produces a findings register and the other review deliverables, plus a coverage scorecard, and it updates a committed summary on every run. *Why it matters:* how the hub decided is now something you can measure and measure again, instead of something reconstructed by hand one close-out at a time.

- **A coverage score you can compare between runs.** Each run scores seven decision areas, rating how much of each area left a record separately from how good that record is, and rolls them into one index built to stay comparable from run to run. It declines to compare runs whose inputs differ. *Why it matters:* the score is built for comparison over time, and it refuses a comparison its inputs cannot support rather than reporting a misleading trend.

- **One list of when the hub stops to ask you.** The points where the hub pauses for your decision now live in a single register, and a first check decides whether an action needs your decision at all before any question is asked. *Why it matters:* routine steps your release approval already covers are carried out and reported instead of coming back to you as questions, and the stop points no longer disagree between documents.

- **The hub writes down its commitments as it makes them.** When the hub routes a decision that leaves follow-up work, it records the action item at that point, and a sweep across the release catches any it missed. *Why it matters:* the close-out check that holds a release until every commitment is resolved now reads a real record rather than passing on an empty one.

- **Choices that differ from the hub's recommendation are part of what the hub records.** Recording where your decision diverged from the hub's recommendation is now a declared part of the hub's recording duties rather than an optional step. *Why it matters:* the health check can see where recommendations and decisions part ways.

## Known limits

- Two runs of the health check over the same releases do not yet reproduce each other: in this release's two runs the findings lists held 10 and 8 findings with only 5 in common, and although the scorecard grades matched, the counts beneath them differed in most areas. The audit does not yet define its finding categories or how much evidence one finding covers, so treat a run-to-run comparison as indicative, not exact. This is tracked as [#7504](https://github.com/cody-hutson/pmo-platform/issues/7504).
- When the audit runs inside a release helper session, its output lands in that session's working copy rather than in the analysis home, so a count of audit folders at the analysis home can read zero after a real run. The committed summary is the reliable record. This is tracked as [#7503](https://github.com/cody-hutson/pmo-platform/issues/7503).
- The sibling architecture-conformance audit still names no output location for four of its six review deliverables. This is tracked as [#7502](https://github.com/cody-hutson/pmo-platform/issues/7502).

Report issues at the platform's GitHub issue tracker.

## Reversibility

CHEAP / HIGH. The whole release reverts as a single merge revert, which restores the previous hub contract and removes the new audit together; redeploying the two skills afterwards puts the previous installed copies back. The version tag stays in place as the record that the version was claimed.

### Operator and engineering detail

**Gate 0 and the single gate register.** The hub's operator-stop enumerations are consolidated into one gate register in the `release-hub` decision-briefing contract. Gate 0, the gate-eligibility precondition, runs before the five information-sufficiency gates and carries both of its classification inputs beside it — the stage-to-autonomy-tier mapping and the standing-GO authorization list — so classification never depends on a file absent from the installed skill tree. After this release's deploy, the installed copy of the contract was read back byte-identical to source, with Gate 0 as its third H2 section immediately before the sufficiency gates.

**A forcing function for the action-item ledger.** ADR-202 records the decision to force commitment emission at the routing point rather than leave it to instruction. A sweep whose window tiles the whole release catches rows a routing point missed, and the close-time attestation declines to recommend where its evidence cannot tell "nothing was owed" from "nothing was written". The recommendation-choice delta gains a declared, conditional row in the emission contract, derived from transition safety, with its promotion condition recorded.

**The decision-health audit (Mode J) and its DS1–DS7 scorecard.** Mode J derives and SHA-pins its oracle set at run time and encodes no cardinality in any artifact. Its rubric fixes the seam-table contract, the separation of coverage from grade, a cardinality-free index with a sibling ceiling term, and a comparability guard; the seven seam rows and their behavioural anchors sit inside that shape, and the index is emitted on every run. Each run overwrites the committed decision-health summary. The method-stability criterion was graded not met and deferred by an operator override; its owning item is [#7504](https://github.com/cody-hutson/pmo-platform/issues/7504).
