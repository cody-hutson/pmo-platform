# Work-item types can now be shared across methodologies

2026-09-03 · v4.49

A deployment can now define one set of work-item types — a kit — and use it whatever methodology it runs, then choose that kit in configuration the same way it already chooses its methodology. Previously, declaring work-item types and naming a methodology were the same act, so a set that spanned methodologies could not be expressed at all.

> **Skip the rest** unless you configure which work-item types your deployment uses, or you author methodology packs.

## Who this affects

- Anyone who configures which work-item types a deployment or a project uses
- Anyone who authors or maintains a methodology pack
- Anyone whose reporting rolls work up from work items to projects, programs, or portfolios

## What changed for everyone using the platform

- **A set of work-item types no longer has to belong to one methodology.** A kit declares its types while naming no methodology, so the same set can be used by a deployment running Scrum, one running Kanban, or one running something else. *Why it matters:* a shared set of types used to be inexpressible — the only way to declare types was to name a single methodology, so the same types had to be duplicated per methodology and drift apart afterwards.

- **You choose a kit in configuration, in the place you already choose your methodology.** A deployment-wide default is set once, and any individual project can override it. *Why it matters:* switching or trying a different set of types is a configuration change rather than an edit to the platform's own files, and one project can differ without affecting the rest.

- **Choosing no kit stays a valid answer.** When neither the deployment default nor a project override names one, no kit is selected and behavior is exactly what it was before this release. *Why it matters:* nothing you already run changes or needs migrating, and existing packs continue to work untouched.

- **Types that group work are now distinguishable from types that carry it.** A type can declare that it groups other work rather than being worked directly. *Why it matters:* reporting and enforcement previously had to recognise grouping work by hard-coded name, so a deployment whose grouping type was called anything else was invisible to it.

- **A kit types work items only, and shows up at every level above them by rolling up.** Portfolios, programs and projects continue to come from the platform's fixed structure, and a kit that tries to claim one of those levels is now rejected with a message naming it. *Why it matters:* your reporting levels stay stable and consistent no matter which kit you select, and a kit cannot quietly introduce a competing notion of what a project is.

- **The full set of places affected by this change was mapped and published before the change was made.** The instrument that produces that map was fixed first, then the map was re-derived against the fixed instrument. *Why it matters:* the map is what makes it possible to tell what a future change to work-item types would touch, and it was previously blind to one whole file type.

## Known limits

- **No kit ships with the platform.** This release makes a kit expressible and selectable; a deployment authors its own. There is nothing to adopt out of the box.
- **One kind of kit exists so far.** The kit that groups work-item types is the only class defined. The design deliberately leaves room for other classes later, and a kit naming an unrecognised class is reported with a note naming the value rather than rejected.
- **Reversal gets more expensive once kits are in use.** While no deployment has authored a kit, the additions are optional and cheap to withdraw. Once packs are written against them and something reads those packs, the shape is a commitment others depend on.
- **Grouping types are recognised, not yet fully relied upon.** The distinction is now expressible and checked, but the places that still recognise grouping work by hard-coded name were mapped rather than converted in this release.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**EXPENSIVE**, confidence **HIGH**. Every change here is a repository file, so the merge reverts as one commit; what makes reversal expensive is not the code but the commitment — the moment a deployment authors kit packs and something resolves against them, the shape is a contract those packs depend on. The release was deliberately taken while that cost is still low: with no kit authored anywhere, reversal today is a single revert with nothing downstream to unwind.

### Operator and engineering detail

Full audit detail is in the RELEASE_LOG Deployment Log for this version and in the release plan. Four points are worth reading rather than inferring.

**The weld was one level below where the founding ticket named it.** The ticket named the pack-level `applies_to` field as the constraint reserving neutrality to base packs, but read against the live grammar that constraint was one-directional — nothing forbade an archetype pack from being neutral. The actual weld sat one level down: every kind's methodology projection carried a required `archetype` key whose value domain held no neutral member. Relaxing only the pack-level field would have validated a kit whose every kind still named an archetype, and the capability would have appeared to land while being absent. Both levels move together here, and the kind-level `archetype = "*"` is the limb that carries the capability.

**Two domains, deliberately opposite.** `kit_class` is OPEN — an unregistered value validates with a caveat naming it, because which kits exist is deployment data and the set is expected to grow. `level_role` is CLOSED — an unknown value is an error, because the grouping/execution distinction is binary and internal to how a rollup traverses, and silently admitting a third value would make a traversal unanalyzable rather than merely under-specified. `level_role` is absent-means-`execution`, which is what keeps the field additive and every shipped pack byte-identical.

**Level coverage is by projection, not declaration, and that is structural.** Every kind's `base` is the constant `Work Item` with no other base permitted, and the entity model holding Portfolio, Program, Project and Milestone is frozen — so a kind declared at a container tier would be the new entity node the level-coverage work explicitly forbids. A validator rule rejects a kit kind claiming a container tier. Measured before the change: the `general_level` field was read by 0 of 244 repo executables while its own schema row called a non-`Work Item` value a modeling smell, and live enforcement hard-coded the literal `type:epic` in 6 executables.

**Shape of a kit pack.** The block below shows the parts that are new — the third `role` value, the class discriminator, the kind-level neutrality marker, and the level role:

```toml
[meta]
pack_id    = "delivery-work-items"
role       = "kit"          # third pack role, alongside base and archetype
applies_to = "*"            # neutral at the pack level
kit_class  = "work-item"    # which facet this kit carries; domain is open
extends    = "_common"

[[kinds]]
kind_id = "discovery-spike"
base    = "Work Item"       # const; no other base permitted
[kinds.methodology_projection]
archetype     = "*"         # neutral at the KIND level — the limb that carries it
general_level = "Work Item"
level_role    = "execution" # closed domain: execution | grouping; absent means execution
```
