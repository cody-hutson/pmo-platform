# Generated artifacts now show which skill produced them and what they drew from

2026-06-26 · v2.28

When a skill writes a generated artifact, the artifact's frontmatter now records which skill and version produced it and which upstream evidence it was built from. This makes any generated file traceable back to its source without guesswork.

## What changed for everyone using the platform

- **Generated artifacts carry their own origin stamp.** A new artifact written by a skill now records the producing skill and its version in its frontmatter. *Why it matters:* you can tell at a glance which skill made a file and which version of it, instead of inferring from the filename or the folder.
- **Generated artifacts list the evidence behind them.** Alongside the origin stamp, an artifact now records the upstream inputs it drew from — the transcripts, messages, or files it was built on. *Why it matters:* you can trace a generated file back to its sources to check or re-derive it, rather than treating it as unsourced.
- **Each generated artifact gets a stable identifier.** A generated artifact now carries a filename-independent identifier of its own. *Why it matters:* the file stays referenceable even if it is later renamed or moved.

## Known limits

- Applies to new artifacts only — existing generated files are not retro-stamped (forward-only; no back-fill).
- The origin and evidence stamps are recorded by the four artifact-writing skills (artifact-generator, comms-writer, daily-status, ppm-agent); files produced outside those skills are unaffected.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `cluster: templates-schemas` label.

## Reversibility

CHEAP / HIGH confidence. `git revert -m 1` of the integration PR reverses the change; every field is additive and optional, so nothing that already exists breaks. No data migration. Standard rollback window.

### Operator and engineering detail

**Instance-side provenance fields** — `core/schemas/frontmatter-schema.md` Category 3 gains the instance-population `generated_by` (skill name + semantic version, distinct from the person-or-skill `created_by`), `source_inputs` defined as the canonical cross-domain provenance carrier (`TR-### | MSG-### | path`) in place of the prior "not yet defined" placeholder, and a stable `id` field (`<type>-<project>-<YYYY-MM-DD>-<nn>`), all `Required: No` per the forward-only no-back-fill lock. The Domain-C `synthesis_scope` is marked DEPRECATED and aliased to `source_inputs` (one live field for the concept; `trigger_source` stays distinct). The §Scope generated-vs-source one-liner is added; the `domain`/`folder` split confirmed already present (#200 absorbed).

**Closes the template-protocol §8 dual-semantics contract** — `core/standards/template-protocol.md` §8 mandated the `generated_by` dual-semantics flag in both the template schema and the instance schema, but the instance side was silent — a dangling forward-reference. This release adds the instance-side field plus the reciprocal flag, so the both-locations contract is now satisfied on both sides (`grep -l generated_by` returns both files). The template-protocol file itself needs no functional edit (the reciprocal note on the schema side closes the contract).

**Emitter, governance, and QA wiring** — the four emitting skills (artifact-generator, comms-writer, daily-status, ppm-agent) stamp `generated_by` + `source_inputs` on write, with a missing-header → regenerate-with-header rule; `core/governance/OPERATIONS.md` records the provenance-marker requirement and the forward-only (no-back-fill) policy; pmo-qa-auditor Mode D adds a `generated_by`-presence spot-check (random ~5/week sample). The five edited `SKILL.md` files bump to `version: v2.28` and their `.skill` packages rebuild at release-cut via this Stage 13 close-out chore PR. The structured `source_ref` tracker field and `relationships[]` edge population are routed to the follow-up #1770.

For full implementation detail see the [RELEASE_LOG.md entry](https://github.com/cody-hutson/pmo-platform/blob/main/release/releases/RELEASE_LOG.md#deployment-log-v228) and [the release plan](https://github.com/cody-hutson/pmo-platform/blob/main/release/releases/plans/15-generated-vs-source-provenance_RELEASE_PLAN.md).
