# The release pipeline's own rules get three precision fixes

2026-07-01 · v3.38

This release makes three small, additive edits to the documents that govern how the platform runs its own releases — sharpening release-identity and frozen-spec precision across the planning, design, and engineering stages so problems are caught earlier instead of surfacing late during deployment. Nothing here changes how anyone uses the platform day-to-day; all three are wording and checklist additions to the internal release-pipeline reference corpus.

## What changed for everyone using the platform

- Nothing changes in how you use the platform. There are no new commands, no workflow changes, and nothing breaking — this is an internal precision-and-consistency improvement to the release process itself. <!-- impact:foundational -->
- The release pipeline now catches a specific class of problem earlier: when a release is planned and then the codebase is rearranged before the release lands, the pipeline now checks up front whether that rearrangement moved or deleted any file the release depends on. *Why it matters:* it prevents a late-stage surprise where a file the release expects has quietly moved.
- The pipeline's design and engineering steps get two small clarity additions — one on tracing which change belongs to which task, and one on being precise about whether a "frozen specification" refers to the written spec or the finished work product. *Why it matters:* both remove a common source of ambiguity that otherwise only surfaces as rework later in the release.

## Known limits

- The commit-traceability addition is intentionally **advisory**, not enforced. Under the platform's normal one-person-per-branch execution model, which change belongs to which task is already reconstructable from the commit messages, so this release documents the guidance without building an automated check. If the execution model ever changes, promoting it to an enforced check is a small additive follow-up.
- These are documentation edits to the release pipeline's reference material. They take effect for releases going forward and are not retroactive.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**CHEAP / HIGH confidence.** All three changes are additive wording and checklist edits to reference documents — no data, no schema, no runtime behavior. Rolling back is reverting the release PR with no migration.

### Operator and engineering detail

- **Placement forward-check (Stage 4, #3).** A new Phase A0.7 / G-PL3 paragraph in the Stage-4 planning reference (with a matching governance summary in the release-process reference) adds a pre-planning check that runs the unified `git log <base>..origin/main --name-status --find-renames` predicate to detect directory-crossing renames and in-scope deletions on the mainline since the release branch's base. It composes with the Stage-4 structural sub-audit and the Stage-12 pre-merge divergence check rather than duplicating them. This closes the "release branch cut before a structural reorg → new-file placement collides at deploy" pattern.
- **Commit-group traceability (Stage 6, #226).** A "documented simplification — advisory, not enforced" note added after Phase B1 in the Stage-6 engineering reference, plus an enforcement-posture sentence in the sub-task methodology standard. A stale target-path in the milestone description (it named a `templates/` home that does not exist; the file lives under `standards/`) was corrected into the plan's change matrix at Stage 4.
