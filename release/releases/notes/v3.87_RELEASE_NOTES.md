# Design diagrams and process flows in the docs are now labeled and findable

2026-07-24 · v3.87

Many of the platform's design artifacts — the diagrams, data flows, and process descriptions that live *inside* its documentation — carried no label, so they could not be told apart from ordinary text or listed as a set. This release gives each one a small, findable marker and adds a rule for how new ones declare themselves, so the whole set can now be listed with one search, checked for gaps, and kept from silently going out of date.

## Who this affects

- Anyone who reads or maintains the platform's documentation and design diagrams. Project and operations work is unaffected — this changes how the platform's own design docs are labeled, not any project deliverable.

## What changed for everyone using the platform

- **The design diagrams and process flows embedded in the docs are now labeled with a findable marker.** Before, an embedded diagram read the same as ordinary text; now each one carries a one-line marker naming what it is and what it describes. *Why it matters:* the whole set of design artifacts can be listed with a single search, so a reader can find them and a reviewer can tell when one is missing or has drifted.
- **A new plain-language guide explains how a release leaves its record.** A short "release record-keeping" page now walks through how any shipped version traces to its entry in the release history. *Why it matters:* you can follow a release from its version number to the record of what changed, without reading the tooling.
- **The rule that every kind of process has a design artifact was corrected and made checkable.** The rule previously left out its own most common case — a diagram embedded in its parent document — and that gap is now fixed, with a way to check the set is complete. *Why it matters:* the "every process has a design artifact" goal can be verified instead of assumed, so a missing or orphaned diagram surfaces instead of hiding.

## Known limits

- The marker has to be added by hand when a new design artifact is written, so a document whose diagram is never marked stays invisible to the search until someone marks it. An automatic check to catch an unmarked artifact is planned but not yet in place.
- A few refinements were deliberately left for follow-up work — extending the detection rule to one more table-rendered case, tightening how a whole-file artifact names what it describes, and a small cosmetic fix to one label. None affect the labels shipped here.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE** · confidence **HIGH**. Rolling the whole release back is a single revert of the merge. The one wrinkle: once the labels are in place, a reversal has to strip them back out — but no data is converted and no format anyone else depends on changes, so nothing has to be migrated.

### Operator and engineering detail

**Identification mechanism (#3725).** The platform's *default* artifact placement — a section embedded in a parent document — previously carried no marker, no frontmatter, and no naming convention, so an embedded artifact was indistinguishable from prose and the artifact set could not be enumerated. A current-state survey proved identification cannot be rendering-based: three of the seven flow types render as markdown tables, and several of the heaviest artifact-bearing files carry zero fenced blocks and zero Mermaid, so any diagram-shape heuristic is structurally blind to them. The mechanism promotes the `depicts:` / `flow_class:` frontmatter fields to required for dedicated artifact files, corrects the Human-process current-state cell in §2, and adds a new §12 of per-flow-type detection criteria (table-aware for the three table-rendered types) plus the enumeration query. The #64 architecture pilot gains its frontmatter as the proof target. **ADR-089** records the embedded-artifact declaration decision — a section-level HTML-comment marker, chosen over a parent-frontmatter index (which decouples declaration from artifact and goes stale) and over a canonical-heading convention (which pollutes the reader-facing heading).

An embedded design artifact now declares itself with a section-level marker placed on its own line directly under the artifact's heading; the full set is enumerated with one enum-anchored, field-order-tolerant search:

```
<!-- design-artifact: flow-class=data-flow; name=stage-io-contracts; depicts=core/schemas/stage-io-contracts.md -->

grep -rnE '<!-- design-artifact:[^>]*flow-class=(architecture|data-flow|agent-process|human-process|concept-model|skill-flow|decision-tree)\b' core operations release docs
```

**Spike completion and the collapse decision (#3614).** With artifacts now identifiable, the enumeration spike produced the real per-flow-type gap as a query result rather than an estimate, and the confirm-or-collapse scope decision rendered **COLLAPSE**: five of the six planned flow-type builds were already covered and needed only to be *declared*, not authored. The corrected completion condition — adding the default embedded-in-parent arm the inherited criteria omitted — is homed in a dedicated how-to outside the standard, so it does not contend with #3725's edit on the same file.

**Declare-sweep and the one real build (#3798, #3441).** The five collapsed flow types were swept: 24 embedded-marker declarations now sit across the data-flow, concept-model, agent-process, decision-tree, and skill-flow artifacts, and the skill-flow markers rebuilt 14 packaged skills. Human-process was the one flow type with no existing artifact, so it kept its full build — a new dedicated page, release record-keeping, with its frontmatter. The design-artifact set at ship time is **24 embedded-marker declarations plus 2 dedicated-frontmatter files** (the architecture pilot and human-process) across the seven flow types.

**Version lineage.** Planned as v3.86 and re-rendered to v3.87 after a concurrent release claimed v3.86; the binding claim is the tag cut at merge, so a name chosen earlier is only a lease. This release cut no tag for the abandoned name, so the re-version ledger correctly records nothing.

**Deferred refinements.** Non-blocking follow-ups are tracked separately: extending the §12 rule-7 detection to the remaining table-rendered case, tightening whole-file `depicts:` scoping, a cosmetic bold-label fix on one marker, an adjacent mark on the architecture overview, and a dual-classifiable stage-04 block. None change the artifacts shipped here.
