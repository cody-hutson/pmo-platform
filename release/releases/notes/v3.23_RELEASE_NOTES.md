# A project health-check you can run on demand: what drifted, with the receipts

2026-06-30 · v3.23

This release adds **`health-check`** — a skill that audits one project for drift between the state you track and the canonical sources that state is supposed to mirror (Confluence, Jira, Smartsheet, SharePoint, plus your local trackers and PROJECT.md). It reads those sources, compares them to your tracked state, and hands back a categorized punch list: what is confirmed current, what is safe to fix, what needs a decision, what it could not verify, and which portfolio-level files have proposed edits. Nothing it finds is ever applied automatically — the output is a reviewable list, and any tracker change it proposes is staged for your approval, never written for you.

## What changed for everyone using the platform

- **Run `/health-check` on a project for an evidence-backed drift audit.** A new skill compares a project's tracked state against its canonical sources (Confluence, Jira, Smartsheet, SharePoint, plus your local trackers and PROJECT.md) and returns a categorized punch list of what drifted. *Why it matters:* you get a fast, sourced answer to "is this project's tracked state still accurate?" instead of manually cross-checking trackers against systems of record.
- **Seven modes scope the question to what you need.** `full` sweeps the whole project (the default); `timeline` audits dates and milestones (with day-of-week validation, and it refuses vague "week of…" ranges); `attribution` audits owners; `comms` audits communications coverage; `plan <name>` audits one named plan; `raid` audits the RAID log with its guardrails enforced; `sources` inventories your canonical sources with a per-source freshness verdict. *Why it matters:* you can ask a narrow question (just the timeline, just ownership) and get a focused answer rather than wading through a full sweep every time.
- **Nothing is ever applied automatically.** Findings are sorted into five fixed sections (confirmed-current, safe-to-fix, needs-a-decision, could-not-verify, proposed portfolio-file edits), each finding carrying a confidence label and a depth band; any tracker change the skill proposes is staged for your approval, and portfolio-file edits are diff-only. *Why it matters:* the audit can never silently rewrite your project state — you see what it found and decide what to act on, and a low-confidence or unverifiable finding is never promoted to the safe-to-fix bucket.

### What the output looks like

Every mode, every run, returns the same five sections in this exact order — a section with no findings still prints its header with `_(none)_`, so a clean section reads differently from one that did not run:

```
health-check · full · project: Atlas-Migration · 2026-06-30 14:30
[MCP UNAVAILABLE: SharePoint] — findings limited to local sources
Summary: 14 checks · 5 confirmed · 2 auto-actionable · 3 decisions · 2 unknowns · 1 rollup-diff

## Confirmed
- Go-live date 2026-07-13 (Mon) matches Jira fixVersion and PROJECT.md. [confidence: HIGH · S0]
- UAT owner "J. Okafor" confirmed in Smartsheet + Jira assignee. [confidence: HIGH · S0]

## Auto-Actionable
- Risk R-07 status is "Open" in the RAID log but Jira shows the blocking story Done; mechanical close-out. [confidence: HIGH · S1]

TRACKER_UPDATES:
  - target: raid-log.md
    action: MODIFY
    entry_id: R-07
    fields:
      status: Closed
    evidence: [SOURCE: Jira PROJ-412 status=Done 2026-06-28]
    reason: blocking story closed; risk no longer active

## Decisions
- Milestone "Cutover" date differs: Smartsheet 2026-07-20, PROJECT.md 2026-07-18 — Smartsheet is newer. Recommend adopt 2026-07-20. Reversibility: CHEAP / MEDIUM. [confidence: MEDIUM · S2]
- Comms: "Steering update" marked SENT 2026-06-15, response expected, none recorded after 14d. Recommend follow-up via /comms-writer (status only). Reversibility: CHEAP / MEDIUM. [confidence: MEDIUM · S2]

## Unknowns
- RAID item I-22 references a "vendor SOW" no surfaced source confirms. Searched: SharePoint (no connector — link-only), 04-PMO-Operations/, transcripts. [confidence: LOW · n/a]

## Rollup-Diffs
- PROJECT.md health "Green" → "Amber" proposed (2 substantive date mismatches open). Diff staged in 08-Generated/_health-check/; not written to the live file. Reversibility: CHEAP. [tier: CHEAP]
```

The `TRACKER_UPDATES:` block above is in the existing tracker-manager schema — `health-check` emits it for approval and routes it to `/tracker-manager`; it never applies it itself.

## Known limits

- **Read-and-recommend only.** The skill never writes a tracker, closes a risk, sends a communication, or edits a Tier-1 file. Auto-actionable items are staged for approval; Rollup-Diffs are diff-only in `08-Generated/_health-check/`.
- **SharePoint has no MCP connector today.** Any run that would probe SharePoint degrades it to "links exist; content not verifiable" and carries an `[MCP UNAVAILABLE: SharePoint]` banner — SharePoint targets are never asserted fresh (per ADR-051).
- **A finding it could not cross-validate is capped at MEDIUM confidence** and routed to Decisions/Unknowns — it is never promoted to Auto-Actionable on a single unverifiable source.
- The skill consumes the platform's existing confidence-band scale and tracker schema; it authors no new contract.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `epic:skill-health-check` label.

## Reversibility

CHEAP / HIGH confidence. This release adds a new skill, its references, its eval suite, a slash command, and one Architecture Decision Record (ADR-051); it changes no existing skill, schema, or stored artifact. Reverting the integration PR removes the skill in one step. ### Operator and engineering detail

**The health-check skill — v1 foundation (#1125).** This issue built the skill's full seven-mode contract once and implemented the three foundation modes (`full`, `timeline`, `attribution`). The contract is identical across every mode: a 4-intent block declaring the mode's purpose and bias, the five fixed H2 output sections (`## Confirmed` / `## Auto-Actionable` / `## Decisions` / `## Unknowns` / `## Rollup-Diffs`), a `TRACKER_UPDATES:` block emitted inside Auto-Actionable in the existing tracker-manager schema (never auto-applied), and the `S0-NONE..S3-STRUCTURAL` depth band paired with a HIGH/MEDIUM/LOW confidence label on every finding line. The skill projects onto the platform's existing `staleness-confidence-standard.md` band scale (ADR-043) rather than inventing a parallel one. `timeline` enforces the platform date guardrails (day-of-week validation; no generalized date ranges); `attribution` enforces the no-fabricated-owners guardrail. Delivered with three reference docs (`mode-intents.md`, `evidence-matrix.md`, `confidence-framework.md`) and an eval suite (7 judges, 11 cases, 3 fixtures).

**Extended modes — v2 (#1126).** This issue implemented the four value-heavier modes on the same contract: `comms` (Communications Tracker lifecycle — stale-SENT, obsolete-DRAFT, unsent-READY; closures route to `/comms-writer` status-only, never message content), `plan <name>` (drift of one named plan; requires a plan-name argument and returns an actionable "which plan?" prompt rather than guessing), `raid` (RAID-log guardrail enforcement — passive-voice risks, missing owners, missing mitigations, entries stale past 30 days; never auto-closes a risk), and `sources` (the canonical-source inventory and graceful-degradation surface — names the MCP-primary and local-fallback sets with per-source freshness verdicts and flags missing-but-expected sources). Both child issues shipped on one branch and one merge per the milestone-as-one-PR model.

**ADR-051 — the canonical source set + graceful-degradation contract.** The release authors `core/ADRs/ADR-051-health-check-mcp-primary-source-set.md`, which records two decisions the skill depends on: the MCP-primary / local-fallback canonical source set (audience-facing sources are the source of truth; local artifacts are fallback and cross-validation), and the graceful-degradation contract (an unreachable connector continues the run local-only with a degradation banner; an uncross-validated finding is confidence-capped and never auto-actionable). ADR-051 was ratified at the milestone's Stage 5 Decision Gate (2026-06-29) and authored at Stage 6 alongside the skill it governs.

This release also adds the `/health-check` slash command (`commands/health-check.md`), the skill's catalog row in `core/skills/registry.md`, and its deploy-roster entry — and ships the built `.skill` package.
