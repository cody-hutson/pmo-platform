# Measure and attribute agent token spend from local session data

2026-07-26 · v3.96

You can now see how many agent tokens a milestone or work item actually cost, computed from your own local Claude Code session data — no provider API or external service required. A new skill extracts per-session token spend, keeps it in an operator-local store, and rolls it up to the owning work item.

> **Skip the rest** unless you want to measure or report agent token spend.

## Who this affects

- Anyone who wants to measure agent token spend — the workspace operator running cost / FinOps analysis. The capability is opt-in: nothing changes until you run the new skill.

## What changed for everyone using the platform

- **Token-spend extraction from your local session data.** A new `finops-usage-extractor` skill reads your local Claude Code session transcripts and records each session's token counts — input, output, cache, and tool-use — into an operator-local store. *Why it matters:* you can measure real agent token spend from data you already have, with no provider API key and no external service.
- **Spend attributed to the owning work item.** The skill rolls each session's spend up to the milestone or issue that owns it, and anything it cannot place lands in a visible "unattributed" bucket alongside a coverage number. *Why it matters:* you can answer "how many tokens did this milestone cost" and see exactly what did not resolve, instead of trusting a silent total.
- **Your usage data stays off the repo by construction.** The store is operator-local and ignored by git, and the extractor refuses to write if the target would land somewhere tracked. *Why it matters:* token records carry branch names and local paths, so this keeps them out of a public repository automatically.
- **Extraction reads your transcripts read-only.** It never edits your session data; the store is a cache that rebuilds from the source on demand. *Why it matters:* running it is safe to repeat and cannot corrupt your source of truth.

## Known limits

- Milestone-level attribution is reliable from local data alone; attributing spend to an individual issue is best-effort, and a hub-vs-spoke role split is not attempted yet — both are planned for the next FinOps milestone, `agent-finops-intelligence`.
- The optional provider cost connector is off by default; extraction completes from local data without it.
- On the hub-spoke model, spokes run as separate sessions, so per-subagent in-transcript records are rare by design; cross-session spokes are attributed as work-item spend, not as nested subagents.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. The feature is additive and content-only — reverting the release removes the skill, schema, and convention, and the operator-local store can be deleted at any time (`rm -rf` the store). No data migration; your session transcripts are never modified.

### Operator and engineering detail

**Data foundation + frozen schema.** The store's contract is a new tracked schema, `finops-usage-store-schema.md`, frozen at v1.0.0 by slice C1 (#3909) with the `meta` / `session` / `subagent` record kinds — cache-write tier split (`cache_creation.{total, ephemeral_1h, ephemeral_5m}`) and `service_tier` were folded in before the freeze so the cost-determining dimensions are captured up front. Slice C2 (#3910) extends it additively to v1.1.0 with the `rollup` and `coverage` record kinds and two optional `session` fields, touching no frozen v1.0.0 field. The store itself is a derived JSONL cache — a deterministic projection of the session transcripts, which remain the source of truth — so it ships no seed file and can be rebuilt at any time. The session→work-item mapping algorithm (the ordered local-only resolver and the `unattributed` rule) lives in the new `finops-attribution-convention.md` standard.

**Fail-closed exfil control (the Stage-5 security remediation).** The r1 design guarded the store with static `.gitignore` patterns alone, which fail open for a custom store path that resolves inside the repo but matches no pattern — a real usage-data leak surface on a public repo. The r2 adversarial review replaced it with a resolve-time `git check-ignore` guard: before any write, the extractor refuses (a dedicated non-zero exit) when the resolved store falls inside a git repository but is not ignored there. Paired with CIAC-3 data-hygiene hardening — all tooling tests use synthetic session fixtures, and no real session-data value appears in any committed or published artifact — this is what keeps token records (which carry `git_branch`, `cwd`, and work-item identifiers) off the public repo. The two decisions are recorded as ADR-096 (data home + git-ignore enforcement) and ADR-097 (attribution convention).

One synthetic `rollup` record (schema v1.1.0) — a work item's spend rolled up from its sessions; every value below is fabricated, not real session data:

```jsonc
{
  "record": "rollup",
  "work_item": "milestone:v9.9",            // synthetic example, not a real milestone
  "work_item_kind": "milestone",
  "attribution_tier": "branch-milestone",   // reproducible from local data alone
  "reproducible": true,
  "tokens": { "input": 120000, "output": 45000,
              "cache_creation": { "total": 80000, "ephemeral_1h": 0, "ephemeral_5m": 80000 },
              "cache_read": 900000 },
  "session_count": 4,
  "token_source": "exact"
}
```
