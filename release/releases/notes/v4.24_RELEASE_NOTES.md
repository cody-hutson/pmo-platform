# Checks must now prove they stay quiet on correct content

2026-08-12 · v4.24

A check that flagged everything used to satisfy its own acceptance criteria perfectly, because those criteria could say what a check catches but never what it leaves alone. This release adds the missing half, and turns two backlog blind spots into findings the platform's check run reports.

## What you need to do

1. When you file a work item whose deliverable is a **mechanical check** — a script, lint, hook, gate, or CI job that emits a finding — add one acceptance criterion naming a specific input the check must **not** flag, and state that its expected result is **zero**. The input should differ from a genuine defect in exactly the property the check tests.
2. Assert that zero at **every invocation option that narrows what the check looks at or changes what it compares against**, not only at the check's default invocation. Open the check's argument parser and list those options — that list is the obligation.
3. If your item **adds** a check rather than modifying an existing one, name the intended options or mark the enumeration as deferred to design. It is then filled in and graded when the design fixes what the check's argument surface actually is; a deferral marker that is never discharged is an unsatisfied criterion, not an exemption.
4. Nothing is owed for a work item that ships no mechanical check, and nothing is owed retroactively — see Known limits.

## What changed for everyone using the platform

- **Acceptance criteria for checks now have to cover precision, not only capability.** A work item shipping a mechanical check must name an input the check must leave alone and state that its expected result is zero. *Why it matters:* an over-firing check used to pass its own acceptance criteria perfectly, because nothing in a capability-only criteria set contradicts a check that flags everything.

- **The platform's check run reports a stage sub-task filed without a milestone.** *Why it matters:* a sub-task with no milestone is invisible to every milestone-scoped query the pipeline runs, so a release could silently lose part of its own scaffold while every surface still reported green.

- **The check run also reports an epic that is really a whole initiative.** It identifies a container whose scope covers an entire label family rather than one thrust inside it. It reports and never blocks, in any mode. *Why it matters:* these containers carry no parent link to the work beneath them, so nothing surfaced them except manual grooming months after they were created.

- **The packaged-skill freshness gate now runs on every pull request.** It no longer decides whether to run based on which paths a change happened to touch. *Why it matters:* a change that could leave a packaged skill stale used to show green by never running the gate at all — which had already happened, staling three packages through changes the path filter did not cover.

- **The issue-reference gate can be run before you push.** The logic that lived inside the CI job is now a script with a fixture suite covering reference blocks, inline provenance, fenced content, overrides, exemptions, legacy identifiers and unresolvable references. *Why it matters:* you can check a reference block locally instead of learning the verdict from a red check after pushing.

- **The deploy-tools reference documents every tool in its directory.** It described 13 of 32; the remaining 19 are written up, and a coverage rule now states that the reference is exhaustive rather than a sample. *Why it matters:* a tool that exists but is undocumented is a tool nobody except its author can safely run.

## Known limits

- **The initiative-detection leg reports and never blocks**, in any mode. That is deliberate: one of its three tests is lexical, so renaming an epic can change its verdict and a single-word label weakens it. Every finding prints the evidence that produced it — the matched label tokens and the in-family references — so a wrong one can be falsified in a single read.
- **The precision obligation applies to work items entering intake from this release onward.** Items authored earlier, and items already in flight when it shipped, are graded against the previous four tests and are not reopened. This release's own cards are exempt for the same reason: they were written before the obligation existed.
- **This release ships the detection of milestone-less sub-tasks, not the repair.** The 278 existing issues are backfilled under a separate work item, because a mutation across 271 closed issues cannot be undone by reverting a merge.
- **The extracted issue-reference checker's equivalence with the CI logic it replaces was verified by agents, not by CI.** This is a known residual accepted at the plan-review gate rather than an oversight; the detail is in the operator section below.

Report issues on the platform's GitHub issue tracker.

## Reversibility

CHEAP / HIGH. Reverting the release merge restores every file; no data migration, no deployment to reverse, no operator data touched. Two caveats travel with the revert: the extracted issue-reference gate needs its fixture suite re-run afterwards to confirm the restored inline logic returns its pre-release verdicts, and the precision obligation lives on two surfaces that must revert **together** or they diverge with nothing to detect it.

### Operator and engineering detail

**The initiative lint is a three-way conjunction, and the reason is a symmetry finding rather than a tuning preference.** The obvious predicate — an epic sharing a `project:` label with N other open epics that are not its children — was implemented and measured against the live tracker before it was rejected: it flags **39 of 42** open epics (92.9%). The cause is structural. The family shape is *symmetric*: a leaf epic shares its label with exactly the same non-children a container does, so every leaf is a false positive by construction, and raising N cannot repair a symmetric predicate. What shipped is a conjunction over that shape — family membership, coextension of the label slug with the title head, and in-family fan-out in the body. Measured individually against the same population the three limbs flag **39, 4 and 6**; conjoined they flag **2**, with zero false positives across seven named near-miss classes. No limb is decorative, and dropping any one restores an over-fire.

**The precision obligation binds to the check's own parameter surface, not to the scopes its author happens to mention.** The obligation's first formulation would have passed the very check whose over-firing motivated it. That check carried a genuine two-armed fixture harness, but its must-not-flag arm ran only at the default invocation with the baseline disabled, while the defect lived where a path-scoped invocation met a *loaded* baseline — the stale set computed against the full baseline while only the scoped subset was scanned. Both parameters had been exercised individually; their combination never was. The arm was real, non-vacuous, and blind. The obligation is also *scoped* by inheritance from the existing capability-class predicate rather than by an invented one, which is what keeps it off every item that ships no check and stops it becoming universal boilerplate.

The shape of the change, as an author writes it:

```
capability-only (passes the old tests, and an over-firing check passes it too):
  predicate: the lint flags the seeded miscount fixture, producing a
             non-empty finding list.

conformant (the discrimination arm, at each narrowing parameter):
  predicate: the lint flags the seeded miscount fixture AND returns
             exactly zero findings against the near-miss fixture whose
             stated count is correct, at both the whole-tree invocation
             and the path-scoped invocation with the baseline loaded.
```

**The release was designed to be its own first test of the obligation, and that test returned a finding rather than a pass.** Three of the seven cards ship mechanical checks, with the one card shipping no code as the negative control — a precision criterion appearing *there* would have been the signal that the obligation had leaked into universal boilerplate. The self-application check found that **0 of 3** check-shipping cards stated an expected zero, and every acceptance spoke concurred this was an authoring gap in the criteria rather than a delivery gap in the code. At the plan-review gate it was therefore ruled **not-applicable by cutover** rather than failed: the release *produces* the obligation, so its own cards were authored before it existed and a rule binding them would be unsatisfiable by construction — grading them against it would record an authoring artifact as a defect. A one-line introducing-release clause now sits on both doctrine surfaces, and the obligation binds from the next release forward. The finding itself stands on the record.

**One residual was accepted at the gate, and it is stated rather than buried.** The equivalence proof for the extracted issue-reference gate has **no CI attestation**. The discovery job checks out shallow and prints a reasoned skip, so the verification standing between a required merge gate and a silent behaviour change is agent-produced only. It was flagged at dev testing, re-flagged at acceptance review, and explicitly not discharged. It is bounded rather than unexamined: two independent agents reproduced it with different mutations, including the load-bearing case where a *strengthening* mutation left exit codes agreeing at 1 while the report text differed by six lines — an exit-code-only comparison would have passed a silently strengthened merge gate. Accepted as a known residual at the operator's GO.

**Six defects were caught before shipping that a less adversarial pipeline would have passed**, and they are worth naming as a set because five of the six were found by controls rather than by review: a lint that flagged 39 of 42 open epics; an implementation that would have counted 10 against a true 278; an equivalence proof with no proof it could disagree; a byte-identical extraction that would have turned a sibling required check red by crossing a gate boundary; an acceptance criterion that passed whether or not its fix worked; and a check declared as advisory that moved the exit code in its shipped configuration.

**The path filter was deleted rather than widened.** Widening was falsified during design: a fourth input was uncovered too, and an earlier resolver change had already reopened the same gap once without anyone noticing. A filter that must enumerate every input that can stale a package is a filter that will be wrong again, so the gate adopted the codified always-reports posture instead, and the coverage register was reconciled to match.
