# Release pipeline re-verifies freshness and constrains agent write-access

2026-07-12 · v3.70

Internal reliability work on the platform's release pipeline. This release adds a freshness gate that re-runs each bundled work item's own check against live `main` before any build agent launches — so work that quietly went stale (already fixed upstream, or changed scope) is caught up front instead of being built against a defect that no longer exists. How you use the platform is unchanged.

> **Does this affect me?** Only if you run platform releases through the hub-and-spoke pipeline, or maintain its governance files. Day-to-day skill users are unaffected.

## What changed for everyone using the platform

No user-visible behavior changes — this is internal release-pipeline hardening. See the operator detail below.

## Known limits

- The freshness gate re-runs only cards that carry a machine-runnable check; cards with judgment-only acceptance criteria still pass through to the existing per-agent re-review — except drift/reconciliation-class cards, which are always re-verified.
- The related "enforce triage formatting at the deploy gate" flip (#1686) was **deferred** from this milestone: turning it on today would block deploys against a 128-issue backlog of pre-existing formatting warnings, and the gate's design (it checks the whole backlog, not the release being shipped) warrants a re-review first. Tracked in observation #3352.
- Five non-blocking follow-ups (observations #3352 / #3354 / #3355 / #3383 / #3388) were filed for corpus and tooling hygiene surfaced during the release; none affect this release's behavior.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH confidence.** The change is documentation, protocol, one release-tool fix, and one architecture-decision record — no data or state migration. Rollback is a revert of the release PR plus a yanked tag/release; recoverable, but stakeholder-visible rather than a silent undo.
