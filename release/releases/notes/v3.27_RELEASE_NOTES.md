# Platform docs now carry consistent metadata — and a check keeps it that way

2026-06-30 · v3.27

The platform's reference documents under `core/` — the standards, schemas, specs, disciplines, and rules the platform runs on — now follow **one written rule for the YAML metadata at the top of each file** (the "frontmatter"). The rule says what every doc must carry and what a doc carries because of what *kind* of doc it is. About 140 framework reference docs that previously had no metadata block were filled in to match, and a new automated check enforces the rule on the governance-class docs and warns about everything else. The result: the reference corpus is consistent and machine-readable, so tooling can find a doc's version anchor and a reader can see at a glance what each doc is and what depends on it.

## Who this affects

Anyone who **authors or edits a platform-reference doc under `core/`** (a standard, schema, spec, discipline, rule, protocol, how-to, template, or reference). New docs in those folders are now expected to carry the standard frontmatter, and the governance-class docs are checked at CI time. If you don't author `core/` docs, nothing in your day changes — this is corpus hygiene under the hood.

## What changed for everyone using the platform

- **One written frontmatter standard for platform-reference docs.** A new standard (`core/standards/platform-doc-frontmatter-standard.md`) defines the required metadata for each kind of `core/` doc and a single canonical list of document `type` values. *Why it matters:* there's now one place that answers "what metadata must this doc carry?", instead of every author guessing — so the corpus stays uniform and tooling can rely on it.
- **~140 reference docs backfilled to match.** Framework reference docs that had no metadata block were filled in with the required fields. *Why it matters:* the docs that tooling reads for a version anchor are no longer silently skipped, and every reference doc now declares its purpose and blast radius up front.
- **A CI check that keeps it consistent.** A new check enforces the standard on the governance-class docs (Tier A) and warns about the rest, so drift is caught at pull-request time rather than discovered later. *Why it matters:* the standard doesn't decay — a new doc that forgets its frontmatter is flagged before it lands.

## What a conforming frontmatter block looks like

Every in-scope `core/` doc carries five core fields, plus a couple more depending on its class. A `standard`-class doc, for example, looks like this:

```yaml
---
title: Platform-Doc Frontmatter Standard      # human-readable title
purpose: Required + optional frontmatter fields per platform-doc class
type: standard                                # one canonical value: standard | schema | spec | discipline | rule | protocol | how-to | template | reference
status: ACTIVE                                # ACTIVE | DRAFT | DEPRECATED | SUPERSEDED
reversibility: CHEAP / Confidence HIGH        # the doc's reversibility tier + confidence
consumers: "who depends on this doc — the blast radius a change must check"   # required for standard / schema / spec
# framework_version_anchor: vX.Y              # required only for docs cataloged in framework-catalog.md
---
```

The first five fields (`title`, `purpose`, `type`, `status`, `reversibility`) are required on every in-scope doc. `consumers` is required for `standard` / `schema` / `spec` docs; `framework_version_anchor` is required only for docs listed in the framework catalog. A handful of optional fields (`composes_with`, `parallel_to`, `tags`, `domain`, …) are available when they carry meaning.

## How to use it

When you author or edit a doc under `core/`, copy the block above and fill it in for your doc's class. Read `core/standards/platform-doc-frontmatter-standard.md` for the full per-class field tables. The CI check tells you at pull-request time if a governance-class doc is missing a required field.

## Known limits

- **Enforced on Tier A, warn-only elsewhere.** The check blocks only on the governance-class directories (Tier A); for the rest of `core/` it warns but does not block yet. The remaining tiers (B/C) and the ADR class are scoped as follow-on backfill.
- **`core/` reference docs only.** The standard governs authored K1 platform-reference docs under `core/`. It deliberately does not cover skill `SKILL.md` frontmatter, release plans/notes, or project operational files — those keep their own existing conventions.
- Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `28-corpus-frontmatter-standardization` milestone.

## Reversibility

MODERATE / HIGH confidence. The standard and the CI check are each removable in one step (delete the standard file; revert the `deploy.sh` hunk and the check tool). The ~140-file backfill is additive — reverting restores the prior no-frontmatter state with no body content lost. Reverting the integration pull request un-does all three pieces atomically. Standard rollback window.

### Operator and engineering detail

**The standard (#295).** `core/standards/platform-doc-frontmatter-standard.md` is the keystone. It fixes three things: the required core field-set every in-scope `core/` doc carries (`title` / `purpose` / `type` / `status` / `reversibility`); the required-by-class fields (`consumers` for standard/schema/spec; `framework_version_anchor` for any doc cataloged in `framework-catalog.md`); and the recommended/excluded fields. It also fixes the canonical singular `type` enum (`standard`, not `standards`), resolving the observed singular-vs-plural drift. It is deliberately scope-disjoint from `core/schemas/frontmatter-schema.md`, which governs project operational artifacts (K4) under a project's `01-08/` folders — disjoint populations, disjoint field sets, disjoint lineage; a doc obeys exactly one. The unify-vs-registry question (one unified standard with per-class extensions, not a dialect registry) was settled upstream and is recorded as a slim design-rationale section rather than a standalone ADR.

**The Tier-A backfill (#109).** Mechanical, additive frontmatter backfill across the framework reference docs that previously carried no metadata block — under `core/disciplines/`, `core/schemas/`, `core/rules/`, `core/governance/`, and `release/references/`. The backfill closes a concrete tooling gap: `check-version-anchors.py` parses the `framework_version_anchor` field, and a cataloged doc with no frontmatter was being silently skipped by that check. Backfilling the frontmatter brings those docs back under the version-anchor check.

**The CI gate (#2220).** A new `core/deploy/tools/check-doc-frontmatter.py` (with a `_frontmatter.py` parsing helper and a `skip-doc-frontmatter-check.txt` allowlist) wired into `core/deploy/deploy.sh` as a new check, plus an update to `check-version-anchors.py`. It ships in warn→enforce form: **enforce** on the governance-class directories (Tier A), **warn** on the rest of `core/` — the same shakedown-then-flip pattern the platform's other corpus-integrity checks use. The standard defines the contract; this gate is the machine that keeps the corpus from drifting away from it.

All three shipped on one branch and one merge per the milestone-as-one-PR model. The release re-versioned forward from a provisional v3.25 to **v3.27** at the Stage-12 atomic claim (concurrent releases had claimed v3.24 and v3.26 while this branch was in flight; v3.25 is a permanent benign gap). For full implementation detail see the [RELEASE_LOG.md entry](https://github.com/cody-hutson/pmo-platform/blob/main/release/releases/RELEASE_LOG.md#deployment-log-v3-27) and the [integration PR](https://github.com/cody-hutson/pmo-platform/pull/2545).
