# See where agent spend goes, and measure estimates against reality

2026-07-29 · v4.0

You can now ask where agent token spend went — by work item, by working directory, by skill, by model, over time — and every answer that rests on partial information says so on the face of it. You can also ask what a planned piece of work is likely to cost, and close the loop afterwards by comparing what was estimated against what actually happened.

> **Skip the rest** unless you plan work in the delivery tracker, or you want to know where agent token spend is going.

## Who this affects

- Anyone planning or sizing work whose estimates you would like checked against what actually happened.
- Anyone who wants to know where agent token spend went.

## What changed for everyone using the platform

- **Spend reports, sliced the way you actually ask the question.** You can now break spend down by work item, by working directory, by skill and by model, over a date range you choose, with a trend view across weeks. *Why it matters:* "where did it go" stops being a question you can only answer by reading raw session data.
- **Every partial answer says it is partial.** Any slice built from incomplete information carries a coverage figure and an explicit uncovered-remainder row, and the numbers reconcile — the covered and uncovered parts add up to the total. *Why it matters:* a chart that is missing two-thirds of its data now tells you so, instead of looking complete.
- **The trend view refuses to guess.** When coverage changes across the periods being compared, the trend declines to state a direction rather than reporting a rise that is really just better measurement. Empty periods are drawn explicitly instead of being skipped. *Why it matters:* the most misleading chart is the one that reports a confident trend from data that got better rather than spend that got worse.
- **Estimates for planned work, when the history supports one.** You can ask what a planned item is likely to cost. The answer lists the past items it was based on, states a confidence level, and names the rule that produced it. When there is not enough comparable history, it declines rather than guessing. *Why it matters:* an estimate you can audit is worth more than a number, and a refusal is more useful than a confident wrong answer. See the known limits below — today it declines for most real questions.
- **The estimate-versus-actual loop closes.** Estimates are now recorded when work is admitted and actuals recorded when it closes, keyed together so they cannot drift apart, and the difference is reported back as accuracy, bias and a red/amber/green band. *Why it matters:* estimating gets better only if someone measures it, and until now nothing did.
- **Calibration is offered as advice, never applied behind your back.** When measured bias suggests your estimates run low, planning shows a recommended adjustment beside your own figure with its full basis. It changes nothing on its own. *Why it matters:* the team keeps its own number, and a suggestion that silently overwrote it would be worse than no suggestion.
- **Spend records no longer keep full directory paths.** The usage store now keeps only the final directory name rather than the complete path to it. *Why it matters:* the file holding your spend history stops carrying a full map of your machine.
- **Nine checks that looked like they were passing were doing nothing.** Each was a case where something silently stopped working while still reporting success — including a single invisible character in one file that made every text search over it come back empty, and, most consequentially, the discovery that none of the four scripts' built-in self-checks were run by anything at all. *Why it matters:* eight of those nine fixes were guarded by self-checks that nothing executed, so shipping them would have repeated the exact pattern this release set out to end.

## Known limits

Three limits are real, known, and filed. None is a defect discovered after the fact — each was found during the release and accepted deliberately rather than papered over.

- **The estimator declines for most real questions today.** The bridge that supplies its history yields roughly ten usable comparable items out of 48 records, which is below the threshold it requires before it will answer. It works correctly on a sample item; it will not generalize until there is more history behind it. Tracked as [#4206](https://github.com/cody-hutson/pmo-platform/issues/4206).
- **Confidence can read HIGH on a set that is really two clusters.** The spread measure the confidence label is built on tolerates a split population, so an estimate drawn from two very different groups of past work can be labelled HIGH while the same output shows the average sitting more than sixteen times the midpoint. Read the comparables list, not just the label. Tracked as [#4207](https://github.com/cody-hutson/pmo-platform/issues/4207).
- **A check can declare that it stops the work on failure without naming what runs it.** There is no requirement that a check which claims to be enforcing name the thing that executes it, so a check can ship, read as enforcement, and never run. This is the same class as the nine fixed above — the instances are closed, the convention that allows them is not. Tracked as [#4208](https://github.com/cody-hutson/pmo-platform/issues/4208).

Two further limits are worth knowing:

- The report has one dimension that renders a table of zeros when the underlying data does not exist, while still carrying the tool's strongest provenance label. It is known and cheap to fix.
- The measured-precision half of calibration reaches reporting but not planning: at planning time your declared confidence in an estimate still binds, and your measured confidence does not.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

EXPENSIVE / HIGH confidence. Undoing this release means reverting the whole merge — the spend-store changes and the calibration changes come back out together, and there is no clean way to take back one half. No data migration is involved: the usage store is a rebuildable cache, and one rebuild resolves it in either direction. A stale store is refused loudly rather than silently mis-read.

### Operator and engineering detail

**The store shape.** The `session` record replaces the absolute `cwd` with a `worktree` basename and gains five additive analysis sub-aggregates plus a stored coverage label. Each token-bearing map carries an always-present reserved `"unknown"` key holding the remainder the source did not attribute, which is what makes a partial dimension structurally incapable of under-reporting — the uncovered spend is *in* the map, never dropped. The new shape:

```jsonc
"worktree":   "<directory basename — never the absolute path>",
"by_skill":   { "<skill-name>": { "turns": <int>, "tokens": { … } }, "unknown": { "turns": <int>, "tokens": { … } } },
"by_mcp":     { "<mcp-server>": { "turns": <int>, "tokens": { … } }, "unknown": { … } },
"by_model":   { "<model-id>":   { "turns": <int>, "tokens": { … } }, "unknown": { … } },
"tool_calls": { "<tool-name>": <int> },
"stop_reason":{ "<stop-reason>": <int>, "unknown": <int> },
"dimension_coverage": {
  "by_skill": { "covered_token_fraction": <float 0..1>, "basis": "best-effort" },
  "by_mcp":   { "covered_token_fraction": <float 0..1>, "basis": "best-effort" }
}
```

The conservation invariants (`Σ by_X.*.tokens == session.tokens` leaf by leaf, and `Σ stop_reason.* == turns`) are asserted in the extractor's self-test, so the coverage label cannot drift from the buckets it describes. The store version stops encoding which processing phase has run; the presence of a `coverage` record is now the predicate for that, which matters because reading an extraction-only store as though a roll-up had run was previously possible and silent.

**The frozen-kind exemption, claimed rather than assumed.** Replacing a field on a frozen record kind reads, under the schema's own rule, as a major bump plus a coordination event across pinned consumers. That would have forced a store version of 2.0.0 for no safety gain. Instead the rule was amended to carry three conjunctive, individually falsifiable conditions — the store is a rebuildable derived cache, it has no external consumer, and every in-repo reader is updated in the same change — each of which was re-tested from scratch rather than asserted, and the exemption is claimed per-change and traceable to its decision record. A runtime preflight enforces the first condition instead of trusting it: a stale on-disk store is refused with a distinct exit code and a message naming the rebuild flag, rather than silently producing an empty roll-up while reporting perfect health.

**A conflict between two release-level criteria was decided, not left partial.** One criterion required that no shipped document route the deferred spawn-ledger marker to this milestone as an undelivered future; another required the frozen record kinds to stay byte-unchanged. They collide at exactly one line — the `No by_role field` note, which sits *inside* the frozen `rollup` kind. **The byte-unchanged criterion was preserved.** Three of the four pointers were re-routed to the durable owner (the parent Agent-FinOps epic); the fourth was left byte-intact and neutralized by a superseding note placed in the non-frozen region above it, which names the clause it supersedes, states plainly that the marker was not built here, re-homes it as an open enhancement on no shipped milestone, and records that the reserved coverage-basis enum is its upgrade path with no shape change. The surviving pointer is stale-but-superseded rather than dangling. This is recorded as a decided conflict with its reason rather than as an unremarked partial completion.

**The calibration capture path needed a full rework to be executable at all.** As first built, the acceptance criterion for recording an actual against a stored estimate could not be performed: nothing created the row. Five coordinated repairs landed mid-release — a row-creating write at the readiness gate rather than only a write at close; a row key of `(item × signal family × close ordinal)`, because a single close-keyed row silently collapses disjoint item sets; an asserted claim of completeness replaced by an enumerated sixteen-row grant table whose missing element was the very field the feedback lever needed; a citation pointing at a requirement that did not exist, reconciled by writing the requirement; and start-date immutability rebound to the *field* rather than to the action, so a corrective edit or a reopen is as prohibited as a close, anchored outside the surface's own rows. Acceptance then walked the whole five-step sequence rather than accepting the assertion, and confirmed every arrow has a named emitter, a named gate, and a fail-closed negative path — a close that resolves to no admission is surfaced as a missing admission, never synthesized. One repair did not reach the sprint template, which is still missing a required column; that is recorded on its issue rather than smoothed over.

**Nine fail-opens, and the one that made the other eight moot.** The recurring finding of this release was the same one its predecessor recorded: controls that read as controls and enforce nothing. A single NUL byte at a known offset in the extractor made plain text search over that file return nothing while reporting success, so every search-based verification against it had been passing vacuously. The store-shape preflight gated on the absence of all current records rather than the presence of any legacy one, so a mixed store walked straight through. An aborted report rendered clean and empty. But the load-bearing one was structural: a search across the workflow directory and the deploy script for the four script names returned **zero hits**. No workflow and no deploy check executed any of their self-tests, so the fail-closed assertions guarding the other eight fixes could not fire — shipping behind them would have reproduced the pattern exactly. The self-tests are now wired into continuous integration by extending an existing workflow that already declares this very invariant, rather than by adding a new one. That job is itself fail-closed: because a self-test that quietly degraded to zero assertions would report success forever, a precision probe deliberately breaks a real declared invariant in a throwaway copy and requires both a non-zero exit **and** the specific assertion name in the output. Both legs were executed before commit — the break correctly fails, and neutering the break correctly makes the probe report that the gate is blind.

**Merge mechanism.** Pre-merge conditions were all satisfied and re-verified at the merge instant against a mainline that had moved five times during the release, with continuous integration fully green. The merge itself required elevated permissions denied to the agent, so the stage handed back **blocked** with the protection control left intact rather than worked around, and the operator performed the merge. A check that had gone red since the review gate was run to ground before any merge attempt rather than merged through; its two underlying defects are filed. An earlier divergence against a concurrently-merged release was resolved by a true merge rather than a rebase, so every prior review comment citing a commit on this branch still resolves, and the two conflicting package binaries were rebuilt from merged source rather than side-picked.
