# Analysis writes work again, and a skippable safety check is fixed

2026-09-04 · v4.53

If you tried to save an audit or review into the platform's own analysis folder, a write guard refused you — that no longer happens. A separate guard that is supposed to check every script before it runs could be stepped around by spelling a command a slightly different way, and those spellings are now covered.

> **Skip the rest** unless you write analysis or audit notes into the platform's analysis folder, or you run scripts from a session.

## Who this affects

- Anyone writing an audit, review, or gap analysis into the platform's designated analysis folder from a session that is not a worktree session — the session shape the analysis standard actually anticipates.
- Anyone running scripts from a session. A small set of command spellings that previously ran unchecked are now checked, and some of them will now be refused.

## What changed for everyone using the platform

- **Analysis notes save again.** The guard that protects the platform's own configuration was also refusing writes to the folder the platform designates as the home for analysis work — the exact place its own standard tells you to put an audit. Those writes are now allowed. *Why it matters:* you can put an audit where the platform tells you to put it, instead of hitting a refusal that offered no fix and contradicted the standard you were following.

- **The new allowance is deliberately narrow.** It admits only dated analysis subfolders at the repository root — not the whole tree, not a folder that merely happens to be named "analysis" somewhere else, and not a path that walks back out through a `..` or `.` segment. *Why it matters:* one wrong refusal is removed without opening a side route into the protected files the guard exists to defend.

- **A script check can no longer be skipped by how you spell the command.** Before running anything, the guard finds the script by scanning the command's words — and it used to stop at the first word that did not begin with a dash. Two everyday spellings defeated that: an option written with a leading plus sign, and an option that carries its own separate value. In both cases the guard settled on the wrong word, concluded the command was not its business, and let it run without ever consulting the allowlist. *Why it matters:* two spellings of the same command used to get two different answers — one checked, one not — and now both are checked.

- **The change can only add checks, never remove them.** The corrected scan either stops at the same word the old one did, or keeps looking where the old one had already given up. *Why it matters:* nothing that was blocked before has become allowed, so if you meet a new refusal on a command that used to run, that is the guard finally doing the job it was always documented to do.

## Known limits

- One gap remains, by design and stated rather than papered over: if an option's own value happens to be a script path that is already on the allowlist, the scan legitimately stops there and the real script goes unexamined. This is strictly narrower than what it replaced — previously *any* value-carrying option hid the script unconditionally, with no further condition on the caller.
- The analysis allowance covers exactly one folder, at the repository root. Folders named "analysis" elsewhere in the tree are unaffected and are still refused.
- The single tracked file sitting directly in that folder is still not writable through this path. The allowance keys on a dated subfolder, which is the shape the analysis standard prescribes, so the one file that is not in a subfolder stays outside it.
- The allowance is written into the guard itself rather than into a settings file or an ignore list. That is intentional and is not a limitation that will be lifted — see the operator detail below.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH confidence.** Reverting the release restores both guards to their previous behavior. The analysis-folder half is cheap to undo — it reinstates a working-but-wrong refusal with no stored state and no settings to unwind. The script-check half is not: undoing it re-opens the bypass, so that revert is itself a security decision requiring sign-off rather than a routine rollback.

### Operator and engineering detail

**Why the scan asks a domain question instead of consulting an option table.** The obvious fix — a per-interpreter table of which flags take an argument — fails open on omission: one unenumerated value-taking flag leaves its argument unconsumed, the argument lands outside the operand domain, nothing is adjudicated, and the invocation reaches ALLOW. That is the original defect re-entering through its own repair, and it is the denylist construction the hook rules already forbid inside a fail-closed control. The replacement asks whether each token is in the arm's declared operand domain and keeps walking when it is not, so `+x`, `errexit`, `extglob` and an rcfile path are all simply not the operand and need no enumeration. One clause is load-bearing and easy to lose in a later edit: a token that cannot be resolved is never skipped, because advancing past a token is an exemption in the same sense skipping one is. A quoted path containing a space is the control that proves it — without the clause the walk advances onto a later fragment and adjudicates the wrong subject.

**The two-arm ordering in the analysis carve-out is the guard, not decoration.** `case` takes the first match, and the first arm matches dot segments and does nothing, so control falls through to the block. This is required *by* the carve-out: the path being tested is the raw, un-normalized target whenever neither it nor its parent exists, and a `case` glob matches across `/`, so a path like `analysis/../core/<file>` would otherwise satisfy the carve-out while naming a tracked platform file. A single `.` is rejected for a different reason — it does not traverse, but it does satisfy the subfolder requirement, which would admit the one tracked file the subfolder condition exists to exclude. A dotfile inside a real subfolder is neither form and remains admitted.

**The exemption is static because the alternative is a widening primitive.** This pattern lives inside the very surface the rule protects. An allowlist file would be agent-appendable by design, and delegating to the repository's ignore rules would answer from configuration that a single global setting can re-point with no hook rule in the way. For the self-modification guard specifically, neither is admissible, so the predicate is spelled out in the guard and anchored at the repository root — sibling paths elsewhere in the tree do not match.

**Coverage is executable, not asserted.** The change adds 469 lines to the hook's test suite across roughly thirty new arms, including plus-form options, options taking separate values, rcfile and init-file forms, quoted and variable-bearing paths, a control arm for the space-bearing quoted path, and a set of mutation arms that verify the tests actually fail when the fix is removed. Two arms are deliberately red-by-design pins: one records the declared residual named in Known limits, the other pins the scoping boundary.

**Documentation was reconciled in the same change rather than left to drift.** Three prose surfaces disagreed with the shipped behavior — including one line asserting a protection scope that was already false before this release and would have been more false after it. The generated hook-registry index was regenerated rather than hand-edited, since editing a fragment without regenerating leaves the index stale and the freshness check reports it.
