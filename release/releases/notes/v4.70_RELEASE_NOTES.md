# The plan check now says what it ran, what it could not, and what it skipped

2026-10-02 · v4.70

The check that grades a release plan's verification rows now reports four outcomes apart: a row that passed, a row whose command it could not run, a row that was never its job, and a row it could not read. A row can no longer pass because of a word in its description, drop out of the results, or pass while part of it went unchecked.

> **Skip the rest** unless you write release plans, run releases through testing and review, or read the results of the platform's release checks.

## Who this affects

- Anyone who writes the verification rows of a release plan
- Anyone who runs a release through its testing and review stages and reads the plan check's results
- Anyone who writes or reads a testing hand-off or an acceptance report that cites a criterion by number

## What you need to do

Only if you have a release plan in flight, or are about to write one. A plan that has already shipped needs nothing, and its recorded results stand.

1. Run the plan check on your plan again and read each row's new outcome. A row that now reads ERROR fails the run until its method is repaired. The usual causes are a search command that names no file inside its backticks, a test with nothing to test, and a count with no comparison written after it.
2. Where a row should be graded by the deploy check, write that check in backticks as the row's only command. A word such as "unchanged" or "regression" no longer sends a row there.
3. Where a row names a tool the plan check does not run — a script, an interpreter, or one command chained to another — either restate it as one read-only query with one comparison, or mark it deferred and name who grades it. Left as it is, the row reads UNRUNNABLE, which is not a pass.
4. Write one command per row. Where a row also needs a person's judgment, declare that part after the command and its comparison, as `[READER-GRADED — <what a reader grades>]`. The row then reads UNRUNNABLE and lists that part for the reader to grade.
5. For each cross-issue criterion, run the authoring check before planning ends and repair what it flags. At plan review, a cross-issue criterion that reads UNRUNNABLE, or that was skipped without a declaration, now counts as not met until it is restated or declared.
6. In a testing hand-off or an acceptance report, name the list each criterion number counts — the issue's, the design's or the plan's — using the two new columns and the header entry the templates now carry.

## What changed for everyone using the platform

- **A command the plan check cannot run is reported as UNRUNNABLE, never as a pass.** When a row's method names a tool outside the six read-only queries the check runs, or chains commands together, the row names that tool and says it did not run; when a row names several commands, it is graded on the first one it can run and lists every part that did not. *Why it matters:* a passing row now means every command it names ran and held, where before a row could pass on its first command while the rest of it never ran.

- **A row is graded by the command in its method, not by a word in its description.** A runnable command now outranks any keyword around it, and the deploy check grades a row only when the row names that check as its one command. *Why it matters:* 22 rows in plans on record had been handed to the deploy check, which tested none of what they claimed, and a failing command can no longer be turned into the deploy check's verdict by the word "unchanged" beside it.

- **A row with nothing to run is a named SKIP, and ERROR is kept for input the check could not read.** A row that describes a judgment, a named read, or behaviour another stage exercises is reported as skipped, with the reason. *Why it matters:* the error count now points at rows that need repair, where before 38 of 47 rows on one live plan read as errors and buried the real ones.

- **A method can no longer make the rows after it disappear.** A search command that named no file used to read the check's own list of rows and silently remove every row after it; such a command is now refused before it runs, and a run that reads fewer rows than the plan holds says so and fails. *Why it matters:* 45 rows across 7 plans on record had dropped out of their results without a trace, and a plan's tally now covers every row it holds.

- **Cross-issue criteria are checked for gradability when the plan is written, and plan review reads every outcome through one table.** An authoring check flags a cross-issue criterion the plan check could not grade, and a criterion only a person can grade is declared as such, naming its evidence. *Why it matters:* a criterion that needed a tool used to be impossible to satisfy at plan review; it now either runs or is graded by the operator from named evidence, and a skip is never read as a pass.

- **A verdict on a numbered criterion now says which list the number counts.** The issue, the design and the plan each number their criteria separately, so testing hand-offs and acceptance reports now name the list. *Why it matters:* "criterion 6 met" could point at three different criteria, and it now points at one.

- **The map that picks which test suite a change must run now reaches the tool test suites and the skill scripts.** It reached none of the 17 tool test suites it existed to select. *Why it matters:* a change to one of those suites or scripts now selects a real test run, where before the map recorded that no suite applied.

## Known limits

- UNRUNNABLE does not fail a run by itself. It is weighed where the criterion is graded: at acceptance testing for a per-issue row, and at plan review for a cross-issue one, where it counts as not met.
- A comparison written as "= N", "→ N" or "returns N" is still not read as a comparison. 56 rows in plans on record are written that way; write "expect N", "at least N" or "at most N" instead. Tracked in [#7837](https://github.com/cody-hutson/pmo-platform/issues/7837).
- A second command in one row is never run: it is listed as not run, so that row cannot pass. There is no authoring form yet for a later command that should run. Tracked in [#7838](https://github.com/cody-hutson/pmo-platform/issues/7838).
- A part of a method described only in prose, with no reader-graded marker, is invisible to the check, which grades the row on its command alone.
- A cross-issue criterion written in a table cell rather than a list entry is run as written, words and all, and the authoring check does not flag it there. Tracked in [#7646](https://github.com/cody-hutson/pmo-platform/issues/7646).
- Running the check today over a plan that has already shipped gives different results from the ones it recorded: 41 plans on record that used to end as failing now end clean, and 2 that ended clean now fail on a row that should not have passed. Shipped plans are records and are not re-graded.
- The self-tests the map now selects for skill scripts have no guaranteed runner in continuous integration yet. Tracked in [#7674](https://github.com/cody-hutson/pmo-platform/issues/7674).
- An installed workspace picks up the two changed skills when it next updates.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

MODERATE / HIGH. The release is a single merge: reverting it restores the previous plan check, binder and suite map, and plans grade under the old outcomes again with no data lost; the two changed skills are then re-deployed from the reverted tree. The revert stops once, on the release plan that the version claim renamed — keep that file and continue. The version tag stays in place as the record that the version was claimed.

### Operator and engineering detail

**One outcome partition.** `release/tools/verify-release-plan.sh` now emits five verdicts — PASS, FAIL, SKIP, UNRUNNABLE and ERROR — and UNRUNNABLE is the new one: a recognised tool outside `RUNNABLE_VERBS` (`grep`, `test`, `ls`, `head`, `wc`, `cat`), a designated command carrying shell syntax outside quotes, a scope assertion with nothing to grade, or a row whose designated command ran while another limb did not. It is never executed, never a pass, and it does not fail the run: exit 0 covers PASS, SKIP and UNRUNNABLE, exit 3 a FAIL or an ERROR, and exit 1 an internal error, a shortened record stream among them. The verb set is unchanged. `SCHEMA_VERSION` moves from 4 to 5 in one bump, which covers the new verdict value, the stream-state fields and the roll-up's counters. [ADR-208](https://github.com/cody-hutson/pmo-platform/blob/main/release/ADRs/ADR-208-a-method-the-verifier-cannot-run-is-reported-unrunnable.md) records the partition. One record and the roll-up from the merged tool, run with `--format=json` over its own can't-run fixture:

```json
{"issue": "#981", "id": "AC-9", "family": "per-issue",
 "method": "`grep -c -F \"RUNNABLE_VERBS\" release/tools/verify-release-plan.sh` at least 1 and `awk 'END{print NR}' core/CLAUDE.md.template` expect 4",
 "expected": "a runnable probe, then a tool: never a pass",
 "observed": "partial-execution: limbs run 1 of 2: limb 1 grep PASS count=14 (>= 1); limb 2 awk did not run (outside the verb set) — a command that did not run is not a pass",
 "verdict": "UNRUNNABLE"}
"rollup": {"pass": 2, "fail": 0, "skip": 6, "unrunnable": 8, "error": 0, "records": 16,
 "per_issue_rows": 10, "cross_issue_records": 4, "always_on_records": 2, "declared_deferred": 0,
 "no_command": 4, "skip_other": 2, "stream_state": "fetched", "records_parsed": 14, "records_read": 14}
```

**The route is declared in the method cell.** The executor reads no cell but the method cell to decide how a row is graded. The class-hint path is removed — a `Predicate class` column stays permitted as a reader's annotation — and the removal changed no output: the executors before and after it are byte-identical on 302 of 302 inputs. Within the cell a runnable probe outranks prose, a declared deferral is read outside every probe span, and the deploy-check oracle is reached by declaration only: a backticked `deploy.sh --check` as the designated command, with no other argument. Before the change 44 rows in the pinned plans reached that oracle; 22 reach it now, each by declaring the check. [ADR-207](https://github.com/cody-hutson/pmo-platform/blob/main/release/ADRs/ADR-207-a-rows-grading-route-is-declared-in-its-method-cell.md) records the seven decisions.

**Input isolation.** Both record loops now close their body's stdin, so no child can read the stream the loop is iterating, and a command that would read stdin is refused before it runs (`stdin-reader:<verb>`, an ERROR). The roll-up carries `stream_state`, `records_parsed` and `records_read`; a run that reads fewer records than the parser produced reports a degraded stream and exits 1.

**The regrade, attributed.** The pre-release executor and the merged one were run over 302 inputs — the 215 plans at the planning pin, 84 fixtures and 3 later plans — reading the record stream, never the markdown block. At the Stage-7 head 1,107 records change and each is attributed to one of the ten cards, with none unattributed; the two fix cycles that followed moved 4 more records and then none. 599 of the moves take a FAIL or an ERROR to a SKIP or an UNRUNNABLE, and the method cell is byte-identical across every one of them. By exit status, 41 pinned plans stop failing and 2 start: one on a count its file had outgrown, and one on a `test` with no operand.

**Authoring and review of cross-issue criteria.** `--ciac-lint` reads a plan's cross-issue criteria with the executor's own readers and runs nothing; it is gate criterion G4-06 at Stage 4. Checkpoint 3.5 in the release process now carries one reading table for Stage 9: PASS reads met; FAIL, ERROR, UNRUNNABLE and an undeclared SKIP read not met; a declared deferral awaits the operator's grade from the evidence it names. The table applies to a release whose Stage 9 begins after this one is on the mainline.

**Criterion namespaces.** Three lists number a card's criteria: the issue body, the Stage-5 design and the plan. The Stage-7 AC map gains `Namespace` and `Maps-to` on every row, and the two Stage-8 payloads declare their namespace once, by identifier class. `check-ac-binding.py` reads both criteria heading forms, appends the same `ns:` key to every line it emits, and checks a declared design-to-issue mapping. [ADR-210](https://github.com/cody-hutson/pmo-platform/blob/main/release/ADRs/ADR-210-acceptance-verdicts-name-their-criterion-namespace.md) records the decision. The AC map's header row and the acceptance matrix's machine-block header, as the specs now carry them:

```text
| AC | Issue # | Namespace | Maps-to | Verdict | Evidence |
# acceptance-matrix v1 · issue:#<N> · release:v<X.Y> · ns:AC=issue,INT=design · verdict:<ACCEPT|CONDITIONAL_ACCEPT|REJECT|HOLD> · score:<0.000> · met:<n>/<total>
```

**The selection map.** `runtime-suite-selection-map.md` now states one glob grammar, names git's pathspec with the `top` and `glob` magic words as the reference resolver, and decides overlaps by the longest literal prefix. Two rows are new: the tool test suites, each run by its own bare invocation, and skill-owned scripts, each run with `--self-test`. On the merged tree they select 19 suites and 8 scripts. [ADR-209](https://github.com/cody-hutson/pmo-platform/blob/main/release/ADRs/ADR-209-runtime-suite-selection-one-glob-grammar.md) records the grammar.

**How it shipped.** Ten cards were built on one branch in 70 commits and landed as one two-parent merge over 47 files. The plan carried a provisional version that another release claimed first, and the claim at the merge returned `v4.70` on the first attempt, as a signed annotated tag. Two skills were deployed and verified by content, `eval-writer` and `finops-usage-extractor`. After the claim, the acceptance-report template's `version:` and `eval-writer`'s were bound to `v4.70`, and `eval-writer`'s package was rebuilt from the bound source. On the merged tree the executor's suite reads 614 passed and 0 failed, and the executor grades this release's own plan 47 PASS and 12 SKIP over 59 records, with no FAIL, ERROR or UNRUNNABLE row.

For full implementation detail see the Deployment Log v4.70 entry in the release log, and [the release plan](https://github.com/cody-hutson/pmo-platform/blob/main/release/releases/plans/v4/v4.70_RELEASE_PLAN.md).
