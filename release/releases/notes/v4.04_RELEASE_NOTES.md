# Blocked tracker writes now work, and checks that could not fail now can

2026-08-01 · v4.04

The tracker assistant could not reach the definitions for six of the ten trackers it supports, so its own safety rule refused every write to them; all ten now resolve. Five other checks that reported success while proving nothing — an existence test standing in for a content test, a freshness probe that exited successfully on a stale verdict, a count that moved every run — were made able to actually fail.

> **Skip the rest** unless you write to project trackers, run the platform's own health checks, or maintain a check the platform declares.

## Who this affects

- Anyone whose work writes to the platform's project trackers — in particular the RAID log, artifact register, milestone tracker, stakeholder register, RACI, and sprint tracker.
- Anyone who runs the platform's own health checks and acts on what they report.
- Anyone maintaining the platform who writes down a new rule and expects something to enforce it.

## What you need to do

1. **Run the normal deploy step for your workspace.** The tracker fix lives in the packaged copy of the tracker assistant, so an existing install keeps the old, blocked copy until it is redeployed. The same step picks up three new test scripts this release registered as permitted to run.

No data is changed, no settings are migrated, and nothing else is required.

## What changed for everyone using the platform

- **Tracker writes that were being refused now go through.** The installed copy of the tracker assistant carried definitions for only four of the ten trackers it supports, while its instructions cited a definitions file the install did not contain — so its own safety rule, which stops a write when it cannot find the tracker's required fields, refused every write to the other six. Those six include the artifact register and the sprint tracker. The definitions file now ships inside the installed copy, and all ten trackers resolve. *Why it matters:* six trackers that quietly could not be updated are usable again, and not one instruction in the assistant had to change to get there.
- **A "packages are up to date" probe no longer exits successfully when it found staleness.** Run on its own, the probe printed a stale verdict and then reported success, so anything reading the result rather than the text — a script, an automation step, a person checking the exit status — was told the opposite of what the probe had just printed. It now returns three results you can tell apart: up to date, stale with a warning, and stale with a failure. *Why it matters:* a probe you run precisely because you want an authoritative answer now gives the same answer in both places it speaks.
- **A health count that changed every time you ran it is now steady.** The measurement of how many fragile references the documentation carries was losing 11 to 15 files' opt-out markers on every run to a timing bug, then counting those files' references anyway. An independent census puts the marker-carrying population at 164 and 26 files; the reported totals have fallen from 477 to 93 and from 45 to 9, and now come back identical run after run. *Why it matters:* the number is something you can act on and compare against last week's, instead of noise that moved on its own.
- **A pointer check now reads what it points at.** The check that validates each design-principle entry's pointer into the charter only confirmed that the target line existed and was not blank, so a pointer that had slipped onto the wrong line passed silently — which is exactly what happens to every pointer below an entry whenever a new value is inserted above it. It now confirms the target line actually names the entry it belongs to. *Why it matters:* a citation that quietly stopped pointing at the right thing is caught instead of being read as correct.
- **A rule written down in the platform's documentation must now name what runs it.** The requirement to name an enforcer covered rules written as code and rules written into automation steps, but not rules stated only in prose — so a rule could be written, read as binding, and be executed by nothing at all. Prose-stated rules are now covered by the same requirement, and naming an enforcer that does not actually carry the rule no longer counts as naming one. *Why it matters:* a rule you read in the platform's own documentation is now backed by something that runs it, rather than possibly being a description of an intention.

## Known limits

- **Two of the checks changed here report without stopping anything.** The pointer check and the reference count are logged but not blocking. The pointer check has no automation step to be promoted into, so it is recorded as waiting on one rather than as still under trial — a distinction that matters, because "waiting on a precondition" and "gathering evidence" have different exits.
- **The new pair register found real divergence on its first run, and that divergence is unresolved.** Two tracker sections declared as shared between the two copies genuinely differ in content. The check is reporting correctly; deciding whether to reconcile the content or reclassify those sections is separate work.
- **Three more instances of the same timing bug are still in the tree.** They use a different command form, which the guard this release added deliberately does not match. Tracked at [#4319](https://github.com/cody-hutson/pmo-platform/issues/4319).
- **The delivery-time figure for this release is still unavailable.** Nothing in the deploy path records the event the measurement needs, so the field reads "not applicable" even though this release ran a real deploy to two locations. Tracked at [#4215](https://github.com/cody-hutson/pmo-platform/issues/4215).
- **This release's own plan file carries a broken title.** A placeholder for the version number was replaced with literal explanatory prose instead of a number, so the plan's title reads as a fragment and its filename carries no version at all.
- **One of the six changes cannot be verified from this release's code.** It corrects a measurement instrument that lives outside the tracked project, so it contributes nothing a reviewer or an automated check can inspect, and it is accepted on the operator's word.
- Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:pipeline` label.

## Reversibility

CHEAP / HIGH confidence. Reverting the single integration commit reverses all six changes at once — the probe returns to its old exit behaviour, the two counters and the pointer check return to their previous predicates, and the pair register and its packaging entry disappear together. Nothing was migrated and no stored data was transformed. One thing a revert does not undo on its own: the installed copy of the tracker assistant, which needs the deploy step run again to return to its previous state. Standard 7-day rollback window.

### Operator and engineering detail

**The convention was extended rather than duplicated, and it was then made to obey itself.** `#4208` was filed asking for a new convention requiring every declared fail-closed check to name a runner. It shipped instead as a widening of `gate-efficacy-standard.md` Requirement (b) — a third governed class, *prose-declared normative predicates*, alongside the two syntaxes already realized — because a parallel convention would have produced a second `enforcement-surface:` declaration schema, which the release's own verification command V6 asserts does not exist (exactly one file defines it). Stage 8 QA then found two Major defects of precisely the shape the milestone exists to eliminate, and the operator returned a **NO-GO** at Stage 9 until both were fixed: the class-3 trigger keyed on *"no code implements it"*, so a predicate whose implementing code existed but was invoked by nothing routed to class 2 and escaped the named-runner obligation entirely; and all three register rows this release added named a runner whose encoded check set carried none of the three predicates — "resolvable" had been read as *the runner exists* rather than *the runner carries the predicate*. Both are closed, and the second is why the standard now points at a specific design-review check rather than at a section that never mentioned it.

**The complementary-pair registry is the release's one new machine-read shape, and its fifth field is load-bearing.** `#4178`'s two copies of `tracker-schemas.md` are complementary by design, not duplicates — the canonical copy owns Trackers 5 to 10, the skill-local copy owns the tracker-integrity rules, and neither is a subset of the other — so registering them for byte-identity would have asserted the opposite of the truth, and would have made the pair *more* invisible rather than less, because the drift check exempts a registered basename outright. A dedicated registry was added instead. A two-field exclusive-ownership schema was designed first and rejected at adversarial review: Trackers 1 to 4 are defined by *both* copies and two of them had *already* diverged, so a partition schema had no expressible answer for that region and listing them either way would have flipped a currently-correct pair to FAIL. Operator decision **D-4** widened the record to a third `shared` field. That field is what surfaced the two live divergences named under Known limits above — the pair's only real drift surface, previously unrepresentable.

The registry's one live record, showing all five fields (the separator is `|||` because the section names legitimately contain `: `):

```
core/schemas/tracker-schemas.md|||operations/skills/tracker-manager/references/tracker-schemas.md|||Tracker 5: RAID Log|Tracker 6: Artifact Register|Tracker 7: Milestone Tracker|Tracker 8: Stakeholder Register|Tracker 9: RACI|Tracker 10: Sprint Tracker|||Tracker Integrity Rules|||Tracker 1: Daily Status Log|Tracker 2: Communications Tracker|Tracker 3: Open Meetings Tracker|Tracker 4: Transcript Register
```

`ADR-104` records both halves as one decision — the registration mechanism, and operator decision **D-2′** to ship the canonical copy into the package at its repo-relative path rather than vendor sections at build time. Option A was bound to `TEMPLATE_SYNC_MAP` under **D-3** rather than hand-coded into the packager, because the two builders that stage a skill are kept aligned only by a prose comment; a one-sided injection would have made the package permanently stale by construction and unfixable by rebuilding. Implementation then found the risk was worse than framed: the template-sync resolver did not resolve *ambiguously* between the two paths, it resolved to **neither** — a basename `case` with no matching arm fell through to a default producing a third path that does not exist. Unfixed, the map entry alone would have failed the build on every run.

**The freshness contract needed atomicity nobody had recorded.** `#4183`'s three-way mapping is `FRESH → 0`, `STALE` with the sentinel not set to enforce `→ 2`, `STALE` under enforce `→ 1`, and any unexpected verdict `→ 1`, fail-closed. The `deploy.sh` mapping and the workflow's gate decision had to land in a *single* commit: the workflow read `if exit code is 0 then green else fail`, so introducing the advisory `2` in one commit and the workflow's handling in another would have turned the non-blocking gate red in between.

**One of this release's own premises was inverted by measurement.** `#3833` was filed as a nondeterminism bug, and the Class V counter looked stable at 45 across every sample, so it was assumed unaffected and out of scope. It was over-reporting **five-fold on every single run** — 45 against a true 9 — because its three dropped files all exceed 71 KB and lost their marker *deterministically*, not racily. Scoping the fix to the visibly-flaky probe would have left a permanently-wrong number that never twitches, which is strictly harder to notice than one that does. Both probes took the fix. Measured on the merged branch: Class L 477 → 93, Class V 45 → 9, across 220 in-scope files, with the marker-carrying census at 164 and 26 re-derived independently through a third mechanism.

**One change is accepted on attestation and produces no diff.** `#4169` corrects the judge instrument that grades an epic's sunset criteria — its confidence enum did not match the canonical three-value set, and it scored turn shapes the shipped rules deliberately exempt, so a working fix would have graded roughly 4.5 points below its own target and read as failure. The instrument lives in the git-ignored operator analysis workspace, so it contributes no diff to the release PR, no reviewer can inspect it, and no automated check can assert any of its criteria. The silence from the freshness and drift checks is correct here and is *not* evidence of completion; its load-bearing criterion is verified downstream by the re-run it gates.

**Residues recorded rather than quietly patched.** This release lost two version slots to concurrent siblings while in flight — `v4.02` and `v4.03` are each now the live canonical tag of the sibling that won it — and `v4.04` was recomputed from scratch at the merge, not inherited from the dry run. Three artefacts still carry a superseded label: one historical commit subject, the release PR body's own heading, and the `ADR-104` frontmatter status line. A fourth is a genuine inconsistency worth naming — `ADR-104`'s frontmatter reads `Accepted` while its own Status section still reads `Proposed`, and the file itself declares the frontmatter field authoritative. None was rewritten at close-out: correcting a public artefact after the fact hides the residue rather than recording it, and the fixes belong in intake under the normal governance path.
