# A partial install now fails loudly instead of reporting success

2026-08-12 · v4.23

Three install tools were reporting a healthier workspace than they had actually produced — an update could leave a security control installed without its escape hatch and still exit clean, and the validator that would have caught it was skipping the check it needed to run. This release makes each of them report what is actually on disk.

## What changed for everyone using the platform

- **The update command stops reporting success over a half-configured workspace.** It now refuses to install a security control whose exemption list is missing, names the surface that is absent, and exits with a dedicated code instead of `0`. *Why it matters:* an update that quietly finished half its job used to look identical to one that finished all of it, so the gap only surfaced later as unexplained behavior.

- **Hook entrypoints are checked for the permission they need to run, and repaired when they are missing it.** A hook deployed without its executable bit is now detected and restored, and a run that repairs one says so rather than reporting that nothing changed. *Why it matters:* a control that is present but cannot execute is indistinguishable from a working one until the moment it is needed.

- **The deploy script ships executable again, so the command the documentation tells you to run actually runs.** *Why it matters:* the validator step that invokes it had been returning instantly and passing — it was reporting a verdict it never earned, which is worse than reporting a failure.

- **The install validator stops failing a healthy install over personal skills you wrote yourself.** Skills authored by the operator are no longer graded against the platform roster, and the check still catches a platform skill genuinely missing its version field. *Why it matters:* a single false failure was suppressing that whole validation mode, so real findings never appeared.

- **A fresh install now lands the ambient-intake drop-zone, the automation dial, and the autonomy-mode file.** They were previously created by nothing, so a new workspace started without them. *Why it matters:* the autonomy ceiling now defaults to logging rather than blocking on a new install, matching what the documentation has always promised.

## Known limits

- **Ambient intake ships ready but inert.** The install lays down the drop-zone, the directories and the dial; it does not register the sweep that would make the platform act on them unprompted. Registration is an operator step, documented in the install guide. The installer structurally cannot reach that surface, so shipping it dormant-and-discoverable was chosen deliberately over building new auto-registration machinery.
- **The post-update validator run now genuinely takes several minutes.** The deploy check it invokes previously cost nothing because it was doing nothing; it now performs about seven minutes of real work. This is the fix working, not a regression.
- **The exemption-list completeness check covers hook-tier surfaces only.** One instance-tier exemption list is still not covered, and it is tracked separately.

Report issues on the platform's GitHub issue tracker.

## Reversibility

CHEAP / HIGH. Reverting the release merge restores all seventeen source files, including the permission change, which travels with the tree entry. No data migration, no deployment to reverse, no operator data touched. The only residue is a set of empty directories on any workspace that ran the new installer before the revert; they hold nothing and removing them is optional.

### Operator and engineering detail

**Install-time configuration gained one operator-settable key and one new mode file.** The generator now emits an `[automation]` table into `operator.toml` carrying `automation_level`, the dial that governs how far ambient intake may act without being asked. It is emitted through the same operator-value-or-default helper as the three pre-existing settable fields, so re-running setup over a workspace where the value was deliberately set to `off` keeps that choice rather than resetting it — and, because the key is also registered in the generator's duplicate-suppression set, a second bootstrap emits it once rather than twice. The install additionally writes `.autonomy-mode`, a one-line mode file the autonomy-ceiling hook reads; absent that file the hook was defaulting to enforce on a fresh install, above the documented level.

The shape of the seeded config block, as an install writes it:

```toml
[automation]
# How far ambient intake may act unprompted: off | recommend | bounded_auto
automation_level = "recommend"
```

**The completeness gate is a sibling gate, not an extension, and that was argued rather than assumed.** The list-less check must run *before* the hook refresh, because its job is to prevent it; the executability check can only be judged *after*, because the refresh is what sets the bit. They share one exit code because they are one operator-facing condition — a deployed control present but not operable — named by one sentence of one acceptance criterion, with one remedy. Detection alone would have produced a permanently-red gate whose named remedy could not work, so the repair landed in the installer's content-match branch, the one path that previously copied nothing and therefore set no permission.

**Two premises stated in the tickets were rejected before any code was written, and both rejections were ratified at the scope-lock gate.** Files flagged as "hooks that can never run" are not hooks — they are libraries other hooks read under a readability guard, and they are correct without an executable bit; the real defect was one validator disagreeing with its sibling, which already implemented and documented that invariant. And the capability that "never activates on install" ships scaffolded rather than auto-registered, because the installer cannot reach the registration surface at all and the alternative was net-new machinery the extend-before-create rule gates.

**Two anti-vacuity findings are worth recording, because they are about this release's own tests.** A regression arm phrased *"the check fails when this directory is absent"* was satisfied by *any* failure of that check, and the sandbox was failing it unconditionally for an unrelated fixture reason — an assertion never shown capable of failing, inside a suite written to enforce exactly that discipline. It was caught by mutation and fixed with a baseline arm, so the two arms now differ in one variable. Separately, a pipeline idiom whose reader stops at its first match was inverting the exit status of five checks under `pipefail`, one of them an absence assertion that would have reported PASS while the forbidden pattern sat in its own output. Both were found by controls rather than by review, which is the generalizable part.
