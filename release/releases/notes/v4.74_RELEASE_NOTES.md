# Pipeline telemetry reads the right rows, or says why it has no value

2026-10-09 · v4.74

Cycle time, plan survival, the close-quality indicators and the action-item check now pick their rows by full identity, so each shows a correct value or an N/A that names its own reason. The Stage 9 verdict that starts the cycle-time clock is recorded at the stage that renders it, and the event writer now refuses that verdict type anywhere else.

> **Skip the rest** unless you run releases through the pipeline, write pipeline event rows by hand or from a script, or read the cycle-time, plan-survival or close-quality figures in release records.

## Who this affects

- Anyone who runs a release through the pipeline: the Stage 9 verdict step, and the event rows the release hub writes
- Anyone who writes pipeline event rows by hand or from a script
- Anyone who reads Cycle-Time, plan-survival or close-quality figures in release records, or compares them across releases
- Anyone who runs a Stage 13 close or the event-record integrity check

## What you need to do

1. **Run the update from your main checkout** (`./update.sh`). The event writer's new refusals apply as soon as this release's code is in your checkout; the release hub's matching Stage 9 step and its verdict guidance arrive with the updated skill.
2. **Only if a release of yours is in flight:** write a Stage 7 or Stage 8 verdict under that stage's own verdict type, a plan approval or a Collective Review outcome as a scope lock, and a change after the lock as a scope change. The writer refuses the Stage 9 verdict type at any other stage or from any other author, and its message names the type to use instead.
3. **Only if you write event rows by hand or from a script:** give a Stage 4 gate row for a single card exactly one `card-disposition:carried` or `card-disposition:removed` segment, and key a Stage 4 delegation row on the milestone. Rows already in the log are not rewritten and are still read.
4. **Only if you close a release by hand instead of with the close-out tool:** include the close-quality field in the release's Deployment Log block. Its presence is now checked on every verified release from v4.55 on.

## What changed for everyone using the platform

- **Cycle time starts at the operator's Stage 9 GO and ends at a deploy that finished.** The figure now starts at the earliest GO the operator recorded at Stage 9 and ends at the last skill or harness deploy that completed. A GO-typed row written at another stage, or by the hub, no longer starts the clock. *Why it matters:* four earlier releases whose figures were inflated, one of them by almost a hundred times, now recompute to their real values, and the event writer refuses the row that inflated them when a new release tries to write it.

- **A cycle time that reads N/A says why.** When nothing can anchor the figure, the reason names each kind of deploy row the release does have and why it does not count, and the close-out carries that reason word for word into its report and its pull request. A package-only deploy that succeeded is no longer reported as a deploy that did not succeed. *Why it matters:* you can tell a release that deployed nothing measurable from one whose deploy failed, without opening the event log.

- **The Stage 9 verdict is recorded where it is rendered.** Stage 9 now writes the operator's GO or NO-GO as one step with the decision record and reads the row back, and the event writer refuses that verdict type at any other stage or from any other author. *Why it matters:* the row that starts the cycle-time clock exists when the decision is made, and a missing one is recorded as missing instead of being filled in later with the wrong time.

- **Close-quality indicators tell "not measured" from "nothing there".** Three indicators — retro conformance, lessons population and rollup presence — now read NOT-EVALUATED when the tool was never pointed at the retro register, and N/A only when a register was looked for and not found. With the register supplied they compute. *Why it matters:* a close that skipped the measurement no longer looks the same as a close that had nothing to measure.

- **The close-quality field is checked on every verified release.** The check that each verified release carries its close-quality field shipped switched off. It is now on from v4.55 forward, reports how many releases it read, and warns when its own settings are in the wrong order instead of over-counting. A finding is logged but not blocking. *Why it matters:* a close that drops the field is now reported, where before the check read nothing and passed.

- **Plan survival counts plans, not delegations.** The plan-survival figure now counts only cards whose Stage 4 gate recorded a decision for that card, and leaves out a card the plan removed. The two scope-lock figures count only a lock recorded at the plan approval or the Collective Review. *Why it matters:* the figures stop rising for bookkeeping rows that were never a plan surviving contact with engineering.

- **Action items are matched by release as well as by number.** The event-record integrity check now pairs each action item with the event rows of its own release, so the first action item of one release can no longer be answered by the first of another. *Why it matters:* stale action items that a shared number used to hide are now reported, so older releases' ledgers show more findings than before; none of them is a regression.

## Known limits

- Release records are not rewritten. The Cycle-Time fields that four earlier releases carry keep the inflated values they recorded; the corrected values come from recomputing.
- A cycle time can still end on a hand-written row. A release-level completion note typed as a skill deploy still anchors the deploy end, and a release whose only deploy ran through the hook refresh writes no deploy row, so it reads N/A.
- A cycle time that rests on rows the query tool reports as release-indeterminate is still published. The notice is repeated on the tool's error stream and nowhere else.
- The carry-forward closure indicator still renders a failed read as a genuine zero, and the close-quality field still reads the decision roll-up as present from its heading alone ([#8012](https://github.com/cody-hutson/pmo-platform/issues/8012)). The roll-up itself has no writer yet ([#8292](https://github.com/cody-hutson/pmo-platform/issues/8292)).
- Plan survival over older releases is a partial reading: rows written before this release carry no per-card decision, and the scope-lock figures identify a lock row without reading its verdict. The event writer still accepts a zero-padded milestone number in a Stage 4 delegation row ([#8291](https://github.com/cody-hutson/pmo-platform/issues/8291)).
- The integrity check's stricter match reports stale action items across earlier releases' ledgers. Draining them is tracked in [#6205](https://github.com/cody-hutson/pmo-platform/issues/6205), and its release-prefixed findings are reported, not blocking, until [#6872](https://github.com/cody-hutson/pmo-platform/issues/6872).
- Stage 7 and Stage 8 verdict rows have named types, but no hub or stage brief yet carries the step that writes them ([#7730](https://github.com/cody-hutson/pmo-platform/issues/7730)). Two instruction texts outside this release still tell a reader to supply a missing Stage 9 row; the four inside it now say to record the absence.
- The close-out's own tests do not yet cover a notice printed ahead of the N/A reason ([#8290](https://github.com/cody-hutson/pmo-platform/issues/8290)), and its shared one-line projection leaves parentheses in place ([#8296](https://github.com/cody-hutson/pmo-platform/issues/8296)).
- The version this workspace reports changes to v4.74 on the first update after this release closes.

Report issues at https://github.com/cody-hutson/pmo-platform/issues, and report a suspected vulnerability privately as the [Security Policy](https://github.com/cody-hutson/pmo-platform/blob/main/SECURITY.md) describes.

## Reversibility

MODERATE / HIGH. Reverting the single release merge restores the earlier tools and stage texts, and the release hub skill is then re-deployed from the reverted tree. The revert stops on one file, the release plan that the version claim renamed, and that one is resolved by hand ([#7887](https://github.com/cody-hutson/pmo-platform/issues/7887)). Event rows written under the new rules stay in the append-only log, findings the close-quality check raised meanwhile stay as records, and the version tag is kept as the record that the version was claimed.

### Operator and engineering detail

**The cycle-time anchors.** `compute-cycle-time.sh` selects T_GO on the full row identity — `gate-outcome` / `plan-review-go` at stage 9 with actor `operator` — and takes the earliest such row. A release whose GO-typed rows all miss that identity reads N/A under its own reason, naming the count and the identity it looked for, with no fallback to the subtype. T_DEPLOY anchors only on a resolved `deploy-skill` or `deploy-harness` row; `deploy-package`, `deploy-rules-mirror` and `deploy-helper` rows are named in the N/A reason with their producer tally and never anchor. An event log the tool cannot read is none of the N/A causes: the tool exits 1. Each read also repeats the query tool's release-indeterminate notice on its own error stream, and the selection, the value and the exit status do not depend on it.

**The Stage 9 verdict binding.** `stage-09-plan-review.md` Phase C1 makes the decision record and the verdict's event row one action, with a typed read-back, and the release hub's playbook points its Stage 9 step there. The event writer's `validate_row_identity` refuses `plan-review-go` and `plan-review-no-go` at any other stage or actor, and its message names the destination for each refused case: the Stage 7 and Stage 8 verdict subtypes, `decision` / `scope-lock`, `decision` / `d-class`, or the sub-task comment alone for a completion note. Check 61's remedy text now says, at all four sites this release edits, that a missing GO row is recorded as absent and never backfilled, because a row written later would anchor the cycle time on the close.

**The close-out's carriage.** Phase 3 of `automated-closeout.sh` keeps the cycle-time tool's own reason line and carries it into the report, the JSON report and the chore pull request body. Its state is one of four that never share a member: a value, `N/A (<reason>)`, `N/A — DEGRADED`, or `NOT-EVALUATED`. A read-only verdict compares the Stage 12 Deployment Log field with the tool's value — `CONFORMANT`, `DIVERGENT`, `ABSENT` or `NOT-EVALUATED` — and never rewrites the field. The tool's remaining error stream reaches the report through the shared one-line projection, with the repository and home roots replaced before the 800-character cap.

**Close-class telemetry.** `compute-close-class-telemetry.sh` separates a caller that supplied no register path from a supplied path that holds no register; the standard is at v1.03 and gains a data-flow section for the three register-fed slots. The first slot's three renderings, as the tool emits them:

```text
retro-conformance 10/10 (1.00)
retro-conformance N/A — no retro register found for v4.74
retro-conformance NOT-EVALUATED — no --retro path was supplied, so no retro register was looked for — this is not a clean result
```

Sub-check (l) of `deploy.sh` Check 48 is armed at the release-log row `v4.55`. Its armed line carries its denominator, a re-dormant line says so, and a telemetry cutoff that arms ahead of the outputs cutoff now draws a warning and a withheld count instead of a count of rows nobody read. At this close it read 20 verified rows with no finding of its own.

**Row identity in the front cluster and the integrity join.** `compute-front-cluster-telemetry.sh` computes plan survival over cards that carry a per-card Stage 4 gate row, treats a `card-disposition:removed` card as dropped, and binds the two scope-lock indicators to the lock's own identity. The writer gates the Stage 4 delegation subject, the per-card disposition segment and the scope-lock identity, and the hub's emission contract gains a conditional `plan-card-disposition` row. `check-event-record-integrity.sh` joins action items on the pair of release and id in every limb, reports its limb-(c) findings on their own line, and grades rows that predate the cutover by a stated legacy rule.

**How it shipped.** Seven cards landed on one branch as one merge at `ff3eecdf`, claimed as `v4.74` with a signed annotated tag on the first attempt; the `release-hub` skill was deployed after the merge and verified by content in both install targets. Four sibling releases merged while this one was in review, so the branch synced with the main branch three times. The third sync merged clean as text and still failed a sibling's static check on the merged tree, which a fix in this release resolved; a merge with a sibling therefore needs the close-out self-test run on the merged tree, not only a clean text merge ([#8295](https://github.com/cody-hutson/pmo-platform/issues/8295)). The release adds no decision record.
