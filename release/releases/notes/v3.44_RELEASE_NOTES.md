# Backlog triage now runs as one command instead of issue-by-issue by hand

2026-07-01 · v3.44

Sorting the improvement backlog — checking each proposed issue for readiness, duplicates, dependencies, feasibility, and priority before deciding what to build — used to be a fully manual pass over the board, one issue at a time. This release turns that whole Stage-2 pass into a single skill you invoke by name. It reads every proposed issue, runs the full readiness analysis across all of them, and hands back one consolidated triage summary with an Approve / Defer / Reject recommendation per issue. You still make every decision — the skill does the legwork and stops for your call, it does not decide for you.

## What changed for everyone using the platform

- **Triage runs in one pass.** Invoking the new `pipeline-triage` skill reads the whole proposed queue and runs the readiness analysis — definition-of-ready completeness, duplicate and subsumption detection, dependency-state validation, feasibility, priority re-evaluation, and oversize routing — across every issue at once, then returns a single summary. *Why it matters:* what took an issue-by-issue crawl over the board is now one command with one report to read.
- **You render one verdict per issue, not one approval per step.** The analysis runs end-to-end without pausing for approval at each enrichment step; the only thing that stops for you is the actual decision. *Why it matters:* the click-through of confirming every intermediate step is gone — your attention goes to the Approve / Defer / Reject call on each issue, which stays yours.
- **The state-changing step still asks first.** The one action that mutates state — closing or rejecting an issue — still requires your explicit confirmation before it runs. *Why it matters:* the time-saving automation covers the analysis, never a decision that closes an issue out from under you.

## Who this affects

This is for whoever runs release triage on the platform's own improvement backlog — the queue of proposed platform-improvement issues. It reads that backlog, not a project's delivery backlog (the Jira / project board), so nothing about day-to-day project work changes.

## Known limits

- The skill triages the platform's improvement backlog (proposed platform issues); it does not triage a project's delivery backlog.
- The Approve / Defer / Reject recommendation is exactly that — a recommendation. The verdict is always the operator's, and the close/reject step confirms with you before acting.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**CHEAP / HIGH confidence.** The release adds one new skill plus its registration and documentation edits; rolling it back is reverting the single release pull request and rebuilding the skill set. It changes no existing behavior and touches no stored data, so there is nothing to migrate back.
