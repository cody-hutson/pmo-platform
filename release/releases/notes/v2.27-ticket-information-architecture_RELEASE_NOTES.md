# v2.27 — ticket information architecture

How a ticket carries confidence, how its title reads, and how its information is structured all get sharper in this release. One staleness scale replaces five, work-item titles become readable from the issue list alone, and the backlog view gains a pipeline-stage column.

## What changed for everyone using the platform

- **One staleness scale instead of five.** When the platform tells you a ticket, status, or reference looks stale, it now speaks one four-level vocabulary — current, cosmetic drift, currency-in-question, or structural rot — instead of five different formats across different checks. *Why it matters:* you learn one way to read "how stale, and how deeply" and it means the same thing everywhere it appears.
- **"Old" no longer reads as "broken".** Staleness now separates *how long* something has gone untouched from *what kind* of staleness it is. A 90-day-old ticket whose plan still holds is flagged differently from one whose premise is gone — age alone never gets labelled as structural rot. *Why it matters:* you can trust the top staleness band to mean a real premise-level problem, not just elapsed time.
- **Work-item titles you can read from the list.** New issues drop the `[Category]:` / `[Bug]:` prefix from the title — the type now lives on the label, and the title spends its whole space on what actually changed. A new floor check keeps titles from being a bare slug or a single word. *Why it matters:* you can tell what an issue is about from the issue list without clicking in, and the type is still one glance away on the label.
- **Legacy issues are left alone.** The title check is logged-but-not-blocking for issues that already exist with the old prefix — nothing fails and no bulk rename is forced on you. *Why it matters:* the new style applies going forward without disrupting the issues you already have.
- **A documented model for how tickets carry information.** Tickets now have a written information model: the body is the source of truth, comments and sub-issues are the per-stage review trail, and Projects fields, labels, and Milestones are the machine-readable pipeline position. The backlog triage view gains a Stage column so bundled work no longer collapses into one undifferentiated group. *Why it matters:* you can see at a glance whether a bundled issue is at Bundle, Planning, or Solutioning instead of guessing from the coarse status alone.

## Known limits

- The title floor checks the shape of a title (no bracket prefix, names an object and a change) — it cannot judge whether a well-formed title is actually informative. A vague-but-well-formed title still passes; the quality bar is author and intake judgment, not an automated score.
- Re-titling the existing backlog to the new style is a separate, deliberately-authorized task — it is not part of this release.
- Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `cluster: data-architecture` label.

## Reversibility

CHEAP / HIGH confidence. `git revert -m 1` of the integration PR reverses the whole release. Every change is additive — a new standard, a new spec, a repurposed (not renumbered) gate criterion, a logged-but-not-blocking gate, and read-only skill edits; no data migration and nothing breaking. Standard rollback window.

### Operator and engineering detail

**Staleness-confidence standard (#436)** — `core/specs/staleness-confidence-standard.md` is the single canonical home for a four-band ordinal **depth** scale (`S0-NONE` < `S1-SUPERFICIAL` < `S2-SUBSTANTIVE` < `S3-STRUCTURAL`). It governs the confidence-representation axis only — bounded away from detection triggers (each mechanism's own spec) and response posture (`reconcile-dont-annotate.md`). The six current ticket-facing mechanisms (binary AC-Drift, the 3-tier context-drift severity, the 3-class mid-pipeline drift verdict, the PT-1..PT-4 premise-rejection taxonomy, the one weighted time-decay score, and age-threshold backlog-aging) each map their states onto the bands; the one mechanism with a continuous score carries a documented `score→band` projection that reaches `S3` only via a contradiction finding, never via a high time-decay value alone. Founding ADR-043 (slim-kernel) records the ordinal-depth-over-time-decay decision — explicitly a reversal of the originating issue's stated lean — with the ADR number re-verified next-free (041/042 were taken by the concurrent v2.25 release). `delivery-engine`'s backlog-scan Aging output now reports on the scale.

**Human-informative titles + G1-01 floor (#545)** — the three work-item templates carry a prefix-less `title: ""`. `core/schemas/gate-criteria-spec.md` repurposes G1-01 in place from a prefix-requirement to a title-informativeness floor (no `[...]:` prefix + a substance floor), holding the ID and every column value so the Gate 1→2 `structural_pass_rate` denominator is unchanged; schema bumps v1.15→v1.16 (criterion-shape change, no renumber), and the former G1-01-Bug / G1-01-Obs adapters retire with no per-template prefix literal left to translate. `deploy.sh` Check 22 enforces the syntactic floor warn-tier — legacy prefixed issues are reported as a non-blocking warning and never fail `--check`. The semantic informativeness bar (lead with the change, name object + action, disambiguate from neighbours, spend the bought-back space on specificity) lives in `release/references/how-to/intake-style-guide.md` §7 as judgment; `intake-desk` elicits to it and runs a title-informativeness check before the confirm. No LLM grading is added.

**Ticket information model + Status/Stage invariant (#211)** — `release/references/specs/ticket-information-architecture.md` defines the Three-Layer Model (Source of Truth = issue body; Stage Reviews = append-only comments or sub-issues; State Anchors = Projects fields / labels / Milestones), the information model that ticket lifecycle, system configuration, field lifecycle, and I/O contracts implement against, recorded as a slim `## Design rationale` rather than a standalone ADR. `core/disciplines/github-projects-guide.md` adds the Stage column to the backlog triage view: Status is the coarse lifecycle axis and the `Bundled` status spans Stages 3–5, so Stage renders the fine pipeline position the coarse axis cannot.

For full implementation detail see the RELEASE_LOG.md Deployment Log v2.27 entry and the release plan at `release/releases/plans/22-ticket-information-architecture_RELEASE_PLAN.md`.
