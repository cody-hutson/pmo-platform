# The filesystem guard refuses paths it cannot know in advance

2026-11-10 · v5.07

The guard that limits where a session's file commands may read and write now refuses a path written with a shell feature that changes a value before it is used. The guard can't tell where such a path points until the shell has already run it, so it now refuses the path instead of letting it through. Ordinary file commands are unaffected.

> **Skip the rest** unless your sessions write file paths using shell variable expansions, or you review what the guards refuse and log.

## Who this affects

- Anyone whose sessions run file commands on a workspace that has taken this release's guard bundle
- Operators who read the filesystem guard's refusals and logged records, or who maintain the guards

## What changed for everyone using the platform

- **A path built by a value-changing shell feature is refused.** The shell can change a variable's value before using it, in ways that can even run other commands. A file path written that way is now refused, wherever it sits in the path, whether or not it is quoted. *Why it matters:* the guard no longer lets through a path it could not check.

- **A few similar-looking paths are refused on purpose.** Some ordinary uses of shell variables end the same way as that feature, such as a default value or a pattern replacement containing an `@`. Those are now refused too, and the guard's documentation lists each of them. *Why it matters:* when one of these is refused, you can find out why. Plain variables, and the common ways of listing several values, are not affected.

- **Two refusals that used to happen by accident are now deliberate.** Two other shell forms that can run commands were refused only because of how the guard happened to split them. Each now has a test that keeps it refused. *Why it matters:* a future change to the guard can no longer let them through without someone noticing.

## Known limits

- Some shell forms get their value from outside the command, from the environment or a file the shell reads. No guard that reads only the command can see that value, so these stay a stated limit with no owner.
- Four places in a command are still never checked by this guard. They are owned by [#8547](https://github.com/cody-hutson/pmo-platform/issues/8547).
- Four extra checks planned for this release could not be run, so the release relies on the guard's own tests for those cases. You accepted that at the release's final review.
- A workspace picks up this release when an update refreshes its guard bundle. The version this workspace reports changes to v5.07 on the first update after this release closes.

Report issues at https://github.com/cody-hutson/pmo-platform/issues, and report a suspected vulnerability privately as the [Security Policy](https://github.com/cody-hutson/pmo-platform/blob/main/SECURITY.md) describes.

## Reversibility

MODERATE / HIGH. Reverting the single release merge restores the guard as it was, and a workspace runs the restored guard only after an update refreshes its guard bundle; the version tag is kept as the record that the version was claimed. A revert reopens the gap this release closes.

### Operator and engineering detail

**The guard (#8322).** `core/hooks/block-fs-boundary.sh` gains a third limb at G2, `_carries_transform_op`: an operand carrying a `${` and, anywhere, the shape `@`, one character other than `]` or `}`, then `}` is refused under `BLOCK-FS-BOUNDARY-003`, as `$(` and a backtick already are. The test is two one-star globs, linear in the operand's length (`XFORM-COST-01`). The span split gains `_span_closed_inside_subscript` (predicate P-2): a `${…}` span whose text holds both a `[` and a nested `${` is refused like an unterminated one, which closes the class of operator uses broken inside a subscript, whose pieces the token walk would otherwise hand over in separate words (`XFORM-COST-02`). The rationale is path-undecidability, not an execution control, which stays with the script-execution allowlist.

**The suite and the fragment.** The XFORM block in `core/hooks/tests/block-fs-boundary.test.sh` grows by 103 arms, to 322, with 19 pairing copies: each refusal pin is held red through the copy that lacks exactly its mechanism. The over-refusal classes are pinned as decisions (`XFORM-OVER-01..11`), and must-not-flag controls stay green (`XFORM-NEAR-01..09`). The fragment `core/rules/bypass-mode-readiness/block-fs-boundary.md` now reads "Parameter-transformation operators are REFUSED at G2", states the value-re-evaluating brace forms as a declared limit without an owner, and pins the two brace forms refused by where the operand breaks (`XFORM-SPLIT-01/02`). The registry index is regenerated.
