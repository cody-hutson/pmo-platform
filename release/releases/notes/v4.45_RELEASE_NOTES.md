# Checks now report what they actually measured

2026-08-30 · v4.45

This release is named for graduating a group of checks from logging problems to stopping work on them, and it graduates none of them. That is the result, not a shortfall: both decisions that could have tightened a check were taken deliberately on measured evidence, and both came back as hold. What shipped instead is the machinery that makes such a decision answerable at all — checks that now actually run, a result that now carries its denominator, and a log that stops growing without throwing anything away.

> **Skip the rest** unless you open pull requests against this repository, run releases, or read the results of the platform's own checks.

## Who this affects

- Anyone who has read a green result from the release-plan verifier and taken it as evidence that something ran
- Anyone whose instance holds the platform's ever-growing deploy check log
- Anyone waiting on one of the ten checks that reported only "shakedown continues"

## What changed for everyone using the platform

- **A check that could report PASS without running anything now says SKIP.** One route through the release-plan verifier reported a pass for work it never executed, and it was matched ahead of the route that would have run it — every row in the whole indexed corpus that reached it was a runnable assertion sent down the wrong path. *Why it matters:* a green result from that tool now means something was executed, not that nothing objected.

- **A "0 errors" result now states how many rows it looked at.** Zero errors over a plan with no readable rows was byte-for-byte identical to zero errors over a plan whose rows all passed, so anything checking for zero was checking nothing. *Why it matters:* you can now tell "nothing failed" apart from "nothing was examined".

- **Verification rows stop vanishing from the count.** Two separate faults dropped them: an empty column collapsed the record and shifted every later field one place left, so the tool graded the wrong cell while the arithmetic stayed correct; and a table it could not read discarded 61 rows from both the numerator and the denominator. *Why it matters:* the tally is now taken over the rows that exist, not the ones the parser happened to recognise.

- **The two bundle-size and citation checks now run on pull requests.** Neither had a runner anywhere — no job executed either one — so no amount of evidence could ever have promoted them. *Why it matters:* a bundle problem is caught before a merge instead of after one.

- **The deploy check log stops growing forever, and nothing is discarded.** It had reached roughly 94 MB with no ceiling. It is now moved whole into a numbered segment once it passes a size budget, and every record is kept. *Why it matters:* the file stops consuming disk indefinitely without deleting the history that other checks read.

- **Ten checks that said only "shakedown continues" now name a condition you can check.** Five are recorded as permanently advisory because their subject is state outside the repository that no pull request can repair; five are recorded as blocked on a missing runner, not on missing evidence. *Why it matters:* you can tell whether a check is waiting for data or waiting for something that is never going to arrive.

- **No check started stopping your work.** Despite the release's name, zero gates changed from logging a finding to failing on it, and zero executable lines changed in the two decisions that considered it. *Why it matters:* nothing here can newly fail a pull request that passed yesterday.

## Known limits

- **The two flip decisions came back as hold, and one of them is deadline-armed rather than settled.** The live half of the `g1-enforcement` check is held on a single measured blocker — one detector was revised six days before the measurement, leaving two days of observation against a three-day floor. Its successor is tracked as #6417.
- **The bundle checks are only half enforceable.** The part that reads files in the repository now runs as a required check. The part whose subject is backlog state outside the repository is recorded as permanently advisory on architectural grounds, because a pull request author can neither see nor repair a failure caused by it.
- **One operator step is still outstanding and cannot be undone.** Two files left behind by the log rotation need to be adopted into the numbered segment set by hand. The step was rehearsed but not executed, and it is IRREVERSIBLE once run.
- **A recorded figure is known to be imprecise and was kept deliberately.** ADR-169 describes an instrumentation gap as "12 days"; the measured value is 11 days 19 hours 32 minutes, and it is one of eleven multi-day gaps rather than a singular one. The correction was offered during the release and declined.
- **Two measurement faults found during this release are recorded, not repaired.** Absolute claims were asserted from truncated reads of long lines (#6418), and 444 rows in the check-log family are not valid JSON (#6419).

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH confidence.** Almost everything here reverts with the merge: the verifier repairs, the register rows, the standard's new declaration rules, and the two workflow extensions are all committed files. The exception is the check log, which has already rotated on the instance — the hot file is now segment `00000`, and reverting the release does not move it back. No records were destroyed, and no external system was touched.

### Operator and engineering detail

**The evidence machinery, not the graduation.** The milestone's outcome statement was that the warn-mode gate cohort can terminate — every gate declaring a warn posture either has a readable advance signal or a recorded, grounded disposition. Both halves landed; the flips did not, and holding them was the correct call in both cases. #4751 records ten register rows partitioned along two independent axes, subject locus and drain behaviour, which turned out to partition the ten identically: five ids whose subject is live GitHub state are ratified permanently advisory (their verdict-input closure over repository paths is empty, so no pull request can repair them, and a network-dependent member would make a transient outage merge-blocking under the subset's fail-closed aggregate), and five in-tree ids are deferred as precondition-blocked rather than evidence-blocked — 0 of 22 workflow files reference any of them. Two defects on the card's own gates were fixed rather than recorded: one deferred its flip to a section of a file that does not exist, and one named a git-ignored file as its flip surface, reproducing this milestone's own signal problem inside its own declaration.

**The shakedown floor was being measured in the wrong unit.** #1686 is the finding that decides the release. Scored at check level, the `g1-enforcement` drain reads 45 days and clears trivially — but five of the seven criteria were revised *inside* that window and one inverted its predicate outright, so a pooled day count grades a moving detector rather than one gate's false-positive rate. Re-scored per emit site, counting only days since that site's own revision, 8 of 9 rendered limbs clear a three-day floor and one does not: a heuristic over free-form prose, revised 2026-08-24, with 14 rows across two emitting days. Arming it would have armed a prose heuristic on two days of unreviewed observation. ADR-120's ratification is written into the row as an explicit precondition, read from that file's own `status:` field rather than inferred — it still reads `Proposed`, 23 days after its code merged.

**Bounded by relocation, not by discard.** #5588 rejected all three lifecycle options the ticket offered, because each discards at its boundary and the arithmetic rules the whole class out: the worst contiguous 30-day window measures 78,642,875 bytes against a 90-day drain horizon, so any ceiling low enough to solve the growth problem sits one to two orders of magnitude below what the sibling drain needs. Both writer variables now assign from a single bounded choke point, so all twelve append sites are untouched and the blast radius is two changed lines behind one new block. A single read surface is the family's only supported entry point — a consumer that opens the hot file directly returns a plausible wrong answer after the first rotation rather than an error. Records ADR-169.

**Two design calls were recorded rather than left to be re-litigated.** #6234's widening of the method-column match preserves containment: tightening to full-cell equality gains the same 59 rows but silently de-indexes 20 that work today, which would have shipped a fresh silent drop inside the fix for a silent drop. Its error discriminator keys on *names a verification-schema column*, not *matched any header keyword*, because the looser rule fires on a live table whose own prose says it carries no verdict — and would turn a correct, shipped, unchangeable plan red. Both are in ADR-168. #6383 additionally retired a prose-keyword route on two independent grounds and added the test arm that the earlier header fix shipped without.

**Process record.** The bundle carried 7 issues at 26 points against a declared bound of 25, taken deliberately at the point of choosing so the verifier surface would land as one unit rather than split across two releases, and recorded as a breach carried rather than a bound satisfied. Two of the seven were late additions taken after the scope lock, and neither had a verification-plan row — so the stage that re-executes from that plan had nothing to run for either, which is this release's own subject one layer up. Four operator override records were signed during the release; all four rest on the enforce flip being held, so none of them gates live enforcement.
