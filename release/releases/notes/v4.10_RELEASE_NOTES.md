# Skills with overlapping triggers now route cleanly, and stay that way

2026-08-05 · v4.10

Fourteen skills advertised trigger phrases that overlapped each other, so which one answered a given request was closer to a coin flip than a routing decision. This release separates them, stands up a check that measures the overlap on every deploy so it cannot quietly return, and corrects a set of places where a skill described itself in terms that were no longer true.

## What you need to do

1. **Run your normal deploy step.** Twenty-one packaged assistants were rebuilt in this release. An existing install keeps its previous copies until it is redeployed, so until you do, your workspace routes on the old overlapping trigger phrases.

Nothing is migrated, no settings change, and nothing you have written needs editing.

## What changed for everyone using the platform

- **Skill routing is separated by what a skill is for.** Fourteen trigger descriptions were rewritten so that skills which perform a function describe the mechanic they perform, and skills which own an area describe what they own. *Why it matters:* two skills advertising the same phrase meant the one you got was not the one you asked for, and there was no way to tell from the outside which had answered.
- **Something now watches for the overlap coming back.** Every deploy check measures trigger collision across the whole skill suite and reports what it found. Findings are logged rather than blocking, so nothing stops working while the measurement settles. *Why it matters:* separating the descriptions once only helps until the next edit drifts two of them back together, and nothing was watching for that before.
- **References between skills stop going stale silently.** Where one skill pointed into another by line number, it now names the section instead, and a second check reports line-numbered pointers if they come back. *Why it matters:* a line number breaks the moment anyone inserts a paragraph above it, with no error and no signal — one such pointer was already aimed at the wrong content when this release began.
- **New capability work has to show the capability actually works.** A work item that adds a capability now owes at least one acceptance criterion describing something observable the capability does after it is installed, exercised against a named realistic example, on top of the criteria that check the pieces are present. *Why it matters:* a capability could previously satisfy every criterion and every automated check while shipping unreachable — all the parts in place, no path that reaches them.
- **Skills stop asserting things about themselves that were not true.** A quality checklist that named six review gates where eleven ship, four shared reference files claiming they are read by assistants that do not read them, and a project record omitting one of its own children are all corrected. *Why it matters:* a wrong self-description is more expensive than a missing one, because it reads as authoritative and gets acted on.
- **Holding one deploy check to a different strictness now works.** The setting that switches an individual check between strict and lenient had no effect whenever the overall setting disagreed with it. It now takes effect in both directions. *Why it matters:* the setting was documented and appeared to work, so anyone who used it to hold a single check back during a rollout was relying on something that did nothing.

## Known limits

- **The two new checks report rather than block, so a clean result from them is not yet proof of anything.** Both were deliberately started in reporting mode. Until a decision is recorded to make either one strict, their green result means "nothing was reported", not "nothing is wrong". Tracked as [#4751](https://github.com/cody-hutson/pmo-platform/issues/4751).
- **The stale-reference check sees a narrower set of references than the problem it was built for.** It recognises pointers into a skill's main file, and not pointers that name any other file alongside a line number. Every one of the 49 stale pointers cleared during this release was of the second kind and was therefore invisible to it. Tracked as [#4750](https://github.com/cody-hutson/pmo-platform/issues/4750).
- **Thirteen skills whose routing changed still record an older release as the one they were last checked against.** The marker each skill carries is meant to say which release its contracts were validated under; for these thirteen it was not advanced when their trigger phrases were rewritten. Tracked as [#4752](https://github.com/cody-hutson/pmo-platform/issues/4752).
- **One deploy check answers to two different setting names.** Its strictness responds to one name and one of its error paths responds to another, so setting the name its own guidance message tells you to set covers only part of it. Tracked as [#4753](https://github.com/cody-hutson/pmo-platform/issues/4753).
- **One reporting threshold is borrowed from a different measurement.** A delivery metric takes its bands from an unrelated metric because none were ever written for it. The borrowing is now stated in place rather than hidden, but whether the bands fit is still an open question. Tracked as [#4754](https://github.com/cody-hutson/pmo-platform/issues/4754).
- Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:skill-suite` label.

## Reversibility

MODERATE / HIGH confidence. One branch, one integration commit, and the merge has two parents, so reverting it restores every file's bytes in a single step. Two things need attention afterward. The trigger rewrites revert *to* the known-overlapping state rather than to a neutral one, so a revert reintroduces the routing ambiguity it removed and the new check will immediately report it. And one member's change was made directly in the project record rather than in a file, so a revert does not reach it — its rollback is the captured copy of the text as it read beforehand. Standard 7-day window.

### Operator and engineering detail

**The gate that measures trigger collision was blind to a fifth of its own published denominator, and the fix was free.** Six of 55 skills parsed to an empty trigger-token set because their descriptions used a clause form that sat outside both arms of the extractor's fallback, so 309 of 1485 pairs could never return a non-zero score. This was proven with a discriminating control — the same phrase text written in the unrecognised form scored 0.000 and passed, written in the recognised form scored 1.000 and escalated. Adding one token to the existing alternation took blind skills from 6 to 2 and effective pairs from 1176 to 1378, with zero new escalations and zero new watch-band findings, so the acceptance criterion the gate had already satisfied was untouched by the fix. The gate also ships an exemption emitter that prints the suppressed set on every run, which is what keeps a composition-linked exemption falsifiable after ship rather than a permanent quiet suppression.

**The usability-AC requirement is a set-level rule, not a per-bullet one, and silence is not an exemption.** An item is capability-class when three limbs all hold — it names an actor, that actor has a runtime trigger, and the observable it produces is not the artifact that was edited. A capability-class item's acceptance criteria must carry at least one usability criterion in addition to its presence criteria, or must name one of five closed exempt classes; an item that carries neither is a finding, which is the part that makes the rule enforceable rather than aspirational. This is the required shape of that criterion, and the four mechanical tests it has to pass:

```
predicate: after a fresh install/deploy, <actor> <verb-phrase> against <named, populated fixture>,
           producing <stated observable>;
method:    <invocation + the observable that must be seen>

U1  post-install anchor present
U2  actor + action verb — not "exists" / "ships" / "contains"
U3  fixture is named and populated
U4  the observable is not the artifact that was edited
```

The requirement was deliberately landed as a refinement to an existing criterion rather than as a new criterion identifier, held at scope-lock after an adversarial review corrected the measured cost of the alternative.

**One schema registry's gate roster was not a stale count — it was a different gate set wearing the same identifiers.** The registry declared six quality gates for the quality auditor; the auditor ships eleven. Only one of the six sat on the same identifier as its shipped counterpart: the registry's second gate is the shipped fourth, its fourth is folded into the shipped fifth, one is no longer a gate at all, and one moved out of the roster into a mode. Editing the range literal from six to eleven would have produced a heading claiming eleven gates over six definitions describing a different set with colliding identifiers — a false authoritative statement in a registry that a regression protocol cites as the audited contract surface. The resolution was to make the registry cite the skill rather than copy it, because replicating eleven definitions rebuilds the identical duplicate-source defect one gate later. The blast radius was eleven live sites rather than the two the finding named, nine of them inside the registry itself, and the tenth was the owning skill's own stale count. The platform had also baselined the contradiction: an accepted-pair ratchet flagged the fix as new drift because a stale row had normalised the defect, and that row was pruned in the same pass.

**The per-check strictness override was inert at the point where it mattered.** The escalation function switched on the shared setting rather than on the check's own resolved setting, so a per-check override was advertised in configuration and had no effect at the moment a finding becomes a failure. Thirteen check identifiers carried that defect. The fix resolves per check through a helper that already existed, giving one precedence model that is most-specific-wins in both directions; back-to-back runs reconciled to zero delta by membership across every verdict class, confirming it changed escalation only and detection not at all. The one place most-specific-wins deliberately does not hold is the global off switch, which remains a detection kill switch a per-check setting cannot override — now stated in a comment rather than left implicit.

**The release reproduced its own thesis sixteen times, and the most dangerous instance was a green gate.** The thesis is that a claim about a population is only as good as the probe behind it. Sixteen distinct probes with a pattern or a denominator narrower than the criterion they were answering were caught and disclosed during the release, six of them by the orchestrating session itself, and every single one produced a null that read as a clean result: a pattern matching two literal strings where the criterion's meaning spanned seventeen; a three-skill sample standing in for a fifty-five-skill denominator; an empty alternative that silently zeroed a whole union; a swallowed file-not-found reading as no matches; a stream editor that no-opped while its caller returned success; and a continuous-integration gate that was green only because it runs in reporting mode. That last shape is the dangerous one — a success signal structurally incapable of being false is the same object as a gate that can never fire, which is precisely what the two new checks exist to prevent, and which both of them currently are, because both ship in reporting mode. Their own green is advisory, not evidence.

**The version label moved three times and the atomic claim held on the first attempt.** The release determined one version at planning and lost it three times over — twice to siblings that merged while it sat at review, and once mid-rebase to the very change its own merge hold was waiting on. The mainline advanced five times and roughly 77 commits across the run. The branch was re-labelled forward before the merge rather than relabelled after it, so the integration commit carries the correct label and no post-merge correction was needed, and the claim at the merge instant won with zero collisions. Worth carrying forward: concurrent-release density now exceeds what labelling a release before the claim assumes. Separately, this release produced the platform's first measured delivery cycle time — 4h26m — where the preceding thirteen entries all record no value, because it was the first to emit both of the anchor events the measurement joins on.
