# Security-hook fixes now reach workspaces you already installed

2026-07-12 · v3.73.1

The v3.73 security patch shipped a hook fix — but the everyday `update.sh` did not actually refresh the security hooks on your machine, so that fix (and any future one) sat undelivered until you re-ran the full installer. This hotfix closes that gap: `update.sh` now refreshes the deployed hook bundle as part of a normal update.

## Who this affects

Every install. If you updated to v3.73 with `update.sh` and did **not** separately re-run `setup-workspace.sh`, your hooks may still be the pre-v3.73 versions — this release delivers them.

## What you need to do

**Pull the latest clone and run `./update.sh`.** It now refreshes your deployed security hooks automatically (this was the whole point of the fix), including the v3.73 hardening that a prior `update.sh` would have skipped. Re-running `setup-workspace.sh` also still works and remains the fallback.

## What changed for everyone using the platform

- **`update.sh` now refreshes your security hooks (#3430).** The update command deploys skills and packages but previously left the deployed security-hook bundle — the hooks plus the small helper files they ship with — untouched. That meant a security fix to a hook only reached you if you re-ran the full installer. Now a normal `update.sh` refreshes that bundle too. *Why it matters:* the v3.73 hook hardening (and anything like it later) actually lands when you update, instead of quietly waiting.
- **Your own edits to a hook are preserved, not overwritten.** The refresh is checksum-aware. A hook that still matches the version the platform last installed is treated as stock and updated to the new version. A hook **you edited** is left exactly as-is, with a one-line notice telling you it was preserved — so a security update never silently clobbers a local change. *Why it matters:* you get the fix without losing your customizations, and you're told when the two are in tension.
- **A no-op update stays a no-op.** If your hooks are already current, the refresh reports "nothing changed" and `update.sh` still exits with its unchanged status. *Why it matters:* the new step doesn't make every routine update look like it did work, so an update that reports a change really made one.

## Known limits

- **You still have to run the update once.** This fix is delivered by the very command it improves, so the first hop requires pulling the clone and running `./update.sh` (or the installer). After that, hook fixes ride along with normal updates.
- **A hook you edited is preserved, which means an edited hook does not auto-receive a security fix.** That is deliberate — the tool will not overwrite your work — but it means the notice ("preserved: this hook diverged from its baseline") is your cue to reconcile the edit by hand and pick up the new version.

## Reversibility

**CHEAP.** The change is additive and opt-in: a new `--refresh-hooks` mode in `setup-workspace.sh` and one delegating phase in `update.sh`, plus a regression test and its CI wiring. A single revert restores the prior behavior, and a full `setup-workspace.sh` run remains an unchanged fallback path throughout.

### Operator and engineering detail

The refresh is a new `setup-workspace.sh --refresh-hooks` mode that re-deploys **only** the security-hook bundle (hooks + co-shipped primitives + `lib/`) into an existing workspace. It reuses the same single-sourced `install_hooks` co-deploy list the full installer uses — so the list cannot drift into a third copy, which is the exact trap that had left one v3.73 helper (`positional-issueref.awk`) uninstalled. Drift handling is non-interactive and checksum-keyed: deployed content matching the recorded baseline (or with no baseline) is refreshed; diverged content is preserved and warned. `update.sh` invokes it as a new Phase 5c and flips its "something changed" signal only on a genuinely refreshed hook, so the `EX_NOCHANGE` exit contract is preserved (the primitives are re-copied every run and would otherwise make every update look non-idempotent). A follow-up (#3429) will let a non-enforce hook whose helper library is missing degrade rather than block — the availability edge noted in the v3.73 release.
