# Roadmaps get a shipped in-repo home; initiative labels read as a grouping

2026-06-27 · v2.33

This release gives roadmap instances a built-in place to live and clarifies how "initiative" labels are described. Neither change alters any behavior or data — they make the platform's structure clearer and safer.

## What changed for everyone using the platform

**Roadmaps now have a built-in home.** The platform ships a `/roadmaps/` folder for roadmap instances. It is present on a fresh clone, your roadmap files stay private (git-ignored — never committed to the repo), and they **survive every update**: the folder sits outside the update process's reach, so nothing overwrites your content. If you prefer to keep roadmaps somewhere else, the location is still repointable (one setting). Previously there was no shipped home — the location pointed at an operator-local path that did not exist on a fresh install.

**"Initiative" labels read correctly.** The label guide used to describe an initiative label as a "binding tier" between tickets, which implied a hierarchy level the platform does not actually have. It now states plainly that an initiative label is a *grouping*, and points to the single source that defines the work-item hierarchy. No labels were added, removed, or re-applied.

## Under the hood

- **ADR-046** records the in-repo roadmap home and supersedes-in-part the operator-local placement of ADR-012 (location) and ADR-017 (the operator-instance path family). The rationale: authored content (roadmaps, like analyses) ships in-repo and git-ignored; operator runtime state stays operator-local.
- The `<OPERATOR_INSTANCE_ROADMAPS_PATH>` token default moves to the in-repo `/roadmaps/` across the two source-of-truth surfaces (the token registry and the resolver config), so the folder is actually resolved — not just present.
- The work-item hierarchy remains methodology-invariant; "initiative" is a grouping label, never a container tier.
- Existing roadmap instances migrate by copy (originals retained); instances stay git-ignored, so the migration has no repository-history effect.

## Reversibility

**MODERATE** — the change spans a handful of governance/config surfaces plus a new folder; a revert restores the prior state in a short window, and roadmap instances (git-ignored throughout) are never at risk.
