# Roadmaps get a shipped in-repo home; initiative labels read as a grouping

2026-06-27 · v2.33

Roadmap instances now have a built-in place to live that survives every platform update, and the label guide no longer implies a hierarchy level the platform does not have. Neither change alters any behavior or data.

## What changed for everyone using the platform

- **Roadmaps now have a built-in home.** The platform ships a `/roadmaps/` folder for roadmap instances — present on a fresh clone, kept private (never committed to the repository), and untouched by updates, with the location still repointable through one setting. *Why it matters:* there is now a known, plug-and-play place for roadmaps that platform updates can never overwrite — previously the location pointed at a path that did not exist on a fresh install.
- **"Initiative" labels read as a grouping.** The label guide used to call an initiative label a "binding tier" between tickets, implying a hierarchy level the platform does not have; it now states plainly that an initiative label is a *grouping* and points to the single source that defines the work-item hierarchy. *Why it matters:* the documentation no longer implies a container level that isn't real, so you won't structure work around a tier that does not exist — and no labels were added, removed, or re-applied.

## Known limits

- Existing roadmap instances are migrated by copy, not moved — the originals remain in their prior location for you to clean up if you want them gone.
- The in-repo `/roadmaps/` folder is the new default, not a forced relocation; a custom location set previously is preserved and still honored.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:methodology-packs` label.

## Reversibility

MODERATE / HIGH confidence. The change spans a few governance and config surfaces plus a new folder; reverting the change restores the prior state within a short window, and roadmap instances (never committed) are never at risk. Standard rollback window.

### Operator and engineering detail

**In-repo roadmap home (#416).** The platform ships a `/roadmaps/` folder — the folder and its README are tracked, while roadmap instances inside it stay git-ignored and are never committed. It is absent from the update/regeneration manifest, so platform updates never overwrite operator content. The `<OPERATOR_INSTANCE_ROADMAPS_PATH>` token default moves to the in-repo `/roadmaps/` across both source-of-truth surfaces — the token registry (`depersonalization-spec.md`) and the resolver config (`operator.toml.template`) — so the folder is actually resolved, not merely present; the path stays repointable as an override. **ADR-046** records the decision and supersedes-in-part the operator-local placement of ADR-012 (location) and ADR-017 (the operator-instance path family): authored content (roadmaps, like analyses) ships in-repo and git-ignored, while operator runtime state stays operator-local.

**Work-hierarchy single-source + Initiative reframe (#1038).** `label-taxonomy.md` no longer describes an "initiative" label as a binding tier between work items; it states the label is a grouping and cites the single source that defines the methodology-invariant work-item hierarchy, with `initiative-roadmap-framework.md` reconciled to that same source. No labels were added, removed, or re-applied — this is a documentation-truth correction with no behavior change.
