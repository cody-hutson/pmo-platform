# The knowledge base can now orient a fresh reader without inside knowledge

2026-07-17 · v3.76

A cleanup pass across the platform's internal knowledge base: every reference document now carries a short standard header (and the build fails if one is missing), the self-audit checklist and a duplicated set of health thresholds now point at where things actually live, and the platform's product vision and install model are written down in the design docs rather than living only in an operator's memory.

## What changed for everyone using the platform

- **Every reference doc now carries a standard summary header — enforced everywhere.** Each non-governance document in `core/` now has a short frontmatter block (title, purpose, type, status), and the build check that verifies it was flipped from "warn on a few folders" to "fail across the whole corpus." *Why it matters:* a new reader — or an agent — can tell at a glance what a document is for and whether it's current, instead of inferring it. A doc that ships without a header now shows up as a build failure, not a silent gap.
- **The platform's self-audit checklist points at where files actually live.** `AUDIT_FRAMEWORK.md` described a legacy folder layout (a `Projects/…` structure) that no longer exists. It was refreshed — every stale path rewritten to its current home — while keeping the audit method itself unchanged. *Why it matters:* anyone (or any agent) running the audit now opens real files instead of dead paths. (We chose to refresh rather than retire it: two live scheduling docs still depend on the method.)
- **A duplicated set of schedule-health thresholds now points to the one official copy.** The schedule-performance RAG bands were written out in two places; the second copy now simply references the canonical definition. *Why it matters:* one source of truth means the two copies can't drift apart over time.
- **A placeholder used in examples is now documented as example data.** `[PROJECT_KEY]` — which appears in illustrative config and sample paths — is now formally classified as example data, distinct from the real substitution tokens the setup process fills in. *Why it matters:* it removes a genuine ambiguity about whether it was a live setting.
- **The platform's vision and install model are now written into the design docs.** Who the platform serves, the kinds of building blocks it's made of, and how it's installed (clone the canonical repository directly — not fork-and-self-host, captured as a formal decision record, ADR-083) are now codified in the architecture overview. *Why it matters:* the "why" behind the platform lives in the repository where it can be reviewed and kept current, not in one person's head.

## Known limits

- **The header check covers authored reference docs, not test fixtures or ADRs.** Architecture Decision Records use their own header convention and are handled by a separate effort; test-fixture files are deliberately excluded. The corpus-wide check applies to the authored-documentation surface.
- **The enforce gate is a local/pre-merge check, not a hosted CI status.** The frontmatter check runs when you run `deploy.sh --check` and at the release readiness review; it is not (yet) mirrored as a GitHub status check. A global emergency off-switch is retained so the gate can never become un-disableable.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility
CHEAP — the whole release is a single squash-merge; a `git revert` of the merge commit removes every change atomically. The frontmatter-gate flip is a one-line revert; all content changes are additive documentation.
