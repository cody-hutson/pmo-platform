# Shared project facts now live in one place, and PROJECT.md links to them

2026-06-30 · v3.37

Until now, every project's overview page (`PROJECT.md`) repeated the same facts — the people involved, the systems in play, the vendors, the workstreams — in its own copy. This release introduces a shared home for those facts (a `_pmo/` area) and turns `PROJECT.md` into a thin index that links to the shared entries instead of restating them. Plans (communications, training, hypercare, cutover, change-management) also become typed entries you can link to and relate to one another. Existing projects are not moved in this release — the new structure is available for new work, and moving a live project over is a separate, deliberate step.

## Who this affects

Anyone who reads or maintains a project's `PROJECT.md`, or who sets up a new project. Nothing changes in how you run day-to-day work; this changes where shared project facts are stored and how the overview page references them.

## What you need to do

Nothing. This release makes the new shared-entity structure and the new `PROJECT.md` index format available. Your existing projects continue to work exactly as before — they are not migrated by this release.

## What changed for everyone using the platform

- **Shared entities have one home.** People, systems, vendors, workstreams, decisions, and cross-project dependencies now live in a shared `_pmo/` area with a consistent page for each, instead of being re-described inside every project. *Why it matters:* a person or system is described once and referenced everywhere, so the facts stay consistent across projects and stop drifting apart.
- **PROJECT.md becomes a linked index.** A project's overview page is now a short index that links out to the shared entity pages and to its plans, rather than a long document that repeats everything. *Why it matters:* the overview is easier to scan, and updating a shared fact updates it for every project that links to it.
- **Plans are typed and linkable.** Communications, training, hypercare, cutover, and change-management plans are now typed entries with defined relationships, and a project's overview links to them. *Why it matters:* you can point to a specific plan and see how it relates to the rest of the project instead of hunting through one big file.
- New projects created with `project-initiator` automatically get the shared-entity layout and the new index-style `PROJECT.md`. *Why it matters:* new work starts in the shared-facts structure from day one, with no manual setup and no per-project copy to keep in sync.

## Known limits

- **Existing projects are not moved by this release.** The new structure ships ready to use, but migrating a live project's `PROJECT.md` to the linked-index format is a separate, deliberate step done one project at a time (with a snapshot taken first and the links verified after). This release ships the capability; no live project is migrated as part of it.
- Bulk migration of many projects at once is intentionally out of scope and will follow after the first single-project migration is proven.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**CHEAP / HIGH confidence.** The structure, templates, and schema are additive and roll back by reverting the release change. The only step with no automatic undo is migrating a live project's overview page — and that step is deferred out of this release, done per-project with a snapshot taken beforehand.

### Operator and engineering detail

See the `#21-shared-entity-storage-layout` RELEASE_LOG row for the raw audit trail. Notable points:

- **`_pmo/` shared-entity layout (#362).** Establishes `projects/_pmo/{people,systems,vendors,workstreams,decisions,dependencies}/` with six entity-page templates (Person / System / Vendor / Workstream / Decision / cross-project Dependency & Conflict) matching the frozen schema sections. The alias-tracking convention composes with ADR-040 `person_id` + the people-roster (compose, not fork). `project-initiator` Mode A gains a `_pmo/` bootstrap step.
- **Composed-index PROJECT.md (#363).** Redesigns `PROJECT.md` as a thin composed wiki-link index (≤50-line template) that links INTO the `_pmo/` entity pages, adds a `project-initiator` Mode A Step-3 template-ref swap, and defines a 4-step live-migration protocol with a backwards-compatibility consumer table against the live `project-schema.md` consumers.
- **Typed plan sub-entities (#159).** Models plans as typed sub-entities (comms / training / hypercare / cutover / change-mgmt) with relationship typing, resolves the deferred `plan_type` G5 enum membership, and drops `plan_subtype`. The composed index's `## Plans` section points at these typed entities.
- **Live migration deferred (AC-5).** The gated proof-of-concept migration of ≥1 live `PROJECT.md` is deferred out of this release. The live overview page and the `projects/_pmo/*` directories are executor-tracked (git-ignored) and are not in the release PR diff; the merge ships the capability only. The deferred migration is done per-project with a snapshot-before / verify-links-after protocol per the release plan's R1 mitigation.
- **New shape — a composed-index PROJECT.md.** The linked-index format looks like this (the overview page links out rather than restating):

```markdown
# <Project Name> — Overview Index

## People
- [[_pmo/people/jane-doe]] — Sponsor
- [[_pmo/people/john-smith]] — Tech Lead

## Systems
- [[_pmo/systems/oms]] — order management
- [[_pmo/systems/wms]] — warehouse management

## Vendors
- [[_pmo/vendors/acme-integrations]]

## Workstreams
- [[_pmo/workstreams/data-migration]]

## Plans
- [[plans/cutover-plan]]        (plan_type: cutover)
- [[plans/training-plan]]       (plan_type: training)

## Decisions
- [[_pmo/decisions/D-014-oms-cutover-window]]
```
