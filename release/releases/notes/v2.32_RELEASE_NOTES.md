# The skill registry now checks itself against the deployed skills

2026-06-27 · v2.32

The platform keeps a catalog of every skill in one file (the skill registry). Until now nothing confirmed that catalog matched the skills actually deployed, so a skill could be added or removed without its catalog entry following — and the gap would sit unnoticed. This release makes the build check the catalog against the live roster: a missing entry, an extra entry, or an entry that points at a skill that no longer exists now fails the build. A few documents that referenced a catalog file which never existed have also been corrected to point at the real registry.

## What changed for everyone using the platform

- **The skill catalog is now checked against the skills that are actually deployed.** The build validation compares every catalog entry against the live skill roster in both directions and confirms each entry points at a skill that really exists. *Why it matters:* if a skill is added or removed and its catalog entry is forgotten, the build now stops and says so, instead of the catalog quietly going out of date.
- **A second, gentler check watches each entry's recorded details.** For role-specialist entries, the build also compares the details recorded in the catalog (such as the skill's modes and what it composes) against the skill itself, and logs any mismatch. *Why it matters:* the catalog stays trustworthy as a description of each skill, not just a list of names — and for now a mismatch is reported, not blocked, while the check settles in.
- **Documents that pointed at a catalog file which never shipped now point at the real registry.** Several reference docs and skills cited a `dependency-graph.md` that was never created; they now cite the live `registry.md`. *Why it matters:* following one of those references used to lead to a dead end — now it lands on the file that actually holds the catalog.

## Known limits

- The entry-details check (the second one above) runs in a logged-but-not-blocking mode for now. It reports mismatches without failing the build until a short settling period confirms it produces no false alarms; only then is it switched to blocking.
- The detail comparison applies to role-specialist entries; it is not yet extended to every entry type in the catalog.
- This release checks the catalog's accuracy; it does not change what any skill does or how you invoke it.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:skill-registry-identity-and-currency` label.

### Operator and engineering detail

**Row-currency is the always-enforce layer (#1811).** `deploy.sh --check` gains `Check 5(d): Registry-currency`, appended after Check 5(c) and reusing Check 5's roster machinery. The row layer asserts three things against the deployed roster (`OPERATIONS_SKILLS + RELEASE_SKILLS + CORE_SKILLS`, canary excluded per ADR-04): (i) every registry row name is a roster member; (ii) every roster member has a registry row — FAIL on asymmetry in both directions; (iii) every registry row name resolves to a live `SKILL.md`. The layer is structural and zero-false-positive, so findings increment `ISSUES` directly. It inherits the `cmd_check` empty-array guards and degrades a broken parse to a single loud audit-baseline FAIL rather than a fail-storm.

**Field-currency is the warn-mode-initial inner layer (#1658).** A per-row inner assertion extends the row loop at a single marked nesting seam, so both layers share one roster source and cannot fork. For each role-specialist row it checks the recorded modes/dependencies (set-equality) and trigger-surface presence against the live `SKILL.md`. It runs warn-mode-initial per the established Check 14/15/18/19 shakedown precedent — mismatches log as `WARN` and do not gate until `registry-field-currency.mode` is flipped to `enforce`. A companion fix (`6e74427`) reconciled the `pmo-architect` composition set — frontmatter plus its registry row — to its true 2-skill set so the field layer reads a clean row on a pristine roster.

**Consumer re-point closed the phantom-citation surface (#1211).** Thirteen files across `core/`, `operations/`, and `release/` cited a `dependency-graph.md` that never shipped; they now cite the live `core/skills/registry.md`. One net-new `registry.md` citation in `skill-workspace-location.md` was de-linked to avoid a forward-reference. This is a pure reference correction with no behavior change; the cross-reference-integrity CI gate passes.

**Sample — the clean Check 5(d) output block:**

```
Check 5(d): Registry-currency (rows)
  OK:    registry catalog current — 43 rows <-> roster (symmetric; canary excluded), every row resolves to a live SKILL.md; field-currency asserted per role-Specialist row (modes/dependencies set-equality, trigger-surface presence; mode=warn)
```

A row-direction failure reads, e.g., `FAIL: registry-currency — roster member '<name>' has no registry row …`; a field-direction mismatch reads `WARN: registry-field-currency — … (warn-mode; flip registry-field-currency.mode to 'enforce' after the shakedown window)`.

**Versioning + packaging note.** The release was planned at the routine class with the concrete number deferred to merge; it bound to v2.32 at the Stage 12 atomic claim above the shipped anchor v2.31. Four drifted distribution packages (`build-reviewer`, `pmo-architect`, `pmo-skill-editor`, `pmo-skill-refiner`) were rebuilt at the release cut.
