# A close-out retrospective template ships, on a decided release-corpus home

2026-06-20 · v2.04

Every release can now close with a structured retrospective and lessons-learned write-up, authored from a single template that ships with the platform. The template combines a blameless retrospective and a lessons-learned ceremony in one file, and it landed on top of a ratified decision about which release records are public capability and which are the maintainer's own working history. This release decides that split and ships the template; the work of physically moving the maintainer's history out of the shared copy is captured as a separate follow-up.

## What changed for everyone using the platform

- **A close-out retrospective template is now available.** Each release can be closed with a single combined template that walks a blameless retrospective (what went well, what we learned, what we'd change) and a lessons-learned write-up (situation, outcome, lessons, next-cycle actions). *Why it matters:* the reflection step at the end of a release has a ready structure to fill in, instead of being assembled from scratch or skipped.

- **Closing a release explains where its filled-in retrospective belongs.** The close-out step now names the template and states that the filled-in copy is written to your own local workspace, not committed to the shared platform. *Why it matters:* your release reflections stay yours and local, and a fresh install of the platform ships the blank template without anyone else's release history.

## Known limits

- This release ships the template and decides the public-vs-local split for release records; it does not yet move the maintainer's existing release history out of the shared copy. That move is tracked as a separate follow-up and changes nothing you observe today.
- The filled-in retrospective is a manual, human-authored reflection. The platform already produces a short machine-generated learnings summary per release; the template is a place to expand on that by hand, and the two are kept side by side rather than one replacing the other.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. This release is additive — a new template file, a new decision record, and a one-section edit to the close-out reference. Whole-release rollback is `git revert -m 1` of the integration merge; the new template has no prior consumer to unwind, and no release records were moved. Standard 7-day rollback window.

### Operator and engineering detail

**#1412 — release-corpus public-vs-instance split (design only this release)** — `core/ADRs/ADR-032-release-corpus-public-vs-instance-split.md` (Accepted) applies ADR-017's S1-Package-vs-S3-State cut to the release corpus: `RELEASE_LOG.md` / `RELEASE_DIGEST.md` / `notes/` / `plans/` are S3 operator-instance content; `CHANGELOG.md` and an empty `RELEASE_INDEX.md` seed are the thin S1 public surface; the templates / schema / pipeline / tools / deploy-checks are S1 public mechanism. The load-bearing rule is "the capability ships; the content instances." The ADR resolves #1412's five open questions, pins the instance-root resolver to the canonical `${CLAUDE_WORKSPACE_ROOT:-$HOME/Claude}` (not the ADR-017-named orphan `PMO_INSTANCE_PATH`), and chooses a HEAD-only removal over an irreversible history scrub (the content is non-PII operational detail; a `git filter-repo` rewrite is force-push-denied, `refs/pull/*`-leaky, and buys nothing the threat model needs). The corpus **migration execution** — `.gitignore` + `git rm --cached` + physical move + re-pointing four tools and two reference docs + converging the 21 `deploy.sh` `PMO_INSTANCE_PATH` fallthroughs onto `CLAUDE_WORKSPACE_ROOT` — is **deferred** to a dedicated follow-up issue, complete-by-construction from the ADR's deferred-migration plan. ADR number provenance: authored as ADR-029 in the Stage 5 design, renumbered to ADR-032 at Stage 6 because ADR-029/030/031 landed first during the engineering window (`check-adr-numbers.py` confirmed 032 gap-free).

**#360 + #361 — combined close-out register template** — one `release/references/templates/release-learnings-register-template.md` ships PUBLIC carrying a full Kerth retrospective block (Prime Directive + three-question framework + ritual of closure) and a full PMBOK 7 lessons-learned block (Situation / Outcome / Lessons / Next-cycle Actions), per the D-RegisterShape "one combined template" and D-Right-Sizing "full ceremony" decisions. `release/references/pipeline/stage-13-close.md` §6 names the register and states its COEXIST relationship to the machine-generated `#### Release Learnings v<X.Y>` triple H4 block — directional: the triple's three fields (`Surprise` / `Would-change` / `Watch-for`) are seed inputs the operator transcribes and expands into the register; the triple stays authoritative for the cross-release pattern-detector and is unaffected by the register's presence or absence.

**Half-migration friction (flagged, not resolved)** — because the #1412 migration is deferred, the operator-instance path tokens do not yet resolve to a real instance tree: `${CLAUDE_WORKSPACE_ROOT:-$HOME/Claude}/personal/pmo-instance/releases/` is not bootstrapped (the `install.sh` skeleton that ADR-032 specifies is part of the deferred execution), and `<OPERATOR_INSTANCE_RELEASE_LOG_PATH>` still resolves to the in-repo `release/releases/RELEASE_LOG.md` per the `release-notes-standard.md` footnote. All five corpus surfaces for this release are therefore written to their in-repo paths under the pre-extraction resolution rule — no corpus migration, `.gitignore` edit, or toolkit re-point was performed. The first filled close-out register (this release's dogfood) was written to the canonical instance path, which had to be created at close because the bootstrap has not run.

**Version reclamation** — scoped `v2.07` at Stage 4, re-versioned up to a provisional `v2.10` at Engineering Commit 0 (v2.07/v2.08 had shipped and `v2.07_RELEASE_PLAN.md` was taken by a different release), then reclaimed the original abandoned `v2.04` slot at the Stage 12 gate. `git ls-remote --tags origin v2.04` confirmed no v2.04 tag existed (the held v2.04-close-out-registers attempt, PR #1407, never merged). A deliberate backwards-version reclamation numerically below the shipped v2.05–v2.08; the operator accepted `git describe` non-monotonicity. The release branch `release/v2.10-close-out-registers` is retained for traceability only; the tag, plan filename, PR title, and commit scope all carry v2.04.
