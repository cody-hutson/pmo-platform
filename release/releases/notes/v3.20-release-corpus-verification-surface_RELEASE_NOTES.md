# Release-pipeline self-checks now fail loud instead of passing on broken paths

2026-06-07 · v3.20

The checks that guard the platform's own release records used to read GREEN even when the file or folder they were supposed to inspect did not exist — so a broken check looked exactly like a passing one. Those checks now fail loud, and the release-planning tool that groups issues into a release now reads the real-world variety of issue formats reliably.

> **Skip the rest** unless you run platform releases or rely on the release-planning and release-close tooling.

## Who this affects

- The workspace operator who runs the release pipeline (planning, bundling, and close-out)
- Anyone maintaining the platform's deploy-check tooling

## What changed for everyone using the platform

- **The release pipeline catches its own broken checks now.** The self-checks that verify the platform's release records (`deploy.sh` Checks 20 and 23, plus the broader deploy-check family) now exit with an error when a path they depend on does not resolve, instead of silently reporting success. *Why it matters:* a misconfigured or moved file can no longer hide behind a green check — the failure surfaces immediately instead of going unnoticed until a release.
- **Release planning reads real-world issue formats reliably.** The tool that groups open issues into a release now parses the heterogeneous ways issue bodies are actually written (varied section headings, missing optional sections) and reaches the ≥90% clean-parse target on the live set of bundle-ready issues. *Why it matters:* release planning no longer chokes on ordinary formatting differences between issues, so fewer items are dropped or mis-grouped at planning time.
- **The release-close tool only uses labels that exist.** A release-pipeline step that files a follow-up issue previously referenced a label that was never created in the project, which would have made that step fail when used. It now uses only labels that exist in the live label set. *Why it matters:* the release-close path no longer carries a latent failure that would surface the first time the step ran.

## Known limits

- This release changes platform-internal tooling and self-checks; it does not change any project-facing skill output, status report, or artifact format.
- The newly-strict deploy-checks report path-resolution errors as hard failures — if a future change moves a tracked file without updating the check, the check now stops the release until the path is corrected (this is the intended behavior).

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. `git revert` of the release PR (#496) reverses every change in this release atomically; the changes are tooling and self-check corrections with no data migration and no persisted state to unwind. Standard 7-day rollback window.

### Operator and engineering detail

**Release-corpus tools rewired to the live layout, deploy-checks made fail-loud (#83, #85, #459).** Both release-corpus tools were hardcoded to the pre-restructure `pmo-platform/...` paths and passed vacuously against the live `core/`/`release/` layout. `lint_release_corpus.py` (Check 20) now lints the real `release/releases/notes/` directory and the stale v11.18 cutover-floor exemption that was masking every live note is removed; `generate_release_index.py` (Check 23 `--verify`) now exits non-zero on a path-resolution failure rather than exiting 0 on a dead path. The `#85` Scope-column miscount is moot by construction — the live INDEX is the 6-column schema (`Version | Milestone | Date | Theme | Release PR | Release Notes`) with no Scope column, and the generator was retargeted accordingly. `#459` generalized the fail-loud-on-path-error contract across the rest of the deploy-check family (`deploy.sh` exits non-zero on path-resolution failure — no more green-on-broken) and fixed a confirmed pre-restructure old-path default in `check-version-anchors.py`; `check-doc-links.py` was rewired in the same pass. Companion doc updates landed in `release-corpus-schema.md`, `core/rules/doc-link-maintenance.md`, and `core/rules/skill-deployment.md`.

**Bundle-issues parser hardened to ≥90% combined-clean on the live substrate (#291).** `release/tools/bundle-issues-parser.py` (the `release-planner` Mode A engine) was repaired against the dominant failure-mode classes on the live conformant-bundleable substrate — field-name heterogeneity (heading aliases such as `### Files Affected` vs `### Affected Files`) and legitimately-absent optional sections previously treated as parse failures — lifting the combined-clean rate from a sub-target baseline to the ≥90% Mode A acceptance target. New fixtures `release/tools/tests/conformant_bundleable_sample.json` and `release/tools/tests/test_bundle_issues_parser.py` lock the behavior; `release/skills/release-planner/SKILL.md` was updated to match.

**release-executor retargeted to live-taxonomy labels only (#425).** Mode G's Pattern-Review file-new step prescribed a `category:`-prefixed label that does not exist in the live taxonomy, so the `gh issue create` call was latently broken. The filing path now uses only labels that exist (the Triage-applied type label; Category carried in-body). `release/skills/release-executor/SKILL.md` and `release/tools/automated-closeout.sh` were updated, and the `release-executor` and `release-planner` skill packages were rebuilt (`packages/release-executor.skill`, `packages/release-planner.skill`).

**Release Class: novel.** The plan carried D-class re-scope decisions for #83/#85/#291 after Stage-4 verification found the original acceptance criteria overtaken by the modular-monolith restructure; corpus-tooling blast radius warranted a Deep Stage 9 review. Engineering Commit 0 landed the release plan; the release PR also carried a prior-release v1.03 RELEASE_LOG/RELEASE_INDEX backfill (historical provenance unrecoverable post-re-versioning, recorded as a backfill rather than reconstructed).
