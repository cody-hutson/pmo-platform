# Release version numbers now bind when a release ships, not when it is planned

2026-07-25 · v3.93

This release changes how the platform names and versions its own releases. A release now keeps its **capability-slug** identity — a readable name like `release-identity-and-plan-naming` — all the way through the pipeline, and binds its concrete version number (`v3.93`) in a single atomic step at the moment it merges. Previously the number was chosen early, at planning time, and baked into the branch and plan filename — so two releases running at once would both grab the same next number and then churn through re-versioning to sort it out. That early-binding collision is now gone.

This release **dogfooded its own change**: it carried the slug `release-identity-and-plan-naming` through all 13 stages and bound `v3.93` only at the final merge — while three other releases were simultaneously sitting on `v3.93` branches. Because none of them had bound the number early, there was nothing to collide on; the first to tag simply won.

## Who this affects

- **Anyone running platform releases** — the release branch, plan file, and in-file version references now stay slug-named while a release is in flight, and the number binds at merge. The re-version churn when two releases overlapped is eliminated.
- **Anyone cutting a hotfix** — the plan-filename check now accepts the three-part patch form (`vX.Y.Z`), so a hotfix plan no longer trips the corpus lint.
- **Everyone else** — no action. Everyday project work is unchanged; this is release-machinery plumbing.

## What changed for everyone using the platform

- **Version numbers bind at the merge-claim, not at planning (#2548).** A release's branch and plan file carry its capability slug (and a `{{RELEASE_VERSION}}` placeholder for in-file references) until it merges; the concrete `vX.Y` resolves in one atomic step at the tag. *Why it matters:* concurrent releases no longer collide on an early-reserved number, and the HALT-and-re-version loop that collision used to trigger disappears. Founding decision recorded in ADR-092.
- **Release branches and plans are slug-primary, and a check enforces it (#3107, #3993).** A new conformance check (`deploy.sh` Check 59) flags a concrete version baked into an in-flight branch or plan name, and the release-planning/execution tooling now accepts the slug form. *Why it matters:* the new convention cannot silently regress back to version-primary naming.
- **The plan-filename check accepts patch releases (#3307).** The corpus lint's filename rule now admits the three-part `vX.Y.Z` hotfix form (while still rejecting malformed names). *Why it matters:* hotfix plans stop tripping a spurious "non-compliant filename" finding.
- **A misnamed, duplicated plan file was cleaned up (#3119).** The v3.60 release's plan was still named for a stale provisional version and duplicated in two places; it is de-duplicated and correctly named — and a second stale file, discovered to belong to a *different* release, was renamed to its correct version rather than deleted. *Why it matters:* the corpus keeps exactly one correctly-named plan per release, so the release history stays navigable and audit-clean.

## What a release looks like now

```text
While in flight (pre-claim):
  branch:   release/release-identity-and-plan-naming        (slug, no version)
  plan:     plans/release-identity-and-plan-naming_RELEASE_PLAN.md
  in-file:  {{RELEASE_VERSION}}                              (placeholder)

At merge (the single atomic claim):
  tag:      v3.93                                            (bound once, here)
  plan:     plans/v3/v3.93_RELEASE_PLAN.md                   (renamed)
  in-file:  v3.93                                            (resolved)
```

## Known limits

- **This applies going forward; existing releases are grandfathered.** Plan files already named `vX.Y_RELEASE_PLAN.md` are not retroactively renamed.
- **The conformance check ships in warn-mode.** Check 59 reports a version-primary in-flight identity but does not yet block; the enforce-flip is a later step.
- **Two of the release's own identifiers were deliberately left out of scope.** The same "bind late" idea was proposed for the `deploy.sh` Check number and the ADR number, but that fights the platform's gap-free ADR rule and its Check-numbering contract — and those two already avoid collisions cheaply by renumbering at build time. They were carved to a follow-up (#3713) that will document the existing practice, rather than force a fragile placeholder.
- **A separate plan-file naming-drift cleanup is tracked.** Auditing the plan folder surfaced a couple of older plans (v3.55 / v3.56) with missing or stale names; that broader cleanup is filed as #4031.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE** · confidence **HIGH**. The release is a single pull request (#4029); a `git revert -m 1` of the merge cleanly restores the prior naming and binding behavior. The change to the version-claim script is purely additive — a stamping pass ahead of the existing atomic claim, which is untouched — and the two skill packages rebuild from reverted source. No data migration.

### Operator and engineering detail

Full detail: RELEASE_LOG row `#deployment-log-v393` (v3.93), plan `release/releases/plans/v3/v3.93_RELEASE_PLAN.md`.

Novel-class release, D-C SINGLE topology, P0 fully-serial — five issues shipped as delivery slices on one slug-primary branch, one PR (#4029), ~28 files, built in dependency order #2548 → #3993 → #3307 → #3119 → #3107. The release was a **Hybrid dogfood**: it adopted the new slug-primary name for its own run but bound its version through the existing (pre-migration) claim path, because a release cannot safely exercise its own just-merged version-substitution engine.

**#2548 + #3993 (lockstep) — the core migration.** `claim-version.sh` gains an additive post-CAS stamping pass (resolve `{{RELEASE_VERSION}}` + rename `<slug>_RELEASE_PLAN.md` → `vX.Y_RELEASE_PLAN.md` on the claim-win path; the existing atomic ref-CAS is untouched). `plans/README.md`, `RELEASE_PROTOCOL.md`, and its `release-process.md` mirror extend the tag's "binds no concrete value" discipline to the plan file and branch, composing with — not collapsing — the `{versioned, version-less}` identity mode. The executing skills (`release-planner`, `release-executor`) and the broad prescribing surfaces (`git-workflow.md` plus several schema/doc files) were migrated to accept the slug pre-claim form, applying a per-occurrence pre/post-claim discrimination so the tag, RELEASE_LOG, and shipped-corpus references were correctly left alone. Founding ADR-092.

**The AC5 carve (the pivotal design call).** The original scope also proposed tokenizing the `deploy.sh` Check number and the ADR number. Stage-5 Solutioning found this infeasible-as-bundled and carved it: a `{{ADR_NUM}}` filename is malformed under the gap-free `check-adr-numbers.py` (which runs on every PR), and a `{{CHECK_NUM}}` breaks Check-57's concrete-integer roster contract and would orphan ~1,192 by-number citations. The premise was corrected too — those two identifiers are *already* cheaply claim-deferred by a working renumber-at-Engineering discipline; only the plan-file churn was expensive. Routed to #3713.

**#3107 — the conformance check.** A git-context-aware primitive (`check-identity-conformance.py`) wired as `deploy.sh` Check 59 (warn-mode), window-gated on `release/*` pre-claim; the lint-check alternative was rejected because a static corpus lint cannot tell a pre-claim version-primary plan from a legitimately-renamed post-claim one.

**#3119 + #3307 — the correctives.** The 86-methodology plan was de-duplicated and renamed to `v3.60`; a second stale `v3.54` file, content-verified as the 80-solutioning plan, was renamed to its shipped `v3.57` (no data loss). The `CANONICAL_FILENAME_RE` was widened in one coordinated change to admit both the slug pre-claim form and the `vX.Y.Z` patch form while still rejecting malformed names; 21 now-redundant allowlist entries were pruned.

**Version lineage.** Slug-primary throughout — no provisional `vX.Y` was bound to any branch, plan, or commit. The provisional-display `v3.93` (a recorded Stage-4 determination) was claimed cleanly at the Stage-12 atomic ref-CAS; `v3.93` was free at the tag level even though three sibling releases sat on `release/v3.93-*` branches, and the atomic claim won it by tagging first — so no forward hop and no reversion-ledger row. Verification: Stage 7 Dev Testing re-ran every self-test (the version-stamp collision-safety fixture, the conformance-check fixtures, ADR contiguity, the regex accept/reject matrix); Stage 8 QA accepted every criterion across all five slices (one cross-issue cohesion check was partial and reconciled in-PR before merge); Stage 9 returned a Deep-review GO.
