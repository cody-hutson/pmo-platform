# The release pipeline can now record the decisions it makes

2026-07-29 · v3.100

A release run can now write down each decision it makes — including the automatic ones nobody is asked to approve — and every record names the release it came from. Most releases previously recorded nothing at all, so there was no way to look back at a finished release and see why it did what it did.

> **Skip the rest** unless you run a release through the platform's release pipeline, or you later need to reconstruct why a past release did what it did.

## Who this affects

- Anyone who runs a release through the platform's release pipeline.
- Anyone reviewing a finished release who needs to see which decisions were made along the way, and by whom.

## What changed for everyone using the platform

- **A release run can record the decisions it makes.** The pipeline now has a working way to write a decision down as it happens — what was decided, at which stage, how reversible it was, and how it turned out. *Why it matters:* the reasoning behind a release stops living only in the conversation that produced it.
- **The automatic decisions count too.** Two kinds of choice nobody is ever asked to approve — handing a piece of work off to a separate helper run, and a run repairing its own failure by retrying, escalating, or rolling back — are now treated as decisions worth recording. *Why it matters:* the choices made without you are the hardest to reconstruct later, and they are exactly the ones that used to leave no trace.
- **Every record names the release it belongs to.** Records now carry a stable release name rather than a number that can shift underneath them, so one release's records can be pulled up as a set. *Why it matters:* you can ask "what did this release decide" and get an answer, instead of guessing which entries belong to which run.
- **Closing a release now asks whether it recorded anything.** A check at the end of every release reports whether the minimum set of decision records is present, and names what is missing. For now the result is logged but not blocking. *Why it matters:* a release that quietly recorded nothing becomes visible, instead of finishing unnoticed.
- **Four checks that looked like they were working turned out to be doing nothing.** This release found a file-path check that had never once run in the project's history, a check described as a hard requirement that passed automatically whenever there was nothing to inspect, a newly written check with nothing calling it, and a guard nobody had wired up. Each is now paired with a test that deliberately tries to break it. *Why it matters:* a check that cannot fail offers protection it is not actually providing, and four of them had been counted as protection.
- **Nothing has been recorded yet — and that is deliberate.** The release that builds this machinery is exempt from using it, so there are no decision records for this release itself and the end-of-release check reports that it has nothing to inspect. *Why it matters:* the mechanism is complete but unproven, and the first evidence that it works arrives only when the next release runs.

## Known limits

- The recording side is finished but has never run in a real release. Every test of it so far used made-up sample data rather than records produced by an actual run, so its behaviour in production is untested.
- The end-of-release check only asks whether a record of each required kind exists. It cannot tell a correct record from a wrong one, and it cannot notice a record written for a decision that was never actually made.
- Nothing inspects the records before a release merges. A release can finish with no records at all and still show a clean set of automated checks.
- One of the new guards is not yet part of the checks that run automatically on every change, so it holds only when someone runs it by hand.
- Six follow-up items were opened from this release's own review; they are listed at the foot of this note.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

MODERATE / HIGH confidence. Undoing the release is a single revert of its merge commit, followed by rebuilding the two packaged skills it changed. It is MODERATE rather than CHEAP because the change spans the recording tools, the record format, and the end-of-release check together, so a revert has to take all three back at once. Standard rollback window.

### Operator and engineering detail

**A complete write side, inert by design.** The release ships the hub write-side of decision telemetry end-to-end — the append/query/contract-subset tooling, the schema extension that gives a decision event a stable release join key, the autonomous-seam definitions for the delegation and self-repair classes, the hub playbook and briefing surfaces that perform the emission, and the enforcement scaffolding including the close-time minimum-set gate. What it does **not** ship is the outcome. The introducing release is exempt from its own emission obligations, so the write side stays inert until the next release runs: live event population is **0** for both `delegation` and every `self-repair/*` subtype, the close-time gate verdicts **SKIP**, and every falsification test in the release is fixture-only. The deployment record is stamped `ALIGNED, UNOBSERVED` rather than `SUCCESS-delivered` for exactly this reason — the Release Outcome Statement promised a minimum decision-event set joining 1:1 to the shipped release, and this release built the mechanism that would produce it without producing any. The next release is this one's first real test, and the honest reading of every number in this note is "not yet measured", not "measured and good".

**Four vacuous controls, and one caught in the act.** The recurring finding of this release was controls that read as controls and enforced nothing. Check 19's event-log integrity assertion resolved the schema at a stale pre-reorganisation path, so sub-checks 19b and 19c had never executed in the repository's history — not once. The Procedure-7a gate was documented as HARD and passed vacuously whenever its input population was empty, which was always. The CIAC-3 lint shipped mid-release with zero call sites. CIAC-1's guard predicate was never funded in CI. Each is now armed with a falsification test — a test that deliberately breaks the condition and asserts the control fires — rather than a test that only confirms the happy path. The pattern was live during the release itself: one of the release's own fixes was caught introducing a *new* silent pass and was corrected before merge, which is the strongest available evidence that the falsification discipline is doing work rather than decorating the diff. Two of the controls this release ships still disagree with each other on the empty-asserted-set case (one exits 0, the other treats it as a repository defect); that disagreement is recorded as accepted residual risk, not resolved.

**The join key and the record shape.** A decision event now resolves to its release through a stable slug-first join key rather than a positional identifier, and the payload column carries a semicolon-keyed grammar with an escaped-pipe convention so a multi-value payload survives the table format. One row of the newly added `delegation` subtype, showing the release key and the payload grammar together:

```text
| 2026-07-28T06:38:10Z | decision-telemetry-emission | 6 | decision | delegation | hub | issue:#N | CHEAP | resolved | ms:#N; chose:spoke; unit:stage-6; merit:context-boundary; why:rename-is-a-graph-op-needs-branch-context |
```

**Residual risk carried into deploy.** Three Operator Override Records were rendered at the plan-review gate, all sharing one root cause: behaviour unobservable until the write side goes live. The accepted residuals are that the close-time gate has no pre-merge surface (a release can close with zero events on a green pipeline); that CIAC-1's guard is CI-unfunded; that the empty-asserted-set disagreement above is unresolved; and that the unenforced MUST in the emission contract carries an exemption which expires the moment the write side goes live. Six follow-ups were filed from the close-out review covering the missing deployment-status emitter, a CI mirror for the decision-emission check, a standing path-literal assertion so a Check-19-class stale path cannot recur, the residual version-keyed occurrences left in the corpus, a subtype-blind telemetry filter, and a schema formatting trap.

For full implementation detail see the [release log entry](https://github.com/cody-hutson/pmo-platform/blob/main/release/releases/RELEASE_LOG.md) and [the release plan](https://github.com/cody-hutson/pmo-platform/blob/main/release/releases/plans/v3/v3.100_RELEASE_PLAN.md).
