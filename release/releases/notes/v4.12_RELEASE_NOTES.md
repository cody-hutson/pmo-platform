# Release pages match their notes, and every release records how it went

2026-08-05 · v4.12

The public release pages had quietly diverged from the notes they were generated from, and nothing was watching closely enough to say how far. This release repairs 29 of them, closes the path that produced the divergence, and makes each release record its own delivery rate and its own learnings instead of waiting for someone to remember.

## What changed for everyone using the platform

- **29 published release pages now show the same content as the notes they came from.** Pages published before the notes were reorganized kept pointing at file locations that no longer existed, and five more had diverged after that. *Why it matters:* the release page is the version most people actually read, so a stale one sends readers to links that go nowhere and to text the platform no longer stands behind.

- **The path that produced the divergence is closed.** Three places in the platform told the publisher to send the note file itself; that form publishes the note's machine-readable header as visible text at the top of the page. They now send the note's body. *Why it matters:* the repair would have started drifting again on the next release without it.

- **Release notes that carry no version number are now actually checked.** The content checks skipped them twice over — once in how notes were discovered, and again in the age cutoff. *Why it matters:* a note reporting "no problems found" now means it was read, not that it was never opened.

- **Every release now records its own delivery rate and its own learnings as part of closing.** Both used to reach the record only when someone remembered a manual follow-up commit, and no check reported their absence. Closing a release now writes both, and a check now fails when either is missing. *Why it matters:* the numbers used to compare releases to each other are only meaningful if they are collected the same way every time.

- **A learning that happens only once now has somewhere to go.** Learnings that recurred were promoted; anything below that threshold simply stopped. *Why it matters:* the one-off observation is often the earliest signal, and it was the one being dropped.

## Known limits

- **26 published release pages are still divergent** and are tracked separately in [#4747](https://github.com/cody-hutson/pmo-platform/issues/4747). They need per-page judgement rather than a mechanical repair, so they were deliberately left out of this release.
- Those 26 all sit below the drift check's age cutoff, which is **deliberately unchanged**. The check therefore reports green, and green here means "no divergence inside the window it watches" — not "no divergence anywhere."
- The drift check itself still runs only when someone runs the local check command. What gained an automatic home in this release is the underlying rule, carried by a different check that already runs on every change.
- One earlier release record is missing its delivery-rate field. It is a real gap, not a false alarm, and it was left in place rather than filled in — a reconstructed number would bias the very baseline the field exists to establish.

## Reversibility

MODERATE / HIGH confidence. Every file change in this release reverts with a single revert of the release commit. The 29 republished release pages do **not** revert that way — republishing is a change to public content — but the previous text of all 29 was captured into the repository and merged before the first page was overwritten, so the prior state is recoverable even though the published surface is not.

### Operator and engineering detail

**The population was 55, not 11 — and the detector was the reason nobody knew.** The drift check resolved a note at its flat path only. After the notes corpus was reorganized into major-version buckets, 110 of 170 notes were unreachable, and each returned a `MISSING` verdict that every consumer read as "no artifact" rather than "could not resolve." The original sweep's `21 clean / 5 DRIFT / 101 N/A` was the fabrication signature, not a clean corpus. A recursive resolver put the real number at 55, split by operator decision into 29 mechanically repairable (this release) and 26 needing per-body judgement (#4747). Close-out re-verified all 29 at MATCH against a denominator of 29, with a sensitivity arm of 40 out-of-scope versions returning 15 DRIFT — so the all-clean result is a measured zero, not a broken probe.

**The same defect class, fixed at one call site out of two.** The read tool got the recursive resolver; the write tool authored alongside it did not, and failed closed on all 18 bucketed notes at Stage 12 with `ABORT: canonical note unreadable`. Failing closed was correct — it refused rather than publishing wrong content — but it stopped the payload at 0 of 29 until the resolver was ported. That is this release's own recorded **Would-change**: fix a defect class at every call site at once.

**Producer and gate shipped as separate halves, deliberately.** The close-out script now emits the delivery-rate field and the learnings block; the close-completeness gate now asserts both. Splitting them let the gate be graded against a real producer rather than against prose. The gate's cutoff is a third file-order latch (`v4.03`) rather than a raise of the shared row cutoff — raising the shared value would have paid for new coverage by narrowing the existing sub-checks from nineteen rows to four. `v4.03` is the oldest anchor with zero standing findings reachable without a prohibited backfill, since the delivery-rate field is explicitly grandfathered with no backfill.

The two Stage-13 outputs now written into each release's Deployment Log block take this shape:

```
**Cycle-Time:** 4h26m — (T_GO=…; T_DEPLOY=…; mechanism: compute-cycle-time.sh)
**Velocity:** planned 22 pts / delivered 22 pts (1.00); files-changed 77; allocation 0/22/0 pts (feature/debt/protocol-slack); class routine; mechanism: compute-release-velocity.sh
**Result:** SUCCESS — …

#### Release Learnings v4.12
**Source events:** 1 `release-synthesis/learnings-triple` row(s) (filter: release=`v4.12`)
**Surprise:** …
**Would-change:** …
**Watch-for:** …
```

**A zero-capture render is now a blocking condition.** If the learnings render finds no source events, close-out fails rather than writing "no novel learning this release" — an absence of evidence recorded as evidence of absence. v4.12's own close was the first live exercise of both new phases; the capture was sequenced ahead of the close, so the guard correctly did not fire.

**This release's own close-out surfaced two true positives in what it had just shipped**, both recorded rather than fixed in place, because a tool change is a governed change with its own issue and approved plan: the close-out report's phase table omits the two new phases, so their outcome never reaches the operator's audit trail; and the delivery-rate phase reads *closed* milestone members while running well before the phase that closes them, which is invisible whenever members auto-close at merge and visible here, where they deliberately did not.
