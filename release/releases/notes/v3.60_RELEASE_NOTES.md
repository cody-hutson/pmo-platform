# Methodology packs: pick a delivery method, or bring your own

2026-07-03 · v3.60

A delivery methodology — Scrum, Kanban, or a house style of your own — is now a self-contained, swappable "pack" instead of assumptions hardwired across the platform. This release lays the foundation: the pack format, two shipped starter packs, and a methodology-neutral label grammar; the agents that read packs to change how they behave come in a follow-up.

> **Skip the rest** unless you configure, customize, or add a delivery methodology.

## What changed for everyone using the platform

Mostly foundational — no change to day-to-day project work yet. For operators who configure delivery methodologies:

- **A methodology is now a single editable pack.** Scrum and Kanban ship as best-practice `core/packs/` manifests; you can copy one, edit it, or add your own archetype as a thin delta on the shared base. *Why it matters:* changing or adding a delivery method becomes a config edit instead of a platform code change.
- **One methodology-neutral label grammar.** The universal label rules live in one place, and each pack contributes its own methodology-specific labels bound to its work-item kinds. *Why it matters:* your methodology's labels come from its pack and can't silently drift from the platform's shared rules.

## Known limits

- The packs aren't read by the skills yet — selecting one does not change agent behavior until the consumer wiring lands (follow-up #2021).
- Kanban's work-in-progress-limit gate ships as a documented placeholder; the concrete limit is operator-local config, deferred by design.
- Two starter packs ship (Scrum, Kanban) on a shared base; further methodologies are added later as thin deltas.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

MODERATE / HIGH confidence. The grammar change is additive (existing type-packs parse unchanged) and the packs are new files, so rollback is a `git revert` of the release plus removing the new pack directory — no data migration, and nothing downstream reads the new surface yet. Standard rollback window.

### Operator and engineering detail

**The pack contract (ADR-069 / ADR-070).** A methodology pack is the plug-and-play composing unit at `core/packs/<archetype>/`, bundling a methodology's kinds, work-status, fields, labels, and gates as best-practice defaults — selected per `delivery_approach`, overridable per project. The composition grammar is recorded as a sibling ADR extending ADR-018 at the meta-schema altitude.

**The grammar widen.** The type-pack meta-schema gains an additive pack-composition layer: a `role` discriminator with `extends` delta-inheritance (a shared `_common` base carries the archetype-invariant majority; archetype packs declare only their deltas), a label-contribution facet, and a work-status projection. The meta-schema stays at v1 because every addition is optional — existing type-packs parse unchanged. A pack manifest is small enough to read or customize directly:

```toml
# core/packs/scrum/pack.toml (illustrative)
[meta]
pack_id    = "scrum"
applies_to = "Scrum"      # the delivery_approach this pack serves
role       = "archetype"  # vs. "base" for the shared _common pack
extends    = "_common"    # inherit the shared majority; declare only deltas

[[labels]]
name          = "type:story"
projects_kind = "story"   # bound to a declared kind so labels can't drift
```

**The label restructure.** `label-taxonomy.md` is now grammar-only (groups + rules); the concrete per-methodology label rows moved into the packs, and the parity check reads the doc and the pack set together so no label is orphaned.
