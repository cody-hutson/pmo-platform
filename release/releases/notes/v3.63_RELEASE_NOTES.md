# The release pipeline now runs on GitHub's native PR-review surfaces

2026-07-03 · v3.63

This release does two related pieces of plumbing for anyone who runs platform releases. First, the pipeline now uses GitHub's own pull-request review machinery — releases open as draft PRs that flip to ready-for-review at the go/no-go gate, review comments are a recognized feedback channel, and GitHub's approve / changes-requested state is surfaced as an advisory signal. Second, the two release-manager skills were brought back in step with the written pipeline they execute, so the skill you invoke and the spec it follows no longer disagree on how a release is evidenced and deployed.

## What changed for everyone using the platform

- **Release pull requests now open as drafts and flip to "ready" at the go/no-go gate.** A release PR is visibly work-in-progress through building, dev-testing, and QA, then transitions to ready-for-review right before the operator's go/no-go decision. *Why it matters:* the PR's state now tells the truth about where the release is — you review it when it is actually ready, not while it is still being assembled.
- **Pull-request review comments are now a recognized release-feedback channel.** A comment left on a release PR is routed the same way as an internal finding — a minor correction becomes a tracked fix with a resolving reply, and a scope- or plan-level comment is escalated to the operator rather than quietly absorbed. *Why it matters:* feedback left in GitHub's natural place — a review comment — no longer falls outside the process; it lands in the same triage the pipeline already uses.
- **GitHub's approve / changes-requested state is now shown at the go/no-go gate as advice, not a gate.** The release's native review-decision state is surfaced in the decision briefing as an advisory signal only; the operator's go/no-go remains the sole binding decision. *Why it matters:* you see GitHub's review signal alongside the evidence when you decide, without it silently blocking or forcing a release on its own.
- **The two release-manager skills are back in sync with the pipeline they drive.** The deploy-execution skill now reads the plan's delivery strategy and follows the current merge-tag-deploy mechanism by name, and the go/no-go evidence skill now names the exact quality and acceptance reports it compiles. *Why it matters:* the skill you invoke and the pipeline spec it follows agree again, so guidance you get from the skill matches how the release actually runs. <!-- impact:foundational -->

Under the platform's normal single-operator setup — where you are your own reviewer — all three PR-review behaviors are deliberately dormant no-ops: with no second reviewer, no review comments or review-decision state arrive, and the draft simply flips to ready by its author. They come to life if the release is ever run with a real second reviewer.

## Known limits

- The three PR-review surfaces are **dormant in single-operator mode.** With `--reviewer` dropped and you as the sole operator, GitHub emits no review-decision state and no review comments, so the review-comment channel and the advisory signal are honest no-ops until a second reviewer participates. The draft→ready lifecycle still runs (your PR opens as a draft and flips to ready), but no external review is required for it to complete.
- This release is **reconciliation and wiring, not new capability** — the release-manager skill modes already existed; this brought their written instructions back in line with the pipeline and added the GitHub-native review touchpoints. No existing release behavior was removed.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**CHEAP / HIGH.** The release shipped as a single pull request and is fully git-revertable. Every change is an in-repo Markdown or skill-definition edit — pipeline stage docs, the release-process governance doc, and three skill bodies (with their compiled packages rebuilt in the same PR) — with no data migration, no external deploy target, and no state to unwind. Rollback is reverting the merge commit, with no data-loss surface.
