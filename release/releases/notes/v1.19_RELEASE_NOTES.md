# Escalations now carry a recommendation and a decision owner, not just a problem

2026-06-14 · v1.19

When a skill raises a Critical or High issue, it no longer just names the problem and hands the thinking back to you. It now states the situation, what it blocks, the realistic options, and a recommended course of action with a confidence level — and it points the escalation at a named decision owner. The same structure is used whether the escalation comes from a status update, a project review, a technical review, or a delivery/RAID surface.

## What changed for everyone using the platform

- **Escalations carry a recommendation, not just a problem.** A raised Critical or High issue now states the situation, the impact, the options, and a recommended option with a confidence level. *Why it matters:* you get the platform's judgment of what to do — not a "here is a problem, you decide" handoff that leaves the analysis on your desk.
- **The recommendation and the ask are kept separate.** The recommendation states what the platform thinks is right; any deadline-bearing ask ("approve by Friday") rides alongside it rather than replacing it. *Why it matters:* you can ratify or override a clear recommendation instead of reverse-engineering one from a bare request to decide.
- **Escalations point at a named decision owner.** Each escalation is routed to the person who owns the decision, drawn from the project's people list; when no owner can be determined, it routes to the program manager with a flag rather than going nowhere. *Why it matters:* an escalation lands with someone who can act on it instead of stalling unassigned.
- **One consistent escalation format across the skills.** Status updates, project reviews, technical reviews, and delivery/RAID escalations now share a single format and the same severity rule for when to escalate. *Why it matters:* an escalation reads the same way and applies the same threshold no matter which part of the platform raised it.

## Known limits

- Decision-owner routing reads the project's free-text people list; until a structured owner field exists, an escalation with no resolvable owner is routed to the program manager with a flag rather than auto-assigned.
- This release standardizes the escalation format and routing; it does not change which issues qualify as Critical or High.

## Reversibility

CHEAP / HIGH confidence. `git revert -m 1 <merge-sha>` reverses the release PR; every change is additive — a net-new canonical document plus references to it — with no data migration. The new shared document has no prior consumers, so removing it is clean, and the revert restores each skill's previous inline escalation wording in the same commit. Standard 7-day rollback window.

### Operator and engineering detail

**Single canonical SIOR source (#179, keystone)** — SIOR (Situation / Impact / Options / Recommendation) escalation discipline previously lived inline across eight files with divergent structure, no shared severity-threshold policy, and — in comms-writer's case — no Recommendation component at all (the 2026-04-18 skill review's P1 gap). This release authors `core/standards/sior-escalation-protocol.md` as the single source for the format (the four mandatory ordered components), the severity-threshold policy (CRITICAL = always; HIGH = SIOR + stakeholder-authority check; MEDIUM = conditional on blocking a downstream deliverable; LOW = no), five worked escalation-class examples, and the decision-owner-mapping pattern. The document is presentation-neutral (content and structure, not rendering) so a future dual-format model can layer on it without changing it. comms-writer's Escalation type is re-specified to emit named SIOR sections with an explicit mandatory Recommendation plus confidence — the prior Ask-conflation is stripped and the Ask demoted to a closing call-to-action — and SIOR is carried into the name-keyed Escalation entry in `core/schemas/per-skill-output-contracts.md`. The decision is recorded in `ADR-025-sior-escalation-canonicalization.md`.

**Three consumers reconciled by relative link (#178, #177, #934)** — ppm-agent's Section 5 `[COMMS]` routing now emits a voice-neutral SIOR block, with its two inline copies (`references/push-to-resolve.md`, `references/proactive-follow-up-tracking.md`) reconciled to the canonical document; pmo-technical-analyst emits a severity-conditional SIOR block on Critical/High findings with an authority check and decision-owner mapping; and delivery-engine reconciles its two inline copies (`references/dependency-rules.md §4.2`, `references/raid-templates.md §7`) to the canonical document. Consumption is **link-reference**, not injection (ADR-025): the canonical stays out of `skills/*/references/`, so the deploy mechanism and the packaged skills carry no copy of it, and the only cross-issue file contention the plan flagged is eliminated. The four skill packages rebuilt only because each consumer skill's own content changed. Each of #178/#177/#934 also adds one new failure mode. The decision-owner mapping reads the project's free-text people list and routes to the program manager with a warning when authority data is absent; a structured owner field is deferred to a follow-up.
