# The PMO's operational data becomes agent-native and self-maintaining

2026-07-02 · v3.47

The platform's day-to-day operational surfaces — the trackers it keeps, the corrections it remembers, the projects it rotates focus across, and the stakeholder updates it sends — now have one agent-native source of truth each, and the stakeholder-facing versions are produced from that source rather than hand-maintained alongside it. The headline piece is a new document model that says, once and for everyone, how an operational artifact and its stakeholder rendering stay in sync so the two never silently drift apart.

## What changed for everyone using the platform

- **Operational artifacts now have one source, with stakeholder views rendered from it.** A new dual-format document model defines, for any operational artifact, a single agent-native source plus a per-audience translation map that produces the stakeholder version (which fields to show, hide, or rename, and in what format). *Why it matters:* you maintain the data once; the stakeholder view (a Confluence page, a CSV export) is generated from it and is flagged when it falls behind the source, instead of quietly going stale.
- **The RAID Log is now agent-native while still exporting the same CSV.** The RAID Log keeps its familiar CSV format for people, but the agent now reads and writes it as a structured surface and produces the stakeholder CSV/Confluence view through the translation map above. *Why it matters:* the log the team sees is unchanged, but the agent maintains it more reliably and the stakeholder export always matches the source.
- **Unanswered action items now escalate on their own.** When an actionable communication goes without a response, the platform drafts a follow-up after two days and prepares a formal escalation after five. *Why it matters:* items that need a stakeholder to act no longer stall silently waiting for someone to notice — the nudge and the escalation are prepared for you.
- **Corrections are now per-project, and repeated mistakes across projects get surfaced.** Behavioral corrections can now be scoped to a single project, and a detector notices when the same kind of correction recurs across two or more different projects and routes it for follow-up. *Why it matters:* a fix meant for one project stops leaking into unrelated ones, and a pattern that keeps recurring everywhere gets caught instead of being re-corrected over and over.
- **Session handoffs now track how long each project has held focus.** The session handoff record now remembers, per project, when it last became the focus, and derives how many weeks it has held that focus. *Why it matters:* it is now visible at a glance which projects have been in focus a long time, so rotation attention lands where it is due.

## Known limits

- The workspace-root operational files these changes govern (the corrections file and the session handoff record) are per-installation and are not stored in this repository; this release ships the source template and the skill logic, and the running files pick up the new fields at your installation.
- The cross-project correction detector fires only when the same correction recurs across two or more distinct projects; a correction seen in a single project is not treated as a cross-project pattern by design.
- The escalation timing (two-day draft, five-day formal escalation) applies to actionable communications; purely informational updates are exempt.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

- **Dual-format document model + ADR-064 (#234).** Authored `core/standards/dual-format-document-model.md` — a K1 standard that governs an operational artifact (the agent-native source of truth) and its stakeholder rendering as three parts: a **source definition**, a **per-target translation map** (field include/exclude/rename + target format), and a **version/drift-tracking rule** keyed on the Artifact Register (Tracker 6) rather than a new tracker. Authored `core/ADRs/ADR-064-dual-format-document-model.md` recording the executor-selection decision (artifact-generator applies the map; comms-writer and a both-skills split were rejected — this also eliminates the soft comms-writer contention with #239). Cited the RAID-Confluence dual-format handling in `core/schemas/tracker-schemas.md` as the proof-of-concept the model generalizes, bound the model to the Artifact entity's existing reconciliation seam (`domain` + `content_lifecycle_pattern`) in `core/disciplines/project-entity-model.md` with no new entity field, and added the dual-format render mode plus the orphan-rendering do-NOT failure mode to `operations/skills/artifact-generator/SKILL.md` (v2.28→v2.29). The per-target translation map — the schema every stakeholder rendering is produced from — is:

  ```yaml
  translation_map:
    map_id: <source-slug>--<target-slug>       # e.g., raid-log--stakeholder-csv
    source_ref: <source.artifact>              # the source-definition this map renders FROM
    target_system: <confluence | csv-export | teams | md>
    target_format: <markdown-table | csv | confluence-storage | prose>
    field_rules:                               # per-field include/exclude/rename
      exclude: [<field>, ...]                  # internal-only fields stripped from the target
      rename: { <source-field>: <target-label>, ... }
      include_order: [<target-label>, ...]     # optional explicit column order for the target
    orphan_guard: reject                       # render REJECTS if source_ref has no live source
    render_stamp_field: <Artifact Register column>   # where the render version/date is recorded (drift key)
  ```

  The map is the ONLY rendering path — a stakeholder view is never produced by a bespoke, hand-written export — and `orphan_guard: reject` halts-and-flags any render whose `source_ref` resolves to no live source, so a stakeholder document without an authoritative source behind it is rejected, never silently emitted.
