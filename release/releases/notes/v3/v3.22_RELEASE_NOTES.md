# PROJECT.md gains deliverable-type, org-structure, and team-roster fields, plus five PMBOK templates

2026-06-29 · v3.22

PROJECT.md can now record what kind of thing a project delivers, how its team is organized, and who is on the team — and the platform ships ready-made charter, lessons-learned, change-log, RACI, and stakeholder-register templates to go with them. These are additive schema and template additions: nothing changes for an existing project until you choose to fill the new fields in.

## What changed for everyone using the platform

- **A project can now declare what kind of deliverable it produces.** PROJECT.md gains a `deliverable_type` field — `software`, `governance`, `web`, `data`, `process`, and so on, or any well-formed custom value — separate from how the project is run (`delivery_approach`). *Why it matters:* the platform can tailor its readiness checks to the kind of work being delivered (a software deliverable verified by tests, a governance deliverable by file-state assertions) instead of applying one generic bar.
- **A project can record its team's org structure and roster.** Two new optional fields — `org_structure_type` (functional, balanced matrix, projectized, and the other PMBOK shapes) and `team_roster` (who is on the team, by reference) — let a project state its organizational shape and membership in its own frontmatter. *Why it matters:* org shape and team membership become structured data the platform can read for rollups and routing, rather than free text buried in prose.
- **Five PMBOK artifact templates ship with the platform.** Ready-made project charter, lessons-learned, change-log, RACI, and stakeholder-register templates are now available and wired into the platform's template set. *Why it matters:* you can generate these standard artifacts from a consistent, governed starting point instead of building each one from scratch.

## Known limits

- These are additive schema fields and new templates — no existing PROJECT.md changes until you fill the new fields in, and absence of any new field is valid (a project with no `deliverable_type` on a legacy file is fully conformant). The `deliverable_type` field is required only on newly-scaffolded PROJECT.md files going forward.
- The `team_roster` field holds references only — it points at people recorded in the operator-local roster and never stores names or personal detail in the committed schema file. Names, capability, and allocation are read through the reference, not copied in.
- This release adds the schema fields and the templates; the per-domain readiness guides that `deliverable_type` will eventually select (one guide per deliverable domain) are authored as the demand appears — an unrecognized-but-valid `deliverable_type` is the signal that a guide is wanted, not an error.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:project-data-architecture` label.

## Reversibility

CHEAP / HIGH confidence. Every change is a `git revert`-able addition to schema, template, and reference files; reverting the integration PR restores the prior schema text and removes the new templates in one step. No data migration, no stored-content move, no change to any existing PROJECT.md, no breaking change — the new fields are optional on existing files. Standard rollback window.

### What the new PROJECT.md frontmatter looks like

A project declaring all three new axes — its deliverable domain, its org structure, and a three-member team by reference (no names stored in the file):

```yaml
---
project_name: Vendor Portal Modernization
project_owner: p_okafor_m          # reference to a roster person (ADR-040)
status: ACTIVE
delivery_approach: Scrum
deliverable_type: web              # the new deliverable-domain axis
org_structure_type: matrix_balanced
team_roster:                       # references only — no names, no PII in the file
  - person_ref: p_okafor_m
    role_on_project: Program Manager
  - person_ref: p_singh_a
    role_on_project: Tech Lead
  - person_ref: p_torres_l
    role_on_project: Business Analyst
---
```

`deliverable_type` records *what* is built; `delivery_approach` records *how* it is governed — the two combine freely. `org_structure_type` defaults to `functional` when absent. Each `team_roster` entry is exactly `{person_ref, role_on_project}`: the `person_ref` resolves to a person in the operator-local roster, and the person's name, capability, and allocation are read through that reference — the schema file itself cannot hold a name, so it cannot leak one.

### Operator and engineering detail

**Deliverable-domain axis + ADR-050 (#351 — keystone).** `core/schemas/project-schema.md` gains the first-class `deliverable_type` open-enum axis (recognized classes `{software, governance, web, data, enterprise-platform, hardware, process}` plus the `^[a-z]+(-[a-z0-9]+)*$` open-escape shape, mirroring `delivery_approach: Custom` openness), defined by the new **V13** rule appended off the V12 tail (no existing rule renumbered; required on forward-scaffolded files, optional/conformant on legacy). A disambiguation table fixes the boundary against the other `domain`-named concepts (`work_item_type`, the Stage-4 `domain:` class field — which now reads `deliverable_type` as its authoritative source where present). The new **§5A Domain-Axis Consumption Pattern** in `methodology-parameterization-v1.md` is the domain-axis sibling of §5: consumers branch on `deliverable_type` (what is delivered) orthogonally to `delivery_approach` (how it is governed), reading both independently. Gate criterion **G3-05** is conditioned on `deliverable_type` (gate-criteria-spec schema v1.18 → v1.19, non-breaking — G3-05 keeps its ID/type/check/automation columns; the conditioning adds a domain-conformance lens, never removes the base measurability check). The placement-on-frontmatter + open-enum decision is recorded in **ADR-050** (`Proposed` at authoring, flipping to `Accepted` at the Stage-9 Deep review; registered in `core/ADRs/README.md`).

**Org-structure + team-roster expansion (#262).** Appended off the keystone's post-V13 tail: `org_structure_type` (**V14** — the PMBOK org-shape enum + literal `Custom`; absent defaults to `functional`, documented-not-silent) and `team_roster` (**V15** — a refs-only list of `{person_ref, role_on_project}`). V15-a is the no-inline-PII invariant (closed key-set, no inline name/allocation/Person-or-Resource attribute — the schema cannot hold a roster name, so an accidental commit cannot leak one); V15-b resolves each `person_ref` against the `person_id` anchor (unresolved → BLOCK-WRITE, external → WARN-HEALTH per ADR-040). `team_roster` composes-not-duplicates the people-graph, replaces the free-text `## Key People` prose, and is reconciled against the Stakeholder Register and the frozen Resource entity as three projections of one `person_id`. `delivery_model` was intentionally NOT added — it resolves to the existing required `delivery_approach`.

**PMBOK artifact templates + Trackers 8/9 (#206).** Five PMBOK artifact templates land under `operations/templates/` — project charter, lessons-learned, change-log, RACI, and stakeholder-register (token-placeholder form, no inline PII) — with **Tracker 8 (Stakeholder Register)** and **Tracker 9 (RACI)** schemas added to `core/schemas/tracker-schemas.md` (column-header roles resolve to the same `person_id` anchor as `team_roster`). Registered in `core/governance/OPERATIONS.md` and wired into `core/deploy/deploy.sh` deploy-sync so the templates propagate to Layer 2; template taxonomy/storage updated accordingly.

**3-state-to-PMBOK lifecycle mapping (#371 — foundation).** The new `core/disciplines/lifecycle-tailoring.md` maps the platform's compact 3-state project model (`ACTIVE → CLOSING → CLOSED`) onto the PMBOK five-process-group convention (citing ADR-004), grounding why the 3-state model is a deliberate lifecycle tailoring rather than an omission; three pointers wire it into `core/disciplines/README.md`, `core/CLAUDE.md.template`, and `core/governance/OPERATIONS.md`.
