# The platform adapts its design gate to your method, treats notes as suggestions, and gives the health colours one home

2026-07-02 · v3.48

This release closes out the last three items of two knowledge-corpus cleanup efforts. Three things change: the point where the platform expects design work to happen now depends on which delivery method you have declared (Scrum, Kanban, Waterfall, and so on); a new rule stops an agent from making large destructive changes off the back of a rough note without checking the source of record first; and the colour bands behind project health status now have a single defined home so the same thresholds are not re-stated in several places.

## What changed for everyone using the platform

- **The design-before-build expectation now follows your delivery method.** When your backlog or project declares how you work — Scrum, XP, Lean, Waterfall, PRINCE2, Kanban, or a hybrid — the platform now expects design to be settled at the point that method calls for: design-first before work is sliced for Scrum-style methods, a phase-gate for Waterfall-style methods, and no sprint-slice gate at all for Kanban's continuous flow. *Why it matters:* the readiness check stops applying a one-size expectation and instead matches the rhythm you actually run, so it prompts for design at the moment that fits your method rather than a moment that does not.
- **Notes are treated as suggestions, not orders.** An agent will no longer perform a large deletion or restructure based on a rough note alone — it first checks the note against the authoritative source and confirms with you before doing anything destructive. *Why it matters:* a quick jotting in a scratchpad can no longer be read as a command to cut or rewrite content, so an offhand note cannot trigger a change you did not intend.
- **Project-health colour bands have one home.** The red/amber/green bands behind status reporting (and the "watermelon" green-outside/red-inside idea) are now defined in a single place that other parts of the platform point to, rather than being restated separately. *Why it matters:* the thresholds stay consistent everywhere they appear, so two reports cannot quietly disagree about what counts as green.

## Who this affects

Everyone using the platform sees the notes-safety and health-band changes. The delivery-method design gate matters most to whoever plans and bundles work for release — it only changes behaviour when a delivery method is actually declared; if none is declared, the platform behaves exactly as it did before.

## Known limits

- The delivery-method design gate is advisory (it recommends, it does not block), and it only activates when a delivery method is declared. With no method declared — or a fully custom one — the previous design-activation behaviour applies unchanged.
- The notes-safety rule governs rough operator notes used as if they were authoritative; findings read directly from the platform's own canonical files are unaffected and stand on their own evidence.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**CHEAP / HIGH confidence.** The release adds two decision records, one advisory gate criterion, two cross-reference pointers, and one governance rule; rolling back is reverting the single release pull request and rebuilding the two edited skills. It changes no stored data and adds no blocking gate, so there is nothing to migrate back.

- **Notes-non-authoritative rule + destructive-action guardrail (#1093).** Codified a Universal Preferences bullet in `core/CLAUDE.md.template`: operator-provided notes are directional inputs, not authoritative specifications. Differences between a notes artifact and the corpus render as non-authoritative observations, never as defects the notes must be "fixed" to resolve. An agent MUST NOT perform a gross deletion, mass-restructure, or other destructive change based on simple notes alone — it must first reconcile the note against the authoritative corpus (SSOT) and confirm with the operator. Findings read directly from canonical corpus files are unaffected. This generalizes the intake-boundary directional-not-authoritative handoff principle from formal tickets to informal operator inputs and is the home of the destructive-action guardrail.
