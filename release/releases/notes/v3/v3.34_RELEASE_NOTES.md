# The release pipeline now measures its own delivery and close-out health

2026-06-30 · v3.34

The release pipeline gains canonical self-measurement: the four DORA delivery metrics at the build-and-deploy layer, and Close-class observability (how well each release closes out) at the close layer. Both are defined in tracked schemas, computed by tooling, and recorded per release — so pipeline health is now a measured number instead of a hand-waved impression.

> **Skip the rest** unless you audit the release pipeline's own delivery health or read its telemetry.

## What changed for everyone using the platform

- **The release pipeline now measures itself.** Each release can now report its delivery metrics (how often the platform ships, how long a change takes to land, how often a release needs a fix, and how fast it recovers) and how cleanly it closed out. *Why it matters:* questions about whether the pipeline is healthy or slowing down now have computed answers from the release history, not guesses.
- No new commands, no workflow changes, and nothing breaking for day-to-day skill or project work — this is an internal measurement capability for the release pipeline itself. <!-- impact:foundational -->

## Known limits

- This release instruments only the **build-and-deploy** layer (the DORA-4 metrics) and the **close** layer (Close-class observability). Front- and middle-of-pipeline observability — demand, definition, solution-design, verify, and authorize phases — is deliberately out of scope and tracked for a later release.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. The whole release is additive — new schema documents and new compute scripts, with no change to existing behavior; rolling back is reverting the release PR with no data migration.

### Operator and engineering detail

**DORA-4 instrumentation (anchor).** A tracked schema (`dora-telemetry.md`) defines the four DORA key metrics — deployment frequency, lead time for changes, change-failure rate, and mean time to recovery — at the Build+Deploy layer, and `compute-dora-metrics.sh` computes them from the release history. This is the first-of-kind net-new instrument; it has no prior pattern to extend, which is why the release is classed **novel**.

**Close-class observability.** A second tracked schema (`close-class-telemetry.md`) plus `compute-close-class-telemetry.sh` measures how well each release closes out: retro canonical-form conformance, lessons-learned population, carry-forward closure, and cross-release pattern emergence. Indicators 1 and 2 build against the close-out registers shipped in milestone 62-close-out-registers (#360/#361). The cross-release aggregation tool (Sub-class D) extends `synthesize-release-learnings.sh` to emit `cross_release_pattern_emergence_rate` (Indicator 4), consuming the per-release Close-class rows.

Because this release changes the pipeline's telemetry surface, the per-release record now carries a computed DORA row and a Close-class row. The shape each compute tool emits is, for example:

```
# compute-dora-metrics.sh — per-release DORA row (illustrative)
deployment_frequency      : <releases / window>
lead_time_for_changes     : <merge − first-commit, hours>
change_failure_rate       : <hotfix releases / total releases>
mean_time_to_recovery     : <hotfix lead time, hours>

# compute-close-class-telemetry.sh — per-release Close-class row (illustrative)
retro_conformance              : <pass | fail>
lessons_learned_population     : <count>
carry_forward_closure_rate     : <closed / opened>
cross_release_pattern_emergence_rate : <recurring-signature patterns / window>
```

The first post-implementation release (this one and onward) is where the compute tools produce a populated DORA row and a Close-class row — the success indicator the milestone outcome statement named. No skill or `.skill` package was touched; the change is confined to release-pipeline standards and tooling, plus telemetry-emission citations added to the Stage 6 / Stage 12 / Stage 13 pipeline references.

For full implementation detail see the [RELEASE_LOG.md entry](https://github.com/cody-hutson/pmo-platform/blob/main/release/releases/RELEASE_LOG.md#deployment-log-v3-34).
