# The eval framework is complete — tested refiner scripts, runnable eval sets, and chain-aware QA

2026-07-02 · v3.52

This release finishes the platform's evaluation framework: the machinery that checks whether the pipeline's own agents and skills are behaving correctly. The scripts that run and tune those evaluations now have automated tests, two stage-gate evaluation sets are runnable instead of just drafted, and quality-assurance can now validate consistency across a chain of dependent work — not only each piece on its own.

> **Skip the rest** unless you run or maintain the release pipeline or its eval infrastructure. This release hardens how the platform tests itself; it does not change how you use skills, read status outputs, or work with project artifacts.

## Who this affects

Whoever runs or maintains the release pipeline and its evaluation infrastructure — operators driving a release through its stages, and the pipeline agents that evaluate skill and stage-gate quality. It does not affect people who only consume status outputs or invoke everyday skills; there is no user-visible behaviour change outside the eval framework and the pipeline.

## What changed for everyone using the platform

No user-visible behaviour changes outside the release pipeline and its eval infrastructure. The changes below are for operators and pipeline agents — see the operator detail below.

- **The pipeline can now catch contradictions across a chain of dependent work before final review.** Quality checks used to look at each piece of work only against its own acceptance criteria; two linked changes could each pass on their own yet contradict each other and slip through to Plan Review. QA now validates the chain for mutual consistency earlier. *Why it matters:* inconsistent chained outputs are caught while they are still cheap to fix, rather than surfacing at the final gate or after a release ships.
- **The framework that tests the platform is itself now tested and runnable.** The eval-tuning scripts gained automated test coverage, and two stage-gate evaluation sets moved from drafted to runnable. *Why it matters:* the safety net the pipeline relies on is now trustworthy — a broken eval script or an un-runnable eval set can no longer pass silently.

## What you need to do

Nothing. There is no setup, no migration, and no user-facing behaviour change. One follow-up — wiring the new script self-tests into continuous integration — is tracked separately (see the follow-up in the References below) and needs no action from you.

## Known limits

- This is a QA and eval-infrastructure release scoped to the pipeline's own evaluation framework. It adds test coverage, eval-asset files, and pipeline-doc rules; it deploys no new skill and changes no stored project data.
- The new refiner script self-tests run on demand but are not yet wired into continuous integration — that wiring is a tracked follow-up, not part of this release.
- Calibration-data aggregation for one eval extension is recorded as a dated deferral in the stage-gate eval index (per the acceptance criteria of the eval-extensions work); it is intentionally out of scope here.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH confidence.** The whole release shipped as one branch and one merge, so rolling back is reverting the single release pull request (`git revert -m 1 6a647c6493b68688d8ee3fcb7dbbf0505b01c699`). It adds test coverage, eval-asset files, and documentation only — no stored data, no runtime blast radius outside the eval framework — so there is nothing to migrate back.

### Operator and engineering detail

See the `#83-eval-framework-completion` RELEASE_LOG row for the raw audit trail. `novel` release class — the bundle adds new eval-asset files and carries release-specific design decisions (the eval-set home, the chain-QA activation posture). Four issues shipped as one coherent capability — *complete the eval framework* — on one branch / one PR (#3060, `--merge` at `6a647c6`). All four cards were verified genuine-open against the live tree at intake; each inherits its design from the eval-infrastructure epic (#325) and does not restate it.

- **Chain-aware QA integration-testing layer (#209).** The pipeline ran QA per-issue: each spoke validated one PR against its own acceptance criteria (unit-level), and integration across a dependency chain was only approximated by the hub injecting cross-issue context into spoke prompts — which evaluates *recommendations*, not whether the *content* of chained outputs is mutually consistent. This adds integration acceptance criteria at Solutioning and a chain-aware layer at Plan Review, so contradictory chained outputs (e.g., a table's values in one issue inconsistent with a permissions table in its upstream) are caught before Stage 9. Touches `stage-05-solutioning.md`, `solutioning-output-template.md`, `stage-07-dev-testing.md`, `stage-09-plan-review.md`, and `hub-spoke-bridge.md` (Option-A activation).
- **Stage-3 Bundle eval set authored into the live eval home (#279).** Encoded the drafted 11-eval Stage-3 Bundle set (4 structural · 2 contract · 4 principal-behavior · 1 proactivity) into a runnable `evals.json` under `core/skills/eval-writer/evals/stage-gates/stage-03-bundle/`, with an escape-rate metric, plus the stage-gates `README.md` and a Stage-07 eval set. The original draft targeted a legacy `pmo-platform/engineering/evals/eval-sets/` path that does not exist in the current modular structure; the live eval home is the per-skill / stage-gate pattern under `core/skills/eval-writer/`, and the resolved home is codified by **ADR-067** (`core/ADRs/ADR-067-stage-gate-eval-set-home.md`).
- **Eval-framework extensions for the refiner (#199).** Three independent eval-infrastructure extensions: a Stage-07 **branch-freshness assertion** (`assert_branch_fresh.py` — asserts `git log --oneline origin/main ^HEAD` is empty, failing with the unreachable commits listed); a second `run_eval_audit.py` regex branch so the audit covers the **`phrases like`** trigger-description format in addition to `Triggers:` (via `improve_description.py`); and calibration-data auto-aggregation, which was **dated-deferred** per the card's acceptance criteria and recorded in the stage-gate eval index rather than shipped here.
- **Hermetic unit tests for the preserved refiner eval scripts (#367).** Added `test_eval_scripts.py` covering the testable pure functions of the three preserved eval scripts at `release/skills/pmo-skill-refiner/scripts/` — `run_eval.py`, `run_loop.py`, and `run_eval_audit.py` (the sibling `test_scaffolder_drift_guard.py` exercises only the scaffolder guard, not these three). The scripts already existed (they shipped with the pmo-skill-reference-substrate work), so the blocking dependency was satisfied. Wiring both self-test suites into CI is a tracked follow-up (see References), not part of this release.
