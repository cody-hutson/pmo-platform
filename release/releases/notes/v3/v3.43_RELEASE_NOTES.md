# The platform's automated pipeline spokes get five new safety guardrails

2026-07-01 · v3.43

The platform runs parts of its release process through automated helpers called "spokes" — each one is spawned to do a slice of work (design a solution, run a check, commit a corpus update) and then reports back. This release closes five ways a spoke could previously go wrong, making each one impossible by construction rather than something to remember to avoid. A spoke can no longer build from a stale copy of the issue it was launched to work on, start commit work when no signing key is available, be blocked by a mis-configured safety hook, change directory into the operator's own working copy, or run outside the security-hook net. None of this changes any project-facing workflow — these are guardrails on the platform's own automation.

## What changed for everyone using the platform

- The platform now checks an issue's stated facts against reality at the moment a spoke starts, and produces a structured drift report when they no longer match. *Why it matters:* work no longer gets built from a stale issue body that has silently fallen out of date, and when something has drifted you get a clear, itemized report instead of a surprise later. <!-- impact:foundational -->
- Before the platform starts any automated step that has to make a commit, it now confirms a signing key is actually loaded first. *Why it matters:* the platform no longer spawns a helper that does its work and then fails at the very last step because commits must be signed and no key was available — which previously wasted the whole run and left a half-done release action.
- The automation-safety hook that guards against destructive commands now recognizes the correct project-repository path for automated work. *Why it matters:* a latent gap is closed before the stricter "block, don't just warn" enforcement mode is switched on, so legitimate edits from an automated session are not wrongly blocked once that happens. <!-- impact:foundational -->
- The rules that govern automated spokes now forbid them from switching into, or writing to, the operator's primary working copy, and add a session-start guard against a non-code session accidentally starting a work branch on the platform repository. *Why it matters:* automated work stays isolated in its own workspace and cannot disturb the operator's checkout.
- A decision record now settles that when the canonical specification and an issue's description disagree, the specification is authoritative and the issue body is treated as historical record. *Why it matters:* there is now one clear, cited rule for which source wins, so automated work stops re-litigating it case by case. <!-- impact:targeted -->

## About the drift report

Because this release adds a new structured drift report, here is the shape of a single report row so its format is on record. Each checkable claim in an issue body produces one row with four fields:

```yaml
drift_class:  state-lifecycle        # closed set: state-lifecycle | population-count |
                                     #             milestone-description | currency-reconciled-upstream
body_claim:   "the issue's claim, exactly as written"   # read-only; never rewritten
current_state: "the value actually observed live now"   # from a live read of the real state
gap_age_days: 12                     # days between when the claim was written and now
```

An empty report is the normal, healthy signal — it means nothing has drifted. A non-empty report routes each drifted claim to one of two dispositions (interpret the design against the live value, or escalate for the operator to decide), and the automated helper never edits the issue body itself.

## Known limits

- The signing-key pre-flight and the no-wander-to-primary rules govern how the platform spawns and runs its own automated spokes; they do not change anything for someone using the platform on project work.
- The safety-hook correction and the session-launch guard ship their first layer this release; a further layer of runtime enforcement follows once the related install-and-config-safety work lands separately.
- One deliberately optional helper script for the drift check was left out of this release; the drift-report step and its rules are the delivered capability and do not depend on it.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH confidence.** Five of the six changes are additive documentation, specification, and decision-record edits; rolling the release back is reverting the single release pull request. The one change that carries more weight is the edit to the executable automation-safety hook: the revert is still clean, but if a wrong configuration had shipped while the stricter enforcement mode was already on, automated edits could have been blocked in the interim — which is why the hook fix was deliberately sequenced to land before that enforcement is switched on.
