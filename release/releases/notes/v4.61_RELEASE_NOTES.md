# Governance documents stop describing the platform from memory

2026-09-11 · v4.61

Four platform documents were describing behaviour that had changed underneath them, and one of them actively instructed a step the current rule forbids. Each now names the rule or the live mechanism it depends on, so a reader is pointed at something that can be checked rather than at a description someone wrote once.

## What changed for everyone using the platform

- **The release protocol no longer tells you to file release notes in the wrong place.** It described a folder layout that the current notes rule had replaced, and one sentence directed a future release to create subfolders that are not allowed. *Why it matters:* following the protocol exactly as written would have put a release note where nothing looks for it.

- **A pipeline step now asks for a value its own checker recognises.** The solutioning stage told authors to record a design's source as a descriptive phrase, but the checker that reads that field accepts only a short set of named forms — so the phrase was read as no source at all. *Why it matters:* anyone who followed that step landed on a value that failed the very check the step exists to satisfy, and only found out by being rejected.

- **A readiness check that reports "clean" now says what makes that safe.** One of its states could return a clean verdict without consulting merge state, and the specification recorded no reason why that was sound. *Why it matters:* a clean verdict you cannot interrogate is hard to tell apart from one that simply did not look.

- **The intake desk no longer claims that nothing watches issue creation.** A control does match that command and read what it sends; the skill said none did, in six separate places. Each corrected sentence now names that control, states which mode it ships in, and says plainly where it is not loaded at all. *Why it matters:* the old wording told you a safety net did not exist when one partly does — and a claim that names a specific control can be checked, where a blanket "nothing does" cannot.

## Known limits

Everything in this release is prose. No running behaviour changed, and no setting, file format or command was altered — so nothing needs doing on your side.

Four findings surfaced while this work was in flight and were filed rather than folded in, because widening a release mid-flight is the habit this discipline exists to prevent:

- **#7399** — three sentences in the intake desk are right in their conclusion but give the wrong reason for it. Correcting the reason is a different question on a different axis, with its own unmeasured surface to establish first.
- **#7412** — the release protocol names a snapshot folder that does not exist in this repository, at five places, two of them instructions rather than descriptions. It is the same defect shape as the one fixed here, found in the same file while fixing it.
- **#7411** — the source grammar this release taught the solutioning stage to follow cannot accept a template file's path, so an author citing one of the platform's canonical templates still lands on an unrecognised value. Whether that exclusion is deliberate belongs to the grammar's owner to say.
- **#7414** and **#7415** — two checks that were fully cleared in earlier releases have accumulated new findings since. The clearing works; something upstream keeps re-introducing what it clears, and draining a third batch by hand would not change that.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**CHEAP**, confidence **HIGH**. Reverting the merge restores all seven changed files exactly as they were; the one rebuilt skill package would need regenerating alongside it. The version tag is retained either way, as the record that this version was claimed. The document that one of these fixes touches is protected against agent edits in both directions, so its reversal is an operator action.

### Operator and engineering detail

Raw audit detail sits on the `v4.61` row of the release log, anchor `#governance-pointer-fixes`.

**The release found one shape four times.** Each card arrived as an unrelated staleness, and each resolved to the same failure: a document asserting something about a mechanism it does not own, with no pointer back to the owner. That is why the fixes are not simply corrections — the protocol's layout sentence now *cites* the standard that superseded it, the solutioning step *names* the form and defers to the stage that owns its grammar rather than restating it, the readiness specification *names* the two mechanisms its state-4 verdict rests on, and every corrected intake sentence *names* the control it asserts coverage for. A correction that merely stops being wrong can silently go wrong again; a correction that cites its owner cannot.

**A gate posture was inherited four times and re-measured once.** The package-freshness check graduated from logging to blocking six days before this release entered planning. The Stage-4 risk register and the Stage-5 design note both recorded the older posture, and every actor downstream inherited the claim and restated it rather than re-reading it. The independent reviewer, carrying no shared context, is what caught it — and the consequence was concrete: the rebuilt package had to land in the release pull request itself rather than at the cut, or the pull request would have been unmergeable. The risk register entry was inverted in the deviation log rather than quietly amended.

**An enumerated repair list was treated as a ceiling, and the plan said so before it happened.** One card's acceptance criterion named two sentences to fix. A whole-file sweep over both files found six occurrences across at least three sites, two of them outside the section the card described. The criterion was re-scoped at planning to *every* occurrence, verified by whole-file count rather than by the two named lines, and the fix was applied by matching the exact sentence text and working upward through the file — because the design's own first edit invalidated every line number it had recorded for the later ones, and one prescribed range enclosed a clause it meant to preserve.

**A count-shaped sweep could not see an instruction-shaped rule.** The earlier cascade that introduced the closed source grammar swept on the phrase naming how many legitimate forms there were. The solutioning step states the same rule as an instruction and names no count, so the sweep was structurally blind to it. The section now carries a note saying so, which is the part a future cascade can actually act on.

**The published release page was created at close, not at deploy.** The deploy stage's publish step ran and correctly declined: the page's body must be the exact text of the in-repo note, and the note is authored here, one stage later. Publishing a placeholder would have violated the rule a separate check audits afterwards. This close created the page from the finished note, then verified both that every annotated tag has a matching published page and that the published body matches the note byte for byte.
