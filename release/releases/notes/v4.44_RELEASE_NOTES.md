# Skills stopped citing things that were never there

2026-08-30 · v4.44

Several skills had drifted away from the surfaces that describe them. One told you to run six checks that resolve to nothing and pointed at a section that does not exist. Another was named as the sole owner of a work-state machine it never once referenced. Two promised guides had never been written. And installed skills quietly fell out of step with their source after every merge, because updating them was a manual step documented as manual.

> **Skip the rest** unless you use a skill's written instructions, or you install skills from this repository.

## Who this affects

- Anyone following a skill's step-by-step instructions and finding the referenced check or section missing
- Anyone whose installed skills have silently diverged from the repository since their last merge
- Anyone who expected security or data guidance and found a placeholder

## What changed for everyone using the platform

- **Instructions point at real things.** One skill told you to run six checks that resolve to nothing and pointed at a section of itself that was never written; both are gone. *Why it matters:* following the written steps no longer dead-ends on a check ID you cannot look up.

- **The skill named as owner of the work-state machine now actually references it.** It was named the sole maintainer of that machine while mentioning the field in none of its twelve files. It now recommends a transition and names the label. *Why it matters:* the skill that documentation says owns your work states finally behaves as though it does — and it recommends rather than silently writing, so the decision stays yours.

- **Security and data guides exist.** Both were promised, cited as sources, and never written; two placeholders sat where the guidance should have been. *Why it matters:* if you went looking for security or data guidance and found a stub, it is now real content you can act on.

- **Installed skills update themselves after a merge.** Deployment was a manual step documented as manual, so an installed copy drifted from its source every time someone forgot. *Why it matters:* the skill you run is the skill in the repository, without you having to remember a step.

- **Chained invocation accepts both formats.** The contract admitted only the older `key=value` form even though the JSON form was already being emitted. *Why it matters:* a correctly-formed JSON call is no longer rejected, and existing `key=value` callers keep working unchanged.

## Known limits

- **Package-freshness enforcement is NOT switched on.** This release supplies only the data prerequisite. Turning it on additionally requires a branch-protection change that lives outside this repository and is owned by no part of this work. Do not read this release as having enabled it.
- **The runner-resolution check runs at deploy time only, in warn mode.** A declaration that stops resolving is caught when you deploy, not when you open a pull request.
- **Seven grading instruments were found to be broken** while checking this work — four reject correct work, three accept incorrect work, and every one passed its own self-test. They are recorded, not repaired. Nothing here depends on them, but reviews elsewhere may.
- **One skill is now one edit away from a silent break.** `tracker-manager` retains a single occurrence of the older invocation marker, and no check guards it. Tracked as #6410.

## Reversibility

**MODERATE.** Five of the six changes are documentation and governance edits that revert with the merge. The exception is skill deployment: it installs a local git hook, which is machine-local state that reverting this release does not remove. Backing that out means deleting the hook on each machine where skills are installed. No data is destroyed and no external system is touched.

### Operator and engineering detail

All six work items passed dev testing and QA acceptance, six of six, with no conditional or rejected verdicts. Continuous integration ran 74 checks with no failures at the merge commit.

Worth recording plainly: no CI had run on this branch at all until its pull request was opened, because the workflows trigger on pull requests and on pushes to the default branch, and a release branch with neither matches neither. The first run caught two blocking failures on work that had been ungated for the whole release. Both were fixed before merge. The lesson is not that the checks failed; it is that opening the pull request is what made any check possible, and it should not be treated as a formality at the end.

The pre-existing `--check` findings were measured against a baseline pinned before any work landed and were unchanged: two, both in files this release does not touch.
