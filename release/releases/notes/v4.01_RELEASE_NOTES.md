# The session learning retro can now actually run

2026-07-30 · v4.01

A background check that was meant to capture a lesson at the end of each working session could never run — it was looking for information the platform does not give it. That is fixed, and it stays switched off until you decide to turn it on.

## Who this affects

- Anyone who has turned on, or is considering turning on, the automatic end-of-session learning retro. It remains off by default and nothing changed for anyone who has not.

## What changed for everyone using the platform

- **The automatic session retro can now run at all.** It was checking two pieces of information the platform has never actually sent it, so it read "nothing happened" for every session and skipped every one, no matter how it was configured. It now measures a session from the session's own record. *Why it matters:* if you had switched this on expecting a lesson to be captured at the end of your sessions, none ever were — and now they can be.
- **It re-checks as the session grows instead of deciding once at the start.** The old version made its call on the very first exchange — always the least representative moment of a session — and then stuck with it. *Why it matters:* a session that starts trivially and turns substantial is now recognised as substantial.
- **It is honest about when it runs.** It runs at the first point a session becomes big enough to be worth recording — not at the literal last message, which nothing can identify while a session is still going. The setting's own description now says exactly this. *Why it matters:* you can predict when it will fire instead of being surprised, and the setting no longer promises something impossible.
- **Turning it on is now three steps, not two.** Switch it on, let it watch a few real sessions until it has recorded at least one "I would have run here", then let it run for real. *Why it matters:* the middle step is now enforced rather than suggested — skipping it does not interrupt your session, it just records that the watching period is not finished yet, so you can see why nothing happened.
- **The "how many turns" setting means what it says.** A turn is now one exchange with the assistant. It used to count the individual pieces a single reply is built from, which inflated the number by an inconsistent amount from session to session. *Why it matters:* a threshold of 12 turns now means 12 exchanges, and it means the same thing in every session.
- **The decision health-check has a decided home.** The planned capability that reviews how release decisions get made will be built as a new mode of the existing quality-audit skill, rather than as a separate skill. *Why it matters:* nothing to use yet — but the work can now start, and it will show up somewhere you already know rather than as another skill to learn.

## Known limits

- **Nothing was switched on by this release.** The retro ships off (`enabled = false`) and in non-interrupting mode. No session behaves differently until you deliberately change your own settings file.
- **The decision health-check itself is not built.** Only its home is decided. The capability and its coverage scorecard are deferred and stay open for a later release.
- **One safeguard is only partly in place, deliberately.** A check that stops malformed entries from polluting the cross-session learning log only catches the one specific spelling the documentation defines. Other spellings still get through, and most of those quietly discard a real pattern rather than inventing a false one. It is recorded as an open condition rather than treated as finished, and it must be closed before the retro is allowed to interrupt a session. The immediate risk is nil: nothing is writing to that log today.
- **The watching period before the retro can interrupt can currently satisfy itself.** It accepts the entry it writes when it declines to run, so a determined operator could reach the interrupting mode without a genuine watching period. A one-line fix is named.
- **How long the release took to deploy is still not measured.** Nothing in the pipeline reports it yet, so that field reads "not available" for this release as it does for every recent one.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `cluster: pipeline-definitions` label.

## Reversibility

CHEAP / HIGH confidence. Reverting the integration commit reverses everything in this release: the retro returns to its previous unable-to-run state and the recorded decision returns to being an open question. Because the retro ships switched off, no live behaviour is being rolled back and no settings file of yours is touched either way. Standard 7-day rollback window.

### Operator and engineering detail

**The two defects, and why a passing self-test hid them.** The sampling predicate read `tool_call_count` and `turn_count` — fields the `Stop` payload has never carried — so a fail-quiet missing-key path mapped both to 0 and the shipped `almost_all` default evaluated `0 < 12 AND 0 < 4` to skip, on every session. Independently, the once-per-session sentinel was written on the *skip* path while the guard exited on any later `Stop`, freezing the predicate at turn 1. Both survived a green `--self-test` because that test exercised `should_run` as a pure function, drove the hook once, and supplied a fixture carrying the very fields the real payload omits — a test built from the code's own premise cannot falsify that premise. The repair pins the payload contract at `core/hooks/tests/fixtures/stop-payload.json` and asserts the two invented keys are **absent** as a negative control; the extended self-test drives the real script across a 3/1 → 9/3 → 40/12 → 95/28 sequence against a real growing transcript, and was independently verified to have the power to fail.

**The `turns` redefinition is a semantic change, ratified at Stage 7.** `turns` now counts distinct request identifiers rather than assistant-role transcript entries. The transcript records one entry per content block, so an entry count inflates the true turn count by a factor measured between **1.46× and 5.32×** across session shapes. Because the factor is not constant, the old quantity was not comparable between sessions, so `min_turns` could not mean what its own setting reads. The durable argument is semantic, not magnitude.

**Two PARTIAL acceptance conditions are carried on the record, not waived.** PA-4: the write-side label gate rejects a stray label on exactly one of the 94 printable-ASCII separators a payload can carry — `;`, the documented segment grammar. Of the remaining 93, **30 inflate one real cluster into three and 63 destroy the genuine `theme` token outright**, so the majority failure mode is the *opposite direction* from the one the criterion named. Its closure is a `theme:`-scoped write-side shape assertion, validated to discriminate against the whole known population (0 of 4 live corpus `theme:` values rejected; the same rule on `learning:` values rejects 12), which deliberately avoids the generic read-side broadening that would endanger the intentional prose-colon case. PA-6: the warn-window gate exists and has power, but its whole-line match self-satisfies on the degrade row it writes itself; graded non-blocking because the Stage-5 operator decision operationalised it as a fixed internal floor of ≥1 would-fire verdict, which is delivered. Both residues are now recorded in `pipeline-event-log-schema.md` as acceptance conditions rather than left implicit.

**Two false property claims were corrected as authorized additional scope.** The schema asserted that both tools assert their static label fallback against the recognized-label table bidirectionally, and that the read side discards unrecognized-label content so already-written rows cannot keep leaking. The first is false for the read side — its label set is a static literal never checked against the table, so a read-side drift passes `--self-test` silently. The second was falsified directly by the acceptance evidence. A governance file asserting two properties the code does not hold is the exact drift class this release exists to close, so both were corrected here rather than deferred. Documentation-only, no behaviour change.

**The recognized-label registry is now single-sourced, and this is the shape contract the release changed.** The schema table is the sole authority; the write-side tool parses it and rejects any other segment-opening label at emit time. One entry of the emission grammar the gate now enforces:

```
theme:over-building; learning:the fix is to do less; session:s6
                   ^                               ^
                   segment boundary is ';' — a label after any other
                   separator opens no segment, so it is swallowed into
                   the preceding field and tokenized as signal
```

**Host decision (ADR-103).** The decision-audit capability hosts as `pmo-qa-auditor` **Mode J — Decision-Health Audit**, sibling to Mode I, not a net-new specialist skill. The determining argument is a rule rather than a balance of cost: the skill-boundary test requires all three conjuncts together for a net-new specialist, and conjunct 3 (distinct primary role) fails — Mode J and Mode I occupy the same primary role, a retrospective cross-release audit against corpus-defined oracles emitting the six-deliverable review set into a dated analysis folder. The size objection against growing the largest SKILL.md in the corpus is refuted on governance rather than outweighed: the canonical structure standard states the line and byte values are triggers, not caps, and a skill crossing one while carrying a non-empty `references/` subtree is compliant however far it exceeds the trigger. Three constraints are stated in the mode body rather than deferred: the oracle set is derived and pinned per run with a bounding control that reports `INDETERMINATE` on a degenerate probe; a seam with zero evidence rows reports `no-evidence`, never a passing grade; and the window orders by merge anchor, never by version number. The when-to-run authority lives in `release/references/protocols/decision-audit-cadence.md` beside the three existing audit cadences, and the four-protocol cadence cascade was applied.

**Both ADRs remain `status: Proposed`.** ADR-087 gained Consequences prose only (the activation-class obligations) with its `status:` line byte-unchanged on both sides of the diff; ADR-103 ships `Proposed` by design. Ratification is an explicit operator act and is never inferred from a milestone reaching close-out.

**Scope that did not ship.** The capability build and its coverage scorecard were bundled and parked on a dependency milestone, and are deferred at this close rather than closed — they stay open for next-cycle re-triage. Their unpark gate is now met on two of three conjuncts (the host decision landed here; the instrumentation stories landed in `decision-telemetry-emission`), leaving only a status transition. Against the milestone's Release Outcome Statement this release is therefore **partially attained**: the learning-loop clause is delivered, the repeatable-health-check clause is not.
