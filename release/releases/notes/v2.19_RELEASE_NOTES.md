# Co-management cleanup: the legacy setting is retired, and the dual-framing rule lives in one place

2026-06-22 · v2.19

This is a cleanup release that finishes what v2.18 started. v2.18 renamed the co-management setting to `dual_framing_enabled` but kept a compatibility shim that still read the old name; v2.19 **removes that shim** and tidies up the last places the old, operator-specific naming lingered. Dual Agile/Waterfall status framing still works exactly as before.

> **Skip the rest** unless you have a project file that still uses the *old* co-management setting name, or you maintain the platform's governance docs.

## Who this affects

- **If any of your `PROJECT.md` files still use the pre-v2.18 co-management key**, you need a one-line rename (below). Projects already on `dual_framing_enabled` — and projects that don't use co-management at all — need no action.

## What changed for everyone using the platform

- **The legacy co-management setting is no longer read.** Through v2.18, a compatibility shim accepted the old key and treated it as `dual_framing_enabled`. That shim is now retired. *Why it matters:* a project file still on the old key would silently stop activating dual-framing — so rename it (one line, identical on/off meaning). See "Action required."
- **The co-management integration fields are renamed** to `co_management_smartsheet_id` / `co_management_sharepoint_folder` — the operator-agnostic naming, completing the v2.18 rename. *Why it matters:* if a project file sets these integration fields, update the two key names alongside the setting rename above so co-management keeps resolving them.
- **The "Dual-Framing Bridge" rule now lives in one place.** It had been duplicated in the workspace director (`CLAUDE.md`) and in `OPERATIONS.md`; the redundant copy is removed so the two can't drift apart again. *Why it matters:* behavior is unchanged — but single-sourcing the rule is what prevents a stale copy from lingering, which is exactly what had happened before this release.

## Action required

If a `PROJECT.md` still carries the **pre-v2.18 co-management key**, rename that one line to `dual_framing_enabled` (the on/off value is unchanged). Re-running the platform's `update.sh` re-renders your workspace `CLAUDE.md` from the corrected template — your project settings and any personal additions are preserved.

## Reversibility

CHEAP / HIGH confidence. The change is a shim removal + a rename + a de-duplication — no data migration. Reverting the release merge restores the shim. The only thing to migrate is a project file that still used the old key — a one-line rename, the same edit in either direction.

### Operator and engineering detail

**Scope — two issues, one theme.** **#1846** retires the legacy co-management deprecation shim (the `project-initiator` Step-1 logic, the `project-schema §7` contract, and the "accepted via shim" clauses in `OPERATIONS.md` ×2 and the methodology specs), genericizes the residual K4 field names to `co_management_*` (`OPERATIONS.md` ×2 config block + `c3-external-sync-path-b.md`, with the inline gate label and the failure-mode root-cause quote reworded), and finishes the v2.18 rename (the remaining stale legacy-key references → the current `dual_framing_enabled` in the config template, failure-mode examples, and regression-check strings). **#1853** single-sources the **Dual-Framing Bridge** rule in `OPERATIONS.md § Dual-Framing Bridge` — removing the redundant `core/CLAUDE.md.template` copy and repointing the 7 citations (`project-schema.md` ×5, `applicability-framework.md` ×2). The drift that motivated #1853 surfaced during #1846: v2.18 updated OPERATIONS.md + the schema but left the CLAUDE.md copy stale — the textbook `duplicate-source-discipline` failure.

**Why a minor, not a patch.** Retiring a documented back-compat shim is a contract change, so v2.19 is a minor release (not a patch on v2.18). All three live `PROJECT.md` files carrying the legacy key were `false` (co-management off), so removing the shim is behavior-neutral in practice; the 3 operator-local files were migrated to `dual_framing_enabled: false` alongside the release.

**The residual.** After v2.19, the legacy key survives in the public corpus only as a single terse `project-schema §7` migration breadcrumb (so a downstream installer knows what to rename) plus the frozen `release/tools/tests/` fixtures (historical issue-body quotes). The `.skill` binaries rebuild from the renamed source at deploy.

**Discipline.** The `project-initiator/SKILL.md` edit followed `pmo-skill-editor` Mode A (impact + coherence + regression; the dual-framing self-test entries were updated, not orphaned). The XC-06 dual-framing regression check is intact and binds `dual_framing_enabled` in both byte-paired copies. No gate or test enforced the shim's existence (verified before removal). `OPERATIONS.md` ×2 and `regression-checks.md` ×2 were kept consistent.
