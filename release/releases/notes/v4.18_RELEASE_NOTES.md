# Background sessions get their own workspace and a capacity check

2026-08-08 · v4.18

When the platform runs work in parallel background sessions, each one now writes into its own folder and is checked against the remaining usage window before it starts, so one session can no longer pick up another's leftover file and no session begins work it has no room to finish. Six further fixes make the release machinery report what it actually did rather than what it was assumed to do.

## What you need to do

Only if you want the new edit guard active. It ships wired but switched off, and three steps you run yourself turn it on. Nothing else in this release needs any action from you.

1. Register the platform's security hooks in your own user-level settings file (`~/.claude/settings.json`) from the template this release ships.
2. Turn on the security-hook master switch (`[security_hooks].master_enabled = true`). **This activates all six workflow-class hooks at once, not just the edit guard** — read what the other five do before you flip it.
3. Set the edit guard itself to enforcing (`block-skill-direct-edit` mode `enforce`). Until this step, it is present and inert.

## What changed for everyone using the platform

- **Parallel background sessions can no longer read each other's leftovers.** Each session is now bound to a single run folder when it reads as well as when it writes, instead of only when it writes. *Why it matters:* a result posted to the wrong place because one session picked up a file another session left behind is no longer possible.

- **Every background session is checked for remaining capacity before it starts.** The check that used to run only when several sessions launched together now runs on a single launch too. *Why it matters:* a session no longer starts work it cannot finish and then stops partway through having produced nothing.

- **There is now a command that refreshes just the generated files.** `update.sh --surfaces-only` regenerates the managed sections of composition surfaces and touches nothing else. *Why it matters:* healing one stale list no longer costs you a full update, and the older instruction to use the deploy command for this was pointing at something that could never do it — the deploy command now says so plainly instead of exiting quietly with nothing done.

- **The action-item vocabulary and the template that seeds it now agree.** Three lists that had drifted apart were reconciled to the standard that defines them, a seventh category was added for a decision that has been set aside rather than merely unannounced, ledgers already written in the old words stay readable through a lookup table, and a new check holds the two in step. *Why it matters:* a commitment written in one vocabulary and read in another can slip through the release-close check that exists to catch it — that gap is closed, and it cannot silently reopen.

- **Release-tag rules are written down, and the recovery runbook no longer tells you to do something that will be refused.** The rule the repository already enforces — version tags are kept, not deleted — is now a decision record, the rollback steps that told you to delete a tag were corrected, and the cleanup tool checks the repository's own policy before offering to remove anything. *Why it matters:* you will not be handed a step that fails mid-rollback, at the exact moment you have least time to work out why.

- **A test that reported success while skipping its strongest check now reports the skip.** The blast-radius suite used to fall back to a pass when its recovery step produced nothing, so its before-and-after comparison quietly stopped running while the suite still looked green; it now reports a skip, and a strict mode treats that skip as a failure. *Why it matters:* a green result now means the check ran, not that it declined to run.

## Known limits

- **The edit guard for background sessions ships wired and inert, and has not been observed working.** This release connects the enforcement point and states exactly what it does and does not cover; it does **not** claim the guard has ever blocked an edit from a background session. That proof is specified precisely enough to run and is deliberately deferred until after the three steps above are done — it is not waived, and the release's own records say so rather than grading an unswitched-on control as satisfied.
- **Turning on the master switch turns on more than the edit guard.** It activates all six workflow-class hooks together; there is no per-hook master switch.
- **An orphaned version tag from an earlier release is still present.** The repository blocks its deletion and this release does not remove it — the decision record explains why keeping it is now the stated rule rather than an unwritten one.
- **The action-item vocabulary check compares the standard and its template only.** Ledgers already written are read through the lookup table rather than rewritten, so an old ledger keeps its old words.

Report issues at [github.com/cody-hutson/pmo-platform/issues](https://github.com/cody-hutson/pmo-platform/issues).

## Reversibility

MODERATE / HIGH confidence. The file changes come out in one operation by reverting the release merge commit. Two carve-outs are recorded in the release plan's rollback section and are the reason this is not CHEAP: the reverted state leaves the three operator-run settings changes in place if they have already been applied, and those are workspace state rather than repository content, so each must be undone by hand. Rollback is operator-authorised; nothing rolls back on its own.

### Operator and engineering detail

**The through-line for the whole release is one shape: a control that is claimed but never exercised.** An allowlist nothing enforced on the path where close-out actually runs. A standing remediation nobody could execute, because the command it named cannot read the manifest it would have to read. A category enum a runtime template contradicted on three of six values. Worked examples showing the pre-change decision-item shape for a contract that now requires a reversibility field. A test emitting a pass where it meant a skip. A tag-retention rule the host enforced and no document recorded. In each case the remedy was the same — make the control either produce a real verdict or say plainly what it does not cover. The release deliberately does not grade the one control it could not exercise.

**The spawned-session enforcement point ships wired but unproven, by decision rather than by omission.** The Edit- and Write-class guards now route through a shared scope guard the block hooks call, with tests for the guard and a separate test asserting the wiring is present. What the release does not have is a negative-control arm run from an actual spawned session. Two blockers stand in front of that arm, not one: the operator-executed precondition set above, and an auto-mode permission classifier that fires upstream of the hook layer and denied even an allowlisted read-only control non-deterministically. The deferral was originally accepted on a one-blocker understanding; the corrected two-blocker shape is in the shipped tree and the probe document no longer describes the negative control as executable. See [ADR-128](https://github.com/cody-hutson/pmo-platform/blob/main/release/ADRs/ADR-128-version-tags-are-retained-not-reaped.md) for the sibling decision on tag retention, which followed the same "codify what is already enforced" reading.

**The action-item category enum expanded from six values to seven, and the runtime template was re-derived from the standard rather than the reverse.** The template had diverged on all three restated enums (`category`, `trigger_type`, `status`); the standard's values won because they are load-bearing — the field-semantics row, the routing-point bindings and the briefing format are all written in that vocabulary, while two of the template's divergent values appear nowhere except the new alias table, as values being read. Existing ledgers are not migrated: a read-time alias table maps the historical values, and every alias is verdict-neutral at the release-close gate. `decision-deferred` carries a `created_at` time-scope rider, because the word meant `decision-to-post` before this revision and means the declared-deferral form after it. Parity between standard and template is now held mechanically by a new deploy check. The shipped enum:

```
category: 7 values (was 6)
  deferred-edit       a file edit deferred to a later trigger point
  reminder            a note to surface at a future routing point
  cleanup             a removal or tidy-up obligation
  decision-to-post    decision rendered; only its announcement is deferred
  cross-issue-merge   gated on another item's resolution
  verification        confirm an executed action produced the expected state
  decision-deferred   NEW - decision surfaced but not yet put to the operator
```

**The blast-radius card was re-scoped away from the defect it was filed for.** The intermittent empty-JSON failure it named had already been fixed by a prior change; that change introduced a worse defect in its place — a fallback emitting a pass where it meant a skip, so the strong before-and-after assertion stopped running while the suite reported green. The card was re-pointed at that. The strong assertion is now anchored on a committed fixture whose golden digest was re-derived rather than adopted from the failing state.

**Worked examples in the bridge document were reconciled with the decision-item contract they illustrate**, so the shape a reader copies carries the reversibility field the contract requires rather than the pre-change shape.

**The composition-surface refresh gap was a late Stage-5 addition and turned out to be an upstream dependency of the enforcement work**, not independent scope: shipping enforcement over a refresh path that structurally could not run would have enabled a control whose remediation was inoperative. A new regression suite covers that path and is registered with the runner that executes it.
