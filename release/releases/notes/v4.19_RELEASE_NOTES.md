# Work that ends in a document can now close without a deployment

2026-08-09 · v4.19

Until now the platform could only finish a piece of work by deploying something, so research and reference writing had to either treat a document as a deployed file or stop short of finished. Work whose result is a document can now be closed by recording that the document was accepted — and this release ships two such documents alongside the mechanism.

## Who this affects

- Anyone running work through the platform's release pipeline — the closing rules changed for you.
- Everyone else: two new reference documents are now available, and nothing you do changes.

## What changed for everyone using the platform

- **Work that ends in a document now has a finished state of its own.** A piece of work can declare that what it produces is an artifact rather than a deployment, and the closing step then asks for the artifact — where it lives, which change landed it, and who accepted it — instead of asking for a deployment record. *Why it matters:* research and written-standard work no longer has to invent a deployment it never performed in order to reach a clean, positive finish.

- **Nothing changes for work that does deploy, and you can check that rather than take it on trust.** Of the nine closing checks, the new path adjusts exactly two and records the other seven as deliberately untouched. Work that does not declare the new class — including work that declares nothing, or declares something unrecognised — follows the old path unchanged, and the platform says in its own report which path it took and why. *Why it matters:* a mistyped declaration cannot quietly reroute a release, because the fall-back is announced rather than silent.

- **There is now a written rule for the command pattern that reports success while writing the wrong value.** Two real incidents lie behind it: a write that returned success and stored a literal file reference instead of the file's contents, and a write that returned success and silently emptied a field because the value it was given was unset. The rule names both bad forms, requires the value be checked before the call, and requires the field be read back after it. *Why it matters:* "the command exited cleanly" is no longer treated as evidence the right thing was written.

- **A survey of eight ways to coordinate multiple agents is now part of the reference material.** Each is compared across twelve of the same properties, each carries a strengths-and-weaknesses read, and the whole set is backed by seventeen outside sources and reconciled against the platform's existing catalogue of frameworks. *Why it matters:* the next design decision in this area starts from a documented comparison instead of from scratch — and the document deliberately picks nothing, so it informs the decision without pre-empting it.

## Known limits

- **The new closing path ships and is recorded, but has not been run from end to end.** This release's own work is classed as governance, so it closed by the existing deployment path. What is shipped is the mechanism and its written record — not a demonstration.
- **A release that declares the new class cannot yet get all the way through the deployment stage.** Two earlier checks still require a deployment record with no exception for the new class. The new path cannot be reached by accident, because it only opens when the work declares it, and completing that stage is tracked as follow-up work.
- **The acceptance field is checked for being present, not for what it says.** A record reading "not accepted" would still satisfy the check. Tracked alongside the item above.
- **The orchestration survey feeds two open design decisions, and only one of them can be written up.** The other depends on a further decision that is still open, which is outside this release's scope.

Report issues at [github.com/cody-hutson/pmo-platform/issues](https://github.com/cody-hutson/pmo-platform/issues).

## Reversibility

MODERATE / HIGH confidence. Every repository change in this release comes out together by reverting the release merge commit — no data migration and no backfill, because the new path is only entered when work declares it and no work has yet declared it. One step in the release's deployment plan does not come back that way and was therefore **not** executed here: retiring the agent-memory note that carried the command-write rule before the written standard existed. Its archive and its corpus-present check are both complete and recorded; the retirement itself is held for explicit operator sign-off, because it touches operator-owned state that no revert restores. Rollback is operator-authorised; nothing rolls back on its own.

### Operator and engineering detail

**The close class is a declared value consumed by the existing gate spec, not a second close path.** The design decision (ADR-129) was to add a recognised value to the existing `deliverable_type` axis and let the `G-CL` criterion bodies branch on it — no parallel spec, no new axis, no new criterion ID, and zero IDs added, renumbered, removed or re-typed. Stage 13 resolves the class through a three-rung ladder before it binds its output set: the release plan's declared domain, then the project's declared deliverable type, then an explicit no-op default. Only the literal value `task-artifact` takes the new branch. Coverage across the live nine-gate set is **2 conditioned, 7 explicit no-ops, 0 unstated** — and both of the two gates that log rather than block were deliberately left unconditioned, so the branch adds no new surface on which a miss could go unnoticed. Stage 6 gained the matching positive deliverable state, so the state a piece of work ends in is named at the point it is produced rather than inferred at the point it closes.

**The acceptance record rides an existing section rather than opening a new ledger.** It is a block inside the release plan's `### Verification Evidence` section — already mandated by `G-CL4`, already written to by four other close-time steps. A new file would have needed its own presence check, its own concurrent-merge rule and its own retention policy to cover ground an existing surface already covers. This is the shape of one row, as it landed for this release's two documents:

```
| Field              | Value                                                    |
| deliverable        | #335 — gh api typed-field discipline (K1 standard)       |
| canonical_path     | core/standards/gh-api-convention.md                      |
| landing_commit     | a4f0c268                                                 |
| acceptance_verdict | ACCEPTED                                                 |
| acceptor           | Stage 8 QA acceptance review, ratified at Stage 9 GO     |
```

**The record has three activation modes, and this release exercises the middle one.** It is *required* when the close class is `task-artifact` — absent means fail, never not-applicable, because an unrecorded acceptance is an unclosed release exactly as an unrecorded deployment is. It is *additive* when a deploying release nonetheless ships artifact deliverables: the release's own close takes the unchanged deployment path while the record captures per-artifact acceptance alongside it. That additive mode is the one this release used, and it is what lets a deploying release ship and accept knowledge artifacts without pretending either one is the other. It is *absent* otherwise — no empty block, no ceremony.

**Both new corpus documents resolved the host-binding rule without spending an allowlist exemption.** The expectation going in was that a document about a specific command-line tool would trip the detector and need a permanent exemption. The premise was wrong, and was disproved by running the real detector against two authorings of the same content: the unconstrained form fired three findings, the constrained form returned zero. Whether a document trips that detector depends on how it is written, not where it lives — so both documents were written to pass it, and no exemption row was added. An exemption would have been actively worse, because it exempts the file permanently and a future edit that genuinely does prescribe a host binding would then go undetected.

**Three residuals are recorded rather than fixed, and one process finding is carried forward.** The two close-path residuals — the acceptance field being checked for presence rather than value, and the deployment stage still requiring a deployment record for every class — are tracked on [#5051](https://github.com/cody-hutson/pmo-platform/issues/5051). The third is that one of the two design decisions the orchestration survey feeds can be drafted but not finalised, because it depends on a further open decision. Separately, this release found that the deployment stage's stated preference for a direct REST call to create a pull request is unfollowable as written — the egress policy denies writes to that endpoint, so the fall-back to the standard command is what actually runs. The outcome was correct; the specification text is what needs amending, and that is routed as follow-up rather than changed here.
