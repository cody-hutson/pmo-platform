# The platform's memory gets one rulebook, and the QA audit flags stale docs

2026-06-27 · v2.31

The platform keeps information in many places — its own documentation, your project files, the running trackers, behavioral corrections, and the operator's notes. This release writes down, in one place, which of those is the source of truth for each kind of fact and who is allowed to change it, so an agent reading or saving a fact goes to the right place instead of guessing. The quality audit also starts reporting documentation that has gone stale or is missing, so doc rot surfaces on its own.

## What changed for everyone using the platform

- **The quality audit now reports stale and missing documentation.** The platform health audit gained a knowledge-management scan that produces two new reports — one ranking documentation that is overdue for review, and one listing documentation gaps — alongside its existing findings. *Why it matters:* if a reference doc has drifted out of date or a needed doc is absent, the audit surfaces it for you instead of it sitting unnoticed until something breaks.
- **There is now one written rulebook for where each kind of fact lives.** A new reference doc lists every place the platform stores information and, for each one, which is the source of truth and who may write to it. *Why it matters:* when the same fact could appear in more than one place, agents read it from the one authoritative place — so a stale copy can't quietly override the real value. <!-- impact:foundational -->
- **Behavioral corrections now get a scheduled review instead of piling up forever.** Corrections you give are now reviewed on the platform's existing pattern-review rhythm — a recurring one graduates into a permanent rule, an obsolete one is retired, and the rest stay active. *Why it matters:* the corrections list stays current rather than growing without bound and silently shadowing the platform's own rules.

## Known limits

- This release writes down and documents the rules for memory; it does not add an automatic check that enforces them. A separate follow-up carries that enforcement check, so for now the rulebook is guidance the agents follow, not a gate that blocks a wrong write.
- The new documentation scan reports what is stale or missing; it does not fix anything on its own. The findings are observations for you to triage, not automatic edits.
- The contacts-and-relationships part of the rulebook points at the people directory that already shipped earlier; it does not create any new place that stores personal data, and that directory stays out of the codebase as before.

### Operator and engineering detail

**The cross-surface memory contract is the new linchpin (#1073, #1074).** The four memory types the platform already named — Work, Knowledge, People, Learning — are reconciled in `knowledge-architecture.md §2.1` against the three classification axes already in use (the K1–K5 universality tiers, the context-file read-precedence tiers, and the document write-approval tiers), demonstrated as four orthogonal coordinates that compose rather than a fourth axis stacked on three. The linchpin is a new sibling discipline, `memory-architecture.md`: a single per-surface table giving every memory surface its memory-type, reader, writer, write-authority (bound to the canonical Autonomy Tier enum), cadence, read/write class, and trigger. It absorbs the no-shadow-SSOT invariant verbatim and generalizes it from the Knowledge cut to all four types. `OPERATIONS.md` and the seed `CLAUDE.md.template` link the contract, and `core/rules/governance-files.md` is the citing consumer that satisfies the "at least one consumer cites it" requirement.

**The decision is recorded in ADR-045, which supersedes ADR-029.** ADR-029 had resolved one boundary (codified Knowledge versus the operator memory store) as a deliberate first slice and named its own revisit trigger. ADR-045 is that reconciliation — it generalizes the one cut into the cross-surface contract across all four types and flips to Accepted at the Stage 9 review.

**People-memory was reconciled-and-cited, not built (#1075).** The contract enumerates a People row that points at the functional people-graph shipped earlier (the operator-local roster read through the in-tree graph view). No new surface and no repository-tracked personal data were introduced — the row describes the existing surface and its source-of-truth posture.

**Operational-state lifecycle and the corrections graduation protocol (#1076).** `operational-artifact-inventory.md` gained an additive §8 keyed by surface-class, giving each operational surface its growth pattern, cleanup trigger, archive path, and retention rule — composed with, not duplicating, the contract's read/write authority. `OPERATIONS.md` gained a thin CORRECTIONS Graduation & Expiry Protocol that binds the corrections file into the existing observation-emergence bar and pattern-review cadence rather than adding a parallel mechanism: a matured correction graduates onto the existing release rails and is then evicted, an obsolete one is retired archive-first, and the rest stay active. No new ADR was authored — the protocol is the corrections-type instance of the same lifecycle, surfaced through ADR-045.

**Active-use adoption: audit plus a wired pilot (#1077).** A new `memory-adoption-requirement.md` standard records which skills read and write memory and sets the forward-only expectation (a SHOULD) that new skills declare their memory adoption. `daily-status` is the wired pilot: its inputs and its status-log append are now annotated against the contract — it consults each surface's read/write class and source-of-truth owner before reading, and its post-confirmation append is explicitly the authorized auto-write of its own surface, never an inline write to a higher-tier surface. The skill edit routed through the skill-edit discipline with a package rebuild.

**Systematic KM scanning in the QA auditor's platform-health mode (#249).** `pmo-qa-auditor` Mode E gained a knowledge-management check-set that runs four mechanical scans over the durable corpus — a documentation-debt audit, a staleness scan ranked by criticality, an artifact lifecycle-state check, and an in-flight-capture verification — emitting two new artifacts (a doc-debt register and a staleness report) plus an in-flight-capture subsection in the findings register. Every threshold, weight, band, and state is consumed from the existing knowledge-management protocols and the canonical lifecycle-state convention; the check-set redefines nothing, and any artifact missing a required field is reported as indeterminate rather than silently passed. The skill edit routed through the skill-edit discipline with a package rebuild.

**Versioning note.** The release was planned at the MINOR bump-class with the concrete number deferred to merge; it bound to v2.31 at the Stage 12 atomic claim above the shipped anchor v2.30. The two edited skills' distribution packages rebuild at release-cut as part of this close-out.
