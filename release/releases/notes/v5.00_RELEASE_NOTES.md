# Releases file only the follow-ups that matter

2026-11-04 · v5.00

A release now opens a follow-up issue only when a user can see the problem, or it touches security or privacy, and it is at least Minor, and it gathers the follow-ups that pass into one sweep issue per repository. Automatic intake logging and triage follow the same rule, and there is nothing you need to do.

> **Skip the rest** unless you run a release's plan review or its close, rely on the platform to log the gaps it notices on its own, or triage the issue backlog.

## Who this affects

- Operators who run a release's plan review or its close
- Anyone who relies on the platform to log the gaps it notices during a session
- Anyone who triages the issue backlog or reads the issues a release leaves behind

## What changed for everyone using the platform

- **A follow-up becomes an issue only when it matters.** Anything a release defers, recommends or detects becomes an issue only when a user can see the problem, or it touches security or privacy, and it reads at least Minor. Anything below that stays in the record of the step that found it, anything an open issue already owns is added to that issue, and anything a decision record already accepts is not filed again. *Why it matters:* the backlog stops filling with issues a release opened about itself that nobody needed to act on.

- **A release files its follow-ups once, at close, in one sweep issue per repository.** The follow-ups that pass are gathered into one sweep issue for each repository they concern, with separate issues only for genuine bugs and features, and only after you confirm anything that surfaced after the plan review. A deferral at the QA review or the plan review now points at its override record or at the sweep instead of opening an issue of its own. *Why it matters:* one release's leftovers arrive as one item to review, not a scatter of cards.

- **The plan review shows how much work a release resolves against how much it creates.** Before the go-ahead, the plan review counts the issues the release resolves against the follow-ups it would file, and shows the difference. When the release would create more than it resolves, the go-ahead waits until you accept the excess or cut it. *Why it matters:* a release that adds more work than it removes is seen and decided before anything is filed.

- **Automatic intake logging applies the same test at every automation level.** When the platform notices a gap and would log it on its own, it applies the filing test first, whatever automation level is set; a signal below it is recorded in the session's own output and not filed. *Why it matters:* changing the automation level changes who confirms an issue, not whether an unimportant one gets filed.

- **Triage counts related observations into one piece of work.** Triage now gathers related observations into one story, or into an issue that already owns the work, and closes each counted observation as done with a pointer to where it went, instead of turning each observation into its own card. *Why it matters:* several notes about one problem become one item to plan, and each note still shows where its signal went.

## Known limits

- The new counting and filing apply to a release whose plan review starts after this release merged. A release whose plan review started earlier keeps the old routing to the end of its run. This release ran its own plan review before it merged, counted its follow-ups the new way voluntarily, found none that passed the test, and filed nothing.
- Two of the three new measurements had nothing to count when this release closed: no automatic intake log entry and no triage batch had run since the merge, about seven hours earlier. Both are carried by an open owning issue until they have members, [#7537](https://github.com/cody-hutson/pmo-platform/issues/7537). The third, the plan review's count, read 1 of 1.
- The filing-test line written into an automatically logged issue shows that the test ran, not that its reading was right; triage checks the reading against the item.
- The workspace's standing instructions still describe the highest automation level as creating an issue directly, without the filing test. That sentence now overstates what happens, and it is corrected at the next revision of those instructions.
- Nothing needs installing: the six skills this release changed were redeployed when it merged. The platform's recorded version moves to v5.00 when this close lands on the main line.

Report issues at https://github.com/cody-hutson/pmo-platform/issues, and report a suspected vulnerability privately as the [Security Policy](https://github.com/cody-hutson/pmo-platform/blob/main/SECURITY.md) describes.

## Reversibility

MODERATE / HIGH. Reverting the single release merge restores every rule, stage procedure and skill as it was, after which the six skills are rebuilt and redeployed. Issues filed and observations counted under the new rules stay valid records and can be reopened one at a time. The version tag is kept as the record that the version was claimed, and the decision record ratified at this close stays in history as written.

### Operator and engineering detail

**One threshold, one home (#8146, ADR-229).** The filing threshold lives in a new core standard, `core/standards/work-item-filing-threshold.md`: two limbs, class (user-visible, security-relevant or privacy-relevant, with user-visible read for a platform-internal item as a user blocked or misled into a wrong action) and severity (at least Minor on the five-bucket finding scale), plus what is not filed even when it passes, already declared or already owned. The release pipeline reaches it through the new § 8 of `finding-disposition-framework.md`, which carries only the release-side routing; automatic intake logging reaches it directly. ADR-229 records the decision and was ratified `Accepted` at this release's Stage 13 Phase A13 on the operator's per-record authorization.

**Counted at Stage 9, filed at Stage 13.** Stage 7 and Stage 8 spokes tag a Defer in their own records instead of opening an issue. Stage 9 Phase A7.6 assembles every tagged follow-up into a ledger, renders one net work line against the issues the release resolves, and holds GO on an excess until the operator accepts it or cuts it; a cut never returns a protected row. Stage 13 Phase A10.5 is the only step that files a follow-up: one sweep per repository, opening with a `release-follow-up` marker, plus one issue per row tagged `bug` or `feature`, after the operator confirms the addendum of anything recorded after Stage 9. A filed follow-up carries no milestone and enters Stage 2 Triage like any intake. The step binds releases whose Stage 9 Phase A starts after this release's merge, so this release's own close assembled it without filing and recorded the line as what it would read:

```text
**Phase A10.5 net-work-ledger (close):** resolved=1 · proposed=0 (sweep=0 · bug=0 · feature=0 · target=0 · platform=0) · net=+1 → NON-NEGATIVE · below-threshold=15 · declared=1 · folded=0 · cut=0 · reclassified=0 · sources: s6=2 s7=2 s8=4 dr=0 hub=0 modec=0 audit=0 late=8 · read 2026-11-04T15:10Z
```

**Automatic intake logging.** `intake-desk` Mode C runs the threshold before the `automation_level` clamp, at every dial. A below-threshold signal returns a held record that its caller notes in its own output; a passing signal named against a running release returns a follow-up candidate for that release's sweep; otherwise a passing signal is created as before, with a `filing-threshold: pass` line directly after the provenance marker. The workspace charter's auto-logging clause still reads as if the top dial creates directly — the accepted residual recorded in ADR-229's Consequences, owned by the operator for the next charter revision.

**Stage 2 observation counting.** Observations are counters for related work, not cards awaiting one-to-one conversion. A triage batch counts related observations into one story or an existing owner, and closes each counted observation `completed` with `status: done` and a `Counted into #` comment naming where it went; `label-taxonomy.md` and `pipeline-triage` carry the same rule.

**Measured at close.** The release added three rows to the gate-coverage register, and Stage 13 Phase A14 measured them. `release-follow-up-ledgers` met its threshold at 1 of 1. `mode-c-threshold-line` and `stage2-counted-observations` had no members in the window since the merge and are carried by the parent epic, #7537, whose comment stream names both populations.

**How it shipped.** One card, built serially on one branch, with one Stage 6 fix pass after Stage 7. Stage 8 recommended ACCEPT with all seven acceptance criteria met, and Stage 9 returned GO. The stamp commit that resolved ADR-229's deferred citations moved the head before the merge, so the merge waited one more CI cycle; the release then merged at `0aeac05d` and claimed `v5.00` with a signed annotated tag. The six skills and the rules mirror were redeployed at Stage 12 with zero diff.

For full implementation detail see the Deployment Log v5.00 entry in the release log, and [the release plan](https://github.com/cody-hutson/pmo-platform/blob/main/release/releases/plans/v5/v5.00_RELEASE_PLAN.md).
