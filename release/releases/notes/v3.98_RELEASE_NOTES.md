# Readiness checks now catch work another epic owns, and render a map

2026-07-28 · v3.98

Before you commit to running a release, the readiness check can now tell you two things it could not tell you before: whether an item is already somebody else's work, and whether the problem it describes actually holds up. It can also show you the answer as a picture instead of a wall of text.

> **Skip the rest** unless you check a milestone for readiness before starting a release, or you act on the answer it gives.

## Who this affects

- Anyone who checks a milestone for readiness before committing to a release.
- Anyone who acts on a readiness result — deciding whether to start, fix, re-confirm, or re-bundle the work in a milestone.

## What changed for everyone using the platform

- **Readiness checks now ask whether another epic already owns the work.** Each item in a milestone is tested against the rest of the backlog three ways: is it a direct child of an open epic, is it listed in an epic's own composition table, or does it closely resemble an open item filed under a different epic. *Why it matters:* the most expensive work is work that did not need doing, and duplicated ownership used to surface during the build rather than before it.
- **There is a new answer for work that is real but filed in the wrong place.** The set of possible outcomes grows from four to five with **move it or drop it**, which names the epic that should own the item. *Why it matters:* previously this finding had to be forced into an outcome that meant "close this" — the opposite of what a move actually needs, since the work is still live and still wanted.
- **Readiness checks now ask whether the problem itself holds up.** A second new check records where each item's evidence came from — an observed pain, a framework, an article, or nothing stated — and whether the fix it proposes is pitched at the right level, flagging a small fix written as a sweeping redesign and a structural change written as a one-line tweak. *Why it matters:* a problem that does not survive contact with the real system is cheapest to catch before the release starts, not halfway through it.
- **A weak single item is no longer treated as a milestone-level alarm.** Only a milestone where at least half the items lack observed evidence raises the finding; one such item is recorded and moved past. *Why it matters:* you get a signal about the shape of the whole bundle rather than a stream of alerts on individual items.
- **Readiness results now render as a map.** The result can be published as a diagram that adapts to light and dark backgrounds, with one legend entry for every check group. *Why it matters:* you can see the shape of a milestone's readiness at a glance instead of reading the full write-up to find the one thing that failed.
- **The seven existing check groups are untouched.** The checklist grows from seven groups to nine; the original seven keep their numbering, wording, and behaviour exactly. *Why it matters:* anything you already rely on — saved notes, prior results, your own habits of reading them — still refers to the same checks.
- **A false alarm in the reference checker is fixed.** A colour code written in regular-expression form was being misread as an issue number, so a file documenting a verification command failed a check it should have passed. *Why it matters:* that check stops flagging documentation it should leave alone, while still catching the real issue references it exists to find.

## Known limits

- The readiness check is advice, not action. It names the epic that should own an item, or the premise that needs re-confirming, and then stops — it never moves an item, re-labels it, removes it from the milestone, or edits it. Every change stays a human decision.
- The ownership check narrows candidates using an item's project label before looking for a real ownership link. An item with no project label is checked against a wider set, and a shared label on its own is never reported as a finding.
- The map is a projection of the written result, never a replacement for it. Where the two would disagree, the map is dropped and the written result stands. A result with no map is complete; a map with no written result is not.
- The map is produced fresh each time a check runs and is never saved as a file, so there is no stored diagram to return to later — re-run the check to see it again.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. The release changes reference documents and skill instructions for a read-only check that stores nothing and changes nothing outside its own written output; reverting the release restores the seven-group checklist and the four-value outcome set intact. No data migration and no stored state to unwind — the only state outside version control is the milestone and issue status, which can be reopened.

### Operator and engineering detail

**Both new groups compose an owner rather than carrying inline logic.** Group 8 (backlog-altitude ownership and subsumption) is owned by `release-planner`, whose cross-milestone backlog read is extended here to cross-epic ownership for sub-checks `8a`–`8c`; `8d` re-reads group 5's existing similarity hits for the ownership signal rather than re-running similarity. Group 9 (problem-validity and abstraction-altitude) is owned by `triage-design-rereview` § 11, whose premise re-review is extended with the provenance and altitude lens. This honours the specialists-compose-not-absorb rule — each group cites its owner's rule and does not restate it. Both owner files were absent from the original Stage-4 change set even though both cards promised to compose them; the operator approved a scope change adding both, so the composition citations point at owners that genuinely own the check. That gap had been recorded once before on an earlier bundle of the same cards and did not survive the re-bundle, which is why the plan records it as a repeat cause rather than a first occurrence.

**The disposition set is closed as a vocabulary, not as a count.** The prior wording froze the set at exactly its four then-current values, justified by the fact that the preceding group had mapped onto an existing one. That sentence hardcoded current membership instead of stating the rule that produced it. It is replaced by the durable invariant — a new group maps onto an existing disposition unless it introduces a materially distinct operator action — plus an explicit per-card precedence ladder. Group 8 failed that fit test four ways and took a new value; group 9 passed it and took the existing `RE-CONFIRM`, exactly as group 7 did. The decisive evidence was that the subsumption protocol behind `DROP-OR-TRIM` terminates in closing the subsumed issue, while a rehome closes nothing — opposite terminal actions. The reasoning, the rejected alternative, and the fit test are recorded in [ADR-099](https://github.com/cody-hutson/pmo-platform/blob/main/release/ADRs/ADR-099-mode-r-disposition-set-fit-test.md).

The disposition vocabulary and the per-card precedence ladder, in their new shape:

```text
# Mode R disposition set — closed vocabulary, 5 values (was 4)
DROP-OR-TRIM      remove the shipped or duplicate item from the milestone   (terminal: closes the item)
DROP-OR-REHOME    move the live item to its owning epic                     (NEW; relocation: closes nothing)
FIX-FIRST         repair the item in place, then re-evaluate
RE-CONFIRM        operator re-validates a moved premise before spending
RE-BUNDLE         the milestone itself is not coherent                      (milestone-level, not per-card)

# Per-card precedence — one disposition per card, highest wins
DROP-OR-TRIM > DROP-OR-REHOME > FIX-FIRST > RE-CONFIRM
# Load-bearing case: an item both already shipped (group 5) and owned elsewhere
# (group 8) resolves to DROP-OR-TRIM — if the work is done, do not rehome it.
```

**One property, checked once.** Groups 7 and 9 both look at altitude, so an explicit routing rule keeps exactly one of them claiming any given finding: a too-low finding routes to `7a` only when its subject is a named delivery or governance methodology archetype whose correct home is a configuration-selected pack; every other band mismatch routes to `9b`, and `9b` emits nothing when `7a` has claimed it. An item tripping both carries two findings and one disposition. Group 8's *backlog* altitude (the hierarchy ladder) is deliberately distinct from group 9's *abstraction* altitude (seam bands).

**The map is a runtime element, not a design artifact.** The readiness map is rendered inside a single emission and is never written to disk — no `.svg` file is committed anywhere in the repository, and a rendered map persisted to disk is a defect rather than a variant. The committed artifact is the markdown scaffold, which stays fully readable in source form. This satisfies the design-artifact standard's stated rationale for rejecting SVG as a durable format by construction rather than by exemption, because the element anchors no platform state. It lives in its own reference file rather than inside the skill instructions, which are read on every invocation of this skill including the orchestration mode that never renders a map.

**Shared count-bearing lines were reconciled in a dedicated commit.** Fifteen shared count and enum surfaces sit across a small set of files, and all three items in this release mutate them. Rather than assigning those lines to any one item, the release used a terminal reconciliation commit that swept every count-bearing and enum-bearing line to its final state — the designed mitigation for the release's top-ranked risk, that a stale "seven groups" or four-value enum survives in one of the mirrors. The authoritative enumeration is the checklist's own disposition table; the two restatements in the skill instructions are mirrors that must agree with it. For full implementation detail see the [RELEASE_LOG entry](https://github.com/cody-hutson/pmo-platform/blob/main/release/releases/RELEASE_LOG.md) and [the release plan](https://github.com/cody-hutson/pmo-platform/blob/main/release/releases/plans/v3.98-release-hub-mode-r-depth_RELEASE_PLAN.md).

**The reference-checker fix is a paired constant across three surfaces.** The hex-colour mask is declared byte-identical in the workflow, the hook, and the fixture runner, so widening it in one place alone would trip the anti-drift check. All three were widened together and a fixture pair was added — one case that must now pass (the regex character-class form) and one that must still fail (a genuine bare issue reference) — so the widening cannot silently swallow the true positives the checker exists to catch.
