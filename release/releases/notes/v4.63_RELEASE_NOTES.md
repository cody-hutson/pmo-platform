# The release close-out now proves what it reports

2026-09-11 · v4.63

A family of checks in the release close-out reported success while proving nothing — a gate that read a typo as a resolved commitment, a wait that reported failure on success, a cleanup preview that predicted the wrong outcome, and two tools that died silently before printing anything at all. Seven of them are fixed; two more of the same kind turned up inside this release's own new test code, and this note says which ones are still open rather than implying the family is closed.

> **Skip the rest** unless you run a release close-out, read its report, or rely on the automated branch-and-worktree cleanup afterwards.

## Who this affects

- Anyone who runs or reads the automated release close-out
- Anyone who relies on the automated branch and worktree cleanup at the end of a release
- Anyone who reads a published release page and expects its title to match the release note

## What changed for everyone using the platform

- **A close-out commitment with a mistyped status no longer counts as handled.** The gate that holds a release open until every recorded commitment is resolved used to treat any value it did not recognise as resolved, so one typo let a release close over an unfinished commitment. It now classifies by membership of a stated set, ignores letter case, and refuses to give a verdict at all over a row it cannot read — that refusal holds the close open, and no attestation clears it. *Why it matters:* a commitment you wrote down is now either visibly resolved or visibly blocking, and never silently skipped because of a spelling.

- **A close-out no longer reports failure on a chore step that already succeeded.** The step that waits for the close-out's own housekeeping change to land had no ending for the case where it had already landed, so a re-run of an otherwise-complete close reported failure on a success. An already-landed change is now a recognised finish, and a genuinely abandoned one is a recognised failure. *Why it matters:* re-running a close-out that was interrupted part-way now tells you the truth about where it got to, instead of reporting a problem that is not there.

- **The cleanup preview now predicts what the cleanup will actually do.** Before, the preview counted zero branches for removal while the real run removed some — because it did not account for branches that its own worktree removals would release. Those are now listed in the preview as branches it expects to drain, and the total you are shown is the total you are approving. *Why it matters:* the preview is the thing you approve, so it now matches the outcome instead of understating it.

- **A worktree the system is not allowed to remove says so, in its own words.** A worktree held under a lock used to be listed for removal and then, when removal was refused, reported as having uncommitted work — a cause that was not the real one. It now carries its own reason, kept separate from the reason used for a worktree a live session is using. *Why it matters:* when cleanup skips something, the reason it gives is the reason it actually hit, so you can act on it rather than hunting for changes that were never there.

- **A missing optional setting no longer kills a close-out tool before it prints anything.** If your configuration file left out an optional entry, two of the close-out tools stopped at start-up with an error code and no message — not even their own help text or self-check would run. Both now treat an absent optional entry as absent. *Why it matters:* a setting you never filled in stops being an unexplained silent failure, and the tools stay usable for diagnosing whatever you were actually looking at.

- **The published release page now carries the same title as the release note.** Nothing owned the job of composing a release's public title, and the step that refreshes an already-published page could not set one, so a title could stay provisional after the note that defines it had been written. Composition is now owned by the close, the refresh passes the title through, and a note with no usable heading leaves a good title alone instead of replacing it with a worse one. *Why it matters:* the public page for a release and its release note now say the same thing.

- **One documented error condition that the code never actually checked is gone.** The close-out's list of error codes described a condition it did not test for, which sent readers looking for a check that was not there. The description now matches what the code does, and says where the real check happens. *Why it matters:* when a close-out stops, its own error list is now a reliable place to find out why.

## Known limits

- **This does not close the family, and the new safeguard is narrower than it looks.** The safeguard added in this release proves that a group of checks *ran*. It does not prove that they can still tell a good result from a bad one — a check whose test has been gutted but still executes passes it. That boundary is why one of the two problems found in this release's own test code needed a separate fix instead of being covered by the safeguard.
- **Nine of the ten release tools still print the same kind of unproven claim.** Measured across the release tool set: 84 lines announce that a group of checks was validated, and only one tool's 30 lines are held to a proof that the checks ran. The other nine tools' 54 lines print regardless. Nothing in this release changes that, and it is stated here so the number is on the record rather than rediscovered.
- **One check found during this release was deliberately left open.** In the automated test run, one of the two tools' self-check suites quietly skips nine of its twenty checks — because of how the code is fetched in that environment — and still reports green. It was found, written up, and left for a later release rather than rushed in beside seven unrelated fixes.
- **The automated test run does not protect one of these two tools.** The job that exercises the cleanup tool's own self-checks is still not one of the checks required before a change can be accepted, so a mistake in that file can still be accepted with everything showing green. The other tool's job was registered as required during this release.
- **Records written before this release are not rewritten.** Commitment ledgers from closed releases keep the wording they were written with; they are read against the new rules, not edited to match them, because rewriting a closed release's record would falsify what its close was judged against.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

### Operator and engineering detail

**The batch is coherent by surface, not by cause, and the honest headline is the class rather than the count.** Seven members across two tools — `release/tools/automated-closeout.sh` and `release/tools/cleanup-orphan-state.sh` — share no root cause. What they share is that a reader of either tool's output could not distinguish a correct run from a defective one: a never-FAIL predicate (the action-item gate's unrecognised-status-reads-resolved), a missing terminal state (the chore-PR merge wait), a prediction that contradicted its own apply (the dry-run's unprojected drain), a mis-attributed failure (the lock-held worktree reported as dirty), a load-time abort with zero bytes on both streams (the untolerated optional-key read), an unowned composition step (the Release title), and a documented condition with no code behind it (the phantom exit-2). Thirty acceptance criteria were graded across the seven members: 29 MET, 1 PARTIAL, 0 NOT MET, and the single PARTIAL's remainder was non-blocking, so no operator override record is owed anywhere in this release.

**The release reproduced its own defect class inside the test code it added, twice, and the two needed different mechanisms.** Every group in the close-out's self-test printed a `… validated (…)` extraction line as an unconditional echo inside a terminal block gated only on a zero failure count — so a group announced that its arms had been validated whether or not a single arm ran. That is the same never-FAIL shape the release exists to close, sitting in the release's own new evidence surface. The fix is a per-arm witness: all 78 arms across the 8 claiming groups record through `_st_arm <group> <label>` (81 call sites measured), behind six gate arms — anti-vacuity, duplicate, orphan-group, arm parity, an **arm-count** arm that closes the delete-the-arm-and-its-recorder hole, and a capability pair exercised on every run — proven by 10 in-place mutations, all restored and hash-verified. The second finding was a strip-guard limb whose substring needle matched the script's own `sed` program, making it tautological; it moved to an anchored whole-line match, measured `(True, True)` before and `(False, True)` after, with a specificity control that fails if the substring form returns. The witness gate does not cover that second class and was never going to: **it grades execution, never discriminating power.** Two failure modes, two mechanisms — recorded as a declared boundary rather than left for a later reader to discover.

**Five further sites of the same silent-abort class were found in two tools this release did not otherwise touch, and the operator took them in-release.** Three in `audit-epic-rollup-close.sh` and two in `synthesize-release-learnings.sh`, all reproduced pre-fix with exit status and byte counts on both streams over a fixture `HOME`. The remedy is two shapes, not one, and the site decides which: the two-part fold (`grep -E` → `grep -m1 -E`, drop `| head -1`, append `|| true`) where a `head` pipe exists, because the enforcing SIGPIPE-idiom job matches `head` as a short-circuiting reader on a changed line; tolerance-only where the site already carried `grep -m1` and never piped into `head`, where the fold's other half has no referent. Both halves of that discrimination come from the two members' own source comments.

**The action-item close gate's shape contract changed, so the note carries the instance.** The gate moved from three verdicts over two counts to five verdicts over three counts, and its recognised `status` vocabulary is now stated once — the authoring enum plus exactly two read-only historical aliases, compared case-folded. Anything outside it is unclassifiable, which blocks and which no attestation clears, because attestation licenses an *absent* ledger and never an *unreadable* one. Where a ledger carries both an open row and an unclassifiable one, `UNRESOLVED` wins because it names the dominant remedy, and its detail carries the unclassifiable rows so one pass covers both:

```
authoring enum   open · in-flight · done · cancelled · superseded
read aliases     resolved -> done          withdrawn -> cancelled   (case-folded)
gate verdicts    RESOLVED        silent pass — >=1 row, all classifiable, none open
                 UNRESOLVED      BLOCKS     — >=1 open/in-flight  (wins over UNCLASSIFIABLE)
                 UNCLASSIFIABLE  BLOCKS     — status outside the recognised set; no attestation clears it
                 NOT-RECORDED    SURFACE    — no ledger file            } require explicit
                 EMPTY-LEDGER    SURFACE    — ledger present, zero rows } operator attestation
```

**`ADR-197` records the classification decision, and its number is the second one it had.** It was authored as `ADR-195` and renumbered when a sibling release merged first and claimed 195 and 196 from the single global sequence shared across both decision-record directories. The renumber was performed by the governed tool, taking `anchor(origin/main) + 1 = 197` rather than `max(claimed) + 1`; another unmerged branch also claims 197, which is detection-only and does not bind. That is the allocation model working rather than a defect, and it is recorded because the required numbering gate was red in the interim.

**What the green check strip did and did not establish here.** Of the required contexts at the PR head, exactly one exercises either tool's self-test suite — `Close-out automation smoke (macOS)`, which was registered as required during this release and covers the close-out tool's macOS partition. The job covering the cleanup tool, `Discovered tool self-tests (Ubuntu)`, is still not required, and neither is the SIGPIPE-idiom job. The self-test discovery partitions by a declared runner pin rather than by job title, which is how an earlier claim in the PR body — that the macOS job ran both suites — was falsified and corrected. The evidence this release carries is therefore the per-member self-test and mutation records, not the check strip; and the one CI failure at merge time was arm-for-arm baseline-identical to `main`.
