# The tooling that guards this platform stops failing silently

2026-08-09 · v4.21

A command meant to keep your usage history up to date had been deleting most of it on every run, and reporting success. That is fixed — along with two other cases of the same thing: six test suites that were written, committed, and never actually run, and a crash pattern that made unrelated checks fail at random.

## Who this affects

- **Anyone who has refreshed their usage history with the incremental option.** Records that run did not re-read were destroyed, silently, on every previous version. Step 1 below rebuilds the store.
- **Everyone whose changes go through the build checks.** Six more suites now run, and one new check can fail a build.
- **Anyone who has dismissed a build failure as flaky.** A specific, real cause of intermittent failures has been removed from the checked surface.

## What you need to do

1. **Rebuild your usage history if you have ever run the incremental refresh.** The incremental mode deleted every record it did not re-read that run. Those records are already gone and cannot be recovered from the store — but the store is rebuilt from your local session files, which are untouched, so running the extractor in its default full mode restores everything the session files still hold. Nothing in the platform can detect for you whether you were affected.
2. **Expect the new build check to fail a build that reintroduces the crash pattern** — it names the file and line, and tells you how to mark a deliberate exception.

## What changed for everyone using the platform

- **Your usage history stops being deleted by the command that was supposed to update it.** The incremental refresh discarded every record it did not re-read on that run — a populated store went from six sessions and two agent records down to one session and none — and then exited reporting success. It now stops on the error and leaves the store exactly as it found it. *Why it matters:* the loss was invisible at the moment it happened, so you would only discover it weeks later, when the history you wanted to look back on was not there.

- **Six test suites that were written and committed but never actually run are now run on every relevant change.** They sat in the repository and were counted as coverage; nothing invoked them. *Why it matters:* six suites' worth of checking was being credited without being performed, so the problems they were written to catch could ship unnoticed.

- **A crash pattern that made unrelated checks fail at random is gone from the checked surface, and a new build check stops it coming back.** 157 places across 35 files used a command shape that can be killed mid-write by whatever is reading from it; 12 were left in place, each with a written reason. *Why it matters:* these failures looked like flaky infrastructure rather than a defect, so they trained people to re-run instead of investigate — and a real failure hiding among them would have been dismissed the same way.

- **The new check states exactly what it catches and what it does not, instead of claiming a category is closed.** Each of its rules now carries a worked example of something it catches and something it misses. *Why it matters:* a check that overstates its reach is worse than no check, because people stop looking at the thing it claimed to cover.

## Known limits

- **The new check runs but cannot yet fail a merge.** It is not registered as a required check, so a change that reintroduces the pattern still merges today. Registration is a repository-settings action outside this release and is tracked as a blocker on this release's close.
- **One of the six newly-run suites executes but asserts nothing about its own subject.** Running it does not yet check the thing its name describes. Repairing it is design work outside the scope of the wiring card, and it is carried as separate work.
- **The method behind one acceptance criterion can pass without proving anything.** The coverage report it reads is satisfied by a build file that merely mentions a suite, whether or not it runs it — so the criterion was additionally graded by a second, structural check. Tightening the underlying method is carried as separate work.
- **One acceptance criterion rests on an operator override, not on evidence.** 9 of the 13 conversion commits never ran the build checks — while the pull request conflicted, the build system could not construct the merged state to test, so nothing ran. That cannot be satisfied after the fact, and it is recorded as an override rather than presented as a pass.
- **The conversion is pinned to a fixed set of 35 files at a fixed commit.** Files added after that point were not swept; the new check is what covers them going forward. The population moved by roughly half in two days during the work, which is why a moving target was replaced with a pinned one plus a durable guard.
- **On this platform's build machines the crash signature is not the one the platform's own documentation named.** Statements elsewhere in the corpus that named a specific exit code as *the* signature were corrected in this release.

Report issues at [github.com/cody-hutson/pmo-platform/issues](https://github.com/cody-hutson/pmo-platform/issues).

## Reversibility

MODERATE / HIGH confidence. Everything in this release comes out together by reverting the release merge commit, and the revert order is the inverse of the merge order — the suite wiring must come out before the conversion, or the wiring re-imports the crash pattern into a job that now runs it. Reverting the data-loss fix restores silent destruction of usage records and is a last resort; prefer a forward fix. Rollback is operator-authorised.

### Operator and engineering detail

**One failure class, three cards, and the class was then found in six of the release's own instruments.** The unifying property is *a check or tool that stops doing its job while its output stays indistinguishable from success.* Having named it, the release went looking for it at home and found it in six places: the usage tool itself; one of the suites it wired; the acceptance criterion for that wiring; the release's own CI, which had never run at all while the pull request conflicted, leaving four green ticks from an unrelated head-triggered workflow to make the page read as passing; the new gate's coverage register; and the gate's own declaration of what it covers. Four were fixed inside the release. Two are carried as separate work. That count is recorded rather than smoothed because a release that names a failure class and then declines to look for it in its own work has not really named it.

**The gate was wrong at six successive levels, and it ended by making its declaration honest rather than by closing the class.** It started as a writer allowlist, moved to a reader allowlist, then had its join semantics corrected, then its marker lookback, then a grammar axis that had been called closed turned out not to be, and finally a POSIX citation was doing work that removed adjectives used to do. What ships is not a claim of completeness: the detector is described as an *enumeration*, with a measured caught / not-caught pair per clause, four named exclusions that all fail closed, and zero live instances of any exclusion across 150 tracked shell files. The durable rule this leaves behind — **do not call an axis closed unless the closure is derivable from the grammar** — is the release's real output, and it is worth more than the gate.

**The story told about the data-loss fix was false, and Dev Testing measured that rather than arguing it.** An earlier account held that correcting the tool's variable binding alone changed nothing observable, and that the exit-code work was what made the fix real. Applied on its own to unmodified mainline, with the error swallow and the unconditional success exit both still in place, the binding correction gives six sessions in, six sessions out. The three changes are independent, not a chain: the binding correction *is* the data-loss fix; removing the error swallow covers a different cause entirely; and restoring the exit code gives a future caller — and the self-test — something to observe. No code changed as a result of the correction. The implementation was right; the causal record was not, and the record was fixed.

**Sixteen broken probes were caught in this release, including one that would have reported every packaged skill as out of date.** That probe compared a package archive's byte hash against a content-hash sidecar — two different things — and read STALE across the board. Package freshness is measured by the platform's own check, which compares a rebuild-stable content manifest, because the archive envelope embeds file timestamps and a content-identical rebuild differs at the byte level. Every count-resting claim in this release carries an invocation, a denominator, and both a sensitivity and a specificity arm with an observed non-zero and an observed zero respectively.

**The conversion shape and its retention marker.** The idiom is a writer piped into a reader that exits early; when the reader exits, the writer is killed mid-write. The fix routes through a shell construct that consumes its input fully, and a site that genuinely needs the old shape carries an inline marker so the gate can tell a deliberate retention from a new mistake:

```bash
# Before — the reader exits on first match and kills the writer mid-write:
printf '%s\n' "$haystack" | grep -q "$needle"

# After — the reader consumes its whole input; no early exit, no signal:
case $'\n'"$haystack"$'\n' in *$'\n'"$needle"$'\n'*) : ;; *) false ;; esac

# Deliberate retention — the marker is what the gate reads, on the line above the site:
# sigpipe-ok: bounded generator, reader exit is the intended stop condition
some_unbounded_generator | head -n 20
```

**Version identity moved five times before it bound.** This release was planned as v4.16 and lost the slot to a sibling five times over, finally binding at v4.21 at the merge-time claim. Nothing but a recorded number moved each time — the branch, the plan file and the release state are keyed on the milestone name, never the version — which is exactly what that design is for. The merged commit messages and the pull-request title still read v4.19, the last provisional value, and that is accepted as an immutable as-authored artifact with its provenance recorded; every durable ledger reads v4.21.
