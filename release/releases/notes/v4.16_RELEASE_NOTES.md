# The delivery-status labels the platform promised now actually exist

2026-08-08 · v4.16

The platform has long declared a set of labels describing where a work item sits in delivery, but two of them had never been created, so nothing could ever be marked as actively being worked on. Those labels now exist, a seventh label group describing work status was added alongside them, and the pipeline applies the in-progress label when engineering begins.

## What changed for everyone using the platform

- **Work items can now be marked as actively in progress, and they are.** Two of the seven declared delivery-status values — in-progress and done — had never been created, so the pipeline step that was supposed to apply the first of them had nothing to apply. Both now exist and the step fires: a whole-population count returns three items currently marked in progress, against a control group of more than two hundred that returns a non-zero figure, where before this release the count was structurally zero because the label did not exist at all. *Why it matters:* you can now filter the tracker for what is actually being worked on right now instead of inferring it from which items have a milestone.

- **A separate six-value work-status vocabulary was added for the delivery board.** Backlog, ready, in-progress, in-review, done and cancelled are now real, each with its own colour, kept deliberately separate from the existing delivery-pipeline status labels so that an item can carry one of each rather than being forced to choose. *Why it matters:* the board's own notion of progress no longer has to borrow a label group whose rules would have made the two mutually exclusive.

- **A label that existed but was broken has been repaired.** One delivery-status row had been created accidentally, carrying a default grey and no description at all, which made it invisible to anyone scanning the label list for meaning. It now carries a proper colour and the description "Active engineering work". *Why it matters:* the label reads as what it is instead of looking like leftover noise.

- **Applying an unrecognised label can no longer silently invent a broken one.** Sending an unknown label name through the interface used to create it on the spot with no colour and no description — which is exactly how the broken row above appeared. A status change now requires that the label already exist. *Why it matters:* the label list stops accumulating malformed entries that nobody deliberately created.

- **There is now a report that finds parent items whose children have all finished.** It runs automatically at the end of every release and lists candidates for closing. Its first run surfaced five clean candidates and ten flagged ones out of forty-two open parents, with a stated reason attached to every exclusion. *Why it matters:* completed parent items stop quietly accumulating, and you get a list to act on rather than having to go looking.

- **Reconciling the label list is now something you can preview before running.** A read-only command prints the exact instructions that would bring the live labels into line with what the platform declares, and runs none of them. *Why it matters:* you can see what would change before anything changes, and decide per row.

## Known limits

- **The work-status field is defined but nothing writes it yet.** This release gave the field a definition, a live label surface and a written contract for how it resolves when no external board is connected. It did not give it a writer: the component the platform names as the field's maintainer does not reference the field in any of its twelve files. So the six new values exist and can be applied by hand, but nothing advances them for you. That refit is tracked in [#5056](https://github.com/cody-hutson/pmo-platform/issues/5056) and is the change that will alter what you see day to day.
- **Three declared labels still do not exist** — the three triage-flag rows were deliberately left out of this release's scope. Tracked in [#5054](https://github.com/cody-hutson/pmo-platform/issues/5054), along with four labels the taxonomy document says were removed but which are still live.
- **Most labels disagree with their own declaration on colour or wording.** Only two of thirty-four labels that exist on both sides match their declared colour and description exactly. This was measured and deliberately not auto-corrected, because some of those differences are probably choices somebody made on purpose and the check cannot tell those apart from drift. Tracked in [#5057](https://github.com/cody-hutson/pmo-platform/issues/5057).
- **The label check reports an error rather than a verdict when the interface quota is exhausted.** The data it needs is available by another route that is unaffected. Tracked in [#5058](https://github.com/cody-hutson/pmo-platform/issues/5058).
- **The parent-item report annotates rather than decides on two of its checks.** Both attempts at automatically telling a true parent from a mislabelled grouping over-matched at fourteen of fifteen candidates, and the narrower one missed the single case it was built to catch. Those two checks therefore add a note for you to read instead of ruling anything in or out.

Report issues at [github.com/cody-hutson/pmo-platform/issues](https://github.com/cody-hutson/pmo-platform/issues).

## Reversibility

EXPENSIVE / HIGH confidence. The file changes come out in one operation by reverting the release. The eight labels this release created do not — labels are repository state rather than repository content, so any item that has acquired one keeps it, and each must be removed by hand and only after the revert. The repaired label is the exception and must be left alone: it existed before this release in a broken form, so deleting it would remove a row the pipeline now uses and restoring its old value would restore the broken one. Rollback is operator-authorised; nothing rolls back on its own.

### Operator and engineering detail

**The Axis-1 symptom deliberately did not change, and that is stated in the corpus rather than only here.** #4179 shipped its unconfigured-adapter fallback and nothing else; the `delivery-engine` binding refit was deferred with cause. The measurement behind that call: `delivery-engine` carries `lifecycle_state` in 0 of its 12 files while `entity-lifecycle-protocol.md` § 3.10 names it as the triggering agent on every transition of the Work Item base machine, and 6 of those 12 files already carry the DoD gate that same section names as the qualifying evidence for `in-review → done`. So the skill implements the evidence half of the transitions it is assigned and none of the state-writing half. [ADR-125](https://github.com/cody-hutson/pmo-platform/blob/main/core/ADRs/ADR-125-status-fallback-k1-binding-k4.md) § Consequences carries this statement so it survives past the plan: *"This decision does not change the operator-visible symptom. The state machine still has no bound writer."* A green Stage 8 on this release means the shipped scope was correct — it does not mean the originating symptom is fixed.

**The Axis-1 rows are a seventh grammar group, not a reuse of the existing status group.** That group's cardinality rule *is* the mutex, so homing the work-status values there would have made the two axes mutually exclusive by construction. The rows home in the shared base pack, and the `work-status:` name prefix is load-bearing independently of the grammar group: the runtime invariant discriminates by prefix, while the grammar group itself is read nowhere in the deploy script. The shipped shape, one row of the base pack's `[[labels]]` contribution:

```toml
[[labels]]
name        = "work-status: in-progress"
color       = "1D76DB"
description = "Work Item is actively being worked"
group       = "work-status"
axis        = 1
```

**The root cause of the malformed row was completed at Engineering and supersedes the Stage-5 reading.** A sibling release applied `status: in-progress` to an issue through the API at 2026-08-07T18:56:45Z — performing the very transition #1828 said never fires. Applying an unrecognised label through the API auto-creates it with a default colour and a null description, which is exactly how the row appeared live mid-release. There *is* a materialization path and it is ungoverned. A create-only fix would have shipped green with the defect intact, which is why the emit path reconciles as well as creates.

**The epic rollup surface is an audit, not a gate**, because the taxonomy exempts the epic type from the status-label invariant and a gate cannot assert on a field governance explicitly exempts. Hosting it as a deploy-time lint was rejected on the merits rather than on scope. Suppression is a comment marker with zero new labels — a new trigger for an existing state does not earn a parallel label.

**The sub-task status mirror was deliberately not resynced and the grammar rule not amended**, on a whole-corpus probe that found zero behavioural sites reading the mirrored value against a non-zero sensitivity arm. That decision is recorded as [ADR-126](https://github.com/cody-hutson/pmo-platform/blob/main/core/ADRs/ADR-126-sub-task-status-mirror-not-resynced.md).

**Parity residual: MISSING went 11 → 3, reduced by 8.** The remaining three are the deliberately-excluded triage rows. This corrects an earlier figure of 12 → 3 — the row that was reconciled rather than created was name-present all along, so it was never counted in MISSING and reconciling it moved that count by zero. A close-out re-measurement confirms MISSING = 3 against a non-empty ORPHAN arm.

**ADR numbering resolved by merge-time renumber, which is governed behaviour rather than drift.** Four in-flight branches held advisory claims on the same next-free slot simultaneously, which [ADR-115](https://github.com/cody-hutson/pmo-platform/blob/main/release/ADRs/ADR-115-adr-number-claim-binds-at-merge.md) says is correct: next-free is the mainline anchor plus one, never the maximum of the claimed set, and reserving a slot above visible claims is worse than a duplicate because a merged gap fails every subsequent check until filled. This release's records renumbered ascending at the pre-merge step and the post-merge contiguity check reads 126 records, contiguous, no duplicates.

**The release plan did not auto-rename, with cause.** `--stamp-slug` was attempted first — the pre-flight is pre-claim and mutates nothing — and HALTed because the plan carries zero version tokens, which the pre-flight treats as a broken stamp manifest. No gate was bypassed: the slug-primary conformance check is window-gated on token presence and skips cleanly. The rename was performed by hand in the close-out. The upstream cause is filed as [#5063](https://github.com/cody-hutson/pmo-platform/issues/5063): the template does emit the token, but seven of the eight slug-primary plans on disk carry zero, because the one cell that holds the token is also the only place to record the bump-class determination.
