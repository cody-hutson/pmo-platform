# One discoverable home for platform config, and a whole-journey onboarding map

2026-06-13 · v1.14

The platform's operator-configurable choices now resolve from one declared surface with a documented precedence order and a catalog that lists every field, its default, and where to set it — instead of being scattered across governance files and reference specs. Alongside it, a new onboarding map lays out the whole clone-to-working-install journey and names where each host choice — your code repository, ticketing system, knowledge base, and AI tool — plugs in.

## Who this affects

- Anyone customizing platform behavior (release sizing, bundling frame, release-class default, calibration cadence) — those choices now live on one resolvable surface with a published catalog
- Anyone setting up the platform from scratch — a single map now orders the steps from clone to working install and shows where each host system attaches
- Release operators — the release planner and executor read their configurable fields from this surface at the start of a run

## What changed for everyone using the platform

- **Every platform configuration field is now discoverable in one place.** A single catalog lists each configurable field — what it does, its default, and where to set it — and a resolver decides the effective value from a clear precedence order (a per-project setting wins over a global default; an individual override wins over a project setting). *Why it matters:* you can see and change what is configurable without reading every governance file, and the plug-and-play promise (bring your own methodology and choices) now has a surface you can actually query.
- **Configuration is split into two surfaces by concern.** Your environment and identity (who you are, your paths, which host systems you use, your delivery approach) live on one surface; tunable platform behavior (bundling, release-class default, calibration) lives on another. *Why it matters:* the security-sensitive identity settings stay separate from the freely-tunable behavior settings, so the two are governed and changed independently.
- **A whole-journey onboarding map is now available.** A new map orders the path from cloning the repository to a working install and names four uniform extension points where each host choice — code repository, ticketing, knowledge base, and AI tool — plugs in. *Why it matters:* a new user has one place that shows the full arc and exactly where their own systems attach, rather than stitching the picture together from separate install and getting-started pages.

## Finding and managing your configuration

- **Where it is.** Every configurable field — what it does, its default, and where to set it — is in the configuration catalog at [`docs/platform-config-reference.md`](../../../docs/platform-config-reference.md). Start there.
- **How it arrives.** The config templates ship with the platform; `./install.sh` lays them down as composition-surface seed files (your custom additions survive updates). After install, two surfaces hold your choices at your operator config path: `operator.toml` (environment + identity + host choices — code repo, ticketing, knowledge base, AI tool) and `platform-config.toml` (tunable behavior — bundling frame, release-class default, calibration).
- **How to change a value.** Set it on the surface that owns it, at the scope you want. The resolver applies the most-specific setting (a per-project value beats a global default; an individual override beats a project value). Setting a value for your own scope is just an edit — no PR; changing a *shipped default* is a governed change. Full precedence + update rules: the **Platform-Config Resolution Protocol** in [`core/governance/OPERATIONS.md`](../../../core/governance/OPERATIONS.md); the onboarding map's **Configure hosts** step ([`docs/ONBOARDING_JOURNEY.md`](../../../docs/ONBOARDING_JOURNEY.md)) shows where it fits in setup.

## Known limits

- This release lands the configuration mechanism, the resolver, and three wired consumers as the foundation — it does not migrate every historically-scattered configuration item onto the new surface. Remaining items move over as later work needs them. The onboarding map names the four host extension points; the host adapters themselves ship in later releases.
- Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. A single `git revert -m 1` of the release pull request removes the new configuration surface, resolver, and onboarding map; the change is additive (new templates, a schema, a catalog, an onboarding doc, and a resolution protocol) with no data migration to unwind. The standard 30-day outcome window applies.

### Operator and engineering detail

**Release shape.** `novel` release class, CHEAP reversibility, two issues on one branch (D-C SINGLE; plan committed as Engineering Commit 0), serialized #22 → #703, one release PR (#759; merge SHA `71047a527eed34d24a0bf059acfc73c20b7ec6b5`; 20 tracked files), signed-annotated `v1.14` tag at the merge SHA (ED25519 signature valid; zero signing bypasses). The milestone carried no `## Release Class` H2 at planning, so the class was declared fresh (`novel`) and Stage 5 activated release-wide (both issues deferred substantial design to Solutioning).

**#22 — unified platform-config surface + 5-rung hierarchy resolver.** The config surface was reframed off the issue body's stale "new YAML/MD file" premise once the hub verified the surface is not greenfield (the operator-identity template, the composition-surface spec, and the deploy rung-reader already existed). It split into two Layer-1 templates by concern — an operator environment/identity template and a platform-behavior template — with a field schema, a human-readable catalog under the docs tree, and the **Platform-Config Resolution Protocol** authored into the operations governance file (the 5-rung most-specific-wins cascade, a 3-level default-fallback that never hard-fails a release, and a two-track update governance split on the Layer-1/Layer-2 boundary). The protocol's cutover SHA is anchored to this release's merge commit; the introducing release is itself exempt per the reflexive-pipeline-loop discipline. Three consumers are wired as worked examples (the release planner and executor resolve named fields at session start; the deploy script extends its rung-reader to the new behavior surface). Scope was mechanism + resolver + three wired consumers, not a migration of every scattered item. The split rationale is recorded in ADR-022.

**#703 — onboarding-umbrella spine.** A new onboarding-journey document maps the ordered clone→working-install arc with four uniform extension-point blocks naming where each host adapter (code repository, ticketing, knowledge base, AI tool) plugs in. Stage 5 set the boundary explicitly: the document is the journey spine plus the extension-point contract, not a re-statement of the existing getting-started and first-steps walkthroughs; Stage 8 verified non-duplication. The journey spine is the surface host adapters compose into in later releases; it is linked from the README's getting-started region.

**Skill version stamp + packaging.** The release PR stamped the release-planner and release-executor skill definitions at the prior version in error; the Stage 12 close-out re-stamped both to v1.14 and rebuilt their packages so the packaged artifacts embed v1.14.
