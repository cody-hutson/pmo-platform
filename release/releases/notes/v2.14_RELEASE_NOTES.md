# A standard way to roll out pipeline changes and plan retiring human checkpoints

2026-06-21 · v2.14

The platform now has one named convention for how a change to its own pipeline is introduced, watched, enforced, and eventually retired — and a companion schema for inventorying every place a human is still in the loop and planning each one's phase-out. This is foundation: it standardizes language and structure that were previously scattered, and it does not change any decision a human makes today.

> **Skip the rest** unless you maintain the platform's pipeline, governance, or deploy checks.

## Who this affects

- The workspace operator and anyone authoring or reviewing pipeline / governance changes. There is no change to how project work, status outputs, or skills behave for everyday users.

## What changed for everyone using the platform

- **No change to everyday platform behavior.** This release adds two reference documents and one non-blocking deploy check; it does not change any skill output, status report, or decision a human makes. <!-- impact:foundational -->
- **A new self-check on deploy can flag a malformed phase-out inventory.** If you keep a (local) inventory of human-in-the-loop checkpoints, `deploy.sh --check` now validates its structure and reports problems without stopping the deploy. *Why it matters:* a structural mistake in that inventory surfaces as a warning instead of silently passing.

## Known limits

- The convention and schema ship as the foundation only. The *populated* inventory of checkpoints and their retirement plans lives in your local instance (it is not part of this public release), and the new deploy check runs in logged-but-not-blocking mode for now.
- Nothing is actually retired in this release — it establishes how retirement will be sequenced, not which checkpoint goes first.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. Every change is additive reference text plus one warn-only deploy check. Reverting the release merge restores the prior state exactly; no data migration, no skill rebuild required for the convention/schema themselves.

### Operator and engineering detail

**Progressive-rollout convention (#164)** — `core/standards/progressive-rollout-convention.md` lifts the three-cycle `shadow / warn / enforce` model that previously lived only inside the release-executor and adds the terminal `removed` rung — the end-state of the autonomy-phase-out program. Each of the four phases is specified with all four contract elements (observable behavior, telemetry contract, advance criteria, retreat trigger). An audit table reconciles the existing in-platform usages (the release-executor's rollout ladder and the security-hook `warn / enforce / off` machine) into one place, graded PARTIAL rather than retrofitted — the convention is the canonical source; it does not author a parallel enum and does not rewrite the hook layer. Recorded in ADR-034 (lift-and-extend). The release-executor's `references/progressive-rollout.md` was re-pointed to cite the convention as canonical via `pmo-skill-editor` (the skill's `.skill` package was rebuilt at this close).

**Touchpoint + phase-out schema (#165)** — `core/schemas/touchpoint-phaseout-schema.md` defines the 16-field operator-touchpoint inventory plus a phase-out-plan overlay (`success_criteria`, `slo`, `risks` with FMEA severity/likelihood/detectability, `rollback_path`, `phase_sequence`). Its `current_phase` field references the #164 phase enum by name rather than hard-coding the list, so the two stay consistent by construction. The populated inventory (≥1 row per pipeline stage, plus pilot phase-out rows with full FMEA) is a K4 instance authored operator-local and git-ignored per ADR-012 — the corpus ships the grammar, not the content. A new `deploy.sh --check` (Check 40) validates an instance's structure when present, skips cleanly when the instance is absent (fresh clone / CI), and runs warn-mode-initial.

**Pipeline-context note** — this release was provisionally versioned v2.12, then re-versioned up to v2.14 at Stage 12 because a sibling shipped v2.13 mid-flight; `origin/main` advanced during the pipeline and a forward-merge reconciled one `deploy.sh` check-number collision (this release's touchpoint check became Check 40). For full implementation detail see the [RELEASE_LOG.md entry](release/releases/RELEASE_LOG.md#deployment-log-v214) and [the release plan](release/releases/plans/v2.14_RELEASE_PLAN.md).
