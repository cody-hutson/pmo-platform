# Every automation now registers before it ships

2026-09-03 · v4.52

Recurring platform routines used to be described in prose that named one host's scheduler directly — on an installation where none of those tasks had ever been registered. This release gives every routine one declared entry, a check that refuses an unregistered one, and a setting of your own that decides how, or whether, it fires.

> **Skip the rest** unless you add or maintain a recurring platform routine, or you follow the install guide to set scheduled tasks up.

## Who this affects

- Anyone adding or maintaining a recurring or scheduled platform routine.
- Anyone following the install guide — it no longer tells you to register tasks on a scheduler the installer cannot reach.
- Anyone auditing which routines the platform claims to run.

## What changed for everyone using the platform

- **Every recurring routine now has one declared entry.** A routine states its identifier, cadence, trigger, entrypoint, governance ceiling and rollback cost in a single registry row instead of in prose scattered across the documents that describe it. *Why it matters:* you can read the whole set of things the platform claims to run as one table, rather than inferring it from nine documents that each mention it in passing.

- **An unregistered automation is caught at check time.** A new check runs in both directions — a document that declares a routine with no matching entry fails, and an entry with no declaring document fails too. It runs when you validate your installation and again on every pull request. *Why it matters:* the gap between what the documentation says runs and what actually runs now surfaces as a named failure instead of an assumption nobody tests.

- **How a routine fires is now your setting, not a name in the documents.** A new `[adapters].scheduler` key in your operator configuration selects the backend, and it ships set to `none`. *Why it matters:* the same documents work on an installation that has a scheduler and on one that does not, so the platform stops assuming a particular host is present.

- **With no scheduler configured, routines tell you how to run them by hand.** Each registered routine prints a line naming itself and the exact command that invokes it, instead of going quiet. *Why it matters:* you can tell a routine that is waiting for you from one that has silently stopped happening — before this, an installation with no scheduler printed nothing at all, and that silence was the defect.

- **The install guide no longer names a scheduler it cannot set up.** The setup steps that pointed at one host's scheduled-task surface now point at the registry and at your own selector. *Why it matters:* following the install guide on a machine without that surface no longer leaves you holding an instruction you cannot complete.

## Known limits

- The new check reports an unregistered automation but is not yet one of the checks that can stop a merge on its own. Making it required is a repository-settings action taken outside this repository.
- There are two backend choices — the scheduled-task surface of whichever runtime you already use, or `none`. No general-purpose scheduler abstraction was built, deliberately.
- The routine documents stay where they are. The registry gives each one an entry, not a new home, so the descriptions remain spread across the standards and protocol folders.
- Two documents still mention a host scheduler illustratively — one describes a registration that does not exist yet, one is an example row in a table. Neither is a live registration, and the migration's own criterion states the exclusion so a later reader does not read them as unfinished work.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**CHEAP / HIGH confidence.** Everything here is additive: reverting the release commits removes the registry, the check and the adapter, and the routine documents return to their previous prose. Nothing on your installation changes on its own, because the scheduler selector ships set to `none`.

### Operator and engineering detail

**Three surfaces, not two.** The decoupling separates what runs, how it fires, and who governs it — and naming the governance ceiling as a *stored* field is what converts "the routine is governed" from a prose promise into a predicate the check can grade. The firing backend is deliberately cited and never stored: it is instance-local, so a git-tracked catalog holding it would move an instance-local fact across the public boundary, which is precisely the defect the hardcoded documents exhibited. One registry row, showing the six fields:

```
| id | cadence | trigger | entrypoint | automation_level_default | reversibility |
| `structural-audit-sentinel` | `0 9 * * 1` | `hybrid` | `release/references/protocols/structural-audit-cadence.md` | `recommend` | `CHEAP` |
```

**The migration measured rather than assumed.** Nineteen occurrences of the hardcoded backend token across nine tracked files fell to zero. The frozen historical release plans that also carry the token were deliberately not edited — they are audit trail — so the population is tracked-minus-frozen-plans, and the same probe run against the pre-merge parent returns nineteen across the same nine files. The zero is a measurement with a control arm, not a pattern that failed to match.

**The degrade contract is graded on content, not exit codes.** Four constraints hold the no-scheduler path honest: an install with no scheduler must exit zero with a `MANUAL` binding; a present backend must produce a fully-populated binding, which forbids the degenerate resolver that would satisfy the first constraint by resolving nothing; a genuine defect must still fail non-zero under every selector value including `none`, so `none` degrades the firing and never the validation; and the degraded outcome must carry the literal `MANUAL` token plus the exact invocation, per routine, so a degraded routine and a scheduled one are distinguishable from the adapter's output alone.

**One admission check, two surfaces, one predicate pair.** The check ships as deploy check 76 and as a CI workflow, both driven by the same conformance and coverage primitives rather than by two implementations free to drift apart from each other.

**Three identifiers that were correct when measured and stale when used.** The ADR number moved from 181 to 184 and the deploy check number from 75 to 76 between the moment this release measured them free and the commit that claimed them; both were re-derived at the claiming commit and landed correct. A third instance landed uncorrected: the new configuration key records the platform version that introduced it as `4.51` rather than `4.52`, because the version determination moved once more after that field was written. It is a metadata annotation with no behavioural effect, recorded here rather than quietly amended. The release's own recorded learning names the pattern — re-derive an allocated identifier at the commit that claims it, not at the measurement that found it free.
