# Claims the documentation makes about itself are now checked

2026-08-02 · v4.05

A document that says "the following six rules" and then lists seven, a pointer that stopped pointing at the right thing, an assistant reporting "0 problems found" from a search that could not have found any — all three are the same failure, and none of them was caught by anything. Four checks now catch them, and five live instances were fixed.

> **Skip the rest** unless you contribute changes to the platform, or you act on an assistant's report that something is clean, absent, or zero.

## Who this affects

- Anyone who acts on an assistant's statement that a search found nothing, a count is N, or a check came back clean.
- Anyone who contributes changes to the platform's documentation — a stated count or a style token you use now has to hold up.
- Anyone who follows citations between the platform's own documents.

## What you need to do

1. **Run the normal deploy step for your workspace.** The new reporting discipline ships inside two packaged assistants, so an existing install keeps the previous copies until it is redeployed.

Nothing is migrated, no settings change, and nothing else is required.

## What changed for everyone using the platform

- **An assistant reporting "nothing found" now has to show that it could have found something.** Reporting a zero, a clean, or an "N of M" now carries an obligation: name the exact command that produced it, state how large the population searched actually was, and run the result past two deliberate test cases — one the check must catch, and one it must ignore. A result that skips these is recorded as unproven rather than clean. *Why it matters:* the most convincing thing an assistant can tell you is that it looked and found nothing, and until now that sentence carried no evidence that the looking worked.
- **A stated count that disagrees with what it describes now stops the change.** Text that says "the four categories below" is checked against the list, table, or block underneath it, and a mismatch fails the change rather than shipping. *Why it matters:* this exact drift happened four times during a single earlier release and was caught only because a person noticed each time.
- **A style token used but never defined is now caught.** Referring to a named colour or spacing value that no theme actually declares is flagged instead of silently rendering as nothing. *Why it matters:* the failure is invisible in review — the text looks right, and only the finished page is wrong.
- **Five stale citations between the platform's documents now resolve correctly.** Two mis-numbered gate references, a detector that could not see decision logic laid out as a table, an under-specified rule for describing whole-file diagrams, and four stage notes describing already-shipped behaviour as a future target. *Why it matters:* following a pointer and landing on the wrong thing is worse than finding no pointer, because you act on what you land on.

## Known limits

- **The count check is deliberately narrow.** It runs against a fixed list of 73 already-known count-and-structure pairs rather than every count in the documentation, so a stated count outside that list is not yet checked. This bounds false alarms while the check earns trust.
- **The count check misreports when pointed at a single folder.** Asked to check one directory, it reports every pair outside that directory as broken — 73 false results. The check as it actually runs is unaffected, because it always runs across everything; the fault only appears under a narrowing option. Tracked at [#4458](https://github.com/cody-hutson/pmo-platform/issues/4458).
- **The de-duplication of repeated patterns did not reach every copy.** Two further copies exist outside the new shared library — one of which has already drifted and now classifies a heading differently from the canonical version. Tracked at [#4459](https://github.com/cody-hutson/pmo-platform/issues/4459) and [#4460](https://github.com/cody-hutson/pmo-platform/issues/4460).
- **Seven more stale citations of the same kind remain.** They describe a gate as having fewer criteria than it now has, and one of them computes a target figure from the outdated range. Tracked at [#4461](https://github.com/cody-hutson/pmo-platform/issues/4461).
- **The new checks can prove they catch problems, but not yet that they leave correct work alone.** The acceptance criteria for all three could not express "and it does not flag correct content", which is how the folder-narrowing fault above got through. Tracked at [#4463](https://github.com/cody-hutson/pmo-platform/issues/4463).
- Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:pipeline` label.

## Reversibility

MODERATE / HIGH confidence. Reverting the single integration commit removes both new checks, the reporting discipline, and the shared pattern library together; the five citation fixes revert with them, restoring the stale text. Nothing was migrated and no stored data was transformed. Two things a revert does not undo on its own: the two rebuilt assistant packages, which need the deploy step run again, and the committed baseline and fixture files, which become inert rather than disappearing. Standard 7-day rollback window.

### Operator and engineering detail

**The sequence was deliberately inverted so the discipline preceded its own consumers.** `#4195` was built first and the three lints after it, reversing the triage-time order at the Procedure 0 gate. The reason is narrow: `#4197`'s AC2 instantiates the probe-validity language verbatim, and `#4196`'s AC3/AC5 and `#4198`'s AC2 instantiate it as mutation controls — so building the citing cards first would have written acceptance criteria against a discipline that did not yet exist. No hard dependency edge existed between any two cards, making this ordering hygiene rather than unblocking. Both new checks visibly carry the result: each reports a denominator and both control arms as first-class output rather than a bare verdict.

`#4195`'s `applies_to` frontmatter binds **the act of claiming a verified result** rather than a skill class, which is why it reaches orchestrating agents and one-off sessions equally rather than only the audit skills. The copy-paste record form it ships, from Section 8.2:

```
**Probe:** <exact command>
**Denominator:** <N> (<how counted>)
**Control — sensitivity:** <input the probe must flag> -> observed <non-zero result>
**Control — specificity:** <near-miss input the probe must not flag> -> observed 0
                           (or: NOT TRIGGERED — <which PV-2c condition fails>)
**Extraction:** <bytes or lines read> for the subject; <same> for each control arm
**Result:** <N>
**Verdict:** CLEAN | INDETERMINATE (<missing element>) | BROKEN PROBE |
             OVER-MATCHING PROBE
```

**The two-armed fixture pair falsified two shipping candidates before they shipped.** The theme-token work built a committed fixture set carrying both must-flag and must-not-flag cases, and it earned its cost immediately. It rejected the heuristic that was on track to ship: a rival scoring **six times better on false positives — 8 against the shipped candidate's 51** — and it surfaced an implementation bug that a corpus scan was structurally incapable of finding, because the corpus contains no instance of the shape that triggers it. A check validated only against real content can only ever discover the defects reality happens to contain.

**Around twenty probe-shape failures were self-caught across Stages 5 through 8**, several by the orchestrating session rather than by a reviewer — the discipline catching its own authors while they were writing it. This is the strongest available evidence that the record format is usable under load rather than merely correct on paper.

**Both blocking CI gates root-caused to one defect, and it is a structural one.** A required check whose verdict is a property of the **repository** rather than of the **change under review** cannot be satisfied by the pull request it blocks. Two independent instances presented at once: the secret scanner, by design, scans full history, so any historical finding fails every subsequent PR forever — this was its second recurrence, filed as `#4185`; and the blast-radius check, by nondeterminism, failed roughly 30% of runs on `main` as readily as on the release branch, so its red told you nothing about the diff. Both were fixed in this release — the scanner narrowed to PR scope, the blast-radius check routed to its own declared determinism fallback.

**Late version binding paid off three times in one run; early number binding cost a seven-surface sweep in the same release.** Nothing about this release was bound to a version number before the merge — plan filename, branch name and plan prose all carried only the slug — so when sibling releases claimed `v4.02`, `v4.03` and `v4.04` **while this one was in flight**, each cost this release exactly nothing. The contrast is available in the same release and points the other way: **check numbers bind early**, a sibling took number 62, and the resulting renumber cost a verified sweep across seven surfaces. Same class of identifier, opposite binding time, and the cost difference is the whole argument.

**Stage 8 disagreed with Stage 7 on four of nine cards**, which is the point of grading acceptance against the card text rather than against a passing test suite. The disagreements were not flaky tests; they were gaps a green suite cannot express — acceptance criteria satisfiable by an outage state, criteria with no way to say "and it does not over-fire", and one criterion asking about the corpus while three consecutive stages answered about the lint. That last shape is the same inherited-unverified pattern carried across four stages, now filed at `#4462` for an owner or an explicit accepted-residual rationale rather than a fifth deferral.

**`ADR-092`'s claim-time stamp did not fire, for the third consecutive release, and the reason is a defect rather than a choice.** The mechanism is built and was exercised successfully once; it is gated on an argument whose pre-flight requires a placeholder token that no release plan currently carries, so passing the argument would halt the claim. The mechanism exists and nothing feeds it. Filed at `#4464`.
