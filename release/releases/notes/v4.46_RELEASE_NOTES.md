# Portfolio frameworks get a home, and a plan check stops missing files

2026-09-02 · v4.46

Portfolio-level governance frameworks had nowhere to live: the platform's methodology settings described how a single project runs, and a portfolio spanning many projects had no equivalent. This release gives that altitude a declared home, a setting to select one, and seven ready-to-use artifact shapes — while leaving everything about how individual projects run exactly as it was.

> **Skip the rest** unless you govern work at portfolio level, or you read the results of the platform's release-plan checks.

## Who this affects

- Anyone running governance above the level of a single project — a portfolio or a program spanning several projects
- Anyone who has read a full-coverage result from the release-plan check and taken it as evidence that every declared row was examined
- Anyone maintaining the platform's methodology settings or its template registry

## What changed for everyone using the platform

- **A portfolio framework can now be named in your configuration.** A new optional setting records which portfolio-level governance framework a deployment follows. It is empty by default, and nothing behaves differently until you set it. *Why it matters:* portfolio-level governance has a declared answer in configuration instead of an unresolved question sitting in a ticket.

- **Seven portfolio and program artifact shapes ship ready to use.** Portfolio charter, strategic alignment matrix, portfolio roadmap, risk profile, program charter, benefits realization, and a program record shape, all drawn from the PMI portfolio-management reference. *Why it matters:* you can start a portfolio-level artifact from a shipped shape instead of authoring the structure yourself.

- **Choosing a portfolio framework does not change how your projects run.** The new setting sits beside the existing project-level delivery-approach setting rather than beneath it, so a deployment can follow one framework at portfolio level while individual projects keep whatever approach they already use. *Why it matters:* adopting portfolio governance does not force a change to any project's way of working.

- **A release-plan check that reported complete coverage was discarding a tenth of what it read.** Its path reader did not recognise one of the platform's top-level directories, so it silently dropped 10 of 31 declared rows — including every one of the seven new artifact shapes this release adds — and still reported that it had interpreted all of them. *Why it matters:* a coverage result from that check now means the declared rows were actually examined, and rows it genuinely cannot read are reported rather than dropped.

- **The existing project-level content was left untouched, and that was verified rather than asserted.** The project-tier pack area shows no change at all in this release, checked by comparing it directly against the state before the release. *Why it matters:* nothing you already depend on at project level can behave differently because of this release.

## Known limits

- **The setting applies to the whole deployment.** It resolves at the deployment and individual levels only — there is no per-project override, and none is planned at this version, because a portfolio framework governs the portfolio rather than any one project beneath it.
- **One framework has shapes behind it.** `pmi` is the only value that ships an artifact-shape directory. A well-formed value with no shipped directory is handled as an unrecognised selection rather than an error, so it will not break a deployment that sets it early.
- **The new shapes are files to copy, not yet wired into any skill.** No skill reads the new directory automatically. Registration with the template registry deliberately waits until a skill declares it needs them, so the platform does not carry a mirror with no consumer.
- **This is the platform's third setting of its kind, and the three still share no common mechanism.** That question was routed to a separate design pass rather than answered here, so the new setting ships as a one-off by decision rather than by oversight.
- **Five decisions raised during this release are recorded open, not resolved.** They cover where this new altitude belongs on a roadmap, whether the three settings above should share one mechanism, an inconsistency between two of the platform's own checker families, a gap in how a mid-release scope change re-derives its file classifications, and a mis-diagnosis in the deployment runbook's guidance for a release whose pull request is opened late.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH confidence.** Everything in this release is committed files — one decision record, three specification and schema edits, one configuration template edit, seven new artifact shapes, three registry-documentation edits, and six rebuilt skill packages — so reverting the merge removes all of it together. A deployment that has already set the new configuration value keeps that value in its own configuration file; clearing it restores the default. No external system was touched and no data was migrated.

### Operator and engineering detail

**Where the content lives, and why both proposed homes were wrong.** #2577 carried an unresolved conflict in its own body between two mutually exclusive homes for portfolio-tier pack content: the delivery-approach pack area, and the neutral core. ADR-170 records the resolution — a framework-keyed subdirectory under the existing template registry — and, for each rejected home, the verified disqualifier that ruled it out rather than a preference. The decision is deliberately cheap to reverse: it touches none of the grammar any consumer already reads, which is why the project-tier area shows a zero difference against the pre-release state.

**The selector is a third orthogonal axis, declared as such.** The new field composes with the existing project-level delivery approach rather than nesting under it — a portfolio framework governs the portfolio a project runs *under*, so a Scrum project inside a PMI-governed portfolio is a valid and expected combination. Neither setting implies the other. The field resolves deployment-global at v1; the narrowing and its reason are recorded at the field's schema row rather than left to be inferred. This is the platform's third orthogonal parameterization axis after delivery approach and deliverable type, which is past the platform's own threshold for promoting a repeated shape to a shared mechanism. That promotion was deliberately declined for this release and routed to a discovery pass asking what the three axes actually share, *before* any mechanism is designed — the decision record states the exclusion rather than leaving it silent.

The new setting as it appears in the operator configuration template, with the one shipped value:

```toml
[methodology]
# Portfolio-level governance framework for this deployment.
# Deployment-global; composes with delivery_approach rather than nesting under it.
# Open value domain: a lowercase-kebab id matching a shipped shape directory.
# Shipped at v1: "pmi".  Default "" = no portfolio framework selected.
portfolio_framework = "pmi"
```

**The checker fix is this release's own tooling repairing itself mid-flight.** The release-plan verifier's file-change-matrix path recogniser omitted `operations/` from its first-segment set. The consequence was not a visible failure but a confident wrong answer: it reported that it had interpreted every declared row and left nothing unparsed, while having discarded 10 of 31 rows — among them all seven artifact-shape additions that are this release's primary deliverable. The fix landed before the work it would have been blind to was engineered, and the plan's own risk row was reconciled to the measured post-repair state rather than annotated and deferred. After the repair the plan reports all nine declared additions recognised and delivered, with one disclosure residual: a bare single-segment directory row in the non-scope fence that the recogniser cannot resolve to a path, which is a documented residual class of the tool rather than a defect in this plan.

**Two consequences the plan re-derived rather than assumed.** Editing two template-storage standards documents moved the content hashes of six skill packages that mirror them, which the pre-merge package-freshness gate would have blocked; the packages were rebuilt and committed inside the release pull request, and the file-change matrix gained the twelve rows it had been missing. Separately, a probe written to verify one acceptance criterion was matching its own text and inflating its own count; it was rewritten to match the claim without matching itself, with its baseline stated explicitly.
