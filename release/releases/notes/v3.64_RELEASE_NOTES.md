# QA can now grade a release against its own acceptance criteria

2026-07-03 · v3.64

This release delivers the first working pieces of automated acceptance testing for the platform's own QA stage. Until now, the QA stage described how it *should* check a release against the acceptance criteria written on each GitHub issue — the process was on paper, but the machine-applicable grader that actually reads those criteria and scores them did not exist. This release builds that grader, gives it a standard report to render its verdict into, and — separately — adds a quality check that catches a skill silently losing its "ask the user when unsure" behavior.

## What changed for everyone using the platform

- **QA can now grade a release against the acceptance criteria written on its GitHub issues.** A new `acceptance` grading type reads the acceptance-criteria list off an issue, judges each criterion against what the pull request actually delivered, and rolls the per-criterion results up into a single acceptance score for the release. *Why it matters:* "did we build what the issue asked for?" becomes a consistent, repeatable check with a number behind it — not a case-by-case judgment call that varies by reviewer.
- **Each criterion gets an honest, drift-aware verdict — not a forced pass or fail.** Every criterion is first checked for whether it can even be graded as written (it may have moved out of scope, gone stale, or depend on work that has not shipped yet); only a genuinely gradable criterion gets a plain pass / fail. A criterion that no longer applies is marked as such with a written reason, rather than being quietly scored as a failure. *Why it matters:* the acceptance score reflects reality — a moved or stale requirement does not drag a release down as if it were broken, and nothing is silently marked "not met" without an explanation.
- **The acceptance verdict now renders into one standard report with three reading levels.** A new acceptance-report template presents the result as a 30-second verdict, a two-minute detail view with the per-criterion matrix, and a deep-dive evidence-and-machine-readable layer — so a busy reader, a reviewer, and an auditor each get exactly the depth they need from the same report. *Why it matters:* the acceptance result is presented the same way every time, and you can stop reading at the level that answers your question.
- **The skill auditor now catches a skill quietly losing its "ask the user when unsure" behavior.** A new auditor check (G11) verifies that a skill which is supposed to ask you a clarifying question when your request is ambiguous still actually does so — flagging the case where a later edit removed that fallback and the skill now just picks an interpretation on its own. *Why it matters:* a skill that should pause and ask you instead of guessing cannot lose that safeguard unnoticed; a broken fallback is caught by an automated check rather than by someone happening to notice it in a transcript.

## Known limits

- **The acceptance grader is a grader-honored contract, not code-enforced.** Like the platform's five existing grading types, the `acceptance` type's rules live in a specification the grading agent follows — no validator enforces the type or the score mechanically today. The grading semantics are defined precisely; the enforcement is the grader honoring them, exactly as the existing structural and judgment grading types work.
- **The new auditor check (G11) is specified ahead of the input it needs.** G11's rules are written in full, but the auditor mode it belongs to does not yet receive the transcript-with-tool-calls input the check requires to run automatically — the specification is honest about that gap by design. G11 becomes a live gate once that input wiring lands; until then it is a complete contract waiting on its substrate.
- **This release lands the acceptance *machinery*, not the QA mode that consumes it.** These are the first executors of the acceptance-testing capability; the QA acceptance-review mode that will call them on every release is a separate, later piece of work. No existing QA behavior changed — this is net-new capability sitting ready for that mode to use.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**CHEAP / HIGH.** The release shipped as a single pull request and is fully git-revertable. Every change is an additive in-repo edit — a new grading-type specification and its eval fixtures, a new report template, a new auditor-gate specification, two skill-body edits (with their compiled packages rebuilt at close-out), one founding ADR, and a two-line wiring note in the QA stage spec — with no code path, no data migration, and no external deploy target. Rollback is reverting the merge commit, with no data-loss surface; the provisional-version gap left by the forward-only re-version becomes permanent per the versioning rule.

### Operator and engineering detail

Three work items closed the `84-executable-acceptance-testing` slice (RELEASE_LOG `#84-executable-acceptance-testing`, Release Class **novel**, **Outcome: SUCCESS**). The slice ships the first executors of the Stage-8 acceptance machinery whose *process* `stage-08-qa-testing.md` already defined, and lands ahead of #219 (the QA acceptance-review mode, milestone #161) that consumes it. Topology D-C SINGLE, P0 fully-serial, sequence #218 → #217 → #197 (#218 builds the framework the report renders; #217 authors the template; #197 is the independent auditor gate).

**#218 — the `acceptance` assertion type.** The sixth value of the eval-schema `evals[].assertions[].type` open enum (`structural | judgment | resolution | non-triviality | read-only | acceptance`), it grades *"does this satisfy the stated requirement?"* — distinct from `judgment` (quality) and `structural` (mechanical presence). It ingests an issue body's `## Acceptance Criteria` (or `## Completion condition (verifiable)`) block via `gh issue view`, grades each criterion, and rolls up a release-level acceptance score. The durable kernel — recorded in **ADR-071** (`core/ADRs/ADR-071-acceptance-assertion-type.md`, Accepted) — is a **two-judgment** grading model: a *gradability-class* judgment (gradable / not-applicable / needs-reinterpretation / blocked-upstream) and, for gradable criteria only, a *binary-satisfaction* judgment (PASS/FAIL, with a PARTIAL refinement). The two judgments **project** deterministically to the Stage-8 §5 six-value verdict enum (`MET | NOT MET | PARTIAL | N/A-WITH-RATIONALE | REINTERPRET-WITH-RATIONALE | FLAG-UPSTREAM`) — the enum is the SSOT and this type authors zero new verdict values. This reconciles the two governing consensuses in tension: the eval-writer binary-judge default (a six-way native judge reintroduces middle-cluster/verbosity bias) versus the Stage-8 requirement to emit the drift-aware six-value enum. The acceptance score uses an **all-drift-out** denominator (all three drift verdicts leave both numerator and denominator, uniform with the §5 out-of-gate treatment). Shipped files: `core/skills/eval-writer/SKILL.md`, `core/skills/eval-writer/references/acceptance-assertion-type.md` (the schema-authority home), `core/skills/eval-writer/references/rubric-templates.md`, `core/skills/eval-writer/evals/fixtures/acceptance-sample-issue.md`, `core/skills/eval-writer/evals/stage-gates/stage-08-qa-testing/evals.json`, and the stage-gates `README.md`. Both the type and the score are grader-honored contracts (no `assertions[].type` validator exists today — the DOC-ONLY-honesty posture is stated in the reference).

**#217 — the acceptance-report template.** `operations/templates/qa-acceptance-report-template.md` is the canonical template the Stage-8 QA spoke renders one report instance from per issue, carrying all six §6-Outputs sections (acceptance matrix, acceptance score, fitness assessment, Stage-7 escape log, lane distribution, overall verdict) organized top-to-bottom as three reader tiers (Tier 1 verdict — 30 s · Tier 2 detail + matrix — 2 min · Tier 3 evidence + machine-readable block — deep-dive). The reader-contract invariant is that each tier is self-consistent read alone (the score derives from the matrix; the Tier-3 machine block is a byte-faithful projection of the Tier-2 rows). The acceptance-matrix columns are the **co-design contract** with #218's `acceptance` type — the columns are exactly that type's §5 columns so report and framework agree by construction (`AC-ID | Criterion | Verdict (6-value) | Evidence | Severity (NOT MET only) | Drift-rationale (drift only) | Disposition` + footer roll-up). The template is wired into `release/references/pipeline/stage-08-qa-testing.md` §6 Outputs (the two-line render-from-template note). Placement was resolved at scope-lock to `operations/templates/` (the deploy-resolver requirement), not an invented path.

**#197 — pmo-qa-auditor gate G11.** `core/skills/pmo-qa-auditor/SKILL.md` gains a Mode A gate, G11 (Conditional-AUQ-Presence Verification), specified in full at `core/skills/pmo-qa-auditor/references/conditional-auq-presence-detection.md`. G11 fires when the output under audit is an **ask-when-ambiguous-tier skill's** output/transcript, and verifies an `AskUserQuestion` invocation trace is present **when** the trigger-match heuristic did not resolve a unique mode (the input was ambiguous) and correctly absent when it did. It is the audit-time detector for the failure mode where a future edit silently removes a skill's `## Mode Selection` fallback, so a mode is chosen without the operator being asked. G11 is the structural analogue of G7 (SKILL.md-scoped) and G8 (cascade-sweep-scoped): a file-type-conditional Mode-A gate with a deterministic Phase 1 and an LLM-graded Phase 2, coexisting with G1–G10. It reads the ask-when-ambiguous roster **live** from `OPERATIONS.md` § Mode Selection Protocol (it does not hardcode skill names — the roster-hardcode regression is documented as its own INPUT-class failure mode). G11 is a **spec-ahead-of-substrate** contract: its input (a transcript carrying AUQ tool-call traces plus the originating request) is not yet delivered by Mode A's single-artifact input, and the spec is explicit about that wiring gap — the same DOC-ONLY-honesty posture #218 took.
