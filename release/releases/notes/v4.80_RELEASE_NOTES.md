# Safety guards now see scripts hidden behind wrappers, quotes and subshells

2026-10-25 · v4.80

The command guards now check a script that used to slip past them behind a wrapper's own options, a quoted flag that closes early, or a substitution such as `$( )`, so a script that is not on the allowlist is refused or logged instead of running unseen. A GitHub write placed behind a prefix command's options is now logged as well, and nothing that was only being logged before has started blocking.

> **Skip the rest** unless your sessions run scripts through a wrapper such as `nice`, `sudo` or `timeout`, run scripts inside `$( )`, backticks or parentheses, or you review the guards' logged-but-not-blocking records.

## Who this affects

- Anyone whose sessions run a script through a wrapper command, a substitution or a subshell, on a workspace that has taken this release's guard bundle
- Operators who read the guards' logged-but-not-blocking records, or who decide when a logged check starts blocking

## What changed for everyone using the platform

- **A wrapper's own options no longer hide the script behind it.** `nice -n 10 bash <script>`, `stdbuf -o 0 bash <script>`, `sudo -u <user> bash <script>`, `env -u NAME bash <script>` and `timeout 5 bash <script>` now get the same verdict as `bash <script>`: a script run through a shell or `source` that is not on the allowlist is refused, and a script run directly or through another interpreter is logged. `nice`, `stdbuf` and `timeout` are now recognised as wrappers, and `if`, `while` and `until` are read like `then` and `do`. *Why it matters:* putting a wrapper in front of a command no longer turns a refusal into a silent run, while an allowlisted script still runs behind any of them.

- **A quoted flag that closes early no longer hides the script.** Spellings such as `bash ""-x <script>` and `zsh ''-x <script>` were allowed while the same command without the quotes was refused; they now get the unquoted spelling's verdict. *Why it matters:* the verdict depends on what the shell actually runs, not on how the flag happens to be quoted.

- **A "parse only" exemption applies only where the shell really parses only.** A `-n` placed after a word the shell does not read as an option, as in `zsh -s -O extglob -n <script>`, used to exempt the command while the shell ran the script; it no longer does. A flag cluster carrying `c`, such as `bash -ec '<program>'`, now has its program checked the way a plain `-c` always did. *Why it matters:* a command is exempted as a syntax check only when nothing actually runs.

- **Scripts inside `$( )`, backticks and parentheses are now seen, logged but not blocking for now.** A shell or `source` inside one of these used to run with nothing refused or recorded; it now writes a record and prints a notice, and it will be refused once the operator decides to turn that on. A script run directly or through another interpreter there is logged the same way. *Why it matters:* this was the widest gap the guard had, and every use of it now leaves a record you can review before the decision to block is made.

- **A GitHub write behind a prefix command's options is now logged.** `env -u NAME gh api -X POST …` and `timeout 5 gh api -X POST …` were never examined, while `env gh api -X POST …` was; the outbound guard now finds the write behind any option or operand and logs it the same way, and it will refuse it once that guard's wider rollout completes. *Why it matters:* the outbound guard's record now includes the writes that a prefix command used to hide, and no write it already refused is let through.

- **The decision on when two script checks start blocking is recorded: not yet.** The checks on scripts run directly and through non-shell interpreters stay logged but not blocking; their review now falls due on 2026-12-15 (Tuesday) and their deadline on 2027-01-14 (Thursday), together with the new substitution check. The script allowlist gained 32 of the platform's own Python tools, the ones those logs showed sessions running. *Why it matters:* the platform's own tools stop filling the logs, so the next reading shows what is actually left to decide.

## Known limits

- The new substitution check and the outbound guard's new finding are logged but not blocking until the operator decides otherwise. The substitution check's decision is owned by [#8549](https://github.com/cody-hutson/pmo-platform/issues/8549), and the outbound guard's by [#6195](https://github.com/cody-hutson/pmo-platform/issues/6195).
- Some spellings still get past the script check, each written down in the guard's own documentation and owned by a card: a split-string value for `env` written with shell quotes or carrying a slash ([#8491](https://github.com/cody-hutson/pmo-platform/issues/8491)); positions the walk does not reach, such as a `case` arm or `coproc` ([#8316](https://github.com/cody-hutson/pmo-platform/issues/8316)); a quote or space inside the script's own path ([#8318](https://github.com/cody-hutson/pmo-platform/issues/8318)); a quoted assignment value ahead of the command ([#8319](https://github.com/cody-hutson/pmo-platform/issues/8319)); a program fed to a shell on standard input ([#8321](https://github.com/cody-hutson/pmo-platform/issues/8321)); a wrapper option that takes a value but is not in the wrapper's row; and a command carried inside one string for another program to run.
- The outbound guard's finding does not reach a command carried as a string, a command word held in a variable, a leading word it does not know, or the spellings its own walk does not resolve ([#8315](https://github.com/cody-hutson/pmo-platform/issues/8315)); the shared command-position reader's own gaps are owned by [#8314](https://github.com/cody-hutson/pmo-platform/issues/8314).
- The filesystem guard's handling of the shell's parameter-transformation operators, such as `${VAR@P}`, is now documented as outside its coverage, with no change to the guard itself; its fix is owned by [#8322](https://github.com/cody-hutson/pmo-platform/issues/8322).
- A few commands that run nothing new are now refused or logged, and each works again when respelled: for example `sudo --list bash <script>`, `bash -eo pipefail -n <script>`, and prose after a `;` inside a quoted argument of a command that is not a known carrier. Text that only names a script inside a substitution, such as a code span in a commit message, can be logged.
- A workspace picks up this release when an update refreshes its guard bundle. The version this workspace reports changes to v4.80 on the first update after this release closes.

Report issues at https://github.com/cody-hutson/pmo-platform/issues, and report a suspected vulnerability privately as the [Security Policy](https://github.com/cody-hutson/pmo-platform/blob/main/SECURITY.md) describes.

## Reversibility

MODERATE / HIGH. Reverting the single release merge restores every guard as it was, and a workspace runs the restored guards only after an update refreshes its guard bundle; the version tag is kept as the record that the version was claimed. A revert reopens every gap this release closes, and the three decision records stay in history as written.

### Operator and engineering detail

**The script walk (BLOCK-DESTRUCTIVE-022).** Three cards change one walk in `core/hooks/block-destructive.sh`. A quote-led flag word is read as the word the shell hands the interpreter, so an early-closing quote no longer ends the walk (#7019). The parse-only grant for `-n` is withheld behind any word the walk cannot read as an option, a cluster carrying `c` opens a program string, and a program on standard input is declared outside the rule's reach (#7018). Every transparent wrapper's option grammar is read from one getopt-notation row per wrapper, a long option is resolved against the program's own option table the way getopt_long resolves it, and the four copies of the wrapper vocabulary are compared word by word on every suite run (#7020, ADR-227). New refusals behind a wrapper's options land on the always-enforce shell arm; a direct execution or a non-shell interpreter there is recorded at its own arm's phase.

**The second view (#7028, ADR-225).** A second view of every segment opens one command position after each `(` and backtick and runs the same walk there, after the first view has finished, so it can add an adjudication and never remove one. A shell or `source` finding there enters a third rollout family, `DESTRUCTIVE_022_ENCL_PHASE`, at `warn`. The carrier's quoted-argument exemption and the here-document receiver, both written for the head of the line, are now read at the enclosure too. Every row a second-view position writes carries `pos: "enclosure"`.

**The egress look-ahead (#7004, ADR-226).** Behind the unchanged head walk, BLOCK-EGRESS-007 looks for the first adjacent `gh` and `api` words later in a segment whose head resolved through a prefix command, and adjudicates that invocation at the rule's current phase, `shadow`. A look-ahead hit never advances the first-invocation counter, so no day-one refusal of a later write is withdrawn. The rule's would-fire row gains one key for these hits; a row the head walk writes carries none, and a refusal record carries none. A look-ahead row reads like this:

```json
{"ts":"2026-10-25T20:41:07Z","hook":"block-egress","rule":"BLOCK-EGRESS-007","tool":"Bash","phase":"shadow","reason":"would-fire","cause":"not-allowlisted","path":"repos/<owner>/<repo>/labels","pos":"look-ahead"}
```

A drain reader that selects shadow rows by `phase` needs no change; the graduation decision should read the `pos` rows apart, because a printed command behind a prefix word is recorded too.

**The filesystem guard (#7027).** No hook line changes. The readiness text for G2 of `block-fs-boundary.sh` now states what G2 reads, that the parameter-transformation operator family is not refused there, and which words the token walk never hands to the cascade, and the suite pins today's verdicts, each pin paired with a mutant copy of the hook that fails it.

**The graduation decision (#7026).** Rendered at the card's own operator gate on 2026-10-16: neither the exec arm nor the interpreter arm graduates. Both arming constants moved from 2026-09-03 to 2026-10-16, so Check 71 warns from 2026-12-15 (Tuesday) and fails from 2027-01-14 (Thursday), the same days as the enclosure family. The allowlist's non-shell section took its first 32 rows from the drain, ADR-150 records the decision and what consumes a Check 71 failure, and the classes that block each arm's graduation are named with their owners.

**The differential.** One tracked corpus, `core/hooks/tests/fixtures/walk-payload-corpus.txt`, holds 1,313 payloads with recorded verdicts — 1,003 for the script rule and 310 for the egress rule — and both hook suites re-grade every row on each run. No payload moved toward allow against the hook before its slice, except the declared precision rows of the wrapper slice, where nothing executes.

**How it shipped.** Seven cards on one branch, built serially in eight commit groups, with eight Stage 7 iterations across six of the seven slices. Stage 8 passed five cards and returned two as conditional, which the operator accepted at Stage 9 with Operator Override Records (#7004 AC-2; #7020 AC-2's closing sentence and AC-6's `sudo` rows) under a GO WITH CONDITIONS. The release merged at `963ba4ee` and claimed `v4.80` with a signed annotated tag on the first attempt, after the displayed version moved twice at Stage 12, from `v4.75` to `v4.79` and then to `v4.80`, as sibling releases claimed those numbers first. Stage 12 deployed the rules mirror; the hook bundle and the regenerated script allowlist followed from the primary checkout, the deployed `block-destructive.sh` and `block-egress.sh` hash-equal to the merged sources, and #7020's fresh-session probe passed against the deployed hook. The three decision records, renumbered under concurrent releases before the merge, were ratified Accepted at this release's Stage 13.
