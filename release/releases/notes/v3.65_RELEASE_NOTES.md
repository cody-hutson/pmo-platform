# The pipeline now tests what a release does, not just reads what it says

2026-07-04 · v3.65

Until now the release pipeline's quality stages could read a change's source and form an opinion, but they could not run it to see whether it actually behaves as promised. This release gives those stages an execution surface: acceptance criteria that describe behavior get a worked way to be exercised, cross-issue promises get checked as one integrated artifact before the go/no-go gate, and the automated invariant re-check that every gate's verdict leans on stops guessing from text matches and starts returning sound verdicts.

## What changed for everyone using the platform

- **A release's quality gates can now run a verification instead of only reading source.** Stage 8 accepts a domain-selected verification run as acceptance evidence, and acceptance criteria written as behavior ("given X, the system does Y") get a worked method for being exercised. *Why it matters:* a change that claims a behavior is now checked by observing that behavior, so "it says it works" is backed by "we ran it and it did."
- **Promises that span several work items are now tested together before the go/no-go gate.** Cross-issue acceptance criteria are expressed as testable predicates and checked as one integrated artifact ahead of the Stage-9 review. *Why it matters:* gaps that only appear when separate pieces have to agree are caught before release, not after — previously that cohesion lived in prose and was never actually tested.
- **The automated invariant re-check behind every gate's verdict is now sound.** The re-verification that confirms a release preserved its declared invariants no longer relies on brittle text matching (which was proven to fail a valid case and could have passed an invalid one); it now checks the right region and returns a correct pass/fail. *Why it matters:* the pass/fail your gates report can be trusted — a false failure won't block a good release and a false pass won't wave a broken one through.
- **A release plan's verification steps can now be run programmatically.** A new verification-automation script executes a plan's Verification Plan directly, as the shared engine behind the two checks above. *Why it matters:* self-verification that used to be a manual walkthrough is now repeatable and consistent from one release to the next.

## Known limits

- This release delivers the Stage-8 and behavioral-acceptance half of the execution surface; the Stage-7 runtime-suite half shipped in an earlier release. The two halves together give Stages 7 and 8 their full execution surface.
- A documentation-only release still passes Stages 7/8/9 unchanged — the new checks fire as no-ops when there is no behavior to exercise. They add rigor to behavioral releases without adding friction to content-only ones.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH.** The release shipped as a single squash-merged pull request and is git-revertable, but it changes shared verification machinery that the pipeline's gates invoke — the sound invariant re-verification in particular sits under every gate's verdict. Reverting is a days-not-hours operation because the next release cycle's gates would fall back to the prior (unsound) re-check; roll back by reverting the pull request and re-running the affected release's Stage-7/8/9 gates under the prior mechanism.

### Operator and engineering detail

Four work items closed the verification-execution-surface slice of the Pipeline Definition & Fitness epic (RELEASE_LOG `#70-verification-execution-surface`, **Outcome: SUCCESS**), moving the pipeline from "read the source and opine" to "exercise the deliverable and accept evidence." Release Class **cross-cutting** — the slice spans Stages 4/6/7/8/9/13 plus shared verification infrastructure, and #99 changes the invariant-re-verification mechanism every gate's verdict relies on. The build sequence followed the bundle-composition foundation → schema → surface → executor order: #99 → #170 → #103 → #227.

**Sound invariant re-verification (#99, bug, foundation)** — QC4-05/AV-1 invariant re-verification was grep/string-match based, with a proven false-FAIL and a possible false-PASS. It now re-verifies region-scoped and returns structurally-sound verdicts, protecting every downstream gate's verdict from the string-match failure modes. This is the foundation card — it lands first because the three surface cards depend on a trustworthy invariant check.

**Cross-issue ACs as testable predicates (#170, story, schema)** — cross-issue acceptance criteria are now expressed as testable predicates and verified by a release-scoped integration check that runs before the Stage-9 gate, replacing the prior prose-only, never-tested cohesion. This is the schema card — it defines the predicate form the executor consumes.

**Stage-8 execution surface + behavioral-AC worked example (#103, story, surface)** — Stages 7/8 gain a domain verification execution surface beyond doc/content review: Stage 8 consumes a domain-selected verification run as acceptance evidence, and behavioral acceptance criteria get a worked verification method. The Stage-7 runtime-suite half shipped separately; this card completes the Stage-8 and behavioral-AC worked-example half.

**Verification-automation script (#227, task, executor)** — a verification-automation script executes a release plan's Verification Plan programmatically and is the shared executor behind #170 and #103. It builds last because it depends on the predicate schema (#170) and the Stage-8 surface (#103) it drives.

The release ran the full 13-stage pipeline (single PR / single squash merge) and merged clean at `b1a2152` with no version collision — the Stage-12 dry-run confirmed next-free = v3.65. The four release issues carried no auto-close keywords on the integration PR and were closed at Stage 13 against their individual Stage-8 QA verdicts.
