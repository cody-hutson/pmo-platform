# Every change now says what it does to documentation, and close-out checks it

2026-10-25 · v4.79

Every work item that can ship a change now declares what it does to documentation, including retiring a document, and the release close-out checks those declarations instead of only describing the check. How the platform's system documentation is organized is now a recorded decision, so the process pages later releases publish already have a home and a standard.

> **Skip the rest** unless you file epics or stories, write documentation that links to other files, or plan, run or close releases on the platform.

## Who this affects

- Anyone who files an epic or a story, and anyone who writes the documentation section of an improvement or bug report
- Anyone who writes documentation that links to a specific line of another file
- Anyone who plans, runs or closes releases on the platform

## What changed for everyone using the platform

- **Epics and stories now ask what a change does to documentation.** The epic and story forms carry the same required Documentation Impact section the improvement and bug forms already had; the observation and decision-record forms stay exempt, each with a stated reason. *Why it matters:* the larger items that ship most changes can no longer be filed without saying which documents they touch.

- **A change can declare that it retires a document.** The Documentation Impact section accepts a fourth action, retire, beside link, create and update, and the user-facing documentation folder is now in scope. A retired document that carries a status field is marked deprecated, or superseded with its successor named, and stays in place; one without that field is deleted; either way every reference to it is re-pointed in the same change. *Why it matters:* removing a capability no longer leaves its documents behind with nothing to say they are gone.

- **Close-out now checks documentation, logged but not blocking.** The two documentation checks at release close now run: one confirms that each document a change declared was actually changed, and the other that each design diagram a release declared was refreshed. Each records a finding for every document that fails, where before both were written down and never run. *Why it matters:* a release that declared a document but never touched it now leaves a record saying so.

- **Planning records the current process pages it read.** Triage and solutioning outputs now carry a line naming the process pages they read for the areas a change touches, or saying that no page covers the area yet, which is the expected answer until pages are published. *Why it matters:* once those pages exist, sizing and design start from a written picture of how the process works today.

- **A link can point at a line.** Both link checkers now read a line fragment such as `#L12` or `#L12-L20` as a line reference: valid when the file has those lines, reported when it does not, and never treated as a missing heading. *Why it matters:* a document can cite the exact lines it relies on without the link being flagged as broken.

- **How system documentation is organized is decided.** The platform's process documentation will be one generated catalog of process pages, each with its diagram written as text beside its prose, kept in a new catalog folder that the design standard now governs. *Why it matters:* the pages later releases publish have one agreed home and format, and their index is generated rather than kept by hand, so a page cannot silently drop out of it.

## Known limits

- No process page exists yet: the catalog folder holds only its README. The generator that builds the catalog's index, graph and views, and the check that a page's diagram still matches its text, ship in later milestones. Until then the planning line reads that no page covers the area.
- Both documentation checks are logged but not blocking until the operator decides to turn each one on. Run over past releases, the declaration check flags most in-scope work items, chiefly declarations written before this release tightened what a declaration may say.
- Nothing yet checks that the Documentation Impact section is present before close-out begins; that check is separate work ([#5062](https://github.com/cody-hutson/pmo-platform/issues/5062)).
- The intake assistant picks the new field up from the forms, but its own type map does not yet point to the rule that names which forms carry it; that pointer was deferred at review.
- A handful of minor gaps in the documentation-check engine, none visible to anyone filing or reading work items, are recorded on the parent epic for its next change ([#8114](https://github.com/cody-hutson/pmo-platform/issues/8114)).
- The version this workspace reports changes to v4.79 on the first update after this release closes.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

MODERATE / HIGH. Reverting the single release merge removes the decision record, the standard and glossary changes, the form and check changes, and the documentation-check engine in one step, and the version tag is kept as the record that the version was claimed. Work items filed on the new forms in the meantime keep their Documentation Impact section, which is harmless after a revert. The decision itself is expensive to change later, because every process page and generator will be shaped by it.

### Operator and engineering detail

**The decision record.** ADR-224, `Accepted` (operator-ratified at the process-baseline planning gate, 2026-10-23), answers the documentation-model spike: D1, one generated catalog of text process pages; D2, each page's visual written as Mermaid text in the same page; D6, one page per node plus generated views; and it settles placement outside the durable-corpus paths, minted stable page IDs, the platform-doc `status` field as the page lifecycle, and committed generated output under a CI drift check. It cites ADR-089's reason for rejecting a hand-kept index. The record was renumbered twice before merge, from ADR-221 to ADR-223 to ADR-224, by `renumber-adr.py`, each time because a sibling release merged first; the Stage 12 pre-merge commit `2fa31bf8` stamped its 9 deferred citations to ADR-224.

**The standard and the catalog folder.** `design-artifact-standard.md` gains § 13, which governs the catalog at `core/process-catalog/`: its page levels, from universe through value stream and sub-process to activity; the fields every page carries; seven link types; the generated index, graph and views; an authority rule (the catalog is derived and descriptive, skills, specs and code govern execution, and a disagreement is corrected in the catalog); and an evergreen-reference rule (a page cites a source by path plus a fingerprinted anchor, carries no bare issue or pull-request number, and the generator re-resolves the anchors in CI). The `state-lifecycle` flow class is added at every enum site, § 5 gains the retire step, and § 9's reciprocal-link rule gives way, for catalog pages, to the generated inbound index. The glossary registers six catalog terms, and the folder joins the shared link-check scope list, so its README must stay while that entry stands.

**Documentation Impact.** The epic and story forms gain the required field, the observation and ADR forms are exempt, and the action must be exactly `link`, `create`, `update` or `retire` — a qualified action, or an `[ASSUMPTION – CONFIRM]` line without a pipe, fails at close. The PR template gains a `RETIRED` status. The G-CL8 row of `gate-criteria-spec.md` now holds the one scope list (the union of its three earlier wordings, plus `docs/`), the form set, and a two-arm retire verification per D-RetireSemantics (A). Check 28 derives its form set from the issue-form folder minus the two exempt forms, so a form added later is checked with no edit. A declaration on the new forms reads like this:

```text
### Documentation Impact
docs/setup-guide.md | update | the install step this change alters
docs/legacy-install.md | retire | replaced by docs/setup-guide.md
```

An item with nothing to declare writes exactly `None — no documentation impact (rationale: <one phrase>)`; a bare `None` fails.

**The close gates.** G-CL6 (design-artifact refresh) and G-CL8 (Documentation Impact resolution) now run through one probe, `deploy.sh --check-doc-gates --gate g-cl6|g-cl8 --pr <N>`, over one engine, `check-doc-gates.py`. Exit `0` is CLEAN, `2` FINDINGS (advisory, one shared deploy-check warn-log row per failing subject), `3` N/A or NOT-EVALUATED (withheld, never a pass), and `1` only once the gate's committed sentinel, `.github/g-cl6.enforce` or `.github/g-cl8.enforce`, reads `enforce`. G-CL8 grades the release range and the release's whole issue population by a net diff, a `create` or `update` row on the document's body with its frontmatter excluded. Check 28 carries each gate's shakedown deadline from 2026-10-24: a warning at 60 days, on 2026-12-23 (Wednesday), and an issue at 90 days, on 2027-01-22 (Friday), until the operator records the decision by setting the sentinel to `enforce` or re-dating the gate's armed constant. This release introduced the gates, so its own close ran them informationally: G-CL8 read CLEAN over all four cards (2, 6, 9 and 14 declared rows resolved; 26 subjects out of scope), and G-CL6 read N/A, because this release's plan declares no Tier-A design artifact. Stage 7 review sent the engine back three times; the fixes made its file reads binary-safe, graded `create` and `update` rows on the body with frontmatter excluded, and cleared a code-scanning alert.

**The planning read and line anchors.** Stage 2 step A4.1 and Stage 5 step A1.7 read the current-state pages a change touches and cite each page ID with its `last_verified_commit`, or record that none covers the area, and the solutioning output template carries the `Current-state pages read:` line. Both `check-doc-links.py` and `check-release-links.py` read a `#L<n>` or `#L<n>-L<m>` fragment as a line anchor; the doc-link rule is a rules-mirror member, and the Stage 12 deploy refreshed its deployed copy.

**How it shipped.** Four cards on one branch, built serially: #8117, #8494 and #8119 under the first scope lock, and #8495 after a return to Stage 5 for re-specification. Stage 8 accepted three cards and conditionally accepted #8495, whose named residuals the Stage 9 GO WITH CONDITIONS accepted. The release merged at `001111e8` and claimed `v4.79` with a signed annotated tag on the first attempt, and Stage 12 deployed the rules mirror, nine files, with no skill or package changed.
