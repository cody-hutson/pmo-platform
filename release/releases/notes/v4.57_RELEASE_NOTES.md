# Agents now follow a written contract when writing into outside systems

2026-09-06 · v4.57

When an agent writes into a system your team reads — a ticket, a knowledge page — it now works to a written contract: durable state belongs in the record's own fields, and the comment stream stays a conversation with a person rather than an append-only log. Most of this release is agent conduct rather than anything you click, so the visible list below is deliberately short.

## Who this affects

- Anyone whose agents write into a ticketing system or a knowledge base
- Any operator who has added an entry to one of the hook allowlists

## What changed for everyone using the platform

- **Agents stop stacking dated log blocks onto records in other systems.** An agent now leaves at most one comment per record per run, addressed to a person with an ask, instead of appending a dated entry each time it runs. *Why it matters:* a record's comment thread stays readable as a conversation, rather than becoming an audit trail your team has to scroll past to find the actual question.

- **Durable state goes into the record's own fields.** Status, owner, dates and estimates are written to the fields that hold them, not narrated in a comment. *Why it matters:* you read a ticket's state from the ticket, instead of reconstructing it from the bottom of a thread — and the fields stay correct for anything that reports on them.

- **An agent that is not confident enough proposes instead of writing.** Confidence now gates the write: high confidence writes, middling confidence proposes the change for you to approve, low confidence asks. *Why it matters:* an uncertain edit into a system your team depends on no longer lands silently and leaves you to discover it.

- **Your own allowlist additions now survive an update.** Entries added through the maintenance helper are placed inside the region that regeneration preserves, instead of below it. *Why it matters:* a permission you deliberately granted stays granted, rather than disappearing the next time the file is rebuilt — which is a real loss of security settings, not a cosmetic one.

## Known limits

- The new automated check is logged but not blocking. It records what it sees and nothing you do is refused by it today.
- The check reaches part of the contract, not all of it. Two of the six rules cannot be decided from what an automated check can see — whether the text being replaced was written by a person or by an agent, and how confident the agent was — so those bind as conduct rather than as a check, enforced by the contract being cited in the skills that write to these systems.
- The narrow pattern this release widened in the new check still ships in four other detectors, three of them security checks. It is recorded as a named gap with its successor rather than quietly left inconsistent, and it is not closed here.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH confidence.** Reverting the release merge restores the previous corpus in one operation. The check itself is installed by the deploy step, so reverting the commit does not remove the installed copy — a full rollback needs a re-deploy as well. Because the check only logs, a faulty detector costs log noise rather than blocked work, which bounds the exposure while it is in shakedown.

### Operator and engineering detail

**The binding is the release, and it is measured.** The discipline states six normative rules for a write into a human-facing system the platform integrates with: durable state belongs in the record's fields (§1); the comment stream is not a register, one agent comment per record per run (§2); the platform's own tracker is out of scope and why (§3); the discriminator for overwriting existing text is **authorship, not staleness** (§4); never-write fields resolve from operator configuration (§5); and confidence gates every write (§6). The predecessor discipline it composes with carried the right posture and bound to **zero** skill definitions, which is why the behaviour it forbade kept reproducing. This release binds the new discipline into **six** skills — comms-writer, delivery-engine, daily-status, pmo-process-designer, intake-desk and health-check — plus a charter guardrail line and a decision-time-adherence trigger row. Measured 0 → 6 across the skill corpus, with a control arm on the same walk returning 57.

The shape the §2 rule refuses, and the shape it asks for:

```text
# refused — a dated log block, stacked on each run
**2026-09-06 — automated run 4**
Status moved To Do -> In Progress. Estimate recalculated.

# asked for — state in the field, comment addressed to a person
[field] status: In Progress
[comment] @owner — estimate needs your call before Friday; I have not changed it.
```

**The hook states its ceiling rather than implying coverage.** `block-external-seam-shape.sh` ships with four detection rules plus a fail-loud integrity rule, its own mode file and its own suite. Its declared reach is **§2 substantially, §1 partially, and §3 / §4 / §5 / §6 not at all** — §4 and §6 are unreachable *in principle* from a PreToolUse content hook, because neither the authorship of the text being overwritten nor the agent's confidence is decidable from an outgoing tool payload. Those sections are recorded as prose-declared predicates with **Runner: NONE**, so a miss is countable rather than invisible. The budget rule is permanently warn-only by design: §2 states the word budget as a ceiling a warranted reply may legitimately exceed, and blocking on word count alone would enforce something the discipline does not say. ADR-191 records that the hook is owned by its discipline rather than by the hook corpus.

**A correction, and the root cause underneath it.** The c3 standard's §9 justified its never-write invariant on a per-install allowlist-contents fact that is false against a real deployment, so a reader auditing the boundary concluded it was closed by configuration when it was not. The reason now states a dependency relation true of every install and names the deployed surface the hook actually resolves plus the two commands that read it, and states that neither surface is load-bearing for the invariant — so no future configuration change can falsify it again. Separately, `allowlist-add.sh` appended at end of file with no marker awareness while the composer captures only the span between the operator-additions markers, so an operator's grant was silently discarded at the next regeneration; measured defect rate **2 of 2** among deployed allowlists carrying operator additions. Entries now insert immediately before the first end marker, which is exactly the span the extractor preserves.

**The residual is named with its measurement.** A structured tool name splits on a double underscore, so a server id containing a single underscore made the split ambiguous and could escape the surface gate. This hook's class was widened to resolve it; four sibling detectors still carry the narrower class and still have the gap. The change here is **non-regressive by construction** — the narrow class is a strict subset of the wide one, so no name that matched before stops matching — and **inert on present traffic**, measured as zero newly-blocked and zero lost across a 216-name live tool population, because no connector today pairs an underscore-bearing server id with a comment-write verb. The gap closed is therefore latent forward protection, not an active leak being stopped. Sweeping the other four is a separate change decided on its own evidence, deliberately out of a scope override granted for one hook.
