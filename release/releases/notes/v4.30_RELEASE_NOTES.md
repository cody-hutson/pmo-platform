# Six release safeguards that never checked anything now do — and can fail

2026-08-15 · v4.30

Six checks in the release process were switched on but never examined anything, so they reported clean by default. Each one now looks at what it was meant to guard, and each was shown failing on a deliberately broken case before it was trusted green.

## What changed for everyone using the platform

- **A draft release can no longer be approved to ship.** The review stage that grants the go-ahead now reads the pull request's draft state at the moment it decides, on two independent readings rather than on one recorded note. *Why it matters:* a release still marked draft stops there instead of collecting an approval it should never have received.

- **Approved file additions are checked against what actually shipped.** The approved change list's declared new files are now compared against the merged difference, and a release with no change list at all reports itself as undelivered instead of being skipped. *Why it matters:* a file you approved into a release can no longer quietly fail to ship.

- **Closing a milestone waits on its open commitments.** The action-item check now runs immediately before the close and stops it while a commitment is still open; the two "nothing was recorded" outcomes require an explicit operator statement rather than passing on their own. *Why it matters:* a milestone can no longer close over work someone still owes — an earlier one closed with six open items because this check had never been connected to anything.

- **Elapsed release time is measurable at all.** Both ends of the measurement are now recorded — the moment a release is approved and the moment it finishes deploying — and a deploy in which every target failed reports no elapsed time rather than a number. *Why it matters:* you can see how long a release actually took; this one took 29 minutes.

- **The overlap check can see branches that have no pull request yet.** It previously accepted only pull requests, so in-flight work without one was invisible to it, and a read it could not perform came back looking clean. *Why it matters:* two releases editing the same lines are flagged before they collide, including before either has opened a pull request.

- **A check that reports green now has to prove it can report red.** Every safeguard this release touched was run against a deliberately broken copy and had to fail there before it was trusted passing. *Why it matters:* a passing result now means the check looked, rather than that nothing was wired to it.

## Known limits

- The action-item check stops the close when a release is closed through the close-out tool. A close driven entirely by hand reaches the same requirement through its own written checklist step instead, so the two paths share the rule but not the mechanism.
- Two of the new checks do not grade this release itself. They were added by it, so this release's own review ran under the checks that existed before it.
- Deploy records are permanent by design. Reversing the code does not remove rows already written to the append-only deploy log; they are honest records of a deploy that happened.
- Two known problems are recorded and not fixed here: a shared test suite that turns a required check red on a freshly cloned copy of the repository, and a deploy that only rebuilds packages being reported as though no targets succeeded.

Report issues at the repository issue tracker.

## Reversibility

CHEAP / HIGH. A single revert of the merge commit restores every code surface at once — no migration, no data change, no external state, no stored-format change. The one exception does not reverse: rows already written to the append-only deploy log stay.

### Operator and engineering detail

**The gate fires on the release that built it.** The Procedure 7a action-item gate is now dispatched immediately before milestone close, three-valued, with the two SURFACE states (`NOT-RECORDED`, `EMPTY-LEDGER`) requiring a closed-enum operator attestation that is itself emitted as a `decision` row. An attestation does **not** clear an `UNRESOLVED` verdict — an open commitment is dispositioned, never attested away. This release's own ledger carries one open row, `AI-001`, so the gate holds this release's close. That is the intended behaviour and the cleanest available demonstration that the gate is not vacuous: the milestone it was written for closed with six open items precisely because the gate had never been wired to the close it guards.

**A control is trusted only after it is shown failing.** The release's own definition of done required every control it adds or repairs to be demonstrated failing on a fixture with its observing step removed, and passing on the conformant control. Fourteen mutants, fourteen killed, zero survivors, forty-six assertions fired. Two of them are the pair that matters: `M14` removes the parity arm's ability to read its canonical source and `M15` neuters the dispatch harness's own close-witness — both go red rather than green-because-inert. The dispatch guard itself was previously unreachable by any test arm (the block sits in main-body code below argument parsing), so arm **F** extracts the two shipped dispatch lines verbatim from the tool's own text and executes them in a subshell under three mutually-controlling limbs: blocking gate leaves the close unfired at exit 3, passing gate fires it (the sensitivity limb), and a constructed `|| true` variant lets it through (the negative control).

**The File Change Matrix became a graded obligation.** `G-PR11` compares a plan's declared unconditional ADDs against `git diff --diff-filter=A` over the release range and reports `MATRIX-DELIVERED` / declared-but-absent / delivered-but-undeclared; an absent matrix now reads `MATRIX-UNDELIVERED` rather than `N/A`. The declaration lives in the plan's machine-readable path list plus its intent table, which is the shape a plan author now has to produce:

```
release/tools/tests/fixtures/fcm-conformant.md
release/ADRs/ADR-135-a-gate-ships-armed-by-a-committed-default.md
```

```markdown
| Path | Intent | Owning card(s) |
|---|---|---|
| `release/tools/tests/fixtures/fcm-conformant.md` | **ADD** | the matrix-delivery gate card |
| `core/schemas/gate-criteria-spec.md`             | EDIT    | the matrix-delivery gate card |
```

A glob arm was added after measuring 27 glob-bearing path tokens across 15 plans — an established authored form rather than an edge case — so a plan that declares a glob is judged rather than mechanically failed. The release ran the gate on itself: 13 declared unconditional ADDs, 13 delivered, both difference sets empty, with a drop-one control proving the instrument reports a missing row.

**Both cycle-time anchors, and the narrowing that makes them honest.** `T_GO` was missing because the hub never called the emitter it was mandated to call; `T_DEPLOY` because nothing emitted `deployment-status` at all. Both now emit, and `T_DEPLOY` accepts only rows carrying `outcome=resolved` — a deploy in which every target failed previously still produced a measured duration and, worse, entered the change-failure-rate denominator only, so the platform's change-failure rate improved as deploys failed. This release measured its own elapsed time at `+1781s` (29 minutes) from `2026-08-15T21:23:00Z` to `2026-08-15T21:52:41Z`, against a log in which that value had been structurally `N/A` for every prior release.

**Release identity is slug-primary, and it paid for itself.** Five version slots (`v4.25` through `v4.29`) were claimed by concurrent siblings while this release was in flight, so the plan's recorded determination of `v4.27` was superseded twice. Nothing renamed: branch, plan filename and hub state are all keyed on the milestone slug, and the version bound only at the Stage-12 atomic claim — first-attempt win, zero collisions. The prediction is not the claim.
