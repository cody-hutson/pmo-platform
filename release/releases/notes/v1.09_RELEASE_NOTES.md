# Scripting decisions now follow a governed promotion ladder (AS0–AS4)

2026-06-11 · v1.09

When repeated agent work should become a script — and what that script owes once it exists — is now a governed, citable decision instead of an ad-hoc call. A new tracked standard defines a five-rung promotion ladder, grounded in a completed census of all 71 tracked scripts and a ranked inventory of what to promote next.

> **Skip the rest** unless you write or review platform scripts, make promote-or-not calls in the release pipeline, or care how the platform decides what gets automated. Day-to-day status, comms, and project artifacts are unaffected by this release.

## Who this affects

- Anyone who authors or reviews platform executables — runtime guards, deploy checks, pipeline tools, or skill-bundled scripts — now has a placement, testing, and review contract to cite
- Anyone making or reviewing a "should this be a script?" decision (design and review stages now expect a recorded promotion decision with named triggers)
- General platform use — status outputs, comms, project artifacts — is unaffected; nothing changes operationally this release

## What changed for everyone using the platform

- **Every platform executable now sits on a named five-rung ladder.** From agent procedure (AS0) through documented command, tracked tool, and checkpoint-wired script up to autonomous guard (AS4), each form has defined obligations — where it lives, how it is tested, how it is found. *Why it matters:* "should this be a script, and how much script?" now has a citable answer instead of being re-argued from scratch each time.
- **Promotion is gated by evidence triggers and blocked by counter-signals.** Five triggers (repetition, output variance, deterministic work class, misexecution risk, token cost) earn promotion; five counter-signals — including "the pattern changed recently" and "an existing guard already owns this failure mode" — block it, and each promoting change records its decision in the pull request. *Why it matters:* unstable or redundant patterns stop getting scripted into maintenance debt, and every promotion is reviewable evidence, not vibes.
- **Judgment never scripts end-to-end.** A judgment-class step may promote only its evidence-gathering substrate; the judgment itself stays with the agent (split promotion). *Why it matters:* automation makes the mechanical parts deterministic without quietly converting judgment calls into scripts.
- **Promoted scripts must ship discoverable.** The promoting change lands its point-of-use citation in the same pull request, so agents find the script exactly where the work happens. *Why it matters:* promoted tooling gets invoked instead of sitting unused.
- **Two worked examples ground the rules in real candidates.** The standard inlines the top promotion candidates from the executed inventory — intake-readiness content validation (a split promotion) and a catalog path-resolution check (a checkpoint wiring). *Why it matters:* script authors copy a worked pattern, not an abstract rule.

## Known limits

- This release ships **paper governance**: the framework itself carries no enforcement tooling yet. Discovery-anchor conformance checks, a script-registry spec, and the catalog path-resolution check from the worked example are named follow-up candidates, not shipped checks.
- The grounding census and ranked inventory are point-in-time artifacts kept outside the public repository (operator-instance, by decision). Freshness is governed by the standard's audit re-run trigger — five or more new tracked scripts, or a module restructure.
- The four promotion-ready inventory candidates are queued for post-release intake; the promotions themselves ship in future releases, not this one.
