# Release quality checks now run automatically and escalate only on failure

2026-07-10 · v3.68

The platform's QA skill can now execute the release pipeline's quality gates itself: it dev-tests a pull request, grades acceptance criteria one by one, and audits the release process — and the dev-test and acceptance stages invoke those checks automatically. You are pulled in only when a check fails or cannot run.

## What changed for everyone using the platform

- **Your release PRs get an automated quality review.** During a release's dev-test stage, the QA skill ingests the pull request and its release plan, runs a four-rung ladder of checks (structure, contract, content quality, integration), and posts the quality report directly on the pull request. *Why it matters:* every release gets the same depth of review, and the evidence lands where you already look — the PR thread.
- **Acceptance criteria are graded one by one.** At the acceptance stage, each criterion on a work item receives its own verdict under the stage's shared verdict vocabulary, consuming the acceptance-contract format shipped in an earlier release. *Why it matters:* you see exactly which criterion passed or failed instead of a single roll-up answer.
- **The release process itself can be audited on demand.** A new fitness-audit mode scores the pipeline against a 13-dimension rubric and classifies each finding as untracked, partially tracked, or already tracked against the backlog, emitting a dated audit artifact with a deep-dive queue. *Why it matters:* process gaps become a work queue you can act on, not anecdotes.
- **Quality checks fire without being asked.** The dev-test and acceptance stages now trigger the eval checks themselves and record a structured result for each run; a failing or erroring check escalates to you through the pipeline's existing feedback path. *Why it matters:* routine green runs no longer need your attention — escalation is the exception, not the ritual.
- **The escalation path caught a real defect on its first live run.** The first automated dev-test check ran on this very release and failed correctly — it detected a stale branch baseline, which was fixed and re-verified in the same run before merge. *Why it matters:* the automation is proven against a real failure, not only against green paths.

## Known limits

- Automated invocation covers the dev-test and acceptance stages; other pipeline stages still run their checks conversationally.
- The automation binds releases that enter those stages after this one; this release itself ran under the previous convention, apart from the recorded live pilot above.
- The fitness audit writes its dated audit folder to the operator's local analysis workspace, not to the public repository.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

MODERATE / HIGH confidence. A single revert of the release pull request removes the three new modes, their reference documents, and the automated-invocation protocol; no data migrates anywhere. From the next release onward the stage gates read the new eval-invocation clause, so a revert must also re-run the skill package and deploy sync. Undoable in days.

Branch and PR names retain the v3.67 label as cosmetic build-record labels; every durable artifact ships v3.68. Both abandonments are recorded in the re-version ledger.

**The three modes** — Mode G (Dev Testing) is the Stage-7 executor: PR + release plan in, the structural→contract→content-quality→integration eval-assertion ladder run, quality report out as a PR comment. Mode H (Acceptance Review) is the Stage-8 executor: it grades GitHub-Issue acceptance criteria per criterion under the Stage-8 enum by consuming the acceptance-assertion contract — it re-defines no rubric. Mode F (Release-Process Fitness Audit) is a producer mode emitting a dated audit folder (13-dimension rubric, UNTRACKED / PARTIAL / ALREADY-TRACKED classification, deep-dive queue the process-fitness cadence dispatches on). The new mode triggers and the eval-invocation record schema:

```
Trigger phrase → Mode (pmo-qa-auditor mode-selection table)
  "dev-test this PR" / "run dev testing on PR #N" / "run the DT ladder"   → Mode G — Dev Testing
  "acceptance review this PR" / "grade the acceptance criteria"           → Mode H — Acceptance Review
  "run the release-process fitness audit" / "fitness-audit the pipeline"  → Mode F — Release-Process Fitness Audit

Eval-invocation record (one row per suite execution, emitted in the executing mode's stage report)
| Suite | Registered-by | Result | Assertions (pass/fail) | Executor | Evidence | Timestamp |
|---|---|---|---|---|---|---|
| stage-07-dev-testing-gate | EI-S7-01 | PASS / FAIL / SKIP / EXCEPTION | structural 3/0 · judgment 1/0 | Mode G (DT spoke) | command / run pointer | ISO-8601 |

Trigger rows: EI-S7-01 (Stage-7 entry) · EI-S7-02 (Stage-7 re-entry) · EI-S8-01 (Stage-8 Phase B, entry-validated)
Result → gate projection: FAIL/EXCEPTION escalate via the Inter-Stage Feedback Protocol (Tier 1 [ADJUST] / Tier 2 [SCOPE CHANGE] / Tier 3 [PLAN REJECTION]); PASS/SKIP record silently.
```

**Register-don't-build** — the automation issue shipped zero new runners, verdict values, or gates: it registers invocation rows against the merged mode identifiers and projects results into the gate evaluator's existing metrics surface. Its autonomy posture is declared Tier-2 Bounded Auto with Tier-1 descent on FAIL/EXCEPTION. The live pilot exercised the whole projection chain: the Stage-7 check failed on a real branch-freshness defect, escalated Tier-1, the fix landed, the re-entry row re-fired and passed; the Stage-8 check passed (structural 1/0 · acceptance 3/0 · judgment 1/0).
