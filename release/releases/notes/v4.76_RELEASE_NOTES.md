# Eight CI and pipeline checks now cover the whole class they name

2026-10-18 · v4.76

Eight checks that each caught only the first case someone reported now cover every case of the same kind, and four more checks must pass before anything merges to the main branch. Four of the changes add a rule a contributor's own change can fail.

> **Skip the rest** unless you open pull requests on the platform repository, commit on a release branch, add a script to its tool folders or a test step to its install tests, or run a release-stamped deploy yourself.

## Who this affects

- Anyone who opens a pull request against the main branch
- Anyone who commits on a release branch
- Anyone who adds a script to the platform's two tool folders, or a shell-suite step to the install-tests workflow
- Anyone who runs a release through the pipeline, or a release-stamped deploy by hand

## What you need to do

1. **Only if you run a release-stamped deploy yourself** (`./deploy.sh --deploy --release <slug>`): name the skills to deploy, or pass `--no-targets` when the release changed none. The bare form, and an empty release key, now stop before anything is written.
2. **Only if you commit on a release branch:** do not put a closing word (close, fix, resolve, in any tense) directly before an issue number in a commit message. Write `References #N` instead. The required commit-message check now fails the pairing.
3. **Only if you add a script that begins with an interpreter line under `release/tools/` or `core/deploy/tools/`:** commit it executable (`git update-index --chmod=+x <path>`), or give it a row with a class and a reason in the exemption list. The deploy check fails otherwise.
4. **Only if you add a step that runs a shell suite to the install-tests workflow:** give it a `timeout-minutes` below its job's limit, or the required job fails.

## What changed for everyone using the platform

- **A closing word in a release commit message is caught before the merge.** The close-keyword rule now covers the pull-request title, the body and every commit message, and the required commit-message check fails a release-branch commit that pairs a closing word with an issue number. *Why it matters:* an issue is no longer closed by a commit message before its release has finished.

- **Four more checks must pass before a merge to the main branch.** The two security scans and the two eval-viewer test suites joined the required set, which moved from 18 checks to 22, and the reconciliation check that compares the checks workflows declare as required with the ones the main branch actually requires can now fail. *Why it matters:* a check that says it protects the main branch now does, and a disagreement between the two lists turns that check red instead of going unnoticed.

- **Platform tools stay runnable by their own path.** Sixteen tool scripts became executable, and a check now fails on any script in the two tool folders that begins with an interpreter line but cannot be run. *Why it matters:* running a tool directly gives you its verdict, not a permission error.

- **A hung install test stops at a stated limit.** All 37 install-test steps that run a shell suite, and each of the four install-test jobs, now carry a time limit, and a guard fails if a new step arrives without one. *Why it matters:* a suite that hangs fails its own step and names itself, instead of running for up to six hours before the host stops it.

- **A pull request that another release's merge made unmergeable is flagged at that merge.** Every push to the main branch now reads the open pull requests and flags each one that push left unable to merge, and a release reports the same at its own merge. *Why it matters:* a pull request whose checks have stopped running is no longer read as green.

- **A release's deploy is recorded as that release's, even when another deploy got there first.** The release pipeline now deploys a release's own changed skills by name and records it, and the deploy tool refuses a recorded deploy that names no targets. *Why it matters:* a release that deployed can no longer look the same as one that deployed nothing.

- **A warning line gives only the instruction its own check accepts.** Warnings no longer append a generic "flip the mode file" instruction; a check that records its graduation in the repository now says so, and a check with no such record says nothing. *Why it matters:* following a warning's advice no longer leads to a change its own check rejects.

## Known limits

- Four more checks stay out of the required set, each held until it graduates from logged-but-not-blocking. Ownership of two of those graduations, and the reconciliation check's known blind spots, are tracked ([#8424](https://github.com/cody-hutson/pmo-platform/issues/8424)).
- The reconciliation check turns red on a disagreement, but it is not itself a required check, so it does not stop a merge.
- The commit-message check runs on release branches only; on other branches the rule is stated and not checked. One shared closing-word grammar for every input is tracked ([#8425](https://github.com/cody-hutson/pmo-platform/issues/8425)).
- Install-test steps that do not run a shell suite are bounded only by their job's limit.
- The rule that an override marker carries a written reason now binds the issue-reference marker alone, and nothing checks that the reason is there ([#8423](https://github.com/cody-hutson/pmo-platform/issues/8423)).
- The unmergeable-pull-request sweep and the recorded release deploy have each run for real once, at this release's own merge. A 30-day window watches them, and the reconciliation check, on later merges.
- The version this workspace reports changes to v4.76 on the first update after this release closes.

Report issues at https://github.com/cody-hutson/pmo-platform/issues, and report a suspected vulnerability privately as the [Security Policy](https://github.com/cody-hutson/pmo-platform/blob/main/SECURITY.md) describes.

## Reversibility

MODERATE / HIGH. Reverting the single release merge restores the earlier tools, workflows and pipeline text, and the next deploy re-lays the rules mirror and the release hub. The four branch-protection registrations stay in place by default, because the four jobs and their required declarations predate this release. Deployment records already written stay, by the event log's design, and the version tag is kept as the record that the version was claimed.

### Operator and engineering detail

**The close-keyword discipline, every parser input.** `core/rules/git-workflow.md` states the rule once for the title, the body and every commit message, projected into the hub-spoke bridge, the Stage-12 and Stage-13 specs and the release hub's playbook. `core/deploy/tools/check-commit-close-keywords.py` runs as a step of the already-required `Commit-message depersonalization gate` job, on release heads only (CR-6), and enforces from its first run: its specificity was measured over the whole history first, 22 of 22 firings true over 5,465 messages (CR-7). An unreadable range reports NOT-EVALUATED, never clean. Every Engineering spoke runs the same tool before it pushes.

**Declared and live required contexts.** `core/deploy/tools/reconcile-gate-posture.py` now reads the public branch object, which returns the same list to any reader, and sorts a gap into three classes: declared required but not registered, held but registered anyway, and registered but declared by no header. A held context that is not registered is listed and is not a divergence. The `Gate posture reconciliation` workflow splits measurement from verdict: a measured divergence turns the verdict red, and a read that did not return skips it and warns. The gate-efficacy standard defines the registration track once and records a disposition for every context on it. The close-out smoke workflow reports on every pull request and declares its context, the conformance ratchet fails a required context declared on a path-filtered workflow, and the pull-request-body close-keyword gate is corrected to the advisory posture it delivers and held. The operator registered the four contexts at the Stage 9 gate; after the merge the reconciler reads `RECONCILED` — 22 reconciled, 4 held, 0 unregistered, 0 held and registered, 0 undeclared.

**The tool exec-mode invariant.** `core/deploy/tools/check-tool-exec-mode.py` reads modes, first bytes and the exemption list from the index, not the disk. It runs in `deploy.sh --check`, enforcing from its first day as an operator-ratified exception to the rollout convention, and on every pull request as an advisory job that turns red on a finding. A file that is sourced, imported or read as data stays non-executable through one exemption row, in this form:

```text
<repo-relative path>  # <class>: <reason>
release/tools/lib/frontmatter-strip.sh  # sourced-library: read with `source` by the release-body and close-out tools; defines one function and has no main
```

The class is `sourced-library`, `imported-module` or `fixture`; a row with no class, an unknown class, no reason or a pattern is a parse error, and a row that no longer applies is itself a finding.

**Install-tests step budgets.** `core/deploy/tests/test_install_tests_step_timeouts.py` derives the population from the workflow, 37 steps where the old guard named five, holds it to a committed floor and reports covered over total. Each step budget is three times the slowest observed run, rounded up to five minutes and never below five; the four jobs carry 70, 30, 130 and 15 minutes.

**The warn emitter's graduation token.** The shared warn emitter states no graduation form of its own. A check declares its form with the closed one-member token `committed-default`, which seven checks pass on nine findings lines, and the required emitter-contract suite fails a missing, misspelt or false token and a dial it cannot follow. No check's verdict or exit status moved.

**Darkened-branch detection.** `.github/workflows/sibling-merge-dark-branch.yml` runs on every push to `main` with read scopes only, and `release/tools/check-dark-branch.py` (a 65-arm self-test) decides which open pull requests that push newly darkened; a sweep that could not measure, attribute or cross-check is skipped, never passed. A release sweeps again at its own merge as Stage 12 Phase B1.1, every spoke that pushes to a release branch renders one `Post-push mergeability:` line, and Stage 7's roster record is informational. Both contexts are advisory and never join the required set.

**The release-stamped deploy.** Stage 12 Phase B4 runs for every release from the executor's worktree at the tip of `main`: it asserts the release key non-empty and reads it back, derives the release's skills and packages from its own merge, keeps those the deploy roster lists, and deploys them by name, or declares `--no-targets`. Phase C2 reads the `deployment-status` rows back by the recorded slug. The post-merge hook is unchanged and a test pins that it forwards no release key; ADR-219 records the decision and the rejected alternative, teaching the hook to stamp. This release's own Stage 12 was its first live run: one `deploy-rules-mirror`, one `deploy-skill` and one `deploy-package` row under the slug, all resolved.

**The declaration-obligation rule.** The repository-integrity rule now scopes the written-reason obligation to the issue-reference marker, the one its matchers read, and carries the same `Runner: NONE` label as the close-keyword passage; for any other marker it sends an author to that gate's own failure output. No gate's verdict changed.

**How it shipped.** Eight cards landed on one branch as one merge at `602bf079`, claimed as `v4.76` with a signed annotated tag on the first attempt. The rules mirror and the release hub were deployed and verified by content at Stage 12. The release hub's `version:` restamp and its package rebuild ride the Stage-13 chore pull request, and its redeploy follows that merge.
