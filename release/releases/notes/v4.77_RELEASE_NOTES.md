# Dependabot pull requests get the personal-data check's verdict on their own run

2026-10-18 · v4.77

A Dependabot pull request that changes no file in the scanned folders now passes the personal-data check on its own run, with no maintainer push and no secret to set up. One that changes a scanned file fails until a maintainer pushes, and the check now fails, instead of passing, on any change it cannot read.

> **Skip the rest** unless you review or merge Dependabot pull requests on the platform repository, or open pull requests on it that change a file whose name git has to quote or a binary file in its scanned folders.

## Who this affects

- Anyone who reviews or merges Dependabot pull requests on the platform repository
- Anyone whose pull request changes a file whose name git has to quote, or a file git shows as binary in a scanned folder

## What you need to do

1. **Only if your pull request changes a file whose name git has to quote** (a name carrying a `"`, a backslash or a control character), in any folder: rename it. The personal-data check now fails such a pull request instead of skipping the file.
2. **Only if your pull request changes a file that git shows as binary under `core/`, `release/`, `operations/` or `packages/`** (outside `release/releases/`): make it readable as text, by removing the NUL byte or the `.gitattributes` entry that marks it `-diff`. Only a compiled skill package under `packages/` may be binary there. The check now fails such a change instead of passing it unread.

## What changed for everyone using the platform

- **A Dependabot pull request outside the scanned folders passes on its own run.** The personal-data check (the `Depersonalization gate`) now works out which files a pull request changes before it reads its configuration, so a Dependabot update that touches none of the scanned folders passes on the bot's own run, with no maintainer push. *Why it matters:* a routine dependency update no longer sits red until someone pushes to its branch or an administrator merges past the check.

- **A Dependabot pull request that changes a scanned file fails until a maintainer pushes.** A run Dependabot starts cannot read the check's configuration, so an update inside the scanned folders fails rather than passing unscanned. A maintainer's push to the branch re-runs the check with its configuration and scans the bot's change. *Why it matters:* no dependency update reaches the main branch unscanned, and today the push that clears it is the one the package rebuild already needs.

- **No secret to set up.** This release adds no secret and keeps no copy of the check's configuration in Dependabot's own secret store. *Why it matters:* there is no setup step to forget, and the personal data the check matches is stored in one place.

- **The check fails when it cannot read a change.** If it cannot list the changed files, read a file's added lines or run its scan, or it meets a file name git has to quote or a non-package file git shows as binary, the check now fails and names the cause. *Why it matters:* a check that could not look no longer reports the same pass as one that looked and found nothing.

- **Every run is scanned the same way, whoever starts it.** The check now matches the same name, email and handle on every run that reaches the scan, and it reads the handle from the repository owner instead of from whoever started the run. *Why it matters:* the old exemption that let a bot's run pass without scanning anything is gone.

- **Dependabot pull requests carry the `dependabot` label.** The label the Dependabot configuration names is now declared in the platform's label set, and it is created as this release closes. *Why it matters:* these pull requests carry the label the security policy says they carry, without a "labels could not be found" comment.

- **The security policy names every required check a Dependabot pull request can fail.** Its table lists the three required checks that can stop a Dependabot update, why each one fails, and what clears it. *Why it matters:* a maintainer can tell why a dependency update is red and what to do about it.

## Known limits

- No Dependabot pull request has opened since the merge, so the bot's own-run behavior is shown by the check's test suite, which runs the check's own steps, and not yet by a live update. The originating issue stays open until the first Dependabot pull request after the label exists shows the verdict on the bot's run and carries the label ([#8092](https://github.com/cody-hutson/pmo-platform/issues/8092)).
- A misconfigured identity secret is now reported on the next pull request that changes a scanned file, and not on one that changes none.
- The check decides whether it is running on the main repository from the repository's name, so a rename or a transfer would quietly switch it to fork behavior ([#8479](https://github.com/cody-hutson/pmo-platform/issues/8479)).
- Whether a changed line holding bytes that are invalid in the runner's locale matches depends on the grep implementation ([#8481](https://github.com/cody-hutson/pmo-platform/issues/8481)).
- Seven other added-line readers in the platform's tools still drop an added line that starts with `++` ([#8482](https://github.com/cody-hutson/pmo-platform/issues/8482)).
- Two process documents give a label-parity command that exits with an error as written ([#8480](https://github.com/cody-hutson/pmo-platform/issues/8480)).
- The other required checks that can stop a Dependabot update, the package-freshness check and the close-out smoke check, behave as before; the security policy gives their remedies.
- The version this workspace reports changes to v4.77 on the first update after this release closes.

Report issues at https://github.com/cody-hutson/pmo-platform/issues, and report a suspected vulnerability privately as the [Security Policy](https://github.com/cody-hutson/pmo-platform/blob/main/SECURITY.md) describes.

## Reversibility

CHEAP / HIGH. Reverting the single release merge restores the earlier check, its shared library and test suite, and the documentation; there is no out-of-tree state to withdraw, because no secret was added. The `dependabot` label is kept on rollback, since it is harmless once declared; if it is dropped instead, its label-set row is withdrawn in the same change. The version tag is kept as the record that the version was claimed.

### Operator and engineering detail

**Scope first, then the identity.** Gate 1 of `.github/workflows/repo-integrity.yml` now lists the changed files and applies the C6 scope filter before `identity_preflight` reads `OPERATOR_IDENTITY`. A pull request that changes nothing under `core/`, `release/`, `operations/` or `packages/` (outside the exempt `release/releases/`) passes there without reading the identity, whoever started the run. One that does reaches the preflight, which a run Dependabot starts cannot satisfy, so it fails closed until a maintainer's push re-runs the gate with the canonical secret; a later `@dependabot rebase` replaces that push. The handle is bound from `github.repository_owner` through `env:`, the resolution the ADR durability gate already uses, and `handle_preflight` requires it to be the canonical repository's owner. The bot-actor exemption is deleted, so the actor changes only a run-summary notice. `OPERATOR_IDENTITY` lives in the Actions store only and is bound to the scan step alone. On canonical, an empty literal set is now an `::error::` and exit 1; a fork keeps its notice and pass. The Stage 9 review chose this design over mirroring the identity into the Dependabot store, and ADR-220 records the decision and the alternatives it rejected.

**Fail-closed reads.** Three verdict functions in `release/tools/lib/deciders-carveout.sh`, `changed_files_verdict`, `added_lines_verdict` and `literal_scan_verdict`, report `UNEVALUABLE` when a read did not run to completion, and Gate 1 turns that, or an unrecognised verdict, into an `::error::` and a red run. The listing turns off git's quoting for high bytes, so a non-ASCII name is scanned under its real name, and it treats a name git still quotes as unreadable. A file git renders as binary fails unless it is a `packages/*.skill` package; an added line carrying a NUL byte past git's 8000-byte window reads as binary; a symlink is read like any file; an added line whose content starts with `++` is extracted like any other; and a scan that reports a match but prints no line reads as unreadable. Only a path with nothing of this repository's content at it is skipped.

**The fixture suite.** `release/tools/tests/test_deciders_carveout.sh` exercises every decision as effect, executes the scan step's own run block against a fixture repository, and pins Gate 1's call sites, ordering, pass arms and failing arms line by line. It reads 233 of 233 on `main` after the merge, against a 33-assertion baseline before the release, under bash 3.2 with BSD grep. The Stage 8 mutation set reads 53 of 54 killed; the survivor, a typo in the canonical repository literal, is the first follow-up below.

**The label and the documents.** `core/packs/_common/pack.toml` gains one Provenance row, which the label-parity gate reconciles against the live label set; its description is held to 98 characters because GitHub caps a label description at 100 and the parity gate compares descriptions exactly. The row, as committed:

```toml
[[labels]]
group = "provenance"
name = "dependabot"
color = "1F6FEB"
description = "Opened by Dependabot (version or security update); applied at PR creation. Persists through close."
applied_at = "PR creation (Dependabot, per .github/dependabot.yml labels:)"
```

`SECURITY.md` § Automated Security PRs carries a three-row table of the required checks a Dependabot pull request can fail, with the remedy for each, and says these runs receive only Dependabot secrets. `core/standards/secrets-handling-policy.md` §2 and §5 record the identity's single store and its update procedure, and the CI-configuration paragraph of `core/rules/git-workflow.md` § Repository-Integrity Gates states the scope-first order.

**How it shipped.** Two issues on one branch, merged at `0324b97f` and claimed as `v4.77` with a signed annotated tag on the first attempt. The rules mirror was deployed and verified by content at Stage 12; no skill or package changed. ADR-220 was renumbered from 217 at the main sync and is ratified `Accepted` at this release's close. The originating issue's three live checks (the gate on a Dependabot pull request's own run, the label applied, and the security policy's labeling statement holding) were deferred to the close by Operator Override Records at Stage 9, so that issue stays open until they are recorded.
