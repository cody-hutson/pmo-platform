# A release close now finishes in two passes and reports what its tools read

2026-10-03 · v4.72

A Stage 13 close can now run a first pass that leaves its chore PR open and a second pass after that PR merges, and neither pass halts on a check it deferred itself. Every verdict the close-out reports now reflects state its tools actually read, the reports it posts to GitHub carry no local paths, and the release's finished threads are locked at close by the tool rather than by a checklist step.

> **Skip the rest** unless you run or review a Stage 13 close, re-verify a release plan after its release merges, or comment on a finished release's GitHub threads from outside the collaborator list.

## Who this affects

- Anyone who runs a Stage 13 close, or reads its report on the close's sub-task
- Anyone who re-verifies a release plan after its release has merged
- Anyone outside the repository's collaborators who comments on a finished release's issues or pull requests

## What changed for everyone using the platform

- **A close can run in two passes without halting on itself.** A `--no-merge` pass now defers, and a `--dry-run` predicts, every check that needs the chore PR merged, and the report lists what the follow-up pass still owes. *Why it matters:* the first pass no longer stops on a false finding about a Release it chose not to publish, so the follow-up `--apply` after the merge is the one remaining step.

- **The follow-up pass finishes after its own chore PR has merged.** The resumed `--apply` now finds its chore PR whether it is open, merged or closed, and carries on to the end of the close. *Why it matters:* a close that was interrupted after its merge can simply be run again, instead of failing on a pull request that already did its job.

- **The report says what actually happened.** A chore branch that cannot be checked out now reads as a failure, the report header names the chore-PR outcome the run recorded, an attestation of the action-item gate is written to the event log, and the close-class telemetry is computed from the retro register produced before the close. *Why it matters:* you can act on each verdict as written, without re-checking it by hand.

- **No local paths in what the close-out posts.** The report, its JSON form, the gate-passage proof, the chore-PR body and the close comments replace the repository and home directories with `<repo>` and `<home>`. *Why it matters:* a close-out report relayed to a public issue no longer exposes the operator's username or local folder layout.

- **Finished release threads lock at close.** The close-out now locks every issue and pull-request thread on the release's milestone against comments from outside the collaborator list, and checks the count it locked against the milestone's own totals. *Why it matters:* finished threads stop collecting outside comments by a step that always runs and records its result; before this release the lock fired on 2 of the last 18 closes.

- **The cleanup preview lists the tracking refs it will prune.** The orphan-cleanup dry run now shows each remote-tracking ref the apply would prune, including those its own branch removals will make stale. *Why it matters:* the preview you approve is the cleanup the apply performs.

- **A release plan can be re-verified after its release merges.** The plan verifier grades a merged release against that release's own merge when run from a commit that contains it, and every failure names the range it compared. *Why it matters:* a re-check after the merge no longer reports delivered files as undelivered.

## Known limits

- The close-out's entry check still stops a close when more than ten of the release's issues are open, so a release whose pull request does not close its cards needs them closed before the close runs; this release's eleven were closed by hand at the start of its close (#5657 owns the redesign, #7490 the missing pre-merge check).
- A lock blocks only accounts outside the collaborator list, and it hides nothing. Reverting this release does not unlock threads that a later close locked; each is unlocked separately. Closes that ran before this release are not revisited.
- Path replacement covers the repository and home directories as the tool sees them. A path spelled another way, such as a resolved symlink, a `~` form or a location outside both directories, is not replaced, and diagnostics a tool writes to its error stream are not report text.
- The plan verifier still reads a merged release's delivered files as outside its range from three starting points: a main-branch commit whose plan names no merge (marked on the run), Stage 12's release-log branch before it merges, and the release's own branch tip. Passing the range explicitly grades all three.
- The machine-readable reports changed shape: a pruned tracking ref is now an object with `ref` and `action`, the cleanup report gains `tracking_ref_enumeration`, and the close-out's chore-PR outcome takes seven values. Nothing in the repository reads the old shapes; a parser outside it needs updating.
- The orphan-cleanup self-test still prunes real stale tracking refs in the repository it runs in (#7900).

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH. Reverting the single release merge restores all three tools, the Stage 13 specification, both decision records and the `release-executor` skill, which is then re-deployed from the reverted tree. Thread locks applied by closes after the merge stay in place until each is unlocked, and the version tag is kept as the record that the version was claimed.

### Operator and engineering detail

**Post-merge phases declare their `--no-merge` behaviour.** Every close-out phase dispatched at or after the chore-PR merge now declares exactly one behaviour for `--no-merge` — run, skip, record or defer — in one table inside the driver, and the deferral helper, both report renderers, the `--help` inventory and the self-test all derive from that table ([ADR-213](https://github.com/cody-hutson/pmo-platform/blob/main/release/ADRs/ADR-213-post-merge-phases-declare-their-no-merge-behaviour.md)). Phase 15.55, which halted every `--no-merge` close on the Release it had itself deferred, now defers; under `--dry-run` its own-tag and ledger-parity gaps are predicted rather than asserted, as [ADR-158](https://github.com/cody-hutson/pmo-platform/blob/main/release/ADRs/ADR-158-dry-run-predicts-apply-asserts-mode-branch-placement.md)'s mode rule requires. A structural self-test arm checks that each deferring phase opens with the declared helper.

**Phase C5 is a close-out phase.** Phase 15.2, `lock_milestone_threads`, enumerates every thread on the milestone through the REST issues listing, which returns issues and pull requests alike, locks each unlocked one with lock reason `resolved`, reads the result back, and records one row: PASS with the locked list, SKIPPED with an explicit zero, or FAIL with per-thread errors. Its count check compares the enumerated total with the milestone's open plus closed counters, both of which count pull requests, so the comparison no longer reports a release's own pull requests as a phantom gap. It never blocks a close, it defers under `--no-merge`, and it predicts statically under `--dry-run` ([ADR-212](https://github.com/cody-hutson/pmo-platform/blob/main/release/ADRs/ADR-212-lock-at-close-is-a-close-out-phase-over-every-milestone-thread.md), which supersedes Decision 3 of [ADR-076](https://github.com/cody-hutson/pmo-platform/blob/main/release/ADRs/ADR-076-comment-author-association-trust-boundary.md) in part, and was ratified at this release's Stage 13 gate).

**The resume path and the report's outcome field.** Phase 11 now resolves the chore PR over its whole open, merged and closed partition through an owner-qualified REST lookup, so a fork's same-named branch can never resolve as the close's chore PR, and a merged PR is confirmed by containment against its own head. The phase records one of seven outcomes, which the report header and the JSON report both render; the collapsed "dry-run or not-yet-created" wording is retired. Phase 5 now judges a checkout by where HEAD lands after it, so a branch held by another worktree fails with git's own message before anything is committed.

**Telemetry, attestation and the verifier's range.** The retro register is produced at Phase A7.2, before the close-out runs, and phase 6.8 passes its resolved path to the telemetry tool, recording WARN rather than a silent N/A when it is absent. The Procedure 7a attestation now passes both flags the event writer requires, and a failed write is reported with the writer's own message. With no explicit range, the plan verifier resolves the plan's own merge from the release log and grades from it when the starting commit contains that merge; a file that is in the tree but outside the range reads `declared-add-not-in-range`, distinct from an undelivered file, and every failure names its range.

**One redaction primitive at every sink and post site.** `_redact_paths` replaces the repository root and the home directory once, at the markdown and JSON report sinks and at the four places the driver hands text to GitHub; the phase record stays raw, and captured diagnostics are projected through one bounded helper.

**The shapes this release changed**, as the cleanup tool's JSON report and the close-out's JSON report now carry them on a `--no-merge` pass:

```json
{"tracking_ref_enumeration": "ok",
 "pruned_tracking_refs": [
   {"ref": "origin/chore/example-stage-13", "action": "PRUNE"},
   {"ref": "origin/release/example", "action": "WILL-PRUNE — stale after same-run remote-branch removal"}]}
{"chore_pr": 1234, "chore_pr_outcome": "created",
 "deferred_under_no_merge": ["post_close_milestone", "manual_close_release_issues", "lock_milestone_threads",
   "publish_github_release", "assert_anchor_hygiene", "check_release_body_drift"]}
```

**How it shipped.** Eleven cards landed on one branch over three tools, the Stage 13 specification, the close-class telemetry standard and two decision records, as one merge at `ad5b996e`, claimed as `v4.72` with a signed annotated tag on the first attempt; the `release-executor` skill was deployed after the merge and verified by content. The release synced with the main branch twice before its Stage 9 GO and renumbered its decision records each time, and it closes with the very tools it changed: each tool's self-test, then dry runs, then a `--no-merge` pass, then a resumed pass after the chore PR merges.
