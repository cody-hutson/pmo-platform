# Twelve role-Specialist agents now cover the core delivery roles

2026-06-20 · v2.11

This release adds twelve principal-level **role Specialists** — named agents for the core software-delivery roles. Each one carries a role's identity, judgment, and boundaries, and *composes* the platform's existing function-skills to do the work rather than re-implementing anything. Where before you invoked a function (run DoR, review an FDD, plan a sprint), you can now invoke the *role* that owns that work and get its full perspective.

## Who this affects

- **PMO practitioners** gain seven operations-role agents: Product Owner, Business Analyst, Program Manager, Project Manager, Portfolio Manager, Scrum Master, and Release Train Engineer.
- **Platform builders** gain five delivery-role agents: Principal Engineer, Software Engineer, Architect, QA Lead, and DevOps/SRE.
- Nothing changes in how you invoke the platform; the new role-skills become available on deploy and trigger on role-shaped requests.

## What you need to do

1. Run `update.sh` to deploy this release — it lands the twelve new role-Specialist skills and ADR-033.
2. (Optional) If you run a methodology other than the default, note that the Release Train Engineer is **SAFe-specific** — it stays dormant unless your `delivery_approach` is SAFe (see "What changed" below).

## What changed for everyone using the platform

- **The core delivery roles are now first-class agents.** Ask for "the product owner's call on this backlog" or "a principal-engineer design review" and you get the role's judgment — value-and-priority framing from the PO, within-component design depth from the Principal Engineer — not just a generic function output. *Why it matters:* you get a role's full perspective and boundaries, the way you would from a senior person in that seat.

- **Each Specialist composes existing skills instead of duplicating them.** The Program Manager invokes the delivery engine and the strategic PMO brain; the QA Lead invokes the auditor and the build-reviewer. *Why it matters:* one consistent engine underneath every role — no divergent re-implementations to drift apart.

- **Overlapping roles are deconflicted so the right one answers.** The Product Owner and Business Analyst (who share the most overlap) split cleanly on decide-value vs. document-requirements; the Program / Project / Portfolio tier splits by altitude. *Why it matters:* a role-shaped request routes to the one role that owns it, instead of two agents both firing.

- **Methodology-specific roles stay dormant when they don't apply.** The Release Train Engineer is meaningful only under SAFe; under the default (Scrum) it announces it is not firing rather than emitting a view your process does not run (ADR-033). *Why it matters:* you only get the roles your methodology actually runs.

## Known limits

- A future **Release Manager** role (go/no-go decision + release-tail orchestration) is named as the DevOps/SRE's sibling but is not built in this release.
- The behavioral evaluation of the two pilot roles (#1341) runs separately and is tracked on its own.
- A small follow-up hardens the deploy tooling's skill-module resolver (#1557).

## Reversibility

CHEAP / Confidence HIGH. The release is purely additive — twelve new skill directories, their packages, one new ADR, and registration entries. Reverting the release fully removes them, and nothing existing changes behavior.
