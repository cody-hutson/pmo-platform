# Stale hand-kept lists get caught, and every release close measures quality share

2026-11-17 · v5.12

The deploy check now reports a hand-kept list of files that has drifted from the files it names, and every release close reports the standing quality initiative's share of recent work against a written band, flagging a share outside it. Three written rules also settle questions that used to be decided case by case: when a release gets a version number, which side wins when a document and practice disagree, and where a decision that constrains code is recorded.

## Who this affects

- Anyone who runs a release through the pipeline, or runs the deploy check.
- Anyone who edits the platform's governance, standards or reference documents.

## What you need to do

1. After pulling this release, run `./update.sh --surfaces-only` from the platform repository root, or a full `./update.sh`. It refreshes two installed files this release changes, the workspace charter and the script allowlist, so the installed copies match the repository.

## What changed for everyone using the platform

- **Hand-kept file lists are checked.** A list or count of files in a document can now carry a short marker naming the files it describes. The deploy check then reports any list whose entries, or count, no longer match those files. The hook lists in the module guide are the first ones marked, and they now match. *Why it matters:* a list that falls out of date is reported at the next deploy, instead of being found later by someone who relied on it.
- **Every release close reports the quality share.** The share of each release's shipped work that belongs to the standing quality initiative is now measured at close, over the last five releases. It is judged against a band of 15% to 35%, written in the platform configuration template. A reading outside the band is flagged, and nothing is blocked. This release's own reading is in band at 34.5%, just under the ceiling. *Why it matters:* whether quality work is getting its intended share is a number you can read at every close, not an impression.
- **A written rule decides whether a release gets a version number.** A release that changes what a skill, check, tool, template, setting or procedure does gets a version. A release that only adds records, such as a decision record or its own plan, ships without one. The operator can override the rule, with a reason. *Why it matters:* the version an install reports always names a change in how the platform behaves.
- **When a document and practice disagree, the document says which side wins.** The resolver reads the governing document first and brings practice into line with it. Where the document is silent, it is amended to name the winning side, and each resolution is recorded in the release plan. *Why it matters:* a disagreement is settled once and on the record, instead of being re-argued, or silently flipped, by each person who finds it.
- **Decisions that constrain code are recorded where that code lives.** A decision that fixes how a script, check or procedure must keep behaving now goes in that file's header or its governing section. A discussion thread can still carry the discussion, but it is never the only record. *Why it matters:* someone editing the file later can see the decision before they undo it.

## Known limits

- The list check is logged but not blocking, and it reads only lists that carry a marker. A hand-kept list with no marker is not checked.
- The quality-share reading is advisory, and the band's values are revisited after three measured releases. The release that sets the band is the first measured one.
- Nothing yet confirms that the version rule was applied when a release was bundled. The release plan records the rule's citation, and a reviewer reads it.
- The release planner's own version step does not yet consult the new rule when it runs from its installed copy, outside the repository. That fix is a follow-up of this release.
- The configuration schema's general advice says to put a personal setting under an overrides section, which some readers do not read. Put a band value under the band's own section header, as its reference page says. Correcting the schema is a follow-up of this release.

Report issues on the platform repository's issue tracker, and report a suspected vulnerability privately, as the repository's security policy describes.

### Operator and engineering detail

**The enumeration-drift check.** `deploy.sh --check` gains Check 83, backed by `core/deploy/tools/check-enumeration-drift.py`. It is a sibling of Check 63 rather than an arm of it, and the tool's module docstring records why. The check runs warn-mode on its own committed dial, and its shakedown was armed on 2026-11-13. The corpus scan runs at deploy time only; CI runs the tool's `--self-test` through the selftest-discovery job. Forty fixture cases, together with the self-test, kill 44 of 46 single-rule mutants, and the two survivors are equivalents. Two other enumerations, the build-philosophy bullet of the charter template and the suite steps of the install-tests workflow, now cite the files they describe instead of listing them. The marker sits on the line before the list it binds:

```text
<!-- enumerates: core/hooks/block-*.sh list -->
<!-- enumerates: core/hooks/*.sh subset-of -->
```

**The quality-share band and reading.** The band is a new `[quality_share_band]` section of `core/config/platform-config.toml.template`, documented in the platform-config schema and reference. It resolves on two rungs, the template and the individual file under that section's own header, and an instance without the section reads `NOT-EVALUATED`, never a default. `release/tools/compute-release-velocity.sh --quality-share` reads the release log by first-parent ancestry, with a guard that every merged release in the window has its row. It judges the pooled share and prints the mean of shares beside it. Stage 13 Phase A14.2 writes the record it prints into the release plan's Verification Evidence, and a reading outside the band is a recorded finding, never a close verdict. The section as shipped:

```toml
[quality_share_band]
counted_label = "project:platform-quality"
scaffolding_label = "sub-task"
bug_type_label = "type:bug"
share_floor = 0.15
share_ceiling = 0.35
window_releases = 5
judged_on = "pooled"
values_set_at = "obligation-runners-declared"
```

**Three rules, each with its runner or a named gap.** The when-to-version rule sits in `release/governance/RELEASE_PROTOCOL.md` § Versioning; the operator committed that text. `release/references/pipeline/stage-03-bundle.md` cites it on the milestone's release-identity line. The adjudication clause is `core/standards/duplicate-source-discipline.md` § 1.2, and the surface requirement for constraining decisions is `core/disciplines/decision-discipline.md` § 3.2. None of the three has an automatic runner. Each is a named gap in the gate-coverage register, with a population that Stage 13 Phase A14 measures at every close. This release's own close records each of its five new populations. One of them, the version rule's, has no members yet, so its parent epic carries it until it does.

**A note moved to its standard location.** One release note for a version-less release sat at the top of the notes folder, where the release-notes standard places every version-less note under `release/releases/notes/_unversioned/`. It moved there, and its index row followed. The notes folder's README records the decision not to add an automated placement check, and what would change that.
