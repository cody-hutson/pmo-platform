# A green check now means the thing it checks is actually true

2026-06-20 · v2.06

This release tightens the platform's own safety nets. Its automated checks — the integrity gates that run on every change before it ships — now carry a written contract: a passing check must confirm the real thing it claims, by looking at the actual content, never at a stand-in signal that merely tends to move with it. The change began from a concrete near-miss: a "this package was rebuilt" check that compared file timestamps, which a routine checkout silently resets — so a stale package could sail through green. That check now compares the package's actual contents. Alongside the new standard, the release restructures how the platform's security hooks are documented so two changes to them can land at the same time without colliding, and resolves a decision to *not* add a pre-commit safety layer that turned out to be redundant. Everything is additive — new rules, new checks, and a documentation restructure, with no existing rule, setting, or behaviour removed or renamed.

## What changed for everyone using the platform

- **The platform's automated checks now have a trustworthiness contract.** A new standard requires every integrity check to confirm what it claims by inspecting the real content behind it — and to say plainly whether it blocks a change or is only advisory. *Why it matters:* a check that passes is now a check you can trust; the platform can no longer manufacture false confidence by going green without actually verifying the thing it guards.

- **The "is this package fresh?" check no longer trusts a timestamp.** The freshness check that used to compare file modification times — which an ordinary checkout resets — now compares the package's actual contents against a known-good baseline. *Why it matters:* a stale, un-rebuilt package can no longer pass as fresh, closing the gap that motivated the whole release.

- **A second copy of a key skill-structure check now runs on every pull request.** A check that previously only ran at deploy time now also runs in continuous integration, sharing a single source so the two can never disagree. *Why it matters:* a structural problem in a skill is caught at the pull-request stage instead of slipping through to a later deploy.

- **Two changes to the platform's security hooks can now land at the same time.** The hook documentation moved from one large shared file to one small file per hook, with the combined reference rebuilt automatically and a check that flags any hook left undocumented. *Why it matters:* concurrent safety-hardening work no longer collides on a single file at merge, and the hook list can no longer quietly drift out of sync with the hooks that actually exist.

## Known limits

- The new completeness check that flags an undocumented hook ships in **report-only mode** for now: it surfaces a mismatch between the hooks that exist and the hooks that are documented, but it does not block a change yet — the blocking version follows after a short observation period.
- The release also closed a deliberate **non-change**: the team evaluated adding a pre-commit safety layer and decided against it, because the protections it would add are already enforced earlier in the process. Nothing shipped for that item beyond the recorded decision and a short residual-risk note.
- This is governance, tooling, and documentation. It changes how the platform checks itself, not how any project-facing skill behaves; there is nothing to install.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. The release is additive — one new standard, one new architecture decision record, a new content-hash freshness baseline, a new CI check sharing the deploy-time predicate, a documentation restructure into per-hook files with a generated index, and two new deploy checks (one report-only, one freshness-only). No existing file, field, or behaviour was renamed. Whole-release rollback is `git revert -m 1` of the integration merge; the report-only check blocks nothing, the generated index regenerates deterministically from its sources, and the new reference material has no prior consumer to unwind. A follow-up point release (v2.06.1) repaired two deploy-script detection bugs that the new content-hash baselines exposed in the `--deploy` path; it is included in the deployment log below. Standard 7-day rollback window.

### Operator and engineering detail

**#1101 — Gate-efficacy standard (assert by content, not by proxy)** — Establishes the release's anchor: `core/standards/gate-efficacy-standard.md`, the normative contract for the platform's **automated-assertion gates** (the `deploy.sh --check` integrity checks and the `.github/workflows/*` jobs, scoped explicitly apart from the LLM-judged pipeline stage-transition gates). It names three requirements — assert the claimed invariant by inspecting the **content** that embodies it (never a proxy that merely correlates), self-declare **required-vs-advisory**, and be auditable both for false-confidence and for coverage gaps — plus the posture rule that decides whether a red verdict blocks. The rule's bite landed on Check 7 (package freshness), converted from an `mtime` proxy to a **content-manifest hash vs committed baseline**; required-vs-advisory declarations were added across the 14 workflow jobs, and Checks 6/7/9/37/38 were brought under the standard.

**#673 — Check-6 CI mirror (close the run-context detection gap)** — A second invocation of the canonical-skill-structure check now runs in CI via `.github/workflows/skill-canonical-structure-check.yml`, sharing a **single-sourced predicate** (`core/deploy/tools/check-canonical-structure.sh`) with the deploy-time Check 6 so the two surfaces cannot diverge — closing the gap where a red-on-main structural breach went undetected between deploys (the v1.10-sweep class). Bundled with it: a `daily-status` `references/` reconciliation (the v2.01→v2.06 substrate alignment, `references/rag-variance-buffer.md`).

**#18 — ADR-030 hook-registry restructure** — `core/ADRs/ADR-030-hook-registry-drop-in-with-generated-index.md` (Accepted) records the decision to break the ~32 KB `bypass-mode-readiness.md` monolith into **per-hook drop-in source fragments** (`core/rules/bypass-mode-readiness/<hook>.md`, one per bypass-mode security hook) plus name-prefixed cross-cutting fragments, with the canonical `bypass-mode-readiness.md` **generated** at deploy time by `core/deploy/tools/build-hook-registry.py` and committed. Two new deploy checks back it: a **completeness check (Check 37)** that reconciles every `core/hooks/block-*.sh` against its declared owning doc (making the prior 5/7/9 registry drift structurally impossible — warn-mode-initial/advisory), and an **index-freshness check (Check 38)** that regenerates-and-diffs the committed index (deterministic, so always-enforce). Check 9's directory-walk was extended to the new per-hook directory. This resolves the parallel-PR cascade-conflict class the milestone exists to kill: concurrent hook-adding PRs no longer collide on a single shared file.

**#90 — Pre-commit localized-context layer (decision spike — NOT needed)** — A decision-only spike that evaluated adding a pre-commit localized-context guardrail and concluded it is **not needed**: the relevant invariants (DC1/DC6) are already gated pre-merge, the residual risk is stable, and a pre-commit layer would duplicate existing enforcement at a lower-trust surface. Closed with a residual-risk register rather than a code change — a deliberate non-change recorded for audit.

**Re-versioning + v2.06.1 hotfix.** The milestone shipped as **v2.06** (PR #1461). A follow-up **v2.06.1** point release (PR #1474, fixing #1475) repaired two `deploy.sh --deploy` detection bugs that the new content-hash sidecar baselines exposed in the previously-untested `--deploy` path: (1) a sidecar mis-enumeration where the `.skill` `sed` was unanchored, so the new `<name>.skill.sha256` content-hash baselines were mis-parsed; and (2) a BSD-`sed` alternation no-op in skill-name detection (the known R1). Both tags `v2.06` and `v2.06.1` are pushed; deploy was verified on main (`daily-status` at v2.06 with `references/` present in the runtime mirror).

For full implementation detail see the RELEASE_LOG.md entry for v2.06 and the v2.06 release plan.
