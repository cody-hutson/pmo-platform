# Release close-out results can now be trusted as read

2026-07-31 · v4.02

The checks that confirm a release finished correctly were reporting answers they had not actually verified — one read its result before doing the work it was measuring, another quietly skipped real work, and a third reported success while unable to see what it was checking against. Each of them now reports what is true after the fact, or refuses to answer at all.

## Who this affects

- Anyone who reads the platform's release records to find out what a past release changed.
- Anyone who runs a release and relies on the close-out report to tell them it finished cleanly.

## What changed for everyone using the platform

- **The close-out report now tells you what is actually true.** The final check answering "did every piece of work in this release get closed?" was reading a snapshot taken *before* the closing happened, so it could report items still open in the very same report that said it had just closed them. It now re-reads after the work is done. *Why it matters:* a report that says the release finished cleanly now means it did, so you no longer have to go and verify by hand whether it half-failed.
- **Delivered work is no longer silently skipped at close.** The close-out was skipping any item whose title merely *mentioned* release close-out, treating it as housekeeping rather than real work. It now decides what is housekeeping by what an item actually is, not by what its title happens to talk about. *Why it matters:* work you shipped stays visible as shipped instead of being quietly left open — thirteen delivered items in the project's history had been mis-identified this way.
- **The version allocator now refuses to answer rather than guess.** When it could not see the full list of version numbers already taken — because a required setting was missing, or because reading the list failed — it carried on anyway and reported success, working from a partial view. It now stops and says why. *Why it matters:* two releases can no longer be handed the same version number because the check meant to prevent exactly that had been switched off without anyone being told.
- **Release records now agree about what their dates mean.** Different records dated the same release differently — some by when the code merged, some by when the release was wrapped up — with nothing stating which was which. Each record now declares which moment its date refers to. *Why it matters:* when two records show different days for one release, you can now tell that it is two genuinely different moments rather than a mistake in one of them.
- **Published release summaries are no longer blank templates.** Nineteen entries across twelve past releases had been published with the unfilled placeholder text still sitting where the summary was supposed to be. They are now written out. *Why it matters:* looking up what a past release did returns an actual answer instead of the instruction left for whoever was meant to write it.
- **Two past release records now point at the right release.** Two deployment records cited the wrong milestone number, attributing one release's version claim to an unrelated release. *Why it matters:* tracing release history backwards no longer sends you to the wrong release.

## Known limits

- **The date convention applies going forward only.** Records written before this release keep whatever date they were originally given rather than being rewritten. An older record still carries its original value, and there is no way to tell from that record alone which moment it meant.
- **Filling the nineteen blank summaries was a one-time repair, not a new safeguard.** Nothing yet stops a future release from publishing a blank one — that still depends on whoever closes the release filling it in before it is published. No automatic check for this was added.
- **The version allocator's new refusals are only as good as the conditions they name.** It now stops on the two specific blind spots found here — a missing setting and a failed read of the published version list. A different way of losing sight of the same information would not necessarily be caught.
- **How long a release takes to deploy is still not recorded.** Nothing in the pipeline reports it, so that field reads "not available" for this release exactly as it does for recent ones.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `project:pipeline` label.

## Reversibility

CHEAP / HIGH confidence. Reverting the integration commit reverses every change in this release at once: the two scripts return to their previous behaviour and the corrected records return to their previous text. One part is **MODERATE** rather than CHEAP — the published date convention, because once a standard is published other documents begin citing it, so reversing it later means finding and updating those citers too. No data was migrated and no stored state was transformed, so nothing needs rebuilding either way. Standard 7-day rollback window.

### Operator and engineering detail

**Two fail-open arms closed in the atomic version claim.** `claim-version.sh` binds a release to its version number at a compare-and-swap against the remote — the one window the CAS exists to protect. Two of the arms feeding `claimed_set()` were failing open into it. In #3724 an unset `CLAIM_REPO` tripped the `: "${CLAIM_REPO:?…}"` assertion inside `_host_published_tags()`, which printed the guard error twice and **still exited 0**, emitting the claimed version to stdout as though nothing had gone wrong; the published-Releases arm was therefore silently unavailable while the claim proceeded. In #4339 `_host_origin_tags()` returned the exit status of `sort` — the last command in its pipeline — not of `git ls-remote`, and discarded the diagnostic via `2>/dev/null`, so a failed remote read (measured `rc=128`) was byte-identical to a healthy read of a tagless repository: `rc=0`, empty stdout. Both now fail closed. A fifth host seam, `_host_resolve_repo()` (lazy, memoized, format-validated; `CLAIM_REPO` → `gh repo view --json nameWithOwner` → hard fail), replaces the bare assertions, and the self-test grew `U-15` (arm-unavailable is not arm-empty), `U-16` (anchor rc-checks) and `U-17` (all three `claimed_set()` arms fail closed, each with its own detector negative control).

**The close-out's two blind spots about its own operation.** #3587: `run_verification` check 5 reported the `read_state` snapshot captured *before* `post_close_milestone` and `manual_close_release_issues` ran, so the v3.78 close-out printed `PARTIAL (5 open)` in the same report where the close phases reported `closed 5/5` and `milestone #264 closed` — a control certifying the state it had not yet observed. #3665: the Stage-13 sub-task auto-exclude in `detect_open_issues` matched on a loose title substring, so it excluded delivered parent issues whose *subject matter* was close-out (observed live on v3.80, where #2678 was auto-excluded and left open for the hub to close by hand). The discriminator is now structural and conjunctive — exact comma-wrapped `,sub-task,` / `,type:subtask,` label membership **AND** an anchored `stage.?13.*close` title match — because the label alone matches every stage sub-task in a milestone while the title alone was the original defect.

**Date anchors were declared, not normalised.** #3718's constraint is that both values were already factually correct about the event each described, so forcing four ledgers onto one number would have destroyed information. `core/standards/date-variable-convention.md` was extended (operator decision: **Option A — EXTEND**; a sibling standard was rejected on the necessity bar and extend-and-rename on sweep cost, with the filename/scope mismatch recorded as an accepted residual) with an emission-time anchor taxonomy, and each ledger now carries a header note naming its own anchor. `RELEASE_INDEX` deliberately takes the **merge** anchor rather than the close-out one: it is the only ledger carrying an automated field-for-field equality assertion against `RELEASE_LOG` (`generate_release_index.py --verify`, via Check 23), and holding two different anchors across an equality check makes it red by construction and unable to report real drift. The close-out instant is preserved on `RELEASE_DIGEST`, the note, and `CHANGELOG`. The anchor is sampled **once per close-out run** so a run straddling a UTC midnight cannot make two writes in one atomic commit disagree. Existing rows are grandfathered — and regenerating the index without `--verify` would rewrite all of them in one pass, which is why that path is now marked prohibited.

The shape the convention declares, as it binds the Stage-13 writes:

```
| Stage-13 write                              | Anchor           |
|---------------------------------------------|------------------|
| RELEASE_INDEX.md   — Date                   | merge event      |
| RELEASE_LOG.md     — Date                   | merge event      |
| RELEASE_DIGEST.md  — ### vX.Y (<date>)      | close-out event  |
| notes/vX.Y_RELEASE_NOTES.md — date:         | close-out event  |
| CHANGELOG.md       — ## [vX.Y] - <date>     | close-out event  |
| RELEASE_REVERSIONS.md — date cell           | close-out event  |
```

**The placeholder backfill was a data repair with no new gate.** #3701 filled 8 `CHANGELOG.md` summaries and 11 `RELEASE_DIGEST.md` H3 headlines — 19 entries across 12 versions (v3.53, v3.58, v3.59, v3.67, v3.69, v3.70, v3.80, v3.81, v3.88, v3.89, v3.90, v3.93), a set that had *grown* between filing and the Stage-4 gate as v3.88/89/90/93 closed. The `≤140 chars` guidance in the scaffold was deliberately not enforced during the fill, because 78% of already-filled entries exceed it. No preventive check was added, which is why the residual is carried as a Known Limit above rather than treated as closed. #3586's correction was applied as anchored per-block edits, never a global substitution, so the two genuinely-correct `#264` references elsewhere in the log were left intact.
