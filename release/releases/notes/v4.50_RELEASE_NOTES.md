# Renumbering a decision record no longer rewrites its own history

Decision records in this platform carry a number, and that number is not stable while a change is in review. If two pieces of work claim the same number, whichever one lands first keeps it and the other is renumbered on the way in. That is routine — it happened **four times to this very release**.

The problem was what renumbering did on its way through. Alongside the live references it was supposed to update, it also rewrote **historical entries** — the lines that record *"this record used to be number X and became number Y."* Rewriting those makes them describe a hop that never happened. The log that exists to explain the change was being edited by the change.

## Who this affects

Anyone whose work adds or edits a decision record, and anyone who later reads a decision record's history to understand how it got its number. If you have never renumbered anything, you will not notice this release — but you were exposed to it, because renumbering happens at merge time and is not something you opt into.

## What you need to do

Nothing. No action is required, no configuration changes, and nothing you have already written needs revisiting.

## What changed for everyone using the platform

- **Historical entries are now left alone.** The tool distinguishes a live reference it should update from a historical record of a past change, and stops rewriting the second. *Why it matters:* the lines that explain how a record got its number were being edited by the very change they describe, so the explanation ended up describing a hop that never happened.

- **When two readings are genuinely indistinguishable, the tool says so instead of choosing.** A site that could be either a live reference or a historical record is reported by name and left untouched. *Why it matters:* a silent wrong guess is indistinguishable from a correct one, so you had no way to know a record had been altered; now you are told exactly where judgment is needed.

- **The preview matches what the real run does.** Previously the dry-run could predict edits the actual run would never make. *Why it matters:* reviewing a preview is only meaningful if it tells you what you are approving, and it did not.

- **A release that changes decision records is now asked about it.** Nothing previously checked whether the published list of decision records had fallen out of step with the records themselves. *Why it matters:* the list is what people read to find a decision, and it could drift without anyone being prompted.

- **An ownership rule that was written down but never enforced now runs.** It had been specified and left unimplemented, so it passed on every input — including inputs that broke it. *Why it matters:* a check that cannot fail offers assurance it is not providing.

## Known limits

Three guard gaps in the same tool were **found during this release and deliberately not fixed in it**, to avoid widening work already carrying four renumbers. All three are filed and none is speculative — each was measured:

- A marker example inside certain documentation sections can still read as a live declaration, and enclosing it in a code fence does not prevent that.
- The main sweep is not fence-guarded, so it can still rewrite text inside fenced blocks and code spans — measured at 208 occurrences across 182 files.
- One test guard does not detect a specific silent revert, confirmed by seeding that revert and reproducing it.

Separately, two governance surfaces still disagree about how many steps the renumber takes — one says six, one says seven, and the tool ships seven.

## Reversibility

**MODERATE.** The release merged as a merge commit with two parents, so a `git revert -m 1` path exists and the change is undoable in hours rather than days. What is *not* cheaply reversible is the renumbering already applied to records on the mainline: those numbers are now cited by other work, and unwinding them would re-open the collisions this release exists to resolve. Reverting the tool is cheap; reverting the numbers it assigned is not.

### Operator and engineering detail

The classifier is a single traversal returning both verdicts and carve-outs, so no second predicate can diverge from the first. Two candidate fixes were rejected on measurement rather than on judgment: an anchor-based extent rule matched **0 of 211** real occurrences, and an opener-match span reclassified **450 of 612** record-line tokens including **210 of 210** inside historical notes — it would have revoked the exemption it was written to protect. The adopted link-span carve-out reclassifies **4 of 612**, with **0** inside historical notes. A whole-corpus differential across **1,858 files / 415,876 lines** reported **0 verdict transitions** in either direction.

The test suite carries 153 arms; the tool's self-test grew from 78 to 86 with an AST label-set diff of `REMOVED = []`, and every new arm is killed by at least one of seven seeded mutants.

This release also renumbered its own decision record four times — 170 → 173 → 177 → 181 — once per merge claim, and had its version claimed out from under it twice before landing on v4.50. Both are the mechanism working as designed rather than a defect: a number binds at the claim, not at authorship.
