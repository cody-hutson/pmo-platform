# Allowlist entries now apply only where they belong, and refusals can be audited

2026-09-25 · v4.69

A GitHub write can no longer get past the outbound-write guard by borrowing an approval meant for a web host. When the guard refuses a GitHub command it cannot read, the refusal record now shows whether the refusal was correct, without storing the command.

> **Skip the rest** unless you add your own entries to the outbound allowlist, or you review the outbound guard's refusal records.

## Who this affects

- Operators who add their own entries to the outbound allowlist
- Operators who review the outbound guard's refusal records

## What you need to do

Only if you have added entries of your own to the outbound allowlist. Otherwise there is nothing to do.

1. Look through the entries you added for any GitHub address whose first part — the text before its first "/" — contains a wildcard. The guard no longer uses such an entry to approve a GitHub write, so a write that relied on it is now refused.
2. Re-add each one with the allowlist helper, giving it a fixed first part and the GitHub-address kind. Your other entries need no change.

## What changed for everyone using the platform

- **Each allowlist entry is now checked only for its own kind of destination.** The outbound guard keeps one list of approved destinations that covers two kinds — web hosts that files may be uploaded to, and GitHub addresses that commands may write to — and each entry now approves only its own kind. *Why it matters:* a GitHub write whose address merely ended in text shaped like an approved web host used to be let through, and it is now refused, while uploads to approved hosts and ordinary GitHub writes work exactly as before.

- **Refusals of commands the guard cannot read now say whether they were right.** When the guard refuses a GitHub write because it cannot make sense of the command's quoting, the record now notes whether the shell itself accepts the command's syntax, how any embedded block of text in it is quoted, and which build of the guard wrote the record — and never the command's text. *Why it matters:* a correct refusal of a broken command can now be told apart from a false refusal of a well-formed one, where before every such record looked identical and false refusals could not be counted.

- **A problem while writing a refusal record can no longer cancel the refusal.** Every step that writes the record is now built so that it cannot fail in a way that ends the guard early. *Why it matters:* a command the guard means to refuse stays refused even when the record-keeping around it runs into trouble, where before one such failure could let the command through with no record at all.

- **The allowlist helper can now declare what kind of destination an entry is.** When you add an entry of your own, you can now say whether it is a web host or a GitHub address, and re-adding an existing entry with its kind converts it in place rather than adding a duplicate. An entry added without a kind keeps the old matching, and the helper tells you so when it writes it. *Why it matters:* you can confine each of your own entries to the one kind it is meant for, and the entries you added before this release keep their old matching, with the one exception noted under Known limits.

## Known limits

- An entry you added yourself without declaring its kind, and that contains no "/", can still be matched as either kind, exactly as before. Declare its kind with the helper to confine it.
- An entry of your own whose first part — the text before its first "/" — contains a wildcard is no longer used to approve GitHub writes, so a write that relied on it is now refused with the usual message. Re-add the entry with a fixed first part and the GitHub-address kind.
- A few less common ways of writing a GitHub command are still recorded rather than refused; they move to refusal when the guard's wider rollout completes, which is tracked in [#6195](https://github.com/cody-hutson/pmo-platform/issues/6195).
- On an install whose guards are set to log rather than block, the corrected check records a would-be refusal instead of refusing.
- Refusal records written before this release carry none of the new facts, so they cannot be classified. They were counted and written off rather than guessed at.
- The syntax check names the shell that judged the command. A different shell may accept a command that one rejects, so a "rejected" reading means rejected by the named shell.
- A workspace picks up this release when the update next refreshes its guard bundle and regenerates its allowlist.

Report issues at https://github.com/cody-hutson/pmo-platform/issues, and report a suspected vulnerability privately as the [Security Policy](https://github.com/cody-hutson/pmo-platform/blob/main/SECURITY.md) describes.

## Reversibility

CHEAP / HIGH. The release is a single merge, so reverting it and then refreshing a workspace's guard bundle restores the previous guard, and the older guard reads the new-format allowlist exactly as it read the old one. Records already written keep their new fields, and the version tag stays in place as the record that the version was claimed.

### Operator and engineering detail

**Row scope — two match domains in one file.** The egress allowlist serves two rules: `BLOCK-EGRESS-004` matches the host of a curl upload, and `BLOCK-EGRESS-007` matches the resolved path of a `gh api` write. The matcher used to apply every row to both domains, so a host pattern could approve a write path that merely ended in host-shaped text. Each managed row now carries an adjacent `# egress-scope: host` or `# egress-scope: gh-api-path` directive that binds only the row directly below it, and `is_allowlisted` takes an optional domain argument that only the -004 and -007 call sites pass; the -011 (ssh) and -013 (WebFetch) sites keep their single-domain behaviour. Independently of any directive, the gh-api-path site never treats a pattern whose first path segment carries a glob character as a candidate, which closes the reported construction for rows written before directives existed and in either publish order. An undeclared row keeps dual scope; `allowlist-add.sh --scope host|gh-api-path` writes a declared row, and a `--scope` re-add upgrades an existing bare row in place inside the operator region. [ADR-206](https://github.com/cody-hutson/pmo-platform/blob/main/core/ADRs/ADR-206-egress-allowlist-rows-declare-their-match-domain.md) records the decision. Two managed rows, as the file now carries them:

```text
# egress-scope: host
api.anthropic.com
# egress-scope: gh-api-path
graphql
```

**The refusal-record field set.** `BLOCK-EGRESS-007` records whose `evidence` reads `path=unknown cause=unparseable` now carry, in both writers — `log_warn` to the warn log and `log_block` to the block log — a nested, versioned `features` object and a top-level `hook_build`. The object holds `schema_version` (1), `oracle` (the parser that judged the syntax, `bash-<major>.<minor>` or `unknown`), `shell_parse` (that parser's `-n` verdict — read, never executed — as `ok`, `error`, `skipped` or `unavailable`) and `heredoc` (the delimiter quoting: `none`, `quoted`, `unquoted`, `both`, `skipped` or `unavailable`); `hook_build` is the first 16 hex of the writing hook's git blob id. `evidence` is byte-identical, no `phase` key is added, and serialization is unchanged. [ADR-205](https://github.com/cody-hutson/pmo-platform/blob/main/core/ADRs/ADR-205-a-refusal-record-carries-structure-never-the-command.md) records the decision and is ratified to Accepted at this close. One warn-log record, with illustrative values:

```json
{"ts":"2026-09-25T12:00:00Z","hook":"block-egress","rule":"BLOCK-EGRESS-007","tool":"Bash","evidence":"path=unknown cause=unparseable","reason":"gh api write denied: the command carries an unterminated quote and cannot be evaluated.","features":{"schema_version":1,"oracle":"bash-3.2","shell_parse":"ok","heredoc":"quoted"},"hook_build":"c84bf7bad8779ea6"}
```

**The record path cannot cost the refusal.** A failure inside a writer used to be able to end the hook in a way the tool runner treats as non-blocking, which would lose the refusal that follows it. Every feature step is now failure-proof, the block log's digest steps are guarded, and a record whose features cannot be computed carries the not-computed set — every member `unavailable`, the oracle `unknown` — beside `hook_build`. The feature path is bounded in time as well as status: both computations are linear in the command's length and share one cap of 1,048,576 characters.

**Pre-fix records and the first live ones.** The 311 warn-log and 4 block-log `unparseable` records written before the fix deployed carry no features and were written off as unrecoverable, bound to deploy time rather than to the absence of a key. The first two records written after the deploy both carry the field set and the deployed build's `hook_build`, and both read `shell_parse: ok` with a quoted heredoc — false refusals of the class tracked in [#7548](https://github.com/cody-hutson/pmo-platform/issues/7548), which can now be counted.

**How it shipped.** Both cards were built assertion-first on one branch, serially, and landed as one two-parent merge; the mainline was merged into the branch twice, and one decision record was renumbered to keep the sequence gap-free. The update path refreshed the hook bundle and regenerated the allowlist's managed section, both hooks match the merged source by content, and the operator region of the allowlist was byte-identical before and after. `v4.69` is a signed annotated tag. A rollback by reverting the merge stops once, on the release plan that the version claim renamed; keep that plan and continue.
