# Scrum and Kanban packs now ship with real, sourced work-item criteria

2026-09-05 · v4.56

Choosing a methodology used to hand you a shape with nothing in it — twelve empty criteria lists and three of four empty field sets across the two shipped methodologies. This release fills them from named published practice, records where each entry came from, and gives every methodology a default so that picking a kit is an option rather than a prerequisite.

## What changed for everyone using the platform

- **Scrum work items now arrive with criteria instead of blanks.** Six criteria blocks across the Scrum epic, story and task kinds carry 21 checks drawn from the Scrum Guide, INVEST and Cohn's story practice, and the story field set is adopted from the platform's existing best-practice default rather than reinvented. *Why it matters:* selecting Scrum gives you a working definition of ready and done immediately, instead of empty lists you have to author before the methodology does anything for you.

- **Kanban work items do too.** The card kind now carries two readiness checks and three done checks drawn from the Kanban Method. *Why it matters:* the same is true of Kanban — you get a usable bar on day one rather than a shape you still have to fill in.

- **Every authored criterion and field records the practice it came from.** Each entry now names its source — the Scrum Guide, a specific INVEST letter, a named Cohn text, a Kanban Method practice. *Why it matters:* you can tell a criterion grounded in published practice from one that is somebody's local convention, and you can challenge the second on the evidence rather than on taste.

- **A methodology now has a defined default, so choosing a kit is optional.** A pack's default is the set of work-item kinds it declares — there is no separate default to configure and nothing to select before you can start. *Why it matters:* you can begin work under a methodology without first making a choice you have no basis to make.

- **The line between what a methodology may change and what the platform fixes is now written down.** Twelve elements are classified as one or the other, each naming the rule that enforces it — or, where nothing enforces it yet, saying so plainly. *Why it matters:* if you extend a methodology you can tell in advance whether your change is inside the boundary, instead of discovering it when something rejects it later.

- **Where a methodology genuinely prescribes nothing, the packs say so rather than inventing a rule.** Four transition gates ship deliberately empty, each carrying a written reason. *Why it matters:* an empty gate you can read the reasoning for is a recorded decision; an empty gate with no note is indistinguishable from an oversight.

## Known limits

- Nothing yet rejects a criterion that omits its source. The requirement is written into the grammar and every entry this release ships carries one, but the enforcement is recorded as a named gap and the checker that would close it is tracked separately as [#6371](https://github.com/cody-hutson/pmo-platform/issues/6371).
- Three of the boundary's rules ship stated but unenforced, and they are recorded as named gaps in the coverage register rather than presented as guaranteed. Closing them inside this release was measured and rejected: the obvious rule fires on 51 of the corpus's criteria tables and would break an unrelated deploy check.
- The Kanban pull-limit gate is preserved as a deliberate stub so it does not pre-empt the work that fills it, tracked as [#1971](https://github.com/cody-hutson/pmo-platform/issues/1971).
- The version stamp on a criteria block is not read by any runner, so keeping it accurate rests on authoring discipline rather than on a check.
- The default-kit rule's tests cannot exercise the one configuration in which it could fail, because the resolution tool has no way to express "resolved to no kit". No kit ships today, so the situation is currently unreachable; the boundary is recorded rather than left to be discovered.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**CHEAP / HIGH confidence.** The release is a single two-parent merge, so reverting it restores the previous pack content in one operation. Every change is additive — no file is deleted, no path moves, and no existing check becomes stricter — so a revert removes new content rather than restoring a changed contract.

### Operator and engineering detail

**Provenance is a required key at two altitudes, not a comment convention.** `source` is declared as a fifth base field on every `criteria.checks[]` entry and every kind-specific field declaration, and projects as a new sibling annotation class. The shape a pack author now writes is one line per check, with the citation carried in the entry rather than in prose beside it:

```toml
[kinds.criteria.readiness]
criteria_version = "0.2.0"
checks = [
  { id = "dor-epic-valuable",
    statement = "as_a, i_want and so_that are each present and non-empty.",
    level = "L1", automatable = true,
    source = "INVEST (Wake 2003) — V, Valuable" },
]
```

**The boundary is a classification over the existing grammar, not a new mechanism.** Twelve elements are placed as methodology-configurable or platform-fixed, each mapped to the runner that executes it, with an author-facing test for deciding where a new field lands. Three invariants the platform states have no runner at all; they are entered in the gate-coverage register with a declared observable and an executed falsification arm each, so the gap is countable rather than invisible. The register's own resolution-pointer total was unmoved by this release.

**Thirteen independent reviews found no wrong shipped value, and that is the finding.** Across five dev-test passes, five acceptance passes, two adversarial design passes and the plan review, every defect raised was a *statement about* an artifact that disagreed with the artifact — a criterion's stated row count that never matched any commit, a verification command whose escaping resolved to an alternation matching every line, a control arm asserting a property its population could not exhibit. Each was corrected in the descriptor, and no pack value, schema value or fixture value moved as a result. The corrections are recorded with the measurement that produced them rather than smoothed away.

**Two of the three decision records changed after they were ratified, on evidence.** One rejection ground was falsified by execution before the record shipped and was re-grounded on a premise that holds rather than reissued as written; one deferred sub-decision's stated rationale did not survive measurement and was re-grounded on three grounds that did. Both records say so in their own text.

**The release lost three version slots and three record numbers to concurrent siblings.** The version claim recomputed twice — once at engineering entry, once mid-dev-testing — as sibling releases took v4.53, v4.54 and v4.55, and the three decision records were renumbered at the merge boundary. Both are governed behaviour: the number binds only at the merge-time atomic claim, and the recorded earlier readings are preserved as the pinned measurements they were rather than restamped.
