# Behavioural regressions are now caught before they ship

2026-09-03 · v4.51

Until now, a change to one skill could silently degrade another and nothing in the tree would notice. This release adds a runner that scores eval suites against committed fixtures, a standing regression corpus, and a check that runs that corpus on every pull request.

> **Skip the rest** unless you write eval suites, open pull requests against this repository, or rely on skill behaviour staying stable across releases.

## Who this affects

- Anyone writing or maintaining eval suites for a skill.
- Anyone opening a pull request — a new check now appears on every one.
- Anyone depending on skill behaviour holding steady from release to release.

## What changed for everyone using the platform

- **A behavioural-regression check now runs on every pull request.** It scores the regression corpus and reports the pass rate; today it reports without blocking, and it blocks only at a major-release tag. *Why it matters:* a change that quietly breaks another skill's behaviour surfaces while you can still fix it in the same pull request, instead of after it ships.

- **Eval suites are executable.** The new runner grades a suite's assertions against a committed fixture and writes the framework's standard report. *Why it matters:* an eval suite you author is now something that runs and produces a score, rather than a document nobody executes.

- **Suites gained two optional fields, `check` and `expect`.** `check` carries the predicate that grades an assertion; `expect` records that an assertion is a known-open defect you expect to fail today. Suites written before these existed score exactly as they did. *Why it matters:* you can hold a known defect in the corpus as one named, visible row instead of hiding it in a lowered threshold or a side allowlist — and when someone fixes it, the run turns red and tells you to retire the exception.

- **A run that could not measure anything now says so instead of reporting a score.** A fixture that is malformed or unreadable ends the run with a named error rather than a number. *Why it matters:* a passing result now means the checks actually ran, not that the tooling crashed in a way that resembled success.

- **The pass-rate threshold is recorded once, as configuration.** Supplying a threshold now genuinely decides the outcome across its whole documented range. *Why it matters:* raising or lowering the bar is an edit to one recorded number, and lowering it now actually takes effect instead of silently doing nothing.

## Known limits

- The corpus ships thin — **3 scenarios**. That is why the check reports without blocking for now; its criterion for being armed is committed alongside it and can be read back from the tree.
- Making the new check a required one is a repository-settings action taken outside this repository. Until that happens it reports on every pull request without being able to stop a merge, even after the in-tree switch is flipped.
- Only the deterministic assertion kinds run. The model-judged assertion types remain unexecuted, so the earlier commitment to wire up the runner is **partially**, not fully, discharged.
- One known-open defect — a reference in the check bank pointing at a path that exists in no checkout — is carried as an expected-FAIL assertion rather than fixed here. The run names it on every execution.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**CHEAP / HIGH confidence.** Every deliverable is additive; reverting the release commits removes the runner, the corpus and the check and restores the previous ungated state, and the trigger-evaluation path is untouched so no revert can disturb it. The one caveat, stated rather than buried: once a corpus check exists and passes, later releases start relying on it, so rollback grows more expensive with each release that trusts it.

### Operator and engineering detail

**The release's own falsification arm carried the anti-pattern the release exists to remove.** The arm proves the check *can* fail by running a deliberately-regressed fixture and requiring exit 1. The runner parsed fixtures with no guard on either the JSON or the YAML branch, so a malformed fixture raised through `main()` and Python exited 1 — the single code the arm reads as a successful falsification. The arm would therefore have printed its green checkmark over a run that graded nothing and wrote no report. It was found at Stage 8 QA, reproduced independently at the hub against a live control, and the Stage 9 gate went NO-GO on it. Both branches now raise the runner's named suite error, which maps to exit 2 — the code the contract already assigned this family, and the code the decision path already treats as *could not measure*. The same guard covers a fixture whose bytes are not valid UTF-8, because a read failure leaked the identical exit 1 through the identical route. The arm's `-eq 1` predicate was deliberately left byte-identical: the exposure was the arm's input, not its strictness, and loosening it would have swallowed the defect rather than caught it.

**A recorded threshold that could not take effect.** A failing-assertion short-circuit preceded the threshold comparison, so within the documented range only a threshold of `1.00` was distinguishable — the "or lower the threshold" remedy named in the release's own decision record silently did nothing. The comparison now decides the outcome when a threshold is supplied; when none is supplied, any failing gradable assertion still fails, stated as a decision rather than left implicit, because defaulting to a tolerance would install a standing regression budget by omission. Verified on a `0.5455` run: threshold `0.50` passes, `0.60` fails, `1.00` unchanged — so the shipped configuration, which runs at `1.00`, behaves exactly as before.

**The non-blocking rung is enforced in the tree, not merely unregistered.** Branch protection lives in repository settings, and no committed file can assert which checks are required — so leaving "the pull-request rung never blocks" to non-membership would have made a load-bearing property depend on a fact nothing here can state. The workflow enforces that clause itself.

**Two optional fields, not a new schema.** The runner consumes the eval-harness schema the platform already ships. The commissioning work item cited a different, trigger-rate-shaped schema that carries no scoring field at all; a runner built against it would have scored nothing while satisfying the literal wording of its own criterion. The delta is two optional fields, both backward-compatible by construction — an assertion without `check` is ungraded rather than failing, and `expect` defaults to the identity. One assertion, showing both new fields:

```json
{
  "text": "the Reference section resolves to a path that exists",
  "type": "resolution",
  "check": { "kind": "resolves_to", "value": "docs/output-contracts.md" },
  "expect": "fail"
}
```

`expect: "fail"` grades the negation of the observed outcome, so a known-open defect keeps the pass rate at the threshold while staying legible as one named row. When the defect is fixed the predicate starts holding, the graded outcome flips to FAIL, and the run says the exception is stale — which is the prompt to retire it in the same change.

**Dogfood result.** The check this release ships ran and passed against post-merge main on the release's own follow-up pull request, so the delivered capability is executing rather than merely present.
