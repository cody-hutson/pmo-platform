# The script guard reads each command the way the shell will run it

2026-11-17 · v5.11

The guard that refuses to run a script your workspace has not listed now finds the interpreter and its script at more places in a command, reads each word as the shell will after it removes the quotes, and treats a command continued onto the next line as one command. A script that is not on your list, reached through any of those forms, is now refused as its plain form already was.

> **Skip the rest** unless your sessions run scripts through a shell from the command line, or you review what the script guard refuses.

## Who this affects

- Anyone whose sessions run shell commands on a workspace that has taken this release's guard bundle
- Operators who read the script guard's refusals, or who maintain the guards

## What changed for everyone using the platform

- **The guard finds the command at more positions.** When a command is written behind a leading redirection, with an escaped or quoted command word or wrapper word, inside a `case` branch, after `coproc` or a zsh precommand word, or inside a brace group, the guard now reaches the interpreter and the script it runs. *Why it matters:* writing a command one of these ways no longer lets an unlisted script run past the guard.

- **Quotes are read the way the shell reads them.** The guard judges each word after the shell would remove its quotes, and keeps track of quoting correctly past a comment or a quote nested inside another. That covers a quote or a space inside a script's path, a quoted value set just before the command, and a quoted or slash-bearing value handed to a wrapper that splits it. *Why it matters:* an apostrophe in a comment or an unusual quote placement can no longer hide a later command, or separate a script's path from the check.

- **A command continued onto the next line is judged as one command.** An interpreter and its script on two lines joined by a line continuation are read together. *Why it matters:* breaking a command across lines no longer turns a refusal into a warning that is only logged.

- **A shell fed by `xargs` stays refused whatever options it carries.** When `xargs` starts a shell that will read a script name from its input, adding one of the shell's own options no longer gets past the refusal. A shell asked only to check syntax, or given its program inline, is still allowed. *Why it matters:* one extra option can no longer let a script named on standard input run.

- **Ten command forms the guard refused before are now allowed.** Where the guard now reads a word as the shell does, ten forms in its test set move from refused to allowed, and each is declared and pinned by a test. *Why it matters:* the closer reading also lifts those ten refusals instead of only adding new ones.

## Known limits

- Some forms are still logged or allowed rather than refused, and each is declared with an owner. A script reached inside a group or a substitution is logged, not refused, until that reading switches from logging to refusing, which [#7637](https://github.com/cody-hutson/pmo-platform/issues/7637) tracks; the guard's readiness check warns on 2026-12-15 (Tue) and reports a finding on 2027-01-14 (Thu). One top-level form of the `xargs` case is logged for the same reason. A path with a space inside its quotes is refused at the script's own position but not yet at three other positions; that remainder is item S-8 of the release's follow-up sweep, [#9052](https://github.com/cody-hutson/pmo-platform/issues/9052). The `xargs` refusal covers shells only, by design.
- Some commands that run nothing unlisted are now refused, and each is declared in the guard's readiness reference: a carrier command whose quoted text names an unlisted script on a line that also holds a comment the guard cannot trust, and a few costs of the wider position walk. The ones a user would plausibly hit are items S-13 and S-14 of the release's follow-up sweep, [#9052](https://github.com/cody-hutson/pmo-platform/issues/9052).
- The added readings make the guard do more work on each command. A limit on the guard's work per command is tracked in [#8327](https://github.com/cody-hutson/pmo-platform/issues/8327).
- Further gaps in what the guard covers, found during this release, are reported privately as the Security Policy describes and are not described here; the release's follow-up sweep, [#9052](https://github.com/cody-hutson/pmo-platform/issues/9052), counts them.
- A workspace picks up this release when an update refreshes its guard bundle. The version a workspace reports changes to v5.11 on the first update after this release closes.

Report issues at https://github.com/cody-hutson/pmo-platform/issues, and report a suspected vulnerability privately as the [Security Policy](https://github.com/cody-hutson/pmo-platform/blob/main/SECURITY.md) describes.

## Reversibility

MODERATE / MEDIUM. Reverting the single release merge restores the script guard as it was, and a workspace runs the restored guard only after an update refreshes its guard bundle; the version tag is kept as the record that the version was claimed. A revert reopens every gap this release closes.

### Operator and engineering detail

**The position walk (#8316).** The walk now reaches the verb behind a leading redirection, an escaped or quoted verb, a quoted wrapper word, a `case` arm, `coproc`, a zsh precommand word and a brace group, in three slices (the words, the redirections and the compound positions). CP17 is the one declared precision move to allowed (PM-1); PC-1 and PC-2 are declared precision costs.

**Quote state and the word after quote removal (#8317, #8318, #8319, #8491).** The quote scanner carries comment state and nested-quote phasing, and the shared ANSI-C test reads an odd-length run of `$` before a quote as opening one. The operand path reads the word the shell passes when a quote or a backslash sits inside the path; at the Stage 9 gate the operator accepted #8318's Decision 4, which closes a whitespace-bearing quoted path at the operand after the flag walk and leaves three other positions not joined, with a successor owner. The assignment-value step only withdraws fragment suppression, never grants it. #8491 reads a quoted or slash-bearing split-string value, with the canonicalizer's twin in the shared awk library and three declared divergences (D-1 to D-3).

**The line continuation (#8320).** A second first-view walk reads the joined logical line (M-CONT-WALK), and the here-document receiver test reads the logical line too, excising only when both readings name a carrier (M-CONT-RECV). After Stage 7 the join takes the segments' linear split, so a large continued command no longer outlasts the hook's timeout.

**The xargs deny (#8492).** The deny holds for an xargs-fed shell whose own flags leave no operand, no inline program and no parse-only grant. A closer-bearing segment takes the enclosure phase whichever view reads it, through a third router argument. PC-X1 and PC-X2 are declared, and PC-X2's Override Record is Accept, owned by the enclosure phase's graduation. The deny stays shell-only (N1).

**The corpus differential.** Each card adds one seed block to the tracked walk payload corpus, recorded at the base before its RED commit. No refused row moves to allowed except a declared precision row: WR134, WR135, AV19 to AV22, AV24, CP17, SV28 and SV30. The fixtures README's real-interpreter check was waived for this release, so those rows carry ground truth `?` (DEV-10). In the hook harness job on the merge commit's push run, the block-destructive suite read 2088 of 2088, and the hook suites 4697 passing and 0 failing.

The corpus gained a newline placeholder, because a row is one line and two of the classes span lines. Row LC14, an allowlisted script after a line continuation, is one such row; its ground truth is `?`, because it was not run under the real interpreter this release:

```text
LC14|block-destructive|rt-cont-near|-|?|a|bash \@NL@@D@/ok.sh
```

**How it shipped.** Seven cards on one branch, built serially. Model-output safety classifiers stopped several spawned agents in the guard's region, so four cards and #8319's third pass were built in the orchestrating session, with Stage 7's dev test as their only independent check. The Stage 9 verdict was GO WITH CONDITIONS, with three conditions (the macOS install suite green at the merged head, four content reads confirming the build, and the operator's review of the diff), all of which held. The release merged at `20149aeb` and claimed `v5.11` with a signed annotated tag, after the provisional label was relabelled twice as sibling releases claimed `v5.08`, `v5.09` and `v5.10`. The hook bundle was refreshed through `./update.sh`, and the deployed guard and canonicalizer byte-equal the merged source. One procedure line in the hub-spoke bridge now sources the version-grammar library by its repository-relative path, because the new word reading refuses the old form (DEV-9).
