# Each safety guard now blocks its own scope, and nothing wider

2026-09-05 · v4.55

The platform's safety guards were refusing work they were never meant to refuse — reading output through a pipe, checking a script's syntax, quoting a command inside a report, working in an unrelated repository that happens to sit inside the workspace. Nine such refusals are fixed, each guard's reach is bounded to what it actually claims to cover, and when a guard does say no, its message now names the retry that usually resolves it.

## What changed for everyone using the platform

- **Reading a command's output through a pipe is no longer treated as touching a file.** The guard that watches file access counted a pipe-reading `head` as a file operation, because it keyed on the command's name rather than on whether a file was actually named. *Why it matters:* ordinary inspection commands run instead of being refused, and the guard still stops the file access it exists to stop.

- **Checking a script's syntax no longer counts as running it.** A parse-only check reads a script, validates it, and executes nothing. The execution guard now recognises that and permits it, while every form that genuinely executes stays refused. *Why it matters:* the check that catches a broken script before it runs is available again — previously it was not, and a real parse error was caught only because somebody happened to read the file closely.

- **Two platform tools that the instructions tell you to run are runnable again.** The convention checker and its own drift-guard test were missing from the execution permit list while their sibling suites were present, so documented commands failed at a refusal that had nothing to do with the command itself. *Why it matters:* an instruction that names a command can now be followed instead of dead-ending.

- **Quoting a command inside a report no longer trips the guard that watches for running it.** Writing evidence that contains a command is now distinguished from issuing that command. *Why it matters:* you can document what happened without the act of documenting being blocked.

- **Working inside a nested repository no longer applies the platform's own layout rules to it.** Two guards matched governance filenames and draft-file placement without first asking which repository the file belonged to. *Why it matters:* an unrelated project checked out inside the workspace is governed by its own conventions rather than by the platform's.

- **A refusal now names the retry that usually works, and the guard covers the ways execution can actually start.** The message previously omitted the repository-relative form that resolves most refusals, and the guard itself keyed on the interpreter word — so starting a script directly by its own header, or through a wrapper command, went unexamined. *Why it matters:* a block tells you what to do next, and the guard's coverage now matches the coverage it claims.

## Known limits

- The guard code reaches a workspace through the security-hook refresh, which is a **different command** from the one that deploys content. This release ran the surfaces refresh, so the permit list is live, but the hook bundle in this workspace was still at its pre-release build when the release closed. Until the hook refresh runs, the parse-only allowance described above is present in the repository and not yet active locally. Nothing detects that combination automatically.
- Commands whose program is a quoted string — the `-c` forms, `eval`, and command substitution — are still not examined for what they would run. This is a pre-existing, recorded limitation that this release restates rather than introduces.
- The set of recognised interpreters is a closed list. Versioned spellings and interpreters outside the list are recorded as known gaps rather than left half-covered.
- One automated check counts a forbidden token by plain text search, so documentation that **forbids** the token scores identically to documentation that recommends it. It reports without stopping a release, and the text it flags is guidance telling agents not to bypass a guard.
- Nine follow-up items are carried open by decision rather than resolved here; they are listed in the references below.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH confidence.** The release is a single two-parent merge, so reverting it restores the previous guard behaviour in one operation, and the version tag remains as the record that the version was claimed. The one surface that does not revert with the source is any guard bundle already refreshed into a workspace; that is restored by running the refresh again from the reverted source.

## Operator and engineering detail

**The carrier that mattered is not the one the plan named.** This release's own plan asserted that the deployed permit list is regenerated by the deploy command from its source file. That claim is false, and the deploy command says so in its own voice at run time: composition surfaces are out of scope for it and are not examined, so a clean deploy result says nothing about them. The permit list is a composition-surface row, and the surfaces refresh is the only carrier that reaches it. Had the close trusted the plan's sentence, the source list would have merged while the deployed list stayed stale — and the acceptance condition below, which is graded against the *deployed* list, would have failed for a reason the deploy result would have reported as success. The false claim is carried as a follow-up rather than quietly corrected.

**The acceptance condition was graded first-hand at close, and it passed.** The operator's override record accepted one criterion on the condition that its second half — re-graded against a real run rather than against a reproduction of the guard's own predicates — be graded at close against the deployed permit list, with failure declared a rollback trigger rather than a residual. It was graded by reading the deployed list directly, where all four rows this release adds are present among 313 entries, and then by *executing* the drift-guard test the criterion names, from the repository root, which returned its own verdict of fourteen passed and zero failed rather than a guard refusal. The control arm ran in the same session: a deliberately unpermitted scratch script was still refused, so the pass is a measured pass rather than a guard that had quietly stopped working. Verdict: **PASS**, and no rollback is owed.

**The half that is not yet live locally, and why it was not deployed at close.** The same reading found that this workspace's guard bundle is materially older than the merged source — the parse-only allowance appears seventeen times in the merged file and zero times in the deployed one — and a live probe confirmed it: a syntax-only check on an unpermitted script is still refused here, while ordinary execution of the same script is refused too, so the guard is active and simply predates the release. This is a deployment gap in the workspace, not a defect in what merged, and the remedy is to run the hook refresh. It was deliberately **not** run at close: the finding is a close-out observation, and refreshing the live security-guard bundle on the operator's workspace is an action that the finding does not by itself authorise. It is surfaced here for the operator to take.

**Check 14 flip-to-enforce assessment.** The doc-link check's own stated thresholds are met. Its broken-reference backlog measures **zero** across sixty-two files carrying one thousand three hundred and eighty-one link occurrences, well under the fewer-than-ten threshold, and the check has reported without blocking for far longer than the two-to-three-release review window. Its self-test passed all eleven fixtures first, so the zero is a measured zero rather than a detector that never engaged. The recommendation is therefore to **flip it to enforcing**. The flip itself is **deferred to the workspace owner**, whom the protocol names as the responsible party, because turning a check into a blocking one is a standing configuration change that the platform's own no-ungoverned-changes rule routes through an issue and an operator decision; a release-close step enacting it unilaterally would be the bypass the same corpus forbids. The mechanism is a single per-check mode file named for the check, holding the word `enforce`, in the operator instance directory; no per-check mode file exists there today.

**The decision record was ratified at close.** The architecture record for this release — command-start position is resolved by a pre-match canonicalizer rather than by a parser or by a wider anchor — was renumbered at merge because the mainline had already claimed its original number. Its status field was read **directly** rather than inferred from the automated check, which cannot fail by design; it still read `Proposed` at close despite the operator's gate decision having been rendered, and it was flipped to `Accepted` in this close-out. Its numbering provenance carries one note per hop.

For full implementation detail see the Deployment Log v4.55 entry in the release log, and the release plan for this version.
