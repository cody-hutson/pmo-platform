# Portability is now a first-class engineering value

2026-07-27 · v3.97

Work that connects the platform to an outside system now has a named standard it gets reviewed against, instead of every proposal re-arguing the same rule from scratch. The platform's list of core engineering values grows from six to seven, and the table showing what is actually enforced now reports its real status instead of a stale "pending".

> **Skip the rest** unless you propose or review work that connects the platform to an outside tool or service, or you read the build-philosophy coverage table.

## Who this affects

- Anyone proposing or reviewing work that binds the platform to an outside system — a new integration, a connector, or a change to how the platform talks to a host tool.
- Anyone who reads the build-philosophy coverage table to find out which engineering values are actually enforced today.

## What changed for everyone using the platform

- **A named standard for connecting to outside systems.** Portability joins the platform's core engineering values: the governed core talks to an outside system only through an adapter, the outside system's model stays inside that adapter and never redefines a platform concept, and a specific host tool is never written up as *the* way to do something in text meant to be host-neutral. *Why it matters:* when you propose or review this kind of work, there is now one named standard to check it against, so reviewers stop re-deriving the same rule on every proposal and can point at a shared rule instead of a personal preference.
- **The new value arrives with a working check behind it.** The existing check that scans skill instructions and their reference files for a host tool named as the only mechanism is now cited as this value's enforcement. *Why it matters:* the value is backed by something real on the surface it covers from the day it ships, rather than being a name with nothing enforcing it.
- **The coverage table now reports its true status.** Three cells that read "pending" — covering the governance and process best-practice rows — now state what is actually wired, and none are left reading "pending". *Why it matters:* if you consult that table to learn what is enforced, you get today's answer instead of a stale placeholder that quietly outlived its accuracy.
- **Gaps are marked as gaps, not left blank.** The new row explicitly marks the surfaces the check does not reach as gaps rather than implying full coverage. *Why it matters:* you can see exactly where the standard is not yet enforced, so you know when a human review is still the only thing catching a problem.

## Known limits

- The automated check reads skill instructions and their reference files. Agent definitions and slash-command prompts are not scanned, so a host tool named as the only mechanism in one of those is not caught automatically — both are marked as gaps in the coverage table.
- The check reads text that already exists. Nothing scores a design while it is still being decided, so a design choice that has not yet been written down will not be caught — that remains a human review step.
- The check reports findings without stopping a release.
- This release adds the standard and its index entry. It changes no skill, hook, command, or packaged behavior — nothing you run will behave differently.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. The release is a markdown-only change to platform reference documents; reverting the release PR restores the previous six-value charter and removes the register entry completely. No data migration, no runtime or packaged behavior to unwind — the only state outside version control is the milestone and issue status, which can be reopened.

### Operator and engineering detail

**What the value adds, and what it deliberately does not.** The platform already *implemented* the adapter-boundary property and already *detected* its failure — anti-corruption adapters, a config-driven selector seam, a registered host-binding-leak class with a rubric and remediation pattern, and a deploy-time detector shipped 2026-06-21. What was missing was the conformance axis: with no value row and no register entry, the Operator Decision Gate and acceptance review had nothing to score an adapter or external-binding option *against*, so each new port card re-derived the rule ad hoc. The detector does not close that gap — it catches a leak mechanically in text it already scans and is structurally blind to a design decision that has not yet become text. A detector without a principle is a lint without a standard. This release supplies the principle; it deliberately does not add a new detector. The premise-currency finding is recorded honestly in the plan: the originating ticket's "no conformance axis exists" claim was *partly* stale by the time it was built, and the slice survived narrowed rather than being waved through unchanged.

**Value, not a cross-cutting discipline.** The charter distinguishes first-class *values* from the two cross-cutting *disciplines* (read-before-edit, track-all-edits), which apply to every domain and every surface. Portability binds only external-binding surfaces — an internal-only change never engages it — so it fails the disciplines' own defining test and is recorded as a value. This is symmetric with the earlier Security elevation, which rejected the discipline option for the opposite reason. The coverage row is honest about reach: Skills carries a real enforcer, Hub/Spokes is thin (spec-text scanning only, no design-time gate), Hooks is marked not-applicable because hooks *are* the host-mechanism perimeter and host binding is their function rather than a leak, and Agents and Slash-commands are both marked GAP because neither surface is inside the detector's scan set.

One register entry in the new shape — the DP-9 row, shown column-by-column (the file itself stores this as a single pipe-delimited markdown table row):

```text
# design-principle-register.md — one DP entry (8 columns, pipe-delimited)
id:                   DP-9
name:                 Portability
statement:            The governed core binds to an external system only through an
                      adapter; the external system's model lives inside that adapter
                      and never redefines a governed concept.
governing_doc:        core/disciplines/build-philosophy.md:54
applies_when:         option binds the governed core to an external system
reversibility:        MODERATE
last_verified_date:   2026-07-27
last_verified_commit: ff616e3
```

**The name changed from the one on the ticket.** The originating ticket proposed coining `substrate-independence`. Collective Review rejected the coinage on evidence and renamed the value **Portability**, keeping the litmus question ("does the governed concept survive a substrate swap?") word-for-word. Three findings drove it: the coined term appeared nowhere in the platform's own writing at decision time, while the corpus already named this exact quality *Portability* in an earlier decision record; the word *substrate* was already carrying two other established senses across hundreds of occurrences, so reusing it would have overloaded it a third time; and in this corpus values are single quality nouns while cross-cutting disciplines are hyphenated compounds, so a hyphenated name would have visually contradicted the value-not-discipline decision made one gate earlier. The naming rationale and the rejected alternatives are recorded in ADR-098.

**Pin integrity across the insert.** Inserting a seventh value shifts the line each register entry points at, and the standing drift check only verifies that a pinned line exists — not that it carries the right principle — so a silently mis-pinned entry would pass. A prior release proved the risk real when two entries shifted by one line each. All nine entries were therefore re-pinned against the final file rather than trusting a projection, and verified at close with a whole-population probe asserting each pinned line actually carries its principle's name: 9 of 9 matched, and a deliberate off-by-one control confirmed the probe can detect a shifted pin. One entry's drifted description was reconciled in the same pass. For full implementation detail see the [RELEASE_LOG entry](https://github.com/cody-hutson/pmo-platform/blob/main/release/releases/RELEASE_LOG.md) and [the release plan](https://github.com/cody-hutson/pmo-platform/blob/main/release/releases/plans/v3.97_RELEASE_PLAN.md).
