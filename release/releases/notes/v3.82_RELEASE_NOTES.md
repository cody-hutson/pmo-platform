# Exec briefs name the real consequence; status updates cite their sources

2026-07-22 · v3.82

Four of the things you touch most often — the executive brief, the daily status update, the weekly rollup, and the check that watches your generated artifacts — behave better in ways you can see. Alongside them, several places where the written guidance said something different from what the platform actually does have been corrected, so following the instructions no longer sends you somewhere the platform will not go.

## What changed for everyone using the platform

- **Executive briefs name the real consequence instead of gesturing at one.** The brief now goes through a compression pass that swaps abstract impact wording for a specific outcome with a date attached, states that outcome in the unit an executive actually tracks, and separates what was expected from what was not. *Why it matters:* a reader can tell what is going to happen and by when without having to ask a follow-up question.
- **Daily and weekly status updates cite where each fact came from.** Both now build from the tracked decision, action, meeting, and risk entries and carry each entry's recorded source, rather than re-reading raw meeting transcripts every time an update is generated. *Why it matters:* you can trace any line in a status update back to the entry behind it, and two updates covering the same week stop disagreeing because each re-read the raw material and drew a different conclusion.
- **The artifact check catches an approved artifact left sitting in either staging folder.** The rule that flags content marked as approved but still parked in a staging area now looks in both staging folder names that are in use while the folder rename is underway. *Why it matters:* an artifact you already approved stops slipping past the check purely because it happens to sit in the newer of the two folders.
- **Escalations look up the decision owner in the stakeholder register.** When an escalation needs an owner, the platform now picks the register row marked as decision owner whose authority covers the decision area, instead of inferring a name from a free-text list of people. *Why it matters:* the escalation reaches someone who can actually make the call, and when the register has not been filled in it still falls back to the old free-text read rather than stalling.
- **Software templates that follow an external standard are no longer stuck.** A software template family with no matching plugin can now meet the promotion requirement by naming the published standard it follows. *Why it matters:* building a template around an established external standard no longer stalls waiting on evidence that could not exist in the first place.
- **The guidance on corrections agrees with itself about where a correction lives.** Three places still described one shared corrections file; all three now describe the arrangement that actually shipped — platform-wide corrections in one file, project-specific corrections stored with the project, and the project file winning when the two speak to the same point. *Why it matters:* a correction you give while working on one project lands where it will not leak into a different one.

## Known limits

- **The corrections change is the documentation catching up, not new behavior.** The two-tier arrangement itself shipped in an earlier release. What changed here is that three descriptions which still referred to a single shared file now describe the shipped arrangement. Nothing about how corrections are read changed in this release.
- **Escalation routing is only as good as the register behind it.** The structured lookup needs a stakeholder register whose decision-owner and authority columns are actually filled in. Where they are not, escalation falls back to reading the free-text list of names, and where that fails too it routes to the program manager rather than guessing a person.
- **The plugin survey behind the template change is dated, not permanent.** The template guidance now records what a survey on 2026-07-03 found installed, rather than asserting a standing fact. If those plugin suites are installed later, that section needs re-checking — it will not correct itself.
- **The status-update change governs reading, not writing.** Status writers now aggregate from tracked entries. The daily writer still reads a single same-day transcript when one triggers the update, which is a deliberate exception and is unchanged.
- **The artifact check still only recommends.** It surfaces a displaced artifact for you to act on; it does not move, promote, or delete anything on its own.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH. The release landed as a single merge commit, so reverting it removes all seven changes atomically, and each slice is an independent commit that can be reverted on its own. Nothing is migrated and no stored state is rewritten — the changes are to guidance text and skill instructions, which take effect the next time a skill runs. The ten rebuilt skill packages are regenerated from source by the standard build, so a revert restores them the same way.

### Operator and engineering detail

**Skill-behavior slices (#2805, #3386, #3385)** — The comms-writer voice guide gains an Executive Compression and Concreteness section plus two anti-pattern rows, and the SKILL.md Executive-brief type gains a five-step compression pass (cause to clause; consequence to concrete-plus-clock; impact to the executive's unit; expected versus unexpected; cut a paragraph) together with two five-field domain failure modes tagged OUT and INPUT. The daily-status and weekly-status-rollup skills gain an explicit read-side aggregation contract: aggregate from the tracked layer — the `DEC-###` / `ACT-###` / `MTG-###` entries, `MSG-##` rows, and RAID rows — and cite each entry's `source_inputs` / `source_ref` provenance rather than re-scanning raw transcripts. Daily-status' single same-day triggering-transcript intake is deliberately preserved as a write-side exception. The artifact-lint Check 4 displaced-content rule is re-keyed onto the ADR-080 folder union (`promotion_state: promoted` implies the artifact is in neither staging bin), so a promoted-but-not-moved artifact is caught in either bin across the taxonomy-migration window; the issue's original ADR-079 citation was a misattribution and is corrected to ADR-080 in both the edit and the plan.

**Standards reconciliation (#2473, #3289, #2854, #2472)** — The SIOR escalation protocol's Decision-Owner Mapping is upgraded from a free-text heuristic to a structured lookup against the Stakeholder Register (`Decision Owner = yes` and `Authority` matching the decision domain), with the free-text `## Key People` path retained as graceful degradation and warn-and-route-to-PgM as the terminal case; its residual note no longer asserts the structured authority field is unshipped. The template-protocol P5(c) promotion clause splits into a project-domain branch and a software-domain branch whose required `canon:` names an external canon with no plugin counterpart, so a software family such as RFC / IETF 7322 finally has a satisfiable `canon_compat: none` path and no family is stranded; the template-taxonomy section 7 is re-expressed as convention-anchors carrying the 2026-07-03 re-survey, reconciling the earlier install assertions with the Row-9 addendum. The two-tier CORRECTIONS model is reconciled across the operational-artifact inventory, the OPERATIONS graduation-and-expiry rule, and the memory-architecture read order; CLAUDE.md was deliberately left untouched because it already described the model correctly. The Stage-4 planning shard's `domain:` list now names the shipped `process` guide and states which four domains ship a guide today.

**Package rebuild fan-out** — Phase B4 was not a no-op for this release. Ten `.skill` packages were rebuilt: four for the directly-edited skills (comms-writer, artifact-lint, daily-status, weekly-status-rollup) and six consumer packages (delivery-engine, eval-writer, pmo-process-designer, pmo-skill-refiner, project-initiator, release-planner) that bundle the two canonicals touched by the template slice through build-time injection. That injection fan-out was not visible in the Stage-4 File Change Matrix, which had scoped the rebuild to the two directly-edited skills; the operator signed off on the in-PR scope addition, and the final package-drift audit reads 52 packages, 52 OK, 0 FAIL.

**Version re-anchor (v3.80 to v3.81 to v3.82)** — While this release ran through planning and execution, two concurrent releases consumed the intervening version slots: close-out-reliability-hardening took v3.80 and the version-identity-and-parser-SSOT release took v3.81. The label was therefore re-anchored twice, upward only, and no v3.80 or v3.81 tag was ever cut by this release. The residual is immutable history recorded as accepted: the branch name and the on-branch commit subjects retain their as-authored provisional labels. The original release PR was auto-closed when the branch-rename call deleted its head ref during the re-version, and a superseding PR carried identical reviewed content — that close was a side effect of the rename, not a rejection. Both abandoned versions are recorded one row each in the re-version ledger.

One acceptance residual — a taxonomy section still framing the plugin cross-references as install claims, contradicting the section the template slice had just reconciled — was swept inside the PR before the gate, so the release shipped with no open acceptance residuals.
