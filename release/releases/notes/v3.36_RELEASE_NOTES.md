# Process-domain specialist skills now share one best-practice anchor

2026-07-01 · v3.36

The four process-domain specialist agents — Scrum Master, Release Train Engineer, Business Analyst, and Product Owner — now ground their work in a shared process best-practice guide instead of asserting practices ad-hoc. This completes the three-part anchoring sequence begun with the software-domain specialists (v3.30) and the governance-domain specialists (v3.33), and also adds a new support-domain best-practice guide plus the change-domain decision to keep its best-practice content self-bundled.

## What changed for everyone using the platform

- The four process-domain specialist skills now cite a shared process best-practice guide (Scrum Guide, SAFe, BABOK, Disciplined Agile) as their design-time anchor. *Why it matters:* their guidance is grounded in one consistent source rather than per-invocation judgment.
- A new support-domain best-practice guide (ITIL 4, tiered incident and escalation practice, SRE) is now available, mirroring the software, governance, and process guides. *Why it matters:* the support specialists gain the same grounded, consistent design anchor the other domains already have.
- No new commands, no workflow changes, and nothing breaking — this is a consistency and best-practice-accuracy improvement. <!-- impact:foundational -->

## Known limits

- The support best-practice guide is authored and registered, but this release wires the **process** specialists; the support specialists' direct wiring follows the same compose-by-reference pattern in a sibling release.
- The change domain deliberately does **not** get a shared best-practice guide in this release: its best-practice content stays self-bundled with the change-management skill. That decision is recorded as a Proposed ADR with an explicit trigger to revisit if a second change-domain designer skill is ever introduced.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**CHEAP / HIGH confidence.** Every change is additive — reference pointers, one new guide, one ADR, and a coverage-matrix row; rolling back is reverting the release PR with no data migration.

### Operator and engineering detail

See the `#90-skill-anchoring-process-support-change` RELEASE_LOG row for the raw audit trail. Notable points:

- **Compose-by-reference (ADR-019).** Each specialist gains a `## Reference docs` pointer — no content is copied into the skills. The Scrum Master, Release Train Engineer, and Business Analyst get a single anchor to the process guide; the Product Owner gets a dual anchor to BOTH the process and governance guides, because value framing and the accept/reject decision span both domains (mirroring the dual-anchor Technical Program Manager). The process and governance guides' `consumers:` fields were appended accordingly.
- **New support-domain guide.** A net-new K1 universal guide covers service management (ITIL 4), tiered incident and escalation practice (with the mandatory paired applicability note), and service reliability (SRE — SLI/SLO, error budgets, toil). Three external source rows and one internal guide row were registered in the framework catalog in the established schema and anchor convention.
- **Change-domain decision (self-bundled).** The change-domain best-practice body stays self-bundled in the change-management skill's `references/`, with the framework catalog as its registry — no shared guide was created, and the OCM lead skill is intentionally unchanged (it reaches the suite transitively via compose-by-reference; a direct cite would bypass that path). Recorded in a Proposed ADR with a reversal trigger: promote to a shared guide only if a second peer change-domain designer skill is introduced. The build-philosophy coverage matrix gained a change-domain row and enforcer citation, and the change-management skill gained one Reference-docs line naming the registered source.
- **One PR, one merge.** All six issues shipped on one branch / one merge per the milestone-as-one-PR model.
- **No re-version.** Provisionally planned as v3.36; the slot was free at the atomic claim (anchor = published v3.35), so v3.36 bound at the merge commit with no collision. The `release/v3.35-skill-anchoring-process-support-change` branch name is retained per the no-retroactive-rename rule.
- **`.skill` packages** for the four edited process skills were rebuilt from source after the SKILL.md edits and committed at the Stage-12 cut (the `build(vX.Y)` convention), so the content-freshness check (Check 7) passes for them.
