# Designs are now checked for the right altitude before they're built

2026-06-21 · v2.17

The pipeline now asks one question of every new capability *before* it is built: does this extend an existing platform seam — a config adapter, a module boundary, a config surface — or does it solve the problem point-wise? Until now nothing forced that question, so a host-concrete point solution could land where a host-agnostic capability behind an adapter was the right design, and only get caught (if at all) by the operator off-pipeline. This release turns "pick the right altitude" from aspirational prose into a forcing function with teeth. It changes how platform capabilities are *designed and reviewed*; it changes nothing about how project work, status outputs, or skills behave day to day.

> **Skip the rest** unless you design platform capabilities or run the release pipeline.

## Who this affects

- The workspace operator and anyone authoring or reviewing a platform capability design (Stage 4 Planning, Stage 5 Solutioning, the design review). There is no change to how project work, status updates, or skills behave for everyday users.

## What changed for everyone using the platform

- **No change to everyday platform behavior.** This release adds a design-time discipline (governance/process specs + one warn-mode check); it does not change any skill output, status report, or day-to-day decision. <!-- impact:foundational -->
- **The seam question is now asked at design time and *blocks* if unanswered.** When a design makes a structural choice, it must name the existing platform seam it extends — or justify a point solution and cite the search that found no seam. A blocking design-review check fails a design that does neither. *Why it matters:* a capability that hardcodes one host's tool (or reinvents a mechanism) where a reusable seam already exists is caught at design time, not after it ships.
- **"Hardcoding a host tool as *the* mechanism" is now a named, detectable defect.** Naming `gh` / `git` / a host API as the one canonical mechanism in universal governance — where it belongs behind an adapter seam — is registered as a `HOST-BINDING-LEAK` (the host-side sibling of the existing path-portability rule), and a warn-mode check surfaces new instances. <!-- impact:foundational -->
- **The independent design reviewer can now flag a mis-framed premise.** The adversarial review — previously barred from re-opening any operator-decided premise — may now raise an advisory flag when a *settled premise itself sits at the wrong altitude*, routed to the operator at scope-lock. It still cannot reverse the decision on its own, and it still cannot re-litigate a settled mechanism choice; it can only surface the altitude concern to the one person who can re-open it. <!-- impact:foundational -->

## Known limits

- The blocking gate's forcing function is complete on its own; a richer architecture-evaluation lens (a separate in-flight effort) will be bound to it later — until then the gate enforces "name the seam or justify point-wise," not a deeper altitude rubric.
- The `HOST-BINDING-LEAK` detector ships **warn-mode** (it reports candidates, it does not fail a build) during its shakedown window; it flips to enforcing later. It is deliberately narrow — it flags a host tool named as *the* prescribed mechanism, not every mention of `gh`/`git` — so a genuinely new leak phrased unusually may not be caught until the rule is tuned.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. Every change is additive — process/governance specs, one core-discipline section, and one warn-mode deploy-check detector; no skills or packages changed. Reverting the release merge restores the prior state exactly; no data migration and no skill rebuild are required.

### Operator and engineering detail

**The forcing function — three insertion points (E1; #1764, sliced #1774/#1775/#1776).** Defense-in-depth across the design path: (1) a **Stage-4→5 obligation rider** on the T3 (structural design) trigger requires the issue to name the platform seam the capability extends — an `operator.toml [adapters]` selector, a module boundary, or a config surface — or justify a point solution with a cited seam-search (`core/standards/planning-solutioning-handoff.md` §3.1); it fires at Stage 4 Planning, *upstream* of the Stage-5 "don't relitigate the ratified frame" estoppel, so altitude stays a design variable while the frame is still open. (2) Design-exploration gains **`altitude`** as a fifth distinctness axis with three bands — **point-fix / extend-seam / new-abstraction** — plus a **≥2-band rule** that forces the seam-extension candidate into the generated set whenever a new mechanism is introduced, and the worked example is replaced with one that diverges on altitude (`release/references/standards/design-exploration.md`). (3) A blocking **§4.7 seam-composition gate** in the design-review checklist makes a missing seam-answer *fail* Section 4 (omission is a fail, not a behavioral marker), wired into the Section-4 Pass criterion and Fail action, and carries the version-claim replay as its validation scenario (`release/references/templates/design-review-checklist.md`).

**The named leakage class + detector (E4; #1767).** `core/disciplines/knowledge-architecture.md` §4.1 registers **HOST-BINDING-LEAK** — hardcoding a host tool as *the* canonical mechanism in universal (K1) governance where the operation belongs behind an adapter seam, an abstraction-altitude leak distinct from the identity/contextual leaks the register already catalogs, and the host-axis sibling of the path-portability class. A warn-mode `deploy.sh` **Check 42** (`core/deploy/tools/check-host-binding.py`, self-tested, with a tracked allowlist for the discipline-defining files that legitimately describe the pattern) flags a host tool prescribed as the canonical mechanism in K1-tier governance. The §4.7 gate cites this class by name when it finds one.

**The independent adversarial surface (E2; #1765).** The Stage-5 A6.5 adversarial review carries a scoped exception to its "does not litigate operator-pre-decided D-decisions" anti-pattern: it MAY flag that a pre-decided premise sits at the wrong abstraction altitude, surfaced as an advisory **Premise-Altitude-Finding** with an explicit no-autonomous-reversal guard, routed to Collective Review scope-lock — the same decision home the §4.7 gate uses. The exception opens *only* the altitude axis (settled mechanism choices stay un-relitigable) and is propagated through the adversarial chip-construction discipline (`release/references/specs/release-personas.md` + `release/references/how-to/hub-spoke-bridge.md`).

**Discoverability cross-references (E3; #1766).** The `release/` pipeline specs now point back to the `[adapters].repo_host` host-operation seam (`release/governance/release-process.md`, `release/references/pipeline/stage-12-execute.md`, `release/references/pipeline/stage-13-close.md`), so a release-module design pass discovers the seam by reading its own specs. Scope-corrected: the version-claim sites already cite the adapter, so this covers the non-version host-op sites.

**ADR posture.** No new ADR — the `[adapters]` host-adapter decision is already operator-ratified (ADR-022); this release adds a *process gate* enforcing it, recorded in the design rationale rather than a duplicate ADR (per the ADR-durability discipline).

**Pipeline-context note.** Cross-cutting release; Stage 6 Engineering executed hub-inline (the Solutioning specs were implementation-ready exact insertions, and the hub operated in an isolated worktree, avoiding the spawned-spoke shared-branch cwd hazard); Stage 9 PR review was the independence/review gate. For full implementation detail see the [RELEASE_LOG.md entry](../RELEASE_LOG.md#deployment-log-v217) and [the release plan](../plans/architecture-altitude-discipline_RELEASE_PLAN.md).
