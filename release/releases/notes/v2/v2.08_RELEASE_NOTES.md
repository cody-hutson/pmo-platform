# Generated artifacts now have a lineage graph, and a lint that surfaces the strays

2026-06-20 · v2.08

This release gives the platform's generated-artifact surface — the staging area where AI-generated artifacts land and the folders they are promoted into — a lineage graph and a graph-integrity lint. Generated artifacts can now record which artifact they came from, a topic that groups near-duplicates, and which artifact they replace; and a new recommend-only skill scans that surface for duplicates, orphans, stale drafts, displaced files, and version chains, surfacing each finding for operator approval instead of letting them silently accumulate. The lint never moves, renames, or deletes anything — every action it proposes is operator-approved. Everything is additive: a new skill and new optional metadata fields, with no existing field, file, or behaviour removed or renamed.

## What changed for everyone using the platform

- **Generated artifacts can now record their lineage.** Three new optional metadata fields let a generated artifact name the artifact it derives from, a grouping topic used to spot near-duplicates, and the artifact it supersedes — recorded the same way on both regular files and their sidecar metadata. *Why it matters:* parent-child and replacement relationships between AI-generated artifacts now survive the session that created them, so the platform can later tell a current version from one it replaced.

- **A new lint surfaces duplicate, orphaned, stale, and misfiled generated artifacts.** A new skill — "artifact lint" — scans the generated-artifact staging area and promoted folders and runs five checks: orphaned artifacts (no recorded source), near-duplicate siblings, stale drafts, files sitting in the wrong folder for their type, and version chains. It produces a single report with a proposed action and an undo-cost rating for each finding. *Why it matters:* the things that quietly clutter a generated-artifact folder over time are now surfaced for review in one place.

- **The lint recommends; it never acts on its own.** Every finding is a proposal — promote this, archive that, link this version chain, move this file to its correct folder — and nothing happens until the operator approves it. The lint performs no file moves and no deletes. *Why it matters:* you get the cleanup analysis without any risk of the tool changing or removing an artifact you wanted to keep.

## Known limits

- The lint is **read-and-recommend only by design** — it surfaces findings and proposes actions, but it never moves, renames, or deletes an artifact. Acting on a finding is a separate, operator-approved step.
- The lineage fields are **optional**. An artifact with no lineage recorded is simply reported as an "orphan" with a proposal to either record its source or archive it — a flag for review, not an error.
- The work-plan taxonomy the "wrong folder" check uses is an **evidence-grounded reconstruction** that was confirmed as authoritative during the release review, because no single canonical taxonomy file existed beforehand. It is treated as a firm reference, but findings against it remain recommend-only like everything else.
- This is governance, tooling, and a new skill. It changes how the platform tracks and checks its own generated artifacts, not how any project-facing skill behaves; there is nothing to install.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

### Operator and engineering detail

**#334 — Horizontal-lineage frontmatter fields (lineage, distinct from provenance)** — Wires the horizontal-lineage scalar fields `parent_artifact` / `sibling_topic` / `supersedes` (with the `supersedes`/`superseded_by` inverse pair) into `core/schemas/frontmatter-schema.md` across **both Domain A (formal-baseline) and Domain C (synthesis)** so an A↔C lineage chain resolves. Adds the **lineage-vs-provenance distinction table** that fixes the boundary the two would otherwise blur: lineage records horizontal edges *between generated artifacts* (parent→child, supersede), while provenance records the *upstream human evidence* an artifact derives from — with `source_inputs` explicitly scoped out as a separate provenance concept not yet defined in the schema. Records the **field-vs-verb composition note**: these are lightweight per-artifact scalar carriers that **compose against** the 7 MVP `relationships[]` verbs rather than extending them — a `supersedes:` scalar denotes the same edge a `type: SUPERSEDES` relationship entry expresses, no new enum value is added, and the 7-MVP-type constraint is unchanged. Specifies **sidecar `.meta.yml` parity** (the lineage fields carry identically on non-markdown artifacts, so edges stay grep-discoverable) and a **WARN-not-BLOCK dangling-lineage rule** (a lineage path that does not resolve is a flag, consistent with relationship-target resolution — not a hard failure). Syncs `core/standards/lifecycle-states-canonical.md §3.2` (the `DRAFT → REVIEWED → APPROVED → PROMOTED → ARCHIVED` Artifact Workflow restatement gains the three lineage-graph fields, with a cross-pointer naming `frontmatter-schema.md` as the schema home) and reconciles `core/standards/template-protocol.md` §9 (`topic` → `sibling_topic`) — the third reconcile target, caught at Stage 5 beyond the two named at planning.

**#1165 — artifact-lint (a NEW recommend-only graph-integrity skill)** — Authors `operations/skills/artifact-lint/SKILL.md`, a NEW **Autonomy Tier 1 (Recommend)** skill that scans a project's generated-artifact surface (`08-Generated/` plus promoted folders) and runs **five graph-integrity checks** reading the #334 lineage frontmatter: **orphan** (no recorded source — propose set-source or archive), **sibling-duplicate** (strict composite-key match — propose keep-current + supersede-edge, or merge), **stale-draft** (a draft older than the staging threshold — propose promote / archive / refresh), **displaced-content** (folder contradicts the type's canonical home — propose correct-folder), and **version-chain** (an ordered `_v1.._vN` set — confirm the head, propose archiving superseded members). It stages a single report to `08-Generated/artifact-lint-YYYY-MM-DD.md` with, per finding, the check, the affected artifact(s), the frontmatter evidence that triggered it, a proposed action, and a reversibility tier + confidence — and performs **no file moves and no deletes** (the operator dispositions every finding). Ships the **17-row work-plan taxonomy** (`references/work-plan-taxonomy.md`) the displaced-content check uses as the canonical-target-folder lookup, plus `references/edge-cases.md`. Registered in `core/deploy/deploy.sh` `OPERATIONS_SKILLS` (and the `build-skill-packages.sh` `ALL_SKILLS` roster), shipping its own `.skill` package and `.sha256` content-hash baseline; its output contract was added to `core/schemas/per-skill-output-contracts.md`.

**FINDING-1 — the dual state-read (load-bearing input rule).** The stale-draft and version-chain checks read **`artifact_state` first, then fall back to `lifecycle_state`** when `artifact_state` is absent. This matters because the two fields come from different places: `artifact_state` is the Artifact Workflow enum (`DRAFT → REVIEWED → APPROVED → PROMOTED → ARCHIVED`) stamped by the artifact-generator and is *not* a field in `frontmatter-schema.md`, while `lifecycle_state` is the schema's REQUIRED state field. Both appear in the wild, so keying on only one would silently mis-read every artifact carrying the other — producing false-negative stale drafts and phantom version-chain heads. The dual-read is the fix.

**FINDING-2 — the 17-row taxonomy is an evidence-grounded reconstruction.** No literal 17-row work-plan taxonomy survived in the canonical corpus — the original split card that would have defined it was deleted — so the taxonomy was reconstructed from evidence: the **Canonical-10** are the Domain-C synthesis `artifact_type` value set in `frontmatter-schema.md`, and the **Situational-7** are the plan-type set plus the waterfall/cutover rows. This reconstruction was **operator-confirmed at Stage 9 Collective Review** as the authoritative taxonomy, so the displaced-content check treats a canonical-home mismatch as a firm finding (still recommend-only).

**Forward-binding follow-up.** `lifecycle-states-canonical.md §3.2` notes a planned co-located protocol document, `core/artifact-workflow-protocol.md`. When that ships, the §3.2 authoritative-source pointer updates to cross-reference it as the operational-protocol home (handled at that release's Stage 13); until then, §3.2 remains the canonical source for the Artifact Workflow vocabulary and state machine.
