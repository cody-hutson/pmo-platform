# The role-Specialist suite is now GA — ask for a role, get routed to it

2026-06-20 · v2.15

The platform's role-Specialist suite reaches general availability. This release adds the last five role agents — Release Manager, Tier-1 Support, Tier-2 Support, OCM Lead, and Knowledge Manager — and a router that turns a role-shaped request into the right Specialist automatically. You can now address the platform as a *role* ("act as the release manager", "tier-1, is this a known issue", "act as knowledge manager") and the request is matched to the Specialist that owns it.

## Who this affects

- **Anyone who invokes the platform by role.** All nineteen role-Specialists are now addressable as one suite, and a request you phrase in role terms is routed to the matching one — you no longer have to know which skill name to call.
- **PMO practitioners** gain the support and change-management seats: Tier-1 Support (triage + known-issue lookup), Tier-2 Support (root-cause + runbooks), the OCM Lead (the change program for a go-live), and the Knowledge Manager (capture-and-file knowledge assets).
- **Anyone running a release** gains the Release Manager — the go/no-go, deploy authorization, and close-out seat.

## What you need to do

1. Run `update.sh` to deploy this release — it lands the five new role-Specialist skills, the capstone router, and the skill registry.
2. Nothing else changes in how you invoke the platform; the new role-skills become available on deploy and trigger on role-shaped requests.

## What changed for everyone using the platform

- **The suite is complete and addressable as one unit.** The nineteen role-Specialists — the fourteen built in prior waves plus the five in this release — are now a single, routable suite. *Why it matters:* you can reach for any delivery role by name and get its full perspective, not a generic function output.

- **A router sends a role-shaped request to the right Specialist.** Ask "which role handles this?" or phrase a request in role terms and the router matches it to the one Specialist that owns the work. *Why it matters:* you do not have to know the skill catalogue — you describe the role you want and the platform picks the right one.

- **The Release-to-Sustain roles are now first-class agents.** A Release Manager owns the release tail (go/no-go, deploy, close-out); Tier-1 Support triages and resolves known issues; Tier-2 Support root-causes the novel ones and writes the runbook; the OCM Lead drives a go-live's organizational change; the Knowledge Manager captures and files knowledge assets. *Why it matters:* the seats that carry a delivery effort from ship through steady-state are covered, each with its own judgment and boundaries.

- **Support escalation has a clean tier boundary.** Tier-1 owns no root-cause analysis — a novel problem is handed to Tier-2 with a structured escalation record, and Tier-2 turns its fix into a runbook so the same problem becomes first-line-resolvable next time. *Why it matters:* known issues get fast answers and genuinely new problems get a real causal investigation, instead of one seat doing both badly.

- **Each Specialist composes existing skills instead of duplicating them.** The Release Manager invokes the release planner and executor; the OCM Lead invokes change-management; the Knowledge Manager invokes the artifact generator and file router. *Why it matters:* one consistent engine underneath every role — no divergent re-implementations to drift apart.

## Known limits

- Routing is governed by a single registry file: a role-Specialist is addressable only once its row is present in the registry, and routing is only as good as each row's description. Adding or changing a role is a registry edit, not a router edit.
- The methodology-specific roles still follow their activation rules (e.g., the Release Train Engineer stays dormant unless your `delivery_approach` is SAFe, per ADR-033) — GA does not change that.
- Follow-on suite work (the System-Specialist frontier, #408; the broader skills-architecture initiative, #410) is tracked separately and is not part of this release.

Report issues at the repository's GitHub Issues.

### Operator and engineering detail

**Suite GA (Phase 4 + Phase 5).** This release closes the final two phases of the role-Specialist build (epic #284): the Phase 4 Release-to-Sustain wave — `pmo-release-manager` (#1120, composes `release-planner` + `release-executor`), `pmo-tier-1-support` (#1121), `pmo-tier-2-support` (#1122, owns the RCA method and authors runbooks), `pmo-ocm-lead` (#1123, composes `change-management`), `pmo-knowledge-manager` (#1124, composes `artifact-generator` + `file-router`) — and the Phase 5 capstone, the `pmo-skill-router` (#181) plus its L4 suite-integration run. Each Specialist is a thin role that composes shipped function-skills via the `core/` registry skill-chain rather than re-implementing them, per ADR-019 + ADR-007.

**The logical skill registry (#1564).** `core/skills/registry.md` is the single classification source the router reads: one row per role-Specialist (`name` / `module` / `trigger surface` / `modes`), authored centrally — a Specialist registers by having its row in the table, not by adding a field to its own `SKILL.md`. The router enumerates no skill list of its own, so routing changes by editing the registry, never the router (the same by-path-consumption posture `pmo-qa-auditor` uses against `per-skill-output-contracts.md`). #1564 also backfilled the fourteen prior-wave rows and the core skills, bringing the registry to its full nineteen-Specialist roster at GA. ADR-035 records the registry decision (renumbered from a branch-local ADR-034 behind main's progressive-rollout ADR-034).

**Version note.** The release branch and milestone are named for the provisional `v2.12`; the release was re-versioned up to **v2.15** at tag time because the `v2.12`/`v2.13`/`v2.14` slots were taken by sibling releases that shipped mid-pipeline (per the versioning-lineage / no-version-less-as-hedge discipline).
