# Ambient intake runs on a schedule now — and one dial controls how far it can go

2026-06-20 · v2.07

The daily processing cycle no longer has to be launched by hand. This release adds scheduled "sweeps" that watch an inbox and your trackers, capture and classify what arrives, and propose updates — all bounded by a single plain-language dial you set in your config. The dial (`off` / `recommend` / `bounded_auto`) is a ceiling: nothing the automation does can exceed the level you choose, and the human-only decisions stay human-only no matter what. A consolidated daily digest reports what every sweep did, with a heartbeat so a sweep that quietly stops can't go unnoticed. A new runtime guardrail enforces the ceiling — it ships in a logged-but-not-blocking mode you turn on after a short trial.

## Who this affects

- Anyone who runs the workspace's daily intake — the scheduled sweeps and the automation dial are new capabilities you opt into by setting the dial and deploying the update.
- The dial defaults to a conservative ceiling; the automation does nothing above the level you set.

## What you need to do

1. Run `update.sh` to deploy this release — this installs the new runtime guardrail (the autonomy-ceiling hook) into your workspace.
2. Set your automation level: open `operator.toml`, find the new `[automation]` section, and set `automation_level` to `off`, `recommend`, or `bounded_auto` for how far you want the sweeps to act on their own. Start at `recommend` if you want the sweeps to surface drafts without writing anything on their own.
3. After a short trial period, switch the guardrail from logged-but-not-blocking to actively blocking by flipping `.autonomy-mode` from `warn` to `enforce`. Until you do, above-ceiling actions are logged but not stopped.

## What changed for everyone using the platform

- **One dial sets how far ambient automation can act.** A new `automation_level` setting (`off` / `recommend` / `bounded_auto`) in your config is a ceiling on everything the automation does — the actual permission for any action is the lower of your dial and that action's own limit. *Why it matters:* you control the autonomy of the whole intake pipeline from one place, in plain language, and the human-only decisions are never unlocked regardless of where you set it.

- **Intake can run on a schedule instead of by hand.** Scheduled sweeps watch an inbox and your transcripts/emails (Path A) and your external trackers — Jira, Confluence, Smartsheet (Path B) — capturing, classifying, and proposing updates, with tracker closes proposed only when the supporting evidence is present. *Why it matters:* the routine processing cycle happens on a cadence without you launching it, and a close never fires without its evidence.

- **A watched inbox no longer ingests the same thing twice.** The new inbox drop-zone tracks what it has already seen with a content fingerprint. *Why it matters:* dropping a file in for processing is safe to repeat — the same artifact is not picked up twice across sweeps.

- **One daily digest reports every sweep, with a heartbeat.** All sweep activity rolls up into the daily status digest, which carries a sweep-health heartbeat. *Why it matters:* you see what the automation did in one place, and a sweep that silently stops shows up as a missing heartbeat instead of going unnoticed.

- **A runtime guardrail enforces the ceiling.** A new check inspects each action against your dial and blocks anything above the ceiling in the highest-stakes categories (governance and cross-domain changes). *Why it matters:* the dial is not just advice — once you turn the guardrail on, it actually stops above-ceiling actions; until then, it logs them so you can see what it would block.

## Known limits

- The runtime guardrail ships **logged but not blocking** at first. It records above-ceiling actions but does not stop them until you flip `.autonomy-mode` from `warn` to `enforce`.
- The guardrail enforces the ceiling on the action categories it can detect from the action itself (governance and cross-domain changes); it does not re-derive intent beyond what the action payload reveals.
- A scheduled Microsoft Teams intake connector was planned for this release but **did not ship** — it depends on a governed Teams integration that is not yet available (its design is tracked separately). Sweeps cover the inbox, transcripts/emails, and Jira/Confluence/Smartsheet for now.
- Onboarding documentation for the new automation settings is tracked as a follow-up and is not part of this release.

Report issues at https://github.com/cody-hutson/pmo-platform/issues with the `cluster: automation` label.

## Reversibility

MODERATE / HIGH confidence. The configuration dial, the sweep specifications, and the daily-status digest are additive and reverse cleanly. The runtime guardrail (the autonomy-ceiling hook) is the part that touches live behaviour: it ships logged-but-not-blocking, so it changes nothing until you turn it on, and turning it off again restores the prior state. Whole-release rollback is `git revert -m 1` of the integration merge plus deleting the `v2.07` tag, after which the guardrail no longer runs and the dial setting has no effect. Standard 7-day rollback window.

### Operator and engineering detail

**#322 — C0: the `automation_level` governor dial** — Adds an `[automation]` table carrying `automation_level` (`off` / `recommend` / `bounded_auto`) to `core/config/operator.toml.template`. It is a workspace-wide ceiling consumed by all ambient automation under `effective = min(automation_level, per-action max)`; the irreducible-human task set is never unlocked regardless of dial position. This card is the single governing surface the other five build on.

**#1159 — C1: ambient inbox drop-zone + dedup cursor** — `core/standards/c1-ambient-inbox-cursor.md` specifies the watched inbox drop-zone and a content-hash dedup cursor, so re-dropping or re-scanning never ingests the same artifact twice across sweeps.

**#1160 — C2: Path-A scheduled intake sweep** — `core/standards/c2-intake-sweep-path-a.md` specifies the scheduled capture→classify→register sweep over the ambient inbox plus drive transcripts/emails, clamped by `automation_level` (a `recommend`-ceiling sweep surfaces drafts and writes nothing above Tier 1).

**#1161 — C3: Path-B external sync + evidence-gated auto-close** — `core/standards/c3-external-sync-path-b.md` specifies the snapshot-diff external-sync against Jira / Confluence / Smartsheet (MCP), reconciling tracker state and proposing closes only when the gate evidence is present.

**#1162 — C4: consolidated digest + heartbeat** — `operations/skills/daily-status/SKILL.md` and `operations/skills/daily-status/references/ambient-sweep-digest.md` roll every sweep into one consolidated daily-status digest carrying a sweep-health heartbeat, so a stalled sweep surfaces as a missing/last-run heartbeat rather than failing silently. The `daily-status.skill` package and its content-hash sidecar were rebuilt and are present on main (deploy Check 7); runtime mirror sync is `./core/deploy/deploy.sh --deploy daily-status`.

**#1163 — C5: PreToolUse autonomy-ceiling hook (v2)** — A unified payload-triggered `core/hooks/block-autonomy-ceiling.sh` (442 lines) plus a cache-primer (`core/hooks/prime-autonomy-ceiling-cache.sh`) and a test fixture, registered in `core/settings.json.template` PreToolUse and shipped warn-mode-initial via `core/hooks/.autonomy-mode.template`. It blocks above-ceiling actions in the payload-detectable Tier-0 classes (governance / cross-domain) once flipped to enforce. The C5 reconciliation **R-C5RECON** resolved to this single unified payload-triggered hook (**ADR-031**, `core/ADRs/ADR-031-autonomy-ceiling-unified-payload-triggered-hook.md`, Accepted), which **supersedes** the `core/standards/subagent-security-posture.md §4` subagent-tier design — the §4 region was reworked to cite ADR-031. The hook-registry drop-in `core/rules/bypass-mode-readiness/block-autonomy-ceiling.md` plus `_header.md` and the regenerated `bypass-mode-readiness.md` index landed alongside (the ADR-030 generated drop-in registry from v2.06).
