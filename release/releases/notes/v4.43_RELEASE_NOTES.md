# Release plans now show when they're done, and reports count every release

2026-08-28 · v4.43

A release plan now tells you whether its work is finished, and it carries one name from the day it is drafted to the day it closes. The counters and queries that report on releases stopped silently skipping the ones that ship without a version number.

> **Skip the rest** unless you read release plans, or read counts and reports produced when a release closes.

## Who this affects

- Anyone who opens a release plan to see whether its work is still in flight
- Anyone who reads release counts, close-out reports, or pipeline event queries

## What changed for everyone using the platform

- **Finished plans now say they are finished.** Every plan carried the same in-progress status for its entire life, so a plan whose release shipped months ago looked identical to one still being worked; a plan now moves to a closed status when its release completes, and 34 existing plans were updated to match. *Why it matters:* you can tell from the plan itself whether its work is still open, instead of cross-checking the release log to find out.

- **A plan keeps one name, and takes a version number only once that version is real.** A plan is named for its release while in flight and renamed to the version number at the moment that version is claimed. *Why it matters:* you can find a plan by the version it shipped as, and a plan can no longer sit on a version number that a different release ends up taking.

- **Counts now include releases that ship without a version number.** Five counters and a set of event queries matched only version-numbered releases, so anything shipping without one was left out — and left out silently, without being reported as skipped. *Why it matters:* a total you read is now the whole population rather than a subset that looks like one.

- **Plan verification stopped reporting results for checks it never ran.** The verifier discarded any row whose text happened to contain a heading word, and read some rows one column out of position, so a result could be taken from the wrong cell entirely. *Why it matters:* a passing verification row now means the check named in that row is the check that actually ran.

- **Every verification method is tied to the criterion it tests.** Plans now bind each verification row to the specific acceptance criterion it covers. *Why it matters:* a plan can no longer show complete verification coverage while one of its criteria goes untested.

## Known limits

- **The closed status is applied by closes that run from this release onward.** Plans for releases that closed before it keep the status they had. Five plans read as in-progress for this reason today, four of them for releases that have already shipped.
- **Most plan files carry no status field at all.** 38 of 184 plan files have one, and the lifecycle governs only those. Older plans that predate the field are unchanged and are not detected as missing it.
- **The two counting fixes cover the surfaces this release inspected, not every surface.** Five counters and one set of event queries were corrected; no mechanism enumerates the full set of places a release population is counted, so another one may exist.
- **A defect found in the plan verifier during this release was scoped, not fixed here.** It is tracked separately and named in the follow-ups below.

Report issues at the repository issue tracker.

## Reversibility

MODERATE / HIGH confidence. `git revert -m 1` on the release merge commit reverses the nine cards together, including the status change to all 34 plan files — every change is a script, workflow, or tracked-text edit, and there is no data migration. Two asymmetries are stated rather than hidden: the version tag and the plan's rename to its version-numbered name are created outside the release merge, so a revert would neither remove the tag nor restore the earlier filename; and this release changed the checks and transitions that run during its own close, so a revert would not un-run a close that has already happened. Standard rollback window.

### Operator and engineering detail

**The status field had exactly one live value, which is why nothing detected the gap.** Before this release the frontmatter `status:` enum admitted a single value, and all 32 files carrying it read `ACTIVE` — so there was no terminal value for a close to write, and no disagreement for a check to find. A three-surface split compounded it: the frontmatter field, a body `**Status**` row carrying twelve free-prose values, and the release log's own `State` column, with 22 files carrying two of those surfaces in disagreement. This release added the terminal value, gave the close-out a writer for it, and backfilled the corpus; the body-row surface and the disagreements between surfaces are not reconciled here.

**Five counters and a set of event-log read sites were anchored to a version-shaped key.** Each matched a version-numbered release and skipped anything else, and none reported the skip — the failure mode the corpus doctrine names as an unparseable or absent input reading as "nothing found, therefore nothing wrong." The fix re-keys them on the release's own identity rather than on the presence of a version stem. The population they now cover includes version-less releases, whose notes and plans live in the corpus under slug-keyed names.

**Two defects in the plan verifier were found by deriving each row's expected verdict from its own predicate rather than by differencing a tally.** An empty field collapsed under the shell's default field splitting and shifted every later field one position left, so the tool dispatched a row's expected-result cell as its method; and a data row containing a heading keyword was consumed as a heading and dropped with no diagnostic. Neither is visible to a count comparison — the first changes which cell produced a verdict without changing any total, and the second removes a row from numerator and denominator together. Both are pre-existing, were verified byte-identical before and after the card that surfaced them, and are scoped to the mechanisms rather than to the two rows that exposed them.

**One decision record was authored on this branch and renumbered three times before it landed.** ADR-161 held three earlier numbers while sibling releases merged ahead of it, and each hop is recorded in the record's own provenance notes. In-release citations naming the earlier numbers denote the same record. Its ratification state is verified by reading the file's `status:` field, never inferred from milestone closure.
