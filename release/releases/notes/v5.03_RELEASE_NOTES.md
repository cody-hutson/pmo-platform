# One standard now says where every kind of out-of-git data lives

2026-11-07 · v5.03

The platform now has one standard that names the class and home of every kind of data it keeps out of git, and one decision record, Accepted at this close, that says why. Nothing moves in this release: every file stays where it is today, and there is nothing you need to do.

> **Skip the rest** unless you add a new kind of data the platform keeps out of git, review a design that decides where such data lives, or read the governance pages that say where data lives.

## Who this affects

- Anyone adding a new log, list, run folder, cache or other data the platform keeps out of git
- Reviewers of designs that decide where such data lives
- Operators and agents who read the workspace charter's classification rule or the governance pages that describe where data lives

## What changed for everyone using the platform

- **Data kept out of git is sorted by its risk.** The platform's own release and run records belong to the repository they are about, usage telemetry that spans the whole install has an install-level home, and leak-risk content such as the PII scan lists and the people roster has a home outside every repository and workspace. *Why it matters:* the reason for keeping leak-risk content out of every repository is no longer applied to everything by default, which is how one folder came to mix both kinds.

- **One standard lists every known surface with its class and home.** The [placement standard](https://github.com/cody-hutson/pmo-platform/blob/main/core/standards/instance-data-placement-standard.md) registers 44 surfaces, each with its class, its home and the path it resolves to today, and gives a five-step routine for a new one: classify, register, provision, protect, validate. *Why it matters:* a new kind of data has one place to look up and one routine to follow, instead of being decided page by page.

- **The decision behind it is Accepted.** A [decision record](https://github.com/cody-hutson/pmo-platform/blob/main/core/ADRs/ADR-231-non-tracked-data-homed-by-risk-class.md) explains the classes and their homes, and it replaces the earlier record that put all of this data in one folder beside the workspace. *Why it matters:* later work that moves data builds against one ratified decision rather than three records that disagreed.

- **The governance pages agree on where data lives.** The workspace charter template, the architecture overview, the memory contract, the operations bridge, the hub-spoke bridge and the hub-state standard state the same classes, cite the standard, and keep today's path beside each new home. The charter's classification rule no longer counts the out-of-repository folder, or the ignored contents of a folder inside the repository, as tracked. *Why it matters:* an agent reading any of these pages gets the same answer, and the path it is told to use today is still the right one.

- **The release records have a declared home setting.** A new `corpus_home` setting in the operator configuration names where the release records live. Its only value is `tracked`, which is today's behavior, and the configuration check accepts it. *Why it matters:* the release records are confirmed as tracked repository content, so no page describes moving them as pending.

## Known limits

- Nothing moves yet. Every file stays where it is, and every running release keeps writing its records to today's folder until a later release of the [parent epic](https://github.com/cody-hutson/pmo-platform/issues/8005) switches that repository over. The resolver, the commit guard for in-repository homes, the installer change and the moves themselves are later releases.
- Four of the 44 register rows are marked Undecided — the methodology packs, the hook runtime logs, the install validator's per-run folder and twelve hook-tier allowlists. Each names the later change that decides its class.
- The `corpus_home` setting is declared but not yet read: the release tooling still finds the release records by looking for the tracked folder first.
- The folder inside each repository that will hold working state, and the guard that stops it from being committed, do not exist yet. Until the guard ships, an ignore rule is the only protection for the in-repository folders that already exist.
- Your workspace charter picks up the new classification rule at your next platform update; until then it shows the old rule. No skill, hook or template changed.

Report issues at https://github.com/cody-hutson/pmo-platform/issues, and report a suspected vulnerability privately as the [Security Policy](https://github.com/cody-hutson/pmo-platform/blob/main/SECURITY.md) describes.

## Reversibility

EXPENSIVE / MEDIUM. Before this close ratified the decision record, reverting the single release merge restored every file, because nothing had moved. Now that the record is Accepted, the decision changes only through a record that supersedes it, though the pages it governs still revert with the merge. The version tag is kept as the record that the version was claimed.

### Operator and engineering detail

**The decision record (#8016).** ADR-231 homes working state in a git-ignored `/local-state/` at the root of the repository it belongs to, beside the registered `/analysis/` and `/roadmaps/` homes; install-scoped working state at `${XDG_STATE_HOME:-$HOME/.local/state}/pmo-platform/telemetry/`; and leak-risk content at `${XDG_DATA_HOME:-$HOME/.local/share}/pmo-platform/pmo-private/`, outside every tree. It supersedes ADR-141 whole and ADR-017, ADR-032, ADR-046 and ADR-096 in part; each partial target's `superseded_by:` gained an appended entry, its kept entries byte-preserved. The main-checkout carve-out is the enumerated set `/local-state/`, `/analysis/<sub>/` and `/roadmaps/<name>`, held to the write-guard hook's static set by a parity check a later wave owns, and the record carries two build obligations for later waves: sandbox parity for the per-user homes, and a loud failure on an empty home. The operator ratified it `Proposed → Accepted` and retired ADR-141 to `Superseded by ADR-231` at this close, one decision per record, in one commit.

**The standard (#8017).** `core/standards/instance-data-placement-standard.md` is the record's operational half: the four classes plus the install-scoped variant, the homes, the three registered in-repo homes, the admission test, the protections, the folder-plus-README idiom, the five-step checklist and a path-token naming rule. Its register reads 44 rows — 18 from the epic's pinned fit/gap population, 13 found in tracked code, 8 from the token registry and 5 from design — with four `Undecided`. The depersonalization spec's token registry gains a `Class` column on its 17 rows; the analysis-workspace standard, the public-versus-instance taxonomy and the depersonalization spec cite the standard instead of restating placement; and `core/standards/gate-efficacy-standard.md` gains a named-gap row for the new-surface checklist, whose `placement-member-census` population read 16 of 16 at its slice head.

**The surfaces (#8018).** Six governance surfaces carry 25 target-home statements, each with today's resolving path beside it, so every running hub still resolves hub state through `<OPERATOR_INSTANCE_HUB_STATE_PATH>`. The charter template's Classification Rule steps 1 to 3 defer platform working state and leak-risk content to step 4, which classes them as never Layer 1. An operator decision during Dev Testing settled their layer: they are Layer 2, and Rule 1 of the operations bridge names the platform's own runs and its installer as the writers of platform working state.

**The selector (#6627).** `corpus_home` sits last in `[adapters]` in `core/config/operator.toml.template`, shipped opt-in, and is declared in `core/config/operator-toml-schema.json` (`since` 5.03) and validated by `deploy.sh --check` Check 33's adapter loop. The record's release-corpus item records `tracked` as the corpus's home, reserves no non-tracked value, and names the release tooling's corpus resolver as the reader that will consult it. The new key, as an install that sets it writes it:

```toml
[adapters]
# placement selector: where the release corpus is homed (declared, not yet read)
corpus_home = "tracked"   # the only value: the corpus stays under release/releases/
```

**How it shipped.** Four cards on one branch, landed one at a time. The register landed at 38 rows against the design's 30; Dev Testing then found its completeness had to rest on a census of what tracked code resolves, not on a list, and it grew to 43 across the Dev Testing iterations. A scoped Plan Review return added the forty-fourth, naming the twelve hook-tier allowlists. At Execute, a sibling release had claimed both ADR-230 and v5.02 first, so the record was renumbered to ADR-231 and the version re-displayed as v5.03 before the merge. The release merged at `ef7a0ec5` and claimed `v5.03` with a signed annotated tag; the deployed rules mirror was re-laid, and the composed workspace charter was refreshed with `update.sh --surfaces-only` at the operator's instruction, because `deploy.sh --deploy` does not carry the charter template.
