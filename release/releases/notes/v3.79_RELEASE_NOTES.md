# Both link checkers now agree, and the deploy tooling stops repeating itself

2026-07-17 · v3.79

The platform checks its documentation links with two different tools, and until now they applied different rules — the same link could pass one gate and fail the other. They now share one rule, the last duplicated piece of deploy tooling was reduced to a single copy, and the one security hook that shipped without a test has one.

## What changed for everyone using the platform

- **A documentation link now gets one answer instead of two.** The two tools that check links across the platform used to resolve them differently, so a link written from the workspace root could be called valid by one gate and broken by the other. Both now follow a single rule: a link resolves next to the file it sits in, and a leading slash means the workspace root — the same way GitHub resolves links when it renders a page. *Why it matters:* a link is either broken or it isn't. You stop getting contradictory verdicts and stop chasing a failure that only one of the two gates can see.
- **Adding a security hook no longer means remembering to update a list somewhere else.** Each hook now names its owning document in its own header, and the build check reads those declarations directly instead of consulting a separate hand-maintained list. *Why it matters:* the step you'd forget no longer exists — add the hook, name its owner inside the hook, and the check finds it on its own.
- **Registering a new template source is now a one-place edit.** Two build tools each carried their own copy of the logic that locates template sources, kept in step by hand. They now share one copy. *Why it matters:* the two copies can no longer drift apart, and adding a source means editing one place instead of knowing to edit both.
- **Every security hook now has a test.** The one hook that had shipped without coverage now has one, bringing the set to twelve hooks and twelve tests. *Why it matters:* a change that quietly weakens a hook's protections now fails a test instead of reaching your workspace unnoticed.

## Known limits

- **Links written in the old workspace-rooted shorthand are now reported as broken.** Before this release, a link that named a top-level folder without a leading slash was quietly resolved from the workspace root no matter where the file sat. That shortcut is gone: write a leading slash for a workspace-rooted link, or write it relative to your own file. The nineteen links in the governance template that used the old shorthand were rewritten as part of this release and resolve to exactly the same pages as before — but anything newly written in the old style will be flagged.
- **The two checkers now agree on how a link resolves, but they still read different sets of files.** One of them still skips some release-notes and release-plan links it ought to follow. That is a separate known gap, tracked on its own and deliberately not widened into this release.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH. The whole release is a single merge commit; reverting it removes every change atomically, and each of the four pieces is an independent commit that can be reverted on its own. No data is migrated and no state is rewritten.

### Operator and engineering detail

**One canonical link-resolution rule (#1471)** — The two markdown-link checkers had diverged: one carried a bare module-prefix fallback that resolved any link naming a top-level module directory against the workspace root, while the other resolved relative-only and skipped leading-slash targets outright. One corpus, two verdicts, across two required gates. Both now implement one rule — resolve relative to the source file's directory; a leading `/` denotes the workspace root — recorded as ADR-085, which supersedes the fallback-establishing ADR-009. Retiring the fallback is the scope escalation the plan accepted: the nineteen workspace-rooted links in the governance template were rewritten bare to leading-slash (verdict-preserving — every target verified to resolve to the same file), and the doc-link maintenance protocol and rule were corrected, including the "matches GitHub rendering" attribution, which belongs to the leading-slash clause rather than the retired fallback.

**Hook ownership by enumeration (#1476)** — Check 37 previously derived hook ownership from two hand-maintained arrays inside the deploy script. Ownership is now declared by a line-anchored `# hook-owner:` magic comment riding each of the twelve `block-*.sh` headers, and Check 37 derives ownership by enumerating them; both arrays are deleted, and bypass membership is derived from the owner value rather than separately declared. The scope was larger than the original framing assumed — four fragment-less non-bypass hooks needed owners, not two, and both arrays had to go, not just one. Blast radius stayed at Check 37; the hook registry builder, its generated index, and Checks 9 and 38 are untouched.

**Resolver single-sourcing (#2158)** — The last duplicated template-sync resolver is extracted to a functions-only sourceable fragment modeled on the already-sourced instance-path library. Both the deploy script and the package builder source it and delete their inline copies; the function name is retained so the deploy script's three call sites are untouched, and the builder renames its single caller. A new regression test sources the fragment, asserts the original fixture case, and adds a drift guard, wired into the install-tests workflow. This completes an established single-sourcing trajectory rather than opening a new one.

**Hook-to-test parity (#1477)** — The missing `block-fragile-refs` test is a fixture-based test consistent with its sibling set and the shared test-runner contract. It runs the real hook at its deployed path so the co-located primitives and allowlist resolve naturally, and toggles the shared mode file through enforce/warn/off with restore-on-exit. It asserts a positive case per detector class plus the clean-inline, out-of-scope-path, wrong-tool, allow-marker, and bypass pass-throughs, restoring twelve-for-twelve parity.

**Version re-anchor (v3.76 to v3.79)** — This release was planned as v3.76. While it ran Stages 6 through 9, two concurrent releases claimed the intervening slots. Unlike the recent re-anchors on this log, the collision was caught by the Stage-12 pre-merge freeness detector rather than at the tag push, so the label was corrected on the branch before the merge and the merge commit carries the correct version. No v3.76 tag was ever cut by this release. The branch name and most commit subjects retain the as-authored v3.76 label — immutable history, recorded as accepted residual.
