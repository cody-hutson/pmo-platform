# Release bundling now gates on size and parse quality and records velocity

2026-06-18 · v2.02

The release pipeline's bundling stage now enforces capacity and sizing as checks rather than leaving them to written guidance. A milestone that is too big for its point band is caught at a named gate and routed to a split or a tighter merge; a release plan whose dependency graph parses below a quality floor is held before it advances; capacity is weighed so a higher-ceremony release counts for more; and the release log now records per-release velocity alongside the existing cycle-time field. Everything is additive — no existing setting, field, or behaviour is removed or renamed.

## What changed for everyone using the platform

- **An over-sized release milestone is now caught at a gate instead of shipping quietly.** Bundle planning sums a milestone's story points and checks the total against its size band; a milestone that runs over is routed to a split or a tighter merge rather than proceeding. *Why it matters:* an oversize bundle is surfaced for a decision at planning time instead of being discovered after the work is already in flight.

- **A release plan whose dependency graph parses poorly is now held before it advances.** The release planner's dependency-graph output is checked against a parse-quality floor of 90% of the eligible items; below that floor the plan stops until it is fixed or an override is recorded. *Why it matters:* a low-confidence dependency graph no longer reaches bundle and planning approval unguarded, where a wrong edge could mis-sequence the release.

- **Release capacity is now weighed by how much ceremony a release carries.** The bundle capacity check now counts a higher-ceremony release's story points for more against the same target band, using weights set per release class. *Why it matters:* a heavier, higher-risk release is sized closer to its real cost instead of being treated the same as a routine one of equal raw point count.

- **The release log now records per-release velocity.** Each release now records its planned-versus-delivered points, files changed, and how its work was allocated, next to the cycle-time field already in the log. *Why it matters:* the platform accumulates the actuals it needs to re-tune the capacity weights from real delivery data after a few releases, rather than leaving the starting estimates unchecked.

## Known limits

- The capacity weights and both new gate thresholds ship as starting estimates marked for recalibration after three releases; until then they are deliberate first cuts, not tuned values.
- The velocity field records "not applicable" for this release: a release that ships the velocity convention does not measure itself, so the first measured figures appear on the next release that carries sized work.
- The size gate and the parse-rate gate are checks layered onto the existing bundle and planning steps — the prior bundling behaviour is unchanged except for these checks running alongside it, and each gate allows a recorded operator override.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

### Operator and engineering detail

**#290 — risk-weighted capacity model + sizing consolidation (capacity TARGET)** — Adds a risk-weighted release-capacity sub-block to `bundle-composition-doctrine.md §3 Step 5`: `effective_pts = round_half_up(Σpts × class_weight)`, so a higher-ceremony release's raw points count for more against the same band. The previously-scattered sizing guidance (item-count vs point-band) is consolidated into that one cross-referenced source, and the rounding mode is pinned `round_half_up` at the definitional home so the producer (#290), enforcer (#294), and recorder (#281) cannot diverge at half-integer boundaries. The `release_class_capacity_weights` inline table `{routine 1.0 / novel 1.15 / cross-cutting 1.3 / hotfix 0.9}` ships as explicitly-labelled MEDIUM-confidence `[CALIBRATE-AFTER-3]` seeds in `core/config/platform-config.toml.template`, with the field documented in `core/schemas/platform-config-schema.md`, a Stage-3 A4 cross-ref, and a `deploy.sh` Check 33 config-field allowlist extension so the new field is monitored rather than silently uncovered (FM3).

**#294 — per-milestone size gate G3-15 (the enforcer)** — A `G3-15` gate in `core/schemas/gate-criteria-spec.md` asserts `effective_pts ≤ band-upper` at per-milestone altitude and routes an oversize milestone to the split / tight-merge disposition (non-dead-end routing), with the enforcement cross-cite added to doctrine §3 Step 5 — the same region #290 edits, so the two were serialized on one branch under D-C SINGLE. The gate carries a `[CALIBRATE-AFTER-3]` threshold and ships logged-but-not-blocking first per the established gate-shakedown precedent.

**#281 — RELEASE_LOG velocity instrument** — An additive velocity convention captures per-release planned-versus-delivered points, files-changed, and allocation actuals alongside the already-shipped `Cycle-Time:` field, codified in the new `release/references/standards/release-velocity-tracking.md` (field schema, the label→work-class map, explicit-N/A discipline, the grandfather/no-backfill policy, and the N=3 recalibration linkage) with the producing tool `release/tools/compute-release-velocity.sh`. The Stage-12/13 emit templates in `stage-12-execute.md`, `stage-13-close.md`, and `hub-spoke-bridge.md` gained the `**Velocity:**` field append step. Per the reflexive-pipeline-loop discipline this introducing release does not self-instrument — its own velocity field is recorded N/A and excluded from the calibration population; the field appears measured only on releases that close after this one.

**#293 — Mode-A parse-rate gate G3-14** — A `G3-14` gate in `core/schemas/gate-criteria-spec.md` holds the `release-planner` Mode A dependency-graph parse rate to a ≥90% floor against the conformant-bundleable denominator before Stage 3/4 may pass, with a documented operator override, and the Mode A acceptance-criteria cross-ref added to `release/skills/release-planner/SKILL.md`. The `gate-criteria-spec.md` schema is bumped v1.11 → v1.12 (additive — both gate rows plus the version-history block), and the gate-ID set is `{#293 → G3-14, #294 → G3-15, #292 → G3-16 reserved}` (G3-13 is the ADR-012 tombstone, excluded).

**Supporting decision — ADR-027 (Accepted)** — Records that the risk-weight axis keys on the shipped Release Class rather than a net-new per-issue Tier field: the Release Class already declares ceremony weight and is gate-enforced per milestone, making it the lowest-blast-radius canonicalization; a multiplier (not an additive budget) was chosen on scale-invariance, since ceremony cost scales with scope. The weights and both gate thresholds remain MEDIUM-confidence pending the three-release recalibration, and the velocity instrument's capture viability is still unproven (the sibling cycle-time field has not yet produced a measured datum) — an operator-awareness item, not a blocker.

This release closed as a combined Stage 12+13: no separate Stage 12 chore PR landed a DEPLOYED row, so the RELEASE_LOG row was authored directly in the VERIFIED end-state per the outcome-bound close. The `release-planner.skill` package was rebuilt at Stage 13 because #293 edited the skill, resolving the deferred package-freshness check.
