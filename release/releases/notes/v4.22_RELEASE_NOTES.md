# Release close-out now records every output it is meant to record

2026-08-11 · v4.22

Closing a release was quietly producing an incomplete record: several outputs the process promises were never written, and nobody could see they were missing. This release makes the close-out emit its full output set, and makes the parts that were unverifiable visible.

## What changed for everyone using the platform

- Closing a release now writes a close-class telemetry line into the release record. *Why it matters:* this measurement was specified but had never once been emitted in roughly thirty releases, so every past close recorded a completeness score of nothing at all.

- The close-out summary now reports the velocity and learnings steps alongside every other step. *Why it matters:* both steps were running and writing, but were absent from the summary — the audit trail understated what actually happened.

- The close-out summary is now built from what the run actually did, rather than from a separately maintained list of what it was expected to do. *Why it matters:* the old list had drifted out of step with reality twice, so the summary could report a step that never ran, or omit one that did.

- Rebuilding packaged skills at close now covers all three of the places skill sources live, not two. *Why it matters:* a skill whose only change came from the missed location shipped stale, with no signal that it had been skipped.

- Archive segments of the release log are no longer dropped when the close-out assembles its change set. *Why it matters:* writes routed into those segments were silently discarded, so the record on disk disagreed with the record the tooling believed it had written.

- The close-out preview now runs far enough to be reviewed before it is authorised. *Why it matters:* the preview used to stop almost immediately, which left the mandated review step with nothing to review.

## Known limits

- The completeness check that consumes the new telemetry line ships switched off on purpose. It has no data to check against until at least one release has emitted the line, so it stays dormant and says so in its own output rather than silently passing. Arming it is tracked as a follow-up (#5245).

- This release's own telemetry line is the first ever machine-written one, and one of its slots reads `N/A` by design — that value depends on a close-gate result the script has no way to observe.

- The close-out preview reaches its review gate but does not yet run to completion on a release closing for the first time. It now stops one step later than before, at the changelog projection, for the same underlying reason the original defect had. This was found by running the preview during this very close-out and is being raised as a follow-up rather than left implicit.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE**, confidence **HIGH**. Rollback is reverting the release merge commit, which restores the previous close-out behaviour in a single step. The corpus rows this close-out wrote would then need reverting alongside it; no external system holds state from this change, so nothing outside the repository has to be undone.

### Operator and engineering detail

Raw audit detail is in the `RELEASE_LOG` row and Deployment Log block for this release (`#closeout-output-completeness`).

This release is reflexive: the close-out tooling it repaired is the tooling that closed it, so its own close is the first live exercise of most of these fixes. Four behaved as designed on their first real run — the telemetry field emitted for the first time, the report derived itself from the executed-phase record, the archive-segment staging and the three-tree package rebuild both resolved correctly.

The preview fix is the honest exception. It removed the original abort and bought eleven phases of reachable review where there had been none, but a live preview run against this release — the first genuine not-yet-closed fixture the platform has had, since every prior attempt ran against an already-closed release and took an idempotent re-run branch — still halted before the end. The cause is the same mode-blindness the original defect had: a phase resolves an input before it branches on preview-versus-apply, against an input that preview deliberately never creates. The convention that fixes this was applied to two phases but not to the one that now aborts. Stage 8 flagged that the later phases had never run in genuine first-close form and accepted the risk on that basis; that flag was correct, and this is the third instance of the same defect class found on this path. The lesson recorded in the learnings block is to treat mode-blindness as a class and sweep for it, rather than patching whichever phase happened to abort.

One further detail worth carrying forward: the remedy text the close-out prints when the learnings capture is missing names a flag value the capture tool rejects. The correct value resolves through the release log, so the capture succeeds once corrected, but the printed instruction does not work as written.
