# The release pipeline can evaluate every stage hand-off from its own written rules

2026-07-02 · v3.50

This release completes the platform's stage-gate criteria surface: the rules that let the release pipeline decide whether each stage is done and ready to hand off to the next. Every stage transition can now be judged from the written gate specs alone, without an operator having to supply knowledge that lives only in someone's head.

> **Skip the rest** unless you run or maintain the release pipeline. This release changes how the pipeline evaluates its own stage gates; it does not change how you use skills, read status outputs, or work with project artifacts.

## Who this affects

Whoever runs or maintains the release pipeline — operators driving a release through its stages, and the pipeline agents that evaluate the stage gates. It does not affect people who only consume status outputs or invoke everyday skills; there is no user-visible behaviour change outside the release pipeline.

## What changed for everyone using the platform

No user-visible behaviour changes outside the release pipeline. The changes below are for operators and pipeline agents — see the operator detail below.

- **Every stage gate can now be scored from the written rules alone.** Two stages that previously had no gate IDs (planning and engineering) now have discrete, checkable criteria, and the late-stage gates that were structure-only now carry the judgment layer that matches them. *Why it matters:* a release run — and anyone auditing one — can confirm each stage is genuinely done from the specs, rather than relying on out-of-spec context that may not be written down anywhere.

## Known limits

- This is a governance and documentation release scoped to the release pipeline's own gate specifications. It adds and reshapes rules the pipeline reads; it deploys no new skill and changes no stored data.
- One gate-spec schema went to a new major version (a table gained a column and inline commands moved into it) — this is a formatting reorganization only; nothing that reads the spec needs to change.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

**MODERATE / HIGH confidence.** The whole release shipped as one branch and one merge, so rolling back is reverting the single release pull request (`git revert -m 1 <merge-sha>`). It changes governance and documentation only — no stored data, no runtime blast radius — so there is nothing to migrate back.
