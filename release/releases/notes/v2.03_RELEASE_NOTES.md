# A role-skill factory ships, plus the first two role agents

2026-06-18 · v2.03

The platform now has a repeatable way to build role-scoped agent skills from a single source document, and the first two agents built that way ship in this release: a Technical Program Manager and a Program Coordinator. The skill builder learned to read a "feeding document" — one structured description of a role — and turn it into a working skill, a set of shared building-block files every role agent draws on was authored, and the document format the factory consumes was locked so later role agents are built against a stable contract. Everything is additive — no existing skill, setting, or behaviour is removed or renamed.

## What changed for everyone using the platform

- **Two new role agents are available.** A Technical Program Manager agent ties a program's technical risk to its delivery plan, and a Program Coordinator agent keeps a program's trackers and status cadence in lockstep. *Why it matters:* you can ask for a program-level technical-readiness read or a tracker-to-status coherence check directly, instead of assembling that view by hand from the individual skills.

- **The two new agents reuse existing skills rather than re-implementing them.** The Technical Program Manager agent draws on the existing technical-review and delivery skills; the Program Coordinator agent draws on the existing tracker and daily-status skills. *Why it matters:* the new agents stay consistent with the skills you already use — a change to the underlying skill flows through rather than drifting in a separate copy.

- **New role agents can now be built from one structured description.** The skill builder accepts a single "feeding document" describing a role and produces the skill from it, drawing on a shared set of building-block files. *Why it matters:* the next role agents arrive faster and more uniformly, because the plumbing every role build depends on is in place and proven rather than rebuilt each time.

## Known limits

- This release builds the factory and two pilot agents that prove it; a third planned agent — a system-scope architect — was deliberately held back to a later release because a skill it needs to build on has not shipped yet.
- The document format the factory consumes is now locked: changing it after this release requires a governance update, so the two pilot agents stand as the reference for how a feeding document is shaped.
- The two new agents are operations-tier skills; they are deployed to the workspace by the operator's normal skill-deploy step, the same as any other skill.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH confidence. The release is additive only — two new skills, five new shared building-block files, a new input path in the skill builder, and one fail-closed deploy-check adjustment, with no existing file, field, or behaviour renamed. Whole-release rollback is `git revert -m 1` of the integration merge; the new shared files have no prior consumer to unwind. Standard 7-day rollback window.

### Operator and engineering detail

**#186 — Phase 0 factory foundation** — Stands up the plumbing every role-skill build depends on. `release/skills/pmo-skill-refiner/SKILL.md` gains a feeding-document consumption path as the pre-Interview input branch of Mode 2 (Create New), authored through `pmo-skill-editor` discipline (impact + coherence + regression on the migrated skill) with a `version:` bump. The 14-section `release/skills/pmo-skill-refiner/references/pmo-feeding-document-v02.md` format reference is authored as the contract the factory reads. Five `operations/skills/_shared/*.md` files (`behavioral-markers`, `anti-pattern-catalog`, `five-model-variations`, `deployment-strategies`, `lifecycle-gates`) are authored as the durable shared-resource surface every later role skill consumes. A fail-CLOSED `core/deploy/deploy.sh` Check 5(a) skip is added as an **exact-match `== _shared` guard** (not a fail-open `_*` wildcard) plus a convention comment, so the new `_`-prefixed sibling directory does not trip skill-roster-drift while a future stray `_`-prefixed directory still FAILs roster-drift unless explicitly allowlisted.

**#185 — Phase 1 pilots + feeding-document format lock** — Gated strictly behind #186's foundation (the format-lock chain: #185 cannot start until #186's plumbing exists). Two pilot skills are built via `pmo-skill-refiner` consuming their feeding documents: `operations/skills/pmo-technical-program-manager/SKILL.md` (composes `pmo-technical-analyst` + `delivery-engine`; modes Technical-Delivery Risk + Release-Readiness Orchestration) and `operations/skills/pmo-program-coordinator/SKILL.md` (composes `tracker-manager` + `daily-status`; modes Cadence Sync + Tracker Reconciliation). Both compose their constituent skills by invocation rather than re-implementation, carry the `skill_discipline_migrated_v10_2` migration flag so future edits route through `pmo-skill-editor`, are registered in the `OPERATIONS_SKILLS` roster, and ship their own `.skill` packages. After sign-off the feeding-document format is locked — a "post-Phase-1 changes require a governance update" note is added to `pmo-feeding-document-v02.md` — so the factory now reads a stable contract.
