# The pipeline is now choosier about what it accepts, builds, and extends

2026-07-26 · v3.94

This release adds four checks to the early stages of the platform's own work pipeline — where work items are taken in, triaged, and designed. Together they make the pipeline decide, on purpose, whether a piece of work should be accepted at all, whether it should be built new or by extending something that already exists, and whether the item's own text can be trusted. None of it changes everyday project work; it is intake- and design-stage machinery.

## Who this affects

- **Anyone filing or triaging work items** — triage can now push back on a net-new or sweeping item and record an explicit accept-or-not decision, instead of absorbing everything by default.
- **Anyone proposing new platform capabilities** — expect to be asked to check existing skills first, and to justify a brand-new component over extending an existing one.
- **Everyone else** — no action. Everyday project work is unchanged.

## What changed for everyone using the platform

- **Incoming work is no longer accepted by default (#779).** When a new work item looks risky to take as-is — for example one an agent drafted, or one that is brand-new and far-reaching — triage now runs an explicit "is this a fit?" check and treats *not accepted* as the starting point until the case for it is made. *Why it matters:* sweeping, net-new changes have to earn their way in, so the backlog stops accumulating work that was never really vetted.
- **An issue's description is no longer trusted just because the issue looks internal (#3303).** The same author check the platform already applied to issue *comments* now also covers the issue *body*, so instructions embedded in a description are only acted on automatically when the author is a trusted one. *Why it matters:* a work item written by an outside or unverified author can't quietly get the intake process to act on instructions hidden in its text.
- **Building something new now starts with checking what already exists (#792).** Before standing up a new capability, the platform has to look for an existing in-house skill (or a supported fallback) that already covers the need, and record that it looked. *Why it matters:* you get fewer redundant one-off tools and more reuse of what the platform can already do.
- **Proposing a brand-new file or component now requires justifying it over extending one (#1007).** At the design step, a net-new addition first has to show why extending something that already exists won't work. *Why it matters:* the platform grows by strengthening the pieces it has instead of piling up parallel new ones, which keeps it simpler to maintain.

## Known limits

- **Two of the new checks are active for work entering the pipeline from this release onward.** The acceptance-fit check (#779) and the extend-before-create check (#1007) start applying at v3.94; this release's own four items were finished before those checks went live, so they were not held to them.
- **The acceptance-fit check stays quiet for routine work.** It only raises the bar when acceptance is genuinely in question — an agent-drafted item, or a brand-new sweeping one — and passes ordinary human-filed items through without ceremony.
- **The trusted-author decision comes only from the platform's record of who filed the item, never from the item's text.** A description that *claims* to be internal — or embeds a marker saying so — does not make it trusted; that claim only raises scrutiny, it never grants trust.
- Report issues at https://github.com/cody-hutson/pmo-platform/issues.

### Operator and engineering detail

Full detail: RELEASE_LOG row `#deployment-log-v394` (v3.94), plan `release/releases/plans/v3.94-intake-and-gate-protocol-hardening_RELEASE_PLAN.md`.

Routine-class release, D-C SINGLE topology, P0 fully-serial — four issues shipped as delivery slices on one branch, one PR (#4030), 20 files (+633/−22), built in dependency + contention order #779 → #3303 → #792 → #1007. Two skills were repackaged in-PR: `intake-desk` (for #779's Mode C provenance emit) and `pipeline-triage` (for #3303's issue-body trust boundary).

**#779 — the Stage-2 acceptance-fit gate (G2-13, ADR-093).** Adds gate criterion **G2-13** (a scoped, conditional-binding acceptance-fit determination) to the gate-criteria schema, an **A4.6 Acceptance-Fit Determination** sub-step to Stage-2 triage, a provenance marker emitted by `intake-desk` Mode C on the agent auto-intake path, and a **"reject is the expected default"** doctrine in triage plus an "acceptance is not a default" doctrine in the intake style guide. The gate fires only under a scoped predicate — agent-authored, OR net-new/sweeping — and passes routine operator-filed tickets trivially. It ships **enforcing from v3.94** (the originally-authored shadow-then-graduate rollout was flipped to day-one enforcement at the Stage-9 GO gate on 2026-07-25); v3.94's own issues are exempt, since the gate binds issues entering Stage 2 strictly after the v3.94 merge SHA.

**#3303 — issue-body author-association trust boundary (A0).** Extends the comment author-association trust boundary (ADR-076) to issue-body ingestion by the auto-executing intake/triage surface, reusing the existing trusted-author set. It is ordered as an earlier triage sub-step than #779's acceptance check (A0 ⊳ A4.6), so trust is decided before provenance — defense-in-depth per the Stage-5 adversarial review. Trust is read solely from the repository host's author-association, never from the body or the provenance marker, so a spoofed marker only *raises* scrutiny (an anchor-less item is an expected reject) rather than conferring trust.

**#792 — module skill-consultation forcing function.** Adds a self-check → in-house-first / Anthropic-backup consultation step (a new skill-consultation map, an anthropic base-vs-build registry edit, and a release-process clause), so a build affirmatively consults existing skills before net-new authoring. Cites ADR-023.

**#1007 — extend-before-create gate (SR-G6, ADR-094).** Adds an affirmative "extend-before-create" criterion at Stage-5 Solutioning by extending the existing SR-G structural-gate family (as SR-G6) rather than minting a new Gate-5, with supporting doctrine in the build-philosophy discipline. Like G2-13, SR-G6 ships enforcing from v3.94. The three determinations stay distinct — accept-fit at Stage 2 (#779), extend-vs-build disposition at Stage 5 (#1007), and the structural-fit reconciliation (SR-G) — with no duplication.

The provenance marker an agent-authored intake emits — a scrutiny signal that *raises* (never lowers) the acceptance bar:

```text
<!-- provenance: agent-authored -->
```
