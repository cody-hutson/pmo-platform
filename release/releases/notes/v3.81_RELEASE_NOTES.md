# Theme-named releases no longer vanish from the release record

2026-07-22 · v3.81

Not every release carries a version number in its name — some are named for their theme instead. Until now those releases quietly left no trace in the changelog, the release index, or the digest, so reading back through the record skipped straight past them as if they had never shipped. They now emit the same complete record as any other release, and the version tooling underneath runs off one shared rule instead of four separate copies that could disagree.

## What changed for everyone using the platform

- **A release named by theme rather than a version number now shows up in the record.** Those releases used to be dropped from the changelog, the release index, and the digest — the work shipped, but the paper trail didn't. They are now written in alongside every other release. *Why it matters:* reading back through what shipped no longer skips releases without telling you. A gap in the record used to be indistinguishable from a release that never happened.
- **Their release notes are now reachable from the index instead of pointing nowhere.** The index entry for a theme-named release now links to where its notes actually live. *Why it matters:* following a release entry gets you to its notes rather than a dead end.
- **Every tool now judges a version number by the same rule.** Four separate copies of "what a valid version looks like" had drifted apart; they now all defer to one shared definition. *Why it matters:* a version number accepted by one step can no longer be rejected by the next, so a release stops stalling on two tools disagreeing about a name they should read identically.

## Known limits

- **The safety net restored in this release is a redundant one, not a new protection.** One of three checks that stop two releases claiming the same version number had been silently dead for some time. It is working again — but the other two already covered the same situation, so nothing that was previously getting through is being caught now. This is defence in depth being restored, not a hole being closed.
- **Release notes are still split across two layouts.** Notes for older releases were filed into per-major-version subfolders while newer ones sit flat in one directory, and the tooling reads the flat location. That split is a known inconsistency tracked separately in [#3118](https://github.com/cody-hutson/pmo-platform/issues/3118) and was deliberately not widened into this release.
- **Only the emit side of theme-named close-out was fixed.** Releases named by theme now write their record correctly going forward; earlier ones that were skipped are not backfilled by this change.

Report issues at https://github.com/cody-hutson/pmo-platform/issues.

## Reversibility

CHEAP / HIGH. The release is a single merge commit and reverting it removes every change atomically; each of the five pieces is an independent commit that can be reverted on its own. No data is migrated, no stored state is rewritten, and nothing already recorded is rewritten in place — the close-out change affects only records written from here on.

### Operator and engineering detail

**Version-less close-out emits the full output set (#2048)** — `automated-closeout.sh` under-implemented Stage 13 for theme-named / version-less milestones: the RELEASE_INDEX row, RELEASE_DIGEST entry, notes link, and CHANGELOG append were all dropped, so those releases left no corpus trace. The close path now emits a version-less marker into the INDEX and DIGEST, links notes at the `_unversioned` location, makes idempotency marker-aware so a re-run does not duplicate, and skips only the CHANGELOG (which is version-keyed by construction). The specific symptoms that opened the issue — a stale `.version` and two missing CHANGELOG entries — had already been resolved by an earlier corpus-completeness sweep, so the issue was re-scoped at readiness to the root-cause tooling gap.

**One version grammar, zero drift (#1800, #1801)** — `version-grammar.sh` has been the declared single source of truth for the version grammar and comparator, but pre-existing parsers had never been migrated onto it. `deploy.sh` Check 39 carried its own `sed` parser and now sources `version_parse` / `version_cmp` through a `set -e`-safe pattern; the close-out tool's `validate_version` was permissive of suffix forms and now defers to the canonical grammar. Worth noting for anyone touching that grammar: it admits three-component `vMAJOR.MINOR.PATCH` — the canonical hotfix form — so a tightening that rejected everything but two-part versions would have broken hotfix releases. The issue's second original target no longer existed and was dropped at readiness; its successor already sourced the SSOT.

**Dead DEPLOYED-row safety net restored (#2075)** — `claim-version.sh` reads the RELEASE_LOG to find versions that are tagged but not yet published, one of three inputs used to decide which version numbers are already taken. It read the State column at field 7; the table puts State at field 8 and Tag at field 7, so the test never matched and that input contributed nothing. The field index and its misleading header comment are corrected, with a fixture asserting a `DEPLOYED` row is now counted. The issue's decisive defect — over-exclusion of unpublished mainline tags — had already shipped separately, so this was trimmed at readiness to the residual: a redundant net, since the two primary inputs already cover the same window.

**Orphan lineage anchors removed (#1286)** — Two schema specs carried version anchors referencing a v7.5 lineage that is not part of the reachable release line. The stale anchors are dropped.

**Version re-anchor (v3.80 to v3.81)** — This release was planned as v3.80 and held at the deploy gate rather than merged. A cross-PR audit at Stage 4 had wrongly reported no competing releases in flight; the pre-merge check caught three, one of them ready to land and overlapping this release's largest file. That release was allowed to merge first and took v3.80. This branch then reconciled with it, re-ran both tooling self-test suites green, and had its label corrected on the branch before merging, so the merge commit carries the correct version. No v3.80 tag was ever cut by this release. The branch name and commit subjects retain the as-authored v3.80 label — immutable history, recorded as accepted residual.
