# A check that always failed now passes — with its finding intact

2026-09-13 · v4.64

A release-tooling check that had reported failure on eighteen consecutive runs of the main branch now reports success, while still printing the same finding it always printed. The finding was never the problem — not being able to tell it apart from a real one was.

> **Skip the rest** unless you read the conclusion of a CI check, or rely on one to stop a bad merge.

## Who this affects

- Anyone who reads whether a release-tooling check passed or failed
- Anyone who relies on those checks to stop a bad change from merging

## What changed for everyone using the platform

- **A check that always failed now passes, and still reports what it found.** One release-tooling job had concluded `failure` on eighteen main-branch runs in a row because a finding it is *supposed* to produce shared a conclusion with the findings that mean something is broken. It now concludes `success` and reports that finding in full. *Why it matters:* a check that is always red tells you nothing, so people stop reading it — and the one time it goes red for a real reason, nobody notices.

- **"Expected", "could not measure" and "clean" are no longer the same answer.** Two checks used to report all three states identically. Each now reports them separately. *Why it matters:* you can tell a check that ran and found nothing from one that never ran at all — previously both looked like success.

- **The annotation you actually see now says which kind of finding it is.** An expected leftover is shown in amber and leads with its own verdict name; a genuine regression stays red. *Why it matters:* the annotation list alone is now enough to triage a run, without opening the log to work out which kind of finding you are looking at.

- **A pass line that counted suppressed findings among the admitted ones now separates them.** *Why it matters:* a summary that folds hidden findings into the visible count overstates how much was actually checked.

## Known limits

- This release partitioned two checks, not the whole family. The identical collapse is still live in a sibling check and across several other jobs; those still report one conclusion for several different states.
- One suppressed finding still reports success on its own when it is the only finding present.
- The self-test roster does not yet cover the newly added conclusions, so those specific outcomes are not exercised by the automated suite.
- The reader-facing annotation change was verified for its own posture class; matching behaviour for differently-cased inputs was not tested.

Report issues at the [pmo-platform issue tracker](https://github.com/cody-hutson/pmo-platform/issues).

## Reversibility

CHEAP / HIGH. Revert the integration merge commit; the checks return to their prior single-conclusion behaviour. No data migration, no stored state to unwind. Reversible at any time.

### Operator and engineering detail

**The shape of the fix is a partitioned exit space, not a suppressed finding.** Both `deploy.sh --check-release-corpus` (Check 32) and `check-selftest-coverage.py --reconcile` previously folded several distinct outcomes onto a single non-failing status, which is what made an expected residual indistinguishable from a regression. Each now has an exit space in which `0` has exactly one producer, and the merge-blocking consumer was re-wired to a four-arm `case` in the same commit rather than left reading the old two-valued result:

```
exit 0   CLEAN        ran, found nothing
exit 2   INCOMPLETE   ran, could not measure everything   (advisory)
exit 3   SKIP         did not run
exit 1   BLOCKING     ran, found a real problem
```

For `#7440` the same principle is applied one level down: `mode_reconcile`'s eight assertion sites were replaced by a finding-class ledger over a five-member exit map, partitioned *inside* Arm F, so a by-construction residual and a genuine Arm B/E regression can never share a member. Severity is a total order, so a blocking finding always dominates a co-occurring residual.

**Adversarial design review found a fail-open inside the fix itself.** The first shape of the classifier would have treated a renamed or absent tool as an expected residual and concluded green — reproducing, in the remedy, exactly the class the release exists to close. Review caught it before it shipped; the closure adds an operand-existence check ahead of the expected-residual classification and a domain guard that fails toward blocking when the allowlist is empty. Both limbs were mutation-proven — each mutant fails its own test and no other — rather than asserted from a passing suite. This is recorded because a fix that reproduces its own defect class is the failure mode this release most needs to be honest about.

**What is carried, named rather than implied closed.** The sibling check carrying the identical collapse is unchanged, and six binary success-or-failure decision sites remain across four workflows; a suppressed finding in one arm still returns a non-failing status on its own; the self-test roster enumerates the older result codes and omits the four added here; the per-criterion acceptance layer remains inert with every criterion unclassified, and its summary does not reconcile with its own printed detail; the case-sensitivity of the classifier's posture lookup is untested; and the allowlist-absent writer has no test grip, so weakening it to a warning would still pass. Each was reviewed and deliberately carried, not missed.

**Two process observations from this release.** The Stage-9 transition that takes the integration pull request out of draft did not run, and was caught and remediated at the next stage by a guard that fired rather than passing silently. Separately, one release tool is tracked without its executable bit where its three siblings carry theirs, so invoking it directly fails; it runs correctly when invoked through a shell.
