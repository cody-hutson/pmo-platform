# The platform's own working files move out of your personal folder

2026-08-23 · v4.38

Three things created once at install and refreshed by nothing afterwards are fixed together here: the platform kept its own working files inside the one workspace folder you are entitled to treat as yours, a fresh clone left you to hand-build every operational folder, and a settings file never learned about settings added after you installed. This release gives the platform's files a home of their own, has a new install build the standard folder structure for you, and brings a settings file forward on every deploy or update.

## Who this affects

- **Anyone who already has the platform installed** — the platform's working files move to a new location, and moving your existing data there is a step you take by hand. See the next section.
- **Anyone installing fresh** — nothing to migrate. The new location and the standard folder structure are both created for you.
- **Anyone who chose a custom location for the platform's working files** — nothing changes. Your setting still wins, at the same precedence it always had.

## What you need to do

Only if you already have the platform installed. Copy first, delete last — the originals are your rollback.

1. **Copy** the platform's working-files folder to its new home: `${CLAUDE_WORKSPACE_ROOT:-$HOME/Claude}/personal/pmo-instance/` to `${CLAUDE_WORKSPACE_ROOT:-$HOME/Claude}/pmo-instance/`. Copy, do not move.
2. **Deploy** this release. The platform now reads from the new home.
3. **Verify** by looking, not by waiting for a complaint. Confirm the new home holds the personal-data list the pre-commit guard reads, carrying at least one real entry, and that your people roster and your saved release-run state are there too. An incomplete copy makes that guard quieter, not louder — which is exactly the failure this step exists to catch.
4. **Delete** the originals only after step 3 passes.

## What changed for everyone using the platform

- **The platform's working files have a home of their own.** Everything the platform writes on its own schedule — saved run state, activity logs, usage records, posture settings and your personal-data list — now sits in its own folder alongside your workspace's other folders instead of inside your personal one. *Why it matters:* your personal folder is yours alone again — the platform creates nothing in it, reads nothing from it, and writes nothing to it.
- **A fresh install now builds the operational folder structure for you.** Installing creates the nine standard tier folders and leaves a short orientation note in each, on both install paths. *Why it matters:* you start from the same structure as everyone else instead of inventing a layout by hand and finding out later that nobody else uses it.
- **Your settings file catches up when the platform adds a setting.** A deploy or an update brings a settings file that predates a new setting forward to the current set. *Why it matters:* a setting added months after you installed actually reaches you, instead of reaching only people who installed after it shipped.
- **Anything you set by hand survives the catch-up.** The catch-up fills in what is missing and never removes a key or overwrites a value you deliberately chose. *Why it matters:* you can let the platform bring your settings current without re-checking afterwards that your own choices are still there.
- **The routine health check now tells you when your settings are behind.** It reports a settings file whose option set is older than the platform's, and stays quiet when it is current. *Why it matters:* being out of date is something you get told, rather than something you discover when a feature does not work.
- **Ten settings arrived with the catch-up, across three new groups.** They cover which services the platform talks to for code hosting, tickets, knowledge and AI; which delivery method it assumes by default; and whether it runs a short reflection at the end of a session. *Why it matters:* these were previously reachable only by hand-editing, and every one of them arrives at a default that changes nothing until you change it.

## Known limits

- **The old location is no longer recognized by the personal-data leak check.** This release both taught the check the new location and retired the old one, so a copy you have not made yet leaves the old location unprotected on that check. That is why the copy comes before the deploy, not after it.
- **Deleting the originals is the point of no return.** Reverting this release points the platform back at the old location, but it does not move your data back. While the originals are still there, rollback is free; once they are gone, it is a manual restore.
- **Four usage-tracking scripts and their test fixture still spell the location themselves** instead of asking the one place that knows it. They were moved in step with this release, so they point at the new home; bringing them onto the shared lookup is separate work that has not happened yet.
- **The standard folder structure is only created where it is missing.** An existing layout is left exactly as it is — nothing is renamed, merged or removed, and running the install a second time changes nothing.

Report issues at the repository issue tracker.

## Reversibility

MODERATE / HIGH. `git revert -m 1` on the merge commit restores every file change at once. Two things it does not undo: your working files do not move back on their own (which is why the originals are kept until you confirm the copy), and settings already written into your file stay written — harmlessly, since each one sits at a default that changes no behaviour. Window: unbounded for the code; the data window closes the moment you delete the originals.

### Operator and engineering detail

**The settings key set is declared as data rather than spelled in code.** `core/config/operator-toml-schema.json` is now the single declaration of every key the generator emits — section, type, default, required-ness, and a per-key `since`. The generator derives its emit from it, the template is linted against it, and three hand-maintained lists (`MANAGED`, `MANAGED_SECTIONS`, `field_to_token`) became derived instead of curated — a net removal of three curation surfaces. The already-wired but hollow `schema_migrate()` reconciler is completed: it backfills a defaulted key silently, prompts for an undefaulted one, and returns exit 66 rather than hanging when a required undefaulted key is missing on a non-interactive run. `deploy.sh --check` Check 70 reports the delta, and it was verified with both arms — it fires on a deliberately stale fixture and stays silent on a current one. ADR-140 records the decision; the alternative considered and rejected was template-as-schema, which would have needed a fourth hand-rolled TOML parser to read a template declaring 40 keys against a generator emitting 16.

Three sections and ten keys shipped in a declaration-only diff — the same commit is the AC-5 proof that adding a field needs no per-field propagation code (zero changed shell lines across all ten). This is the shape they take in a generated config:

```toml
[adapters]
repo_host = "github"
ticketing = "github"
kb = "markdown"
ai_tool = "claude-code"
[methodology]
default_delivery_approach = "Scrum"
[session_retro]
enabled = false
mode = "warn"
sample = "almost_all"
min_tool_calls = 12
min_turns = 4
```

**The relocation was a 60-file surface, not a one-line default flip.** Measured at the release baseline: 60 files and 159 occurrences over a 1,741-file denominator, partitioned 14 immutable / 46 live. The resolver carried three executable literals rather than one — the base resolver, its explicit-workspace-root variant, and the evals-results accessor's own inline default — and six more executable defaults sat in the FinOps subsystem, none of which sourced the resolver. Shipping those after the flip would have left the resolver pointing at the new home while the usage store silently kept writing to the old one, with no error and no failing test, so they moved in lockstep. The order was detector-first throughout: nothing wrote the new form before the leak detector recognized it. ADR-141 records the placement decision and its supersession scope, and states the decision kernel plainly — platform-written runtime state is a peer of the operator's content, never a tenant of it, and placement is decided by who writes a path family rather than by how private it is.

**The PII guard needed hardening in the same breath, and an adversarial review is why it works.** The pre-commit guard resolves both its needle file and its severity dial from the relocating base, so on an un-migrated instance the flip would have invalidated the guard's data and its escalation path in the same instant — and worse, would have classified a configured instance as a fresh clone, taking the branch that cannot block at any severity. The relocation makes that guard quieter, not louder, which is the whole reason step 3 of the migration is a positive assertion. The first-specified hardening addressed only the branch predicate and not the dial, so it would have printed a blocking message and then exited zero; an independent adversarial review found that, and also found that any fixture asserting the intended behaviour could only place the dial where the hook still read it, so the fixture would have passed while the field case failed. The shipped hardening adds a legacy-home rung to the dial-resolution loop and rebuilds the fixture so that it can actually fail.

**Slice 9 — closing the both-forms window in the same release — shipped as built, on an operator decision that overrode the design.** Both the designing spoke and the hub recommended deferring it, because retiring the old form narrows the detector's predicate and strands any un-migrated instance on that surface. The residual is real and was not argued away; what makes accepting it safe is that the precondition is unobservable from inside the release — no gate here can see an operator's filesystem — so it converted to an explicit operator attestation at the Stage 12 Execute gate, with a single self-contained revert available if the attestation could not be given. The attestation was given, the slice shipped, and ADR-141 needed no amendment because it already stated the retired form is dropped in this same release. One spelling of the retired leaf survives on purpose, in a named accessor whose sole job is to tell an un-migrated instance apart from a fresh clone.

**The install validator had to move with the installer.** Its workspace-layout assertion required the personal area to exist; once the installer stopped creating it, that gate failed a healthy install. The failure was caught by an end-to-end regression that runs a real sandboxed install — not by any file-change matrix — and the assertion now targets the instance home instead.
