# Security architecture and data engineering now have owners in the skill suite

2026-08-08 · v4.17

Asking about the security properties of a design, or about a nightly load that dropped rows, now reaches something built to answer it rather than the nearest general-purpose skill. The architect gained security as a full third operating mode alongside real enterprise and data coverage, a new data-engineer skill ships, and the build reviewer gained a security review pack.

## What changed for everyone using the platform

- **Security architecture now has an owner that decides, not just reviews.** The architect skill carries threat modeling, trust-boundary placement, and security-control selection as a full third operating mode, reachable with phrases like "threat-model this design" or "which security controls this architecture owes". *Why it matters:* a question about the security properties of a design now gets a decision rendered against it instead of a critique of someone else's.

- **A new data-engineer skill owns pipelines and data correctness.** Ingestion and transformation build, data-quality assertions, source-to-target reconciliation, and idempotent replay — reachable with phrases like "the nightly load dropped rows" or "reconcile target row counts against source". *Why it matters:* pipeline and data-correctness work routes to a skill built for it rather than to the general software-engineering skill, which builds features and does not own whether the data is right.

- **Security review is now a selectable pack on the build reviewer.** Eight hands-on security dimensions across three areas — control hygiene, dependency and secret posture, and enforcer coverage — load alongside the three review packs that already existed, reachable with phrases like "run the vulnerability assessment" or "which of these CVEs are actually reachable". *Why it matters:* vulnerability triage, secret-exposure review, and penetration-test triage now run against a named checklist instead of ad-hoc judgment.

- **The architect's data and enterprise coverage is real rather than advertised.** Its description already claimed cross-component, middleware, and data architecture; this release built the capability behind that claim and added enterprise-altitude coverage alongside the existing system-scope work. *Why it matters:* asking where data is mastered, or for an enterprise-wide capability landscape, now reaches something that can answer instead of a promise in a description.

- **Adding an architecture domain no longer means adding a skill.** A recorded decision settles that a domain — security, data, or a future one — is a setting on the architect role, exactly as altitude already was. Three separate proposals for an enterprise architect, a security architect, and a data architect resolve to that one rule. *Why it matters:* you route to one architect rather than several with overlapping names competing for the same request.

## Known limits

- **The platform has no security or data practice guide of its own.** Its domain-practice library ships four guides and none of them covers either field, so the security mode and the data skill encode practice from general knowledge rather than from a platform source. The gap is named inside the security mode's own sourcing note rather than hidden, and it is tracked in [#4975](https://github.com/cody-hutson/pmo-platform/issues/4975).
- **Nothing checks that two skills do not claim the same output.** The ownership reconciliation this release owed was done by hand, because the check that would do it automatically is specified but not built. Tracked in [#4929](https://github.com/cody-hutson/pmo-platform/issues/4929).
- **The security capability landed as a review pack, not as its own skill.** Held to the platform's three-part test for splitting a role, the proposed security-engineer skill failed two of the three parts on enumerated evidence, so the capability moved home rather than being dropped. If review-time dimensions turn out not to reach hands-on remediation work, that is evidence to revisit the placement.
- **The new skill has no row in the per-skill output-contract schema.** No role specialist has one today, so adding a single row would have created a one-of-twenty asymmetry; it is routed to its own work item rather than solved here.

Report issues at [github.com/cody-hutson/pmo-platform/issues](https://github.com/cody-hutson/pmo-platform/issues).

## Reversibility

MODERATE / HIGH confidence. Reverting the release merge removes every file change in one operation, and re-running the deploy step drops the new skill from the deployed set and restores the two changed packages. The expensive half is the trigger vocabulary: once a dimension's phrases are live, requests route to them, so extracting a dimension into its own skill later is a cross-reference sweep plus a fresh collision audit rather than a revert. No data migration and no external state.

### Operator and engineering detail

**Security shipped as a mode rather than a split, on enumerated evidence rather than a judgment call.** The security-engineer proposal was run against the software engineer, the devops/SRE skill, and the newly-extended architect's security mode, and failed conjuncts two and three of the ADR-019 boundary test: six candidate write surfaces with none unclaimed, and the one genuinely distinct method — reasoning inward from adversary goals through trust boundaries to a control set — already allocated to the architect's third mode one wave earlier. The capability was delivered in full; only its home moved. Consequently that card owes no skill catalog row, no deploy roster entry, and no new package, and the routing-view counts move by **+1 skill, not +2** — a mechanical "add one everywhere" sweep over the count-bearing cells would have corrupted them.

**The durable output is the axis rule, not the three skills.** [ADR-127](https://github.com/cody-hutson/pmo-platform/blob/main/core/ADRs/ADR-127-domain-is-a-parameter-of-the-architect-role.md) records that the skill-boundary rule ranges over the **domain** axis exactly as it already ranged over **altitude**, so a future domain proposal starts from a recorded answer and a stated bar: a domain that cannot be authored to the depth of the existing modes is evidence to revisit the rule, not permission to ship it thin. Security is the flagged risk the record itself names — its method differs from cross-component design even where scope overlaps — which is why it ships as a full mode rather than a parameter.

**Trigger phrasing is domain-anchored, deliberately.** The architect's surface grows by six phrases and its frontmatter description was compressed rather than truncated to fit the character cap, so every previously-shipped trigger phrase survives byte-identical. Domain-anchored phrasing adds discriminating vocabulary; a uniform ownership scaffold adds shared vocabulary, and a prior pass over this corpus using one cleared every role-versus-function collision while creating five new role-versus-role collisions. The measured boundary against the within-component principal engineer tightens rather than loosens.

**The security pack is a fourth entry in an existing selectable set, not a new file shape.** The build reviewer's packs are selected by name at invocation; the shipped roster now reads:

```
copilot-builder    Copilot Builder Agent document packs
pmo-platform       PMO platform surfaces
security           AppSec / SecOps — 8 dimensions in 3 areas
generic            Any governed document pack
```

**The unsourced-domain flag traveled with the plan rather than being resolved inside it.** Stage 4 resolved the domain-practice provenance to the unsourced-domain flag instead of the pipeline-internal exemption, precisely because the deliverable content of the security and data cards must encode external practice the platform does not carry. The two missing guides are filed as their own work item rather than written as a rider on a skill extension.

**Registration writes were hoisted into one commit rather than serialized.** The skill catalog, the deploy roster array, and the new package plus its sidecar all landed atomically, which removed the contention between the parallel cards instead of scheduling around it. That the commit had to be atomic was demonstrated by falsification: pulling the catalog row while leaving the roster entry turns the currency check red naming the skill.

**ADR numbering resolved by merge order, which is governed behaviour rather than drift.** The decision record was allocated at the mainline next-free slot rather than one slot above a sibling branch's unmerged claim, because allocating at next-free is safe under every merge order and allocating above it is safe under exactly one. This release merged first and kept its number; the sibling that merged after renumbered its own record to ADR-128. The record carries its full renumber provenance, so in-release citations to the earlier numbers still resolve.
