# ADR-075 — Plan-verification executor: a versioned shared-executor contract over a thin check-family dispatcher

## Status
Proposed. Drafted at Stage 5 Solutioning for the executor card — the executor (last) card of the 70-verification-execution-surface release (foundation → schema → surface → executor). The Stage-5 design recorded that no ADR was strictly required (the parse/dispatch architecture is a single-reasonable-shape build-mechanics choice, and the Evidence-Grounding artifact is the durable name/format record), while explicitly flagging that if Collective Review judged the *shared-executor output contract* — the versioned evidence shape other stages come to depend on — to warrant a standing decision record, its natural home is a short ADR authored at Stage 6 first-commit alongside the `SCHEMA_VERSION` constant. This ADR is that record. It flips to Accepted at this release's Collective Review scope-lock (the ratification surface the release-ADR README names), consistent with how in-repo release ADRs set their own status. Recorded Proposed because that gate has not yet run. (Originating-issue provenance is carried in the `source_observations` frontmatter.)

## Context
The build/tweak stage of the pipeline (Engineering) requires a self-verification step that runs the release plan's declared checks and emits a per-issue PASS/FAIL evidence block into the PR body. Historically that step was manual — the agent read the plan and executed each check in conversation. The design question this ADR settles is not *whether* to automate it (that is the card), but *how the executor's boundary is drawn* so it (a) does not fork the two upstream surfaces the same release ships, and (b) does not become a brittle, unversioned dependency once multiple stages consume its output.

The executor consumes two surfaces authored earlier in the same release:
- the **Cross-Issue Acceptance Criteria** schema (authored at Stage 4 Planning; each entry is a testable predicate spanning ≥2 issues with a reproducible verification method) — the integration-check input; and
- the **runtime-suite selection map** + the **`test-run` event contract** (the runtime dispatch surface) — a dispatchable check family.

Both are read-only inputs. The executor is the *runner of their outputs*, never the definer of their contracts.

## Decision
1. **Thin dispatcher over a check-family registry — not a monolith, not a DSL.** The executor owns exactly *parse + dispatch + emit*. A parser reads the plan's Verification Plan (and Cross-Issue Acceptance Criteria) section into check records; a family classifier maps each record to one of five families (per-issue, integration, regression, sync, runtime-suite); a dispatch table routes each family to a small handler; a single emitter renders the evidence. A new check family is one registry row plus one handler function — no core rewrite. The two rejected alternatives were a monolithic grep-and-`eval` block (an arbitrary-code-execution surface over a governance document, and un-testable) and a full check-DSL the plan must author into (which forks a third surface and forces the schema and runtime cards to co-adopt a grammar).

2. **No `eval` of plan-derived strings.** A check method's command is extracted (from its backtick-quoted span) and run through a quote-aware tokenizer whose tokens are passed straight to an **allowlisted read-only verb** (grep / test / ls / head / wc / cat) as separate arguments — there is no shell to interpret a chained command, redirection, or substitution embedded in a plan string. This is the maintainability + stability posture the monolithic-`eval` alternative fails.

3. **Consume, do not re-implement — the two HARD edges are read-only seams.** The integration family reads the plan's Cross-Issue Acceptance Criteria section verbatim and runs each entry's declared method; the sync and regression families shell the existing deployed-copy check (`core/deploy/deploy.sh --check`); the runtime-suite family emits through the existing pipeline-event `test-run` writer (`release/tools/append-pipeline-event.sh`, subtypes `suite-pass` / `suite-fail` / `suite-skip`). The executor defines no schema, no diff engine, and no event shape of its own. A method that matches no family is a loud `ERROR` (never silently dropped); a declared-deferred method (`[DEFERRED …]` / "verification deferred to …") is an honest `SKIP`, never a fabricated `PASS`.

4. **Sole runner of Cross-Issue Acceptance Criteria methods; sole emitter of their verdicts.** The executor is the single place the release's cross-issue methods run. It emits each cross-issue verdict at Stage 6/7 in the Verification Evidence block; the Stage-9 release-integration check reads those emitted verdicts **read-only** (it does not re-run the method), with an evidence-freshness guard — a verdict is emitted against the final PR SHA, and a stale verdict is refreshed by re-running the executor. This single-runner rule is what keeps the cross-issue check from having two disagreeing execution loci.

5. **A day-one versioned output contract (`SCHEMA_VERSION`).** The emitted evidence shape (the per-issue `### Verification Evidence` table, the verdict enum {PASS, FAIL, SKIP, ERROR}, the check-record fields, and the roll-up) is the contract downstream stages consume. It carries a `SCHEMA_VERSION` constant from the first commit, so a future change to the evidence shape / verdict enum / record fields is a detectable schema bump rather than a silent break. The default `--format=md` output is a superset-compatible enrichment of the existing hand-authored Verification Evidence section — it preserves the section heading and per-issue PASS/FAIL tokens the Gate-6 verification-evidence check greps for; `--format=json` emits the same verdict set as an object array for CI. Exit code is `0` when all checks are PASS/SKIP and non-zero when any check is FAIL/ERROR (CI-consumable).

## Alternatives Considered
| Option | Decision | Rationale |
|---|---|---|
| (a) Thin dispatcher + check-family registry, with a versioned output contract | **Accepted** | Additive tool (delete to revert); a new family is one registry row + one handler; handlers *call* the deployed-copy check and the event writer and *read* the Cross-Issue AC section rather than re-encoding any of them; the output contract lives in one emitter behind a `SCHEMA_VERSION` so its cross-stage consumers see a bump, not a break. |
| (b) Monolithic grep-and-`eval` script | Rejected | An `eval` of plan-derived strings is an arbitrary-code-execution surface over a governance document; it hard-codes the five families into one un-testable block. Fails the maintainability and stability axes. |
| (c) Full check-DSL / new plan grammar | Rejected | Forces the schema and runtime cards (and every future plan author) to co-adopt a new grammar, forking a third surface and breaking the consume-not-reimplement constraint; over-builds against the stable per-issue-table + Cross-Issue-AC-section contracts that already exist. |
| (d) No standing decision record (rely on the A4 trade-off matrix + Evidence-Grounding artifact only) | Superseded by this ADR | Defensible for the parse/dispatch mechanics alone, but the *shared-executor output contract* is load-bearing across Stage 6 / Stage 7 / (via runtime evidence) Stage 8; `SCHEMA_VERSION` is meaningless without a documented contract to version against. Collective Review elected the ADR at Stage-6 first-commit — the case the Stage-5 design explicitly flagged. |

## Consequences
### Positive
- Stage-6 self-verification and Stage-7 Dev Testing gain a single plan-driven executor that emits the Verification Evidence block programmatically; a re-run and an A8 runtime run agree by construction because both go through the same `test-run` event path.
- The two HARD edges are read-only seams: whatever the schema and runtime cards finalize, the executor adapts at the section-locator / registry-row grain, never at the architecture grain — the design's answer to the forked-surface risk.
- The cross-issue check has exactly one execution locus (the executor) and one read-only consumer (Stage-9), so a cross-issue verdict cannot diverge between two runners.
- The output contract is versioned from day one, so the rising blast radius of a *future* contract change is a detectable schema bump, not a silent break for the stages that come to depend on it.

### Negative / cost
- The executor becomes a surface other stages depend on: CHEAP to add now, MODERATE-and-rising to change later. The `SCHEMA_VERSION` discipline is the mitigation, not an elimination — a contract change still requires updating the consumers, but it is now detectable.
- The per-issue and integration handlers execute only methods whose declared command uses an allowlisted read-only verb; a method authored as free prose with no runnable command is an honest `SKIP` (recorded), not a graded result — the executor is only as complete as the plan's methods are reproducible.
- The sync/regression families delegate to the deployed-copy check, which is a heavy full-workspace validation; a plan that declares several deploy-check-family methods runs it once per such method unless the run is memoized. (Memoizing the deployed-copy check within a single executor run is an additive refinement that changes no contract.)

## Reversibility
**CHEAP / Confidence HIGH.** The executor is an additive tool plus two cross-reference lines (the Stage-6 self-verification xref and the Stage-7 Dev Testing xref); nothing consumes it until those xrefs point at it. Whole-release rollback = revert the single squash-merge, which deletes the script and its tests and removes the two xref lines, restoring exact prior behavior. The `SCHEMA_VERSION` constant makes any later contract change a versioned, revertible step rather than an untracked drift.
